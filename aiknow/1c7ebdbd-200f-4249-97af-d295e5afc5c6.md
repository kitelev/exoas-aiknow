# SHACL validate: rm cache перед re-validation после file edits

При re-validation после vault file edits — обязательно `rm -f <vault>/.exocortex/cache/triples.json` перед запуском `validate schema`. Иначе stale cache читается как первый источник истины и продуцирует **phantom violations** — assertions против old frontmatter state, не текущего.

## Когда правило срабатывает

- Цикл point-fix SHACL violations (edit asset → re-validate to confirm)
- Любая re-validation после Edit/Write на vault file где предыдущий validate run уже был выполнен в той же сессии
- Diff baseline vs current для attribution (resolved vs new violations)

## Anti-pattern

```bash
# WRONG — может вернуть phantom violations (stale cache hit)
cd /Users/kitelev/vault-2025 && npx @kitelev/exocortex-cli validate schema --shapes-mode --format json > /tmp/current.json

# RIGHT — force fresh load from source files
cd /Users/kitelev/vault-2025 && rm -f .exocortex/cache/triples.json
npx @kitelev/exocortex-cli validate schema --shapes-mode --format json > /tmp/current.json
```

## Detection signal

Если diff baseline vs current показывает **NEW violations** focus которых = file который вы только что edited / created — почти наверняка это stale cache. Particularly suspicious когда:

- `propertyPath` в violation ссылается на field которого нет в текущем frontmatter
- `actualValue` указывает на target который был removed/replaced в текущем frontmatter
- Violation против только-что созданных файлов с unfamiliar property paths

Mechanical confirmation: `stat -f "%m %N"` for file vs cache — если file mtime > cache mtime, cache stale.

⛔ Сообщение одинаковое, лечения РАЗНЫЕ. Дискриминировать в этом порядке — первые два
дают ложную картину чаще всего, а последний вообще инвертирован:

| что проверить ПЕРВЫМ | если да ⇒ механизм | где |

⛤ **ЗЕРКАЛО, которое ищут дольше всего:** `sh:class` **МОЛЧИТ** («unresolvable ref, not

## ⛔ ВТОРОЕ молчание, и оно ТИШЕ первого: молчит не `sh:class`, а ВЕСЬ property-shape — субъект вне `Property_domain`

Зеркало выше — про **цель** (`sh:class` не проверил, потому что таргет не резолвится): проверка
запускалась и честно призналась, что не смогла. Второй случай радикальнее: **shape не запускается
вовсе**, потому что **субъект не принадлежит домену свойства**. Тогда в выдаче нет **ни строки** —
ни нарушения, ни предупреждения, ни «not validated».

- ⛔ **Следствие для ПРИЁМКИ, а не для диагностики:** дельта «0 нарушений / N предупреждений»,
  посчитанная по СОСТАВУ и с канарейкой, останется **посимвольно тождественной** до и после
  починки такого дефекта. Гейт зелен в обе стороны ⇒ он этот класс не покрывает **по построению**.
  Приёмочный критерий «фикс уменьшит число предупреждений ровно на столько, сколько починил» на
  таком дефекте **ложен**, и написать его легко: он звучит как строгий.
- ⚠ **Симптом-tell, ловится ДО работы одним грепом:** предиката, который ты собрался чинить, **нет
  ни в одной строке** перечня предупреждений — при том что битые значения у него точно есть.
  Не «повезло», а «шейп к этим субъектам не применяется».
- ✅ **Дискриминатор — прочитать `exo__Property_domain` у самого свойства** и сверить с
  `exo__Instance_class` носителей. Не совпало ⇒ SHACL здесь не детектор.
  ```bash
  grep -m1 'exo__Property_domain' <property-def>.md       # чей это домен
  # → затем класс носителя; расхождение = shape не применяется
  ```
- ✅ **Детектор для этого класса — SPARQL-РАСПРЕДЕЛЕНИЕ значений предиката**, а не SHACL:
  `SELECT ?v (COUNT(?s) AS ?n) WHERE { ?s <предикат> ?v } GROUP BY ?v HAVING (COUNT(?s) > 0)`.
  Битое значение видно как группа с адресом-`obsidian://vault/<uid>.md` **без каталога**; живые
  значения приходят symbolic-IRI. ⛔ `HAVING` обязателен: агрегат над пустым паттерном
  **фабрикует** строку `n=0` (`self-satisfying-metric-weak-verifier` §АГРЕГАТ над пустым паттерном).
- ⛤ **Класс шире SHACL:** всякий гейт, применяющий правило **по типу субъекта**, слеп к носителям
  не того типа. Спрашивать надо не «зелёный ли гейт», а **«применяется ли он к этим субъектам»**.

## ⛔ Считаешь ДЕЛЬТУ по составу — у предупреждения ДВЕ формы сообщения, и покрытие одной даёт ложную пару «добавлено/удалено»

Дельта «по составу» (а не только по счётчикам) требует свести каждое предупреждение к строке
`<focus> <Предикат> -> <target> [<ОжидаемыйКласс>]`. Класс извлекается из `message` — и форм у него
**две**, а не одна:

| форма `message` | как достать класс | доля (замер `vault-exodev`, 558 предупреждений) |
|---|---|---|
| `sh:class unresolvable-ref: … not validated against <IRI>` | `not validated against (\S+)` | **557** |
| `sh:class violation: … does not conform to expected class <IRI>` | `does not conform to expected class (\S+)` | **1** |

⛔ Регэксп по одной форме оставляет у второй **пустой** класс — и та же самая строка попадает
**одновременно** в ADDED (с `[]`) и в REMOVED (с `[<Класс>]`). Читается это как изменение данных.

- ✅ **Floor — альтернатива, а не второй проход:**
  `re.search(r'not validated against (\S+)', msg) or re.search(r'does not conform to expected class (\S+)', msg)`
- ⚠ **Редкая форма прячется за долей:** 1 из 558 не попадёт ни в какую выборку «посмотрю несколько
  сообщений». Перечисляй **формы**, а не примеры: `Counter(m.split(':')[0] for m in messages)`.
- ⛔ **Оба счётчика при этом ЗЕЛЕНЫ.** `0 / 558 → 0 / 558` не меняется, потому что строка не
  исчезает и не добавляется — она **переписывается**. Дефект виден ТОЛЬКО в составе, и только при
  сверке с чужим сохранённым перечнем (собственное «базлайн ↔ после» сокращает форму с обеих
  сторон и молчит) — `self-satisfying-metric-weak-verifier` §Оба floor'а выше ПРОХОДЯТ.
- ⛤ **`sh:class violation` в тексте ≠ нарушение в счётчике:** та единственная строка живёт в
  `warnings`, а `violationCount` = 0. Классифицируй по массиву (`data.violations` / `data.warnings`),
  а не по слову в сообщении.

### ⛔ Парс выдачи `--format json`: ключи лежат под `data`, и чтение ВЕРХНЕГО уровня даёт ЛОЖНО-ЗЕЛЁНОЕ `0/0`

Строка выше называет правильный путь (`data.violations` / `data.warnings`), но читается как совет
по **классификации** найденного. Недостающая половина — что происходит, когда путь взят неверно:
`json.loads(out).get("violations", [])` на верхнем уровне **не падает** (ключей там нет вовсе —
только `success` и `data`) и возвращает пустые списки ⇒ вердикт «0 нарушений, 0 предупреждений».

- ⛔ **Отказ тише обычного: ноль — ЖЕЛАЕМЫЙ ответ.** Проверка «а вдруг я читаю не то?» не
  запускается, потому что результат совпал с ожиданием (`self-satisfying-metric-weak-verifier`).
- ⚠ **Симптом-tell, ловится без чтения кода:** `warnings = 0` на большом vault. У `vault-exodev`
  база предупреждений — **сотни** (cross-vault unresolvable-ref); ровный ноль по ОБЕИМ величинам
  почти всегда означает неверные ключи, а не чистый граф.
- ✅ **Floor — распечатать ФОРМУ выдачи, а не угадывать:** `print(list(d.keys()))` перед разбором.
  Секунда работы; сразу видно `['success', 'data']`.

### ⛔ «Появилось N новых» ≠ «N записей несут признак источника»: новизна меряется ОТСУТСТВИЕМ в базовом множестве

Меряя вклад источника в дельту (смонтировал ассетспейс, включил шейп), естественно посчитать записи
с его признаком — у SHACL это `focusNode` внутри новой папки. ⛔ Признак отвечает «кто ссылается»,
а не «появилось ли»: цель, на которую ссылаются И новый источник, И старый, в списке **уже была**.

- ⚠ **Tell:** твой счёт больше чужого ровно на 1-2, и оба выглядят верными. ⛔ Не читать как
  «предшественник ошибся» — в роли приёмщика это уходит находкой ПРОТИВ исправной поставки.
- ✅ **Floor:** по каждой цели-кандидату собрать ВСЕ её `focusNode` и вычесть те, у кого есть хоть
  одна ссылка вне нового источника. Один проход по `warnings`, дискриминатор арифметический.
