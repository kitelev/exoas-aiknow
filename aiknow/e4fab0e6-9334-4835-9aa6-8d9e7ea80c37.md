# Pre-spawn parallel-session conflict check (mandatory before ANY child spawn)

## Принцип

Перед запуском **ЛЮБОЙ** дочерней Claude-сессии (`/spawn-nested-claude`, `spawn-session.sh`, orchestrate loops, meta-orchestrator waves, `/child-interactive-interview`) — **обязательно** сначала обнаружить текущие параллельные Claude-сессии и провести риск-менеджмент по **пересечению file/component scope**.

**Rate-limit — НЕ сдерживающий фактор** (лимиты аккаунта большие; user directive 2026-06-05). Единственный реальный риск конкурентного спавна — **конфликт на одних и тех же файлах / компонентах кода**. Даже когда сессии работают в изолированных git-worktree, оставшаяся сессия **фрустрируется на этапе merge**: её изменения придётся адаптировать под изменения другой сессии, и узнает она это **поздно** (merge conflict / rebase pain на этапе слияния), а не на этапе планирования.

## Когда срабатывает

Перед **каждым** спавном child — без исключений. Особенно критично когда:
- На машине уже есть активные child-сессии (свои ИЛИ чужого оркестратора)
- Несколько оркестраторов работают параллельно (ccgram pool, multi-session setup)
- Backlog-программа спавнит несколько children подряд (cap=N>1 или волны)

## ⛔ Mandatory pre-spawn gate

```bash
# 1. Discover active child sessions (любой оркестратор)
tmux list-sessions 2>/dev/null | grep -iE 'claude-child|claude-issue|claude-phase|claude-loop'

# 2. Для каждого: STARTED но ещё не EXITED? (= активен)
grep -E 'STARTED|PROGRESS|EXITED|COMPLETED' ~/.claude/audit/child-lifecycle.jsonl | tail -40
#    Active = последнее событие для этого child = STARTED/PROGRESS, НЕ EXITED.

# 3. Для каждого АКТИВНОГО child — определи его file/component scope:
#    - pane: tmux capture-pane -t "<name>:0.0" -p -S -50   (какие файлы/пакеты он трогает)
#    - worktree + branch: какой пакет/директорию правит
#    - orch owner: grep "<child>" lifecycle.jsonl → поле "orch"
#      (orch ≠ твой $TMUX_PANE → child ЧУЖОГО оркестратора; координируй, НИКОГДА не kill)
```

**Risk assessment — file/component overlap:**

| Overlap verdict | Action |
|---|---|
| Scope нового child **disjoint** от всех активных (разные пакеты/файлы/компоненты) | ✅ Spawn в параллель безопасен. Rate-limit не учитывать. |
| Scope **пересекается** (те же файлы/директории/компоненты) | ⛔ Conflict risk. Выбери: (a) **defer** новый child пока overlapping не смержится (sequential); (b) **re-scope** один из children чтобы не делить файлы; (c) **escalate** к user с деталями overlap. НЕ спавнить в overlap молча. |
| Scope активного child определить нельзя (pane нечитаем, нет worktree-инфо) | Считать potential overlap → defer ИЛИ escalate (консервативно). |

**Документируй решение:** какие активные сессии найдены, scope + orch owner каждой, overlap verdict, spawn/defer выбор.

## Как оценивать overlap дёшево

Не нужен полный AST-анализ. Достаточно сопоставить **top-level scope** обеих сессий:
- Пакет (`packages/core` vs `packages/cli` vs `packages/obsidian-plugin`) — разные пакеты обычно disjoint.
- Директорию/подсистему (`services/`, `infrastructure/adapters/`, `specs/step_definitions/`).
- Конкретные файлы из Scope-секции промпта нового child vs файлы, которые правит активный.
- Shared-сигналы: оба трогают `index.ts` barrel того же пакета, общий тип/интерфейс, общий config (`ci.yml`, `package.json`, `tsconfig`) → overlap даже если «основные» файлы разные.

Если пересекается только **read** (новый child лишь читает то, что активный пишет) — это slabый сигнал; всё равно отметь, т.к. читаемый код изменится под ним.

## Запреты

- ⛔ Спавнить child без pre-spawn discovery текущих параллельных сессий.
- ⛔ Гейтить parallel spawn по rate-limit (устаревший критерий — лимиты большие).
- ⛔ Спавнить в overlapping scope молча, надеясь что merge разрулится — оставшаяся сессия узнает о конфликте поздно и фрустрируется.
- ⛔ Убивать/трогать чужой active child (orch ≠ свой pane) ради освобождения scope — координируй (defer/re-scope), не kill.
