# YAML frontmatter: `: ` (colon-space) в unquoted plain-scalar значении молча ломает парс → дропает ключи

## Принцип

Значение frontmatter-свойства, записанное **unquoted plain-scalar** и содержащее `: ` (двоеточие-пробел) в середине текста, — **невалидный YAML plain-scalar** (`: ` зарезервирован как key-value разделитель). YAML-парсер тихо мис-парсит эту строку → в зависимости от парсера **дропает свойство ИЛИ соседние ключи** (не всегда fail-loud). В Exocortex-конвейере это приводит к **silent потере триплов** (напр. `exo__Class_superClass` не эмитится → класс не резолвится в SHACL-иерархии → фантомные `sh:class` violations на инстансах).

Симптом коварен: файл выглядит валидным, SHACL/wikilink-хуки не ловят (frontmatter «есть»), но конкретное свойство **отсутствует в store** (`?s <prop> ?o` → 0). Load-count может даже вырасти (часть ключей загрузилась), маскируя потерю.

## Когда правило срабатывает

- Пишешь frontmatter-свойство со **свободным текстом**: `exo__Class_description`, `exo__Asset_description`, любой prose-scalar.
- Текст содержит `word: word` (двоеточие-пробел): «X: participates», «serviceId: repairFolder», «см.: …», time-like «15: 30», ratio «2: 1».
- Особенно опасно, когда за prose-свойством или рядом идёт **несущий** ключ (superClass, Instance_class), который может быть дропнут.

## Что делать

- ⛔ Не класть `: ` в unquoted plain-scalar значение frontmatter.
- ✅ **Квотировать** значение с `: ` в двойные кавычки: `exo__Class_description: "Наследует X: участвует в Y"` — тогда `: ` литерален.
- ✅ Либо **убрать `: `** из текста (переформулировать без двоеточия-пробела: «X — участвует в Y»).
- ✅ Либо **вынести prose в тело** ассета (markdown body), оставив во frontmatter только структурные ключи (как `ems__TaskPrototype` — без `description`). Часто лучший вариант для длинных описаний.

⛔ **Заквотировал — ЭКРАНИРУЙ внутренние `\"`: лечение выше даёт ВТОРОЙ невалидный YAML, если в тексте есть свои кавычки.** `"…grounding 1bc1e938 ("Create action"), …"` рвёт double-quoted скаляр (`expected <block end>, but found '<scalar>'`), то есть floor этого правила ведёт прямо в следующий дефект.

- ⚠ **Tell при написании:** цитируешь чужое имя/команду ВНУТРИ квотированного значения. Типовые носители — прозаические поля (`covers`, `implementedBy`, `verifiedBy`), где цитата термина естественна.
- ✅ Внутри `"…"` → `\"`; проще — одинарные кавычки/«ёлочки» в самом тексте либо prose в тело (вариант выше).
- ⛔ **Дороже `: `-формы: `: ` роняет ОДИН ключ, вложенная кавычка — ВЕСЬ fence** ⇒ ассет «дропнут до классификации», и гейт, читающий корпус целиком, краснеет у ВСЕХ, а не у автора.
- ✅ Verify — `yaml.safe_load` фронтматтера, ⛔ не глазами: файл выглядит безупречно.

_Empirical 2026-09-10 (`exoas-ems-reqs/2821fdf0`, починка `622bdf0`): 2 строки, 6 неэкранированных `"`; `requirements-trace` падал INPUT-integrity на КАЖДОМ PR `kitelev/exocortex` — whole-repo блокер, найденный чужой сессией через свой красный CI._
- **Verify после записи класса/свойства:** `?s <несущий-ключ> ?o` в store НЕ пусто (напр. `SELECT ?o WHERE { ?class exo:Class_superClass ?o }`), либо SHACL 0 фантомных violations. `grep` frontmatter недостаточно — там ключ виден, а в store дропнут.

## ⛤ Addendum 2026-08-05 — ЗЕРКАЛО на стороне ЧТЕНИЯ: в СВОЁМ парсере frontmatter `\s*` после ключа перехлёстывает через `\n` и съедает первый элемент списка

Тело правила — про **запись** (`: ` в значении ломает YAML). Зеркало — про **чтение**: свой ad-hoc парсер frontmatter (regex вместо `yaml.safe_load`, типично в одноразовом скрипте инвентаризации/классификации) молча теряет данные из-за одного метасимвола.

- **Механизм.** Естественная форма «взять скалярное значение ключа»:
  ```python
  re.search(r"^%s:\s*(.+)$" % re.escape(key), fm, re.M)   # ⛔
  ```
  `\s` матчит и `\n`, поэтому на **многострочном** значении (YAML-список) регэксп перехлёстывает через перевод строки и захватывает **первый элемент списка** как якобы инлайновое значение:
  ```yaml
  exo__Instance_class:
    - "[[uid-A|ems__Task]]"      # ← попадёт в scalar() как значение
    - "[[uid-B|ems__Prototype]]" # ← и вся остальная часть списка потеряна
  ```
  Дальше `scalar()` возвращает непустое → ветка «это скаляр» побеждает → `multi()` не вызывается → **у мульти-значного ключа читается ровно ОДИН элемент**.
- ✅ **Floor: `[ \t]*`, а не `\s*`** — во ВСЕХ регэкспах, читающих frontmatter построчно (и в `scalar()`, и в детекторе начала списка):
  ```python
  re.search(r"^%s:[ \t]*(.+)$" % re.escape(key), fm, re.M)   # ✅
  ```
- ⚠ **Отказ ТИХИЙ и правдоподобный.** Ошибки нет, значение непустое, тип верный; теряется только **хвост** списка. На корпусе, где мульти-значные ключи — меньшинство, итог отличается от истины на единицы процентов и выглядит нормально.
- ⛤ **Ловится ТОЛЬКО заранее выведенным ожидаемым N** (`sparql-iri-form-pre-verify` §Addendum 2026-08-05). Эмпирика: классификатор дал `pn__DailyNote` = **310** плюс 53 файла в мусорном классе с обрезанным именем `- "[[pn__DailyNote`, тогда как независимый замер обещал 363. Мусорный класс — второй tell: **имя класса, начинающееся с `- "[[`, означает, что парсер прочитал строку списка как значение.**
- ⛤ **Практический вывод шире регэкспа:** ad-hoc frontmatter-парсер пиши на `yaml.safe_load` по срезу между `---`; regex оправдан, только когда важна скорость на десятках тысяч файлов — и тогда обязан быть **прогнан против известного N** хотя бы по одному ключу.

⛔ **`\s*` — не единственная поломка своего парсера: построчный разбор frontmatter врёт ещё ДВУМЯ способами, и оба тише.** (а) **Условие выхода** из сбора списка (`elif ln.strip() and not ln.startswith(" "): break`) обрывает перечисление на первом же непробельном соседе ⇒ список недосчитан целиком, а не на один элемент. (б) **Область поиска не ограничена frontmatter'ом** (`re.search(..., re.M)` по всему файлу) ⇒ предикат ловит `<prefix>__<Name>:` в **ПРОЗЕ** (типично — документирующий yaml-фенс в теле) и выдаёт документацию за данные.

- ⚠ **Tell АРИФМЕТИЧЕСКИЙ, не визуальный** (оба дефекта дают правдоподобные числа): счёт по диску обязан сойтись со счётом по графу. Замер 2026-09-12 (L1): построчный парсер дал **45** значений `dependsOn` против **86** рёбер в графе; он же объявил «объявление записано литералом» у ассета, чья строка живёт в прозе на 27 строк ниже frontmatter.
- ✅ **Floor: для ПЕРЕЧИСЛЕНИЯ frontmatter — `yaml.safe_load` границы `---…---`**, а не построчный разбор (`\s*`-патч чинит один симптом из трёх). Правило и так предписывает `yaml.safe_load` для **verify** — тот же парсер обязан быть и **читателем**.
- ⛤ Оба дефекта поймала **вторая величина в той же выдаче**, а не перечитывание: диск против графа. Аккуратность их не ловит — числа выглядят нормально.

## ⛔ Addendum 2026-08-07 — классификация по UID «где угодно во frontmatter» ловит TBox-ОПРЕДЕЛЕНИЕ СВОЙСТВА: у него тот же UID под `exo__Property_domain`

Аддендум выше — про парсер, который **теряет** данные (регэксп съел хвост списка). Соседний дефект того же слоя — парсер, который **находит лишнее**: классификация «этот файл — инстанс класса X», выполненная как подстрочный поиск UID класса по всему тексту frontmatter, матчит **определение свойства этого класса**. У property-def тот же UID стоит под `exo__Property_domain` (по смыслу «свойство применимо к классу X»), и подстроке эти два употребления неразличимы.

- ⛤ **Опаснее обычного ложного матча тем, что находка ВЫГЛЯДИТ валидной:** это настоящий ассет с настоящим frontmatter, просто другого рода. Дальше потребитель честно читает у него `<Class>_<field>` — их нет — и получает `None` по каждому полю, то есть **симптом смещён на другой слой**: «поле не заполнено» вместо «файл не того рода».
- ⚠ **Пока рядом стоит немой пропуск — дефект безвреден и невидим.** Он всплывает **ровно в тот день**, когда добавляют логирование пропусков: канал немедленно наполняется `unparseable`-строками про определения свойств. Тогда наблюдаемость, ради которой лог и заводили, обесценивается в первый же день — **канал, кричащий «волк», перестают читать**. ⇒ чинить оба вместе, иначе вторая правка убивает первую.
- ✅ **Floor: класс читать ТОЛЬКО под `exo__Instance_class`** — отдельным обходом, а не общим `parse_frontmatter`. Обход обязан покрывать обе формы (`exo__Instance_class: "`uid`"` инлайном и многострочный список), и именно поэтому он **отдельный**: типовой ad-hoc парсер отбрасывает строки с отступом, поэтому многострочный список читается у него **пустым** — то есть «правильный» ключ даст ложный ноль там, где подстрока давала ложную единицу.
- ⚠ **Симптом-tell:** в выдаче классификатора попадаются ассеты, чей `label` = **имя свойства** (`ems__Reminder_at`), а не имя сущности. Один взгляд на label отличает определение от инстанса.

### ⛤ ТРЕТИЙ сосед — ad-hoc парсер BASH: конец функции ≠ баланс скобок

Баланс `{`/`}` ломается **дважды**, и оба раза молча: функция «не закрывается» и **поглощает остаток файла**, приписывая себе чужие строки.

- ⛔ **python/heredoc внутри функции** несёт свои `{`/`}` ⇒ баланс не сойдётся никогда. ✅ Конец функции — строка **РОВНО** `}` в столбце 0; тело heredoc исключать (`<<-?'?TAG'?` … строка `TAG`).
- ⛔ **Однострочная с хвостовым комментарием** (`f() { …; }  # …`) не матчит `endswith("}")` ⇒ глотает соседей. ✅ `re.compile(r"\}\s*(#[^\n]*)?$")`.
- ⚠ **Tell АРИФМЕТИЧЕСКИЙ:** распознанных функций меньше, чем объявлений (`grep -c '^[a-z_][a-z0-9_]*() {'`). Печатать оба числа рядом — ловится до первого вывода находок.
