# Multi-agent RFC review ≠ user intent validation

## Когда правило срабатывает

Любой onto-RFC, который вводит/меняет:
- Новый класс артефактов (`exo__Class`)
- Domain / range / cardinality existing properties
- Положение AssetSpace ABox в системе (где живёт root asset)
- Semantic numbering / versioning (0.0.2 / 0.0.3 / ...)
- Naming conventions (bijection rules, exceptions)
- Foundational architecture concepts

## Запрет

⛔ Auto-execute Phase 1 (implementation) сразу после "PASS verdict" от `/rfc-quality-check` skill + 4-agent review. **Multi-agent review проверяет technical conformance с standards (SHACL, Noy-McGuinness §4.2-§4.6, SPARQL feasibility, migration realism, YAGNI scope) — но НЕ проверяет user intent.**

## Обязательная процедура

Перед `Phase 1` implementation любого onto-RFC из списка выше:

1. Сформулировать **3-5 атомарных вопросов** через `AskUserQuestion`, проверяющих:
   - Правильно ли AI интерпретировал scope ("public-ontologies — это catalog для foreign W3C, или meta-репо для всех assetspaces?")
   - Где должны жить новые ABox assets (vault submodule vs own repo)
   - Какая naming convention применяется (с exceptions или без)
   - Какой scope materialization (минимально / полностью / deferred)
2. Получить explicit answers от пользователя
3. Если user редиректит — обновить RFC до v2/v3 **до** implementation, не после

## ⛔ Addendum 2026-07-30 — интервью о ФОРМЕ артефакта ≠ интервью о МЕХАНИЗМЕ цели: спроси «что должно РАБОТАТЬ без тебя», прежде чем моделировать

Тело правила закрывает «панель проверила корректность, но не intent». Есть более коварный подвид: интервью **проведено**, 9 Vision Lock'ов зафиксировано, панель отревьюила — но все вопросы были про **ФОРМУ артефакта** («какие роли», «класс или свойство», «своя онтология или расширение»), тогда как реальная просьба была про **МЕХАНИЗМ** («чтобы это работало без меня»). Интервью тогда лишь *качественно уточняет неверную рамку*.

- **Tell в формулировке пользователя:** слова про **непрерывность / автономность / роль-в-процессе** — «чтобы разработка была **постоянной**», «я **фаундер**, а не вайбкодер», «чтобы **само** шло», «работало **пока я сплю**». Это требования к **петле исполнения**, а не к номенклатуре сущностей. ⛔ Гомоиконичный рефлекс («всякая user-configurable семантика → в vault-ассеты») тянет отвечать **моделью** (онтология ролей/этапов) — и это ощущается правильным, потому что не нарушает ни одного инварианта.
- **Floor (первый вопрос интервью, до любого моделирования):** «**что конкретно должно происходить БЕЗ твоего участия**, и что ты хочешь оставить себе?» — то есть где граница «я решаю ЧТО» vs «механизм делает КАК». Ответ разводит две принципиально разные поставки: (а) **модель** (классы/свойства — описывает мир) vs (б) **механизм** (петля/демон/оркестрация — меняет мир). Модель без механизма НЕ закрывает боль про автономность; механизму часто достаточно 1 тонкого класса вместо продуманной иерархии.
- **Проверка на себе перед спавном реализации:** сформулируй одной фразой, **что пользователь сможет НЕ делать** после поставки. Если ответ — «сможет запрашивать граф красивее» на просьбу «чтобы шло само», рамка неверна → вернись к интервью, не к панели.
