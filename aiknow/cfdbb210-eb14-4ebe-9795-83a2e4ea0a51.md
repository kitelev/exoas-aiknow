# Overnight orchestration design — prevent cold-start spawn cascade death

## Принцип

When designing a session that will spawn child processes overnight (user-asleep, no human supervision), **two independent failure modes** must be mitigated, not one:

1. **System-side death** (Jetsam memory pressure, OS cleanup) — accumulation pattern: high Monitor count, large context, multi-hour uptime, heavy parent
2. **API-side death** (Anthropic rate-limit cascade) — quota strain pattern: parent burnt mass quota recently, first spawned child gets orientation-phase silent rate-limit, loop interprets as 1 death not catastrophe, attempts retry, retry also dies, loop itself dies

Mitigations for these modes are **orthogonal** — addressing one does NOT address the other. Both must be explicitly designed in the prompt + tooling.

## Когда правило срабатывает

- Delegating overnight batch work via spawn loop (cap=N children, until-empty backlog patterns)
- Long-running orchestrator that will run while user sleeps with no chance to interrupt
- Restored sessions handing off work to fresh spawned executors
- After SIGKILL recovery — designing follow-up topology

## Required mitigations (apply ALL — orthogonal coverage)

### Type 1 — System memory pressure prevention

- ✅ Two-session split: heavy state-holder + light active-worker in separate standalone tmux sessions (see `[[6dddc3bf|two-session split mitigation]]`)
- ✅ Cap concurrent Monitor tasks at 3 max per active session (each = Node child RSS baseline)
- ✅ Cap concurrent children at 2 max per orchestrator (NOT 3-4)
- ✅ Standalone tmux per session, NOT ccgram pool (pool death cascade kills all tenants)
- ✅ Periodic checkpoint writes (every 5-15 min) — recoverable state if SIGKILL'd

### Type 2 — API rate-limit cascade prevention

- ⛔ **CRITICAL: 1 silent death = immediate pivot к orchestrator-direct mode** в cold-start scenarios. Не «3+ silent deaths in 1h» — first death is signal enough when parent quota strained.

  **Cold-start scenario** = ANY of:
  - Parent session has burnt heavy quota in last 60 min (multi-PR work, releases, multiple child spawns)
  - Other claude processes active on same machine (ccgram tenants, parallel user sessions)
  - Recent silent death events for unrelated children (last 30 min)

- ✅ Pre-spawn quota check: before first child spawn, **delay 5-10 min** if parent has done heavy work recently
- ✅ Stagger child spawns: minimum 5 min between child spawns (don't spawn 2 back-to-back at session start)
- ✅ Orientation-phase health check: after spawn, wait 60-90 sec post-STARTED ping. If no PROGRESS event by then → child silently rate-limited → pivot, don't retry
- ✅ Embed counter in prompt: track `consecutive_silent_deaths`; threshold = 1 in cold-start, 2 in steady-state

### Type 3 — Loop self-monitoring (covers BOTH modes)

- ✅ Persistent state file (continuous append, not on-wake-only): document each PHASE A/B/C/D transition + spawn attempts + outcomes
- ✅ Recovery instructions baked into prompt: «если ты сам умрёшь — restored session/user может resume через `claude --resume <session-id>` ИЛИ re-spawn с этим prompt'ом + state file»
- ✅ Notify-on-death mechanism: arm callback в parallel session (e.g. restored state-holder) если loop не ping'нёт в 30 min — restored session can wake user OR re-spawn loop

## Запреты

- ⛔ Single-mitigation thinking: «I capped at 2 → safe» — NO, this only addresses Type 1. Without Type 2 mitigations, first cold-start spawn cascade kills the loop.
- ⛔ Passive stop conditions: «stop if N deaths» — too late, loop already dead. **Active prevention** required (pre-spawn checks, orientation-phase verification).
- ⛔ Spawn-and-pray pattern: spawn child without verifying orientation success в первую minуту. Silent rate-limit deaths look identical to successful spawns в первые 60 sec.
- ⛔ Trust в loop prompt's «3+ silent deaths» as defense. **1 silent death in cold-start = catastrophe**, не сигнал.
