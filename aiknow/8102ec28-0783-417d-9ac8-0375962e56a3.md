# Skill discipline под context-budget pressure

## Принцип

Когда user triggers a skill via trigger phrase OR explicit `/skill-name` mention — **ALWAYS invoke `Skill` tool**, никогда не write markdown файл directly или not вызвать skill mid-session due к context pressure.

Под compact pressure (>70% context) skill invocation **становится ещё более** обязательным, не less. Skills имеют hidden mandatory steps that markdown shortcuts always skip.

## Дискриминатор (один вопрос)

> **Скилл НАЗВАН — в промпте, в директиве, в фразе пользователя?**

- **Назван** ⇒ вызвать `Skill`. Условие — **факт называния**, а не остаточная неясность: качество
  пересказа шагов ничего не смягчает, а чем пересказ полнее, тем меньше повода открыть источник.
- **Не назван**, но задача его тема ⇒ подобрать по описанию; два кандидата ⇒ спросить.

⛔ Контекстное давление дискриминатор не сдвигает ни на байт: под компактом hidden-шаги скилла
пропускаются первыми, поэтому bypass дороже повторного прогона, а не дешевле.

⚠ **Скилл структурно неприменим** (репо без CI, нет предмета) — это не разрешение пропустить:
перечисли его шаги и по каждому напиши «сделал» либо «неприменим, потому что …».

## Tell

- ⚠ Ты пишешь в тело PR / требования «скилл X это разрешает» или «X не требует» — и **не открывал**
  X в этом ходе.
- ⚠ Промпт назвал скилл и тут же **пересказал его шаги**, а ты исполняешь по пересказу: полнота
  пересказа — не замена вызову, а его самый частый вытеснитель.
- ⚠ Ты рассуждаешь «контекст близок к компакту, скилл съест больше» — это рационализация bypass'а,
  и она приходит ровно там, где скилл нужнее.
- ⚠ Ты собираешься написать markdown-«эквивалент» вывода скилла вместо его вызова: hidden-шаги
  такой эквивалент пропускает всегда.
- ⚠ Ты собрал строку вызова shell-скрипта **по интуиции** («наверняка `--name`»), не прочитав его
  разбор аргументов: catch-all свернёт флаги в позиционные и вернёт `rc=0`.

## Запреты

- ⛔ **НЕ** писать markdown файл «эквивалент» skill output вместо invoke skill — это всегда пропускает hidden steps
- ⛔ **НЕ** rationalize «context близок к compact, skill съест больше» — bypass дороже re-run (empirical reference ниже)
- ⛔ **НЕ** parse skill SKILL.md и manual emulate steps — invoke skill tool properly
- ⛔ **НЕ** оптимизировать на «speed under pressure» в ущерб skill discipline

## Mechanical pre-check перед skipping skill

Перед написанием markdown «вместо skill» — проверка:

```
1. Did user trigger phrase match a skill in skill list?
2. Have I invoked that skill yet в этой сессии для этой задачи?
3. If NO + NO → MUST invoke skill, не write markdown
4. If context >70% → skill invocation становится ещё more critical (compact risk скушает quality of manual workflow)
```

## ⛔ Дополнение к §A3b: «счёт автору промпта» верен, а его АДРЕСАТ зависит от ТОПОЛОГИИ — в цепочке равных исполнителей «перенести на оркестратора» есть совет без адресата

§A3b лечит непройденное ревью так: «назвать в промпте перенос ревью **на оркестратора** и прогнать
`code-reviewer` по коммиту ребёнка СЕЙЧАС». Это верно для **звезды** (оркестратор + дети): у совета
есть кому адресоваться. ⛔ В **цепочке равных** (конвейер этапов, очередь ролей, staged-pipeline)
оркестратора нет — каждый следующий актор такой же исполнитель с тем же шаблонным запретом
суб-агентов, — и floor молча становится неисполнимым.

- ⚠ **Симптом-tell — ПОВТОРЯЕМОСТЬ формулировки, а не отдельная её строка.** Каждый исполнитель
  пишет «внешнего ревью не было» **честно и корректно** (это и есть floor §ПРЕЕМНИК), поэтому по
  одной записи дефекта не видно. Видно **счётом**: одна и та же ось названа непройденной N этапов
  подряд ⇒ это свойство КОНВЕЙЕРА, а не N совпавших недоработок.
- ✅ **Floor: в цепочке ревью обязано стать МАНДАТОМ РОЛИ/ЭТАПА, а не строкой промпта.** Свежий
  читатель там уже есть — следующий актор берёт чужую работу со своим окном; недостаёт не носителя,
  а объявления «читать дифф предшественника» как предмета этапа. ⛔ Суб-агент при этом не нужен, и
  запрет снимать по-прежнему не надо.
- ⛔ **Заводя ревью этапом — объявить его ветку ОТКАЗА явно.** Этап с единственным выходом вернуть
  работу не может **по модели** и вырождается в «принять»; ревьюер без ветки отказа наследует ту же
  немоту (`autonomous-process-scope-filter` §ЧИСЛО доступных выходов этапа).
