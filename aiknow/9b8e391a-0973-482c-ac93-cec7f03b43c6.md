# Vault content-search: SPARQL/CLI-query FIRST — рефлекс `grep -r <vault>` тратит токены на блокировку хуком

## Принцип

Любой **содержательный/структурный поиск по каноничному vault** (`~/vaults/vault-{my,tbank,exodev}`) — «найти инстансы класса», «где ассеты со свойством X», «сколько задач в статусе Y», «какие ассеты ссылаются на Z» — идёт через **`exocortex-cli query "SELECT …"`**, НЕ через `grep -r`/`rg`/`ag`. Хук `~/.claude/hooks/dogfood-vault-search.sh` (PreToolUse Bash, Dogfooding §6) **БЛОКИРУЕТ** рекурсивный grep каноничного vault → каждый рефлекторный `grep -rl <pattern> <vault>` = **впустую потраченный tool-call + повторный заход** через SPARQL. Проактивно маршрутизируя в SPARQL с самого начала, эта потеря устраняется.

⚠ Хук **реактивен** (говорит только ПОСЛЕ блокировки); это правило **проактивно** (грузится в контекст → выбираю верный инструмент ДО грепа).

## Когда срабатывает

- Задача требует найти/посчитать/перечислить ассеты vault по любому критерию (класс, свойство, статус, ссылка, дата, label).
- Рука тянется к `grep -rl "<uuid-or-pattern>" ~/vaults/…` — СТОП, это заблокируется.
- Scope хука — ТОЛЬКО `~/vaults/` / `/Users/kitelev/vaults/`. Код-репо `/Users/kitelev/Developer/…` (тест-фикстуры `assetspaces/`) grep НЕ блокирует.

## Tell — два токена в одной строке (ядро накопленных floor'ов)

- ⛔ **COMPOUND-ЛОВУШКА — главная.** Одна vault-grep-часть роняет **весь** многосоставной вызов, включая легитимные соседние команды (`git grep` по коду, `ls -d` структуры, `find` по UID). Держать в РАЗНЫХ Bash-вызовах **не только «vault-поиск vs код-поиск», но и любой vault-путь vs любой рекурсивный grep — даже если grep нацелен на не-vault каталог** (напр. `~/dotfiles/.claude/rules`).
- ✅ **Группировать по ПРЕДМЕТУ ЧТЕНИЯ, а не по цели:** «всё, что трогает vault-пути» — в один вызов, «всё, что рекурсивно грепает» — в другой, **даже когда оба ответа нужны для одного решения**. Единство вопроса не даёт права на единство вызова.
- ⚠ **Симптом-tell до нажатия Enter:** в одной строке есть и `$V/assetspaces/…`, и `grep -r`. Наличие обоих токенов достаточно — не рассуждай, куда именно нацелен греп.
- ⛤ Полный список floor'ов по рецидивам и провокаторам (пять связок, хук матчит ТЕКСТ, compound без side-effects) — в теле: «Накопленные floor'ы» и «Floor'ы по конкретным задачам».

## Что делать вместо — матрица инструментов (что разрешено без блокировки)

| Задача | Инструмент |
|---|---|
| Content/структурный поиск по vault (инстансы/свойства/ссылки/counts) | `npx -y @kitelev/exocortex-cli@latest query --vault <v> "SELECT … WHERE { … }"` |
| Прочитать поле по **известному UID** (один файл) | `grep -m1 'exo__Asset_label:' <vault>/.../<uid>.md` (⛔ без `-r`) |
| UID → путь файла | `find <vault> -name '<uid>*.md'` (find не трогается) |
| Отфильтровать/распарсить вывод CLI | `…exocortex-cli query… \| grep …` / `\| python3 …` (это и есть dogfooding) |
| SPARQL реально не выражает (engine gap) | добавить трейлинг `# dogfood-fallback: <reason>` (сигнал = issue-кандидат) |

## SPARQL-грабли (чтобы первый запрос сразу сработал)

- **Enumerate инстансы класса:** `?s exo:Instance_class <…#<UID>>` часто **0** — объект instance_class эмитится **symbolic-IRI** (`ems#TaskPrototype`), не UID. Матчить `FILTER(CONTAINS(STR(?c), "<LocalName>"))` ЛИБО `find -name '<class-uid>*.md'`. См. `sparql-iri-form-pre-verify`.
- **Prototype-инстансы:** `?t exo:Asset_prototype ?p . FILTER(CONTAINS(STR(?p), "<proto-uid-8char>"))` — надёжнее literal-match (форма может быть file-IRI или literal).
- Status-фильтр: матчить обе IRI-формы (UID **и** symbolic-localname) — `sparql-iri-form-pre-verify` Addendum 2026-07-02.

## Накопленные floor'ы (каждый добыт отдельным рецидивом)

- ⛔ **COMPOUND-ЛОВУШКА — главная.** Одна vault-grep-часть роняет **весь** многосоставной вызов, включая легитимные соседние команды (`git grep` по коду, `ls -d` структуры, `find` по UID). Держать в РАЗНЫХ Bash-вызовах **не только «vault-поиск vs код-поиск», но и любой vault-путь vs любой рекурсивный grep — даже если grep нацелен на не-vault каталог** (напр. `~/dotfiles/.claude/rules`).
- ✅ **Группировать по ПРЕДМЕТУ ЧТЕНИЯ, а не по цели:** «всё, что трогает vault-пути» — в один вызов, «всё, что рекурсивно грепает» — в другой, **даже когда оба ответа нужны для одного решения**. Единство вопроса не даёт права на единство вызова.
- ⚠ **Симптом-tell до нажатия Enter:** в одной строке есть и `$V/assetspaces/…`, и `grep -r`. Наличие обоих токенов достаточно — не рассуждай, куда именно нацелен греп.
- ⛤ **РЕТРОСПЕКТИВА — провокатор №1** (5 из 16 повторов), и провоцирует она **в ДВУХ разных шагах**, а не в одном:
  - **Step 3a** (кросс-референс) требует «грепни правила» и «сверь артефакты в vault» подряд — два РАЗНЫХ предмета в одной мысли.
  - ⛤ **Step 1** (проверка артефактов на диске) — тоньше: там предмет ОДИН («мои артефакты»), но проверок две разного класса — **single-file** чтение по известному пути (`grep -c … <vault>/…/<uid>.md`, легально) и **vault-wide** счёт остатков (`grep -rl` — блокируется). Единство предмета делает единство вызова естественным, и вся связка падает, включая легальные однофайловые чтения.
  - **Практическое следствие (общее для обоих):** сначала выполнить ВСЕ grep'и по корпусу правил и все однофайловые чтения, и только потом — **отдельным вызовом** — vault-wide поиск, причём через **SPARQL**, а не grep. Не «не смешивать» (это сказано десять раз), а **разнести по порядку**.
  - ⚠ Для «сколько осталось X в vault» ответ всегда SPARQL + **канарейка** (тот же запрос без FILTER обязан быть непустым), иначе ноль неотличим от мёртвого запроса.
- ⛤ **Вторая связка-провокатор:** «SPARQL дал ноль → рука тянется перепроверить грепом». Ложный ноль (dual-IRI, `sparql-iri-form-pre-verify`) сам подталкивает к запрещённому инструменту.
- ⛤ **Третья связка-провокатор (08-09): PUSH-ISOLATION.** «Кто ещё пишет в этот vault?» (`concurrent-session-vault-write-isolation`) по построению требует **обоих** токенов в одной мысли: `ls -d <vault>/assetspaces/…` (какие mount'ы есть) **и** `grep -rl '<vault>' ~/Library/LaunchAgents/*.plist` (есть ли постоянный писатель). Провокация сильнее Step 3a: там два РАЗНЫХ предмета, здесь один — «этот vault», — поэтому единство вызова кажется естественным. ## Floor'ы по конкретным задачам (вместо рефлекторного грепа)

- **«Найти ассет по содержимому/свойству»** (в т.ч. **registry-дескриптор по URL репо**) → SPARQL по нужному свойству. ⛤ Он строго **лучше** задуманного грепа, а не «просто разрешённый»: возвращает субъект-IRI = готовый путь к файлу И полноту выборки (один запрос дал **все 47** дескрипторов — греп по шести именам этого дать не мог).
  <!-- Added by /session-retrospective 2026-09-10 (F1.1 e7c9e451) — root: рефлекс дал `grep -rl 'exo__AssetSpace_namespace: public'` по vault-my; хук заблокировал, а доменный инструмент отвечал точнее и дешевле SPARQL. -->
  - ⛤ **Дескриптор АССЕТСПЕЙСА (не любого ассета) — дешевле SPARQL: `resolve-deps`.** `node <cli> resolve-deps --registry <реестр> --self kitelev/<repo> --format json` печатает `self.uid` вместе с `namespace`, `source`, `dependsOn` и всем транзитивным закрытием ⇒ отвечает и «где дескриптор», и «что он тянет», одним вызовом без запроса. ⛔ `--format urls` печатает ТОЛЬКО зависимости (self исключён) — для uid нужен `json`. ⚠ Tell: ищешь дескриптор по namespace / имени репо и уже набираешь `SELECT ?s WHERE { ?s exo:AssetSpace_namespace … }` — сперва спроси, не ответит ли `resolve-deps`.
- **«Подсмотреть форму свойства у соседа»** → known-UID есть (типично в `/feature-sdd`) → **single-file** `find <uid>*.md` + `grep -m1/-E <props> <файл>` (**без `-r`**); нужен ЛЮБОЙ носитель свойства → `query` (`?s <prop> ?v`). ⛔ НЕ `grep -rl '<prop>' <vault-dir>/`.
- **«Сколько ассетов класса лежит на диске»** → `find <vault> -type d -name '<ns>'` → `ls` папки → `grep -m1 'exo__Asset_label:' <файл>` в цикле (single-file, без `-r`). Точнее грепа и не блокируется. ⛔ НЕ `grep -rl <class-uid> | wc -l` — и не SPARQL-`CONTAINS` по подстроке (ловит sibling-классы: `CONTAINS "bot#Message"` = 39 против точного IRI-матча 35).
- ⛤ **Оркестраторский нюанс:** роль оркестратора **системно провоцирует** рефлекс — независимая верификация claim'а ребёнка требует «быстро посчитать что-то в vault». Но именно здесь SPARQL строго лучше: он даёт тот же счёт **тем же движком**, которым мерил ребёнок ⇒ расхождение означает расхождение ДАННЫХ, а не разницу методов подсчёта. **Floor: тот же SPARQL, что у ребёнка, — не «свой» греп.**
## ⛤ Статистика по vault считается ДВИЖКОМ, а не питоном: `agg:` даёт 13 агрегатов

Вопросы «медиана / разброс / перцентиль / есть ли корреляция» рефлекторно уходят в
`python3` поверх выгрузки. Не нужно: движок их считает сам, и результат приходит тем
же запросом, что и выборка.

```sparql
PREFIX agg: <https://exocortex.my/ontology/agg#>
SELECT ?st (COUNT(?t) AS ?n) (agg:median(?len) AS ?med) (agg:percentile90(?len) AS ?p90)
WHERE { ?t ems:Effort_status ?st . ?t exo:Asset_label ?l . BIND(STRLEN(?l) AS ?len) }
GROUP BY ?st ORDER BY DESC(?n)
```

| одноколоночные | двухколоночные (с 16.233.0) |
|---|---|
| `median` · `variance` · `stddev` · `mode` | `corr(?x,?y)` — Pearson r |
| `percentile25/50/75/90/95/99` | `slope(?x,?y)` · `intercept(?x,?y)` |

- ⛔ **Набор перцентилей ФИКСИРОВАН**: `agg:percentile33` не существует и **бросает**
  (не интерполирует). Отказ **перечисляет зарегистрированные** — то есть сам служит
  справкой, и опечатка (`agg:medain`) самокорректируется.
- ⛔ **Двухколоночные отдают `NaN`, а не `0`, когда ответа нет** (n < 2 либо колонка
  константна). ⚠ Проверять на `NaN` **до** того, как трактовать r как результат: `0`
  означал бы «измерено, связи нет» — другое и ложное утверждение.
- ⚠ **Арность проверяется**: `agg:median(?x, ?y)` бросает, а не считает медиану по `?x`.
- ⛤ Полный справочник с проверенными примерами — `docs/reference/ExoQL-Aggregates.md`
  в репо exocortex.

**Empirical 2026-08-21:** тринадцать агрегатов существовали **без единой строки
документации** — ни в `docs/`, ни в этом корпусе; я узнал о них, только читая issue
#3994. Пока такой строки нет, следующая сессия снова посчитает медиану питоном.
