## Разборы

## §A1 ⛤ Addendum 2026-07-29 — push SCOPE = **per-vault** (НЕ device-wide); default push = `force:false` non-fast-forward rejection (no data loss); true CAS только в `flushOutbox`

Source-grounded (origin/main `5cb36d8e`, read-only spike для RFC `23e6082d` `$ExoSync-worktree`). Три факта, важных для рассуждений о ExoSync-контеншене:

1. **`exosync <sync|pull|push> --vault <V>` — PER-VAULT-scoped, НЕ device-wide.** Repo-enumeration = **один** коллектор `collectVaultSpecs(vaultPath)` (CLI, `exosync-parity.ts:159`) / `collectSyncRepoSpecs(this.app)` (plugin) — оба walk'ают файлы **ОДНОГО** vault, классифицируют `exo__AssetSpace`-дескрипторы (`classifySpaceDeclaration`), и `existsSync(V/localPath)`-gate'ят каждый. Пушит **ВСЕ** репо этого vault (⛔ **нет `--repo` селектора на push/sync** — `--repo` только на `quarantine resolve`). Per-vault watermark/manifest/mount-base/outbox/conflict-cache под `<V>/.obsidian/plugins/exocortex/`. Whole-repo `git grep origin/main` подтверждает: `collectVaultSpecs`/`collectSyncRepoSpecs` — единственные коллекторы, **device-wide-скана нет**. ⚠ **CLAUDE.md §ExoSync «оперирует ВСЕМИ materialized-репо устройства» — imprecise**: scope = per-vault, не per-device (contention = per-shared-repo across vaults, а не per-command-device-scope). Правка CLAUDE.md — с явного разрешения Андрея.
2. **Within-vault bundling:** `exosync push --vault <V>` бандлит ВСЕ pending-дельты V (любого процесса, редактировавшего файлы V — плагин, другая сессия). Два vault, монтирующих ОДИН remote-репо, — **независимые** watermark'и → пушат его независимо и рейсят на remote. → перед push проверять `exosync-parity --vault <V>`; если M2 > своих правок — push забандлит чужое (defer или изолируй).
3. **Default push = `force:false` non-fast-forward rejection (HTTP 422), НЕ compare-and-swap — но zero data loss.** Losing concurrent push **отвергается** (`restCommit.ts` step 4 `force:false`) → `isNonFastForwardError` (`SyncEngine.ts:445`) → D16 re-pull/retry → на retry-cap (`DEFAULT_MAX_PUSH_RETRIES`) contended-пути → quarantine sink (D17) **БЕЗ** advance watermark → losing-байты сохранены, **никогда не bundled/overwritten**, worst-case = bounded triage (не unbounded storm). True CAS (`expectedHeadSha` pre-check) — **только** в `flushOutbox` (`SyncEngine.ts:1950`). `MergeShaclGate` фейрит только на merge-пути (invalid merged result → quarantine) → **никогда не шипит bad merge**. ⚠ Nuance: losing **BULK** push пере-derive'ит **весь group** (rate-limit exposure, см. [[exosync-bulk-push-secret-scan-and-rate-limit]]) — не дёшево на 1 ассет.
4. **Практика:** для bulk-мутации под активным concurrent-writer — session-isolated **worktree-vault** (RFC `23e6082d`) устраняет within-vault bundling (#3a); **disjoint mount** → shared-repo race (#3b) vanishes; иначе — quiet-window (quiesce другого pusher) для large shared-repo bulk, existing D16/D17 для incidental.

## §A2 ⛤ Addendum 2026-07-30 — ЧУЖИЕ in-flight pending в репо-сотенанте блокируют push: пушь свой репо из ДРУГОГО vault, который его монтирует (если там M2 чист); `quarantine-pinned` файл push МОЛЧА пропускает ⇒ verify по СОДЕРЖИМОМУ, не по `pushed N`
<!-- Added by /session-retrospective 2026-07-30 — root: child phase1-onto-delta-bot, exoas-exodev держал 5-6 чужих in-flight pending -->

Addendum 2026-07-29 (§выше) фиксирует: push **per-vault**, **нет `--repo` селектора**. Практическое следствие, с которым сталкивается любая child-сессия, пишущая в ОДИН репо, пока родитель/сиблинги пишут в ДРУГОЙ репо того же vault:

1. **Проблема.** `exosync-parity` показывает M2-дельту твоего репо = ровно твои файлы ✓, НО в репо-сотенанте того же vault висят **чужие in-flight pending** (родительский проект, sibling-задачи, чужой RFC — mtime'ы «минуты назад», набор РОС между двумя парити-прогонами). Per floor «чужие pending → не пушь» push из этого vault запрещён (забандлит чью-то незавершённую работу), а per-repo селектора нет.
2. **⛤ Обход — push из АЛЬТЕРНАТИВНОГО mount'а того же репо.** Найди все vault, монтирующие твой репо: `ls -d ~/vaults/*/assetspaces/kitelev/<repo>`. Если в каком-то из них `exosync-parity` даёт **M2=∅ по всем репо** — сконвергируй туда свои файлы **байт-в-байт** (`cp` + `diff -q` verify; это НЕ дубль-ассет, это ровно то, что сделал бы там `exosync pull` — тот же ExoSync-репо, те же UID) → `exosync push --vault <этот-vault>` отправит **только твои файлы**, 0 чужих байт. Исходный vault сойдётся своим следующим pull (контент идентичен → без конфликта; проверено: parity после push показал твой репо `24/25 in parity`, конфликтов 0).
3. **⛤ `quarantine-pinned` файл push МОЛЧА пропускает** (частичный push). Если в альтернативном vault один из твоих файлов уже `quarantine-pinned` (pre-existing пин, не твой) — он **не входит в local delta** → уедет N-1 файлов. `Summary: pushed 2` при 3 подготовленных = именно этот случай. ⇒ **verify по СОДЕРЖИМОМУ каждого файла** (`gh api "…/contents/<path>?ref=main" --jq .content | base64 -d` + grep своих маркеров), НЕ по счётчику `pushed N` и НЕ по факту существования файла на remote (пин-файл там ЕСТЬ — но в старой версии). Оставшийся файл: не форс-резолвить пин автономно (§Принцип) — отдать владельцу vault'а/оркестратору, чей push его вынесет.
4. **Побочная выгода:** валидацию TBox-дельты против **инстансов** удобно прогнать в том же альтернативном vault (там они и живут) — SHACL baseline ДО конвергенции → после → `0 new` доказывает отсутствие self-brick'а на существующих инстансах предметно, а не по рассуждению.

## §A3 ⛤ Addendum 2026-08-08 — ПРИЁМ чужой дельты (`pull`) — тоже мутация состояния, и baseline для неё СНИМАЕТСЯ hard-link копией за секунды, а не прогоном

Правила «снимать baseline ДО» ([[vault-asset-creation]] §surgical-python, п. 4 выше) сформулированы для **своей** мутации — bulk-правки, push, конвергенции. Массовый `pull` под них не подпадает по формулировке, и потому baseline перед ним не снимают **никогда**: изменения-то чужие, «я ничего не делал». Но состояние vault меняется ровно так же, и после приёма 400+ файлов «SHACL = 6 нарушений» **неотличимо** от «было 6» и от «было 0, стало 6».

- ⛤ **Дешёвый носитель эталона — не прогон, а КОПИЯ ДЕРЕВА.** `cp -al <vault>/assetspaces /tmp/base-$(date +%s)` — хардлинки, секунды, диск не растёт. Она позволяет снять baseline **позже**, когда стало ясно, что он нужен: валидатор натравливается на копию и отдаёт до-состояние. Прогон SHACL по 9k файлов стоит минуты и требует знать заранее; копия не требует ничего.
- ⛔ **Сравнивать СОСТАВ, а не счётчик.** «6 → 6» согласуется и с «те же шесть», и с «шесть ушло, шесть пришло». Дискриминатор — `diff` отсортированных списков нарушений; равенство чисел при разном составе выглядит как чистый результат и им не является ([[self-satisfying-metric-weak-verifier]]).
- ⛤ **Дельта warnings объясняется правдоподобно и потому НЕ верифицируется — а объяснение оказывается НЕТОЧНЫМ.** ⛔ Мой первый черновик: «ссылки на несмонтированные в этом профиле **классы**». ✅ Замер (417 warnings vault-tbank, каждая цель сверена с индексом имён файлов): **409 (98.1 %) — цель есть ФАЙЛ, которого нет в этом vault**, он живёт в личном ассетспейсе вне рабочего профиля (`exoas-my/my-concepts/…`, анкер `$kitelev`); 4 — symbolic-IRI свойства (`ems#Effort_blocker`); 3 — файл **есть и смонтирован**, но тип не резолвится (dual-IRI). ⇒ дело **не в TBox**: классы как раз смонтированы (`exoas-public` в профиле), нерезолвимы **инстансы данных**.
  - ⛔ **Штатный вывод списка НЕ даёт — только счётчик** (`ℹ️ 417 warning(s) … not validated`). Проверить гипотезу можно исключительно через `--format json` → `data.warnings[].message`, откуда цель достаётся регэкспом `unresolvable-ref: <([^>]+)>`. Без этого «объяснение» остаётся непроверяемым **по построению**, а не по лени.
  - ✅ **Дискриминатор — форма IRI цели**: `obsidian://vault/<uuid>.md` **без пути** ⇒ ассет вне vault (построен из голого UID); `obsidian://vault/assetspaces/…/<uuid>.md` **с путём** ⇒ файл есть, причина другая (dual-IRI). Сверять с индексом имён — один `os.walk`, не 177 вызовов `find`.
  - ⚠ Практический вывод: такие warnings — **нормальное свойство профильной изоляции**, а не последствие pull. Они растут вместе с числом рабочих ассетов, ссылающихся на личные концепты, и «чинить» их нечем, пока профили разделены намеренно.
- ⛤ **Копию удалять сразу после сверки:** хардлинки безопасны на чтение, но следующая мутация в vault **разорвёт** их ровно у тронутых файлов ([[integration-test-revert-verify]] §Addendum 2026-08-07 (ХАРДЛИНК-копия перестаёт отслеживать источник)), и старая копия начнёт молча смешивать до- и после-состояния.
### ⛤ Уточнение 2026-08-03 — альтернативный mount почти всегда ОТСТАЁТ, а не «чист»; и настоящая гарантия — ОТСУТСТВИЕ чужого репо в его наборе, а не его parity

Пункт 2 выше ищет альтернативный mount с **`M2=∅` по всем репо**. На практике такого обычно нет: бот-vault'ы синкаются реже рабочего, поэтому их parity показывает **`pending-remote-*`** — это не грязь, а **отставание** (матрица §Addendum 2026-08-02: `−` локально `+` на remote ⇒ **pull**, не push). Отбрасывать такой mount как непригодный — ошибка: он приводится в годность одной командой.

- ✅ **Рецепт:** `exosync pull --vault <alt>` → он становится текущим (**0 quarantined** — проверять эту цифру, а не только «pulled N») → `cp` своих файлов + `diff -q` → `push`.
- ⛤ **Дискриминатор пригодности — НЕ parity, а СОСТАВ mount'ов.** Спрашивать надо «монтирует ли этот vault репозитории, где лежит чужой WIP?», и проверять `ls -d <alt>/assetspaces/*/*/`. Если чужих репо там **физически нет** — push оттуда не может их задеть **по построению**, независимо от того, что показывал parity минуту назад. Это sandbox-by-absence, и он строго сильнее «parity был чист» (parity — снимок, состав mount'ов — свойство).
- ⚠ Из этого следует и **обратное**: alt-mount, который чужой репо всё-таки монтирует, безопасным не становится от чистого parity — чужие файлы могут появиться там между проверкой и push.

  - ⛔ **Промах, который эта строка описывает, но не предотвращает: дискриминатор применяют к репо, ГРЯЗНЫМ НА МОМЕНТ ПРОВЕРКИ, а не ко ВСЕМУ составу mount'ов.** Смотришь parity → видишь чужой WIP в репо X и Y → выбираешь alt-mount, который X и Y не держит → считаешь вопрос закрытым. Это снова **снимок вместо свойства** — ровно та подмена, против которой написан пункт выше, просто применённая на шаг раньше.
  - ⛤ **`exoas-exoass` — постоянный живой риск, а не «сейчас чистый» репо.** Туда пишет **КАЖДАЯ** ретроспектива любой сессии (Step 6 роутит aiKnow-ассеты именно туда). Значит alt-mount, который его монтирует, с высокой вероятностью получит чужой файл в любое окно длиной в минуты. По той же причине живые: `exoas-exodev` (задачи, зеркала issue), `exoas-sessions` / `exoas-decisions` (петли).
  - ✅ **Floor:** спрашивать не «что грязно сейчас», а **«в какие из смонтированных здесь репо пишет ХОТЬ КТО-ТО ещё»** — и держать `exoas-exoass` в этом списке всегда. Полностью изолирующего alt-mount может не быть; тогда честный ход — **пере-снять parity непосредственно перед push** и признать остаточную гонку, а не считать её устранённой.
  - ⚠ **Остаточная гонка неустранима в принципе:** между parity и push всегда есть окно, а push не селективен. Поэтому цель не «доказать чистоту», а **сузить окно** и **проверить постфактум, что именно уехало** (`gh api "repos/<o>/<r>/commits/<sha>" --jq '.files[].filename'`). Уехало чужое → проверить его **завершённость** (не обрыв ли на середине записи) и сказать вслух, а не молчать.
  - **Empirical 2026-08-04** (воркер `alp-01f365f9`): parity показал чужой WIP в `exoas-decisions` (5) и `exoas-sessions` (2); `vault-bot-exodev` их не монтирует → выбран как alt-mount. Но он монтирует `exoas-exoass`, и за ~3 минуты между проверкой и push соседняя сессия дописала туда готовый aiKnow-ассет (`ab7282cc`) — он уехал вместе с моим файлом. Урон 0 (ассет **завершён**: 7120 байт, штатный футер `_Происхождение:`), но состав mount'ов был **напечатан в моём же выводе** и не прочитан.
- ⛤ **ПОСЛЕ push через alt-mount — сделай `pull` и в ИСХОДНОМ vault, иначе он покажет ТВОИ ЖЕ файлы как `pending-conflict`.** Исходный vault о чужом push не знает: его watermark остался до-пушевым, поэтому «локально изменено + на remote изменено» = **semantic divergence**. Симптом пугающий (конфликт на файле, который ты только что корректно отгрузил), а разрешается **сам**: содержимое-то совпадает — `exosync pull --vault <origin>` сводит без quarantine. ⛔ Не чинить это руками и не трактовать как реальный конфликт. Особенно бьёт при **повторном** заходе: отгрузил через alt-mount → доредактировал в исходном → parity исходного показывает конфликт вместо ожидаемого `pending-local-edit`. **Empirical 2026-08-03:** после второго alt-mount push два моих файла висели `pending-conflict (frontmatter differs, body differs)`; `pull` в `vault-exodev` → `pulled 1, quarantined 0`, дельта схлопнулась с 7 до 4 (остались ровно 4 чужих).
- ⛔ **Правишь файл, который УЖЕ правил кто-то ещё и НЕ ЗАПУШИЛ? Рецепт alt-mount молча ОТКАТИТ его правку.** Механика: alt-mount синхронизирован с **remote**, а чужая правка живёт только в исходном vault как `pending-local-edit`. Копируя туда «свою» версию, ты копируешь версию **remote + свои изменения**, то есть **без** чужих; push делает это состояние каноничным, и чужая правка исчезает, не оставив ни конфликта, ни quarantine — она просто никогда не была на remote.
  - ⚠ **Симптом-tell (дешёвый и однозначный):** гомоиконичная команда отказывает предусловием на alt-mount-копии, хотя в исходном vault она заведомо применима (`apply mark-done` → `Precondition not satisfied`, потому что там статус ещё `Backlog`, а в рабочем vault уже `Doing`). Отказ читается как «команда сломалась», а означает «я смотрю на устаревшую копию».
  - ✅ **Floor: сравнить ТРИ копии — исходный vault / alt-mount / remote — прежде чем править файл на alt-mount.** Расходятся ⇒ чужая правка не запушена. `grep -E '<ключевое поле>' <origin>/… <alt>/…` + `gh api …/contents/<path>?ref=main | base64 -d | grep …` — один вызов.
  - ✅ **Рецепт при расхождении: сперва принести версию ИСХОДНОГО vault в alt-mount** (`cp origin → alt`, `diff -q` для доказательства), и только потом накладывать свои изменения. Тогда push несёт чужую правку **вместе** со своей, а не поверх неё.
  - ⛤ **После push исходный vault сам НЕ сойдётся: `pull` его правку не перезапишет** (она локальная ⇒ пинится), и на следующем sync он попытается запушить старое поверх твоего. Довести до идентичности явно: `cp alt → origin` + `diff -q`, затем parity — твой файл обязан исчезнуть из списка pending. ⛔ Ограничиться `pull`-ом (как предписывает пункт выше для СВОИХ файлов) здесь недостаточно: там расходились watermark'и при одинаковом содержимом, здесь содержимое разное.
**Empirical (2026-08-03, разбор очереди решений RFC):** 6 моих файлов в `exoas-exodev`; `vault-exodev` нёс **62 чужих pending** (55 `exoas-decisions` + 6 `exoas-sessions` + 1 `exoas-exoass`) от **живого** воркера `alp-ffc2e19a` (спиннер тикал, суб-агент ревью в полёте) ⇒ push оттуда запрещён. `vault-bot-exodev` монтирует `exoas-exodev`, но **отставал на 42 файла**; ключевым был не его parity, а то, что `exoas-decisions`/`exoas-sessions` он **не монтирует вовсе**. `pull` (42 pulled, 0 quarantined) → `cp` 6 файлов (все `diff -q` identical) → `push` → **`exoas-exodev: pushed 6`, все прочие репо `pushed 0`** → remote-verify по содержимому: 5 RFC (статус + решение в теле) + 2 задачи. Cost: 1 pull + 1 cp-цикл; 0 чужих байт на remote.

**Empirical (2026-07-30, Phase 1 онто-дельта `$bot`):** 3 файла в `exoas-bot` готовы; `vault-exodev` — сотенант `exoas-exodev` с 5-6 чужими in-flight pending (parity-прогоны 15:35 → 15:44 показали рост 5→6) ⇒ push оттуда запрещён. `vault-bot-messages` (второй mount `exoas-bot`) — M2=∅ по всем 5 репо ⇒ cp 3 файлов (diff-verified identical) → `push` → `pushed 2` (третий — `quarantine-pinned` анкер, пропущен) → remote-verify по содержимому подтвердил 2/3; анкер отдан оркестратору. Побочно: SHACL в этом vault (35 инстансов `bot__Message`) 0→0 violations ⇒ отсутствие `minCount` эмпирически безопасно. Cost: 1 доп. parity + cp; 0 чужих байт на remote.

## §A4 ⛤ Addendum 2026-08-02 — тот же mount-drift на ЧТЕНИЕ: «в моём vault этого нет» ≠ «этого не существует»

Аддендумы выше — про **запись** (чей pending уедет при push). Зеркальная сторона того же факта «два vault монтируют ОДИН репо независимыми watermark'ами» бьёт на **чтении**, и там она тише: локальное отсутствие ассета выглядит как факт о мире, а не как состояние одного mount'а.

- **Механизм:** shared-репо (`exoas-exo` и любой другой) смонтирован в нескольких vault; каждый догоняет remote своим темпом. Ассет, созданный из vault A, физически появляется в vault B только после его pull. До этого SPARQL/`find` по vault B возвращают **ноль** — без ошибки, без предупреждения.
- ⚠ **Почему опаснее write-стороны:** отсутствие читается как «фича не отгружена / property-def не создан / RFC не реализован» и уходит в **вердикт**. Write-дефект ловится parity; read-дефект не ловится ничем — ноль неотличим от честного нуля.
- ✅ **Floor для negative-claim о shared-репо:** прежде чем записать «этого нет», проверить **другие mount'ы того же репо** — `for V in ~/vaults/*/; do …$V/assetspaces/**/<repo>/… ; done`. Присутствие в одном и отсутствие в другом = **drift**, а не отсутствие. Плюс, где есть авторитетный внешний сигнал (статус требования, merged PR) — он сильнее любого локального замера.
- ⛤ Смежно с [[verify-before-assert]] §negative existence claims: там недосмотр по **типам файлов / IRI-формам**, здесь — по **экземплярам монтирования**. Один и тот же класс «искал не везде, где живёт зависимость».

## §A5 ⛤ Addendum 2026-08-02 — pinnedPaths живут в WATERMARK-файле (CLI их не показывает); матрица LOCAL±/REMOTE± классифицирует за один проход; ⛔ «локальная сторона новее» — ложная презумпция; и состояние может РАССОСАТЬСЯ, пока диагностируешь

Практическое продолжение §2 («`quarantine list` пусто ≠ нет конфликта»). Когда `list` пуст, а синк явно стоит:

1. **Где смотреть.** Пины лежат в `<vault>/.obsidian/plugins/exocortex/exosync-watermarks.local.json` → `repos["<owner>/<repo>#main"].pinnedPaths`. Это **единственное** место, где виден масштаб — CLI их не перечисляет, `resolve` к ним неприменим. Один python-проход по всем `repos` сразу даёт счётчики по каждому репо.

2. **Классификация за один проход — матрица 2×2** (по одному `gh api "repos/<o>/<r>/git/trees/main?recursive=1"` на репо, ⛤ URL в кавычках — Грабля 5):

| локально | на remote | что это | лечение |
|---|---|---|---|
| `−` | `+` | **отставший vault**, НЕ потеря. Pin **защищает**: без него push из этого vault протолкнул бы удаление и снёс файлы у всех остальных | `exosync pull` (⛔ не push) |
| `+` | `−` | свежее локальное, которое пин **не выпускает** — типичный симптом «мои заметки не уезжают» | завершить синк |
| `+` | `+` | контентное расхождение либо уже сошлось | full diff, §5 |
| `−` | `−` | фантом (§3) | watermark, не автономно |

   ⛤ **Тот же UID запинен в ДВУХ репо (симметрично)** = незавершённый cross-repo переезд: одна сторона держит новое место, другая — старое. ExoSync такое не решает by design.

3. ⛔ **Не презюмировать, что локальная сторона новее.** Если переезд выполнялся из ДРУГОГО vault (или с телефона), новое состояние живёт на **remote**, а локальный vault держит **старьё** — и выглядит это неотличимо от обратного случая. Определять сторону по `exo__Asset_updatedAt` обеих версий + резолву `exo__Asset_isDefinedBy` (анкер прямо называет каноничную папку), а при живом пользователе — **спросить его**: одна фраза владельца дешевле любой археологии. Эмпирика ниже — ровно промах на этой презумпции.

4. ⛤ **Blast-radius: один застрявший переезд останавливает синк ЦЕЛИКОМ.** Страдают совершенно посторонние файлы — сегодняшняя заметка не уезжает, десятки ассетов не подтягиваются. Поэтому «пара застрявших зон» и «синк не работает» — один и тот же инцидент, и искать надо не там, где болит.

5. ⛤ **Перед предложением мутации — перечитать состояние.** Оно живое: фоновый auto-sync или pull из соседней сессии может разрешить конфликт, пока идёт диагностика. Дважды за один разбор файл, минуту назад бывший «LOCAL-OK», исчезал — и это был не сбой, а сходимость.

статуса у ассета НЕТ вовсе (свежесозданный) ⇒ задавать в `create`, готовая форма —

в alt-mount ⇒ **это правило**, §Уточнение 2026-08-03 (альтернативный mount почти всегда ОТСТАЁТ) ·
машина состояний исправна, перехода в ТЕКУЩЕЕ состояние нет ⇒ [[vault-asset-creation]] §A3.
