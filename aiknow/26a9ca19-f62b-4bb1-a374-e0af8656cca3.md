# Migration: pre-verify use case BEFORE moving files

## Принцип

При любой миграции файлов, которые участвуют в **discovery-фильтре** какого-либо runtime'а (Obsidian plugin, GitHub Actions, CLI scanner, npm linker, etc.) — **сначала** охарактеризуй фильтр (по какому критерию runtime находит файлы), **потом** двигай.

Discovery-фильтр может быть по:
- Path (hardcoded folder, glob pattern)
- isDefinedBy / parent ontology reference
- Specific class chain (Instance_class wikilink target)
- Filename pattern (UUID-named, label-named, etc.)
- Frontmatter property presence
- Submodule mount point

Если runtime filter уже работает на тех файлах что собираешься двигать — то значит он использует **некий** из этих критериев. Найти какой именно — **обязательно до миграции**.

## Чек-лист pre-migration

1. **Identify all runtimes** which currently consume the source files:
   - Plugin? CLI? CI workflow? Build tool?
2. **For each runtime — locate discovery logic in source code** (`grep -rn "<source-dir-path>"` или `grep -rn "<isDefinedBy-UID>"` в repo).
3. **Predict failure mode under proposed migration:**
   - If runtime filter = source-path-prefix → migration that changes path will break discovery.
   - If runtime filter = isDefinedBy UID → migration that updates isDefinedBy will break discovery.
   - If runtime filter = class chain — check if class wikilink resolves at new location.
4. **Smoke-test predicted failure mode WITHOUT committing the migration:**
   - Create a worktree / branch
   - Move files locally (no push)
   - Run the runtime against new state (Obsidian Reload, CLI invocation, CI workflow_dispatch on branch)
   - Verify discovery still works (or document expected breakage + planned fix)
5. **Only commit migration after smoke test confirms** runtime still finds files OR a planned fix is queued (e.g., plugin PR to broaden filter, CI workflow update).

## Дискриминатор (один вопрос)

> **По какому КРИТЕРИЮ runtime находит эти файлы — и могу ли я показать строку, где он это делает?**

- **Могу** (path-prefix · `isDefinedBy` · цепочка классов · шаблон имени · ключ frontmatter · точка
  монтирования) ⇒ видно заранее, переживёт ли критерий перенос.
- **Не могу** ⇒ фильтр неизвестен, а «на уровне файловой системы перенос чистый» — догадка о чужом
  коде, а не свойство операции.

⛔ **«Файл тот же, изменилась только папка» дискриминатором не является:** discovery-фильтр почти
всегда несёт **неявное** допущение (префикс пути, корень онтологии, соседство с анкером), и ломается
именно оно — молча, без ошибки, с обнаружением через жалобу пользователя.

⚠ **Второй вопрос — к ПОПУЛЯЦИИ, и он ортогонален первому:** я двигаю «файлы из каталога» или
«множество по ПРИЗНАКУ»? Контейнер — место **обнаружения**; если критерий приёмки звучит «в папке
X пусто», он меряет контейнер, а не предмет.

## Tell

- ⚠ Ты собрался двигать или удалять и **не открывал** код, который эти файлы находит.
- ⚠ Радиус удаления померен **одним** запросом по предикату: он не видит ни body-упоминаний, ни
  option-set, ни второй IRI-формы — ноль тут гипотеза, а не факт.
- ⚠ Ты снял скрипт после caller-грепа, **исключив `.md`**: шаги скиллов — полноценные callers, и
  промах всплывёт при следующем их запуске.
- ⚠ Предикат приёмки удаления — `-d` или плоский листинг: он судит глубину 1, а подпапки разрешены
  ⇒ ложно-зелёный совпадает с желаемым и потому не перепроверяется.
- ⚠ Доля «дефектного» неправдоподобно велика (полкорпуса) — сначала чини **замер**, а не корпус.
- ⚠ Декоммиссия идёт **по префиксу имени**, а область компонента шире префикса: имя — корреляция,
  несущее свойство лежит в другом месте.

## Запреты

- ⛔ Migrate files referenced by a runtime without first locating the runtime's discovery logic — even if "file system level" the move looks clean.
- ⛔ Assume "filesystem move = semantically equivalent" — runtime filters often have implicit assumptions (path-prefix, ontology root, etc.) that break under move.
- ⛔ Discover the break post-closure через user complaining about lost UI feature. Pre-verification is cheap (15 min); post-closure correction expensive (revert commit + bump submodule pointers × 2 + verify + retrospective on lost trust).

## Mitigation hierarchy

If pre-verification was skipped and migration broke a runtime:

1. **Detect early** — run target use case smoke test BEFORE closing the issue/project.
2. **Revert if discovered post-merge** — `git revert <migration-commit>` is usually safer than forward-fix when discovery filter is in someone else's code.
3. **Forward-fix only if** the runtime's discovery filter can be updated by you (e.g., plugin code change to broaden acceptance) AND time is on your side.

## ⛔ Декоммиссия по ПРЕФИКСУ ИМЕНИ сносит компонент, чья ОБЛАСТЬ шире префикса — и молчит двое суток

Сворачивая подсистему, набор к удалению собирают **именем** (`alp-*`, `legacy-*`, `v1-*`) — это
дёшево, механически и почти всегда верно. ⛔ Почти: префикс описывает **происхождение**
компонента, а не его **область применения**, и они расходятся ровно у тех компонентов, которые
оказались полезны шире, чем задумывались. Такой компонент сносится вместе с подсистемой, хотя
его потребитель к ней отношения не имеет.

- ⚠ **Отказ не всплывает там, где сделан.** Потребитель — обычно фоновый джоб; он падает
  штатно, пишет в свой журнал и **не эскалирует**. `launchctl list` показывает его живым
  (запись есть, интервал идёт), и единственный след — ненулевой `rc` в колонке, которую
  никто не читает. Замер 2026-08-21: `rc=2` у одного джоба из 28, 1440 записей `BROKEN` в
  сутки, двое суток, ноль уведомлений.
- ✅ **Floor ПЕРЕД удалением набора по префиксу: у каждого файла спросить не «чей он», а
  «кто его зовёт».** Одна команда, и она же даёт ответ:
  ```bash
  for f in <набор>; do n=$(basename "$f")
    grep -rl "$n" ~/.claude/bin ~/.claude/hooks ~/Library/LaunchAgents ~/dotfiles/scripts 2>/dev/null \
      | grep -v "$n" | sed "s|^|  $n ← |"; done
  ```
  Нашёлся потребитель **вне** сносимой подсистемы ⇒ компонент не её; переименовать в
  нейтральное и оставить, а не удалять.
- ⛤ **Обратный детектор — ПОСЛЕ декоммиссии, ловит то, что floor пропустил:** джобы, чья
  программа не существует, и живые скрипты, зовущие снесённые файлы. Стоит один проход и
  находит ровно этот класс:
  ```bash
  for p in ~/Library/LaunchAgents/*.plist; do prog=$(python3 -c "import plistlib;a=plistlib.load(open('$p','rb')).get('ProgramArguments',[]);print(a[0] if a else '')")
    [ -n "$prog" ] && [ ! -x "$prog" ] && echo "⛔ $(basename "$p") → $prog"; done
  ```
- ⛔ **Восстанавливая — ПЕРЕИМЕНУЙ.** Вернув файл под прежним именем, ты сохраняешь ровно тот
  признак, по которому его снесли: следующая декоммиссия повторит ошибку, и floor выше её опять
  не поймает (он смотрит потребителей, а решение принимается по имени).
- ⚠ **Симптом-tell при планировании:** в наборе к удалению есть файл, чьё **описание в шапке**
  говорит об области шире подсистемы («для ЛЮБОЙ сессии», «общий», «не только»). Шапка написана
  автором, который эту широту и заметил.

**Empirical 2026-08-21:** `alp-pane-trace.sh` (снимок tmux-панели, единственная улика при смерти
сессии) снесён с 58 файлами петель. Его потребитель `pane-trace-all.sh` перечисляет **все**
сессии и заведён после инцидента, где 10 пользовательских сессий умерли без улик. Восстановлен
как `pane-trace.sh`; свип по обоим детекторам дал ровно **один** экземпляр — класс не тиражирован.

## ⛔ ЗЕРКАЛО на стороне ПИСАТЕЛЯ: МЕСТО записи и КЛЮЧ её поиска обязаны зависеть от ОДНИХ И ТЕХ ЖЕ величин

Правило выше — про **мигратора**: двигаешь файлы, охарактеризуй discovery-фильтр runtime'а.
Зеркало возникает **при написании писателя** и не требует никакой миграции: реестр
раскладывает записи по времени (`<repo>/<ns>-YYYY-MM/<uid>.md`), а ищет их по **ключу
сущности** (`session_id`, `chat_id`, `issue`). Пока обе величины совпадают, всё работает;
на границе периода путь меняется, ключ — нет, и `get-or-create` **не находит** запись ⇒
заводит вторую с тем же uid.

- ⛔ **Это НЕ накопление мусора, а РАСЩЕПЛЕНИЕ КЛЮЧА.** Там, где uid == ключ поиска,
  дальнейшие ссылки уходят на ту половину, которую вернул дефектный поиск, а вторая
  осиротевает. Замер 2026-09-05: 1291 входящая ссылка → на «новые» половины, **0** → на
  исходные, при том что исходные несли верный `createdAt`.
- ⚠ **Симптом-tell, ловится ЧТЕНИЕМ функции:** в одной функции построение пути содержит
  период (`strftime("%Y-%m")`, `month_anchor`), а решение «не создавать» ключуется на
  `os.path.exists(<этот путь>)` либо на обходе **одной** периодной папки.
- ✅ **Floor: поиск идёт по КЛЮЧУ, значит и область поиска — все периоды.** Обход
  `<repo>/<ns>-*` свежими первыми с ранним возвратом; запись — по-прежнему в текущий период.
  ⛔ Согласовать «путь ↔ ключ» нельзя ни расширением ключа (он приходит извне), ни отказом
  от периодной раскладки (она нужна для объёма).
- ⛤ **Форма отказа ДВОЙНАЯ, и вторая тише: `get-or-create` — не единственный носитель.**
  Рядом обычно живёт резолвер связей (родитель, владелец, предыдущий), ищущий **обходом
  той же одной папки**. Он не создаёт дублей — он **молча не находит** и подставляет пустоту.
  ⇒ починив первый, грепнуть второй: `os.listdir` по периодной папке.
- ⚠ **Ноль по свипу засчитывать ТОЛЬКО с канарейкой на ДО-фиксной ревизии** (`git show

## Addendum для debug-driven migrations

Перед migration «потому что я думаю это исправит баг»:

```bash
# 1. Locate the function that's failing
grep -rn "<function-name>\|<symptom-pattern>" <repo>/src/

# 2. Read it. ALL of it. Including helpers it calls.

# 3. Verify hypothesis source-empirically:
# Add console.log / DevTools eval / unit test that proves hypothesis BEFORE migration.

# 4. If migration still seems necessary post-source-read → proceed
# 5. If source shows bug elsewhere → fix at source, skip migration
```

Особо опасно — migrations, которые «и так should be canonical» (e.g., moving TBox to assetspaces/). Они feel justifiable, но **не должны быть motivated by debug pressure**. Запланируй их отдельно.
