# Dry-run preview не доказательство shipped behaviour

## Правило

При verification что shipped CLI / plugin feature работает — **не использовать `--dry-run` preview** как final proof для transformations (ordering, normalization, helper-applied changes). Preview pipeline часто форматирует **raw input** независимо от production write pipeline, который применяет transformations.

Required: execute real write path (create actual file / mutation), then read back the result via `Read` или `cat`.

## Когда правило срабатывает

- Smoke-testing freshly-shipped CLI feature после merge
- Acceptance verification что migration / transformation применилась
- Phase 6 / Phase N post-ship verification в любом next-session-prompt task
- Code-reviewer / advisor требует empirical proof of transformation

## Anti-pattern (что НЕ делать)

```bash
# WRONG — dry-run preview может скрыть отсутствие transformation
npx <cli> create --vault X --class Y --dry-run | head -40
# → showed "insertion order" → assumed feature broken → spent 10 min debugging singleton state
```

```bash
# RIGHT — real write, read back via cat / Read tool
npx <cli> create --vault X --class Y
NEWEST=$(ls -t X/path/*.md | head -1)
cat "$NEWEST"  # ← canonical order visible here
```

## Mechanical verification protocol для post-ship feature smoke

```bash
# 1. Make sure CLI / plugin version is the shipped one (not local stale build)
npx <cli>@latest --version

# 2. Execute REAL mutation (NOT --dry-run)
npx <cli>@latest <verb> <flags-without-dry-run>

# 3. Locate the produced/modified file
NEWEST=$(ls -t <output-dir>/*.md | head -1)   # ⛔ см. caveat ниже — небезопасно, если команда трогает и ИСХОДНЫЙ ассет

# 4. Read content — this is the actual shipped behaviour
cat "$NEWEST"
# OR use Read tool for non-Bash contexts
```

### ⛔ Caveat к шагам 3 выше — `ls -t | head -N` находит НЕ созданный файл, если команда мутировала и источник

`ls -t` ранжирует по **mtime**, а команда-мутатор обычно трогает **два** файла: создаёт новый И переписывает ассет, на котором её вызвали (бампает `exo__Asset_updatedAt` ⇒ и mtime). Тогда «самый свежий» — это **исходный** ассет, а не результат. Симптом коварен вдвойне: чтение просто покажет не тот файл, а **cleanup по тому же `ls -t` удалит живой ассет**.

- ✅ **Брать путь из вывода команды, а не угадывать по времени.** `exocortex-cli create` печатает JSON `{uuid,path,label}` — это авторитетный путь результата. Дёшево: `PATH=$(… create … | python3 -c 'import json,sys;print(json.load(sys.stdin)["path"])')`.
- ✅ Если вывод пути не даёт (`apply <create-command>` печатает только `✅ … created`) — **снять список ДО и ПОСЛЕ** и взять разницу множеств, а не «самый свежий». Разница множеств иммунна к бампу mtime у источника.
- ⛔ Не использовать `ls -t | head` там, где следом идёт `rm`. Ошибка отбора становится потерей данных, а не просто неверным чтением.
## Diagnostics: when verification fails after preview suggested success

If preview showed expected output but real write doesn't match (or vice versa):

- **Likely cause:** preview formatter reads pre-transformation input; real-write path runs transformations downstream.
- **Action:** grep CLI source для `dryRun`/`--dry-run` branch, identify whether it bypasses key transformation helpers.
- **File follow-up:** низкоприоритетный bug — preview should mirror real output to maintain consistency.

## Разборы случаев — ВЫНЕСЕНЫ В ГРАФ (справочник on-demand)

⛤ **4 разбора** (~21 КБ) — справочник on-demand: читают, когда механизм **уже соврал**, а не перед действием.

⛔ Даты НЕ уникальны: строка, помеченная `⛔` после даты, делит её с соседней — разрешать по теме.

⛤ **`precondition passed` — ТРИ разных следующих шага за одним выводом:**
**(1)** ты записываешь «команда применима **к классу**» ⇒ ⛔ нет: dry-run доказывает
резолюцию по `cliName`, оракул применимости — `resolve-buttons`
(`decision-surface-must-derive-from-mechanism` §A2) · **(2)** ты прогнал его на РЕАЛЬНОМ
застрявшем ассете и пишешь «verified» в закрывающий артефакт ⇒ ⛔ dry-run ничего не
ПРИМЕНИЛ: либо применяй в том же ходе, либо скажи явно, что не применял (§A1 ниже) ·
**(3)** ты проверяешь, не устарел ли issue ⇒ здесь dry-run авторитетен именно для
ПРЕДУСЛОВИЯ, это законное употребление (`pre-spawn-issue-staleness-check`).
