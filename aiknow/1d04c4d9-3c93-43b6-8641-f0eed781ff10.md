## §A1 — Update 2026-06-11 — stash-рецепт опасен после commit фикса (двойная грабля)

<!-- Added by /session-retrospective 2026-06-11 — root: stash-based revert-verify on committed fix → vacuous pass + foreign stash pop -->

Если фикс **уже закоммичен**, `git stash push <file>` не стешит ничего («No local changes to save» — легко пропустить, если output перенаправлен в /dev/null), и происходят сразу две беды:

1. **Vacuous verify:** тест прогоняется против НЕоткаченного кода → PASS в «обоих» состояниях → ложная уверенность, что revert-verify пройден.
2. **Foreign stash pop:** последующий `git stash pop` вытаскивает **верхний ЧУЖОЙ stash** — stash stack у git один на репозиторий, **общий для всех worktrees**. Empirical 2026-06-11 (PR #3470 session): pop притащил чужой `pre-migration-branch-switch` stash — 11 файлов, конфликт-маркеры в CommandResolver.ts, AA/UU/DU статусы. Recovery: бэкап своих незакоммиченных правок → `git reset --hard HEAD` → selective restore; чужой stash при конфликтном pop НЕ дропается (данные целы).

**Правила:**
- Перед stash-based revert-verify — проверь `git status --short <file>`: файл чистый → фикс закоммичен → используй `git checkout origin/main -- <file>` / `git checkout HEAD -- <file>`, НЕ stash.
- НИКОГДА не перенаправляй stash output в /dev/null — строка «Saved working directory…» vs «No local changes to save» — это и есть верификация. ⛤ **`git stash -q` — та же самая ошибка**: `-q` глушит ровно эту строку. Запрет на подавление относится к СМЫСЛУ («не лишай себя верификации»), а не к конкретной форме `>/dev/null` (эмпирика 2026-07-31 — рефлекторно написал `-q`, читая запрет как про redirect).
- Помни: stash stack общий между worktrees одного репо. На multi-session машине `git stash pop` без проверки `git stash list` — лотерея чужих изменений.

⛤ **Сравнить своё состояние с BASELINE-веткой (lint/поведение «а как на master?») — вообще НЕ повод трогать рабочее дерево.** Соблазн `git stash && git checkout master && <проверка> && git checkout - && git stash pop` возникает каждый раз, когда надо доказать «эти N ошибок pre-existing». У него две отдельные цены: (а) `stash`/`pop` рискует foreign-stash (§выше), (б) `checkout` переключает ветку под тобой — если что-то упадёт посередине, дерево остаётся не в том состоянии, с незакоммиченными правками в стэше.

**Безопасная форма — читать baseline, а не переключаться на него:**
```bash
git show master:src/tools/computer.ts > /tmp/baseline.ts
npx eslint /tmp/baseline.ts        # те же правила, тот же файл, ноль мутаций рабочего дерева
```
Даёт тот же ответ («на master эти же 5 ошибок, только номера строк сдвинуты на +16»), не трогая ни ветку, ни stash-стек. Годится для любого «а как оно там»: lint, grep, чтение реализации, сравнение конфига. Empirical 2026-07-31: я сделал через `stash -q` + `checkout` (сработало, урон 0), а ревьюер той же сессии независимо проверил тот же факт через `git show` — и его способ был строго безопаснее.

## §A2 — Update 2026-06-12 — зеркальная грабля: checkout-рецепт опасен ДО commit фикса

<!-- Added by /session-retrospective 2026-06-12 — root: git checkout HEAD -- file затёр uncommitted working-tree fix при pre-existing-failure проверке -->

Симметрично Update 2026-06-11: если фикс **ещё НЕ закоммичен** (живёт в working tree), пара `git checkout origin/main -- <file>` → `git checkout HEAD -- <file>` **теряет правку**: HEAD её не содержит, restore возвращает не твою версию, а базовую. Git молчит, `git status` чист — потеря обнаруживается только grep'ом.

- **Empirical 2026-06-12 (PR #3487 session):** при проверке «pre-existing ли падение CommandResolver-suite» откатил файл на origin/main и «восстановил» через `git checkout HEAD --` — незакоммиченная замена Buffer→utf8ToBase64 испарилась. Поймано немедленным grep'ом; cost 2 Edit-вызова на повтор.
- **Правило:** revert-verify / pre-existing-проверки с `git checkout` — **только после коммита** своих правок. До коммита: либо сначала закоммить (можно amend-free доп-коммитом), либо скопировать файл в /tmp перед откатом, либо проверять в отдельном чистом worktree.

## §A3 — Update 2026-06-21 — break-точка на typed-TS должна СОХРАНЯТЬ тип переменной (иначе `tsc` падает «suite failed to run», не RED)

<!-- Added by /session-retrospective 2026-06-21 — root: revert-break через `false &&` / `? undefined : undefined` сломал TS type-narrowing → ts-jest «Test suite failed to run», ложно похоже на RED -->

При revert-verify в TypeScript-кодбазе (`ts-jest`) break-правка должна **сохранять статический тип** переменной, которую ты нейтрализуешь — иначе `tsc` отвергает файл с **compile-ошибкой**, и suite даёт `● Test suite failed to run` / `Tests: 0 total`. Это **НЕ** валидный RED (тест не исполнился) — легко спутать с «тест упал», но это сломанная компиляция, а не проваленная ассерта. Две конкретные грабли:

1. **`if (false && cond) { x.foo }`** — `false &&` short-circuit'ит, и TS перестаёт narrow'ить `x` внутри блока (guard `cond` недостижим) → `x` остаётся `T | undefined` → `'x' is possibly 'undefined'` (TS18048). Наблюдалось: revert mount-base lookup через `if (false && store !== undefined)` → `store.get` упал TS18048.
2. **Тернарник с `undefined` в ОБОИХ ветках** (`cond ? undefined : undefined`) — TS сужает результат до `undefined`, и downstream `base.blobSha`/`base.path` становятся `never` → `Property 'X' does not exist on type 'never'` (TS2339). Наблюдалось: revert uid-match через `? undefined : undefined` → 4× TS2339 на `base.*`.
3. **⛤ Временный `return {...}` ВЫШЕ narrowed-кода (recurrence 2026-07-30, orch-exosync #3976)** — чтобы «отреверть» ветку целиком, соблазн вставить `return {kind:"conflict",...}` ПЕРВОЙ строкой блока. Но код ПОСЛЕ безусловного `return` становится **unreachable**, и TS control-flow перестаёт narrow'ить переменные под ним → `'kinds' is possibly 'undefined'` (TS18048) на `const kinds = map.get(...); if (kinds===undefined)... else kinds.push(...)` (narrowing из `if/else` не применяется в unreachable-регионе) → `Test suite failed to run / Tests: 0 total` (ложный «RED»). **Fix: помести terminal-`return` в РЕАЛЬНО ДОСТИЖИМУЮ позицию** — не выше narrowed-кода, а ПОСЛЕ него (напр. в конце того же блока, после того как весь skip/квантайн-код отработал, ИЛИ строкой ниже, где предшествующий код reachable). Тогда компиляция проходит, narrowing цел, revert даёт настоящий RED. Диагностический tell тот же: `error TSxxxx` + `Tests: 0 total` = сломанная компиляция, НЕ проваленная ассерта.

**Type-preserving break-приёмы (дают НАСТОЯЩИЙ RED — компиляция проходит, ассерта падает):**
- **Mismatched lookup key:** `map.get(d.uid + "__revert-disabled__")` — `.get()` сохраняет union-тип возврата (`T | undefined`), runtime-miss → ветка не матчит, downstream narrowing цел. Самый чистый: даёт faithful поведение (rename → delete+add).
- **Обнулить РЕЗУЛЬТАТ после реального вызова:** `await store.get(key); mountSha = null;` — guard/тип сохранён, значение нейтрализовано.
- **`void v;` вместо `arr.push(v)`** — пропустить сайд-эффект, не трогая типы (collected-set остаётся пуст → ассерта на «не пусто» падает).

**Диагностика:** `● Test suite failed to run` + `error TSxxxx` в выводе jest = сломанная компиляция твоей break-правки, НЕ RED. Перечитай ошибку (`grep -E 'error TS|<File>.ts:'`), применяй type-preserving приём, перезапусти. Cost инцидента (al-reqmgmt-p2-inc3): ~4 лишних Edit+test цикла (SyncEngine `false &&` → TS18048; ChangeDetector `? undefined : undefined` → TS2339), самопойман по «suite failed to run», 0 shipped impact.

## §A4 — Update 2026-06-22 — tightening МАКСИМАЛЬНО-пермиссивной gate-ветки: revert-verify бьёт на hole-case (revert → spurious PASS), НЕ на «without-wiring=red»

<!-- Added by /session-retrospective 2026-06-22 — root: al-gui-ci-runner, дедуп eka-gui-e2e в ui-acceptance checker. Фича = tightening `if (isBound) continue;` для ui-acceptance branch. -->

Когда фича **ужесточает** ветку, которая сейчас **максимально пермиссивна** (`if (isBound) continue;` — любой `@req`-тег удовлетворяет req), для неё **нет** красно→зелёного revert-verify: старый код пропускает ВСЁ, что пропускает новый (+ ещё больше). Поэтому единственный revert-verifiable delta — на **hole-case** (вход, который старый код ложно ПРОПУСКАЛ, а новый корректно ЗАВАЛИВАЕТ):
- **Фича-тест (tightening):** вход, который ДОЛЖЕН падать (напр. active ui-acceptance req, привязанный ТОЛЬКО non-GUI unit-тегом, без committed evidence) → новый код raise violation (тест PASS) / **body-revert** (восстановить broad `if (isBound) continue;`) → no violation (тест **FAIL**). Это и есть revert→fail / restore→pass — но направление инвертировано относительно наивного «without-wiring → red».
- **Positive demo (не revert-bound):** вход, который ДОЛЖЕН проходить (GUI-runner binding ИЛИ committed evidence) → PASS обоими способами (старый код тоже пропускает любой тег). Этот тест **не** даёт revert-delta — он лишь демонстрирует, что новый satisfaction-путь работает. Не путать его с revert-verify.

**Эвристика:** если prompt просит «без wiring → gate red, с wiring → green», а реальный текущий код уже пропускает «с wiring» (пермиссивно), то «без wiring → red» = «req без любого binding → red» (уже покрыто базовым active-gate, тривиально). Настоящая фича — **сузить**, и revert-verify смещается на hole-case. Сформулируй ОБА теста (tightening + positive), но помни: body-revert кусает только tightening-тест. Empirical (al-gui-ci-runner, PR #3717): TEMP-REVERT broad `isBound` для ui-acceptance → tightening-тест 1 FAILED / 70 PASSED; restore → 71/71. Cross-tie `verify-before-assert` (single empirical observation ≠ доказательство механизма) — здесь: «any-tag-passes» был verified чтением active-gate ДО дизайна tightening.

## §A5 — Update 2026-07-04 — revert-verify count-throttled / gated фичи через выталкивание порога-КОНСТАНТЫ за диапазон

<!-- Added by /session-retrospective 2026-07-04 — root: ExoSync progress-логи PR #3831, revert-verify трёх count-throttled progress-фаз. -->

Для фичи, чья наблюдаемость гейтится **числовой константой-порогом** (progress-тики каждые N итераций; sampling каждые K; batching при size≥M; announce при total≥MIN) — самый чистый **type-safe faithful revert** для revert-verify = **временно выставить порог за пределы, которых тест не достигает** (`STEP = 100_000_000`, `MIN = 1_000_000`), НЕ комментировать emit и НЕ `if(false)`:
- **Type-safe** — это смена литерала `const`, никаких TS-narrowing граблей (в отличие от `false &&` / `? undefined : undefined`, см. Update 2026-06-21) → компиляция проходит, RED честный (тест исполняется, ассерта падает на «0 тиков»).
- **Faithful** — фича наблюдаемо ВЫКЛючена (события не эмитятся), что и есть pre-фичное состояние контракта.
- **Pre-commit-safe** — это Edit-правка (не `git checkout`), поэтому работает ДО коммита правок этого файла (Update 2026-06-12: checkout-before-commit теряет незакоммиченную правку).
- **Изолирует фазы** — при нескольких порогах (напр. reads-STEP + writes-STEP) выталкивание ОБОИХ роняет ровно те тесты, а независимые фичи (со своим порогом) остаются GREEN → доказывает, что каждый тест ловит СВОЮ фазу, а не соседнюю.

Восстановление порога → все тесты GREEN. **Empirical (PR #3831):** `BLOB_PROGRESS_MIN_TOTAL 25→1_000_000` → fetching-blobs-тест FAIL, остальные PASS; `LOCAL_{READ,WRITE}_PROGRESS_STEP 500/25→1e8` → reading-local + writing-files FAIL, fetching-blobs не задет; restore → 9/9. Cross-tie `verify-before-assert` (revert-verify — эмпирическое доказательство, не «выглядит правильно»).

## §A6 — Update 2026-07-19 — КАЖДЫЙ call-site общего cleanup/rollback-хелпера нужно revert-locked'ить ОТДЕЛЬНО (revert-lock одной ветки НЕ покрывает другую)

Когда функция зовёт **один и тот же** rollback/cleanup/delete-хелпер из **≥2 call-site** (напр. две failure-ветки, обе вызывающие `this.rollback(...)`) — revert-verify-тест, упражняющий **только одну** ветку, **НЕ** локает вторую. Дроп guarding-аргумента из **другого** call-site оставит все существующие тесты GREEN → **false-positive-coverage** для этой ветки. **Пиши по одному revert-verify на КАЖДЫЙ call-site.**

- **Enumerate все call-site** хелпера (grep имени) — каждый = независимая revert-lock-цель. «Прошёл revert-verify для одной ветки» ≠ «обе ветки locked».
- ⛤ **Труднодостижимая ветка — всё равно обязанность покрытия.** Composite-executor, чей top-level `execute()` **оборачивает** step-throw'ы в `{success:false}`, делает `catch`-ветку **defensively-unreachable** через нормальный step-dispatch (throw шага возвращается как `{success:false}` → step-failure-ветка, НЕ catch). Чтобы упражнить catch честно — **форсировать реальный throw**: переопределить private step-runner на **инстансе** так, что первый (реальный `create_instance`) шаг отрабатывает и наполняет tracked-paths, а второй бросает: `(exec as any).executeStep = async (...a) => { if (++n===1) return realStep(...a); throw new Error("boom"); }`. Ассертить **error-shape** (`Composite execution failed`), чтобы доказать, что попал в catch, а не в step-failure-ветку.
- **Revert-verify КАЖДУЮ ветку независимо** — дроп guarded-арга из **только** этого call-site (через Edit break/restore) → **только** этот тест RED, остальные GREEN. Эта per-branch RED-on-revert и есть доказательство, что call-site locked.

**Empirical (2026-07-19, #3921, autonomous bug-fix-turnkey child → CLI v16.187.1):** `executeComposite.rollback` зовётся из step-failure-ветки (~L769) И catch-ветки (~L799); обе получили аргумент `createdPaths` (удаление orphaned create_instance-ассетов). Мой первый тест-набор revert-lock'нул только step-failure-ветку; **orchestrator round-2 code-review** поймал catch-ветку как partial revert-lock (false-positive-coverage). Добавил один production-shape catch-branch тест (форс-throw через instance-override `executeStep`) + revert-verified его (дроп `createdPaths` из L799 → RED **только** он, 6 остальных GREEN). Cross-tie `test-fixture-realism` (production-path, не hand-injected), aiKnow ``5df24069-bef6-46b1-a974-09a2b3860428``.

## §A7 — ⛤ Update 2026-08-02 — НОВЫЙ гвард ВЫШЕ по потоку ОБНУЛЯЕТ покрытие старого: revert-verify своих осей этого НЕ видит

§2026-07-19 (выше) — про **N call-site одного** хелпера. Здесь другая механика, дающая тот же false-positive: ты добавляешь **новый гвард** в ту же функцию, и он начинает возвращать **раньше** существующего. Все прежние тесты этого блока внезапно проходят через **твою** ветку, а старый гвард перестаёт исполняться вовсе — его покрытие **молча обнуляется**, оставаясь зелёным.

- ⛔ **Собственный revert-verify это НЕ ловит по построению.** Ты проверяешь оси **своей** правки (снял мой гвард → мой тест RED). Вопрос «а что моя правка сделала с ЧУЖИМ покрытием» в этот прогон не входит — и ответ «обнулила» выглядит идентично «всё зелено».
- ✅ **Floor: добавив гвард/ранний `return` в существующую функцию — перечисли гварды НИЖЕ своего и revert-verify КАЖДЫЙ.** Нейтрализуй нижний гвард → хоть один тест обязан покраснеть. Остался зелёным ⇒ твой гвард его затенил, покрытие потеряно.
- ⛤ **Чинится тестом на конфигурацию, где твой гвард ПРОПУСКАЕТ, а нижний — держит.** Такой вход и есть единственное место, где нижний гвард ещё несёт вес.
- ⚠ **Ловушка при написании этого теста: он сам может быть шунтирован ЕЩЁ более ранним гвардом.** Первая попытка обычно повторяет форму соседних тестов — и попадает в них. Тест обязан обойти **все** предшествующие условия, а не только твоё; проверяется это тем же нейтрализующим прогоном, а не чтением кода.
- ⛤ **Красное ≠ покрытое: смотри, ПО КАКОМУ ассерту красит.** Тест может краснеть по побочному ассерту (лог, счётчик, тост) при полностью непокрытом основном эффекте (запись/мутация). Тогда гвард формально «под тестом», а его настоящая работа — нет.
- ⛤ **Затенение бывает ГРОМКИМ — и это единственный случай, когда оно ловится бесплатно.** Формулировка «покрытие обнуляется **молча**» верна, когда затенённая ось ассертит на условии, которое просто перестало достигаться (утверждение остаётся истинным ⇒ зелено). Но если ось ассертит на **АРТЕФАКТЕ, который твой ранний выход УСТРАНЯЕТ** (напечатанная строка, отправленное сообщение, созданный файл), она краснеет сразу на первом же прогоне.
  - ⚠ **Диагностический tell, который легко прочесть наоборот:** сразу после добавления гварда краснеет **СТАРАЯ** ось, которую ты не трогал. Первая мысль — «сломал логику» и порыв чинить движок. Прежде чем править — спроси, **не устранил ли твой ранний выход то, на что она смотрит**; тогда дефект не в движке, а в МЕСТЕ оси, и лечится он переносом на конфигурацию, где гвард пропускает (пункт выше), а не откатом гварда.
  - **Практический вывод:** громкий вариант — подарок, а не проблема; он делает за тебя перечисление из floor'а. Молчаливый вариант остаётся единственным, ради которого пер-гвардовый счёт краснот обязателен.

|---|---|---|

⛤ **Все три — не три правила, а один вопрос, и у него один дешёвый ответ: НЕЙТРАЛИЗУЙ КАЖДЫЙ ГВАРД ПО ОДНОМУ И ПОСЧИТАЙ КРАСНЫЕ.** Гвард, чья нейтрализация даёт **0 красных**, не под тестом — независимо от причины. Это одна команда на гвард и полностью механическая проверка, в отличие от рассуждения «ну мои оси же его задевают».

- ⛔ **Почему собственный revert-verify этого не видит ПО ПОСТРОЕНИЮ.** Он отвечает на вопрос «краснеет ли мой тест, если убрать мою правку» — то есть меряет **ось**, а не **достижимость каждого гварда внутри правки**. Убрав правку ЦЕЛИКОМ, ты гарантированно краснеешь через первый же гвард цепочки и никогда не узнаёшь, что остальные мертвы. Чем больше осей, тем убедительнее ложная уверенность.
- ✅ **Что делает поздние гварды достижимыми:** фикстура, где присутствуют **И** реальный ключ/вход, **И** коллидирующий сосед. На фикстуре только с соседом ранний гейт возвращает «нет такого» и короткозамыкает; только с реальным ключом — коллизии нет. Нужны оба одновременно.
- ⚠ **Смотри, ПО КАКОМУ ассерту красит** (усиление §2026-08-02): красный по побочному ассерту при непокрытом основном эффекте = гвард формально «под тестом», фактически нет.

Пер-гвардовый замер по полному core-сьюту дал **1 / 0 / 0 / 0** красных: `hasProperty` гейтит обоих писателей и короткозамыкает, поэтому **три анкера из четырёх можно было снять при зелёном CI**. Каждой из трёх зон соответствует свой отдельный дешёвый зонд (пер-гвардовый счёт краснот · дифференциальная нейтрализация нижнего гварда · прогон настоящего парсера на настоящем ассете, `test-fixture-realism` §Addendum 2026-08-03) — и ни один из них не является revert-verify.

### ⛔ Сам ПЕР-ГВАРДОВЫЙ ЗОНД лжёт ДВУМЯ способами (2026-08-11): абсолютный счёт краснот вместо РАЗНОСТИ, и COLLIDE, читаемый как успех

§Update 2026-08-03 выше предлагает пер-гвардовый счёт краснот как **единый** ответ на «достижим ли каждый гвард». Недостающая половина: у самого зонда есть **две** формы отказа, и обе наблюдались на первой же его реализации. Пока они не закрыты, зонд не измеряет ничего — но выглядит работающим, потому что рапортует числа.

**1. ⛔ Вердикт из АБСОЛЮТНОГО счёта краснот вместо разности ⇒ ветка ZERO НЕДОСТИЖИМА.** Мутация прода краснит не только ось своего гварда, но и **побочные** оси, судящие сам файл прода (бит исполнения, синтаксис, наличие счётчика в выводе). Одна такая красная делает `reds ≥ 1` у **каждого** гварда ⇒ доказанные дыры приходят как `RED 1`, «дыр: 0», rc=0.

- ⛔ **Положительный контроль этого НЕ ловит** — он тоже красный, просто по чужой причине. То есть контроль проходит ровно в том состоянии, где вердикт мёртв.
- ⛤ **Триггер производится ТЕМ ЖЕ классом правки, который зонд и меряет:** любая ось на свойства файла прода (`os.access(PROD, X_OK)`, `bash -n`, «в выводе есть счётчик N») даёт побочную красноту у **всех** мутантов сразу.
- ✅ **Floor:** базовая линия на **пристинном** проде **первым шагом**, вердикт — **разность множеств** краснот, и `exit 2`, если базовая линия не зелена (иначе разность считается от мусора). Оси разбирать якорем уровня харнесса (`^  ❌ <ось>`), иначе строки предмета, вклеенные в вывод провала, завышают `n`.
- ⛔ **`BROKEN` у ИЗМЕРЯЕМОГО гварда нельзя проглатывать в зелёный прогон** — иначе «дыр: 0» означает «дыр не найдено ИЛИ не измерено», а это разные утверждения.

**2. ⛤ COLLIDE — честный третий исход, и он же читается как успех.** Гвард, который харнесс **уже** заклюнил, имеет якорь, занятый его собственным мутантом ⇒ свип не может собрать свой ⇒ `COLLIDE`. Это ожидаемая подпись закрытой дыры — и **ровно поэтому** её нельзя принимать за доказательство:

- **COLLIDE доказывает ЗАЯВКУ на гвард, а не РАЗЛИЧЕНИЕ.** Различение доказывает пара «ось + свой мутант» (§Recurrence 2026-08-06 «ось, КОТОРАЯ ПРОГОНЯЕТ проверяемое, ВСЁ РАВНО бывает осью НАЛИЧИЯ» ниже в этом файле), а не свип.
- ⚠ **Переход `ZERO → COLLIDE` неотличим от «я переименовал якорь, и теперь не измеряется ничего».** Различает только прогон пары.
- ⛤ **Честная область зонда — РЕГРЕССИЯ:** снимут ось вместе с её мутантом → якорь освободится → гвард снова придёт `ZERO`. Так и формулировать в отчёте, а не «гвард покрыт, свип подтвердил».

⚠ **Симптом-tell для обеих форм:** зонд рапортует `RED n` про гвард, о котором ты **знаешь**, что он дыра. Смотри на формулу вердикта, а не на гвард.

**Empirical 2026-08-11** (`rules-xref-guard-sweep.py`, ALP `62fc18a9`): свип написан ради доказательства «4 дыры закрыты» и в первой редакции выдавал `✅ RED 1` × 4 и rc=0 **на четырёх доказанных дырах** — вердикт шёл из «есть ли хоть одна `❌`», а побочную красноту давала ось A0 (мутант писался режимом `644`, прод зовётся по пути — `harness-invocation-surface`). Ревьюер предъявил это конструкцией; revert-verify: прежний свип → `RED 1` ×4 / rc=0, новый → `BROKEN` / rc=2. Ещё два дефекта того же свипа поймал его **собственный положительный контроль** (COLLIDE детектился подстрокой `BROKEN`, которую харнесс печатает в ЗЕЛЁНОЙ оси; и негодность одного контрольного гварда как RED-контроля). ⇒ у пер-гвардового зонда положительный контроль **обязателен**, и требовать он должен **свой ожидаемый исход** у каждого контрольного гварда, а не «хоть что-то покраснело».

### ⛤ Четвёртая механика того же вопроса (2026-08-05) — ДУБЛИРУЮЩИЕ гварды: оба достижимы, но нейтрализация ОДНОГО не наблюдаема, потому что второй держит тот же инвариант

Три механики выше объясняют, почему гвард **недостижим** (чужие call-site / затенён сверху / короткозамкнут соседом). Четвёртая — гвард **достижим и исполняется**, но его снятие **не меняет наблюдаемого исхода**, потому что рядом стоит вторая защита того же инварианта. Пер-гвардовый счёт краснот тогда даёт **0** — и читается как «гвард не под тестом», хотя верный вывод обратный: он **под тестом дважды**.

- ⛔ **Вывод из нуля здесь ПРОТИВОПОЛОЖНЫЙ остальным трём.** Там ноль = дыра покрытия (чинить фикстуру); здесь ноль = избыточная защита (чинить **ось**, воспроизведя до-фиксовое состояние **целиком**). Спутав их, либо снимешь рабочий гвард как «непокрытый», либо будешь искать несуществующую дыру.
- ✅ **Дискриминатор — прочитать, ЧТО удержало инвариант при снятом гварде.** Исход не изменился ⇒ найди строку, которая его удержала. Нашлась — это второй гвард, и ось обязана снимать **оба** (`sed -e … -e …`). Не нашлась — настоящая дыра покрытия.
- ⛤ **Две защиты — часто правильно** (авторитетный источник + вычисляемый фолбэк), но тогда **ось пишется на пару**, а не на каждую по отдельности. Иначе набор молча зеленеет на любой одиночной мутации.
- ⚠ **Tell:** мутант применился (маркер на месте, `bash -n` чист), а исход байт-в-байт прежний. Это НЕ «мутация не сработала» (§Update 2026-08-03 про no-op — там код фактически не менялся); здесь менялся, но результат удержан соседом.
- **Empirical 2026-08-05** (пулл в тике ALP): фикс двойного счёта поставил ДВЕ защиты — якорь на строку `Summary:` и `grep -v '^Summary:'` в фолбэке. Ось «без якоря → ×2» вышла зелёной (фолбэк удержал верное число); удвоение вернулось только когда мутант снял обе. Цена: один цикл «почему ось не краснеет».

### ⛔ ПЯТАЯ механика (2026-08-06) — гвард полностью покрыт как ФУНКЦИЯ, а его ВЫЗОВ не покрыт ничем: мутация тела краснит N, удаление вызова краснит 0

Четыре механики выше отвечают на «достижим ли гвард» (чужие call-site · затенён · короткозамкнут · дублирован). Пятая — гвард **достижим, исполняется в проде, дубля не имеет и честно покрыт**: мутация его тела краснит N осей, покрытие строк 100 %. Не покрыто **ребро** — тот единственный вызов, который заставляет его действовать.

- ⛤ **Пер-гвардовый зонд из §Update 2026-08-03 эту дыру НЕ ВИДИТ ПО ПОСТРОЕНИЮ:** он мутирует **тело** гварда и получает здоровый счёт краснот. Вопрос «а вызывает ли его кто-нибудь из прода» в этот замер не входит — и ответ «никто» выглядит точно так же, как «всё покрыто».
- ⛔ **Гвард, который никто не вызывает, тождественен отсутствию гварда** — но отгружается с зелёным набором, стопроцентным покрытием и убедительным тест-файлом. Это дороже обычной дыры: у неё нет ни одного симптома, а у самого гварда есть все признаки исправности.
- ⚠ **Симптом-tell читается за секунду, без прогона:** все оси гварда начинаются с `import { theGuard }` и зовут его **напрямую**; ни одна не конструирует продовый объект и не идёт через реальную точку входа. Тест-файл при этом выглядит образцовым — он и правда образцово тестирует **функцию**.
- ✅ **Floor: мутировать ВЫЗОВ, а не тело.** Убери строку вызова в копии (`integration-test-revert-verify` §ZERO-GIT-TOUCH) → посчитай красные. **0 ⇒ продовый путь не упражняется ничем**, и добавлять надо не ещё одну ось на функцию, а **ось на проводку**: драйвить настоящую точку входа и утверждать, что эффект гварда **дошёл** до вызывающего (исключение всплыло / мутация не состоялась).
- ⛤ **Правило шире гвардов: любая правка, добавляющая ВЫЗОВ в существующую функцию** (новая валидация, новый шаг, новый эмит) несёт две независимые оси — «новый код делает, что обещает» и «новый код **включён** в продовый путь». Вторую почти всегда забывают, потому что первая ощущается исчерпывающей.

## §A9 — Update 2026-07-30 — revert-verify НЕ только «ловит ли тест баг», но и «НУЖЕН ли вообще мой ФИКС»: фальсифицируй load-bearingness ДО отгрузки (особенно в shared infra)

Всё правило выше — про revert **production-фикса**, чтобы доказать, что **тест** его ловит. Зеркальное применение того же приёма, дешёвое и недооценённое: когда чинишь **несколько** вещей разом (или починил «по пути» смежный дефект) — **отреверть КАЖДУЮ правку по отдельности** и посмотри, вернётся ли симптом. Так отделяется **load-bearing** фикс от **сопутствующего**, который ты применил по гипотезе.

- **Зачем:** правдоподобная причинная история («цепочка классов оборвана → значит вот почему падает») ощущается доказанной, когда симптом исчез — но исчезнуть он мог от ДРУГОЙ правки в том же заходе. Без per-fix revert ты отгружаешь ненужное изменение под видом необходимого — и в **shared infra** (общий TBox, конфиг, зависимость) это раздувает blast-radius на ровном месте.
- **Механика (дёшево, ~1 прогон на правку):** оставить остальные фиксы, откатить ОДИН (`cp` из бэкапа) → перепрогнать гейт → симптом вернулся? **load-bearing, оставляем**. Не вернулся? **не требуется** → откатить байт-в-байт и вынести отдельным наблюдением/issue, а не протаскивать в этот заход.
- **Дисциплина скоупа:** «не нужен для симптома» ≠ «неверен». Правка может быть корректной по конвенции — но это **отдельное решение** (особенно shared), а не бесплатный довесок к текущей задаче. Осознанно применять — только по явной директиве, с озвученным blast-radius. Sibling `child-scope-immutability` (не расширять scope молча).
- **Empirical (2026-07-30, SHACL-разбор vault-my):** на 1 violation я применил ДВЕ правки — (a) strip-canon stale-алиаса в инстансе и (b) рутование shared-TBox-миксина `ems__AreaAware` в `exo__Asset` (казалось load-bearing: «цепочка не доходит до exo__Asset»). SHACL стал 0. **Revert-verify (b)** при оставленной (a) → **тоже 0** → (b) НЕ требовался; настоящий корень — только stale-алиас. Откатил (b) байт-в-байт (`exoas-public` pushed **0**), вынес как наблюдение; применил уже осознанно, отдельным шагом, по явной директиве Андрея + с проверкой blast-radius. Без этой пробы в общий TBox уехало бы немотивированное изменение, «обоснованное» ложной причинностью. Cost пробы: 1 валидация (~1 мин).

## §A10 — ⛤ Update 2026-07-30 — ZERO-GIT-TOUCH revert-verify: ломай КОПИЮ дерева, а не рабочий файл (обходит ОБА footgun'а stash/checkout сразу; работает и на git-free/не-repo цели)

Все механизмы выше — `git stash` и `git checkout` — имеют по 3+ задокументированных recurrence с реальным ущербом (foreign-stash грабёж, стёртые uncommitted-правки). Правило дважды упоминает «ЛИБО проверять в отдельном чистом worktree» вскользь; вот конкретный рецепт, который **не выполняет НИ ОДНОЙ git-операции над рабочим деревом**:

1. **`shutil.copytree(src, dst, ignore=ignore_patterns("__pycache__"))`** — копия движка/пакета в `/tmp`.
2. **Сломать КОПИЮ exact-literal splice'ом + abort-if-not-found:** скрипт ищет анкер-блок и `sys.exit(...)`, если вхождений `!= 1`. Так «сломанное» состояние (а) воспроизводимо, (б) самодокументируемо (`diff` показывает ровно снятую строку), (в) не может молча промахнуться по анкеру. ⛔ НЕ regex по данным (§`string-replace-dollar-corruption`) — literal `str.index` + срез.
3. **Гонять каждое состояние ОТДЕЛЬНЫМ процессом** (`harness.py <engine-dir>`), т.к. в одном процессе кэш модулей (`sys.modules`) склеит fixed и broken варианты.

**Почему строго лучше stash/checkout в этом классе задач:** рабочий файл **не трогается вообще** ⇒ uncommitted-правки физически не могут пропасть, shared stash-стек не задействован, и **не нужно коммитить фикс перед revert-verify** (Update 2026-06-12 требует этого только потому, что checkout мутирует рабочий файл). Плюс работает там, где git-механизмы не применимы: git-free vault, каталог скриптов вне репо, цель = целый пакет с sibling-импортами.

### ⛔ Addendum 2026-08-07 — ХАРДЛИНК-вариант копии (`cp -al`) ПЕРЕСТАЁТ отслеживать источник ровно у тех файлов, которые ты уже мутировал ⇒ измеряешь СТАРЫЙ предмет

⛤ **Механизм — два шага, каждый по отдельности верный:**
1. Мутируя файл в копии, ты **обязан порвать его хардлинк** (`os.unlink(dst)` перед записью), иначе запись пройдёт **сквозь** общий inode и испортит рабочее дерево. Это и есть «ZERO-GIT-TOUCH» в хардлинк-варианте.
2. Но с этого момента **именно этот файл** в копии — независимая сущность. Любая последующая правка **источника** (Edit тест-файла по замечанию ревью, доработка фикстуры) в копию **не приезжает**.

⇒ Следующий прогон матрицы измеряет **предыдущую редакцию** предмета. Числа выходят правдоподобные, ошибки нет, и они прямо противоречат тому, что ты только что написал в коде.

- ⚠ **Симптом-tell:** ты изменил тест/фикстуру и ждал сдвига матрицы — а она **не сдвинулась вовсе**. «Мутация не влияет» здесь читается как вывод о предмете, тогда как это утверждение о **несвежести копии**.
- ✅ **Floor — проверять ИДЕНТИЧНОСТЬ inode, а не существование файла:** перед каждым прогоном сверять `os.stat(src).st_ino == os.stat(dst).st_ino` для файлов, которых мутация НЕ касается, и **пере-копировать** те, где расхождение (`rm dst && cp src dst`). Одна строка; без неё несвежесть невидима, потому что содержимое «похоже».
- ⛤ **Дискриминатор дешевле пересборки:** `stat -f %i` на паре путь-источник/путь-копия. Совпало — копия отслеживает; разошлось — файл уже отвязан и обязан быть пере-скопирован.
- ⛔ **Не «пересоздавать копию целиком на каждый прогон»** — это возвращает цену, ради ухода от которой брали хардлинки. Пере-копировать нужно **только отвязанные** файлы.

## §A12 — ⛤ Update 2026-08-03 — МУТАЦИЯ, КОТОРАЯ НИЧЕГО НЕ МЕНЯЕТ, читается как «тест не умеет краснеть»; зелёный после нейтрализации — сперва улика против мутации, а не против теста

§Update 2026-06-21 разбирает мутацию, которая **ломает компиляцию** (`Tests: 0 total` — ложный RED). Зеркало: мутация **семантически пустая** — код исполняется как прежде, набор остаётся зелёным, и это читается как «мой тест вакуумный / ось не дискриминирует». Вывод противоположен истине: тест в порядке, не сработала правка.

Две формы, обе выглядят убедительно в диффе:

| Написал | Почему это no-op |
|---|---|
| `if (false \|\| A \|\| B) { … }` — добавил `false \|\|` в дизъюнкцию | `false \|\| X` ≡ `X`; условие не изменилось |
| мёртвую ветку **ПЕРЕД** живой (`if (false && cond) { return null; } if (cond) { …настоящая… }`) | живая ветка ниже отрабатывает как прежде |

- ⛤ **Дискриминатор — не рассуждение, а ПРОВЕРКА САМОЙ МУТАЦИИ.** Прежде чем толковать зелёный результат, убедись, что правка вообще применилась и меняет поведение: `grep -n 'TEMP-REVERT' <файл>` (маркер на месте?) плюс — для дизъюнкций и ранних веток — прогон одного точечного случая, который обязан флипнуться. Литеральный splice с `assert count==1` доказывает, что **строка найдена**, но не что **смысл изменился**.
- ✅ **Надёжные формы нейтрализации:** заменить условие целиком (`if (cond)` → `if (false)`), **вырезать блок** литеральным splice'ом, вернуть фиксированное значение **первой** строкой функции. Ненадёжные: дописывать операнд в булево выражение, вставлять ветку рядом с живой.
- ⛔ **Не делай вывод «ось не нужна» по одному зелёному прогону.** Именно так вакуумный тест получает индульгенцию: мутация была пустой, зелёный — закономерен, а списывается это на «здесь нечего ловить».
- ⚠ Соседний, честный случай: мутация применилась, поведение изменилось, и тест **правда** не краснеет — потому что смещение идёт в **разрешающую** сторону (граница сдвинулась так, что маркер всё равно показывается). Такой тест бесполезен как ось и его следует **удалить**, а асимметрию записать комментарием. Отличается от no-op тем, что здесь мутация проверена и реально работает.

### ⛤ Четвёртая форма того же: мутация применилась НЕ ТУДА — `assert` доказал «строка НАЙДЕНА», а не «поведение ИЗМЕНИЛОСЬ»

- ⛤ **Комментарий — системный источник ложной цели**, потому что хороший комментарий ОБЯЗАН цитировать то, что объясняет («⛔ `-e "$re"`, а НЕ `"$re"`: …»). Она встроена в **харнесс отгружаемой работы**; но по ходу той же сессии почти всегда делается **опортунистическая боковая проверка соседнего файла**, который в scope не входит. Она не наследует ни одной гарантии харнесса — ни якоря на строку, ни счёта вхождений, ни печати диффа, — а её результат неотличим по виду от результата харнесса: то же «нейтрализовал X → N красных».

- ⛔ **Отказ тише обычного промаха мутации.** Обычный промах даёт зелёный там, где ждали красного, и это видно в прогоне. Здесь мутация **сработала** и дала осмысленные числа — просто **не про тот гвард**. Числа правдоподобны, таблица заполнена, вывод сформулирован; опровергнуть его можно только пере-замером.
- ⛤ **Дальше числа ЛАУНДРЯТСЯ через вторые руки и приобретают статус проверенного факта.** Боковая находка оформляется задачей → задачу читает оркестратор → он переписывает матрицу в спавн-промпт, добавляя от себя «доказано по построению». Ни один из двух шагов не воспроизводил замер, но каждый добавил уверенности. Это тот же laundering, что `decision-surface-must-derive-from-mechanism` §Addendum про автономного воркера: подпись, которую некому оспорить между чтением и исполнением.
- ⚠ **Симптом-tell у ИСТОЧНИКА:** ты меряешь файл, которого **нет в списке файлов твоего PR**. Это и есть признак, что ты вышел из-под своего харнесса. Тогда либо прогони замер тем же скриптом (он у тебя уже написан), либо помечай вывод как **наблюдение, не замер** — и пиши в задачу «похоже, что…», а не таблицу с числами.
- ⚠ **Симптом-tell у ПОТРЕБИТЕЛЯ (оркестратора):** ты переписываешь в промпт таблицу, которую **не воспроизводил**, и сопровождаешь её усилителем («доказано», «по построению», «verified»). Усилитель — ровно то место, где чужое наблюдение становится твоим фактом. Либо воспроизведи, либо назови источник и оставь как гипотезу, которую ребёнок обязан проверить первым шагом.
- ✅ **Что реально спасло:** в промпте стояла инструкция «STEP A — воспроизведи замер, не верь ему на слово; если числа не сойдутся, это находка, эскалируй, не подгоняй». Ребёнок воспроизвёл, получил другое, нашёл причину и эскалировал. ⇒ **пункт «воспроизведи прежде чем строить» в промпте дешевле любой проверки на стороне автора** — он ловит и то, чего автор не заподозрил.
- ⛤ **Многократность подстроки — свойство файла, а не невезение.** Проверять её до мутации одной командой: `grep -c '<подстрока>' <файл>`. Больше одного — якорь непригоден by construction.

⛤ **Зеркало по позиции: подстрока-ловушка живёт не только в МУТИРУЕМОМ файле, но и в ДРАЙВЕРЕ — там, где он решает «покраснело ли».** Формы выше про якорь мутации (куда лёг патч). Драйвер же ищет **needle** в выводе прогона (`"anchor 5"`, `"0 без токена"`, `"3 нарушения"`), и подстрочный матч там даёт **ложно-ЗЕЛЁНУЮ** ось — противоположный знак ошибки.

- ⛔ **Цифра прирастает С ОБЕИХ сторон, и вторая сторона забывается.** `anchor 5` ⊂ `anchor 50` (справа) и `0 без токена` ⊂ `10 без токена` (**слева**). Гвард только по правой границе выглядит достаточным и молча пропускает вторую половину класса.
- ✅ **Floor: гвард на обе границы одной формой** — `re.search(r"(?<![0-9])%s(?![0-9])" % re.escape(needle), out)`, и ставить его **в общем хелпере драйвера**, а не в каждой оси: тогда следующая ось наследует защиту, а не дисциплину автора.
- ⛤ **Проверять флип на СИНТЕТИКЕ, а не на живых осях.** Живые числа могут не иметь соседей-удлинителей сегодня — и ось будет зелена по совпадению. Пара `("anchor 5","anchor 50")` + `("0 без токена","10 без токена")` даёт вердикт за секунды и переживает дрейф данных.
- ⚠ **Симптом-tell:** needle содержит **число** и матчится подстрокой. Число — единственный тип needle, у которого сосед может отличаться на один символ и при этом означать другое.
- **Empirical 2026-08-09** (`rules-xref-check-verify.py`, ALP `0b8627f0`): `code-reviewer` (LOW) показал, что needle `0 без токена` матчит `10 без токена` ⇒ ось не различает. Закрыто digit-guard'ом с **обеих** сторон в самом драйвере; дискриминация предъявлена на 6 синтетических случаях, 0 провалов. ⛤ Показательно, что собственный чек-лист страховочной задачи **предсказал ровно это** («проверить, что `10 без токена` тут невозможно») — и всё равно поймал ревьюер, а не автор.

**Empirical 2026-08-07** (парковка ассетспейсов, `SyncDepsFactory.ts`): PR #4033 отгрузил матрицу **17 гвардов**, и его тело **дословно** описывает эту опасность («a token anchor can land in a comment… the harness anchors on a full code line, asserts `src.count(old) == 1`, and prints the diff of every mutation; audit of all 16 diffs: none landed on a comment line») — то есть дисциплина была, работала и покрывала весь отгружаемый scope. ## §A13 — ⛔ Update 2026-08-05 — фикстуры-заглушки нужны и в ОСЯХ, где ИСПРАВНЫЙ движок до опасного кода не доходит: харнесс безвреден ровно настолько, насколько безвреден на СЛОМАННОЙ копии

§Update 2026-08-03 (выше) требует, чтобы харнесс был структурно неспособен на побочный эффект. Недостающая половина — **в каких осях** это требование действует. Естественная (и неверная) экономия: ось проверяет режим, который **выходит раньше** опасного кода (`--dry-run`, `--selftest`, «только напечатай план»), поэтому фикстуры источника данных в неё не передают — исправный движок до них не дойдёт.

⛔ **Но revert-verify гоняет ту же ось против СЛОМАННОЙ копии, у которой раннего выхода нет.** Копия проваливается в основной путь и работает с **боевым** источником: читает живой `ps`, ходит в сеть, трогает продовое состояние. То есть проверка режима «ничего не делать» сама становится действием над продом — и ровно в тот момент, когда никто этого не ждёт, потому что ось задумывалась как самая безобидная.

- ✅ **Floor: фикстуры передавать в КАЖДУЮ ось**, включая те, где исправный движок их не читает. Стоимость — одна строка env; выгода — харнесс безвреден независимо от того, что осталось в мутанте.
- ⛤ **Тот же вопрос задать про КАЖДЫЙ внешний канал, а не только про источник данных:** сеть, файловая система, спавн процессов. У безопасной оси должен быть закрыт **каждый** из них (у меня: источник — фикстурой, сеть — `DRY_RUN` в одной оси и стабом ответа в другой).
- ⚠ **Симптом-tell:** пишешь ось со словами «сюда он всё равно не дойдёт». Это утверждение об **исправном** коде, а ось существует ради **сломанного**.
- **Empirical 2026-08-05** (`claude-bloat-check`): оси нового selftest-режима не несли `BLOAT_PS_*`, и копия без этой ветки уходила сканировать живые процессы машины — у монитора, который умеет их **убивать**. Поймано при первом же прогоне мутанта (ось покраснела не по той причине, что ожидалась); урона не случилось только потому, что счётчик strike'ов лежал в подменённом HOME и стартовал с нуля.

## §A14 — ⛤ Addendum 2026-08-05 — СМЕШАННАЯ дисциплина внутри ОДНОГО харнесса: оси, извлекающие предикат из прода, соседствуют с осью, держащей ручную КОПИЮ — и копия тождественно-зелёная

Правило выше требует по оси на гарантию. Недостающая половина — **подлинность** оси: читает ли она
БОЕВОЙ предикат или свою копию. Копия проверяет сама себя и потому зелена при любой мутации прода —
это `self-satisfying-metric-weak-verifier` на поверхности харнесса.

- ⛤ **Дефект приходит НЕ от небрежности, а от разной «извлекаемости».** Регэксп вытаскивается из
  прода одной строкой `sed` — и её пишут. Многострочный предикат (`if` + пара присваиваний) руками
  скопировать **быстрее**, чем извлечь, — и его копируют. Оси в одном файле, дисциплина разная.
- ⚠ **Симптом-tell — арифметический и виден без запуска:** в харнессе есть `sed`/`grep` по
  `$PRODUCTION_FILE` для ЧАСТИ осей. Значит остальные оси читают что-то ещё — проверить каждую.
  (Тот же счёт «членов N, образцов 1», что §ТРЕТЬЯ форма weak-verifier, но применённый к осям.)
- ✅ **Floor: извлекать блок целиком и `eval`'ить**, с обязательным bail-out на неудачу извлечения —
  иначе пустая выборка даёт тождественно-зелёную ось вместо громкой поломки:
  ```bash
  PRED=$(sed -n '/^ *<первая строка блока>/,/^ *fi$/p' "$PROD")
  case "$PRED" in *<опорная-подстрока>*) : ;; *) echo "не извлёк — харнесс сломан"; exit 2 ;; esac
  ```
- ⛔ **Встроенный флаг мутации НЕ доказывает подлинность оси** — он мутирует харнесс. Доказывает
  только мутация **прода в копии** (`PROD=/tmp/mutant`): ось обязана покраснеть.
- ⛤ **Мутировать надо СМЫСЛ, а не наличие блока.** Удаление гварда краснит структурную проверку и
  создаёт иллюзию рабочей оси; **инверсия условия** оставляет блок на месте и меняет поведение на
  противоположное — вот она и есть решающая проба.

#### ⛔ Addendum 2026-08-07 — bail-out выше стережёт НЕДО-извлечение; ЗЕРКАЛО (ПЕРЕ-извлечение) не стережёт никто: диапазон, чей КОНЕЦ привязан к строке, которую мутант УДАЛЯЕТ, не закрывается и молча заглатывает ОСТАТОК ФАЙЛА

Floor выше (`case "$PRED" in *опорная-подстрока*`) отвечает на вопрос «извлёк ли я **хоть что-то**» и
потому ловит только пустую выборку. Обратный отказ рождается из **того же** решения — выбора анкера, —
но проверкой на непустоту не ловится **по построению**: над-широкий блок опорную подстроку содержит.

⛤ **Механизм.** Диапазон `awk '/начало/{f=1} f&&/конец/{exit} f{print}'` закрывается по анкеру конца.
Если этим анкером взята строка, которую **легитимный мутант удаляет** (сам детектор, сам гвард — то
есть ровно то, что мутируют), на мутанте диапазон **не закроется никогда** и утащит в извлечённый блок
весь хвост файла.

| | недо-извлечение | **пере-извлечение** |
|---|---|---|
| что в `$PRED` | пусто | **блок + весь остаток файла** |
| ловит ли bail-out | да | **нет** (подстрока на месте) |
| исход прогона | тождественно-зелёная ось | **пустой outcome** — читается как «ось не различает» |

- ⛔ **Дороже неверной метрики: это ВЕКТОР ПОБОЧНОГО ЭФФЕКТА.** §Update 2026-08-03 требует, чтобы
  харнесс был **структурно неспособен** мутировать мир; здесь автор уверен, что извлёк 30 строк
  предиката, а `eval` получает 400 — вместе с кодом, который **исполняется** (потолок расхода,
  вызовы CLI, спавн). Гарантия «мой харнесс безобиден» перестаёт быть свойством конструкции и
  становится **везением по содержимому хвоста**.
- ⚠ **Оба готовых теля НЕ фаерят.** Тель `waiting-decision-ping-before-selector` §Recurrence
  2026-08-07 («вывод драйвера пуст ЦЕЛИКОМ») молчит: драйвер печатает нормальную строку провала
  с ПУСТЫМ значением (`получено ''`), а не пустоту. Тель «несоразмерность числа краснот» тоже
  молчит: 3 краснот из 41 — вполне соразмерно.
- ✅ **Floor двойной, обе половины дёшевы:**
  1. **Анкерить ОБА конца на строки, которых мутант НЕ касается** — это тот же принцип, что для
     sanity-guard'а (`waiting-decision-ping-before-selector` §Recurrence 2026-08-07), просто
     применённый к **границе диапазона**, а не к условию гварда. Практически: конец брать на
     строке ПОСЛЕ мутируемой области (сброс счётчика, начало следующей секции).
  2. **Ассерт на РАЗМЕР извлечённого** — единственное, что отличает «блок» от «блок + хвост»:
     `[ "$(printf '%s
' "$PRED" | wc -l)" -le 40 ] || { echo "пере-извлёк"; exit 2; }`.
- ⛤ **Порядок правил в `awk` несущий:** `exit` обязан стоять ПЕРЕД `print`, иначе анкер конца сам
  попадает в выборку — и тогда мутант, удаляющий строку ВНУТРИ блока, снова меняет его границы.
- ⚠ **Симптом-tell, единственный работающий:** мутант даёт **пустой** outcome, а не НЕВЕРНЫЙ.
  Настоящая красная ось называет другой исход (`worker-quiet` вместо `worker-thrashing`); сломанное
  извлечение не называет никакого. Пустое значение в строке провала = смотри на диапазон, не на предмет.
- ⛤ **У того же пустого значения есть ВТОРАЯ причина, и она НЕ про диапазон: непарная кавычка ВНУТРИ
  извлечённой строки.** Строка вырезана правильно, но несёт хвост синтаксиса вызывающей функции
  (`… "$hint")` → закрывающая кавычка без открывающей) ⇒ `eval` рвётся и отдаёт пусто. Здесь диапазон
  ни при чём, и правка анкеров ничего не даст. ✅ Дискриминатор — распечатать саму извлечённую строку:
  оборванная кавычка/скобка на конце видна глазом мгновенно; лечится обрезкой хвоста
  (`H="${H%\"}"`) ЛИБО извлечением ЗНАЧЕНИЯ, а не всей строки вызова. Тот же класс, что
  `bash-loop-eval-pitfalls` Г4 (спецсимволы), но спецсимвол пришёл **из данных прода**, а не из твоей
  клавиатуры — поэтому Г4-рефлекс «кавычить своё» его не ловит.

**Empirical 2026-08-07** (`alp-size-refusal-verify.sh`, распознавание отказа по размеру в диспетчере
петли): диапазон `#--DETECT--` заканчивался на последнем ДЕТЕКТОРЕ — то есть ровно на том, что удаляет
мутант «снять детектор». На трёх мутантах из пяти блок не закрывался, `eval` получал ещё и потолок
расхода с `run_cli`, а цепочка возвращала пустой outcome ⇒ **3 ложные красноты**, прочитанные как
«ось C не работает». Починка — перенос анкера конца на строку сброса счётчика, присутствующую в **обеих**

записан в корпус **тем же днём** и применён мной к sanity-guard'у того же харнесса; к границе диапазона —

**Empirical 2026-08-05** (ALP `0e75f2a7`): в одном харнессе ось A извлекала регэксп из тика

⛔ **Recurrence 2026-08-05, через 43 МИНУТЫ после этой записи — тот же дефект в НОВОМ харнессе, у автора, у которого правило было в контексте.** Аддендум выше закоммичен в 15:12; воркер `alp-permprompt-verify.py` написан в 15:56 — то есть floor «мутировать СМЫСЛ, а не наличие блока» лежал в system-reminder всё время написания осей. Оси всё равно проверяли **наличие** конструкции: «блок предела существует», «в ветке есть счётчик». Мутант, заменивший порог литералом с `&& false`, оставил структуру на месте → харнесс зелёный, предел мёртв. Починено переводом осей на смысл: сравнение обязано **ссылаться на переменную-порог** и не быть короткозамкнутым.

- ⛤ **Что делает рецидив показательным: дело НЕ в памяти.** 43 минуты — это не забывание; правило было свежим и прочитанным. Проигрывает то, что ось «проверь, что блок есть» пишется в одну строку и выглядит завершённой, а ось «проверь, что условие означает то, что должно» требует решить, **какая мутация была бы содержательной**. Дешёвая форма побеждает не по незнанию, а по трению.
- ✅ **Практический floor, снимающий это трение: сначала напиши МУТАНТА, потом ось.** Мутант заставляет назвать смысл («что сломается, если порог перестанет быть порогом»), и ось выводится из него автоматически. Обратный порядок (ось → мутант) допускает ось, под которую мутанта не существует.
- ⚠ **Ловится тем же способом, что и в исходной записи — пер-мутантным прогоном и ревью, а не чтением.** Оба раза автор считал набор полным; оба раза красноту предъявил `code-reviewer`. Terminal accept-baseline: хук невозможен (нельзя механически отличить структурную ось от смысловой).

## §A17 — ⛔ Addendum 2026-08-06 — ассерт, чьё ОЖИДАЕМОЕ значение = ПУСТОЕ МНОЖЕСТВО, тождественно-зелён при мёртвом производителе; лечится не проверкой, а ЗАСЕВОМ положительного члена

Соседи выше — про мутанта (не туда / ничего не меняет / не тот субъект). Здесь мутант ни при чём: ось написана верно, гоняет что надо, но её **ожидаемое значение** — `[]`, и потому она не различает «производитель отработал и корректно ничего не нашёл» от «производитель мёртв». Обе ветки дают пустой список.

- ⛤ **Отличие от §ТРЕТЬЕЙ оси weak-verifier'а — в ЛЕЧЕНИИ, а не в диагнозе.** Там сканер обязан печатать РАЗМЕР ВХОДА рядом с числом находок (`scanned: 6, candidates: 0`). - ⚠ **Симптом-tell, ловится чтением набора:** в ассертах есть `toEqual([])` / `toHaveLength(0)` / `not.toContain(...)` для величины, которую **производит обход/сканер/фильтр**. Спроси: «а если этот обход вообще не выполнится — ассерт покраснеет?». Нет ⇒ ось вакуумна.
- ⛔ **Ручная трассировка «я проверил, что `[]` истинно» НЕ закрывает вопрос** — она доказывает первую ветку и молчит о второй. Закрывает только **мутант производителя** (ранний `return`), и он же отличает «починил» от «казалось».

## §A18 — ⛔ Addendum 2026-08-07 — ШЕСТАЯ механика: ось-ИСПОЛНИТЕЛЬ с НЕУНИКАЛЬНЫМ ЯКОРЕМ покрывает ТОЛЬКО ПЕРВЫЙ из N однотипных путей. Конверсия структурной оси в исполняемую переносит слепоту с ФОРМЫ на ОКНО ПОИСКА, а не устраняет её

§Addendum 2026-08-03 («мутация, которая ничего не меняет») и §Четвёртая форма 2026-08-05 («мутация легла НЕ ТУДА») — про **мутант**, промахнувшийся мимо цели. Зеркало: промахивается сама **ось** — она честно **исполняет** извлечённую из прода строку (то есть не структурная, floor §Update 2026-08-03 соблюдён), но извлекает **не ту** строку, потому что якорь ищется текстом.

⛤ **Ключевое: починка структурной оси на исполняемую НЕ закрывает класс — она его ПЕРЕНОСИТ.** Была слепота «считаю форму, а не поведение»; стала слепота «исполняю поведение, но не того экземпляра». Обе тождественно-зелёные, обе выглядят как выполненный floor.

**Два подвида, оба наблюдались за один заход:**

1. ⛔ **Окно поиска не ограничено** — якорь «дотягивается» до однотипной строки **ниже по файлу**, и ось проверяет чужой путь вместо своего. Мутант, ломающий целевой путь, остаётся **зелёным**.
   ```bash
   resets_of() {  # окно поиска после якоря ОГРАНИЧЕНО двумя строками
     awk -v a="$1" 'index($0,a)>0 && /rm -f/ && /NUDGEC/ {print; exit}
                    index($0,a)>0 && !/rm -f/ {f=2; next}
                    f>0 { if (/rm -f/ && /NUDGEC/) {print; exit} ; if (--f==0) exit }' "$TICK"
   }
   ```
2. ⛔ **Окно ограничено, но якорь НЕУНИКАЛЕН** — `awk … {print; exit}` берёт **первое сверху** совпадение, и все остальные пути с тем же текстом **молча не покрыты**. Симптом отсутствует: ось зелёная, извлечённая строка настоящая, исполнение честное.

- ⚠ **Дискриминатор — АРИФМЕТИКА, а не чтение осей:** число путей в проде против числа **индивидуально** проверенных. Одна команда:
  ```bash
  grep -c 'rm -f.*NUDGEC' prod.sh              # 12 путей
  grep -c '^resets_ok ' harness.sh             # 7 осей → максимум 7, и то при уникальных якорях
  grep -Fn '<якорь>' prod.sh                   # дубли якоря ⇒ реально покрыт ОДИН
  ```
  Расхождение = частичное покрытие, независимо от того, сколько осей зелено.
- ✅ **Floor: якорить по НОМЕРУ СТРОКИ либо по УНИКАЛЬНОМУ комментарию, отчеканенному специально под ось.** Текст самой строки кода — плохой якорь ровно потому, что однотипные пути пишутся одинаково (в этом и смысл однотипности).
- ⛤ **После починки ЛЮБОЙ оси — прогнать ВЕСЬ набор мутантов, а не только тот, ради которого чинил.** Правка оси — такая же правка, как правка прода, и ей полагается свой revert-verify. Зеркало §Update 2026-08-02 (новый гвард обнуляет покрытие старого) на **тест**-слое.
- ⚠ **Симптом-tell при ревью своего же харнесса:** якорь — это **строка кода**, а не комментарий/номер. Значит спроси `grep -Fc '<якорь>'` по проду прежде, чем считать ось покрывающей.

**Empirical 2026-08-07** (`alp-nudge-cap-verify.sh`, счётчик бесплодных толчков в петле): ревью round-1 показало, что ось C структурная (`false && ` перед сбросом оставляет 18/18 GREEN) → переписал на исполнение извлечённой строки. **Немедленно после фикса мутант M2 стал ЗЕЛЁНЫМ** — `resets_of` искал без ограничения окна и матчил чужой сброс ниже (подвид 1); поймано только потому, что после правки прогнал ВСЕ 7 мутантов, а не один. Round-2 (`code-reviewer`) вскрыл подвид 2: якорь `rm -f "$SLOT" "$NUDGEC"` встречается в проде **дважды** (`:549` и `:937`), якорь `rm -f "$SLOT" "$CAPPED" "$QUIET" "$PERMC" "$NUDGEC" "$NOTIFIED"` — **четырежды** ⇒ при 12 путях сброса и 7 осях индивидуально проверены **5**. Прод при этом признан корректным обоими раундами — дефект был чисто в покрытии. ## §A19 — ⛔ Addendum 2026-08-08 — СЕДЬМАЯ механика: якорь МУТАНТА, втянувший ПРОЗУ, протухает вместе с ней; отказ громкий, но `exit 0` ⇒ читается как зелёный. Лечится ФОРМОЙ МУТАЦИИ — ВСТАВКОЙ вместо перестановки блока

Механики выше — про **ось** (структурная · неуникальный якорь · вырезка вместо строки) и про **мутант, промахнувшийся мимо цели** (§Addendum 2026-08-03 «ничего не меняет», §Четвёртая форма 2026-08-05 «лёг в комментарий»). Седьмая — мутант, чей якорь **перестал матчиться вовсе** (`вхождений 0`), потому что он **охватывал прозу**, а прозу переписали.

⛤ **Почему проза попадает в якорь не по небрежности, а ПО ФОРМЕ МУТАЦИИ.** Мутант «переставить шаги 2 и 3» обязан взять **непрерывный** кусок текста, а между переставляемыми командами почти всегда стоит **пояснение** к первой из них. Значит перестановка **вынуждает** втянуть прозу — и якорь наследует её срок жизни. Правка пояснения (штатная, частая, кем угодно) убивает мутант.

- ⛔ **Отказ ГРОМКИЙ, но не меняет `exit` — и это опаснее тихого.** `⚠️ мутация не применилась — ось НЕ проверена` не инкрементит ни `PASS`, ни `FAIL` ⇒ rc остаётся 0, набор «зелёный». Читатель видит частокол ✅ и одну строку ⚠️ посередине. Это тот же **третий вердикт, схлопнутый в ok**, что `self-satisfying-metric-weak-verifier` §BROKEN — только на слое мутанта.
- ✅ **Floor: мутация ВСТАВЛЯЕТ, а не переставляет.** Вместо «поменять местами A и B» — «вставить копию B выше A». Якорь тогда = **маркер шага + сама команда**, ноль прозы, а ось (берущая `head -1`) видит именно вставленный элемент ⇒ краснеет ровно на проверяемом свойстве. Побочный дубль B ниже допустим и его надо **назвать намеренным**: он сохраняет нумерацию и канарейку, поэтому красной остаётся одна ось.
- ⛤ **Дискриминатор при написании мутанта:** посмотри, что лежит **между** элементами, которые собираешься переставить. Проза ⇒ перестановка невозможна без её втягивания ⇒ переходи на вставку.
- ⚠ **Симптом-tell при чтении вывода:** в прогоне есть `⚠️` — и ты идёшь дальше, потому что `FAIL=0`. Любая `⚠️` означает **ось не проверена**, то есть покрытие меньше заявленного; читать её надо как красную, пока не доказано обратное.

## §A20 — ⛔ Addendum 2026-08-09 — ВОСЬМАЯ механика: ПОРТ харнесса убивает ось не ПОТЕРЕЙ свойства образца, а его УЖЕСТОЧЕНИЕМ; отсутствие мутанта на эту ось делает смерть ненаблюдаемой

Корпус уже знает, что порт **теряет** уточнения референса (`self-satisfying-metric-weak-verifier` §Empirical 2026-08-05 «порт „по описанию“ потерял оба уточнения» (разделов с этой датой **четыре** — нужен тот, что про ПОРТ selftest-режима)). Обратное направление тише и контринтуитивнее: порт **добавляет строгости**, и добавка попадает ровно на токен, который удаляет легитимный мутант.

⛤ **Почему привычная осторожность не помогает: ужесточение проверки ощущается улучшением.** Широкий guard образца (`*spawn*|*SPAWN*`) выглядит небрежным — он матчит подстроку, присутствующую в **обоих** вариантах строки. Узкий (`*DLP_SPAWN*`) выглядит аккуратным: он проверяет именно то, ради чего ось написана. Но потому и сталкивается с мутацией, а широкий её переживает и пропускает мутанта к исполнению.

| guard | оригинал | мутант «захардкодить путь» | судьба оси |
|---|---|---|---|
| образец `*spawn*` (широкий) | ✓ | **✓ пропускает** | **жива** — мутант доходит до стаба |
| порт `*DLP_SPAWN*` (узкий) | ✓ | **✗ обрывает `exit 2`** | **мертва** — ни ✅, ни ❌ |

- ⛔ **Отсутствие мутанта на ось превращает этот дефект из громкого в невидимый.** `exit 2` заметен, только когда кто-то запускает мутанта; без него харнесс всегда зелен, и «ось D проверяет подменяемость» остаётся **заявлением**. Два нарушения множатся: §«сначала мутант, потом ось» не просто пропущено — его пропуск **скрывает** первое.
- ⚠ **Симптом-tell при порте, ловится чтением диффа:** ты сузил guard/якорь относительно образца, и новая формулировка называет **ровно предмет оси** (`$DLP_SPAWN`, имя порога, имя ветки). Предмет оси и есть то, что мутирует мутант ⇒ guard обязан якориться на **соседний инвариант** (`SPAWN_SESSION_ROLE`, терминальный выход, форма строки), а не на него.
- ✅ **Floor: сузив guard при порте — прогони мутанта ЭТОЙ оси немедленно.** Не «когда напишу драйвер»: между ужесточением и драйвером проходят десятки правок, и к моменту прогона причина забыта.
- ⛤ **Не откатывать ужесточение целиком.** Широкий guard образца пропускает мутанта, но и хуже ловит настоящую поломку извлечения. Верный размен — **узкий якорь на инвариант**: строже широкого и при этом мутанту не по зубам.

## §A21 — ⛔ Addendum 2026-08-09 — ВЫБИРАЯ мутанта: тот, чей эффект зависит от СРЕДЫ, хуже отсутствующего. Флаки-ось не «слабее» — она ОТРАВЛЯЕТ набор

Все механики выше отвечают на «краснеет ли ось». Недостающий шаг — **выбор между двумя мутантами, которые оба формально её краснят**. Соблазн взять тот, что ближе к формулировке гварда («гвард — это `sorted()`, значит мутант — снять `sorted()`»), и он же часто оказывается **вероятностным**: эффект зависит от порядка ФС, `PYTHONHASHSEED`, времени, сети, порядка обхода словаря.

- ⛔ **Флаки-ось не деградирует до «иногда ловит» — она деградирует до НЕЧИТАЕМОЙ.** Ось, краснеющая через раз, за два-три прогона получает ярлык «шум», и дальше её красноту **пролистывают вместе с настоящей**. То есть один вероятностный мутант обесценивает не себя, а **доверие ко всему набору** — это дороже, чем непокрытый гвард, о котором хотя бы известно, что он непокрыт.
- ⛤ **Дискриминатор при выборе: «зависит ли исход мутанта от чего-то, кроме моего кода?»** Да ⇒ ищи детерминированную замену, а не принимай «обычно краснеет». Обычно — это про сегодняшнюю ФС, а ось живёт годами.
- ✅ **Детерминированная замена почти всегда есть и требует ФИКСТУРЫ, а не другого мутанта.** Гвард без наблюдаемого предмета → **дай ему предмет**: у сортировки это **ничья** в фикстуре (два элемента с равным счётом), у дедупа — дубль, у нормализации — два написания одного значения. Тогда мутант становится тривиально детерминированным (`sorted(..., reverse=True)` вместо «снять `sorted()`»), и ось краснеет **всегда**.
- ⛤ **Отвергнув мутанта ревьюера — назови ПРИЧИНУ и предъяви замену.** «Не беру, потому что эффект зависит от hash-seed; вместо этого фикстурная ничья + разворот сортировки» — это разрешение находки, а не отклонение: гвард в итоге покрыт **лучше**, чем предлагалось.
- ⚠ **Оставшуюся вакуумной ось не выбрасывать молча, а ПОМЕТИТЬ в коде.** Если после введения предмета часть исходной оси всё равно никем не краснеет (у меня — «два прогона идентичны»), её вакуумность пишется рядом с ней прямым текстом; иначе следующий читатель примет зелёный за покрытие (`self-satisfying-metric-weak-verifier`).

Мутант отвергнут: порядок `glob.glob` на неизменном каталоге стабилен **на практике**, поэтому ось краснела бы от среды, а не от кода. ## §A22 — ⛤ Addendum 2026-08-09 — ЗЕРКАЛО «ручной копии»: когда прода ЕЩЁ НЕТ, копию держит ОТГРУЗКА, и floor «извлекай из прода» неприменим по построению

§Addendum 2026-08-05 (СМЕШАННАЯ дисциплина) лечит ось, держащую **копию прода** вместо извлечения. Его floor — «извлекать блок из `$PRODUCTION_FILE`» — предполагает, что прод **существует**. Для **нового** артефакта (новый precondition, новый конфиг, впервые отгружаемая форма) это не так: прода нет, есть только форма, которую ты проверяешь. Тогда копию держит **не ось, а отгрузка**, и направление зависимости обратное.

- ⛔ **Механизм: харнесс собирает проверяемую форму СВОИМ кодом, а apply-скрипт — своим.** Оба выглядят источником истины, расходятся молча, и матрица честно зеленеет на форме, которая на прод **не поедет**. Это тот же класс, что «матрица снималась на другом тексте запроса»: проверка была, но проверяла не то (`verify-before-assert`).
- ⛤ **Особенно вероятно, когда формы собираются РАЗНЫМИ способами:** харнесс склеивает предикат из кусков (чтобы уметь снимать конъюнкты по одному), а отгрузка пишет его целиком. Куски и целое — два представления одного, и совпадение держится на дисциплине, а не на конструкции.
- ✅ **Floor: отгрузка ЧИТАЕТ форму из АРТЕФАКТА ХАРНЕССА, а не собирает заново.** Харнесс всё равно сохраняет прогнанные варианты (json/лог) — их и брать: `ASK = json.load(open("matrix-full.json"))["variants"]["BASE"]`. Тогда «отгружено то, что проверено» становится свойством **конструкции**, а не намерением.
- ⛤ **Если второй источник всё же остался — байт-в-байт гвард с ТЕРМИНАЛЬНЫМ выходом**, а не сверка глазами: расхождение здесь означает, что вся матрица относится к другому артефакту, поэтому гвард обязан **останавливать отгрузку**, а не предупреждать.
- ⚠ **Симптом-tell, ловится чтением до прогона:** проверяемая форма встречается **дважды** — в харнессе и в апплае. Два вхождения одной формы = два источника, независимо от того, насколько они сейчас похожи.
- ⛤ **После отгрузки сверять по СОДЕРЖИМОМУ записанного артефакта**, а не по коду возврата: `set-property`/`set-body` рапортуют `rc=0` и при корректной, и при неполной записи.

## §A23 — ⛤ Addendum 2026-08-09 — ДЕВЯТАЯ механика, зеркало восьмой: порт ДОБАВЛЯЕТ ось, которой у образца НЕТ, — и она РЕТРОАКТИВНО доказывает дефект в ОБРАЗЦЕ

Восьмая механика (§выше) — порт **убивает** ось ужесточением. Обратное направление: порт **добавляет** ось (по требованию ревью либо ради полноты), и эта ось — не только гейт твоей работы, но и **детектор дефекта в источнике, откуда копировали**.

⛤ **Механизм:** зеркаля прецедент, ты наследуешь его **непроверенные гарантии**. Пока у прецедента нет оси на конкретную гарантию, его дефект по этой гарантии **невидим и жив** — не потому что редок, а потому что **некому покраснеть**. Твоя новая ось разрывает симметрию: она краснит у тебя, а прогнанная против образца — краснит и там.

- ✅ **Floor: добавив ось, которой у прецедента НЕ БЫЛО, прогони её ПРОТИВ прецедента.** Одна команда, и она различает два исхода, неразличимых иначе: «дефект только у меня, образец чист» против «дефект был в источнике и я его унаследовал». Второй исход означает, что копировали **дефектную** форму — и следующий, кто скопирует, унаследует её снова.
- ⛤ **Это ТРЕТИЙ, самый дешёвый детектор класса «прецедент несёт латентный дефект»** (`migration-pre-verify-use-case` §Addendum 2026-08-07 п.1). Тот аддендум предлагает обнаружение **чтением** (сверить направление видимости), `self-satisfying-metric-weak-verifier` §«Floor держится на починенном компоненте» — **грепом политики** (у кого нет проверки). Здесь — **исполнением**: у тебя уже есть работающая ось, прогнать её на соседе стоит секунды и не требует ни знать, где смотреть, ни угадывать форму дефекта.
- ⚠ **Симптом-tell, ловится в момент написания оси:** ты добавляешь ось на гарантию, которую **не проверял и образец**. Спроси: «есть ли у прецедента ось на это?» Нет ⇒ его дефект по этой гарантии не опровергнут, а **не проверен** — разные вещи.
- ⛔ **Исход НЕ обязан быть правкой образца.** Если образец — механизм, который **тебя же и исполняет** (петля-супервизор, раннер, диспетчер твоей сессии), правка его на ходу запрещена (`child-scope-immutability`) ⇒ follow-up. Но follow-up обязан нести **порт ОСИ и МУТАНТА**, а не только строчку фикса: иначе сосед получит заплату и снова останется без детектора, и класс воспроизведётся с третьим потребителем.
- ⛤ **Не путать с sibling-sweep** (`verify-before-assert` §sibling-symbol cascade): там ищут **соседей по коммиту** уже найденного дефекта. Здесь дефект в источнике **ещё не найден** — его существование выводится из того, что у источника нет оси, и подтверждается её прогоном.

## §A24 — ⛔ Addendum 2026-08-11 — гвард, КЛЮЧЁВАННЫЙ К РЕАЛЬНОМУ КОРПУСУ (храповик), НЕ проверяется копией дерева: инъекцию дефекта делай в ЕГО ДАННЫЕ, а гасящий мутант обязан КОМПОНОВАТЬСЯ поверх неё

§ZERO-GIT-TOUCH предписывает ломать **копию** дерева. Но у гварда, который **сам решает, работать ли ему** (сверяет путь корпуса с эталонным — храповик, монотонная метрика, baseline-allow-list), копия даёт **ложно-зелёное по построению**: на копии путь не совпадает ⇒ гвард **выключает себя** и рапортует «чисто», не исполнив ни одной проверяемой ветки.

- ⛔ **Соблазн, который надо назвать: «внесу дефект в живой корпус».** Для гварда над **общим** состоянием (каталог скиллов, реестр, vault) это мутация того, чем пользуются другие сессии, — запрещено ровно так же, как правка рабочего дерева.
- ✅ **Floor: инъекция идёт в ДАННЫЕ гварда, а не в корпус.** У храповика такие данные — его **базовая линия**: убрал имя из линии ⇒ живой объект стал «новым» ⇒ ветка регрессии достижима, корпус не тронут. Один и тот же приём даёт и второе направление (добавил в линию имя, которого в корпусе нет ⇒ ветка протухания).
- ⛤ **Гасящий мутант обязан КОМПОНОВАТЬСЯ с инъекцией, а не заменять её.** Ось «есть ли гвард» = инъекция **плюс** снятие гварда; применив одно вместо другого, получишь «мутант не изменил поведение» и прочитаешь это как «ось не различает». Практически — мутатор принимает **список** замен и падает fail-loud, если якорь встретился ≠ 1 раз:
  ```python
  def mutant(tmp, tag, old, new, extra=()):
      for o, n in ((old, new),) + tuple(extra):
          if src.count(o) != 1: broken("мутант %s: якорь встречается %d раз(а)" % (tag, src.count(o)))
          src = src.replace(o, n, 1)
  ```
- ⚠ **Гвард корпуса сам обязан быть осью** — иначе он ZERO-locked: сузишь его условие (или снимешь `realpath`, а корпус смонтирован симлинком) — и храповик молча выключится на боевом прогоне. Ось: **запуск через симлинк-путь** + мутант «плоское сравнение вместо `realpath`».
- ⚠ **Симптом-tell:** твой гвард читает **путь/идентичность корпуса** и на несовпадении **тихо смягчается**. Всякое «смягчается» без печати причины = ветка, которую копия дерева проверить не может, а фикстура — не имеет права.

**Empirical 2026-08-11** (`rules-xref-check.py` ↔ `rules-xref-check-verify.py`, ALP `8e6d4a66`): храповик ключуется на `~/.claude/skills`, поэтому фикстурные корпуса его не упражняют **вовсе**. Все четыре состояния (новый долг / долг погашен / имя исчезло / корпус не тот) предъявлены инъекцией в `PARTIAL_BASELINE` + композицией мутантов; 7 новых осей, 6 мутантов, каждый краснит ровно свою. `code-reviewer` нашёл, что `realpath`-подтерм был **несущим и ZERO-запертым** (плоское сравнение давало `PASS=99 FAIL=0`) — закрыто отдельной осью с запуском через симлинк.

## §A25 — ⛔ ЗЕРКАЛО §A7: правка добавила код, исполняемый на входах, которые СУЩЕСТВУЮЩИЙ ранний выход ПРОПУСКАЕТ — твои оси этого не видят ПО ПОСТРОЕНИЮ

В наблюдённом файле это был **второй** случай: предыдущий уже стоял в нём комментарием с собственной осью, и я воспроизвёл класс, редактируя строки рядом.

## §A26 — ⛔ Ось на ГОНКУ: ждать ФАКТИЧЕСКОГО состояния, а не фиксированного числа тиков — и МУТАЦИЯ ТОЖЕ должна попасть в окно


<!-- Added by /session-retrospective 2026-08-14 — root: ALP alp-24993104, ось «invalidate() во время идущего обхода не ставит устаревший индекс» была зелена ПРИ СНЯТОМ гварде. -->

Ось, проверяющая **порядок** (гонка, отмена, инвалидация во время работы), устроена так: подвесить предмет → изменить мир → снять гвард → убедиться, что предмет заметил изменение. Обычная ошибка — смоделировать «дать предмету дойти до подвеса» **фиксированным** ожиданием (`await Promise.resolve()`, один-два `setTimeout(…,0)`).

⛔ **Этого не хватает по построению, если предмет уходит в ожидание НЕ на первом await'е.** Рекурсивный обход, цепочка запросов, вложенные слои — каждый уровень съедает свои микрозадачи. Тогда к моменту мутации мира предмет уже **отработал целиком**, увидел НОВЫЙ мир, и результат совпадает с ожидаемым — то есть **тест зелен и с гвардом, и без него**.

- ⚠ **Симптом-tell отсутствует у наблюдателя:** ось выглядит написанной верно, мутация применяется, набор зелёный. Единственный детектор — **прогнать мутанта** и увидеть, что он НЕ роняет свою же ось.
- ✅ **Floor: ждать ФАКТА, а не времени.** Предмет (через фейк/порт) выставляет флаг ровно в точке подвеса; тест крутит `while (!suspended) await new Promise((r) => setTimeout(r, 0));`. Тогда окно открыто **гарантированно**, независимо от глубины.
- ⛤ **Подвешивать надо в ПРАВИЛЬНОЙ точке, а не в первой попавшейся.** Подвес на **первом** обращении оставляет остаток работы на «после релиза» — и он увидит новый мир, снова обнуляя различимость. Подвешивай там, где предмет **уже собрал старую картину целиком** (последнее обращение), тогда изменение мира физически не может в неё просочиться.
- ⛤ **У направления мутации есть различимость, и она несимметрична.** «Убрать сущность» часто НЕ различает устаревший результат от свежего (обе ветки упираются в один и тот же отказ ниже по течению — файла нет, ссылка не резолвится). «**Добавить** сущность» различает: устаревший результат её не содержит, свежий содержит. ⇒ на гонках выбирай ADD-направление.

### ⛔ ЗЕРКАЛО floor'а «ждать ФАКТА»: над ОТЦЕПЛЁННЫМ предметом он НЕПРИМЕНИМ — доказательство ОТСУТСТВИЯ требует ФИКСИРОВАННОЙ паузы, ВЫВЕДЕННОЙ из положительного случая

<!-- Added by /session-retrospective 2026-08-26 — root: тикет 4479364a, харнесс надзора D6: положительная ось ждёт факта (sc_wait), отрицательная спит фиксированно (sc_quiet); floor «ждать ФАКТА, а не времени» покрывает только первую, и наивный перенос его на вторую даёт вакуумную ось. -->

Floor выше («ждать ФАКТА, а не времени») верен для **положительной** оси: факт наступит, надо лишь
дождаться. ⛔ Для **отрицательной** («вызова НЕ было», «ничего не отправлено», «лечение не
запущено») ждать нечего **по построению** — факта, которого ты ждёшь, не существует. Цикл ожидания
там либо крутится до таймаута, либо — что пишут чаще — **снимается вовсе**.

⛔ **Снятый вовсе = проверка СРАЗУ после запуска, и над отцеплённым предметом она ВАКУУМНА.**
`setsid`/`start_new_session`, фоновый процесс, очередь, сетевой вызов — предмет физически не успел
записать, и пустота читается как «не вызывал». Ось зелена **и при снятом гварде**.

- ✅ **Floor: отрицательная ось = ФИКСИРОВАННАЯ пауза + проверка ЭФФЕКТА.** Это не регресс
  дисциплины, а другой предмет доказательства: положительное доказывается наступлением, а
  отрицательное — **истечением окна**, в которое наступление было бы видно.
- ⛔ **Паузу ВЫВОДИТЬ ЗАМЕРОМ положительного случая, а не назначать.** Сколько занимает запись у
  настоящего вызова × запас. Назначенная «на глаз» пауза даёт ту же вакуумность, только с
  задержкой — и выглядит при этом дисциплинированной.
- ⛤ **Замер обычно БЕСПЛАТЕН: положительная ось уже его делает.** Если её опрос в норме отрабатывает
  на первой итерации, шаг опроса × N и есть обоснованный запас. Тогда обе оси связаны одним числом,
  и оно не выдумано.
- ⚠ **Симптом-tell, ловится ЧТЕНИЕМ набора:** рядом стоят две функции ожидания ОДНОГО И ТОГО ЖЕ —
  одна опрашивает, другая спит. Асимметрия **правильна**; ⛔ не «унифицировать» их под опрос —
  унификация убьёт отрицательную ось, оставив её ждать несуществующего факта до таймаута.
- ⛤ **Эффект проверять АРТЕФАКТОМ предмета** (журнал вызовов, файл, счётчик), а не отсутствием
  строки в СВОЁМ выводе: отсутствие строки доказывает, что ты её не напечатал, а не что вызова не
  было (`activity-signal-is-not-progress` §Floor).

**Empirical 2026-08-26** (`vteam-supervise-verify.sh:523-524`, харнесс надзора D6): пара
`sc_wait()` — опрос 30 × 0.1 с до появления записи (положительные оси, AC2) и
`sc_quiet() { sleep 0.7; [ ! -s "$SCLOG" ]; }` — фиксированная пауза (отрицательные оси AC3/AC4/AC5:
«лечение НЕ запущено»). Предмет — `self-compact.sh`, запускаемый **отцеплённым**, поэтому проверка
без паузы была бы зелена при любом состоянии гварда. Обоснование запаса: положительная ось
укладывается в первую итерацию (≤0.1 с) ⇒ 0.7 с = **7×**. ⛤ AC7 того же набора добирает вторую
половину floor'а — «ничего не отправил» доказано **пустым журналом `send-keys`** подменённого
`tmux`, а не отсутствием строки в выводе.

## §A27 — ⛔ Фикс, обоснованный СИММЕТРИЕЙ с соседней проверкой, требует ТРЕТЬЕЙ оси: обе объявленные его регрессию ПРОПУСКАЮТ


<!-- Added by /session-retrospective 2026-08-23 — root: тикет c349803c/req 501cdf2c, StageSpecification. -->

Типовая формулировка фикса: «у имени свойства валидация есть, у значения нет — **симметрия нарушена,
правка её восстанавливает**». Она звучит как вывод из механизма и им не является: обе стороны
валидируются **по своим** допустимым множествам, и дословный перенос предиката (`X.trim().length === 0`
с имени на значение) режет живые значения другой стороны.

- ⛔ **Пара осей, которую такой req объявляет сам («пустое ⇒ отказ» + «`false`/`0` ⇒ запись»),
  регрессию НЕ ЛОВИТ:** слишком широкий гвард удовлетворяет обе и проходит зелёным. Нужна **третья**
  ось — на форму, которая по строгому предикату проходит, а по скопированному отсекается.
- ✅ **Floor: ширину предиката выводить ЗАМЕРОМ живых носителей ДРУГОЙ стороны, а не симметрией.**
  Один проход по frontmatter/корпусу: сколько значений попадает между строгой и расширенной формой.
  Ноль ⇒ переносить можно; больше нуля ⇒ каждое из них твой «фикс» отнимает.
- ⚠ **Симптом-tell, ловится ДО написания кода:** в обосновании стоит слово «симметрия» / «как у
  соседнего поля» / «по аналогии», и ты **не можешь назвать замером**, совпадают ли допустимые
  множества сторон. Совпадение формы предиката ≠ совпадение множества.
- ⛤ **Ошибка идёт в самую дорогую сторону: отнимает ЕДИНСТВЕННЫЙ рабочий путь.** Если у формы,
  которую съедает расширенный гвард, других писателей нет, свойство становится неписуемым **ни одной
  командой** — то есть фикс не «слегка строг», а выводит функциональность из строя.

**Empirical 2026-08-23** (`set-property --value ""` создаёт `prop: ""`, req `501cdf2c`): §«Где чинить»
предписывал восстановить симметрию с `property.trim().length === 0`. Замер трёх vault (34 327 файлов,
331 263 ключа, заголовки multi-value отсечены) дал: форма `key: ""` — **0** носителей (запрет
безопасен), форма `key: " "` — **15** живых (`exo__PrintedLiteral_literal` 9,
`exo__DisplayNameSpec_separator` 6), и `set-property --value ' '` — **единственный** документированный
способ их записать (`create` срезает обрамляющие пробелы). ⇒ граница исправлена на строгую
`value === ""`, третья ось (`" "` ⇒ запись) добавлена в req.

### ⛔ У §«Где чинить» ВТОРАЯ форма отказа — МЕСТО, а не предикат; и третья ось ВАКУУМНА, если её фикстура ПРАВДОПОДОБНА, а не ИЗМЕРЕНА

<!-- Added by /session-retrospective 2026-08-23 — root: реализация того же req 501cdf2c (PR #4183). Секция выше ловит ширину предиката; оба дефекта ниже она пропускает. -->

Секция выше лечит **ширину предиката**, названную в §«Где чинить». Тот же пункт требования несёт
**второе** утверждение — **координату в коде** («чинить внутри `<функция>`, обе ветки»), — и оно
проверяется отдельно: координата есть **claim о потоке управления**, а не адрес.

- ⛔ **Дословная реализация РЕГРЕССИРУЕТ, когда названная точка стоит ВЫШЕ существующих гвардов.**
  Валидация ЗНАЧЕНИЯ, поставленная перед гвардами ИМЕНИ, перехватывает вход, который сегодня
  отвергается **верно и по другой причине**, — то есть подменяет корректный вердикт своим. Дефект
  тише обычного: оба исхода «отказ», меняется лишь **основание**, и ни один существующий тест этого
  не видит.
- ✅ **Floor: измерить ОБА конца названной точки на опубликованном артефакте** — вход, который сегодня
  обрабатывается **верно**, и вход, на котором живёт дефект. Совпали по маршруту ⇒ координата верна;
  разошлись ⇒ гвард ставится **после** всех проверок того класса, что уже работает.
  ```bash
  <cli> set-property <p> --property <ГВАРДЕД-имя>   --value "" --vault <v>   # обязан отказать ПО-СТАРОМУ
  <cli> set-property <p> --property <обычное-имя>   --value "" --vault <v>   # здесь и живёт дефект
  ```
- ✅ **Отклонился от буквы — ЗАПРИ отклонение своей осью + мутантом:** ось «гвардед-свойство сохраняет
  прежний отказ» и мутант «поднять новый гвард выше гвардов имени» ⇒ краснеет **ровно** она. Без этой
  пары отклонение — мнение, и следующий рефактор вернёт координату из требования.
- ⛔ **И назвать отклонение в теле PR/тикета с ЗАМЕРОМ.** Иначе приёмщик читает расхождение с §«Где
  чинить» как scope drift (`decision-surface-must-derive-from-mechanism` §форма №6).

⛔ **Второй дефект — в самой ТРЕТЬЕЙ оси: её фикстура обязана нести ИЗМЕРЕННУЮ форму, а не правдоподобную.**
Floor выше выводит **предикат** замером живых носителей и на этом останавливается; значение фикстуры
при этом выбирается «реалистичным» — и ось становится **вакуумной**, потому что расширенный предикат
на нём не срабатывает.

- ⚠ **Симптом-tell — только МУТАНТ:** мутант, воспроизводящий отвергнутую широкую форму, **не краснит
  ничего**. Контроль зелёный, ось выглядит написанной, различимости нет.
- ✅ **Floor: значение фикстуры берётся из ТОГО ЖЕ замера, что и предикат** — из перечня живых
  носителей, а не из головы. Замер уже сделан; переиспользовать его дешевле, чем угадывать.
- ⛤ Правдоподобная форма может отличаться от измеренной **ровно тем**, что снимает различимость:

## §A28 — ⛔ КОНТРОЛЬ ПЕРВЫМ: у копии-вне-репозитория ломается РЕЗОЛЮЦИЯ МОДУЛЕЙ, и «сьют не запустился» рапортуется как `Tests: 0` — то есть неотличимо от «ничего не упало»


§A10 (`ZERO-GIT-TOUCH`) велит ломать **копию**. У приёма есть отказ, не связанный ни с мутацией, ни с предметом: копия лежит вне рабочего дерева, поэтому подъём по `node_modules` до воркспейса не доходит, и сьют **не запускается**. Раннер печатает `Tests: 0 total` либо усечённое число — а это ровно та форма, в которой выглядит успех.

- ⛔ **§A3 этот случай НЕ покрывает.** Там `Tests: 0` от того, что **твоя break-правка не скомпилировалась**; здесь мутация корректна, а сломан **харнесс**. Симптом один, корень другой, и лечение другое.
- ✅ **Floor: прогнать НЕМУТИРОВАННУЮ копию ПЕРВОЙ и потребовать от неё точный baseline.** Не сошлось — числа мутантов не значат ничего, и читать их нельзя. Один лишний прогон, зато вердикт становится осмысленным.
- ⚠ **Корней у этого минимум два, и второй не угадывается:** (а) не резолвится транзитивная зависимость (`tslib`) — лечится симлинком `node_modules` в корень копии; (б) **дублирующий пакет**: `packages/<x>/node_modules/<dep>` держит CJS-версию, а корень хойстит ESM-версию, и, исключив `node_modules` из копии, ты молча повышаешь сборку до ESM. Лечится симлинком **пакет-локального** `node_modules` тоже.
- ⛤ **Число «прошло» врёт тише, чем число «упало».** Не-запустившийся сьют вносит **0**, поэтому сравнение итогов выглядит стабильным, пока покрытие незаметно уменьшилось. Сверять надо **число сьютов**, а не только тестов.

## §A29 — ⛔ ВЕРДИКТ ДОЛГОГО ХАРНЕССА — функция НАГРУЗКИ МАШИНЫ, а не только предмета: не гоняй его параллельно с другой тяжёлой работой


Харнесс на десятки минут, у которого каждая ось — отдельный `subprocess` с таймаутом, при
параллельной CLI-нагрузке начинает давать **красноту, не относящуюся к предмету**: часть прогонов
не успевает произвести разбираемый вывод, оси читают `None`, и мутанты «пересвечивают» — краснят
куда больше осей, чем объявили. Внешне это неотличимо от регрессии: набор красный, имена осей
настоящие, вердикт `FAIL`.

- ⛔ **Опаснее обычного флака, потому что бьёт по МУТАНТАМ, а не по контролю.** Контроль остаётся
  зелёным (он гоняется первым, машина ещё свободна) ⇒ ты видишь «предмет исправен, но мутанты
  разошлись» и ищешь дефект в различимости осей — то есть в самом тонком месте, где искать дороже
  всего.
- ⚠ **Симптом-tell, ловится по ФОРМЕ красноты:** пересветившие наборы **комплементарны** (один
  мутант краснит одну половину осей, другой — ровно оставшуюся), и у красных осей поля разбора
  пусты (`занятость=None`, `выдача=[]`), а не содержат неверные значения. Неверное значение = дефект
  предмета; **отсутствие значения** = прогон не доехал.
- ✅ **Floor: долгий харнесс — ЕДИНСТВЕННАЯ тяжёлая работа в окне.** Пока он идёт, не запускать ни
  живые прогоны предмета, ни соседние харнессы, ни CLI-запросы. В промптах это обычно стоит как
  совет по СТОИМОСТИ («гоняй один раз в конце») — читать надо как условие **корректности** вердикта.
- ✅ **Разделить «предмет» и «условия» можно только ФЛИПОМ, и он двусторонний:** прогнать тот же
  харнесс (а) на **до-правочном** предмете (`SUT=$(git show <sha>:<путь>)` — большинство харнессов
  берут предмет из env) и (б) на **своём** — оба в тишине. Строки различаются ровно одной
  переменной, и вывод следует из таблицы, а не из правдоподобия:

  | прогон | предмет | условия | вердикт |
  |---|---|---|---|
  | 1 | мой | ⛔ под нагрузкой | FAIL |
  | 2 | до-правочный | тихо | PASS |
  | 3 | **мой** | тихо | **PASS** |

  2 и 3 различаются ТОЛЬКО предметом и обе зелены ⇒ предмет ни при чём; 1 и 3 — ТОЛЬКО условиями.
- ⛤ **Дешевле флипа (минуты против часов) — ТОЧЕЧНЫЙ ЗОНД: одна фикстура, оба предмета, ±мутация.**
  Строить фикстуру **кодом самого харнесса** (`importlib` + его `build_vault`/`item`), а не
  переизобретать — иначе меришь свою реконструкцию. Зонд отвечает на вопрос «делает ли мой предмет
  на фикстуре хоть что-то иначе», и ответ «нет, побайтно так же» снимает гипотезу о коде **до**
  того, как тратить час на полный прогон.
- ⛔ **Красный ДОЛГИЙ харнесс из раннера — КАНДИДАТ, а не находка; но «источник шума» ищи
  СНАЧАЛА В СЕБЕ.** Ниже — два поворота одного дня, оба показаны, потому что каждый по
  отдельности выглядел убедительным выводом. Итог: раннер последователен по построению, и
  если пере-прогон «в тишине» идёт МЕДЛЕННЕЕ раннерского — шумит проверяющий, а не раннер.
  Прогоняя набор ПОСЛЕДОВАТЕЛЬНО, раннер выглядит «одной тяжёлой работой»; долгий харнесс
  внутри него действительно соседствует с чужой нагрузкой (интерактивная сессия, боты,
  ждуны) — но это гипотеза, требующая ЗАМЕРА, а не объяснение по умолчанию.
  ⚠ **Симптом-tell дешевле флипа:** в вердикте раннера красных **мало** (1-2 из десятков), и
  это всегда САМЫЕ ДОЛГИЕ харнессы — то есть те, чьё окно шире всего, и потому вероятность
  пересечься с чужой нагрузкой у них максимальна. Короткие в тот же прогон зелены.
  ✅ **Floor: красный ДОЛГИЙ харнесс из раннера — не находка, а КАНДИДАТ.** Прежде чем заводить
  дефект, пере-прогнать его ОДНОГО в тишине.
  ⛔ **КОРРЕКЦИЯ (в тот же день, показана, а не переписана молча): мой собственный «замер»,
  стоявший здесь, был ЛОЖНЫМ — и ровно того класса, ради которого пишется эта страница.**
  Я утверждал, что `vteam-record-verify.py` краснел в раннере осями H2/H4, а в тишине дал
  ✅ H2 / ✅ H4 ⇒ «contention». Фактически я читал **вывод МУТАНТА M1**, приняв его за
  контроль: одиночный прогон печатает `=== КОНТРОЛЬ` → `✅ Контроль: 27/27 осей зелены`
  (строка 30) → `=== M1 схлопывание снято` (строка 32), и красные H2/H4 лежали на строках
  55/57 — **внутри блока M1**, где их краснота есть ОЖИДАЕМЫЙ исход.
  ⚠ **Симптом-tell, который я пропустил:** `grep -c '❌'` по всему выводу дал **34** при
  контроле 27/27 — то есть счёт смешивал контроль и мутантов. Красноты «в контроле» не было

  ТОЛЬКО до первого мутанта, а вердикт брать из строки `Контроль: N/N`. ⛔ `grep -c` по всему

  ⛔ **И ВТОРОЙ поворот того же дня: contention создавал Я, а не раннер.** Пере-прогон «в

  тот же харнесс в раннере. Раннер по построению последователен; если у тебя медленнее — шумишь

## §A30 — ⛔ Мутацию может ОТМЕНИТЬ САМ ПРЕДМЕТ по ходу прогона: ось зелена/красна не по своей логике, а по тому, доступен ли механизм самовосстановления


Разделы выше разбирают мутацию, которая **не применилась** (§A12: no-op форма, якорь в комментарии) и мутацию, которая **не попала в окно** (§Ось на ГОНКУ). Третий случай: мутация применилась корректно, окно правильное — а предмет **вернул состояние обратно сам**, потому что мутированный артефакт для него не источник истины, а **производный кэш**.

- ⛤ **Механизм:** предмет на промахе кэша перестраивает его из настоящего источника (онтология, БД, конфиг, remote) и перепроверяет. Твоя правка кэша при этом живёт ровно до первого промаха — то есть до момента, который сам же тест и вызывает.
- ⛔ **Ось при этом НЕ вакуумна — она отвечает на другой вопрос.** «Убрал строку → блок» верно, пока путь самовосстановления **недоступен**; в проде он доступен, и та же ось даёт **allow**. Оба исхода корректны, а вывод «гвард читает этот файл» — только у первого. ⇒ ось, чей исход зависит от наличия соседнего скрипта, обязана называть это условие в своём имени.
- ✅ **Floor: прогнать ОБА состояния и предъявить оба.** (а) без механизма самовосстановления — доказывает, что артефакт вообще читается; (б) с ним — показывает боевое поведение. Расхождение исходов и есть находка: **артефакт не является источником истины**.
- ✅ **Настоящий дискриминатор ищи в ИСТОЧНИКЕ, а не в кэше:** вход, которого нет в источнике (необъявленный предикат, отсутствующая запись), заблокирован **при любом** состоянии кэша — это единственная ось, чей исход не зависит от самовосстановления.
- ⚠ **Симптом-tell до написания оси:** артефакт, который ты собрался мутировать, кто-то **генерирует** — рядом лежит `refresh-*` / `rebuild-*` / `*-cache.*`, либо в шапке самого предмета написано «Cache: …». Тогда «правка файла» и «изменение поведения» — разные вещи, и первое не влечёт второго.

**Empirical 2026-08-16** (задача `3a79a2ce`, whitelist предикатов): `valid-properties.txt` выглядел рукописным whitelist'ом; фактически его пересобирает `refresh-properties-cache.sh` сканом трёх vault и заменяет через `mv`. Ось A2 (снять строку, refresh недоступен) → deny с именем снятого предиката; ось A4 (та же мутация, refresh доступен) → **allow**, кэш восстановлен по ходу прогона, а заблокированным остался только необъявленный `flow__Stage_bogusZzz`. Прогон обоих состояний — единственное, что показало: источник истины не файл, а онтология, и «внести предикат руками» бесполезно (следующий `mv` затрёт).

## §A31 — ⛔ Гвард, чья ценность в ДИАГНОСТИКЕ, требует оси на СОДЕРЖИМОЕ сообщения — набор осей по коду возврата к ней слеп ПО ПОСТРОЕНИЮ


У блокирующего гварда две поставки: **решение** (пропустить/заблокировать) и **сообщение** (что теперь делать). Оси пишутся на первую — она выражается кодом возврата и проверяется тривиально. Вторая остаётся непокрытой, хотя именно она и есть причина, по которой блокировка полезна: заблокированный читатель без внятного текста не знает ни предмета, ни выхода.

- ⚠ **Симптом-tell: набор зелёный, а на живом прогоне сообщение выглядит битым** — оборванное имя, `�`, пустая подстановка, «для « в этой сессии». Код возврата при этом верен, поэтому ни одна ось не краснеет.
- ✅ **Floor: ≥1 ось ассертит ПОДСТРОКУ сообщения** — ту, ради которой текст и писался (имя предмета, путь, команду-выход):
  ```bash
  MSG=$(printf '%s' "$INPUT" | "$SUT" 2>&1 >/dev/null)
  echo "$MSG" | grep -q '<ожидаемый предмет>' || bad "предмет в сообщении искажён"
  ```
- ⛤ **Классический источник искажения — Г10** (`bash-loop-eval-pitfalls`): `«$KEY»` — многобайтовый сосед съедает имя переменной. Форма `${KEY}` чинит, но **обнаруживается только чтением текста**, не кодом возврата.
- ⛤ **Живой прогон в проде остаётся дешевле дополнительной оси и находит другое:** он проверяет доставку (матчер зарегистрирован, хук исполняется) — ось этого не видит, потому что зовёт предмет напрямую (`hook-matcher-vs-declared-surface`). Держать оба: набор для логики, один живой вызов для доставки+текста.

## §A32 — ⛔ Ось, чья ФИКСТУРА взята из ЖИВОГО ДЕФЕКТА, умирает вместе с его починкой — и выглядит это как регрессия предмета


Ось проверяет **ветку обработки аномалии** (имя резолвится в два индивида · дубль ключа ·
битая ссылка · рассогласованная пара). Чтобы такая ветка исполнилась, нужен **аномальный вход** —
и его берут оттуда, где он уже есть: из живых данных, которые харнесс копирует в фикстуру.

⛔ Пока аномалия в данных живёт, набор зелёный и выглядит образцовым. В день, когда её **чинят**
(отдельной задачей, часто другой сессией), оси краснеют **все разом** — и краснота указывает на
предмет, который не менялся.

- ⚠ **Симптом-tell, отличающий от настоящей регрессии:** покраснела **группа** осей одной темы,
  их код возврата — «данных не найдено» (`DICT-GAP`, `0 записей`, `not found`), а `git log` по
  предмету за окно **пуст**. Регрессия предмета так не выглядит: она бьёт по одной-двум осям и
  меняет ПОВЕДЕНИЕ, а не наличие входа.
- ⛔ **Два соблазна, оба неверны:** откатить починку данных (возвращает дефект ради зелёного
  набора) и ослабить оси (снимает покрытие ветки, которая нужна — аномалия может вернуться завтра).
- ✅ **Floor: фикстура СЕЁТ аномалию САМА, а не наследует её.** Параметр сборки
  (`build_vault(ambiguous=True)`) правит **копию** и делает вход независимым от состояния
  прода. Мутация обязана лечь **ровно один раз** с fail-loud при `n != 1` — иначе «ось не
  краснеет» неотличимо от «фикстура не построена».
- ⛤ **Ветку НЕ снимать после починки данных:** инвариант гарантирует чистоту **сегодня**, но не
  запрещает завести аномалию завтра — и тогда предмет обязан отказать громко. Покрытие ветки и
  инвариант — **разные** гарантии, не заменяющие друг друга.
- ⚠ **Правя шапку харнесса, снимай устаревшее УТВЕРЖДЕНИЕ, а не дописывай коррекцию снизу:**
  «замер: 71 индивид, **70 имён**» вверху файла победит любую приписку внизу

## §A33 — ⛔ Проверка-ДИЗЪЮНКЦИЯ не переворачивается ОДНОМЕСТНОЙ мутацией — и это читается как «ось не различает»


Ось формулируют дизъюнкцией, когда предмет выразим несколькими конструкциями («исход сверяется
с ожиданием» = `== expect_red` ИЛИ `"$actual" = "$want"` ИЛИ «ось ВАКУУМНА» ИЛИ …). Тогда мутант,
снимающий ОДИН дизъюнкт, проверку **не роняет**: свидетельство осталось в других местах.

- ⚠ **Симптом неотличим от настоящего дефекта оси:** мутант применился (якорь принят, `n == 1`),
  а проверка зелена ⇒ вердикт «мутант не различает». Тот же вывод дала бы вакуумная ось —
  и починка пойдёт не туда (станешь усиливать ось вместо того, чтобы чинить мутацию).
- ✅ **Дискриминатор — ПОСЧИТАТЬ свидетельство до мутации:** сколько вхождений даёт предикат
  на этом файле. Больше одного ⇒ одноместная мутация бессильна **по построению**, и дело не в оси.
- ✅ **Два выхода, оба законны:** (а) **усечение по уникальному маркеру** — срезать блок, где
  живут ВСЕ вхождения (`s[:s.index(marker)]`), а не заменять одно; (б) **сменить жертву** на
  файл, где свидетельство ровно одно. ⛔ Не «добавлять мутантов по одному на каждый дизъюнкт» —
  это whack-a-mole, и число дизъюнктов растёт с каждой правкой проверки.
- ⛤ **Усечённая копия синтаксически неполна — и это ЗАКОННО**, если мутанта только ЧИТАЮТ
  (статический аудит). Исполняемость требуется там, где мутанта запускают.
- ⚠ **Tell при проектировании проверки:** ты пишешь предикат через `|` из 4-5 альтернатив,
  «чтобы поймать все формы». Ровно эта широта и делает его неопровержимым одной мутацией.

## §A34 — ⛔ ФЛИП ПИШЕТ ИНДЕКС: `git checkout <ref> -- <file>` не read-only, и следующий bare `git commit` унесёт откат


Восстановление после флипа проверяют содержимым файла — `shasum` до и после, «✅ восстановлено
побайтово». Проверка верна и **не та**: `git checkout <ref> -- <file>` обновляет **и рабочую копию,
и ИНДЕКС**. `cp` возвращает рабочую копию, индекс остаётся с откатом, и следующий **bare**
`git commit` (без pathspec) уносит **весь индекс** — то есть отменяет твой же фикс.

⛔ **Ветка тогда несёт ТЕСТ без КОДА**, и это самая обманчивая её форма: локально всё зелено
(рабочая копия правильная), а CI краснеет твоими же осями с сообщением «получено — старое
поведение». Легко прочитать как «фикс не работает в CI» и уйти чинить не то.

- ⚠ **Симптом-tell, отличающий от настоящего расхождения сред:** CI-вывод показывает **в точности
  до-фиксное** поведение, а не искажённое. Настоящая разница сред искажает; отсутствие кода
  воспроизводит старое **дословно**.
- ✅ **Floor — проверять `git status --porcelain`, а не только содержимое файла.** После
  восстановления дерево обязано быть **пустым** (либо ровно с твоими изменениями). Помеченный `M`
  файл, который ты «восстановил», = откат сидит в индексе.
- ✅ **И коммитить PATHSPEC'ом** (`git commit <file> … -m`), а не bare — тогда чужое/устаревшее
  содержимое индекса физически не может уехать (`commit-and-push` §Bare `git commit`).
- ⛤ **Дешевле обоих: восстанавливать НЕ через `cp`, а `git checkout -- <file>`** (без ref) — он
  синхронизирует рабочую копию **с индексом**, оставляя обе стороны согласованными; либо сразу
  `git restore --staged --worktree <file>`.
- ⛔ **Восстановление — ОДНА операция, не цепочка.** Составив `cp <бэкап> <файл>; rm <бэкап>;
  git checkout -- <файл>`, получаешь ровно противоположное задуманному: `checkout` возвращает
  версию **из индекса** (то есть откат), а следующий `cp` — уже no-op, бэкап удалён. Правка теряется
  **полностью**, и `git status` при этом выглядит правдоподобно чистым.
  - ⚠ **Симптом-tell:** твой sha256-гвард печатает «разошёлся» **у ВСЕХ** восстанавливаемых файлов
    сразу. Один разошедшийся — случайность; все — значит восстановление как процедура не сработало.
  - ✅ **Floor: сперва `git restore --staged --worktree <файлы>` (или `git checkout -- …`), и ТОЛЬКО
    потом трогать бэкап** — либо не удалять бэкап в том же вызове вовсе. ⛤ И держать под рукой
    способ **переприменить** правку (скрипт-патч с якорем), а не только копию: тогда потеря
    восстановима за один вызов, а не «по памяти».
  - ⛤ Родственно `bash-loop-eval-pitfalls` §заблокированный compound: команды в одной строке
    исполняются последовательно и **не** знают о намерении друг друга.

**Empirical 2026-08-20** (PR #4110): флип оси `ErrorHandler`, восстановление через `cp` + sha256
(«✅ восстановлено»), затем `git add <тест>` и **bare** `git commit`. Ветка уехала с тестом и без
фикса; CI дал `Received: "❌ Error: remote rejected"` — ровно старый обработчик. `git show
origin/<branch>:<file> | grep -c <маркер>` = **0** при **5** в рабочем дереве, и `git status`
показывал файл как `M` — то есть оба дешёвых детектора были доступны и не запрошены.

## §A35 — ⛔ Гвард, чьё условие ВЛЕЧЁТ тот же исход арифметически, осью НЕОТЛИЧИМ — мутируй РЕШЕНИЕ, а не строку


Мутант снял гвард — **ни одна ось не покраснела**. Естественный вывод: «ось вакуумна,
надо усилить». ⛔ Часто вывод неверен: гвард **defensive** — состояние, при котором он
срабатывает, даёт тот же наблюдаемый результат и без него, потому что этого требует сама
арифметика (или тип-система, или ранний выход ниже).

⛤ **Классическая форма — деление, чей знаменатель обнуляется вместе с числителем.**
`if (n < 2) return NaN` выглядит несущим; но при `n < 2` дисперсия равна нулю, а при
константном столбце обнуляется и ковариация (`Σxy = c·Σy` и `Σx = n·c` сокращаются
точно) ⇒ выражение и так даёт `0/0 = NaN`. Снятие гварда не меняет **ничего**
наблюдаемого.

- ⚠ **Дискриминатор — АРИФМЕТИКА, а не ещё один прогон.** Посчитай на бумаге (или
  однострочником), чему равно выражение при условии гварда. Совпало с тем, что гвард
  возвращает ⇒ он defensive; ось усиливать бесполезно, её просто **не существует**.
  ```bash
  node -e 'const n=1,sx=7,sy=3,sxx=49,syy=9,sxy=21;
           console.log((n*sxy-sx*sy)/Math.sqrt((n*sxx-sx*sx)*(n*syy-sy*sy)))'   # → NaN
  ```
- ✅ **Floor: мутируй НАБЛЮДАЕМОЕ РЕШЕНИЕ, а не строку гварда.** Здесь решение — «отдавать
  `NaN`, а не `0`»; мутант «вернуть конвенцию `0`» роняет ровно те оси, что описывают
  контракт. Строка `if (n < 2)` не запираема ничем и запирать её не надо.
- ⛔ **Гвард при этом НЕ удалять.** Он выражает намерение и снимает зависимость от IEEE-754
  (`0/0` даёт `NaN`, но числитель иной формы дал бы `±Infinity`). Удаление ради
  «покрываемости» меняет контракт на неявный.
- ✅ **Назвать его defensive В КОДЕ.** Иначе следующий читатель примет его за механизм,
  а следующий ревьюер — за непокрытый гвард и потребует оси, которой быть не может.
  Формулировка, которая работает: «тесты пинят наблюдаемое РЕШЕНИЕ (X вместо Y), а не
  эти две строки».
- ⚠ **Симптом-tell, отличающий от настоящей вакуумности:** мутант снят, оси зелены —
  и ты **можешь назвать вход**, на котором результат совпадает с гвардовым. Не можешь
  назвать ⇒ ось действительно вакуумна, чини ось.

**Empirical 2026-08-21** (PR #4180, двухколоночные агрегаты): мутанты `n<2 → n<0` и
`vx<=0 → vx<0` дали **ноль** краснот при контроле 0 — сперва прочитано как «оси 4 и 5
вакуумны». Арифметическая проверка показала, что оба условия влекут `0/0` ⇒ гварды
ненаблюдаемы **по построению**. Замена мутанта на «NaN → 0 (конвенция файла)» дала ровно
`axis 4, axis 5`. Оси остались как были — неверен был мутант, а не они.

## §A36 — ⛔ Мутант, снимающий TYPE-NARROWING, ломает КОМПИЛЯЦИЮ, а не поведение — и рапортует BROKEN, читаемый как «ось не различает»


Самый естественный мутант для гварда — обнулить его условие: `if (cond) { … }` → `if (false) { … }`.
⛔ В типизированном языке это **вторая мутация помимо задуманной**: исходное условие обычно ещё и
**сужает тип** (`if (iri.startsWith(NS))` доказывает компилятору, что `iri` не `null`), а `false`
это сужение снимает. Тело блока перестаёт компилироваться, сьют не запускается, драйвер печатает
`BROKEN` / `Tests: 0`.

- ⚠ **Читается ровно наоборот:** «мутант применился, красных осей нет» ⇒ вывод «ось вакуумна» ⇒ идёшь
  усиливать корректную ось. На деле предмет вообще не исполнялся (`verify-before-assert` §«проверка
  была, но проверяла не то»).
- ⛤ **Отличать от §A3 по ПРИЧИНЕ, а не по симптому:** там `Tests: 0` от того, что **твоя break-правка**
  не скомпилировалась в проде; здесь компиляцию ломает **сам мутатор**, а прод и тест целы. Симптом
  один, чинится в разных местах.
- ✅ **Floor: мутант обязан сохранять ФОРМУ выражения и менять только ИСТИННОСТЬ.**
  ```
  if (iri.startsWith(NS))            →  if (iri.startsWith("\u0000-never-matches"))
  ```
  Тот же вызов того же метода на той же переменной ⇒ narrowing цел, блок недостижим в рантайме.
  ⛔ Не `if (false)`, не `if (0)`, не удаление условия.
- ✅ **Драйвер обязан печатать ПРИЧИНУ broken** (первую строку с `error TS` / `SyntaxError`), иначе
  различить «мутант убил компиляцию» и «ось не различает» нельзя вовсе — а это противоположные диагнозы.
- ⛤ **Тот же приём нужен для type-guard'ов и `assert`-функций:** снятие `if (typeof x === "string")`
  меняет тип `x` ниже по блоку, поэтому мутант «убрать проверку» роняет компиляцию, а не тест.

**Empirical 2026-08-21** (PR #4179, fail-loud для `agg:`-агрегатов): мутант `if (false)` дал
`TS18047: 'iri' is possibly 'null'` → `Tests: 0` → драйвер напечатал `BROKEN`. Замена на
`iri.startsWith("\u0000-never-matches")` дала чистую картину: контроль 0 красных, мутант A → ровно
`axis 1`, мутант B → ровно `axis 3`. Причина найдена только потому, что драйвер после правки стал
печатать первую строку ошибки — до этого он одинаково говорил `BROKEN` и на сломанный мутатор, и на
сломанное окружение.

## §A37 — ⛔ Ось на ВЫХОД (escape, исключение, «этот случай пропускаем») зелена по НЕЗАВИСИМОЙ причине, если её фикстура не содержит ЗАПРЕЩЁННОЙ формы


У всякого гейта, кроме собственно запрета, есть **выходы**: escape-маркер, разрешённый
инструмент, путь вне охраняемой зоны, режим, в котором гейт не применяется. Ось на такой
выход пишется естественно — «команда с маркером пропускается» — и **проходит**. Но проходит
она, только если вход **иначе был бы заблокирован**; иначе она зелена потому, что запрещать
там было нечего.

- ⛔ **Мутант, снимающий выход, такую ось НЕ роняет** — и вердикт «ось не различает» указывает
  на ось, хотя дефектна **фикстура**. Оба состояния («выход работает» / «входу и так ничего не
  грозило») дают одинаковый rc.
- ✅ **Floor: фикстура оси-на-выход ОБЯЗАНА содержать запрещённую форму.** Проверка одна —
  мысленно снять выход: вход должен блокироваться. Не блокируется ⇒ ось меряет не то.
- ⛤ **Тот же дефект у осей на «путь вне зоны»**, когда снаружи действует второй слой защиты:
  путь вне охраняемого корня пропускается и без раннего выхода, потому что «не git-репо».
  Различающий вход строится так, чтобы **все прочие слои пропускали**, а решал ровно проверяемый.
- ⚠ **Симптом-tell:** мутант покраснил все оси, кроме одной-двух — и это оси на выходы/исключения.
  Не «эти оси избыточны», а «их фикстуры не доходят до проверяемой ветки».

⛤ **Это САМЫЙ частый дефект при написании харнесса для гейта — 3 случая на 14 харнессов
за одну сессию.** Причина систематическая: фикстуру оси-на-выход пишут «реалистичной»
(команда, которую выход и должен пропускать), а реалистичная команда обычно НЕ содержит
запрещённой формы — иначе её не написал бы живой человек. То есть естественная фикстура
здесь почти всегда вакуумна, и это надо ожидать, а не обнаруживать.

**Empirical 2026-08-21** (три случая, при написании харнессов для блокирующих хуков):
ось «путь вне охраняемого корня пропускается» не роняла мутанта «ранний выход снят» — путь
вне корня всё равно пропускался вторым слоем; исправлено git-репо ВНЕ корня. Ось «запрос через
CLI пропускается» не роняла мутанта «выход по CLI снят» — фикстура не содержала рекурсивного
поиска; исправлено формой «CLI + фильтрация вывода». В обоих случаях контроль был зелёный,
а ось — вакуумной.

## §A38 — ⛔ «Любой ненулевой rc» — НЕ ось: она не различает ОТКАЗ и ЗАВИСАНИЕ, а мутант обычно даёт второе


Ось на отрицательный исход естественно пишется как `[ "$rc" != 0 ]` — предмет обязан отвергнуть
плохой вход, значит «не ноль» и есть требование. ⛔ Но у снятого guard'а исход почти никогда не
«принял и отработал»: он **уходит дальше по коду**, упирается в ожидание внешнего состояния и
возвращает **124** от `timeout` — тоже ненулевой. Ось остаётся зелёной, мутант «не различает», и
вывод уходит на ось, хотя дефект в её **пороге**.

- ⚠ **Симптом-tell, ловится ЗА ОДИН прогон:** мутант, снимающий именно этот guard, не краснит
  именно эту ось, а соседние мутанты работают. Прежде чем «усиливать ось» — **напечатай rc
  мутанта и пристинного рядом**: `124` против `1` и есть ответ.
- ✅ **Floor: ось на отказ требует БЫСТРОГО ЯВНОГО отказа** — исключать и `0` (принял), и `124`
  (завис вместо отказа):
  ```bash
  if   [ "$rc" = 0 ];   then bad "вход принят молча"
  elif [ "$rc" = 124 ]; then bad "guard не сработал — завис вместо отказа"
  else                       ok  "отвергнут быстро и явно (rc=$rc)"
  fi
  ```
- ⛔ **`timeout` в харнессе при этом ОБЯЗАТЕЛЕН, а не желателен.** Без него мутант, ломающий
  разбор аргументов, вешает весь прогон, и «мутант не различает» становится неотличимо от
  «харнесс не завершился» — то есть теряется даже сигнал о проблеме.
- ⛤ **Класс шире rc:** всякая ось, чей предикат — **отрицание** («не пусто», «не равно», «не
  ноль»), удовлетворяется **множеством** исходов, и снятый guard попадает в это множество
  случайно. Спрашивать надо не «плохо ли», а **«ТАК ЛИ ИМЕННО плохо, как обещано»**.

**Empirical 2026-08-21** (`spawn-setting-sources-verify.sh`, req 1b181627): ось «`--setting-sources`
без значения отвергнут» в форме `rc != 0` осталась зелёной под мутантом, снимающим `${2:?…}`.
Замер обоих: мутант **124** (спавнер ушёл в ожидание сессии), пристинный **1**. После сужения
до «не 0 и не 124» мутант красит ровно её; два соседних мутанта краснят свои оси, контроль зелен.

## §A39 — ⛔ ИЗОЛЯЦИЯ осей не должна опираться на ПРОВЕРЯЕМЫЙ механизм — иначе один мутант роняет полнабора


Оси делят состояние всякий раз, когда предмет держит его **на уровне модуля** (кэш,
счётчик, реестр, латч, синглтон). Чтобы оси не заражали друг друга, `beforeEach`
сбрасывает это состояние — и естественнее всего сбросить его **тем же публичным
средством, которое предмет для этого и предоставляет**.

⛔ Ровно это и есть циркулярность: сбрасыватель нередко **сам является предметом**
одной из осей. Тогда мутант «сбрасыватель ничего не делает» ломает не свою ось, а
**все, что шли после неё** — состояние течёт из теста в тест.

- ⚠ **Симптом-tell, ловится по МАТРИЦЕ мутантов, а не по одной оси:** мутант краснит
  набор осей, у которых **нет общей темы** — например A2 (инвалидация), A3 (истечение)
  и A4 (не кэшировать провал) разом. Тематически несвязанная гроздь = утечка состояния,
  а не «сильный мутант».
- ✅ **Floor: изоляция берётся из СРЕДЫ, а не из предмета** — свежий экземпляр на тест.
  Для модуля это `vi.resetModules()` + динамический импорт; для процесса — свой каталог
  состояния; для БД — своя схема. Тогда изоляция не может отказать вместе с предметом.
- ⛤ **Побочно это делает ожидания мутантов ЧЕСТНЫМИ.** До правки «инвалидация no-op»
  роняла три оси, и соблазн был записать это в ожидание как есть; после — ровно одну,
  и набор снова говорит, ЧТО именно сломано.
- ⛔ **Но не всякая множественная краснота — дефект изоляции.** Дискриминатор: спроси,
  следует ли краснота **из семантики мутанта на предмете этой оси**. «Кэш не читается»
  ⇒ проба на каждом вызове ⇒ ось «читающее действие не добавляет проб» падает
  **законно** — она наблюдает рост числа проб напрямую. Такое перечисляют в ожидании
  явно; ⛔ «усиливать» оси до различения семантически неразличимого — вред.

**Empirical 2026-08-21** (кэш macOS-диагностики, `computer-use-mcp` PR #8): `beforeEach`
звал `invalidateMacDiagnostics()` — предмет оси A2. Мутант «инвалидация no-op» ронял
`A2 A3 A4`; после перевода на `vi.resetModules()` + свежий импорт — ровно `A2`. Матрица
из 8 мутантов после этого стала читаемой: 6 роняют по одной оси, 2 — по нескольку, и оба
раза это **дублирующее покрытие**, зафиксированное в ожидании.

## §A40 — ⛔ Инвариант, ОБЩИЙ для двух соседей, не покрыт НИ ОДНИМ из их харнессов — у шва нет владельца


Набор осей пишется **по предмету**: харнесс `A` проверяет контракт `A`, харнесс `B` — контракт `B`.
Когда контракт **общий** (оба объявляют один формат вывода, один словарь кодов, одну форму записи),
он не принадлежит ни одному харнессу — и расхождение между соседями **не краснит ничего**.

- ⛔ **Оба набора зелены ПО ПОСТРОЕНИЮ, а не по удаче.** Ось «мой скрипт печатает TSV» истинна у
  каждого; ложно лишь то, что из неё выводят — «значит, у пары один контракт». Дефект доживает
  до первого, кто **исполнит шов** (e2e, живой тик, интеграция) — то есть до прода.
- ⚠ **Симптом-tell при чтении шапок:** два файла объявляют один и тот же контракт СВОИМИ словами
  («stdout — ОДНА строка TSV»). Дублированная формулировка = инвариант без владельца; спроси, какой
  харнесс упадёт, если один сосед от неё отступит. Ответ «никакой» и есть находка.
- ✅ **Floor: ось, чей ПРЕДМЕТ — инвариант, а не скрипт.** Прогонять её на **обоих** соседях одним
  кодом: тогда она заодно проверяет, что сформулирована симметрично, а не подогнана под того, кого
  чинишь.
- ⛔ **Перечислять ПОИМЁННО, а не агрегатом** (`файл:строка` каждого нарушителя). Иначе мутант
  «снять инвариант у ОДНОЙ точки» краснит агрегат, а не точку, и «ось различает» недоказуемо.
  ⛤ Когда все выходы сведены в один `finish()`, мутация формулируется как «заменить ОДИН вызов
  `finish(...)` на голый `exit N`» — и ось обязана назвать ровно эту строку.
- ⛔ **Ложно-положительная ось хуже отсутствующей: сперва чини ДЕТЕКТОР, а не соседа.** Разбор
  общего инварианта идёт по **структуре** (AST для python; для bash — маска кавычек), иначе `exit`
  внутри `bash -c '…'` — выход **чужого интерпретатора** — объявляется нарушением, и ось гонит
  править исправный код.

**Empirical 2026-08-18** (`vteam-admit.sh` ↔ `vteam-record.sh`, задача `1668d525`): у `record`
**21** ненулевая точка выхода, из них печатали счётную строку **0** (4 stdout-`print` — все на
rc=0); `admit` держал инвариант одной `finish()`. Ни `record-verify` (22 оси), ни `admit-verify`
(16 осей) этого не видели. Лечение — `finish()` у обоих + ось на ПАРУ
(`vteam-stdout-contract-verify.py`, 20/20 + 6/6 мутантов, каждый называет свою строку).

## §A41 — ⛔ АНКЕР, скопированный из выведенного тобою же ТЕКСТА, несёт отступ ТВОЕГО префикса — стройте его из ФАЙЛА, а не из вывода


Правя файл программно (`str.replace` с `assert n == 1`), анкер берут из того, что только что
прочитали. Читают почти всегда **с префиксом** — `sed 's/^/  /'`, отбивка `> `, номера строк, —
потому что так вывод читаем. ⛔ Скопированный оттуда анкер несёт **чужие 2 пробела**, и
`assert n == 1` честно падает `x0`.

- ⛤ **Гвард РАБОТАЕТ — в том и коварство.** Отказ громкий, данные целы, ущерб = один цикл. Поэтому
  класс не воспринимается как класс: каждый случай выглядит опечаткой, чинится за минуту и не
  оставляет следа. Замер 2026-08-19: **три** промаха за одну сессию, все три — одна причина.
- ⚠ **Второй, более тихий подвид — отступ, выведенный ПО ПАМЯТИ о структуре.** «Тело `it` внутри
  `describe` ⇒ 4 пробела» — правдоподобно и неверно, если файл держит `describe` на нуле. Тогда
  анкер не совпадёт даже при чтении без префикса.
- ✅ **Floor: анкер СТРОИТЬ ИЗ ФАЙЛА, а не копировать.** Найти строку по подстроке и взять её
  дословно; для вставки — вычислить границы блока и работать номерами строк:
  ```python
  lines = open(p, encoding="utf-8").read().split("\n")
  i = next(k for k, l in enumerate(lines) if "<уникальная подстрока>" in l)
  ind = len(lines[i]) - len(lines[i].lstrip())      # отступ берём У ФАЙЛА, не у себя
  j = next(k for k in range(i, len(lines)) if lines[k] == ind * " " + "});")
  lines[i:j+1] = [...]                               # правим диапазоном
  ```
  Тогда отступ — **свойство файла**, а не твоего вывода, и промах невозможен by construction.
- ✅ **Печатать сырьё с ДЕЛИМИТЕРАМИ, когда всё же смотришь глазами:**
  `print("%4d |%s|" % (i, line))` — `|` показывает границы строки, и лишние пробелы видно. ⛔ Не
  `cat -A` (BSD его не знает — `illegal option`).
- ⛤ **Диагностический tell после падения:** `assert … x0` на анкере, который ты **только что видел
  на экране**. Файл не менялся между чтением и правкой ⇒ различие внесено **отображением**.

**Empirical 2026-08-19** (PR #4113, три промаха подряд): (1) отступ `10` в исходнике против `12` в
анкере — разница ровно от `sed 's/^/  /'`; (2) тот же префикс на блоке теста; (3) отступ выведен по
памяти (`describe`-тело считал за 4, фактически 2). Каждый стоил цикла; ни один не дошёл до диска —

## §A42 — ⛔ ВАКУУМНЫЙ ОТКАТ фабрикует ОПРОВЕРЖЕНИЕ верного факта — и это опаснее пропущенного дефекта


Корпус разбирает вакуумную **ось** (зелена по независимой причине). Зеркало — вакуумный
**откат**: ты «возвращаешь предмет к до-фиксному состоянию», операция отрабатывает без ошибки,
обе половины флипа дают одинаковый результат — и ты заключаешь «фикс ничего не меняет».

⛔ **Вывод при этом ЛОЖЕН, а направление ошибки — противоположно привычному.** Вакуумная ось
**пропускает** дефект (не краснеет там, где должна). Вакуумный откат **фабрикует опровержение**:
он объявляет неверным утверждение, которое верно, — и толкает внести ложную коррекцию в
durable-артефакт, то есть **испортить правильную запись**.

- ⛤ **Самый частый носитель — `git stash` при ЧИСТОМ дереве.** Если правка уже закоммичена,
  `stash` откатывает **ничего**: команда успешна, вывод пуст, дерево не меняется. Обе половины
  флипа гоняются на **одном и том же** (уже пофикшенном) предмете.
- ⚠ **Симптом-tell, ловится ДО вывода:** обе половины дали **побайтно одинаковый** результат.
  Настоящий флип почти никогда не даёт идентичности — он либо краснеет, либо меняет числа.
  Идентичность = подозрение на no-op отката, а не на бесполезность фикса.
- ✅ **Floor: откат делать ЯВНЫМ извлечением из истории, а не командой, чей эффект зависит от
  состояния дерева:**
  ```bash
  git show <fix-sha>^:<путь> > /tmp/before.py   # ← до-фиксная версия ГАРАНТИРОВАННО
  <прогон> /tmp/before.py …                     # ← и гнать ЕЁ, а не «дерево после stash»
  ```
- ⛤ **Тот же класс у любой «отменяющей» операции, чей эффект условен:** `git checkout --` на
  неизменённом файле, `unset` невыставленной переменной, `rm -f` отсутствующего маркера. Все
  успешны, все могут быть no-op, и все читаются как выполненное действие.

**Empirical 2026-08-21:** правка `mutant-driver.py` (разворот `$HOME` в поле `subject`) — флип
через `git stash` дал идентичный результат в обеих половинах ⇒ вывод «фикс не нужен, обоснование
коммита ложно». Явный откат (`git show <sha>^:`) показал `FileNotFoundError` до фикса ⇒
обоснование **верно**, а 22 spec-файла действительно были неисполнимы. Ложная коррекция в тело
коммита не ушла только потому, что идентичность половин показалась подозрительной.

## §A43 — ⛤ У гварда формы «ЯВНОЕ ИСКЛЮЧЕНИЕ + УЗКИЙ ДЕТЕКТ» исключения покрыты ДВАЖДЫ — мутант на одном не краснит, и это НЕ дефект оси


Типовой блокирующий гвард устроен парой: **список исключений** («индекс памяти пропускать»,
«репо-дерево пропускать») и **узкий детект предмета** («блокировать только имена вида
`feedback_*`»). Пара избыточна по построению: то, что попало в исключение, обычно **и так**
не матчит детект.

⛔ **Следствие для проверки: мутант, снимающий исключение, НЕ роняет ось на это исключение** —
срабатывает второй заслон. Вывод «ось не различает» тут **ложен**; верный вывод обратный —
**поведение под защитой дважды**.

- ⚠ **Симптом-tell:** мутант снял ровно тот кусок, который ось называет по имени, а ось зелена.
  Прежде чем усиливать ось — спроси, нет ли ВТОРОГО пути к тому же исходу.
- ⛔ **Мутант «снять оба заслона» проблему не решает** — он роняет и соседние оси, то есть
  перестаёт различать. Такого мутанта писать не надо.
- ✅ **Floor: зафиксировать причину В ДВУХ носителях** — в spec (`_note_<ось>`) и **у самой оси**
  комментарием. Иначе следующий читатель увидит недоказанную ось и сочтёт её недоделкой либо
  «усилит» её, сломав различимость соседних.
- ⛤ **Отличать от вакуумной оси** (`self-satisfying-metric-weak-verifier`): там ось зелена
  **по независимой причине** и не проверяет ничего; здесь она проверяет ровно то, что обещает,
  просто предмет защищён избыточно. Дискриминатор: сломай **оба** заслона — ось краснеет ⇒
  дублирование; не краснеет ни при каком ⇒ вакуум.

**Empirical 2026-08-21** (два случая за одну сессию, оба на блокирующих хуках):
`co-location-enforce` A5 (без `isDefinedBy` ⇒ пустой якорь ⇒ онтология не находится ⇒ второй
fail-open) и `block-old-memory-dir-writes` A2/A3 (индекс и в явном исключении, и не матчит
регэксп тематических имён). В обоих случаях первая реакция была «ось слаба» — неверная.

## §A44 — ⛔ ОЖИДАНИЕ мутанта выводится из ЗАВИСИМОСТЕЙ ОСЕЙ, а не из темы мутанта — иначе оно систематически УЖЕ фактического


Записывая, какие оси обязан покраснить мутант, естественно перечислить те, чья **тема** совпадает
с темой мутации («снял ярус ⇒ покраснеет ось про ярус»). ⛔ Это даёт ожидание **уже** фактического
почти всегда, потому что оси не независимы: предикат одной часто **включает** условие другой.

- ⚠ **Симптом-tell:** прогон печатает «ожидалось [A1], покраснели [A1 A2]» — то есть красноты
  БОЛЬШЕ. Первая реакция «оси смешаны» **неверна**: смешение — это когда ось краснеет от мутации,
  к её предмету не относящейся. Здесь же A2 честно зависит от того, что предмет дожил до её шага.
- ✅ **Floor: перед записью ожидания спросить по КАЖДОЙ оси — «исполнится ли она вообще, если
  мутация применена?»** Ось, стоящая ПОСЛЕ мутированной точки в потоке (или опирающаяся на её
  результат), краснеет **по построению**, и это надо назвать заранее, а не задним числом.
- ⛤ **Не «чинить» ось под ожидание.** Дискриминатор: следует ли краснота из семантики мутанта на
  предмете ИМЕННО ЭТОЙ оси? Да ⇒ законно, дописать в ожидание. Нет ⇒ смешение, чинить фикстурой.
- ⛔ **Расхождение НАЗЫВАТЬ в самом харнессе**, а не молча править число: следующий читатель иначе
  прочитает список как «оси проверяют независимое» и построит на этом неверный вывод.

**Empirical 2026-08-21** (три случая за одну сессию, все — ожидание уже фактического):
`claude-bloat-aggregate` M1 → ожидал A1, покраснели A1+A3 (предикат A3 включает условие A1);
M2 → ожидал A2, покраснели A1+A2+A3; `orch-watchdog-window` M1 → ожидал A1, покраснели A1+A2
(мутант даёт мгновенный терминал, и окно A2 не успевает открыться). Ни один не был смешением —
все три законны, и во всех трёх ожидание было записано по ТЕМЕ мутации.

### ⛔ ЗЕРКАЛО: ожидание ШИРЕ фактического — и когда его писал ПРЕДШЕСТВЕННИК, дискриминатор читается ДО прогона

Секция выше разбирает ожидание **уже** фактического (краснот больше, чем предсказано) и потому
формулирует tell как «покраснели [A1 A2] при ожидании [A1]». Обратный знак — краснот **меньше** —
она не покрывает, и у него другой корень: не зависимость осей, а **несовпадение ГВАРДОВ**.

⛤ **Механизм: мутант снимает ОДИН гвард, ось запирает ДРУГОЙ.** Оси именуются по теме
(«opt-in», «класс затыка», «латч»), гварды тоже — и совпадение тем читается как совпадение
предметов. Но ось краснеет, только если мутант убрал **тот самый** гвард, который она запирает;
соседний гвард той же темы её не трогает **по построению**, сколько бы правдоподобно ни звучало
предсказание.

- ⛔ **Опаснее прямого знака, когда матрицу писал ПРЕДШЕСТВЕННИК по конвейеру.** Мутантная матрица
  в §Спецификации — это **предсказание**, а не замер: её автор гвардов не снимал. Преемник читает
  её как предмет реализации (`decision-surface-must-derive-from-mechanism` §ВЕРДИКТ ПРЕДЫДУЩЕГО
  ЭТАПА) и, не получив предсказанной красноты, идёт «усиливать» корректную ось.
- ✅ **Floor: дискриминатор ЧИТАЕТСЯ, а не прогоняется** — назвать гвард мутанта и гвард оси по
  имени и сравнить. Разные ⇒ предсказание ложно **до всякого прогона**, и это надо сказать вслух,
  а не подгонять. Совпали ⇒ краснота обязана быть, и её отсутствие есть дефект оси.
- ✅ **Оси, оставшейся без различающего мутанта, завести СВОЙ** — это исполнение требования
  невакуумности, а не расширение scope: ось без мутанта осью не является.
- ⛔ **Расхождение со спецификацией НАЗЫВАТЬ в отчёте этапа**, а не выравнивать матрицу молча:
  иначе следующий этап унаследует ложное предсказание как проверенный факт
  (`retracted-claim-outranks-its-correction` §ТРЕТИЙ носитель).
- ⚠ **Симптом-tell:** предсказанная ось — единственная, чья тема совпадает с темой мутанта
  **словом**, а не механизмом («opt-in» у обоих, но у мутанта это класс находок, у оси — гейт
  доставки).

**Empirical 2026-08-26** (`vteam-supervise-detect.py`, тикет `4479364a`): §Спецификация предсказала
`M-c → AC3+AC4+AC5`; измерено `AC3+AC4`. `M-c` снимает **класс** затыка (ветка контекста), а `AC5`
запирает **opt-in** доставки (`VTEAM_SUP_NOTIFY`) — разные гварды, поэтому предсказание было ложно
по построению. Заведён `M-c2`, краснящий ровно `AC5`; расхождение выписано в отчёт этапа.

## §A45 — ⛔ ЗЕРКАЛО §A7: чужой ранний выход глотает ТВОЙ новый блок — и он не исполняется на самом частом пути


§A7 разбирает случай «я добавил ранний `return` ⇒ гвард НИЖЕ перестал исполняться». Обратная
сторона встречается чаще и ловится хуже: ты дописываешь блок **в конец** функции/скрипта, а выше
уже стоит **ранний выход по успеху** (`if [ ok ]; then exit 0; fi`, `return` при пустом наборе,
`continue` при отсутствии находок). Твой блок тогда исполняется **только на редкой ветке** — при
ошибке, при непустом результате, при падении.

- ⚠ **Опаснее, чем «не работает»: он работает ИЗБИРАТЕЛЬНО.** На красном прогоне блок печатает,
  на зелёном молчит — и молчание читается как «находок нет», а не «проверка не выполнялась».
  Именно зелёный путь при этом самый частый.
- ⛤ **Дискриминатор дешёвый и механический: назови ПУТЬ, по которому пойдёт типичный прогон**, и
  проверь, лежит ли твой блок на нём. Для проверки-детектора типичный путь — **успех**, а не отказ.
- ✅ **Floor: пробу гнать в ОБОИХ состояниях предмета** (находка есть / находки нет). Одна половина
  доказывает, что блок печатает; вторая — что он молчит по делу, а не потому, что до него не дошли.
- ⚠ **Симптом-tell после первой пробы:** ты создал условие срабатывания (фикстуру, сироту, ошибку),
  а вывод пуст. ⛔ Не читать как «детектор не видит» — сперва спроси, дошёл ли поток до него.

**Empirical 2026-08-21** (пост-проверка осиротевших фикстурных сессий в `verify-harness-runner.sh`):
блок встал ниже `if [ "${#red[@]}" -eq 0 ]; then exit 0; fi`, то есть исполнялся **только при
падении набора**. Проба с живой `probe-orphan-check` дала пустой вывод — и это выглядело как
дефект детектора, хотя детектор был верен, а недостижим. После переноса выше раннего выхода: с
сиротой печатает её имя, без сироты — ноль строк.

## §A46 — ⛔ Мутант, меняющий ТЕКСТ СООБЩЕНИЯ, не меняет ПОВЕДЕНИЯ — и «не покраснело» читается как «ось не различает»


Мутируя гвард, естественно взять якорем **строку, которая его называет** — она уникальна,
хорошо читается и содержит суть (`print("⛔ контроль не зелёный")`). ⛔ Но у гварда две части:
**сообщение** и **решение** (`return 1` / `bad += 1` / `sys.exit`), и якорь по сообщению меняет
первую, оставляя вторую нетронутой. Поведение идентично ⇒ ни одна ось не краснеет.

- ⚠ **Вывод драйвера при этом ЛОЖНО обвиняет ось:** «красные = НИ ОДНОЙ — ось не различает».
  Ты идёшь усиливать корректную ось вместо того, чтобы починить мутант.
- ⛤ **Дискриминатор — назвать вслух, ЧТО изменит мутация в исходе.** Не можешь сформулировать
  иначе как «сообщение станет другим» ⇒ поведение не тронуто. Работающая формулировка звучит
  как «прогон перестанет валиться», «файл не будет записан», «ветка станет недостижимой».
- ✅ **Floor: якорь — ПАРА строк (сообщение + решение)**, замена оставляет сообщение и
  обнуляет решение. Тогда мутант меняет ровно исход:
  ```python
  i = next(k for k, l in enumerate(lines) if МАРКЕР in l)
  old = lines[i] + "\n" + lines[i + 1]        # сообщение + решение
  new = lines[i] + "\n" + "        pass"      # сообщение то же, решение снято
  ```
- ⛤ **Побочно пара-якорь чинит и уникальность:** одиночная строка `bad += 1` встречается в файле
  многократно, а в паре с конкретным сообщением — ровно один раз (`assert count == 1` проходит).

**Empirical 2026-08-21** (харнесс для `mutant-driver.py`): первые четыре мутанта меняли `⛔` на
`⚠` в тексте — **ноль краснот**, и вывод честно сообщил «ось не различает» про четыре корректные
оси. Пере-собранные парой строк дали ровно ожидаемое.

## §A47 — ⛔ ИМЯ ОСИ — ИНТЕРФЕЙС с драйвером: не совпало с его регэкспом ⇒ «мутант не различает» при ИСПРАВНОЙ оси


Драйвер мутантов извлекает красноту из вывода харнесса **регэкспом** (`⛔ (A\d+\w?)`). Значит имя
оси — не подпись для человека, а **машинный ключ**. Назвал ось осмысленно (`A-print`, `A-iso`,
`A-net`) — краснота не извлекается, множество красных пусто, и драйвер честно рапортует «ось не
различает ЛИБО гвард defensive».

- ⛔ **Вердикт указывает НЕ ТУДА, и это дороже пропуска.** Ты идёшь усиливать ось, которая
  работает; настоящая причина — в имени. У меня это стоило четырёх итераций подряд (⇒ каждая
  «починка» добавляла свой дефект: не задал `SDT_BIN` ⇒ гонял боевые детекторы; не очистил
  каталог фикстур ⇒ прогон уходил в чужую ветку; имена фикстур не из декларации предмета ⇒ rc=3).
- ⚠ **Дискриминатор одноразовый и решающий: прогони ТОТ ЖЕ мутант РУКАМИ.** Краснеет вручную и
  «не различается» под драйвером ⇒ дефект в связке (имя оси / доставка), а не в оси. Ручной
  прогон стоит одну команду и снимает четыре гипотезы разом.
- ✅ **Floor: имя оси = `A<цифра>[буква]`, всегда.** Смысл — в ТЕКСТЕ оси, не в её имени.
  ⛤ Или, если хочется говорящих имён, — расширить `red_re` драйвера И записать это в спеку,
  но тогда конвенция обязана быть общей для всех харнессов, иначе разъедется молча.
- ⛤ **Ошибка невозможна в наборе, писавшемся целиком под драйвер** — она приходит с ДОПИСАННОЙ
  осью, когда автор думает о предмете, а не о протоколе. То есть класс срабатывает ровно при
  расширении зрелого набора.

## §A48 — ⛔ «Ось не различает» — вердикт ДРАЙВЕРА, а не факт: у spec есть СКРЫТОЕ ПЕРЕЧИСЛЕНИЕ имён осей


Драйвер мутантов решает, какая ось покраснела, регэкспом по выводу харнесса. Если регэксп
перечисляет **префикс имени** (`⛔ (A\d+\w?)`), то ось, названная другой буквой, для него
**не существует** — и он честно печатает «красные = НИ ОДНОЙ — ось не различает».

- ⛔ **Вердикт указывает НЕ ТУДА:** он обвиняет ось (или предмет), тогда как сломан **сбор**.
  Дальше чинится исправная ось, а настоящий дефект — литерал в конфиге — остаётся.
- ⚠ **Симптом-tell, ловится за секунду:** «не различает» получила **новая** ось, а старые
  краснеют штатно. Различие между ними — не логика, а **имя**.
- ✅ **Floor: инвертировать полярность перечисления** — `[A-Z]\d+` вместо `A\d+`. Тогда
  следующая ось с любым префиксом попадает в сбор **по построению**, а не после отладки.
- ⛤ Это ровно `self-satisfying-metric-weak-verifier` §инверсия полярности, применённое к
  **собственной оснастке**: перечисляли то, что ожидали увидеть, вместо того чтобы принимать всё
  и отсеивать явно-чужое.
- ⛔ **Не «переименовать ось под регэксп».** Это чинит экземпляр и оставляет класс: следующий
  автор снова назовёт ось иначе и снова получит ложный вердикт.

## §A49 — ⛔ Инъекция ЕСТЬ, но ею ЗАБЫЛИ воспользоваться — гвард на забытую изоляцию


§ИНЪЕКЦИЯ ВНЕШНЕГО СОСТОЯНИЯ выше требует сделать путь эффекта подменяемым. Следующая форма
отказа: подменяемость **реализована и документирована**, а ручная проба запускается без неё —
и уходит боевой эффект (письмо фаундеру, запись в общий журнал, реальный спавн).

- ⛤ **Дисциплина тут структурно бессильна:** забывается ровно та переменная, которая делает
  прогон безопасным, а отказ **тихий** — боевой эффект выглядит боевым, и ничто не говорит, что
  он пришёл из пробы.
- ✅ **Floor: у пробы обычно ЕСТЬ собственный признак — переменная, существующая ТОЛЬКО для
  харнесса** (каталог фикстур, тестовый корень). Задана она **И** не задана изоляция канала ⇒
  **fail-loud**, а не тихий фолбэк на стаб: тихая подмена скрыла бы сам факт пробы.
- ⚠ **Ось обязана быть ПАРНОЙ:** «гвард срабатывает» без «с изолированным каналом проба
  проходит» неотличимо от «гвард запретил пробы вообще» — то есть от поломки харнесса.
- ⛔ **Фикстурный каталог в оси брать ИЗ ХАРНЕССА, а не по догадке.** Я взял `$T/bin`, а харнесс

  типовая ловушка: сверять надо **текст отказа**, а не только код.

## §A50 — ⛔ «Подмена НЕ доезжает» может означать ДЕФЕКТ ПРЕДМЕТА, а не доставки — канарейка врёт в сторону ложно-мёртвого


Канарейка доставки подсовывает **заведомо непригодный** предмет и требует, чтобы выдача
изменилась. Не изменилась ⇒ вердикт «путь не доставляется». ⛔ Но у этого вердикта есть **второй**
корень: доставка исправна, а предмет **принимает непригодный вход как валидный** — и потому
выдача честно не меняется.

- ⛤ **Типовая форма:** харнесс судит по **коду возврата**. Пустой (или подменённый) исполняемый
  файл выходит нулём ⇒ читается как «чисто» ⇒ красных нет ⇒ канарейка объявляет подмену
  недоехавшей. Виновата при этом **ось**, которая тождественно-зелёная.
- ⚠ **Симптом-tell, отличающий от настоящей проблемы доставки:** ты уже сменил способ доставки
  (env → argv → плейсхолдер) и вердикт не изменился. Значит дело не в способе.
- ✅ **Floor: ось обязана требовать СЛЕД РАБОТЫ, а не только `rc`** — маркер, который печатает
  только настоящий предмет (`CLEAN`, число просмотренных, имя проверки). Тогда пустой предмет
  краснит ось, выдача меняется, и канарейка оживает **как побочный эффект** укрепления оси.
- ⛤ **Порядок диагностики:** сперва спроси «а что мой харнесс сделает с ПУСТЫМ предметом?» —
  ответ «скажет, что всё хорошо» и есть дефект. Только если ответ «покраснеет» — иди чинить
  доставку.
- ⛔ **Отдельно: для обёртки, которая САМА СЕБЕ харнесс, канарейка структурно неприменима** —
  пустой предмет не печатает ничего, красные оси совпадают с зелёным контролем при любой
  доставке. Такую обёртку мутируют не саму, а её **зависимость** (чекер, движок), доставляемую
  через env.

## §A51 — ⛤ РЕЛИЗНЫЙ флип берётся ПРЕДЫДУЩЕЙ ОПУБЛИКОВАННОЙ ВЕРСИЕЙ — мутировать код не нужно и не надо


Всё правило выше строит флип **мутацией предмета** (сломать копию → ось краснеет → вернуть). На
этапе релиза предмет — **опубликованный артефакт**, и мутировать его нельзя. Отсюда типовой промах:
проверку «фикс доехал до пользователя» гоняют один раз на текущей версии, получают зелёное и
считают вопрос закрытым. ⛔ Такая проверка **зелена при любом состоянии продукта**: она не
предъявляет, что вообще способна покраснеть.

- ✅ **Floor: тот же прогон против ПРЕДЫДУЩЕЙ опубликованной версии** — `npx <pkg>@<prev>`,
  `gh release download <prev-tag>`, `npm pack <pkg>@<prev>`. Дефект обязан быть **жив** там и
  **мёртв** здесь. Мутировать нечего, ломать нечего, стоит один прогон.
- ⛤ **Строго сильнее jest-мутанта на этом этапе.** Мутант доказывает, что различает **твой код**;
  две опубликованные версии доказывают, что различают **артефакт, который ставит себе
  пользователь** — то есть ровно ту сущность, о которой этап и отчитывается.
- ⚠ **Различать «доехало» и «смержено».** Флип берётся между **опубликованными** версиями; сравнение
  с `origin/main` на этот вопрос не отвечает (`auto-release-gated-on-ci-workflow-conclusion`
  §Update 2026-08-20 — `npx @latest` = «что ОПУБЛИКОВАНО», не «что в main»).
  - ⛔ **Строка выше верна для КАНАЛА С ВЕРСИЯМИ и ИНВЕРТИРУЕТСЯ там, где канал публикации — сам git.**
    У предмета, живущего в dotfiles (`~/.claude/bin` — симлинк в рабочее дерево, launchd исполняет
    файл оттуда, «релиз» = `git push`), `origin/main` **и есть** опубликованный артефакт ⇒ буквальное
    применение floor'а запрещает **единственный доступный** источник флипа и оставляет этап без
    различимости вовсе. Там флип берётся **`<sha>` против `<sha>^`**, а «доехало» доказывается
    `merge-base --is-ancestor` + побайтным `diff` блоба с файлом на диске.
  - ⚠ **Дискриминатор канала — один вопрос: «ЧТО ставит себе пользователь?»** Тарбол/пакет ⇒ версии,
    строка выше в силе. Файл из рабочего дерева репозитория ⇒ ревизии, и `origin/main` авторитетен.
  - ⛤ Класс не краевой: замер 2026-08-26 — **25** скриптов движка vteam в dotfiles, 2 launchd-джоба,
    npm-пакета у движка нет (`E404` при живой канарейке). Трансляция всех четырёх осей —
    `~/dotfiles/.claude/agents/release-agent.md` §ФОРМУ пунктов 1-4 задаёт КАНАЛ ДОСТАВКИ.
- ⛔ **Предыдущую версию брать ЗАМЕРОМ, а не «какая нашлась в кэше»:** `npm view <pkg> time --json`
  → взять соседнюю по времени публикации. Кэш `npx` накапливает сотни сборок, и произвольная
  старая версия может не содержать предмета вовсе — тогда «дефект жив» ничего не значит.
- ⚠ **Симптом-tell:** ты отчитываешься «проверено на опубликованном артефакте» и не можешь назвать
  версию, на которой та же проверка **краснеет**. Значит различимость не предъявлена.

**Empirical 2026-08-24** (тикет `c349803c`, StageRelease): смок `set-property --value ""` через

## §A52 — ⛔ Фикстура подаёт КОНСТАНТОЙ то, что прод обязан ВЫЧИСЛЯТЬ — набор проверяет арифметику ПРИ данной величине, а не саму величину


§A21 разбирает фикстуру, **выведенную** из проверяемой константы (она подстраивается ⇒ ось зелена
при любом значении). Зеркало: фикстура **фиксированная** — и ровно это её ломает, потому что
фиксирует она **выход прода**, а не его **вход**.

⛤ Механизм: у предмета есть промежуточная величина (потолок, супремум, порог, нормировка), которую
он **вычисляет** и кладёт в свою же запись. Харнесс собирает записи `mkrec(...)` и проставляет её
**литералом** — тем, что видел в живой выдаче. Дальше каждая ось честно проверяет, что решение из
этой величины выведено верно; **никто не проверяет саму величину**.

- ⛔ **Область покрытия сдвигается молча:** набор доказывает «при sup = 4.1667 решение верно», а
  читается как «гвард корректен». Между этими утверждениями лежит вся арифметика вычисления sup.
- ⚠ **Симптом-tell, ловится ГРЕПОМ по своей фикстуре:** одно и то же число стоит во **всех**
  записях (`grep -c '<величина>=' <харнесс>` = числу фикстур). Величина, одинаковая во всех
  сценариях, — почти всегда не вход, а **замороженный выход**.
- ✅ **Floor: разделить ВХОД и ВЫХОД по происхождению.** Вход (окно, K, ряд наблюдений) — литерал в
  фикстуре, это законно. Выход (то, что прод считает из входа) — **не подавать вовсе**: пусть
  считает предмет, а ось сравнивает с независимо выведенным ожиданием.
- ✅ **Дешевле полного разделения — одна ось на КРАЙ области определения:** подать вход, при котором
  величина обязана измениться качественно (у меня `TEMPO_WIN_H = 168` ⇒ `sup` падает до `0.5952` и
  `cap_reachable` обязан стать `false`). Ось краснеет ровно тогда, когда вычисление сломано.
- ⛤ **Дискриминатор «моя ли это ось» одним вопросом:** «если предмет начнёт считать эту величину
  неверно — покраснеет ли хоть что-нибудь?» Не можешь назвать ось — величина заморожена.

## §A53 — ⛔ Фикстура, прибитая к АБСОЛЮТНОМУ моменту времени, — ОТЛОЖЕННАЯ МИНА: набор зелен сегодня и покраснеет на ИСПРАВНОМ коде, когда календарь пересечёт эту точку


Секция выше — про величину, замороженную **в пространстве значений** (предмет обязан её вычислять,
а фикстура подаёт готовой). Соседний случай: величина заморожена **во времени**. Её смысл существует
только **относительно `now`** (момент сброса окна, дедлайн, TTL, `expiresAt`, «в будущем ↔ в прошлом»),
а в фикстуре стоит абсолютная константа. Пока `now < константы`, знак разности один; после —
противоположный, и **каждая** ось, чей предмет зависит от этого знака, переворачивается разом.

- ⛔ **Отказ отложенный и БЕЗ ВИНОВНИКА.** `git log` по предмету и по харнессу пуст: покраснению не
  предшествует ни одна правка. Диагностика поэтому начинается с поиска регрессии, которой не было, —
  и ищет её в коде, а не в календаре.
- ⛤ **Бьёт не только по существующим осям, но и по НЕНАПИСАННОЙ.** Ось на новую ветку требует, чтобы
  фикстура выразила «сброс через 3 ч» — абсолютная константа этого не умеет **по построению**. ⇒
  константа ограничивает не только срок жизни набора, но и то, какие оси в нём **можно написать**;
  параметризация фикстуры становится **предусловием реализации**, а не улучшением.
- ⚠ **Симптом-tell ловится ЧТЕНИЕМ ОДНОЙ СТРОКИ:** в одном литерале соседние поля вычислены
  по-разному — одно от `now`, другое магической константой:
  `{"ts": int(time.time()) - shift, "anchor": 1800000000}`. Приём относительного времени в фикстуре
  **уже применён рядом** и не применён здесь — значит это упущение, а не решение.
- ✅ **Floor: фикстура принимает СДВИГ относительно `now`** (`anchor = int(time.time()) + 3*3600`),
  а не абсолют. ⛔ И **мутант тоже** — иначе он протухнет вместе с ней и перестанет краснить свою ось.
- ⛔ **«Отодвинуть константу подальше в будущее» — перенос мины, а не снятие.** «Дата ещё не
  наступила» не является утверждением о корректности; оно устаревает само.
- ⛤ **Отличать от секции выше по ТОМУ, ЧТО ЗАМОРОЖЕНО:** там заморожен **выход прода** (набор
  проверяет арифметику при данной величине, а не саму величину); здесь заморожен законный **вход**, и
  портит его не прод, а **часы**.

**Empirical 2026-08-24** (`vteam-supervise-verify.sh:165`, захват тикета `57de43cd`): `mkburn` пишет
`"anchor": 1800000000` = **2027-01-15 08:00 UTC**, тогда как соседнее `ts` в том же литерале —
относительное (`int(time.time()) - shift`). Сегодня `T = anchor − now ≈ 3446 ч`, поэтому все **10**
осей D4 остаются зелёными; после 2027-01-15 якорь уходит в прошлое, второй конъюнкт предложенного
фикса (`rem_h < WARN_H` И `rem_h < (anchor − now)/3600`) становится ложным всегда ⇒ правило
подавляется, и набор краснеет на исправном коде. ⛤ За **50 минут** до находки другой воркер правил
ЭТОТ ЖЕ харнесс (добавил ось `A34` + мутант `M24`) и мину не заметил — она не видна при обычной
работе с файлом, только при попытке выразить фикстурой относительное время.

## §A54 — ⛔ Флип, прогнанный на НИЖНЕМ слое, доказывает ПРИМЕНИМОСТЬ мутации, а не ВЕРДИКТ осей: предсказание «краснеют ровно A+B» из него не следует

§A44 разбирает ожидание, выведенное **из темы мутанта** («снял ярус ⇒ покраснеет ось про ярус»), и
§Зеркало — случай, когда автор матрицы **не гонял вовсе**. Третий случай лежит между ними и потому
выглядит добросовестным: автор спецификации **прогнал флип** — но на **нижнем слое**, а утверждение
сделал про **верхний**.

| что прогнали | что этим доказано | что утверждали |
|---|---|---|
| сам сканер/хелпер на трёх копиях предмета | «мутация ляжет, сканер её увидит» | «мутант краснит **РОВНО** оси A+B» |

⇒ проверена **применимость мутации**, а не **вердикт набора**. Это разные утверждения, и второе не
следует из первого ни при каком качестве первого прогона.

- ⚠ **Симптом-tell АВТОРУ спеки, ловится ДО отгрузки формулировки:** твой флип трогает **функцию**
  (сканер, хелпер, предикат), а предсказание сформулировано в **именах осей**. Уровни разошлись ⇒
  предсказание есть вывод, а не замер, и помечать его надо как гипотезу.
- ✅ **Floor: утверждение о вердикте ОСЕЙ доказывается прогоном ОСЕЙ на полном наборе** — то есть
  внешним мутантом предмета и чтением строки `PASS/FAIL` вместе со списком красных. Один прогон;
  он же даёт число для §Приёмки.
- ⛤ **Частая механика неотделимости, из-за которой предсказание промахивается именно вверх:**
  ассерты соседних осей ключуются на **ОДНОМ агрегатном счётчике** («без дефолта == 1»). Внешний
  мутант снимает один дефолт, внутренний мутант соседней оси кладётся **поверх** ⇒ счётчик `2` ⇒
  ассерт не выполняется. Зеркально, внутренний мутант «своей» пары не ложится вовсе (гвард
  `line.count(FRAG) != 1` → `SystemExit(2)`) ⇒ ветка «мутация не легла». Обе оси краснеют по
  ЗАКОННОЙ причине — это не смешение (§A44), а свойство агрегата.
- ⛔ **Радиус чужой оси НЕ расширять.** Устойчивость к внешней мутации соседней пары требует правки
  ЕЁ ассерта, а он принадлежит своему тикету; §Границы это запрещают. Верный ход — назвать
  расхождение в теле тикета и оставить решение приёмке.
- ⛤ **Намерение критерия при этом часто ДОСТИЖИМО другим носителем, и его надо предъявить.** Если
  спека сама назвала атрибуцию («форма строки, а не число осей»), покажи её замером: у меня `U3`
  печатает `БЕЗ ДЕФОЛТА irun/VTEAM_NOTIFY` против `irun/VTEAM_DISPATCH_LOG` — то есть оси
  различают предмет поимённо, хотя число красных совпадает.

**Empirical 2026-08-27** (тикет `848f5034`, `vteam-supervise-verify.sh`, StageImplementation):
§Чем проверить п.3/п.4 обещали `notify → ровно U3+U5` и `dispatch → ровно U3+U4`; прогон дал
`U3+U4+U5` в обоих случаях. §Флип спецификации гонялся на `_defscan` (сканер), не на осях. Флип
самого фикса при этом состоялся и подтвердил посылку тикета: внешний мутант на ДО-правочном файле
`PASS=103 FAIL=0 rc=0` (ноль краснот — дефект воспроизведён), на ПОСТ-правочном `PASS=101 FAIL=3
rc=1`. Радиус не расширен, расхождение выписано в тело тикета.

## §A55 `2026-08-27` — мутант, делающий предмет НЕИСПОЛНИМЫМ, есть БЕСПЛАТНЫЙ детектор вакуумных осей

Мутант «снять бит исполнения» писался как ось A0 (предмет обязан запускаться ПО ПУТИ) и
предсказание к нему стояло `[A0]`. Прогон дал **16 красных из 20**. Первая реакция — «оси
смешаны, надо чинить предсказание»; она неверна и стоила бы всей ценности прогона.

⛤ **Механика:** неисполняемый предмет проваливает КАЖДУЮ ось, которая его реально
запускает. Значит предсказание `[A0]` было ложным по построению, а полный набор красных —
не шум, а **перепись осей, у которых предикат зависит от живого предмета**.

⇒ Отсюда бесплатный аудит, ради которого разбор и записан: **оси, оставшиеся ЗЕЛЁНЫМИ под
таким мутантом, вакуумны** — их предикат удовлетворился мёртвым предметом.

### Что нашлось (замер 2026-08-27, харнесс `founder-notify-verify.sh`)

| ось | предикат до | чем удовлетворилась у мёртвого предмета | предикат после |
|---|---|---|---|
| A12 «токен не печатается» | искомого нет в выводе | у мёртвого предмета вывода НЕТ вообще | + канарейка «прогон СОСТОЯЛСЯ» |
| A16 «битый JSON ⇒ PARSE» | `rc != 0` | неисполняемый даёт `rc=126` | `rc = 1` + свой текст в stderr |
| A17 «нет токена ⇒ CONF» | `rc != 0` | то же 126 | `rc = 1` + свой текст в stderr |

Замер кодов: `${1:?}` (штатный отказ) → **rc=1**; неисполняемый файл → **rc=126**. То есть
`rc != 0` не различал «предмет отказал по делу» и «предмет не запустился» — ровно форма,
которую `self-satisfying-metric-weak-verifier` §A38 называет слабым предикатом-отрицанием.

### Floor

- ⛔ **Пересвет широкого мутанта НЕ чинить правкой предсказания в одиночку.** Сперва
  выписать зелёные под ним и по каждой ответить, чем она удовлетворилась.
- ✅ Предикат отказа — **конкретный код** (`rc = 1`) плюс **собственный текст** предмета в
  stderr. Тогда «не запустился» перестаёт удовлетворять ось «отказал по делу».
- ✅ Ось вида «искомого нет в выводе» обязана нести **канарейку прогона** (маркер, который
  живой предмет печатает всегда), иначе пустой вывод мёртвого её удовлетворяет.
- ⛤ Предсказание для такого мутанта пишется **полным множеством** с комментарием, почему
  оно широкое, — иначе следующий читатель прочтёт его как смешение осей.

### Разграничение с соседями

| раздел | наблюдаемое | корень |
|---|---|---|
| **§A55** (этот) | покраснело БОЛЬШЕ предсказанного, контроль зелёный | пересвет ЗАКОНЕН: предмет убит целиком |
| §A44 | ожидание ШИРЕ фактического | оси не независимы; предикат одной включает условие другой |
| §A29 | пересвет + контроль ЗЕЛЁН | НАГРУЗКА: прогоны не успевают произвести разбираемый вывод |
| §A12 | набор зелёный, красных нет | мутация НЕ ЛЕГЛА — проверять саму мутацию |

⚠ **Tell, ловится до всякого разбора:** мутант, чья тема — способ ЗАПУСКА предмета (бит
исполнения, shebang, пустой файл, права на каталог), а предсказание названо одной осью.
Такой мутант по построению не может быть узким.


## §A56 `2026-08-28` — предмет есть МЕТА-ИНСТРУМЕНТ: его собственный механизм мутантов направлен на ЕГО предмет, а не на него

§A51 берёт флип двумя ревизиями, потому что артефакт **опубликован** и ломать нечего. Здесь
предмет ломать **можно**, и мутанты у него **есть** — но они мутируют **его предмет** (харнессы,
файлы каталога, входы линтера), а мутировать надо **сам инструмент**. Механизм выглядит
применимым и таковым не является.

⚠ **Симптом-tell, ловится ДО написания оси:** ты собираешься проверить правку инструмента его же
`MUTANTS`-таблицей — и не можешь назвать строку этой таблицы, которая тронет **строку, изменённую
тобой**. Таблица адресует чужой файл.

✅ **Форма:** две ревизии инструмента на **копиях** (`git show HEAD:<путь>` против живого файла),
обе грузятся отдельными модулями, сравниваются **МНОЖЕСТВА** их вердиктов. ZERO-GIT-TOUCH
сохраняется — боевой файл не трогается ни разу.

⛔ **`rc` дискриминатором быть НЕ МОЖЕТ, если он НАСЫЩЕН.** У инструмента, чей контроль красен по
вне-scope причинам, `rc = 1` в **обеих** ревизиях ⇒ флип невидим, а «rc не изменился» читается как
«фикс ничего не дал». Судить надо по составу: `было − стало` (что фикс снял) и `стало − было`
(регрессия). Замер 2026-08-28 (`vteam-catalogue-audit.py`, тикет `17d97ac0`): **9 → 8** красных из
126, `ИСЧЕЗЛО = {(vteam-dispatch-verify.sh, Т4)}`, `ПОЯВИЛОСЬ = ∅` — при `rc = 1` до и после.

⛤ **Контроль брать на ЖИВОЙ популяции предмета, а не на фикстуре.** У мета-инструмента она уже
есть — это его боевой вход (здесь 14 харнессов); прогон обеих ревизий по нему доказывает
отсутствие регрессии на **реальных** данных, чего фикстурный набор не даёт по построению.

⛤ **Мутанты на саму правку писать всё равно**, но применять к **копии** и проверять ОБЕИМИ
поверхностями — боевой популяцией и встроенным selftest'ом: они краснят разное. Замер: M1 (снять
распознавание новой формы) краснит обе; M2 (ослабить предикат) и M3 (снять внутренний гвард) —
только selftest, потому что боевые данные их не упражняют. ⇒ проверка одной поверхностью
объявила бы M2/M3 неразличимыми.

⚠ **Канарейка реверта обязательна** (§A42): маркеров фикса в ревизии ДО должно быть **0**, иначе
«две ревизии» окажутся одной и флип выйдет вакуумным. Замер: 0/0/0/0 до против 2/3/3/2 после.

⛤ **Сосед по предмету, но по ДРУГОЙ оси:** `harness-invocation-surface` §САМОРЕФЕРЕНТНОСТИ
КАТАЛОГА — там мета-инструмент находит САМ СЕБЯ при обходе (рекурсия исполнения); здесь он
**не может себя проверить** (форма revert-verify). Общий предмет, разные отказы.
