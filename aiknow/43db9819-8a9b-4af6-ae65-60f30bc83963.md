# GUI mutation-testing → dedicated temp-vault, НИКОГДА не live vault

## Принцип

Любое **мутирующее** GUI-тестирование Obsidian-плагина через computer-control (BRAT install/update, `bootstrap-vault`, `add-assetspace`, `apply-profile`, ExoSync `sync`/`push`, create-instance, любая команда, пишущая на диск/в remote) выполняется на **выделенном свежем temp-vault**, а **НЕ на живом vault пользователя** (vault-2025 / vault-exodev / vault-my / vault-2024) — **даже если пользователь/оркестратор назвал живой vault как «тест-окружение»**.

«Тестировать на vault-2025» в ответе на вопрос о тест-окружении ≠ «мутировать боевой vault». Read-only осмотр живого vault (открыть страницу, посмотреть layout, Esc) — допустим; **мутация боевого vault — нет** без явного, отдельного, mutation-aware подтверждения.

## Когда правило срабатывает

- Фаза execution computer-control тест-прогона плагина, где сценарии включают BRAT/bootstrap/apply/sync/create (мутации диска или remote).
- Интервью/директива назвала живой vault как «test environment» / «vault-2025» — это НЕ санкция на BRAT-update + мутации боевого vault.
- Любой `apply-profile` (strict-replace mount → может unmount/удалить AssetSpace), `add-assetspace` (пишет на диск), ExoSync `push` (необратимо в remote).

## Протокол (safe temp-vault gate)

1. **STEP 3.0** — создать temp-vault: `mkdir -p /Users/kitelev/Developer/temp-vaults/ux-test-$(date +%s)/.obsidian` + минимальный `app.json` (+ опц. `Welcome.md`).
2. **STEP 3.1** — открыть его в Obsidian. ⛤ `obsidian://open?path=…` URI работает ТОЛЬКО для уже-зарегистрированных vault (для нового — «Vault not found»); надёжный путь — vault-switcher (имя vault внизу-слева) → «Manage vaults…» → «Open folder as vault» → native picker (часто уже в `temp-vaults`) → выбрать папку → Open.
3. **STEP 3.2 — HARD GATE (одноразово, ПЕРЕД любым действием):** screenshot → проверить имя активного vault внизу-слева = `ux-test-<ts>`. Если видишь `vault-2025`/`vault-my`/любой не-temp → ⛔ STOP, переключиться, не действовать. Только подтверждённый temp-vault → дальше. (Re-verify identity per-action избыточен — активный vault сам не переключается; reload re-открывает тот же vault, после reload — один re-check разумен.)
4. **STEP 3.3** — мутирующие тесты против temp-vault: BRAT install → PAT в Settings (data.local.json, device-local, ⛔ НЕ git config — dotfiles-симлинк-утечка) → bootstrap/add/apply. ⛔ **`sync`/`push` temp-vault НЕ покрывает** — REST-push идёт в remote из registry-дескриптора, включая **public prod repo** ⇒ только supervised и после трёх проверок §Addendum 2026-06-22.

## Запреты

- ⛔ BRAT install/update плагина на боевом vault для «verification» (правило obsidian-plugin-update-via-brat — про КАК обновлять, это правило — про ГДЕ тестировать). Manual-copy тем более.
- ⛔ Трактовать «vault-2025» из интервью/директивы как санкцию на мутации боевого vault. При сомнении — temp-vault + спросить.
- ⛔ Re-verify vault-identity опускать совсем (HARD GATE обязателен один раз ПЕРЕД первой мутацией).
- ⛔ PAT в git config (host `~/.gitconfig` = симлинк в tracked dotfiles → утечка). Только Settings PAT-поле → data.local.json.

## ⛔ Addendum (2026-06-22) — temp-vault ≠ безопасный ExoSync push (tarball-mount AS зеркалят public prod repos)

<!-- Added by /session-retrospective 2026-06-22 — root: child al-night-uxcc, create-команды создали тест-ассеты в exoas-exo (public prod mirror); ExoSync Sync без изоляции REST-пушнул бы их в production. -->

Temp-vault защищает от мутации **live-vault на диске**, но НЕ автоматически от **push в чужой remote**. AS, смонтированные через «Add a knowledge pack», — **tarball mounts** (нет локального `.git`/remote), НО ExoSync push идёт через **GitHub REST API** против remote из registry-descriptor. Если тест создал ассеты в папке AS, зеркалящей **PUBLIC production repo** (напр. `exoas-exo` ← `kitelev/exoas-exo`), и AS registry-registered → `ExoSync Sync/Push` REST-пушнет тест-мусор в production.

**Перед ExoSync Sync/Push в computer-control тесте (даже на temp-vault):**
1. Убедиться, что local changes ТОЛЬКО в изолированном приватном test-AS (exoas-temp), НЕ в public-AS-mirror папках. Удалить тест-артефакты из public-AS папок ИЛИ свежий temp-vault с ТОЛЬКО приватным test-AS.
2. PAT write-scope verify (`gh api repos/<o>/<r> -q .permissions`) перед push.
3. **Supervised** операция (push мутирует remote) — ⛔ не автономно. Это пересекает irreversible/live-data guardrail.

Cross-tie: `verify-before-assert` (проверь push-target до Sync), FINDING-3 (ad-hoc AS не синкается без descriptor — обратная сторона).

## Addendum (2026-07-10) — программная регистрация temp-vault в obsidian.json + restart безопаснее GUI vault-switcher; HARD GATE ловит уже-открытый живой vault

STEP 3.1 предлагает открывать temp-vault через GUI vault-switcher («Open folder as vault»). Эмпирически (visual-smoke conditional displayName, 2026-07-10) обнаружены две вещи:

1. **`obsidian://open?path=<temp>` на НЕзарегистрированный vault показывает «Vault not found» ПОВЕРХ уже-открытого ЖИВОГО vault** (у меня — vault-my с личным ассетом). Клик OK по диалогу лишь закрывает его → остаёшься в **живом** vault. Если тут же начать визуал-smoke (toggle статуса) — мутируешь личный vault. **HARD GATE (STEP 3.2) поймал это**: `window_title`/имя-vault-внизу-слева = `vault-my`, не `dn-uismoke-*` → СТОП, переключиться. Урок: **проверять имя активного vault по `window_title` СРАЗУ после любого `obsidian://open`**, до любого клика-мутации — диалог «Vault not found» НЕ означает пустой экран.

2. **Программная регистрация безопаснее GUI-навигации в живом vault.** Вместо кликов по vault-switcher (риск mis-click по элементам живого vault): добавить temp-vault в `~/Library/Application Support/obsidian/obsidian.json` (`vaults` map: `{"<sha1-id>": {"path":"<temp>","ts":<ms>,"open":false}}`) программно (python), затем **обязательно перезапустить Obsidian** — запущенный инстанс кэширует реестр vault'ов при старте, `obsidian://open?path=` НЕ подхватит новую запись без restart (verified: URI дал «Vault not found» повторно, пока не сделал `osascript quit` + relaunch). После restart → `obsidian://open?path=<temp>` открывает temp-vault + Trust-диалог («Trust author and enable plugins» — обязательно, иначе плагин не загрузится). **Cleanup:** quit → удалить temp-запись из obsidian.json → `obsidian://open?path=<vault-my>` (вернуть живой vault). Оба пути (GUI vault-switcher из STEP 3.1 ИЛИ программный obsidian.json+restart) валидны; программный — меньше GUI-mutation-риска.

Cross-tie: `computer-control` (IMAGE-координаты, re-screenshot после мутирующих кликов), `gui-input-verify-then-poll` (verify фокус/состояние до действия — здесь: verify имя vault до мутации).

## ⛔ Addendum 2026-08-15 — `cp -al` НЕ изолирует CLI-мутацию: `exocortex-cli` пишет frontmatter НА МЕСТЕ, и правка «копии» уходит в ЖИВОЙ vault

Всё правило выше — про **GUI**-мутацию (BRAT, apply-profile, клики). Для **CLI**-проверки («а что реально сделает эта команда?») напрашивается более дешёвый ход: `cp -al <vault> <scratch>/copy` — хардлинк-копия строится за секунды, места не занимает, и по интуиции «мутация отвяжет линк, оригинал уцелеет».

⛔ **Интуиция неверна, проверено замером.** `exocortex-cli set-property` переписывает файл **по тому же inode** (`links=2` сохранён), поэтому правка копии **видна в оригинале немедленно**:

```
до : inode orig=330092069 copy=330092069 links=2   probe__field: BEFORE
set-property … --vault <copy> --value AFTER
после: inode orig=330092069 copy=330092069
ОРИГИНАЛ: probe__field: AFTER      ← живой файл изменён
КОПИЯ   : probe__field: AFTER
```

- ⛤ **Изоляция асимметрична, и это единственное, что делает приём иногда пригодным:** **создание НОВОГО** файла даёт новый inode ⇒ безопасно; **мутация СУЩЕСТВУЮЩЕГО** — сквозная. Композит `create_instance → property_set(created) → repairFolder(created)` не трогает пре-существующих файлов и потому прошёл без урона (прототип `123b28ef`: mtime остался `2026-07-11`). Но это свойство **конкретного композита**, а не метода: один шаг без `targetsCreatedInstance` — и мутация уходит в живой прототип.
- ✅ **Floor: `cp -al` годится ТОЛЬКО read-only** (SHACL-скан, `audit co-location`, `resolve-buttons`) **и для команд, чьи шаги доказанно пишут лишь в созданный инстанс.** Всё прочее — `cp -a` (полная копия, ~сотни МБ, но честная) либо temp-vault по протоколу выше.
- ⚠ **Симптом-tell до запуска:** ты собираешься запустить на копии команду, чей target — **пре-существующий** ассет (`mark-done`, `set-parent`, `set-label`, любой `apply` по клик-таргету). Проверка одна: `stat -f %l <файл>` — `links > 1` означает «это тот же файл, что в живом vault».
- ⛔ **Копию удалять СРАЗУ после проверки.** Замер 2026-08-15 нашёл чужую копию двухдневной давности: **9193 из 9212** файлов всё ещё хардлинкованы в `vault-my` — то есть любая CLI-мутация в том scratchpad ушла бы в живые данные, а автор об этом не знает.
- ✅ **ДЕТЕКТОР класса — одна команда, и он не зависит от того, где лежит копия** (её каталог может называться как угодно, лежать в чужом scratchpad и пережить свою сессию). Спрашивать надо **живой vault**, а не искать копию:
  ```bash
  find ~/vaults/vault-my ~/vaults/vault-tbank ~/vaults/vault-exodev -name '*.md' -type f -links +1 | head
  ```
  Непусто ⇒ где-то существует hard-link копия; найти её по inode: `find /private/tmp/claude-501 -inum <inode>`.
  ⛤ Это **положительный** детектор: он ищет свойство, которое в норме отсутствует у **всех** файлов (замер 2026-08-15 после уборки: `links>1` = **0** во всех трёх vault), поэтому ложных срабатываний у него нет по построению.
- ⛤ **Удаление копии БЕЗОПАСНО для оригиналов, но НЕ для файлов без второго линка.** `rm` снимает линк, данные живут, пока остаётся хотя бы один ⇒ живой vault не страдает (замер: 9254 → 9254 файла, байт-в-байт, sha256 пробы не изменился, `links 2 → 1`). ⛔ Но файлы с `links == 1` существуют **только в копии** — их `rm` уничтожает окончательно. **Floor перед удалением:** `find <copy> -type f -links 1` → по каждому проверить, есть ли он в живом vault; нет ⇒ либо тестовая проба (удалять), либо последний экземпляр (страховать). Замер: 21 singleton = 17 устаревших версий (живой файл пересоздан **атомарной записью Obsidian**, которая линк как раз рвёт — в отличие от CLI) + 3 пробы + 1 намеренно удалённый ассет, живой ещё в двух mount'ах.
- ⛤ **Побочно опровергнут документированный рационал соседнего рецепта** (`exosync-quarantine-triage` §A3a): SHACL-baseline через `cp -al` держится на том, что «мутация рвёт хардлинки». Она их **не рвёт** ⇒ такой «эталон» меняется вместе с живым vault и baseline'ом не является. Годен только когда между снимком и сравнением мутаций **нет** (внешняя дельта от `pull` — да, своя правка — нет).

## ⛔ УБОРКА ПОСРЕДИ ЖИВОГО ХОДА наблюдаемого: он рапортует ЛОЖНЫЙ ДЕФЕКТ СВОЕГО инструмента, и обвиняет НЕ ТЕБЯ

§Addendum 2026-08-04 (соседнее правило) лечит ось **авторства**: дифф `before/after` не отличает
своё от чужого ⇒ удалять по принадлежности. Здесь ось **времени**: файл однозначно **твой** (создан
твоей же пробой), а наблюдаемый **ещё с ним работает** — его цепочка не закончилась.

⛔ **Отказ приходит не тебе и выглядит убедительно.** Актор обнаруживает исчезновение файла посреди
своей последовательности и объясняет его **единственным механизмом, который знает** — своей же
командой: «команда отрапортовала успех, а файл физически удалился, похоже на баг/регрессию».
Это правдоподобный отчёт о потере данных, и он адресован **владельцу инструмента**, а не тебе.

- ⚠ **Симптом-tell, ловится ЧТЕНИЕМ отчёта:** актор жалуется на дефект инструмента, которого ты
  **не менял**, в окне, где ты **удалял** его артефакты. Совпадение окна и есть подозреваемый.
- ⛔ **Цена — не лишний цикл, а ЛОЖНЫЙ БАГ В ТРЕКЕРЕ.** Актор обычно предлагает его завести;
  согласие владельца стоит одного слова, а расследование несуществующей потери данных — дней.
  ⇒ обнаружив, **снять вслух и немедленно**, тем же каналом: «дефекта нет, файл удалил я».
- ✅ **Floor: уборка — ПОСЛЕ завершения хода, и завершение проверяется НЕ одним замером.** Предикат
  «артефакт не менялся N секунд» лжёт у актора, который **думает между шагами**: пауза внутри хода
  легко длиннее интервала. Требовать **несколько подряд** стабильных замеров с интервалом, заведомо
  бо́льшим типовой паузы (у LLM-актора — от 10 с, 2-3 подряд).
- ⚠ **Замер 2026-08-30: тот же предикат обманул ДВАЖДЫ за один проход** — я прочитал середину хода
  и счёл её финалом; во второй раз ход продолжился ещё **20** запросами после «завершения».
- ⛤ **Побочная выгода честного признания:** актор, получив корректировку, снимает наблюдение
  («убираю из головы, баг заводить не буду») — то есть ложный дефект гаснет там же, где возник,
  и не оставляет следа в его памяти.

**Empirical 2026-08-30** (живая проба `scn__StateReaction`): бот создал инстанс `e5ac99e9` и вёл его
по цепочке `create → backlog → start → done → archive`; я удалил файл после шага `done`, приняв
паузу за конец хода. Бот сообщил: «на шаге `apply archive` он **бесследно исчез** — команда
отрапортовала успех, а файл физически удалился… похоже на баг/регрессию в CLI. Хочешь, заведу баг
