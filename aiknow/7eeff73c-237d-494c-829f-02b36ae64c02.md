# PMBOK WBS = nested-ассеты, не body-only

## Принцип

WBS (Work Breakdown Structure) любого оркестрируемого `ems__Project` **ОБЯЗАН** быть материализован как **вложенный граф ассетов**, а не описан только текстом в body проекта.

- **root** `ems__Project` (сам проект)
- → **internal node** `ems__Project` на каждую фазу / major-grouping (⛔ **новые `pmbok__Milestone` НЕ заводятся** — директива фаундера 2026-08-16, бессрочная: «Даты вех не нужны ни сейчас ни в будущем. Это избыточно». Линковать только **исторический** `pmbok__Milestone`, где он уже есть — их 49 от проектов до директивы, и они остаются как есть)
- → **leaf** `ems__Task` на каждый атомарный work-package

Связь строго **child→parent через `ems__Effort_parent`** (UWI — никаких A↔B пар). Статус каждого узла = `ems__Effort_status` (Backlog / Doing / Done), **не** markdown-чекбокс `- [x]`.

**Authoritative WBS = граф, queryable** через transitive property-path:

```sparql
SELECT ?node ?label ?status WHERE {
  ?node ems:Effort_parent+ <PROJECT-UID> .
  ?node exo:Asset_label ?label .
  OPTIONAL { ?node ems:Effort_status ?status }
}
```

Body проекта может содержать **summary-tree-зеркало / narrative / RESUME / Progress Log** — но если оно расходится с графом, **граф = истина**. Body-WBS как единственная (authoritative) форма — **недопустимо**.

## Почему (rationale)

Body-only WBS (markdown-чекбоксы / bullet-список фаз в теле проекта):
- **не queryable** — нельзя `?t ems:Effort_parent+ <project>`, статус/прогресс невозможно агрегировать SPARQL'ом (`/pmbok-status` §4 Schedule, `/pmbok-close` completeness-check ломаются);
- **не resumable надёжно** — cold-start оркестратор (Step-0) парсит текст вместо графа, легко рассинхронизируется;
- **не first-class** — задачи не существуют как ассеты → нельзя линковать PR/lessons/locks/responsible, нельзя независимо менять статус, нет co-location;
- **дрейфует молча** — чекбокс в body и реальное состояние работ расходятся без детекта.

Nested-граф решает всё перечисленное: каждый work-package — первоклассный ассет с собственным статусом, линками, co-location; прогресс агрегируется детерминированно; resume опирается на граф.

Это **тот же паттерн, что PMBOK Charter/Milestone/Risk** — связанные ассеты, не body-текст. И тот же фрактал, что уже встроен в `/pmbok-init` («Vision core invariant»: root=Project, internal=Project, leaf=Task; `ems__Effort_parent` polymorphic поддерживает Task→Project и Project→Project).

## Создание — через `exocortex-cli` (canonical), issue+fallback

- **ВСЕ WBS-узлы создаются через `npx @kitelev/exocortex-cli create`** (CLI-first, согласовано с EKA / UI-CLI-parity). CLI создаёт queryable граф напрямую.
- **CLI-проблема/неудобство** (класс не поддержан, нет `ems__Effort_parent`-флага, broken/stale version, неверная co-location) → **немедленно GitHub Issue (kitelev/exocortex)** с конкретикой + **fallback на `/exocortex-asset` / Write**. Документируй issue# + причину fallback.
- **⛔ Safety floor:** CLI-create идёт через Bash → PreToolUse Write/Edit hooks (`validate-wikilinks` / `co-location-enforce` / SHACL pre-validate) **НЕ срабатывают** (см. `vault-asset-creation`). Поэтому после CLI-batch **обязателен** post-validate: `rm -f <vault>/.exocortex/cache/triples.json && npx @kitelev/exocortex-cli validate schema --shapes-mode` → **0 violations** (см. `shacl-validate-clear-cache`). Без post-validate CLI-create = слепой bypass (запрещён). Все UID в CLI-аргументах — pre-verified (резолв полного UID, не дописывать по памяти — `verify-before-assert`).
- co-location invariant (CR-1) + UID-canon + UWI соблюдаются для каждого узла.

- **⛤ Write-fallback порядок при body-cross-links: создавай BOTTOM-UP, не top-down.** Hook `validate-wikilinks` блокирует Write файла, чьё **тело** (или frontmatter) ссылается `uid` на ещё-не-существующий ассет. Frontmatter `ems__Effort_parent` всегда указывает child→parent (UWI) → **родитель должен существовать до ребёнка** (parent-first для frontmatter). Но **тело родителя**, перечисляющее детей через `child-uid`, ссылается forward → блок. Разрешение: (1) Write родителя с **placeholder** в теле (напр. `<!-- WBS-LINKS -->`) без forward-wikilinks → (2) Write детей (их `ems__Effort_parent` резолвится, родитель уже есть) → (3) `Edit` тело родителя, заменяя placeholder на `child-uid`-ссылки (дети теперь существуют). Sibling-cross-links в теле задач — тоже forward-риск: либо plain-text UID, либо тот же placeholder-then-Edit. ## ⛔ Новый work-item → немедленно в граф (2026-06-14, user-flagged)

Любой **newly-created project work-item** (GitHub issue — заведён оркестратором ИЛИ child'ом; finding/баг; decision-task; выявленная под-работа) **ОБЯЗАН быть немедленно материализован как nested `ems__Task` под проект** (`ems__Effort_parent` → milestone/sub-project; статус Backlog/Doing) — **если нет ЯВНОЙ инструкции не добавлять.** ⛔ Не откладывать «на потом»: issue/задача без WBS-узла = **scope-дыра** (граф неполон, прогресс не queryable, при resume теряется). ## ⛔ Internal WBS-узел ОБЯЗАН быть ems__Project, не ems__Task (SHACL ParentEffort shape, 2026-06-20)

Инвариант «internal=Project» имеет **конкретный SHACL-механизм**: shape для `ems__Effort_parent` требует, чтобы **target принадлежал классу `ems__ParentEffort`** (`17c5cf45-ce6a-4142-8d2a-65ac447f1168`). `ems__Project` (`7db5eeff`) **IS-A** ParentEffort (через superClass). `ems__Task` (`1b20a8f0`) — **НЕ** ParentEffort (superClass только `ems__Effort` `086f71fa`). → Ребёнок, чей `ems__Effort_parent` указывает на **Task-typed** узел, даёт `sh:class violation: <parent> does not conform to ems#ParentEffort`.

**Gotcha при декомпозиции:** если milestone/направление было создано как `ems__Task` (лист), а потом добавляешь под него детей — **сначала re-type его `exo__Instance_class` `1b20a8f0…`→`7db5eeff…`** (Task→Project), затем создавай детей. Иначе SHACL краснеет на КАЖДОМ ребёнке. Семантически корректен (узел с детьми = internal node = Project). Project→Project parent-link (если у самого узла есть parent) валиден (polymorphic).

- ✅ **Порядок обязателен и он ровно обратный интуитивному** («сначала почищу, потом разложу»):

- ⛔ **CLI-пути «снять `ems__Effort_status`» НЕ существует:** `remove-property` отказывает fail-loud

### ⛔ Тот же shape ловит дефект НА УРОВНЕ КЛАССА, а не только инстанса (2026-08-05)

Абзац выше лечит случай «узел создан не тем классом». Зеркальный, менее очевидный: **класс выбран верно, но САМ КЛАСС не наследует `ems__ParentEffort`** — тогда нарушения дают все его инстансы, у которых есть дети, и виноват TBox, а не разметка.

- ⛔ **Заводя НОВЫЙ класс-эффорт, спроси: «у его инстансов будут дети?»** Да ⇒ `ems__ParentEffort` в `superClass` **сразу**, при создании. Иначе класс выглядит рабочим ровно до первого ребёнка, и дефект всплывает у того, кто просто размечал данные.

## ⛔ Interview/discovery-сессия = WBS-task (business-analysis work-unit, 2026-06-20 user-directive)

**Проведение интервью — это discovery-этап продуктовой разработки (бизнес-анализ), а значит самостоятельный work-unit → ОБЯЗАН иметь свою WBS-task ноду.** Не только impl-задачи материализуются в граф (R16/R17) — **interactive interview / requirements-discovery / decision-gathering сессия ТОЖЕ** (это «работа по выявлению требований/решений», не «ничто»).

**Что засчитывается:** любая дочерняя (или orchestrator-direct) сессия, чья суть = задать пользователю вопросы и собрать решения/требования: `/child-interactive-interview`, roadmap-интервью, decisions-интервью, RFC-fork-интервью, custdev/discovery, templating/dedup/docs-paradigm interview-фазы.

**Протокол (orchestrator + interview-child):**
1. **Orchestrator создаёт discovery-task ноду ПРИ спавне** interview-child (как любой work-item, R16 «новый work-item → немедленно в граф»): `ems__Task` под проект/milestone, статус **Doing**, label «Discovery/интервью: <тема>», responsible (a.kitelev если решения его). Co-located, isDefinedBy, SHACL=0.
2. **Interview-child записывает в эту ноду** (или orchestrator по докладу): **повестку** (вопросы) + **решения Андрея по каждому** (decisions-record) в теле → флип **Done** на завершении. Нода = durable-трасса discovery-работы.
3. **Downstream-impl ноды линкуются** к discovery-task (decisions материализуются в impl-задачи, но сама discovery остаётся отдельным затрассированным узлом — не «растворяется» в impl).

**Образец (хорошо):** `al-roadmap-iv` (16 направлений → decisions-doc + 20 аннотаций + 4 флипа). **Анти-паттерн (gap, который закрыло это правило):** `al-decisions-iv` / `al-diagram` — решения/работа только в ping'ах + downstream, своей WBS-ноды нет → discovery-работа не queryable, при resume теряется.
## ⛔ Flip node `ems__Effort_status` ПО ХОДУ работы, не откладывать на closure (2026-07-06)

<!-- Added by /session-retrospective 2026-07-06 — root: displayName-labeling v1 (47d57acf) — orchestrator трекал прогресс в body-WBS-чекбоксах `[x]`, но 6 leaf-нод остались `Backlog` в frontmatter до самого closure. -->

Правило §выше запрещает body-чекбокс как источник истины (строка «⛔ Считать body-чекбокс источником истины»), но есть **скрытый под-провал**: оркестратор может добросовестно вести body-WBS-чекбоксы `[x]` и Progress Log, **забывая флипать `ems__Effort_status` самих leaf-нод** по мере завершения фаз. Тогда граф молча расходится с реальностью весь проект, и closure натыкается на «6 нод Backlog при AllAccepted» = red-flag, требующий batch-флипа в конце.

- **Флипай статус ноды в момент завершения фазы** (R16 «отражать непрерывно» применяется к **frontmatter-статусу ноды**, не только к body-зеркалу). `Backlog→Doing` при старте фазы, `→Done` при мёрдже/релизе/верификации.
- **Механика (dogfood-hook блокирует raw Edit frontmatter):** `apply start-effort <path>` (Backlog→Doing) → `apply mark-done <path>` (Doing→Done), батчем через stdin-pipe для нескольких нод. CLI сам ставит start/end/resolutionTimestamp.
- **Closure WBS-completeness check тогда тривиален** (все ноды уже Done по ходу), а не «batch-флип 6+ нод в закрывающую сессию».
- **Empirical 2026-07-06 (47d57acf displayName-labeling v1):** все 6 leaf-нод + проект остались `Backlog` в frontmatter (прогресс жил только в body-чекбоксах `[x]` + Progress Log). Closure потребовал batch `apply start-effort`→`mark-done` ×6 нод + проект (2 CLI-вызова батчем + project ×2). Урон 0 (граф приведён в порядок при closure, SHACL 0), но это был отложенный долг вместо непрерывного отражения. Floor: флипать node-статус при каждом фазовом transition, не копить до closure.

## ⛤ Настоящая цена сироты — НЕ «не сделают», а «НЕ ЗАКРОЮТ»: замер дал 4 из 4 уже починенных

Класс обычно объясняют так: «сирота невидима селектору ⇒ работу никто не возьмёт». Замер
2026-08-19 показывает, что это **не главный** ущерб — и второй тише.

Из 288 Backlog-задач `vault-exodev` без `ems__Effort_parent` оказалась **21**; после отсева
контейнеров (12 — они бесродительские **по замыслу**: `ems__Project` либо имеют детей) и задач,
ведущихся другой осью (5 — `Effort_area`/`plannedStartTimestamp`), истинных сирот-**листьев**
осталось **4**. Все четыре — дефекты движка.

⛔ **И все четыре к моменту замера были УЖЕ ПОЧИНЕНЫ** — каждая своим оракулом:
трёхсторонняя проба `set-property --dry-run` (два подкласс-случая приняты, несуществующее свойство
отвергнуто ⇒ гвард жив, а не снят) · `rollback` принимает `createdPaths` и удаляет их (#3921) ·
комментарий инстанциатора прототипов на `origin/main` прямо называет старую форму «DANGLING» ·
`Class_` убран из `EXO_NON_RELATION_LOCALNAME_PREFIXES`, и в тесте стоит `// Revert-verified`.

⇒ Работа **делается** — через issue, ревью, соседние PR. Не делается только **закрытие записи**:
сирота не попадает ни в очередь, ни в обзоры, ни в сверки, поэтому её никто не перечитывает.
Бэклог годами несёт фантомный вес, и по счёту он неотличим от настоящего.

- ✅ **Floor: сироту сперва ИЗМЕРЬ, а уже потом планируй.** Порядок обратный интуитивному —
  кажется, что сироту надо «взять в работу»; на деле первый шаг дешевле и чаще терминален:
  прогнать её собственный оракул. Четыре из четырёх закрылись без единой строки кода.
- ⚠ **Симптом-tell:** задача-сирота старше месяца и описывает **конкретный** дефект. Конкретность
  и есть причина: такой дефект чинят по другому поводу, а запись остаётся.
- ⛤ **Отделять контейнеры МЕХАНИЧЕСКИ, а не по названию:** «сирота» = нет родителя **И** нет детей
  **И** класс не `ems__Project`. Без этого 12 корневых направлений попадут в список как дефект,
- ⛤ **Та же поправка нужна ЛЮБОМУ детектору «занятости», а не только свипу сирот.**
  Сторож, считающий «сколько тикетов держат слот дольше N часов», по построению видит
  контейнеры: направление в `Doing` — норма, оно работает, пока есть дети. Замер
  2026-08-22 на живой доске: из пяти старейших находок ЧЕТЫРЕ были `ems__Project`,
  старейшей приписали 465ч «удержания слота». После исключения контейнеров: в работе
  29 → 16, застрявших 15 → 8, неизмеримых 13 → 7 — **почти половина находок была ложной**.
  ⚠ Печатать число исключённых РЯДОМ со счётом находок, иначе «стало меньше» неотличимо
  от «детектор ослаб» (`self-satisfying-metric-weak-verifier` §A9).
  и свип начнёт «чинить» здоровое.
- ⛔ **Подцепляя сироту к контейнеру, проверь ПЕРЕСЕЧЕНИЕ МОНТИРОВАНИЙ:** ассет может жить в
