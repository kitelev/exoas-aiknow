# Submodule cross-boundary moves: plain `mv`, never `git mv`

## Принцип

При перемещении файлов **через границу git-submodule** (из суперпроекта в сабмодуль, или из одного сабмодуля в другой) — использовать обычный `mv`, **никогда `git mv`**. `git mv` не понимает границу сабмодуля: он переносит файлы физически И регистрирует их в индексе **суперпроекта** как обычные файлы по пути назначения. Затем последующий `git add <submodule-path>` **удаляет gitlink** и «поглощает» все файлы сабмодуля в суперпроект как regular files. Связь submodule ломается молча.

## Когда правило срабатывает

- Перенос ассетов из vault-root (`assetspaces/tbank-persons/`) в сабмодуль (`assetspaces/kitelev/exoas-draft-ontologies/`).
- Перенос между двумя сабмодулями (cross-submodule co-location repair).
- Любая реорганизация, где источник и назначение лежат в разных git-репозиториях.

НЕ применяется к перемещению **внутри одного** сабмодуля (напр. раскладка по подпапкам `exoas-ems/ems/`) — там `mv`/`git mv` оба ОК, файлы остаются в том же репо.

## Правильный паттерн (cross-boundary)

```bash
# 1. Обычный mv (НЕ git mv) — файл физически уходит в сабмодуль
mv "assetspaces/src-dir/<uid>.md" "assetspaces/kitelev/exoas-dest/"

# 2. В САБМОДУЛЕ: add + commit + push (файл становится untracked там)
git -C assetspaces/kitelev/exoas-dest add -A
git -C assetspaces/kitelev/exoas-dest commit -m "feat: import ..."
git -C assetspaces/kitelev/exoas-dest push origin HEAD

# 3. В СУПЕРПРОЕКТЕ: stage удаления источника + bump указателя
git add "assetspaces/src-dir" assetspaces/kitelev/exoas-dest
# ⛔ ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА перед commit: указатель = ОДНА строка mode 160000
git ls-files --stage assetspaces/kitelev/exoas-dest   # → 160000 <sha> 0  <path>  (1 line)
git commit -m "..." && git push
```

## Anti-pattern (что сломало сессию 2026-06-07)

```bash
# ⛔ WRONG — git mv через границу сабмодуля
git mv assetspaces/tbank-persons/*.md assetspaces/kitelev/exoas-draft-ontologies/
# → файлы зарегистрированы в индексе СУПЕРПРОЕКТА по пути сабмодуля
git add assetspaces/kitelev/exoas-draft-ontologies
# → gitlink (160000) УДАЛЁН, 79 файлов сабмодуля добавлены как regular (100644)
# → commit поглотил сабмодуль; .gitmodules рассинхронизирован; clone сломается
```

## Восстановление если поглощение уже случилось

```bash
# 1. Убрать поглощённые файлы из индекса суперпроекта (НЕ с диска)
git rm -r --cached "assetspaces/kitelev/exoas-dest"
# 2. Re-add как gitlink (сабмодуль на диске цел: .git + .gitmodules entry)
git add "assetspaces/kitelev/exoas-dest"
# 3. VERIFY: одна строка, mode 160000 (warning «embedded git repository» — норм)
git ls-files --stage "assetspaces/kitelev/exoas-dest"
# 4. commit + push
```

## Smell-test перед commit любой submodule-операции

`git diff --cached --name-status` НЕ должен содержать `A` / `D` для файлов **внутри** пути сабмодуля. Изменение сабмодуля = ровно одна `M` (или `A`) строка на путь сабмодуля с mode `160000`. Если видишь `<submodule>/<file>.md` в staged diff суперпроекта — поглощение, откатывай (см. выше).

## Связанные грабли той же сессии

- **Detached-HEAD сабмодуль после `git submodule update --init`.** `git submodule update --init` чекаутит gitlink-коммит в detached HEAD. Тогда `git push origin HEAD` падает (`You must fully qualify the ref... HEAD:refs/heads/HEAD`). Fix: `git push origin HEAD:main` (fast-forward на ветку) затем `git checkout -B main` (переподключить локальную ветку). Проверять: `git -C <sm> rev-parse --abbrev-ref HEAD` == `main`, не `HEAD`.
- **Selective staging на live-synced vault** (⛤ исторически vault-2025 = iPhone Sync; он декоммиссирован 2026-06-27, каноничные vault теперь git-free — читать как принцип, не как рецепт). После удаления `.gitignore` из сабмодулей риск случайного попадания `.DS_Store`/`.obsidian/`/`.exocortex/` в `git add -A` будущих коммитов вырос. Стейджить выборочно (`git add <конкретные пути>`), не `git add -A`/`.` — особенно на vault-root (см. `pre-migration-submodule-stash.md` live-synced exception).

## Addendum 2026-06-10 — plain-dir → submodule conversion: absorption when path has PRE-TRACKED files

Тот же failure mode возникает **не только при `git mv`**, но и при **конвертации существующей populated plain-папки в submodule** (`cd dir && git init && commit && push`, затем в суперпроекте `git add <path>` для gitlink). `git add <path>` создаёт корректный gitlink (mode 160000) **только если под этим путём в индексе суперпроекта НЕТ уже tracked-файлов**. Если хоть один файл по этому пути уже был закоммичен ранее как plain-файл — `git add <path>` добавит остальные файлы как blobs (100644) **вместо** gitlink → поглощение.

**Root cause (эмпирически подтверждён):** в одной партии из 3 конвертаций — `exoas-kitelev-inbox` (1 untracked файл) и `exofs-kitelev-files` (195 untracked) дали чистый gitlink; `exoas-kitelev-private` (59 файлов, из них **4 уже tracked** в HEAD суперпроекта по старому plain-пути) → поглотился как 59 blobs. Pre-tracked файлы под путём — это и есть триггер.

**Pre-check перед `git add <new-submodule-path>`:**
```bash
# Есть ли уже tracked-файлы под этим путём? (любой вывод = absorption-риск)
git ls-files -- "<path>" | head
```
Если непусто → сначала `git rm -r --cached "<path>"` (снять старые plain-файлы с трекинга, на диске остаются — они уже в submodule-репо), **потом** `git add "<path>"` → gitlink.

**Verify (всегда, mandatory):** `git ls-files --stage "<path>"` → ровно ОДНА строка mode `160000`. Если видишь строки `100644` под путём — поглощение, recovery: `git rm -r --cached "<path>"` + re-add (см. секцию выше). Это и был fix в сессии 2026-06-10.
