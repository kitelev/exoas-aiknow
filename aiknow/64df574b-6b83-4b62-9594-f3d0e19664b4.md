## Разборы

## §A1 Addendum 2026-06-20 — gotcha при PR-watch до merge

1. **Push может НЕ создать `github-actions` check-suite (CI не стартует).** Наблюдено: после **локального** `git merge origin/<pr-branch>` (чтобы вобрать server-side update-branch merge) + push новый HEAD получил check-suites только от 3rd-party (`cursor`/`vercel`), а `github-actions` suite **не создался** → required check-runs `0/N` 45 мин, `statusCheckRollup` пуст. ci.yml триггерится на `pull_request: synchronize` без paths-filter → docs-push должен был триггернуть, но не сделал. **Root cause не подтверждён** (Actions-hiccup vs merge-commit-quirk — не доказано, не over-claim'ить). **Детект:** watcher показывает `0/N` дольше ~5-10 мин И `gh api repos/<o>/<r>/commits/<sha>/check-suites` показывает **нет `github-actions` suite** (только 3rd-party) → push не зафайрил CI, НЕ ждать дальше. **Fix:** `update-branch` (server-side merge → новый HEAD → `synchronize` → CI стартует немедленно) ИЛИ empty-commit push. Предпочитать server-side `update-branch`, а не **локальный** `git merge`-commit, который при push может не CI'нуться.

   <!-- Added by /session-retrospective 2026-06-21 — root: al-ux-findings PR #3704, update-branch И empty-commit ОБА не зафайрили CI; close+reopen сработал. -->
   **Recurrence 2026-06-21 (al-ux-findings PR #3704) — update-branch И empty-commit ОБА не зафайрили CI; reliable recovery = close+reopen.** На PR #3704 (UI-copy): `update-branch` merge-commit (9fe77618) → check-suites только cursor/vercel, 0 check-runs ~10 мин. Затем **empty-commit** push (82f35e21, реальный content-change-event) → ТОЖЕ не зафайрил github-actions (~2 мин, canary-проверка: B1-PR #3706 нормальный push в ту же минуту CI зафайрил → Actions работал, проблема специфична для этих pushes). **Сработал `gh pr close <N> && gh pr reopen <N>`** → `pull_request: reopened` event → CI немедленно queued на текущем head. ⚠ update-branch **интермиттентен**: на СЛЕДУЮЩЕМ PR #3706 тот же `update-branch` merge-commit (00d016c5) CI зафайрил чисто (github-actions suites present). **Floor-recovery-ladder когда watcher видит 0/N + нет github-actions suite >5 мин:** (1) убедись Actions вообще жив (canary: любой свежий нормальный push в репо фай­рит CI?); (2) `update-branch` если BEHIND; (3) если не зафайрил за ~2-3 мин → **empty-commit push**; (4) если и это молчит → **`gh pr close N && gh pr reopen N`** (reopened-event — самый надёжный force). Cost инцидента: ~3 recovery-цикла + диагностика; пойман watcher'ом (0/N persisted) + canary.

   <!-- Added by /session-retrospective 2026-07-20 — root: bug-fix-turnkey #3923 merge to main produced ZERO workflow runs → release stranded; no PR-branch lever exists on main. -->
   **Recurrence 2026-07-19/20 (3rd occurrence; НА `main`, НЕ на PR-branch → recovery-ladder выше НЕ применима → добавлен `workflow_dispatch` рычаг).** Squash-merge PR #3923 в `main` (commit `b11f8cb5`): commit приземлился (main HEAD = он), но `commits/<sha>/check-suites` = **0**, ни одного workflow-run (`ci.yml/runs?branch=main select(head_sha==merge)` → пусто). Actions `enabled`+`active`, репо public, githubstatus all-operational, предыдущий push (`7b7820be`) зафайрил CI штатно — то есть **GitHub принял push, но не породил push-event для Actions** (тот же класс, что 2026-06-20/21, но на main). Т.к. `auto-release.yml` достижим ТОЛЬКО через `workflow_run: workflows:["CI"]` → релиз **завис нерелизнутым** (main зелёный, PR merged — ничего не сигналит). ⛤ **Ключевое отличие от PR-веток:** recovery-ladder выше (`update-branch` / close+reopen) на MAIN **не существует** (ветка уже смержена, нет PR). Единственный доступный лечащий ход был **empty-commit в main** (штатный per [[pr-auto-merge-chicken-egg]], не обход гейтов). **Detection-сигнал (быстрее, чем висящий release-watcher на «новый тег»):** для merge-SHA НЕТ ни одного `workflow_run` вообще (`ci.yml/runs?branch=main --jq select(head_sha=="<merge>")` пусто) — отличать от `auto-release`=`skipped` (это уже задокументированный [[auto-release-gated-on-ci-workflow-conclusion]] non-required-fail failure-mode; здесь run не создался ВООБЩЕ). **Постоянный рычаг (issue #3925, PR #3927):** добавлен `workflow_dispatch:` в `ci.yml` → застрявший main-commit ре-триггерится `gh workflow run ci.yml --ref main`. ⛤ **Gotcha при добавлении dispatch-триггера:** `dorny/paths-filter` на dispatch не имеет базы для диффа → фильтр надо `if: github.event_name != 'workflow_dispatch'` пропустить и форсить `detect-changes.outputs.code='true'`, иначе dispatch прогонит docs-only-подмножество (e2e скипнуты) и выпустит релиз с ЧАСТИЧНОГО прогона. Cost: ~10 диагностических gh-api + 1 issue + 1 fix-PR (сам его merge стал свежим push-event → CI зафайрил 4 runs → v16.187.2 вышла).

2. **`tail`-пайп фонового status-watcher'а маскирует его exit-code.** `run_in_background` `./watch.sh ... | tail -40` → task-notification отрапортовал **exit 0**, хотя скрипт `exit 124` (TIMEOUT) — exit пайпа = exit `tail` (0). Чуть не принял «exit 0» за «CI green». **Root confirmed/reproducible** (pipe exit = last cmd). **Fix:** для watcher'а, чей exit НЕСЁТ смысл (GREEN/FAIL/TIMEOUT) — НЕ пайпить через `tail`/`head`; либо запускать bare (exit пробросится в notification), либо писать вердикт в файл (`echo GREEN/FAIL/TIMEOUT > /tmp/verdict.txt`) и читать файл независимо от reported-exit. Cross-tie [[event-driven-coordination]], aiKnow `[[a8033d3e-2cc6-430b-ac2a-bb779d8f3ed7]]`.

3. **`case`/`grep`-матчинг по jq-compact JSON со СВ-пробелом даёт ложный TIMEOUT.** _(Added by /session-retrospective 2026-06-20 — root: release-watcher child `al-sparql-rm` PR #3649.)_ Фоновый Auto-Release-watcher детектил успех `case "$RUN" in *'"cc": "success"'*)` — с пробелом после двоеточия (как `jq -j`/pretty-print). Но строка строилась `jq '{cc:.conclusion}'` → **compact**-вывод `{"cc":"success"}` БЕЗ пробела → паттерн НЕ сматчил → watcher отработал все 40 итераций до `exit 124` (TIMEOUT), хотя релиз (v16.124.1) **успешно вышел** на 2-й минуте. Поймано прямой проверкой `gh api .../auto-release.yml/runs` (run head=merge-SHA = completed/success) → false-TIMEOUT, урон 0 (релиз верифицирован напрямую). **Root confirmed** (jq compact не вставляет пробел после `:`; bash `case`-glob с пробелом не матчит). **Fix:** НЕ матчить строкой по compact-JSON. Либо (a) `jq -e 'select(.conclusion=="success")'` и проверять **exit-код** jq (0=match), либо (b) `CC=$(... --jq '.conclusion'); [ "$CC" = "success" ]` (сравнение голого значения, без скобок/пробелов/кавычек compact-объекта), либо (c) предпочесть `gh run watch <id> --exit-status` (нативный, не парсинг). Тот же класс «watcher-script парсит не тот формат», что [[bash-loop-eval-pitfalls]] Грабля 3b ($PIPESTATUS) — bash/jq формат-предположение ломает детекцию.

4. **`skipped`/`neutral` required-чек = SATISFIED, считать его «done-and-passing» в settle-условии (иначе docs-only PR никогда не «settle»).** _(Added by /session-retrospective 2026-06-20 — root: child `al-onboard-gap` docs-only PR #3651.)_ Settle-условие выше (`DONE==len(req)`, где `DONE` считает только `c=="success"`) **никогда не сойдётся** на docs-only PR: `detect-changes` пропускает code-jobs → `test-component` приходит `status=completed, conclusion=skipped` (НЕ `success`), `mergeStateStatus=UNSTABLE` (не CLEAN). GitHub branch-protection трактует `skipped` required-чек как **удовлетворённый** (merge разрешён, `mergeable=MERGEABLE`). Watcher на строгом `DONE==len(req)` мис-репортит: либо timeout (если ждёт 13/13 success — не дождётся), либо ложный GREEN (если зевает условие). **Fix для settle-предиката:** считать required-чек завершённым-и-проходным, если `status=="completed"` И `conclusion ∈ {success, skipped, neutral}`; FAIL-set = `conclusion ∈ {failure, timed_out, cancelled, action_required, startup_failure}`. Settle ⇔ FAIL пуст И каждый required-чек `completed` с conclusion НЕ из FAIL-set. **Authoritative-арбитр перед merge — `mergeStateStatus` + `mergeable`** (UNSTABLE+MERGEABLE = mergeable; BLOCKED = реально не готово), не счётчик `DONE`. Эмпирика: watcher вышел «GREEN» на `DONE=12/13|NOTDONE=0` (12 success + test-component skipped) — авторитетная per-check проверка подтвердила 12 success + 1 skipped + 0 fail + `mergeable=MERGEABLE` → merge корректен; урон 0 (per-check backstop поймал).

5. **Back-to-back merge двух PR в одно окно → Auto-Release concurrency cancel'ит run первого PR; release-watcher, ключованный по merge-SHA ПЕРВОГО PR, ловит false-TIMEOUT (хотя релиз вышел).** _(Added by /session-retrospective 2026-06-20 — root: child `al-polish-ship` PR #3663 plugin + #3664 docs смержены 4 сек врозь.)_ Смержил PR1 (plugin, merge-commit `94e4ce22`) → PR2 (docs, `e05d8295`) за 4 секунды. Auto-Release триггерится на push-to-main с **concurrency-group**, который **cancel'ит in-progress run** при новом push → run для `94e4ce22` отменён/superseded, реально выполнился и опубликовал релиз (v16.130.1) run, ключёванный по `e05d8295` (последний HEAD main). Мой release-watcher ключевался по `94e4ce22` (merge-SHA plugin-PR) → ни одного `auto-release` run с этим head_sha → **40 итераций → false RELEASE_TIMEOUT**, хотя v16.130.1 уже вышел. **Урон 0** — поймано прямой проверкой: `gh release view <tag> --json body` показал ссылки на ОБА PR (#3663+#3664), bundle-grep подтвердил мой код. **Root confirmed** (concurrency cancel + watcher ключ на «не тот» merge-SHA). **Fix:** при merge >1 PR в одно окно — release-watcher ключевать по **текущему `origin/main` HEAD ПОСЛЕ всех merge** (`git fetch origin main && git rev-parse origin/main`), не по merge-SHA конкретного PR; ⛤ authoritative-верификация релиза = **release body содержит твой PR#** (`gh release view <latest-tag> --json body | grep <PR#>`) + bundle-grep символа (per [[obsidian-plugin-update-via-brat]] «verify BUNDLE CONTENT»), а НЕ совпадение run.head_sha. Релиз строится из main HEAD (⊇ все смерженные коммиты) → твой код в нём, даже если run ключёван по чужому/позднему SHA. Тот же класс «watcher сматчил не тот объект», что addendum #3 (формат) и `obsidian-plugin-update-via-brat` (head_sha merge-коммита).

6. **Gate-aggregator чек (`test-coverage`) лагает на `status=in_progress` ПРИ уже-проставленном `conclusion=success` → settle-предикат на `status=="completed"` даёт ложный TIMEOUT.** _(Added by /session-retrospective 2026-06-27 — root: child `al-alias-exocmd` PR #3735.)_ `test-coverage` — downstream gate-aggregator (см. [[perf-tests-dont-hard-gate-ci]] «test-coverage = gate-aggregator»). Наблюдено: все его upstream-шарды (`test-coverage-shard (1..6)` + `test-coverage-exocortex` + `test-coverage-cli`) = `completed/success`, но сам `test-coverage` check-run застрял на **`in_progress`** с уже-проставленным **`conclusion=success`** (внутренне противоречивое, но реальное состояние GitHub API — status-флаг лагает за conclusion). Watcher считал `notdone = [n for n in req if by[n]["s"] != "completed"]` → `test-coverage` вечно в notdone → **80 итераций → false TIMEOUT** (13/14 done, `notdone=test-coverage`), хотя PR был готов. **Урон 0** — авторитетный арбитр **`mergeStateStatus=CLEAN` + `mergeable=MERGEABLE`** (сразу) опроверг TIMEOUT, и прямой per-required-check API показал все 14 с `conclusion ∈ PASS_C` (`test-coverage` = `in_progress/success`). **Root confirmed** (aggregator status-lag). **Fix settle-предиката:** считать required-чек «settled-and-passing», если **`conclusion ∈ {success,skipped,neutral}`** — НЕ требовать `status=="completed"` (аггрегатор может лагать со status, имея финальный conclusion). Т.е. `notdone = [n for n in req if n not in by OR by[n]["c"] not in PASS_C]` (ключ на conclusion, не на status). И ⛤ перед merge всегда сверяться с `mergeStateStatus` (CLEAN / UNSTABLE+MERGEABLE = mergeable; BLOCKED = реально не готово) — он авторитетнее любого снимка check-runs. Тот же класс «watcher переусложнил settle-условие», что addendum #4 (skipped-чек) — оба про «conclusion важнее строгого status=completed».

7. **Shell-loop watcher: python settle-предикат БЕЗ явного `sys.exit(<nonzero>)` для pending-кейса → `rc=$?`=0 → ложный «SETTLED GREEN» на 1-й итерации.** _(Added by /session-retrospective 2026-06-27 — root: child `claude-issue-3705-onboarding` PR #3755.)_ Watcher-цикл `python3 - <<PY ... PY; rc=$?` решал «settled» по exit-коду python-блока. Python писал verdict + `sys.exit(0)` для GREEN, `sys.exit(3)` для FAIL, но для **pending** (notdone непуст, fail пуст) **просто доходил до конца блока** → python завершался **exit 0 по умолчанию** → shell читал `rc=0` → ветка `[ $rc -eq 0 ] && SETTLED GREEN` сработала на **1-й итерации** при `DONE=5/14` (NOTDONE непуст!). Verdict-файл при этом НЕ создавался (пишется только в GREEN/FAIL-ветках) → его отсутствие — сигнал ложного срабатывания. **Урон 0** — пойман немедленно: арбитр `mergeStateStatus=BLOCKED` + лог `DONE=5/14 NOTDONE=[...]` противоречили «GREEN», verdict-файл отсутствовал → переписал watcher с `sys.exit(1)` в конце pending-кейса (settle сошёлся корректно на 14/14 CLEAN). **Fix:** в любом shell-loop-watcher, где терминальность определяется exit-кодом инлайн-python/script-блока, **pending-кейс ОБЯЗАН явно `sys.exit(<nonzero, отличный от FAIL-кода>)`** (`sys.exit(1)` = «ещё бежит», `sys.exit(3)` = FAIL, `sys.exit(0)` ТОЛЬКО для GREEN). Бездействие = exit 0 = ложный happy-path. ⛤ Доп. guard: писать verdict-файл в КАЖДОМ терминальном исходе + проверять его наличие перед тем как верить «SETTLED» (отсутствие verdict при rc=0 = баг логики, не настоящий settle). Корень — не check-runs-формат (addendum #3-#6), а **shell↔script exit-code-контракт** (sibling [[bash-loop-eval-pitfalls]] Грабли про `$?`/`$PIPESTATUS`).

8. **Deploy/publish-watcher (Pages, npm publish, release-asset): поллить ARTIFACT-URL вместо conclusion workflow-run'а → провал деплоя виден только по таймауту поллера (×5-7 медленнее).** _(Added by /session-retrospective 2026-07-03 — root: сессия targetPrototype chain-walk, публикация proposed-req на Living-Docs Pages.)_ После merge pointer-bump PR заармил поллер на `curl <pages-url>` (404→200) с единственным negative-исходом «40 итераций → TIMEOUT» (20 мин). Реально `living-docs` deploy-job упал через ~3 мин **транзиентной ошибкой GitHub Pages** («Deployment failed, try again later», 10 внутренних ретраев) — URL-поллер это в принципе не видит, узнал бы через 20 мин. User поймал раньше таймаута («Ты слишком долго ждал поллер»). **Fix:** для ЛЮБОГО deploy/publish-ожидания primary-сигнал = **conclusion workflow-run'а** (`gh api .../actions/workflows/<w>/runs` для merge-SHA) с **fail-fast exit на `failure`**; artifact-URL — только ФИНАЛЬНОЕ подтверждение ПОСЛЕ `completed/success` (URL может лагать за run на ~минуту CDN). Recovery транзиентного Pages-провала: `gh run rerun <id> --failed` (1-2 раза), затем `workflow_dispatch` свежего run. Тот же класс, что тело правила (симптом vs authoritative источник) — но для deploy-объекта, не PR-чеков.

9. **Python watcher: `gh api --jq '[...]'` может транзиентно вернуть НЕ-dict элемент → `by[r["n"]]` крэшит `TypeError: string indices must be integers` (весь watcher exit 1 на 2-й итерации).** _(Added by /session-retrospective 2026-07-04 — root: child `datetz-low` CI-watcher #3817.)_ Питон-поллер строил `by = {r["n"]: r for r in runs}` где `runs = json.loads(gh([...,"--jq","[.check_runs[]|{n:.name,...}]"]) or "[]")`. На 2-й итерации `gh api` вернул транзиентно неожиданную форму (пустой/частичный вывод, или jq выдал строковый элемент) → `r` оказался строкой → `r["n"]` = `TypeError` → **весь watcher упал exit 1** (не GREEN/FAIL/TIMEOUT — просто крэш, verdict-файл пуст). **Fix:** guard каждый jq-parsed элемент перед subscript'ом: `for r in runs: if isinstance(r, dict) and "n" in r: by[r["n"]] = r`. Тот же принцип и для release-watcher (`workflow_runs`-массивы). Транзиентный gh-вывод — норма при поллинге; watcher обязан пережить одну «мусорную» итерацию, а не падать. Cost: 1 крэшнутый watcher + рестарт (self-caught по task-notification `failed exit 1` + traceback в логе); урон 0. Sibling addendum #7 (shell↔script exit-code) — оба про «watcher падает/врёт из-за неучтённого edge-состояния», здесь — python-parse робастность.

10. **Фоновый (`run_in_background:true`) python-watcher с `subprocess.run(["gh",...])` может ПЕРСИСТЕНТНО отдавать 0/N (пустой `runs`), пока CI реально settled минуты назад — root cause НЕ подтверждён.** _(Added by /session-retrospective 2026-07-30 — root: orch-d7f89d46 PR #4003.)_ Watcher структурно корректен (check-runs ∩ required-set, conclusion-keyed, per addenda #4/#6 выше — `PASS={success,skipped,neutral}`), тем не менее **17 итераций подряд (~8.5 мин)** печатал `DONE=0/14 NOTDONE=[все 14]`, хотя прямой `gh api commits/<sha>/check-runs` (тот же вызов, foreground) в ЭТОТ момент показал **все 32 check-run (incl. все 14 required) = `completed/success`**, часть завершилась ещё за ~4 мин до начала наблюдаемого стейлинга. **Root cause НЕ подтверждён** — пробовал дёшево воспроизвести (`subprocess.run(["gh","auth","status"])` foreground: auth ОК), но не смог cheaply воспроизвести именно внутри `run_in_background`-контекста; **гипотеза** — `gh`-подпроцесс внутри background-Bash теряет auth/PATH silently, и watcher'ский `gh()`-хелпер (`return "" on exception` + `jq(out or "[]", [])`) молча схлопывает ЛЮБОЙ nonzero-exit/empty-stdout в дефолтный пустой список, БЕЗ различения «CI ещё не settled» от «gh-вызов упал». **Fix (защитный, не устраняющий гипотетический root cause):** `gh()`-хелпер watcher-скрипта обязан **логировать returncode+stderr** каждого вызова (не молча сворачивать в `""`), чтобы отличить «0 check-runs потому что gh упал» от «0 check-runs потому что CI ещё не создал их» — такой лог сразу вскрыл бы silent-fail на итерации [0], а не после [16]. **Floor подтверждён ровно как задумано правилом:** watcher's false report НЕ привёл к ошибочному merge/выводу — прямая foreground-проверка (`gh api` тем же паттерном) ПЕРЕД merge вскрыла реальное состояние за 1 вызов; merge прошёл на верных данных. Cost: ~8.5 мин напрасного background-поллинга + 1 отдельный direct-check tool call; урон 0 (self-caught, per правило «never trust a watcher blindly»).

## §A2 ⛤ Addendum 2026-08-03 — ТРАНЗИЕНТНЫЙ отказ инфраструктуры: дискриминатор — СОСЕДНИЕ прогоны в том же окне, а не пост-фактум достижимость и не страница статуса
<!-- Added by /session-retrospective 2026-08-03 — root: PR #4023, дважды упал Checkout сабмодуля (503); мой диагноз «сторона GitHub» опровергнут кросс-чеком оркестратора. -->

Аддендумы выше — про то, как **читать** вердикт CI. Отдельный вопрос: как **атрибутировать** падение, не относящееся к коду (шаг `Checkout` упал сетевой ошибкой — 503, таймаут клона сабмодуля). Рефлекс даёт две гипотезы, «это я сломал» и «GitHub лежит», и обе проверяются не тем.

- ⛔ **Пост-фактум достижимость НЕ доказательство.** «Пин сабмодуля жив, коммит на месте, страница статуса зелёная» отвечает на вопрос «сломано ли СЕЙЧАС», тогда как отказ был **в окне прогона**. При реальном узком рассинхроне реплик обе проверки проходят — и подтверждают ложную гипотезу «глобальный отказ».
- ⛤ **Дискриминатор — СОСЕДНИЕ прогоны с тем же пином в ТОМ ЖЕ окне.** Прошёл ли `main` или чужой PR свой CI за минуты до/после падения, с тем же SHA сабмодуля? Да ⇒ глобального отказа не было; окно узкое и обычно прилегает к **твоему** недавнему push в этот сабмодуль (репликация не догнала). Нет ни одного ⇒ отказ широкий, и только тогда уместна гипотеза о стороне GitHub.
  ```bash
  gh api "repos/<o>/<r>/actions/workflows/ci.yml/runs?branch=main&per_page=5" \
    --jq '.workflow_runs[] | "\(.created_at) \(.conclusion) \(.head_sha[0:8])"'
  ```
- ⚠ **Приём УЖЕ есть в корпусе — но под другими failure-mode**, и потому не вспоминается при сетевом падении: [[unpinned-ci-tool-version-drift]] §Диагностический ключ («тот же base-commit проходит в другом прогоне?») и Addendum #1 выше (canary: фай`рит ли CI любой свежий нормальный push). Здесь — обобщение: **любой отказ инфраструктуры атрибутируется сравнением с соседями по времени, а не проверкой состояния постфактум.**
- **Практика:** третье падение того же шага **спустя** окно убивает гипотезу узкого рассинхрона → эскалировать в сторону «что специфично для этого прогона», а не «GitHub лежит».
- **Empirical 2026-08-03 (PR #4023):** два падения `Checkout` сабмодуля (`exoas-exocmd`, 503) в разных волнах. Собственную причастность я исключил корректно (пин — предок main, ahead=17 / behind=0) и на этом заключил «сторона GitHub». Кросс-чек оркестратора: `main` прошёл CI **через 13 минут после** моего push в тот сабмодуль, соседний PR — за 5 минут до, пины идентичны и достижимы ⇒ окно узкое и прилегает к моему push (мой прогон стартовал через минуту после него). Мой набор проверок был **слишком грубым**; недостающий шаг — ровно соседние прогоны. Ретраи прошли, CI 14/14, третьего падения не было — гипотеза подтвердилась.

## §A3 ⛔ Addendum 2026-08-04 — CONFLICTING PR даёт НОЛЬ check-runs: `pull_request`-воркфлоу гоняются против `refs/pull/N/merge`, которого у конфликтующего PR НЕ СУЩЕСТВУЕТ
<!-- Added by /session-retrospective 2026-08-04 — root: PR #4026, watcher 80 итераций на DONE=0/14 при FAIL=[]; корень — origin/main уехал на 1 коммит, PR стал CONFLICTING. -->

Addendum #1 (§выше) разбирает «push не создал `github-actions` check-suite» — там суита **не создалась**, но PR **mergeable**. Здесь другой корень с идентичным симптомом на приборах: **PR конфликтует с базой**, и потому `pull_request`-воркфлоу физически не на чем запустить — они гоняются против **merge-ref** `refs/pull/<N>/merge`, а GitHub вычисляет его только для PR без конфликтов. Ноль check-runs, ноль check-suites, никакой ошибки.

- ⛤ **Tell, отличающий от Addendum #1 за один взгляд:** watcher показывает `DONE=0/N` при **`FAIL=[]`** и **пустом** `commits/<sha>/check-runs` (не «часть чеков есть, часть pending»), а `gh pr view <N> --json mergeable,mergeStateStatus` даёт **`CONFLICTING` / `DIRTY`**. У Addendum #1 `mergeable` при этом **`MERGEABLE`**, и лечится он `update-branch`/empty-commit/close+reopen — здесь они **бесполезны**.
- ✅ **Лечение — разрешить конфликт** (`git fetch origin main && git merge origin/main` в ветке, зафиксировать резолв, push). Merge-ref становится вычислимым → воркфлоу стартуют сами, без пинков.
- ⛔ **Не долбить `gh run rerun` / `update-branch`** — перезапускать нечего, а `update-branch` на конфликтующем PR не поможет (он делает fast-forward-merge базы, который как раз и конфликтует).
- ⚠ **Особо коварно для долгого PR:** конфликт возникает **после** зелёного прогона, когда сосед мержит в `main`. Watcher, заармленный на «дождись зелёного», не различает «ещё не стартовало» и «уже не стартует никогда» — он честно крутится до таймаута. Поэтому watcher, простоявший на `DONE=0/N` дольше ~5 минут, обязан **сам** сходить за `mergeable` ([[verify-before-assert]]: «CI ещё не стартовал» = гипотеза, а не факт).

## §A4 ⛔ Addendum 2026-08-06 — у отказа инфраструктуры есть САМОИДЕНТИФИЦИРУЮЩАЯ подпись в логе; и `conclusion` её НЕ несёт: «cancelled = инфра, failure = моё» — ЛОЖНЫЙ дискриминатор

Аддендум 2026-08-03 (выше) даёт дискриминатор **сравнением с соседями по времени** и справедливо отбрасывает страницу статуса. Наблюдение 2026-08-06 уточняет обе половины и добавляет сигнал, который вообще не требует сравнения.

1. ⛔ **`conclusion` джоба не различает инфру и код.** Рефлекс «`cancelled` — это инфра, `failure` — это я» кажется естественным и неверен: в одном прогоне `test-ui`, `test-coverage-exocortex` и `NPM Security Audit` пришли как **`failure`**, при этом **ни один тест не исполнялся** — раннер не смог скачать composite-actions. Отсортировав по `conclusion` и взявшись «за настоящие failure», уйдёшь чинить свой диff по трём сьютам, зелёным локально.
2. ⛤ **Самоидентифицирующая подпись — В ЛОГЕ, и она сильнее любого кросс-прогонного сравнения:** `Failed to resolve action download info. Error: Service Unavailable | Internal Server Error | Bad Gateway`. Плюс структурный близнец: `.steps` джоба содержит **только `Set up job`** со статусом `cancelled` — смерть наступила **до первого шага**, значит диff не мог быть причиной **по построению**. Ни соседей, ни истории для этого вывода не нужно.
   ```bash
   jid=$(gh api "repos/<o>/<r>/actions/runs/<run>/jobs?per_page=60" --jq '.jobs[]|select(.name=="<job>")|.id')
   gh api "repos/<o>/<r>/actions/jobs/$jid/logs" | grep -E "Failed to resolve action|Service Unavailable|Bad Gateway" | head
   gh api "repos/<o>/<r>/actions/jobs/$jid" --jq '[.steps[]|{name,conclusion}]'   # только «Set up job» ⇒ шагов не было
   ```
3. ⛤ **Страница статуса бесполезна как ОТРИЦАНИЕ и ценна как УТВЕРЖДЕНИЕ — различает `created_at`.** «Зелено сейчас» действительно ничего не говорит о прошедшем окне (аддендум 2026-08-03 прав). Но **открытый** инцидент, чей `created_at` **предшествует** `created_at` прогона, — прямое положительное свидетельство, и стоит один запрос:
   ```bash
   curl -s https://www.githubstatus.com/api/v2/summary.json | python3 -c "
   import json,sys; d=json.load(sys.stdin)
   print([c['status'] for c in d['components'] if c['name']=='Actions'])
   [print(i['name'],i['status'],i['created_at']) for i in d.get('incidents',[])]"
   ```
4. ⚠ **Проверять НАДО и тот отказ, у которого есть правдоподобное «своё» объяснение.** `NPM Security Audit` был `success` на предыдущем head и `failure` на текущем — идеальная форма для известного класса «опубликовалась новая advisory» ([[auto-release-gated-on-ci-workflow-conclusion]] §2026-07-21). В логе — та же outage-подпись и ноль `GHSA`. Совпадение «стало красным ровно на моём head» тут не значит ничего: во время аварии краснеет всё, что запустилось.
5. ⛔ **Не ретраить в открытое окно.** Отказ детерминированный, `rerun` упрётся в тот же неразрешимый action-download и сожжёт минуты ([[gh-retry-limit]]). Поллить **статус компонента**, а не свой прогон, и запускать rerun по `operational`.
6. ⚠ **Авария может ЭСКАЛИРОВАТЬ, а не рассосаться** — планируя ожидание, не закладывать «минуты». Наблюдалось `partial_outage` → **`major_outage`** через ~1.5 ч после открытия инцидента, с формулировкой «queued jobs may time out».

Прогон 1 — 5 джобов `cancelled` + `test-coverage` (гейт-агрегатор) `failure` «потому что upstream != success»; прогон 2 — 9 `cancelled` + 3 `failure`.
