# Гомоиконичный конфиг ВНЕШНЕГО движка: vault-ассеты + fresh-read + defensive-load + generic-write
## Принцип

Когда у Exocortex-vault есть **внешний движок** (launchd/cron python, n8n, любой скрипт вне плагина/CLI), чья user-configurable семантика захардкожена в коде — расписание, вопросы, шкалы, эмодзи, тексты, пороги — переноси эту семантику в **vault-ассеты** (Homoiconicity Invariant Q1=да). Это отдельный класс homoiconic-задач от «плагин/CLI читает свой конфиг»: тут потребитель — **сторонний процесс**, а не сам продукт. Рецепт ниже отработан на ADHD-чек-ин-боте (3 класса `checkin__CheckinConfig/Dimension/Option`).

## Ключевые решения рецепта (проверены советом + build'ом)

1. **MOUNTED assetspace, не cold.** Если конфиг надо **править в Obsidian** (в т.ч. на iPhone) — создавай ассетспейс по рецепту `exocortex-cold-archive-assetspace` (repo + anchor 2-step self-ref + registry-дескриптор), НО **добавь UID дескриптора в `exo__Profile_includes` нужного профиля** (`$$kitelev-my` = `49bd4414`). Cold-вариант (observations) в профиль НЕ добавляют — вот и вся разница.
2. **Движок читает конфиг ПРЯМЫМ stdlib frontmatter-парсом, НЕ SPARQL.** Причины (verify-before-assert): npx cold-start ~2-4с/тик неприемлем для непрерывного демона и излишен для мелкого owned-конфига; npx хрупок под launchd minimal-PATH; конфиг — единственный потребитель = сам движок (нет divergence-риска с плагином). Парсер покрывает ровно используемые формы (single-line scalar, ``uid` (label)`, простые YAML-списки); **block-scalar избегается** — многострочная проза (текст сообщения) живёт в **ТЕЛЕ** ассета, не во frontmatter (тело не в triple-store, но его читает только движок).
3. **FRESH-READ каждый вызов, НЕ mtime-кэш.** mtime-кэш = staleness-ловушка (Obsidian atomic-save `rename()`, clock-skew sync) → «бот молчит 3 дня / спамит в 3 ночи» (council Contrarian). Свежий процесс на тик (send/batch) читает заново → «правка в Obsidian → следующий тик без перезапуска» получается **бесплатно** (нет кэша = нет staleness). Долгоживущий демон (poll) читает конфиг заново на каждое событие (события редки). ~34 мелких файла парсятся <10мс. **atomic-read** (retry на ENOENT/пустой — файл мог быть в середине rename).
4. **Defensive-load: last-known-good + fail-loud.** `load_config()` → `(cfg, warning)`. Чистая загрузка → persist snapshot (`config_cache.json`). Битый конфиг → fallback на snapshot (демон жив на последнем рабочем) + движок шлёт alert «⚠️ конфиг сломан». Нет snapshot → raise. **Никогда мусор, никогда навечно-молчание.**
   - ⛔ **Тестовое следствие, обратное этой добродетели: «конфига нет» НЕЛЬЗЯ воспроизвести опустошением каталога конфига.** Снимок лежит ВНЕ него (`~/.adhd-checkin/config_cache.json`) и есть на любой машине, где чек-ин когда-либо работал ⇒ `load_config()` вернёт **последний рабочий вопросник**, а тест «бот без конфига молчит» пройдёт, **отправив живому человеку настоящий чек-ин**. Подменять надо **границу зависимости** (модуль `checkin_lib`, который бросает), а не содержимое каталога. Плюс `CHECKIN_DIR` — константа времени импорта, поэтому фикстурный env перебивается кэшем модуля: выкидывать из `sys.modules` **и** `checkin_lib`, не только свой модуль. _(Empirical 2026-08-03, ось graceful-degradation задачи `4204cc4b`: первая версия оси «проходила» ровно так. Класс — `graph-record-outlives-its-referent` §Addendum «сохранённая копия отвечает за момент своей записи».)_
5. **Generic-write через `_targetProperty` + `_targetClass`.** Движок пишет `<targetProperty_label>=<value>` в инстанс `_targetClass` — НЕ хардкод имён свойств. Следствие: **добавить новую ось = создать Dimension-ассет + её property-ассет** (обе правки в vault, 0 кода); движок пишет generic; SHACL требует, чтобы property была задекларирована (RDF-гигиена, не facade — council First-Principles catch «моделируем форму, не субстрат» закрывается именно `_targetClass`).
6. **Секрет НЕ в vault.** Токены/пароли/chat_id остаются в локальном `config.json` (600) — это инфраструктура, не user-semantics (Homoiconicity Q3).

## Verify-цепочка (перед «Готово»)

- **Byte-equivalence:** новый config-driven build == старый хардкод (собери оба, `==`).
- **Revert-verify VALUE-assert** (не non-empty): на `/tmp`-фикстуре (`CHECKIN_CONFIG_DIR` env override — НЕ мутируй живой конфиг) испорти label ОДНОЙ опции → эта строка **отсутствует** в собранном сообщении (RED); восстанови → присутствует (GREEN).
- **Defensive-path тест:** битый конфиг+snapshot → fallback+warning; битый+нет snapshot → raise.
- **Real-data e2e:** прогони реальный batch на настоящих ответах → инстанс с верными свойствами.
- **Homoiconic-proba:** правь ассет → FRESH процесс (= launchd-тик) отражает без рестарта демона.
- **SHACL floor:** bulk-python обходит хуки → `rm cache` + `validate --shapes-mode` = no-regress (`shacl-validate-clear-cache`, `vault-asset-creation`).
- **Cutover демонов:** свежепроцессные (send/batch) подхватывают новый код сами; **долгоживущий (poll) — рестарт последним** (`launchctl kickstart -k`), verify PID стабилен (не crash-loop на новом import). Порядок: batch → send → poll (council Executor).
  <!-- Added by /session-retrospective 2026-08-27 (vteam-5c888d98, StageStandards) — root: совет `kickstart -k` был безусловным, а он перечитывает КОД, но не ОПИСАНИЕ джоба. -->
  - ⛔ **`kickstart -k` верен для смены КОДА и НЕДОСТАТОЧЕН для смены `EnvironmentVariables`.** Он «kill the running instance before restarting» (man), то есть перезапускает **процесс**; описание джоба launchd держит с момента загрузки ⇒ новый `PATH`/env до процесса **не доедет**, и фикс останется мёртвым **молча**. Смена env ⇒ `launchctl bootout gui/$(id -u)/<label>` + `bootstrap`.
  - ✅ **Вердикт — по секции `environment` живого джоба, а не по plist на диске:** `launchctl print gui/$(id -u)/<label>`. ⚠ PATH там печатается **дважды** — `default environment` (узкий дефолт launchd) и `environment` (объявленное джобом); наивный `grep PATH` отдаёт первую, и она читается как «фикс не доехал» (`harness-invocation-surface` §Обобщение).

## Моделирование (onto-RFC)

- 3 класса: **Config** (синглтон, superclass exo__Asset) → **Dimension** (ось) → **Option** (кнопка). Прецедент: `exo__Layout`→`exo__LayoutBlock`.
- **UWI child→parent + явный `_order` int**, НЕ forward-массив (`_dimensions`/`_options`). Forward-массив нарушает UWI И теряет SPARQL-orderability (RDF set-семантика роняет порядок YAML-массива). `_order` = queryable (как `ems__*_order`).
- Option-as-class оправдан **аналитикой** (`Option_value` ⋈ observations → «какая ось даёт сигнал»), НЕ read-path (движок парсит frontmatter). Council value-tension — решён в пользу консистентности+аналитики.
- **Отложить (YAGNI/quarantine за реальным триггером):** пресеты (`_name`/`_activeConfig`), feature-flag targeting (`_matchDay`/`_matchHours`), A/B (`_experimentGroup`). Задел есть (Config=questionnaire), НЕ строить без 2-го потребителя.

## ⛔ ДЕФОЛТ на ОБЩИЙ ресурс переживает разделение этого ресурса — и превращается в тихую потерю

Env-переменная, задающая **куда движок пишет** (vault, каталог, репо, очередь), почти всегда рождается с «разумным дефолтом» на общий ресурс. Потом ресурс **разделяют** — по боту, по пользователю, по устройству, — все живые потребители получают явное значение в своих plist, и дефолт остаётся указывать на **осиротевший** объект: формально существующий, фактически ничей.

- ⛔ **Отказ тише обычного: писать продолжает работать.** Файлы создаются, ошибок нет, `rc=0`. Не работает только то, чего у осиротевшего ресурса больше нет — **владелец**: никто его не синкает, не мониторит и в него не смотрит. Замер 2026-08-16: 17 записей журнала висели непушнутыми **300 часов**; нашёл их монитор, расширенный по другому поводу, а не отсутствие данных.
- ⚠ **Симптом-tell при ревизии:** ресурс, на который указывает дефолт, **не назван явно ни в одном** живом конфиге. Проверяется одной командой — перечислить значение переменной у всех джобов:
  ```bash
  for p in ~/Library/LaunchAgents/com.kitelev.*poll*.plist; do
    printf '%-45s ' "$(basename "$p" .plist)"
    grep -A1 '<КЛЮЧ>' "$p" | grep string | sed 's/.*<string>//;s|</string>||' || echo '⛔ НЕ ЗАДАН → дефолт'
  done
  ```
  Дефолт не выбран **никем** ⇒ он не «запасной вариант», а ловушка для следующего потребителя.
- ✅ **Floor: после разделения ресурса дефолт УБИРАЕТСЯ, а не перенацеливается.** Отказ ранний и громкий (`raise` при импорте с внятным текстом): имя ресурса — единственное, что отличает потоки друг от друга, и молчаливая подстановка делает их слияние невидимым. Перенацеливание на «живой» ресурс лишь меняет адресата тихой ошибки: чужой журнал уедет не в свой поток.
- ⛤ **Blast-radius проверяется ПЕРЕД ужесточением, и обычно он узкий:** `grep -rn 'import <модуль>'` даёт список импортёров (у меня — ровно один, при пяти ботах: движок общий, различает env). Тогда ранний `raise` безопасен. Проверять надо **исполнением с реальным окружением** — прочитать env каждого джоба из его plist и прогнать импорт с ним, а не выдуманным (`harness-invocation-surface`); ось обязана падать, если джобов на входе ноль, иначе «все прошли» неотличимо от «проверять было нечего».

## ⛔ ЗАИМСТВОВАННЫЙ секрет: выбирать источник ПО СВЕЖЕСТИ, а не по имени backend'а — иначе его переезд даёт ВЕЧНЫЙ отказ

Движок бота не владеет OAuth-токеном — он **зеркалит чужой**, принадлежащий интерактивной сессии. Значит место хранения токена — **чужое архитектурное решение**, и оно меняется без предупреждения: Claude Code до ~2.1 держал ротируемый токен в Keychain-item `Claude Code-credentials`, с 2.1.222 ротирует в **файл** `~/.claude/.credentials.json`, а Keychain-запись просто перестаёт обновляться (замер 2026-08-12: `mdat` записи 08-11 07:30, токен в ней истёк 08-11 15:30; файл в тот же день держал токен до 21:34).

- ⛔ **Отказ ВЕЧНЫЙ, а не «до следующего логина», и это его главное свойство.** Зеркалящий читает старый backend, исправно копирует протухший токен и отказывается от хода — то есть ведёт себя ровно как при разлогине. Совет пользователю («открой Claude Code на маке») **не помогает по построению**: открытие обновляет НОВЫЙ backend, которого зеркалящий не читает. Пользователь выполняет инструкцию, ничего не меняется, и это выглядит как поломка его машины.
- ✅ **Floor: читать ВСЕ известные источники и брать больший `expiresAt`.** Не «перейти на файл» — а перестать зависеть от имени хранилища: устаревший backend тогда просто **проигрывает голосование**, а не роняет систему. Следующий переезд переживается молча.
- ⛔ **Собственное зеркало источником НЕ считать** (сравнить `realpath` с `<CLAUDE_CONFIG_DIR>/.credentials.json`): иначе свежесть самоподтверждается — зеркало всегда согласно с собой, и проверка устаревания не может покраснеть **никогда** (`self-satisfying-metric-weak-verifier`).
- ⚠ **Дешёвый дискриминатор «переезд или разлогин» — одна команда:** `security find-generic-password -s "Claude Code-credentials"` (без `-w`, секрет не печатается) даёт `mdat`; сравнить с `stat -f %Sm` файла и с его `expiresAt`. Keychain сильно старше файла ⇒ переезд, а не логин. ⛔ И `grep -ac 'Claude Code-credentials' <бинарь claude>` = **0** — прямое доказательство, что имя больше не используется (проверено на 2.1.222).
- ⛤ **Ищи бинарь по РЕЗОЛВУ, а не по привычному пути.** Легаси-установка (`/usr/local/lib/node_modules/.../cli.js` от 1 марта) грепается «успешно» и отвечает про мёртвый артефакт; актуальный путь — через шим/`command -v` до `claude.exe` в nvm (`declaration-and-executable-carrier` §A4).
- ⛤ **Отказ обязан НАЗЫВАТЬ источники.** Лог, где стоит только `cred_expired`, не различает «backend протух» и «пользователь разлогинен» — писать `source` победителя и `expiresAt` **каждого** проверенного источника, иначе следующая диагностика начнётся с нуля.

**Empirical 2026-08-12:** отказ у Оли шёл с **8 августа** (92 записи), у личного — с 11-12-го; ни один сторож этого не заметил, поймал Андрей вручную. Фикс — `sync_credentials` читает оба источника и берёт max (dotfiles `a53fba6`); revert-verify `scripts/bot-cred-source-verify.py` (7 осей + 4 мутанта; мутант `only-keychain` воспроизводит инцидент). Очередь при этом отработала штатно — припаркованные вопросы были отвечены после фикса (`cred_queue_drain n=1` → `qa`).

## ⛔ Вторая цена floor'а «проверять бота ЧЕРЕЗ бота»: прямой прогон даёт ЛОЖНО-ОТРИЦАТЕЛЬНЫЙ вердикт, а не только портит креды

§A21 обосновывает floor **ущербом**: диагностический `claude -p` в песочнице без файла cred
создаёт пустую Keychain-запись и ломает бота. Ущерб громкий, поэтому floor читается как
«осторожно, не сломай». У него есть **вторая цена, тише первой**, и она проявляется даже когда
креды в порядке и прогон отработал успешно.

⛤ **Механизм: прямой вызов пропускает ПОДГОТОВКУ ХОДА, которую делает поллер.** Движок
(`poll_assistant.py`) перед каждым ходом выполняет `pull_vault()` → `build_cache()`
(`index --force`, при `ASSIST_BUILD_CACHE=1`) → и только потом зовёт `claude`. Прямой
`claude --print` не делает ни того, ни другого ⇒ бот отвечает по **устаревшему состоянию
графа**, честно и уверенно.

- ⛔ **Наблюдаемое — не ошибка, а ФАКТ О СИСТЕМЕ, произнесённый ботом:** «ассетов такого класса
  в графе нет ни одного». Это читается как вердикт о данных, а не как артефакт способа запуска,
  и потому не перепроверяется.
- ⚠ **Симптом-tell, ловится ОДНОЙ командой:** бот говорит «нет ни одного», а `ls` показывает файл
  на диске его же vault. Расхождение диска и ответа = смотри на **подготовку**, а не на модель.
- ⛔ **Цена — не потерянный прогон, а ЛОЖНАЯ ГИПОТЕЗА, уходящая в работу.** Ложно-отрицательный
  вердикт объясняется чем угодно (кэш, форма запроса, дефект движка) — и каждое объяснение стоит
  цикла. Замер 2026-08-30: два нуля подряд едва не превратились в issue о несуществующем дефекте
  `FILTER(CONTAINS(…))`; спасло только то, что репро прогнали на **четырёх** классах и ноль не
  воспроизвёлся (`self-authored-claim-loses-its-provenance` §A25 — два своих измерителя
  разошлись ⇒ воспроизводить ОБА, а не сочинять механизм расхождения).
- ✅ **Floor остаётся прежним и получает вторую причину: бот проверяется ЧЕРЕЗ бота** — живым
  сообщением, чтобы отработал его собственный pre-turn. Нужен именно прямой прогон (быстрее,

## ⛔ Дополнение к §A13: plist бывает битым для ОБОИХ парсеров — и джоб при этом ЗАГРУЖЕН, потому что launchd держит старую копию в памяти

§A13 фиксирует расхождение `plutil -lint` OK ↔ `plistlib` падает. Недостающий, более опасный
случай: файл невалиден **и для plutil тоже**, а `launchctl list` показывает джоб живым.

⛤ **Механизм:** launchd прочитал файл при `bootstrap` и держит **разобранную копию в памяти**.
Дальнейшая правка файла его не трогает — джоб продолжает работать по прежней версии. Значит
`launchctl list` **не является** проверкой валидности plist: он отвечает про память, а не про диск.

- ⛔ **Мина отложенная:** дефект всплывает при следующем `bootstrap` (ребут, переустановка,
  ручной re-arm) — то есть тогда, когда меньше всего ждёшь и когда причину связать не с чем.
- ⚠ **Симптом-tell отсутствует полностью:** джоб работает, лог пишется, `rc=0`. Единственный
  способ узнать — **прочитать файл парсером**, а не спросить launchd.
- ✅ **Floor: проверять ФАЙЛЫ, а не состояние джобов** — сплошной проход обоими парсерами по
  `~/Library/LaunchAgents/*.plist` и по шаблонам. Механизировано:
  `~/.claude/bin/plist-parse-detect.py` (rc=0 чисто · rc=1 находки · rc=3 не найдено ни одного).
- ⛤ **Чужие джобы из вердикта исключать** (сторонние приложения ставят свои, править их нельзя):
  иначе детектор тождественно красный и его перестают читать. Называть отдельной строкой.
- ⚠ **Типовые источники невалидности:** голый `&` в `<string>` (например `2>&1` в команде —
  обязан быть `&amp;`) и двойной дефис в XML-комментарии (`--watch`, `--flag`).

**Empirical 2026-08-21:** `com.exocortex.cli-autoupdate.plist` — голый `&` в `2>&1`; **битый для
обоих** парсеров, при этом `launchctl list` → `rc=0`, джоб живой. Найден не свипом по
`com.kitelev.*` (он этот label не покрывал), а сплошным детектором на первом же прогоне.
