# ExoSync bulk-push: R5 secret-scan block (one bad file blocks the WHOLE repo) + GitHub secondary rate-limit (core-full is misleading)

Две независимые грабли, которые всплывают только на **крупном bulk-push** (сотни-тысячи файлов за раунд — mass-migration, bulk-typing sweep, batch re-anchor). На мелких пушах ни одна не проявляется. Обе пойманы в одной сессии (Delta-3, 1204-файловый broader→genus sweep).

## Грабля 1 — ⛤ ИСТОРИЯ: R5 блокировал пуш ВСЕГО репо (per-file skip+quarantine ОТГРУЖЕН 2026-07-30)

⛔ **Поведение ниже СНЯТО:** PR **#4002** («R5 secret-scan per-file skip+quarantine, not whole-repo refuse»; issue #3976 закрыт COMPLETED 2026-07-30) — файл с секретом теперь карантинится **поштучно**, остальные уходят. ⇒ рецепт «restore флаг-файлы из backup, чтобы они выпали из changeset» для разблокировки больше не нужен; читать как историю и как описание того, ЧТО ищет R5. ⚠ Живое поведение проверять прогоном (CLI ≥ 16.195.0).

`exosync push` прогоняет **secret-scan (R5)** по файлам changesetّа. Если ХОТЯ БЫ ОДИН файл содержит секрет-паттерн (`ghp_…`/`github_pat_…` GitHub PAT, и др.), ExoSync **отказывает в пуше ВСЕГО репо** (`error … refusing to push — <path> (github-token) (R5); remove the secret and re-sync`), `pushed 0` — остальные сотни легитимных файлов changeset'а тоже не уходят. Это **корректное поведение** (R5 защищает от утечки), но диагностически коварно: `error` без деталей в кратком выводе; полный текст — только с `grep -iE 'refusing|secret-scan|github-token'` по stderr.

**Как секрет попадает в changeset:** файл с секретом мог годами лежать в vault (напр. концепт-заметка «GitHub Token» с примером/живым PAT в теле). Пока его не трогали — он не в changeset, R5 молчит. Как только bulk-операция **перезаписывает** его (даже только frontmatter — genus/updatedAt), он попадает в changeset → R5 срабатывает → блок всего репо.

**Диагностика:** `exosync push … 2>&1 | grep -iE 'refusing to push|secret-scan|github-token'` → покажет точные пути. Классифицировать (реальный секрет vs пример-placeholder) — грепнуть паттерн `(ghp_|gho_|ghs_|ghu_|github_pat_)[A-Za-z0-9_]{20,}` в файле, **не выводя токен в логи** (маскировать: `sed -E 's/(ghp_)[A-Za-z0-9]{4}.*/\1XXXX…REDACTED/'`).

**Unblock (разблокировать остальные N-1 файлов, НЕ пушить секрет):**
1. **Restore флаг-файлы из pre-операционного backup** → они совпадают с remote (нет diff) → **выпадают из changeset** → R5 их не сканит → остальной bulk пушится. (`cp <backup>/<uid>.md <vault>/…/<uid>.md`.)
2. Секрет-файлы обрабатывать ОТДЕЛЬНО (см. redaction ниже) + surface пользователю (security-решение).

**Redaction секрет-файла (когда решено чистить):** bulk-python replace `(ghp_|…)[A-Za-z0-9_]{20,}` → `[REDACTED-GITHUB-PAT-revoke-<date>]` (тело концепта сохраняется как документация), НЕ echo токен. Затем re-push проходит R5. ⛔ **Redaction ≠ митигация утечки:** токен мог уже уйти в remote git-history (пушился до появления R5) → **владелец ОБЯЗАН revoke PAT** на github.com/settings/tokens; redaction лишь чистит текущий файл + разблокирует пуш. Verify после: `gh api contents?ref=main | base64 -d | grep -c 'ghp_'` = 0 на remote.

## Грабля 2 — GitHub secondary rate-limit на rapid bulk (`git/trees` POST 403); `gh api rate_limit` core-full ВВОДИТ В ЗАБЛУЖДЕНИЕ

Массовый bulk-push (1204 файла = тысячи blob/tree REST-вызовов быстро подряд) ловит **secondary rate-limit** GitHub: `POST …/git/trees → HTTP 403: API rate limit exceeded for user ID <N>`. ⛤ **`gh api rate_limit --jq .rate.remaining` показывает CORE-лимит ПОЛНЫМ** (напр. 4994/5000) — потому что secondary rate-limit (abuse-защита от быстрых write-операций) **отдельный от core и НЕ отражён в `.rate`**. Core-reset (по часу) при этом нерелевантен.

**Диагностика:** `exosync push … 2>&1 | grep -A3 -iE '403|rate limit'` → `API rate limit exceeded for user ID` на `git/trees` POST = secondary (не core). Отличать от secret-scan (Грабля 1): secret-scan даёт `refusing to push … R5`; rate-limit даёт `403 … rate limit exceeded`.

**Что делать:** secondary rate-limit сбрасывается за **минуты** (не за core-hour). Per `gh-retry-limit` — не долбить, но **retry-with-backoff** (sleep ~100s, до ~8 попыток) в фоне: `run_in_background` until-loop, пушит когда лимит сбросится, затем verify. Плюс фоновый launchd ExoSync auto-sync САМ до-пушит при сбросе (не обязательно форсить руками). ⛤ Не ждать core-reset (56 мин) — это не тот лимит.

**Профилактика:** ⛔ **чанкинг НЕ применять** — триггер не объём, а CPU-time (#3973 признан «мимо», открыт). С **v16.195.0** транспорт сам спит ровно `Retry-After` (`maxRetries` 6) и досинкивается; ручной retry-loop нужен только когда встроенный исчерпан (§Addendum 2026-07-28).

## Когда правило срабатывает

- Крупный `exosync push` (mass-migration, bulk-typing, batch re-anchor — сотни-тысячи файлов).
- `exosync push` вернул `error`/`pushed 0` на репо, где заведомо есть pending-дельта.

## Addendum 2026-07-28 — SYNC-engine (не только bulk-push) теперь honors Retry-After (v16.195.0); secondary-limit ЛИКЕЛИ CPU-time, НЕ content-volume — fix trigger-agnostic

Тело правила про **bulk-push** (Грабля 2 — secondary 403 на `git/trees` POST). Тот же secondary-limit бьёт и по **интерактивному `exosync sync`** (обычный vault-sync, не mass-migration). Дизайн-выводы из RFC ExoSync perf/rate-limit (`6a1a6518`, 4-агентная адверсарная панель):

- **`/rate_limit` показывает ТОЛЬКО primary — подтверждено ещё раз** (Грабля 2 core-4994/5000 при активном secondary). Sync-path pre-flight gate по primary-remaining = слабый сигнал (отложен в issue #3974).
- **⛤ Misattribution пойман ревью:** «content-creation limit» GitHub — это **request-count** (80 content-creating req/min), **НЕ** content-**volume**. Инцидентная телеметрия (core 4994/5000) исключает volume-триггер → secondary-limit **вероятнее CPU-time** (secondary-limit points-модель). Следствие: гоняться за конкретным триггером (chunking больших коммитов ради «объёма» — issue #3973) — мимо; **honoring Retry-After (или ≥60s fallback при absent-header) trigger-agnostic** — уважает лимит, каким бы он ни был.
- **A shipped (v16.195.0, req `0fd4c819`):** транспорт (CLI+plugin) сохраняет `Retry-After`/`x-ratelimit-reset` из `resp.headers` ДО throw + прикладывает как own-props (`.message` байт-в-байт — `error-enrich-preserve-message`); `withRateLimitBackoff` спит ровно Retry-After, absent→≥60s, `maxRetries` 3→6; **глобальный per-sync time-budget** в `SyncEngine` (warn-defer, НЕ hard-block — иначе один залоченный репо стопорит все под single-flight `syncAll`). Замена «3 слепых ретрая по 1-8s → `pushed 0` → руками ~15 мин» на «жду ровно Retry-After → досинкивается сам».
- **C shipped (v16.196.0/.1, req `a04c4fce`):** `collectRemoteChanges` — bounded worker-pool **cap 6** (~20× под GitHub-лимитом 100 concurrent; безопасно ТОЛЬКО после A даёт solid backoff) + **indexed write-back** (пред-размеренный массив по индексу `changed`, НЕ completion-order push — иначе rename-пары/dup-uid из `matchLocalVsRemote` молча меняют порядок → недетерминизм) + fail-fast error-aggregation (один упавший blob → весь pull падает, 0 partial-apply). Метрика — реальный `Date.now()` вокруг фазы, НЕ `SyncPhaseTimer` (он суммирует per-call длительности → под concurrency не сдвигается → ложное «не быстрее»).
- **Отложено в issues (не «недоделано» — pragmatist-decouple):** #3973 push-chunking (низкий ROI после A), #3974 primary-gate, #3975 ETag/If-None-Match conditional reads, #3976 R5 per-file skip+quarantine.
