# «Смонтировать меньше» ограничено `dependsOn`-ЗАКРЫТИЕМ, а не floor'ом — мерить закрытие, а не пол

## Принцип

Оценивая, сколько можно срезать смонтированного набора (Exocortex assetspaces; шире — любая система с mount-профилями и объявленными зависимостями), **потолок выигрыша задаёт транзитивное `exo__AssetSpace_dependsOn`-закрытие рабочего ассетспейса, а НЕ always-mounted floor.**

Интуиция «floor маленький ⇒ можно срезать почти всё» — **ложная**, и ошибка тихая: floor действительно крошечный, поэтому проверка «а велик ли floor?» возвращает обнадёживающий ответ и закрывает вопрос. Реальный ограничитель лежит на другой оси — в графе зависимостей, который apply разворачивает и монтирует целиком.

## Как мерить правильно (порядок)

1. **Floor** — из кода, не из RFC: `packages/core/src/domain/profile/TsFloorGuard.ts` (`SDK_FLOOR_ASSETSPACE_UIDS` / `PLUGIN_UI_FLOOR_ASSETSPACE_UIDS`) + `CATALOG_KEEP_NAMESPACES` (keep-if-materialized). Это нижняя граница, обычно несущественная.
2. ⛤ **Закрытие** — `transitiveDependsOnClosure(profile._includes, dependsOnMap)` из дескрипторов registry (`exo__AssetSpace_dependsOn`). Считать **в файлах**, не в ассетспейсах: один AS может весить 3k файлов, другой 13.
3. **Дельта** = |полный mount| − |закрытие рабочего AS ∪ floor ∪ catalog|. Это и есть весь доступный выигрыш от «монтировать меньше того же самого».
4. **Только потом** timing — и то ради константы, а не ради доли (см. §Линейность).

⛔ Не отвечать на вопрос «стоит ли строить UX вокруг mount-less» до шага 3. Шаги 1-3 — это чтение кода + `os.walk`, десятки минут; UX-проект — недели.

## Линейность: доля файлов = доля времени

Время индексации **линейно по числу смонтированных файлов** — измерено на двух независимых движках:

- `exocortex index --force`: `ms = 0.677 × files + 181`, **R² = 0.9995** (5 точек, 23-кратный разброс N);
- сырой parse+wikilink-extract (прокси того, что делает Obsidian `metadataCache`): `ms = 0.0294 × files − 6`, **R² = 0.996**.

⇒ **вердикт «помогает / не помогает» решается счётом файлов** и не зависит от абсолютной константы конкретного движка/устройства. Устройство (iPhone vs desktop) меняет константу, а не долю. Это позволяет закрыть falsification-gate, не имея доступа к устройству — но обязывает сказать вслух, что мерилась доля, а не абсолют.

## Когда правило срабатывает

- RFC/проект обещает перф-выигрыш через «монтировать/загружать меньше» (профили, lazy-mount, partial-checkout, workspace-scoping).
- Открытый вопрос сформулирован как «насколько велик неснижаемый floor».
- Соблазн начать с timing-замеров: сперва посчитай закрытие — timing без него не отвечает на вопрос.

## Проверка жизнеспособности «просто разделить большой AS»

Стандартная митигация при фальсификации — «агрессивный shared-split» (вынести доминирующую массу в отдельный AS, чтобы рабочий на неё не зависел). **Она тоже требует замера, а не веры:**

- посчитать **входящие wikilink-ссылки** из рабочего AS в кандидата на вынос → если ребро load-bearing, вынос = массовые dangling-ссылки;
- посчитать **достижимое подмножество** (прямые ссылки + transitive внутри кандидата) → split-safe остаток = то, что реально можно вынести без битых ссылок.

Эмпирика 2026-08-02: доминирующая масса `shared-private-concepts` = 2774 файла (32 % vault-my), но в неё идёт **3684 ссылки из 1464 личных ассетов** (39 % личного корпуса); split-safe остаток — **732 файла (8.4 %)**. Т.е. митигация даёт либо 32 % ценой битых ссылок, либо безопасные 8 %. ⛤ **Но это не весь выбор:** замер §A3 нашёл разрез ВДВОЕ шире (52 %) и при этом на 43 % ДЕШЕВЛЕ по битым ссылкам — оптимум ищется по числу пересечённых рёбер, а не по объёму.

## ⛤ Операционный минимум вокруг `apply-profile` (читается В МОМЕНТ команды)

`apply-profile` — **strict-replace**: он сносит всё, что смонтировано СВЕРХ закрытия профиля.
Дрейф копится сам (ассетспейс смонтировали `assetspace-add`'ом и забыли дописать дескриптор в
профиль), и обречённость видна только в момент применения — заряжает одна сессия, стреляет другая.

1. ⛤ **`apply-profile <uid> --vault <V> --verbose` БЕЗ `--yes` = де-факто dry-run.** Флага
   `--dry-run` у команды нет, но headless-гейт отказывает **после** печати плана:
   `N files to remove, M AS to tear down, K AS to materialize` → `Refused: --yes flag required`.
2. ⛔ **Никогда не применять профиль, не посмотрев план.** `M > 0` на рабочем vault = ты сносишь
   чужое; это блокер, а не деталь.
3. ⛤ **Teardown-набор спрашивать у CLI, а не выводить своим обходом registry** — наивное
   «закрытие минус смонтированное» ПЕРЕоценивает снос (движок держит TS-floor и
   `CATALOG_KEEP_NAMESPACES`), см. §A2.
4. ⛤ **Соответствие «профиль ↔ vault» устанавливается ЗАМЕРОМ, а не по имени:** прогнать план
   всеми профилями-кандидатами; совпадение даёт ровно один — `0 / 0 / 0`. Имена (`-full`-зеркала)
   в общем случае лгут.
5. **Починка аддитивна:** дописать недостающие дескрипторы в `exo__Profile_includes` (чистый
   multi-value append → `Edit` fail-opens). ⛤ Правя базовый профиль, правь и его `-full`-зеркало.
