# ExoSync quarantine triage: диагностировать до мутации, не хирургить watermark приватного репо

## Принцип

Когда `exosync sync` репортит `quarantined N` / `conflict group <uid>` на приватных данных пользователя — **диагностировать полностью до любой мутации**, и ⛔ **не делать рискованную watermark-хирургию / повторные sync автономно**. Многие «конфликты» — доброкачественные (косметическая разница) ИЛИ фантомы (путь, которого нет ни на remote, ни локально). Правильный исход чаще = «диагноз + issue», не «force-resolve».

## Триаж-чеклист (по шагам)

1. **`exosync quarantine list` требует `--token-from-gh`.** Без токена → `Error: A GitHub token is required (private sync units read as 404)`. Всегда `exosync quarantine list --vault . --token-from-gh`.
2. **`quarantine list` пусто ≠ нет конфликта.** Sync может печатать `quarantined 1` + `pinned to re-derive on the next sync (#3477)`, но `quarantine list` → «No open conflicts — nothing to resolve». Это **транзиентный re-derive pin**, НЕ регистрируемый quarantine → `exosync quarantine resolve` **неприменим** (нечего резолвить). Отличать: `resolve --take local|remote|file <path>` работает только для того, что реально в `list`.
3. **Проверить, что «конфликтующий» путь реально существует — ОБЕ стороны.** Cross-path конфликт (`local change at A/uid.md vs remote change at B/uid.md`, same UID) часто содержит **фантом**: `gh api repos/<o>/<r>/contents/<B-path>?ref=main` → 404 И `ls <local>/<B-path>` → absent. Фантом = устаревшая ссылка в локальном watermark/base, а не реальные данные → ничего не осиротит.
4. **Определить сторону (keep-local vs keep-remote) по КОНВЕНЦИИ соседей, не угадывая.** Если реальная разница тривиальна (напр. один символ в `exo__Ontology_url` — trailing `#`), грепни sibling-ассеты того же класса/папки: у большинства есть `#` → keep-local (с `#`) правильно. Verify-before-assert: не решать «какая сторона права» без sibling-эмпирики.
   - ⛔ **Конвенция бывает СИММЕТРИЧНОЙ, и тогда шаг 4 молчит, а не отвечает.** Замер 2026-09-06
     (`exoas-exo-reqs`, порядок ключей `approvedAt` относительно `covers`): **45 против 46** из 190 —
     то есть форма не канонизирована вовсе, и «у большинства» не существует. ⚠ Tell: доли сошлись
     в пределах единиц ⇒ ⛔ не додумывать «наверное, правильнее…», а искать ДРУГОЙ дискриминатор.
   - ✅ **Замена — ИНВАРИАНТ ДАННЫХ, проверяемый по корпусу** (`updatedAt >= approvedAt`,
     `endTimestamp >= startTimestamp`, статус ↔ таймстемп). Считать обе стороны и весь корпус:
     держится у 64/64 соседей ⇒ сторона-нарушитель проигрывает по существу, а не по вкусу.
     ⛤ Работает и там, где данные ИДЕНТИЧНЫ построчно: инвариант судит метаданные, а не diff.

5. **Full diff перед вердиктом «доброкачественно».** `gh api .../contents/<path> --jq .content | base64 -d > /tmp/remote.md; diff <local> /tmp/remote.md`. Пусто/1-символ → косметика.

## ⛔ Карантин — ПОЗДНИЙ сигнал того же класса; ранний и куда более частый — `pending-local-*`

Класс отказа называется «правки не уехали», но карантин — лишь **одна его форма**, и возникает она, только когда **обе** стороны разошлись. Гораздо чаще push молча не отрабатывает, и правка висит `pending-local-*`, конфликта не порождая. Гвард, проверяющий только `quarantine list`, к этому слеп **по построению** — и молчание читается как «чисто».

- ⚠ **Замер 2026-08-16, два независимых случая:** 5 задач, закрытых ботом одним batch'ем, висели непушнутыми **5 дней** (карантин по СОСЕДНЕМУ файлу всплыл лишь на 4-й); 17 записей журнала — **300 часов**. Оба нашлись только после расширения монитора на `pending-local`.
- ✅ **Ранний детект — `exosync-parity`**, но судить по нему нужно строго:

| наблюдаемое | что значит | действие |
|---|---|---|
| `pending-local-*` | наша правка не уехала | ⇒ тревога, если старше порога |
| `pending-remote-*` | мы отстали, remote ушёл вперёд | ⇒ норма, лечится `pull` |
| `quarantine-pinned` | обе стороны разошлись | ⇒ ловит `quarantine list`; ⛔ `pull` его НЕ снимает — см. ниже |
| `no-watermark` | репо ни разу не синкали НА ЭТОМ устройстве | ⇒ parity его НЕ проверяет; один `sync` |
| `status: error` | 404 / нет прав | ⇒ слепая зона; чужой тестерский — норма. ⛔ У 404 есть ТРЕТЬЯ причина, которую сообщение НЕ называет — §ПУСТОЕ ДЕРЕВО ниже |

- ⛔ **ВЫДАЧУ parity НЕ УСЕКАТЬ — ни `tail`, ни `head`: это ПЕРЕЧИСЛЕНИЕ по 20+ репо, а ИТОГОВАЯ СТРОКА ВНИЗУ делает `tail` субъективно правильным выбором.** У других инструментов усечение ощущается компромиссом; здесь сводка стоит в конце, поэтому `tail -N` читается как «взять итог» — и режет ровно построчный отчёт по репо, где лежит ТВОЯ строка. Порядок обхода не твой ⇒ своего репо в хвосте может не оказаться.
  - ⛔ **Прежняя редакция этих двух строк называла итоговую строку `Summary` — ЛОЖНО, снято 2026-09-02 замером.** У `exosync-parity` слова `Summary` нет **ни в одной** из трёх форм (чтение бандла CLI): `ExoSync parity: VACUOUS — 0 of N repo(s) checked (errors / never synced)` · `ExoSync parity: M1=0, M2=∅ (N repo(s) checked[, K skipped])` · `ExoSync parity: M1=<n>, M2=<n> diff(s) (N repo(s) checked[, K skipped])`. `Summary` печатает **`exosync push`/`sync`** (§ниже — там цитата верна), и claim приехал переносом формы соседней команды. ⇒ **tell был НЕИСПОЛНИМ**: условие «в выдаче есть `Summary`» у parity не истинно **никогда**, то есть floor стоял без работающего детектора.
  - ⚠ **Симптом-tell (исполнимый):** в выдаче есть строка `^ExoSync parity:`, а строки твоего репо нет. ⛔ Не читать как «у меня чисто» — читать как «я смотрю на усечённое». ⛤ Якорь `ExoSync parity:` общий у всех трёх форм ⇒ переживает и `VACUOUS`, и `M2=∅`.
  - ✅ **Floor: отчёт целиком в файл, свой репо доставать ЗАГОЛОВКОМ, а не хвостом:**
    ```bash
    node "$IDX" exosync-parity --vault /Users/kitelev/vaults/vault-exodev --token-from-gh > parity.txt 2>&1; echo "rc=$?"
    awk '/kitelev\/<repo>#/{f=1;print;next} f&&/^kitelev\//{exit} f' parity.txt | cat
    ```
    ⛔ `rc` снимать ОТДЕЛЬНОЙ строкой, не через пайп (`bash-loop-eval-pitfalls` Г3b: `$?` после пайпа = rc последнего звена).
  - ⛔ **`#` в якоре — НЕСУЩИЙ разделитель, а не часть форматирования: без него имя репо матчит СОСЕДА-ПО-ПРЕФИКСУ.** Имена ассетспейсов образуют префиксные семьи (`exoas-exodev` ⊂ `exoas-exodev-archive`, `exoas-my` ⊂ `exoas-my-archive`), а parity печатает `kitelev/<repo>#<ветка>` — то есть `#` и есть граница имени. Якорь без него отдаёт **первый** матч по порядку обхода, и это может быть архив.
    - ⚠ **Симптом-tell:** выданные строки описывают репо, к которому твоя работа отношения не имеет (`no-watermark` у архива, тогда как ты правил рабочий) ⇒ читать не как «мой репо не синкается», а как «якорь сматчил не тот».
    - ⛤ **Цена — вывод, ОБРАТНЫЙ истине:** у меня архив дал `M2 diffs 0` при `no-watermark`, что читалось как «в альте мой репо не синкается» и едва не отменило корректный путь отгрузки. Пере-замер точным якорем: `2079/2080 in parity, M2 diffs 0` ⇒ синкается.
    - ✅ **Дешевле `awk` — `grep -E 'kitelev/<repo>#'`**, когда нужна одна строка состояния: короче, и потерять `#` в нём сложнее (он рядом с именем, а не в конце регэкспа с экранированием).
  - ⛤ **Класс задокументирован** (`self-satisfying-metric-weak-verifier` §ТРЕТИЙ/§ЧЕТВЁРТЫЙ исход — там же эмпирика 2026-08-26 по этому же инструменту), но носителем был **измеритель**, а не **инструмент**: зовущий parity в то правило не пойдёт. _Рецидив 2026-08-28 (vteam-7494fe23): `tail -60` на 24 репо скрыл строку `exoas-exoass`; урон 0 — усечение замечено сразу, но стоило лишнего прогона._
- ⛔ **rc самого `exosync-parity` дискриминатором НЕ является: он равен 1 при ЛЮБОМ M2>0**, включая совершенно здоровое отставание. Замер: `vault-bot-diary` даёт `rc=1` и 101 diff, будучи исправным. Гвард, ключующийся на rc или на «M2 diffs > 0», станет **тождественно-красным** (`self-satisfying-metric-weak-verifier` §ЗЕРКАЛО) — к такому привыкают и перестают читать.
- ⛔ **`no-watermark` — НЕ «недоступно», и склеивать их нельзя.** Замер: репо, помеченное мной как недостижимое, оказалось здоровым (ветка резолвится, доступ есть) — его просто ни разу не синкали; один `sync` дал `pulled 1, pushed 0`, **ничего не терялось**. Общее у них одно (parity такой репо не проверяет), но причина, лечение и серьёзность разные, и говорить «правки не уедут» про `no-watermark` значит врать о механизме.
- ⛤ **Возраст мерить по ПЕРВОМУ НАБЛЮДЕНИЮ, а не по `mtime`.** mtime отвечает на вопрос «когда файл меняли», а нужен «сколько он висит непушнутым»: файл со старым mtime может стать pending сию секунду, а у `pending-local-delete` локального файла нет вовсе.
- ⚠ **Порог обязателен, и нулевой порог даёт ложную тревогу ПО ПОСТРОЕНИЮ.** Разовый диагностический прогон с `MAX_AGE=0` показал «82 застрявших файла» в активно пишущем vault — через минуты всё уехало (4429/4429 в parity). «Есть непушнутое» и «застряло» — разные вопросы.
- ⛤ **Где смотреть у ботов:** поллер делает `exosync push` после **каждого** хода, поэтому `pending-local` старше часа = push не отработал. Реализация — `~/dotfiles/scripts/bot-parity-pending.py` (+ харнесс `…-verify.py`, 12 осей / 7 мутантов), вызывается из `bot-quarantine-watch.sh`.

    - ⚠ **Tell арифметический:** `resolve` вернул `rc=0`, `quarantine list` → «No open conflicts», а `gh api …/contents/<path>?ref=main` даёт **404**. Три сигнала, из них два ложно-успокаивающих.
    - ✅ **Floor: после `resolve` — один `exosync sync`**, он re-деривит пины (#3477). Вердикт по СОДЕРЖИМОМУ на remote, ⛔ не по `quarantine list`.

## ⛔ `sync` детектит изменения ПОРЕПОШНО — правка, легшая ВО ВРЕМЯ раунда, молча не уезжает, и `Summary` об этом не скажет

Раунд `exosync sync` обходит два десятка репо и идёт **минуты** (замер: 191 с на 24 репо). Обнаружение изменений происходит **в момент, когда обход доходит до конкретного репо**, а не на старте. Значит правка, сделанная уже после того, как её репо пройдено, в этот раунд **не попадает** — при том что синк отработал успешно.

- ⚠ **Отказ тихий и правдоподобный:** репо честно рапортует `synced — pushed 0`, суммарная строка бодрая (`pushed 71`), ошибок нет. «0» неотличимо от «нечего было пушить», а именно так выглядит и успех.
- ⛔ **`Summary` дискриминатором НЕ является** — он агрегат. Пропущенный репо в нём просто не виден: его вклад ноль, а соседи дают большие числа (`aggregate-hides-dead-stream`).
- ✅ **Floor: после синка проверять СВОЙ предмет на remote по СОДЕРЖИМОМУ**, а не по строке синка — `gh api "repos/<o>/<r>/contents/<path>?ref=main" --jq .content | base64 -d | grep -c '<маркер правки>'`. Ноль ⇒ прогнать синк ещё раз; второй раунд подхватывает (проверено: `pushed 0` → `pushed 8`).
- ⛔ **`<path>` в этом вызове — РЕПО-относительный, а НЕ vault-относительный, и подстановка второго даёт HTTP 404, читаемый как «файл не доехал».** Ошибка систематическая: путь у тебя перед глазами именно в vault-форме (её печатают `find`, `set-body`, parity), и она выглядит полной. Вывод же — противоположный истине: ты идёшь пере-пушивать то, что уже на remote.
  - ✅ **Floor: выводить МЕХАНИЧЕСКИ, а не вспоминать** — repo-relative = vault-relative минус префикс `assetspaces/<owner>/<repo>/`:
    ```bash
    P="assetspaces/kitelev/exoas-exodev/exodev/<uid>.md"          # ← как печатает vault
    REPO_P="${P#assetspaces/*/*/}"                                 # → exodev/<uid>.md
    ```
  - ⛤ **Дешевле и надёжнее — вообще не выводить:** взять путь **листингом** из своего же коммита (`gh api "repos/<o>/<r>/commits/<sha>" --jq '.files[].filename'`), он уже repo-relative. Тот же floor, что `vault-asset-creation` §A2b («путь брать листингом, не конструировать URL»), — здесь он нужен и когда UID известен целиком.
  - ⚠ **Симптом-tell, отличающий от настоящей недоставки:** 404 приходит **сразу**, а `Summary` синка показал ненулевой `pushed` по этому репо. Настоящая недоставка даёт `pushed 0` (§выше) — то есть два случая различаются **до** обращения к API.
- ⚠ **Симптом-tell до проверки:** ты правил файлы, пока синк уже шёл, ЛИБО репо твоего предмета отсутствует в списке с ненулевым `pushed`. ⛔ Не читать его отсутствие как «там нечего пушить» — фильтр вида `grep 'pushed [1-9]'` прячет ровно этот случай.
- ⛤ **Обратная сторона того же свойства полезна:** долгий раунд означает, что `parity`, снятый ДО синка, к моменту push уже устарел — ещё одна причина, почему вердикт даёт только состав коммита ПОСЛЕ (`concurrent-session-vault-write-isolation` §Recurrence 2026-08-16).

## ⛔ ПУСТОЕ ДЕРЕВО у `main` ⇒ ExoSync пропускает репо НАВСЕГДА, а его сообщение называет ДВЕ ЛОЖНЫЕ причины

Репозиторий, чей `main` указывает на **пустое дерево** (`4b825dc642cb6eb9a060e54bf8d69288fbee4904` —
git empty tree), для GitHub API не существует **как дерево**: `git/trees/<empty>` отвечает **404**,
хотя сам репо и ветка живы. ExoSync трактует этот 404 как недостижимость и **пропускает репо
целиком** — то есть push туда не случается **никогда**, а не «падает».

⛔ **Его собственная диагностика уводит от корня, называя два неверных подозреваемых:**

```
warn: repo unreachable (HTTP 404): dead AssetSpace pointer,
      or the fine-grained PAT does not allowlist this repo — skipped
```

Оба ложны и оба правдоподобны ⇒ расследование уходит в дескриптор реестра и в права токена.

- ✅ **Дискриминатор — ОДНА команда, и он терминальный:** `gh api repos/<o>/<r>/commits/main --jq
  .commit.tree.sha`. Ответ `4b825dc6…` ⇒ дерево пустое, и ни pointer, ни PAT ни при чём.
  ⛔ Не `git/trees/main` — он даёт тот же 404, что и у несуществующего репо, то есть **не различает**.
- ⚠ **Оба «естественных» подозреваемых снимаются замером, а не рассуждением:** репо существует —
  `gh api repos/<o>/<r> --jq .default_branch`; права есть — `--jq .permissions` (`push: true`).
  Если ты читаешь метаданные тем же токеном, версия «PAT не allowlist'ит» уже опровергнута.
- ⛤ **Корень обычно — ИСПОЛНЕНИЕ floor'а «ассетспейс asset-only, README не нужен»**
  (`exocortex-cold-archive-assetspace` §шаг 1) **без его неназванного предусловия**: удалять
  единственный файл можно ТОЛЬКО после того, как лёг первый ассет. Снёс README у пустого репо ⇒
  дерево стало пустым ⇒ ExoSync ослеп, и заметить это можно лишь по сводке `N repo(s) checked,
  1 skipped`.
- ✅ **Лечение — положить ОДИН настоящий ассет через API** (`gh api -X PUT …/contents/<путь>`
  с `content` = base64), а не заглушку: дерево перестаёт быть пустым, репо возвращается в обзор,
  и остаток догоняет штатный `exosync push`. Флип предъявляется parity: `error — 0/0 … skipped`
  → `checked — 1/N, M2 diffs N-1`.
- ⚠ **Сводка `… , 1 skipped` — единственный ранний сигнал**, и он тонет в перечислении. Читать
  её отдельно; ⛔ выдачу parity при этом не усекать (§выше — итоговая строка `ExoSync parity: …`
  внизу делает `tail` субъективно верным и режет строку своего репо).

## ⛔ `exosync dedup-uids --auto` KEEP'ает СТАРУЮ запись и re-uuid'ит СВЕЖУЮ — где uid есть КЛЮЧ ПОИСКА, это разрыв, а не уборка

Инструмент перечисляет дубли `exo__Asset_uid` на диске и предлагает zero-loss план. ⛔ Но «zero-loss» у него о ФАЙЛАХ, не о **ключах**: оба файла выживают, а тот, что получил свежий uuid, перестаёт находиться по прежнему uid.

- ⚠ **KEEP выбирается по ПОРЯДКУ ОБХОДА, а не по свежести** ⇒ у папок-по-месяцам (`sessions-2026-08/` ↔ `-09/`) uid остаётся у **устаревшей**, а актуальная теряет ключ.
- ✅ **Floor: перед `--apply` спроси, ЯВЛЯЕТСЯ ЛИ uid КЛЮЧОМ ПОИСКА.** Запись сессии ищут по `session_id`, и uid ему равен ⇒ `--auto` там НЕЛЬЗЯ. Сухой прогон план печатает — читать его, а не доверять слову «zero-loss».
- ⛤ **Дискриминатор «мусор или модель» — ПРОЧИТАТЬ ОБА ФАЙЛА:** разные метки/статусы ⇒ два разных ассета (настоящий дубль); совпадающие при разных путях ⇒ один объект, чьё РАЗМЕЩЕНИЕ месяц-зависимо — дефект ПУТИ, уборкой не лечится.
- ⛔ **`exo__Asset_uid` сменить `set-property` НЕЛЬЗЯ** (fail-loud: «refusing — the asset identity»). Нужно свести дубль вручную ⇒ **пересоздать `create`** (свежий uid естественно) + `rm` старого; так выбираешь ТЫ, кто сохранит uid, а не порядок обхода.

## Запреты

- ⛔ **Не долбить `exosync sync` повторно** в надежде на fluke-конвергенцию — фантом-watermark re-derive **детерминированно** re-quarantine'ит (3 re-sync = 3 одинаковых quarantine). Это анти-паттерн уровня `gh run rerun --failed` на systemic-fail (`gh-retry-limit`).
- ⛔ **Не делать watermark-хирургию / force-resolve на приватных данных пользователя автономно** — даже когда keep-сторона очевидна. Приватный репо + ambiguous ExoSync-состояние = user-decision territory (floor: live-data + irreversible → backup + не автономно на ambiguous).
- ⛤ Если корень = баг конвергенции ExoSync (фантом в watermark, re-derive loop) — **завести issue** (`kitelev/exocortex`, labels bug/exosync), НЕ обходить руками. Доброкачественный (косметический diff, данные целы) → низкий приоритет, но затрассировать.
