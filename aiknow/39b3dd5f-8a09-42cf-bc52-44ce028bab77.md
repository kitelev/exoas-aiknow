## Mechanical pre-check перед merge / push

```bash
# Identify ALL parents containing this submodule
for repo in vault-2025 vault-exodev exocortex; do
  path=$(eval echo "/Users/kitelev/{,Developer/exocortex-development/}$repo")
  if [ -d "$path/.git" ] || [ -f "$path/.gitmodules" ]; then
    grep -l "<submodule-name>" "$path/.gitmodules" 2>/dev/null && echo "  → in $repo"
  fi
done
```

Если ≥2 hits — pointer bump в каждом **lockstep** parent — обязательная часть commit chain; exocortex — только после fixture-check (§Complement edge case).

## ⛔ Complement edge case (2026-06-15): exocortex consumer is FIXTURE-COUPLED — bumping its pointer is NOT a bare mechanical bump

The 2026-05-23 incident taught «bump all consumers, including exocortex `packages/exoas-exocmd`». But the **inverse failure** is just as real: bumping the exocortex pointer **without a paired fixture/code update can BREAK exocortex CI**. Before bumping exocortex's `packages/exoas-exocmd` pointer, check whether the new submodule content changes the output of any **coupled CLI fixture** — esp. `packages/cli/specs/fixtures/groundings/<grounding-uid>.expected.json` (golden snapshot of a grounding's apply-output).

**Decision rule for the exocortex consumer:**

| Did your submodule change alter the apply-output of a grounding that has a `*.expected.json` fixture in exocortex? | Action on exocortex `packages/exoas-exocmd` pointer |
|---|---|
| No (e.g. you only added a TBox class/property unused by any fixtured grounding) | Bare pointer bump OK (mechanical), still as a PR. |
| **Yes** (e.g. you added an inheritance-rule that now adds a frontmatter key to the created asset) | ⛔ Bare pointer bump **breaks CI**. Requires a **coupled PR**: bump pointer + regenerate the `expected.json` fixture(s) in the same change. This is a separate, fixture-aware task — **legitimately deferred** from a vault-only homoiconic fix. |

**Why the two vault clones differ from exocortex:** vault-2025 + vault-exodev are **lockstep runtime consumers** (the Obsidian plugin / CLI read the live grounding) — bump both immediately, that's what fixes the user-facing behavior. exocortex `packages/exoas-exocmd` is on an **independent PR cadence** (often several commits behind vault) and its CI **re-derives** grounding outputs against pinned golden fixtures — so its bump is fixture-coupled, never a bare pointer bump.

## ⛔ Addendum 2026-07-11: bumping a data-submodule surfaces a STALE-WALKER test (regression vs stale-test — trace the invariant, don't revert the bump)

The 2026-06-15 edge case covers **golden-snapshot** fixtures (`*.expected.json` — the bump changes an apply-output). A **second** class of consumer breaks on a bump: a test that **walks the submodule data at runtime** (reads the `.md` assets, classifies them, asserts a structural invariant). When the submodule's data is **restructured** (schema/shape change) but the pinned pointer lags, bumping surfaces the walker as RED — **not** because the invariant is violated, but because the walker's assertion form is **stale relative to the new data shape**.

**Diagnostic — regression vs stale-test (do this BEFORE reverting the bump):** trace whether the invariant still HOLDS in the new data shape. If the thing the test guards (e.g. "the not-a-prototype clause") is still present but **moved** (flat → nested composite / a `Not(IsPrototype)` wrapper / a deeper leaf), it's a **stale test** (fix: make the walker structure-aware — traverse the new shape). If the invariant is genuinely **gone** in the new data, it's a **real regression** the bump correctly caught (fix: the DATA, or block the bump). ⛔ Do not reflexively pin at the old pointer — that hides the invariant behind stale data.

**Blast-radius check:** run **all** suites that read the submodule (`grep -rl '<submodule-path>\|SUBMODULE_<X>' packages/*/tests`) against the bumped pointer. If exactly ONE walker-test is RED and every other reader is green → the bump is clean, only that walker is stale (fix it + bump together). Note: `test-coverage-exocortex` now runs the **FULL** `packages/core/jest.config.js` (no `--testPathPatterns` allowlist — the CLAUDE.md "Test Suite Awareness" allowlist note is STALE), so such a walker under `tests/integration/**` **is** CI-gated — a stale walker reds required CI once the pointer is current (it only stayed green because the pinned pointer held old-shape data).
## ⛔ Verify submodule push SUCCEEDED before bumping the superproject pointer (broken-pointer trap)

<!-- Added by /session-retrospective 2026-06-27 — root: child al-exocmd-bootstrap, bumped vault-exodev pointer to an UNPUSHED submodule commit after a rejected push. -->

Bumping the superproject pointer to a submodule commit that is **not on the submodule's remote** produces a **broken pointer**: `git clone --recursive` / CI / sibling sessions fail to fetch that gitlink commit. This is worse than a misleading commit subject — it breaks checkout for everyone.

Two ordering bugs cause it (observed together):

1. **Rebasing with a dirty working tree refuses, and the subsequent commit lands on the STALE base.** `git fetch origin main && git rebase origin/main` while the asset file is still modified-but-unstaged → `error: Please commit or stash them` → rebase is a **no-op** → the following `git commit <file>` creates a commit on top of the OLD local HEAD, not the fetched `origin/main`. If origin moved, the push is then **non-fast-forward rejected**.
2. **Bundling `submodule-push + pointer-bump` in one compound Bash call without checking the push result.** The rejected push prints `hint: ... before pushing again`, but the same call proceeds to bump+push the superproject pointer → pointer now references an unpushed commit.

**Correct ordering (per submodule write):**
```bash
SM=<vault>/assetspaces/kitelev/<submodule>
git -C "$SM" add <file>                 # stage FIRST (clean working tree for rebase)
git -C "$SM" commit -m "..."            # commit BEFORE rebase
git -C "$SM" fetch origin main && git -C "$SM" rebase origin/main   # now rebase applies (tree clean)
git -C "$SM" push origin main           # ⛤ VERIFY: output shows `<old>..<new>  main -> main` (fast-forward)
#   ↑ if output shows `hint: ... before pushing again` → push FAILED → STOP, do NOT bump pointer
NEWSM=$(git -C "$SM" rev-parse --short HEAD)
git -C <vault> ls-remote origin >/dev/null   # (optional) confirm reachable
git -C <vault> add assetspaces/kitelev/<submodule>   # bump ONLY after confirmed push
git -C <vault> commit assetspaces/kitelev/<submodule> -m "chore(submodule): bump ... → $NEWSM"
git -C <vault> push origin main
```

**Floor practices:**
- **Commit before rebase** — never `git rebase` with uncommitted changes to the file you're about to commit (the rebase no-ops and your commit lands on stale base).
- **Verify the push fast-forward line** (`<sha>..<sha>  main -> main`) before bumping the pointer; treat any `hint: ... before pushing again` / `! [rejected]` as STOP.
- **Don't bundle push + pointer-bump in one un-checked compound call** — split so the push result gates the bump.

**Recovery if a broken pointer was already pushed:** rebase the orphan submodule commit onto `origin/main` + push it; then re-bump the superproject pointer to the now-pushed SHA (a `fix(submodule): re-bump → <sha> (prev was unpushed)` commit). Verify `git ls-tree HEAD <submodule-path>` 160000-SHA == submodule remote HEAD.

**Recurrence 2026-07-12 (feature-3896 child, git-free reqs repo clone+push) — a `git push … 2>&1 | tail -1` pipe MASKS the non-fast-forward rejection (pipe exit = `tail` exit = 0), and the following `&& echo PUSHED` prints a false success.** Applies to ANY clone+commit+push to a reqs/shared repo (git-free vault flow, feature-sdd Step 1.4/6), not only submodule pointer bumps. Cost: 1 masked-fail push + 1 rebase+re-push; uron 0. **Floor:** never gate a push's success on a `| tail`/`| head` pipe (pipe exit hides the git exit — `bash-loop-eval-pitfalls` Грабля 3b family); read the raw push output for the `<sha>..<sha> → main` fast-forward line OR (best) confirm via an authoritative `gh api …/contents?ref=main` read of the pushed field, as here.

**Recurrence 2026-07-30 (child Phase 2 per-bot log-vault, dotfiles commit) — the SAME `| tail` mask, but it hid a REFUSED REBASE, and the false "Everything up-to-date" came from a THIRD party (the hourly auto-backup) having already pushed.** One chain: `git fetch origin "$BR" -q && git rebase origin/"$BR" 2>&1 | tail -2 && git push origin "$BR" 2>&1 | tail -3`. The rebase refused (`cannot rebase: You have unstaged changes` — foreign dirty files: another session's `meta-session/SKILL.md`, `.gitconfig`, a tracked `.pyc`) — **exactly the dirty-tree refusal this rule documents above** — but `| tail -2` swallowed the non-zero exit, so `&&` ran the push anyway; the push then printed `Everything up-to-date`, which read as "nothing to do / maybe already fine". **Two independent masks in one line.**
- ⛤ **New wrinkle worth its own tell:** `Everything up-to-date` after your own fresh commit is NOT self-evidently benign on this machine — `~/dotfiles/scripts/auto-backup.sh` runs hourly with `git add -A` + commit + push, so it can push YOUR commit (plus the foreign dirty files, in ITS commit) between your commit and your push. Do not infer "my commit didn't land" NOR "my commit landed cleanly" from that string.
- **Authoritative verification is what resolved it** (per the Floor below): `git rev-parse --short HEAD` vs `origin/main` (equal, 0/0 ahead-behind — but HEAD was now the auto-backup's SHA, not mine) → `git merge-base --is-ancestor <my-sha> origin/main` = YES → `git show --stat <my-sha>` (confirmed my commit is exactly my 2 files, the foreign files went into the auto-backup commit, not mine) → `gh api repos/…/contents/<path>?ref=main | base64 -d | grep -c <new-marker>` (my content present on remote main). Cost: 1 masked failure + 4 verification calls; урон 0.
- **Floor reinforced (unchanged, now 2× empirical):** never put `git rebase` / `git push` behind `| tail`/`| head` when you intend to act on the result; and for "did my change land" prefer `merge-base --is-ancestor` + a `gh api …/contents?ref=main` content read over ANY local git summary line. Habit-recurrence (the rule was in this session's system-reminder); hook not introduced (cannot distinguish a result-bearing pipe from a cosmetic one) — accept baseline.
