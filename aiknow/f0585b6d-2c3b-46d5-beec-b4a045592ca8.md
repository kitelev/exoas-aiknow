# Integration tests for regression fixes: revert→fail / restore→pass discipline

⛔ **БАРЬЕРА НЕ БУДЕТ — и это ЗАМЕР, а не лень (2026-08-22, метод задачи 7156e4c2).** Нарушение здесь СЕМАНТИЧЕСКОЕ («ось вакуумна», «мутант не различает»), а хук видит только вызов инструмента: в тексте `Bash`/`Edit` нет признака, по которому отличить ось, которая проверяет, от оси, которая зелена по независимой причине. ⇒ рецидивы (9 за 30 дней) ловятся **симптомом из таблицы**, а не гвардом; ускорить это можно только сжатием текста, не механикой.

Любой integration test, который claims «exercises the regression», обязан быть **empirically verified** двумя прогонами:

1. **Revert production fix** → test must FAIL (it should detect the absence of the fix).
2. **Restore production fix** → test must PASS.

Если test passes в обоих состояниях — он не exercises regression; он vacuously passes по другой причине (fixture defect, wrong assertion, shape mismatch). Это **false-positive coverage** — ship'нутый guard, который не guard'ит. ⛔ (квалифицировано 2026-09-02: верно для оси **на дефект**; ось на **отсутствие побочного эффекта** зелена в обе стороны ЗАКОННО — §сразу ниже.)

## ⛔ Ось на ОТСУТСТВИЕ побочного эффекта зелена в ОБЕ стороны ЗАКОННО — и это её ПРОДУКТ, а не вакуумность

Строка выше безусловна и потому применяется к **каждой** оси набора. У косметического фикса
(вычистить NUL-байты, переименовать переменную, снять мёртвый импорт) в наборе штатно живёт ось
**«поведение не изменилось»** — и она обязана быть зелёной И на предмете, И на мутанте: её
зелёность на до-фиксной половине **и есть** доказательство, что правка ничего не сломала.

- ⛔ **Дискриминатор — ПРЕДМЕТ оси, а не её исход.** Ось на **дефект** («грep без `-a` видит»,
  «носитель чист») обязана краснеть на мутанте. Ось на **отсутствие регрессии** обязана НЕ
  краснеть — иначе фикс не косметический, и это находка.
- ⛤ **Отличать от «контроля на невакуумность»** (§капабилити-латч): там соседняя ось зелена,
  потому что мутант бьёт **не в неё**. Здесь мутант бьёт **ровно в предмет** оси (заменён весь
  файл), и она всё равно зелена — по существу, а не по промаху.
- ✅ **Floor: такая ось законна ТОЛЬКО в наборе, где ≥1 соседняя ось КРАСНЕЕТ на том же мутанте.**
  Ноль краснот на весь набор ⇒ вакуумен набор целиком, и строка выше применяется без поблажек.
- ⚠ **Симптом-tell, ловится ПРИ ЧТЕНИИ набора:** ты собираешься назвать ось вакуумной — спроси,
  что она утверждает. «Ничего не изменилось» — это утверждение, и оно проверяемо.

### ⛤ Инструмент для таких фиксов: git отдаёт ПАРУ бинарной ⇒ построчного диффа нет, сверяй `cmp -l`

Приёмка косметического фикса упирается в «а ровно ли то изменено, что заявлено». При NUL-байте
в любой из ревизий `git diff --numstat` даёт `-  -`, а `git show` — `Bin N -> N bytes`:
построчного диффа **не существует**, и глазами сверить нечего.

```bash
cmp -l <(git show <sha>^:<path>) <(git show <sha>:<path>)   # rc=0 идентичны · rc=1 различия
```

- ⛔ **Не пайпить** (`| cat`, `| head`): `$?` тогда берётся у последнего звена, и `rc=1` читается
  как `0` — `bash-loop-eval-pitfalls` Г3b. Вердикт — по `rc` **или** по числу строк вывода.
- ⚠ **Смещения 1-based, значения ВОСЬМЕРИЧНЫЕ:** `0` = NUL, `40` = пробел (не «сорок»).
- ⛤ Ноль строк сверх ожидаемых = «прочих правок нет» — ровно то, что нужно приёмке; `diff -q`
  этого не даёт (он говорит лишь «Binary files differ»).

**Empirical 2026-09-02** (`91c5fef9`, приёмка NUL-фикса `save-retrospective-verify.sh`): `numstat`
пары → `-  -`; `cmp -l` → **ровно 3 строки** (4819 / 5745 / 6458, `0o0 → 0o40`) ⇒ правка = три
NUL→пробел и ничего больше. Ось «поведение не изменилось» дала `PASS=6 FAIL=0` на **обеих**
половинах при двух краснеющих соседних осях — то есть косметичность доказана, а набор не вакуумен.

## Когда правило срабатывает

- Writing integration test для bug fix (любая природа: parser, validator, executor, indexer)
- Writing integration test для new feature, который reintroduces a previously-fixed scenario
- Writing acceptance test после code-reviewer flag'нул "test doesn't exercise the regression"

НЕ применяется к:
- Unit tests, где input/output контракт явный (failing input → failing output detector)
- Test для new feature без regression history — здесь нечего «revert»

## Required workflow

```bash
# Step 1: Verify test fails without fix
# Fix ещё НЕ закоммичен (изменения в working tree):
# ⛤ Нужно только БАЗОВОЕ СОДЕРЖИМОЕ файла ⇒ `git show <пред-фиксный-sha>:<path> > /tmp/base` — stash не нужен ВОВСЕ (§A1).
#    Нужна копия ДЕРЕВА (мутировать нельзя) ⇒ §A10 ZERO-GIT-TOUCH. У обоих механизмов ниже — по 3+ рецидива с ущербом.
git stash push <production-file>   # OR temporarily revert the lines
<run the test>                     # Must fail
git stash pop                      # OR restore lines

# Fix УЖЕ закоммичен — stash НЕ работает (см. §A1 — stash-рецепт после commit):
git checkout origin/main -- <production-file>
<run the test>                     # Must fail
git checkout HEAD -- <production-file>

# Step 2: Verify test passes with fix
<run the test>                     # Must pass

# Step 3: Document in PR / commit
# "Empirically verified: FAILS pre-fix (N/N), PASSES post-fix (N/N)"
```

⛔ **ХАРНЕСС, ЧЕЙ `restore()` — `git checkout --`, ОБЯЗАН САМ ОТКАЗЫВАТЬСЯ НА ГРЯЗНОМ ДЕРЕВЕ.** §A2 («checkout-рецепт применим ТОЛЬКО после коммита») — правило для того, кто печатает команду. Но revert-verify быстро превращается в **скрипт**, и дальше его **переиспользуют**: написан он был на закоммиченном состоянии, где `checkout` восстанавливал точно, а запускается позже — поверх свежих незакоммиченных правок, которые молча уничтожает. Дисциплина тут не работает **по построению**: команду в этот момент никто не печатает.

- ✅ **Floor — три строки в начале харнесса, до первой мутации:**
  ```bash
  D=$(git -C "$WT" status --porcelain -- $FILES)
  [ -z "$D" ] || { echo "ABORT: незакоммиченные правки в $FILES — restore их СОТРЁТ:"; echo "$D"; exit 2; }
  ```
  Отдельный код возврата (`2`) обязателен: «не запускался» и «оси не различают» — разные исходы, и смешивать их нельзя.
- ⚠ **Симптом-tell ПОСЛЕ прогона, если гварда не было:** финальный «restored»-прогон даёт **не** контрольные числа (у меня `failed=1` при контроле `0/100`), либо `git status` показывает изменённым **не тот** набор файлов, что до старта. ⛔ Не читать это как «ось нестабильна» — это стёртые правки.
- ⛤ **Дешевле гварда только порядок: коммить ДО revert-verify.** Тогда `checkout` восстанавливает ровно то, что нужно, и харнесс безопасен по построению. Гвард нужен потому, что порядок соблюдается не всегда — а скрипт запускается всегда.

⛔ **Гвард выше POINT-IN-TIME, и его недостаточно: коллизия приходит ВНУТРЬ окна мутации.** Floor проверяет дерево **до** первой мутации — то есть отвечает на «была ли чужая правка, когда я стартовал». Между мутацией и restore проходят минуты прогона, и в это окно чужой актор (параллельная сессия, оркестратор, я сам) пишет в тот же файл. На старте было чисто, гвард промолчал, а restore всё равно уничтожил работу.

- ⛔ **Байтовый restore «из памяти» вместо `git checkout` эту дыру НЕ закрывает** — он тоже перезаписывает файл целиком. Разница только в том, к какому состоянию откатывает; чужая правка гибнет одинаково.
- ✅ **Floor: запомни sha256 ТОГО, ЧТО ТЫ НАПИСАЛ, и сверь ПЕРЕД restore.** Не совпало ⇒ писал не ты ⇒ ⛔ **не восстанавливать**: отложить текущее содержимое (`<file>.concurrent`) и упасть громко.
  ```python
  SRC.write_text(mutant); mine = sha(SRC)          # ← что написал Я
  run()
  if sha(SRC) != mine:                              # ← кто-то писал в окно
      shutil.copy(SRC, str(SRC) + ".concurrent")
      sys.exit("⛔ CONCURRENT WRITE: чужая правка сохранена, restore НЕ выполнен")
  SRC.write_text(original)
  ```
- ⚠ **Симптом-tell у ПОСТРАДАВШЕГО:** твоя правка «исчезла», `git status` чист, mtime файла — момент чужого restore. ⛔ Не читать как «Edit не применился»: он применился и был снесён.
- ⛤ **Обязанность симметрична и лежит на ОБОИХ.** Пишущий в общий worktree, где кто-то может гонять мутанты, обязан **сказать об этом** (иначе харнесс не знает, что теперь дерево грязное); владелец харнесса обязан **проверить перед restore**. Ни одна половина по отдельности класс не закрывает.
- **Empirical 2026-08-18** (PR #4078): раунд-2 ревьюер гонял permutation-харнесс в том же worktree; я правил комментарий внутри его окна. Его teardown (`git checkout HEAD -- <file>`) снёс правку; гвард на старте был удовлетворён. Обнаружено им же и честно отрапортовано, но правку пришлось накладывать заново.

## Common false-positive shapes

| Symptom | Underlying cause | Fix |
|---|---|---|
| Test passes both ways, assertion looks tight | Shape/contract mismatch — fixture doesn't trigger the code path | Inspect emitted triples / API calls; mirror production shape exactly |
| ⛔ Ось ИЗОЛЯЦИИ («предмет не тронул живой X») краснеет, а предмет исправен — и краснеет НЕ каждый прогон | Дискриминатор — СНИМОК общего ресурса до/после (манифест `.md`, `shasum` журнала, mtime каталога состояния). В общий ресурс пишут ТРЕТЬИ ЛИЦА (живой демон, репликация, соседний бот), и их запись, попавшая в окно прогона, читается как утечка изоляции. ⛤ Отличать от строки «КОНТРОЛЬ красный сразу после правки» ниже: там третье лицо тронуло ПРЕДМЕТ/ХАРНЕСС (код), здесь — ПРЕДМЕТ НАБЛЮДЕНИЯ самой оси | Ось обязана **атрибутировать АВТОРА**, а не фиксировать факт изменения: у прогона есть уникальный маркер (nonce вопроса, свои uid), и запись, им порождённая, его содержит ⇒ `mine` / `foreign`, красным считать только `mine`. ⛤ Границу назвать в коде: удаление маркера не оставляет ⇒ считается своим безусловно (ошибка в громкую сторону). ⚠ Вероятность считается, а не оценивается: `частота чужих записей × длительность прогона` (замер 2026-09-07: 99 записей/сутки × 310 с ⇒ треть прогонов). ⛔ Не «ослабить ось» и не «мерить реже» — оба снимают защиту. ✅ Если маркера нет по построению (предмет — чужой журнал), судить ИНВАРИАНТ («путь не боевой»), а не снимок |
| ⛔ Ось зелена под мутантом, который её предмет ЗАВЕДОМО ломает; предикат — `grep -q '<маркер>'` по ВСЕМУ выводу предмета | Маркер встречается и в СОСЕДНЕЙ строке того же вывода — той, что печатается ВСЕГДА (справка о смежном механизме, подсказка «вернуть», статус соседа) ⇒ вердикт берётся из неё, а не из статусной строки, и ось сравнивает предмет с КОНСТАНТОЙ | Судить по ОПРЕДЕЛЁННОЙ строке (`head -1` для статусной), а не по вхождению. ⚠ Tell ловится ДО прогона: маркер вердикта — общеупотребительный символ (эмодзи-статус, `OK`, `✅`), а вывод предмета многострочный. ⛤ Обнаруживается ТОЛЬКО мутантом: контроль зелен в обе стороны |
| Test passes pre-fix, fails post-fix | Test asserts buggy behaviour; the «fix» is correct but test codifies old bug | Update assertion to expected post-fix behaviour. ⛔ **И спроси, ПОЧЕМУ он был зелёным** — почти всегда он проверял НЕ ТО поле: ассерт стоял на признаке, который дефект не менял, а поле, где дефект жил, не проверялось ВООБЩЕ. ⇒ обновляя, **усиль**: допиши ось на то самое поле, иначе набор снова не поймает свой предмет. ⚠ Tell: ассерт называет ТИП/ФАКТ («это minus», «вернулось число»), а дефект — в ЗНАЧЕНИИ/ОПЕРАНДЕ |
| ⛔ Ось краснеет ПОСЛЕ фикса, хотя её ассерт ВЕРЕН и стоит на ТОМ САМОМ поле | Фикстура нереалистична, а прод **ОТБРАСЫВАЛ** значение, которое эту нереалистичность обнажает: пока возврат игнорируется (`f x` вместо `if f x`), любая статическая фикстура проходит. Фикс начинает значение ПОТРЕБЛЯТЬ ⇒ та же фикстура становится законным «отказом». ⛤ Отличать от строки выше: там ассерт кодифицировал баг, здесь ассерт верен — **дефект прода МАСКИРОВАЛ дефект фикстуры** | ⛤ **Предсказывать ДО отгрузки, а не реагировать после:** прогнать КАЖДУЮ существующую фикстуру через ново-потребляемый предикат и посчитать, сколько дают «отказ» — это и есть список осей, которые покраснеют. Он **часть работы**, а не scope drift: фикс не может лечь зелёным иначе. ⚠ Tell при чтении прода: есть вызов, чей результат не читается, и на нём стоят оси |
| ⛔ Фикс применён верно, а repro КАК БЫЛ красным, так и остался | Корень на слой глубже, чем ты решил; «применил и не помогло» само по себе НЕ говорит, где именно | ⛤ **Матрица проб по осям, а не гадание.** Взять предмет и варьировать ОДНУ ось за раз, пока не найдётся ближайшая пара «работает / не работает». Тогда корень зажат между ними и его не надо угадывать. Пример-форма: тот же оператор ВНЕ конструкции / внутри неё · внутренний аргумент КОНСТАНТА / внешняя переменная. ⚠ Пробы писать **в одном сьюте с `console.log`**, а не по одной — сравнимость даёт именно таблица |
| Test fails both ways | Fixture setup wrong (missing required props, validator skips file) | Trace via debug script: dump triples / log emission counts |
| ⛔ Ось зелена, мутант её НЕ краснит — а предикат ждёт **ТОЧНОЕ** значение (`rc == 2`), не отрицание | У предмета **ДВА разных отказа сводятся к одному коду**: «инструмент недостижим» и «прогон не помог» оба дают `rc=2 BROKEN` ⇒ ось удовлетворяется чужим отказом. §A38 сюда НЕ дотягивается — он про предикат-ОТРИЦАНИЕ (`rc != 0`), а здесь равенство, и оно ощущается точным | Грепать **СВОЙ текст** отказа (`grep -q '<инструмент> недостижим'`), а не общий маркер. ⚠ Tell до прогона: в скрипте `exit 2` встречается >1 раза (`grep -c 'exit 2' <предмет>`) ⇒ код возврата ось не различает ⛔ **И сам tell НЕПОЛОН: он считает `exit 2` в ПРЕДМЕТЕ, а путей к одной точке выхода бывает несколько по ВХОДУ** (валидный вход и мусорный аргумент дают тот же код) ⇒ счёт даст `1`, и tell промолчит. ✅ Второй tell, независимый от предмета: **все оси набора судят по ОДНОМУ наблюдаемому** ⇒ общий дефект фикстуры пройдёт набор целиком; хотя бы одна ось обязана судить по ДРУГОМУ (метка на диске, запись в журнале, побочный артефакт). _Empirical 2026-09-05: 3 оси хука зелены на фикстурах с литеральным `{VB}` в пути — `rc=2` приходит и для несуществующего пути; поймала ось, судившая по МЕТКЕ._ |
| ⛔ Мутант ПРИМЕНИЛСЯ (`cmp` показывает различие), а красных **НОЛЬ** | У предмета **ДВА механизма одного назначения на разных уровнях** (латч «уже сообщали» ↔ дедуп по подписи; гвард входа ↔ гвард выхода; кэш L1 ↔ L2), и ось упражняет **не тот**, который ты мутировал ⇒ ось корректна, неверен **ЯКОРЬ** | Грепнуть **назначение**, а не имя переменной (`grep -n 'latch\|LATCH'`); носителей >1 ⇒ выбрать тот, что стоит на пути фикстуры ЭТОЙ оси. ⚠ Tell: пустая дельта при успешном `cmp` — это НЕ «ось вакуумна» (вакуумная даёт [] и на мутанте, бьющем в ЕЁ механизм). ⛤ Побочно вскрывает ПРОБЕЛ: механизм, который ты мутировал, не упражняется ничем — оставить мутант с ожиданием `[]` как **детектор пробела**, он позеленеет ровно когда ось заведут |

## Anti-pattern

⛔ «Test passes → ship it» без revert-проверки. Особенно опасно для:
- Tests с synthetic vault fixtures (validator may silently skip files with missing required properties)
- Tests против graph databases (subject/predicate scope mismatch hides regression)
- Tests с complex JSON Schema validators (default to «no errors» if shape doesn't match scope)

<!-- Added by /session-retrospective 2026-08-14 — root: ТРИ вакуумные оси подряд за одну сессию, все на харнессах тиков автономных петель; каждая падала на СВОЁМ раннем выходе (узкое окно лога · нет снимка лимитов ⇒ burn-rate-unknown · нет живой tmux-сессии ⇒ worker-died), и каждая находилась только прогоном мутанта. -->
⛔ **Предмет — ДЛИННЫЙ СКРИПТ С МНОЖЕСТВОМ РАННИХ ВЫХОДОВ (тик петли, cron-джоб, диспетчер)? Перечисли ВСЕ выходы ВЫШЕ проверяемого блока и удовлетвори КАЖДЫЙ — иначе ось вакуумна по построению.**

Такой скрипт устроен как лестница гвардов: блокировка · темп расхода · память · занятый слот · cooldown. Твой предмет лежит **ниже** них, поэтому фикстура, не удовлетворившая любой один, останавливает исполнение **до** предмета — и ось зеленеет/краснеет по причине, не имеющей к нему отношения.

- ⚠ **Симптом-tell — ВЕРДИКТ НЕ ПО ТЕМЕ:** ось про закрытие слота печатает `burn-rate-unknown`, ось про уведомление — `worker-died`. Исход, называющий **чужой** гвард, = до предмета не дошли. ⛔ Не «ось краснеет, значит различает»: краснеть она может на гварде.
- ✅ **Floor: `grep -n 'finish\|exit\|return' <тик> | head -40` ДО написания фикстуры** — получаешь список выходов; для каждого спроси «моя фикстура его проходит?». Дёшево и однократно.
- ⛤ **Часть выходов удовлетворяется КОПИРОВАНИЕМ БОЕВОГО СОСТОЯНИЯ, а не синтетикой:** снимок лимитов (`cp rate-limits.json`), живая tmux-сессия-пустышка, непустой файл слота. Синтезировать их «правильно» дороже, чем скопировать то, что уже лежит рядом.
- ⛔ **Мутант ЭТО НЕ ЛОВИТ.** Мутант проверяет, различает ли ось предмет; вакуумная ось не доходит до предмета и краснеет на мутанте **тоже** — просто по другой причине. Единственный детектор — **прочитать исход**, а не факт красноты.

⛔ **ВЫБОРКА обязана совпадать с ОБЛАСТЬЮ ДЕЙСТВИЯ механизма — иначе журнал врёт В ОБЕ СТОРОНЫ**

- ⛔ **Вакуумное ЗЕЛЁНОЕ:** «N из N в проде после фикса» не доказывает ничего, если в окне не исполнялась **исправленная ветвь** — на успешном пути обе ревизии печатают побайтно одно и то же, и метрика не может покраснеть (`self-satisfying-metric-weak-verifier`).
- ✅ **Дискриминатор — счёт ПРЕДВЕСТНИКА ветви в том же окне** (строка, которую она логирует **до** отказа). Ноль ⇒ ветвь не исполнялась ⇒ прод о фиксе молчит. Прод доказывает, что ветвь **жива и в агрегате не нема**; **различимость** — только флип двух ревизий (§A51). ⛔ Не взаимозаменяемы.
- ⛔ **Ложное КРАСНОЕ:** отсекай строки **старше самого механизма** — до его появления они нарушают инвариант ПО ПОСТРОЕНИЮ. Возраст брать `git log -S '<маркер>' -- <файл>`, не по памяти.
- ⚠ **Tell:** «немых» больше, чем называл предыдущий этап ⇒ проверь ГРАНИЦЫ ОКНА, а не предмет.
