# req-first SDD: CI binding mechanics + local-suite discipline (exocortex)

Two CI gotchas that recur on **every** req-first SDD feature in `kitelev/exocortex` (RFC 0003). Both empirically hit on PR #3793 (dn-toggles, 2026-06-28).

## 1. `requirements-trace` clones the reqs-repo REMOTE HEAD — not the exocortex submodule pointer

The required `requirements-trace` CI job does `git clone --depth 1 https://github.com/kitelev/exoas-exo-reqs.git "$RUNNER_TEMP/reqs/..."` (+ exoas-ems-reqs) and audits `--reqs "$RUNNER_TEMP/reqs" --tests .`. It does **NOT** read `packages/exoas-exo-reqs` (the exocortex submodule pointer).

**Consequences (the actionable part):**
- A `@req:<uid>` tag in a test file resolves (not "dangling") **iff the req asset is pushed to the `exoas-exo-reqs` REMOTE main** — regardless of whether the exocortex submodule pointer is bumped. ⛤ You do **NOT** need to bump the exocortex `packages/exoas-exo-reqs` pointer for the binding to resolve. Just `exosync push` the req to the remote.
- The audit's `DEFAULT_TEST_GLOBS` = `**/*.test.ts|tsx`, `**/*.spec.ts|tsx` over `--tests .` (repo root) → any standard test path (`packages/core/tests/**`, `packages/obsidian-plugin/tests/**`) is scanned. A `@req` tag anywhere in test content (incl. file-header comments) counts; convention puts it in the `it()`/`test()` name.
- A `@req` tag under `tests/e2e/eka-gui/` = live-UI evidence; a tag in **any other** test = a standard automated binding (satisfies Component/Unit bindingClass — no live-UI evidence needed).

**Active-gate ordering (HARD — flip Active strictly AFTER the binding is in main):** the BLOCKING active-gate (required-14) enforces that every **active** req carries ≥1 binding. So:
1. Merge the PR carrying the `@req:<uid>` tags into exocortex **main** first.
2. THEN flip the req `proposed→active` on the `exoas-exo-reqs` remote (`exosync push`).
⛔ Flipping Active **before** the tags are in main → the next exocortex CI run (ANY PR) clones the remote, sees the active req with no binding → active-gate RED → blocks/skips releases for **everyone**. A `proposed` req with no binding is vacuous (safe); an `active` one without a binding reds the gate.

⛤ **2.5. ПРЕД-ФЛИП: симулируй флип на КЛОНЕ и прогони НАСТОЯЩИЙ аудит — до мутации общего remote.** Порядок выше говорит «когда», §3 — «чем доказать **после**». Между ними отсутствует дешёвая превентивная проверка, а асимметрия цены требует именно её: ошибочный флип краснит `requirements-trace` на **каждом** PR репозитория, откат — ещё один push в общий remote.

```bash
mkdir -p /tmp/reqs-audit && cd /tmp/reqs-audit
for R in exoas-exo-reqs exoas-ems-reqs; do gh repo clone kitelev/$R -- --depth 1 -q; done
# 1) применить флип ТОЛЬКО в клоне   2) прогнать ТОТ ЖЕ вызов, что и CI (взять из ci.yml, не по памяти)
npx tsx <repo>/packages/req-audit/src/cli.ts --reqs /tmp/reqs-audit --tests <repo> \
  --gate soft --output json --expect "exoas-exo-reqs,exoas-ems-reqs"
```

- ✅ **Два дискриминатора, оба обязательны:** `activeTotal` вырос **ровно на 1** (флип увиден) **И** `activeViolations == 0`, а твой uid **отсутствует** в `orphans`/`dangling`. ⛔ Один `activeViolations: 0` недостаточен — он же будет нулём, если флип в клон не доехал вовсе (тождественно-зелёный вход, `self-satisfying-metric-weak-verifier`).
- ⛤ **Строго сильнее грепа `@req:<uid>` по `origin/main`** (тот floor — в `/feature-sdd`): греп доказывает **наличие токена**, аудит — что он **резолвится как биндинг**. Между ними живут отказы, которые греп пропускает: усечённый uid, req вне объявленного `--expect`-набора, неверный `bindingClass`, битый wikilink статуса.
- ⚠ **Вызов брать ИЗ `ci.yml`, а не по памяти:** верб мигрирует (`exocortex requirements audit` → `packages/req-audit`), и «unknown command» под `2>/dev/null` превращается в пустой JSON, читаемый как «0 нарушений» (`bash-loop-eval-pitfalls` Г1×Г8).
- ⛤ **§3 этим НЕ отменяется:** предполётный прогон судит по клону, пост-верификация — по живому CI. Первый дешёв и предотвращает; вторая авторитетна и подтверждает.

⛤ **3. VERIFYING the flip needs a run that STARTED AFTER it — the merge run cannot prove anything.** The ordering above is necessary but not sufficient: you still owe evidence that the gate is green *with the req Active*. The obvious source — `requirements-trace: success` on the merge run — is **worthless for this**, because `requirements-trace` **clones the reqs-remote at job start** (§1), so a job that began before your flip evaluated the *pre-flip* corpus. Its green says «the req was still `approved` and therefore ungated», not «the binding holds».
- ⚠ **The trap is that it looks like proof**: same repo, same check name, same commit, green — and the timestamps differ by a couple of minutes, which nobody reads.
- ✅ **Floor — compare two timestamps, then dispatch if needed:**
  ```bash
  gh api "repos/kitelev/exocortex/commits/<merge-sha>/check-runs" \
    --jq '.check_runs[]|select(.name=="requirements-trace")|"\(.started_at) \(.conclusion)"'
  # started_at EARLIER than the flip ⇒ proves nothing → force a fresh evaluation:
  gh workflow run ci.yml --repo kitelev/exocortex --ref main
  ```
  Then read `requirements-trace` off **that** run and confirm its `started_at` is later than the flip. Authoritative, ~1 CI cycle.
## 2. Changing `packages/core/src/**` → run the FULL core suite locally before push

`test-coverage-exocortex` runs the **full** `packages/core/jest.config.js` (TF-gate dropped the old allowlist — every `packages/core/tests/**` suite is gated). But husky's lint-staged safety net does **not** reliably catch a broken EXISTING test of a changed core file:

- lint-staged runs `jest --findRelatedTests --config packages/obsidian-plugin/jest.config.js` on changed `packages/!(cli)/src/**`. For a `packages/core/src/*.ts` change, `--findRelatedTests` (under the obsidian-plugin rootDir) did **not** map to the sibling `packages/core/tests/.../*.test.ts` → the existing test was never run pre-commit → the commit succeeded → only CI `test-coverage-exocortex` caught the RED.
- Empirical (PR #3793): added `AssetClass.ACTION` enum → the pre-existing **brittle count-assertion** `AssetClass.test.ts "should have exactly 24 constants"` broke (24→25). Ran only the NEW test files locally, not the existing `AssetClass.test.ts`. Cost: 1 CI iteration (~8 min) + 1 fix commit. Self-caught pre-merge via the CI watcher.

**Floor:** when a change touches `packages/core/src/**` (esp. enums/constants/shared types with existing tests), run the affected package suite locally before push:
```
node ./node_modules/jest/bin/jest.js --config packages/core/jest.config.js --runInBand <changed-dir-or-file-glob>
```
ideally the directory of the changed file (catches its sibling `*.test.ts`), or the full config if the change is broad. Don't trust husky `--findRelatedTests` to cover cross-package core src→core test. Sibling: count-assertion tests (`"exactly N constants/items"`) are brittle by design (the `check-test-antipatterns` ratchet's spirit) — any additive enum/constant change must update them.

## 3. `req__Requirement_verifiedBy`/`_implementedBy` frontmatter ≠ the CI @req-binding — an "open-requirement" detector by frontmatter measures MODEL-traceability, not test coverage
The **CI active-gate** (`requirements-trace`) binds a req to a test by grepping the literal `@req:<uid>` token in **test-file content** (§1). This is a **separate channel** from the req asset's own frontmatter properties `req__Requirement_verifiedBy` / `req__Requirement_implementedBy` (graph edges → test asset / PR). The two are **not auto-synced**: a req can be **Active** (so its CI @req-binding exists in code) while its `verifiedBy`/`implementedBy` **frontmatter is empty**.

- **Consequence for a KAOS-style "open-requirement" / completeness detector** (active req lacking `implementedBy` ∧ `verifiedBy`): it measures **model/graph-traceability completeness**, NOT test coverage. An "open" req by this detector likely still has a CI test-binding in code — the frontmatter edge is just unpopulated. ⛔ Do NOT read "38 open-active reqs" as "38 untested requirements".
## 4. A deliverable for which NO faithful `@req` binding can EXIST → keep the req `approved`, never flip Active (there is no vault-data binding tier)
§1-§3 assume a binding **exists but is late / malformed / unsynced**. A distinct case: the
deliverable is **pure vault-data in an assetspace that `exocortex` does not pin as a submodule**
(it pins only `exoas-exo`, `exoas-exocmd`, `exoas-exo-reqs`). Then **no faithful binding can be
written at all** — a jest test would have to hand-author its own fixture TBox and would pass
whether or not the real definitions shipped (**false-positive coverage**, `test-fixture-realism`).

- **Verified mechanism (`requirements-audit.ts`, read on origin/main):** an `active` req is a
  hard `activeViolation` unless `occByUid.has(uid)` (a literal `@req:` token in a test) **or**
  `isManuallyVerified(r)` (i.e. `bindingClasses` includes `ui-acceptance` **and** it has a
  GUI-runner binding or a resolving committed evidence attestation). There is **no tier** for
  "verified by assetspace CI + CLI oracle". `req__RequirementBindingClass` offers exactly
  unit / component / integration / e2e / gui-bdd / ui-acceptance — enumerated 2026-07-30.
- ⇒ **Floor: leave the req `approved`.** A `proposed`/`approved` req with no binding is
  **vacuous and safe**; an `active` one is a repo-wide block. Record the reason IN the req body
  (verification surface = the assetspace `assetspace-ci.yml` SHACL gate + a CLI oracle), so a
  later reader doesn't "helpfully" flip it. ⛔ Do NOT mis-tag it `ui-acceptance` to slip past the
  gate — that tier demands GUI-runner/evidence and is a lie for a TBox-data change.
- ⛤ **The CLI property-name guard is the executable RED/GREEN oracle for a new TBox property
  def** (reqs `40a9a81b` create / `c616a289` set-property, v16.189.0+): before the def exists,
  `set-property <asset> --property <new__Name> --value x --dry-run` exits **2** with
  `UnknownPropertyError` (+ fuzzy suggestions); after it exists, exit **0** with a preview.
  Two independent names ⇒ two independent axes ⇒ non-vacuous, and `--dry-run` mutates nothing.
  This is a genuine revert-verify for a data-only deliverable — use it instead of inventing a
  code test.

## Когда правило срабатывает

- Any req-first SDD feature in `kitelev/exocortex` (binding a `@req:<uid>` test tag + flipping the req Active).
- Any change to `packages/core/src/**` with pre-existing tests.
- Any req whose deliverable is **vault-data only** (TBox defs, exocmd assets, layouts) — check §4 before even considering an Active flip.
