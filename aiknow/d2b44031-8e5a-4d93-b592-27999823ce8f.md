# Bash SIGKILL pattern: chained tmux send-keys to ccgram at child spawn

## Принцип

При chained tmux operations targeting ccgram pool (multiple `send-keys` + `sleep` + `capture-pane` + `kill-session` в одном Bash invocation) — **observed twice ending in Bash subprocess SIGKILL** (exit 137) at the moment of script completion. Exact root cause не verified, но pattern достаточно стабильный чтобы заслуживать defensive mitigation.

## Когда правило срабатывает

- Orchestrator spawn'ит child через `cs` alias (ccgram routing)
- Bash invocation содержит ≥3 `tmux send-keys` + ≥1 `sleep` (cumulative ≥3s) + `capture-pane`
- Cleanup chain включает `tmux kill-session ... && echo ...` в конце
- Parent session уже долго работает (uptime ≥ 1h) или после Phase-marathon

## Observed pattern (2 incidents, exact signature)

```bash
# Both deaths followed this exact script shape:
tmux send-keys -t "ccgram:@<N>" "/rename [...]"
sleep 1
tmux send-keys -t "ccgram:@<N>" Enter
sleep 2
tmux send-keys -t "ccgram:@<N>" "Выполни под ключ <path>"
sleep 1
tmux send-keys -t "ccgram:@<N>" Enter
sleep 5
echo "=== ccgram:@<N> capture ==="
tmux capture-pane -t "ccgram:@<N>" -p | tail -15
tmux kill-session -t "$SESSION2" 2>/dev/null && echo "orphan2 killed"
# ↑ Returns exit 137 — Bash subprocess SIGKILL'd at near-completion
```

**Tool result:** `Error: Exit code 137` с complete output preceding (including final `orphan2 killed` echo). Bash ran nearly full expected runtime (9-10s of 9s expected), then was killed.

**Parent claude TUI:** dies shortly after, lifecycle hook fires `EXITED rc=1`.

## Hypotheses (root cause не verified)

1. **macOS Jetsam memory pressure** — fork-heavy operation peaks RSS, kernel kills process tree at peak. Kernel logs не accessible by default — `log show --predicate jetsam` returned empty для obоих death windows.
2. **Process group / parent termination cascade** — claude TUI itself killed first, propagating to bash subprocess. Why claude TUI dies — unknown.
3. **macOS sleep cycle interaction** — Death 2 (03:15:55) после Claude.app NoIdleSleepAssertion expired (~02:51) — system may have entered short sleep state mid-operation.

Strongest evidence-based candidate: **Jetsam** — но без proof.

## Defensive mitigations (apply ALL when possible)

### 1. Don't chain many tmux operations в одном Bash call

⛔ Anti-pattern:
```bash
tmux send-keys ... ; sleep 1 ; tmux send-keys ... ; sleep 5 ; tmux capture ... ; tmux kill-session ...
```

✅ Better:
```bash
# Multiple separate Bash tool calls — each is its own subprocess, no compound RSS spike
# Tool call 1: tmux send-keys rename
# Tool call 2: tmux send-keys prompt content
# Tool call 3: tmux capture + verify
# Tool call 4 (optional): cleanup kill-session if needed
```

Trade-off: more tool round-trips, но каждая Bash invocation has bounded scope. Если одна умирает, others не аффектят.

### 2. Avoid ccgram pool для child spawn from orchestrator

ccgram pool — shared resource, multiple tenants. Pool itself crashed once already (00:37, Death 1 cascade). Spawn'ить новый child прямо в pool увеличивает per-tenant pressure.

✅ Better: standalone tmux per child (per `[[6dddc3bf|two-session split mitigation]]`).

### 3. Pre-flight memory pressure check

Перед heavy tmux orchestration:
```bash
# Check free memory (rough proxy for Jetsam risk)
vm_stat | awk '/Pages free/{print $3}' | tr -d '.'
# If <50000 (≈200 MB) — defer operation, reduce parallelism
```

### 4. Reduce sleep+capture+kill cleanup chains at script end

Final `&& echo "orphan2 killed"` cleanup is cosmetic. If concern про orphan tmux session — delete it в a separate Bash call минуту later, не at end of spawn script.

### 5. Verify by orientation health check anyway (per spawn-issue-standalone update)

Even if Bash subprocess не killed, child might fail orientation. Apply 90s post-spawn health check (per skill update 2026-06-03).

## Запреты

- ⛔ **НЕ retry same operation сразу после Exit 137.** Pattern repeats — if mechanism is Jetsam-like, system pressure remains.
- ⛔ **НЕ assume root cause = API rate-limit.** Both deaths показали same signature regardless of quota state.
- ⛔ **НЕ rely на отсутствие kernel log evidence.** macOS doesn't expose Jetsam events в default log streams; absence is not negative proof.
