# lint-staged worktree commit corruption под нагрузкой → коммить через fresh clone (НЕ --no-verify)

## Симптом

Коммит в exocortex-worktree через husky `pre-commit` → `lint-staged` **детерминированно** падает, оставляя индекс worktree corrupt:

- `[FAILED] fatal: unable to read <objSHA>` в шаге lint-staged «Applying modifications from tasks» / «Failed to get staged files» (это backup-stash объект lint-staged, который потерян).
- `error: invalid object 100644 <varyingSHA> for '.gitmodules'` + `error: Error building trees` от финального `git commit` (фантомный `.gitmodules` blob в индексе → `git write-tree` падает).
- Часто `✅ All pre-commit checks passed!` ПЕЧАТАЕТСЯ (eslint/jest/archgate реально проходят) — падает именно git-plumbing lint-staged-стэша, не качество.
- Фантомный `.gitmodules` SHA **меняется** run-to-run, хотя файл на диске константный (нет clean/smudge-фильтра) → объектные записи теряются.

## Root cause

`git stash` (неявный backup lint-staged) пишет объекты в **shared object DB** (один `.git/objects` на все worktree одной репы). Под нагрузкой — много node/claude-процессов делят DB + диск ~98% — свежесозданные loose-объекты lint-staged **теряются/портятся до чтения обратно** (concurrent gc/repack ИЛИ near-full-disk non-durable writes). Результат: индекс worktree ссылается на несуществующий blob → каждый commit падает. `git write-tree`/`git stash create` на ЧИСТОМ индексе работают — портит именно многошаговый lint-staged-stash под contention.

Родственно (но шире) `fab02fa5` «Никаких git stash в multi-worktree setup»: там — cross-worktree foreign-stash pollution (`git stash pop` цепляет чужой stash@{0}). Здесь — потеря/порча СОБСТВЕННОГО backup-объекта lint-staged под нагрузкой, даже когда foreign-stash не причина (проверено: foreign `pre-migration-branch-switch` stash не трогал `.gitmodules`).

## Что делать (ranked)

1. **Коммить через FRESH CLONE** (отдельный object DB, нет shared-stash contention). `git clone <repo> /tmp/<x> && cd /tmp/<x> && git checkout -b <branch> && <скопировать изменённые файлы> && git add <pathspec> && git commit` → hook отрабатывает чисто. **НЕ bypass** — pre-commit реально прогоняется. После — `git push origin <branch>`. (Так оркестратор разблокировал PR #3609.)
2. **Recover corrupt worktree index** (если нужен сам worktree): `rm -f <gitdir>/index && git read-tree HEAD && git checkout-index -f -- .gitmodules && git update-index --refresh` → `git status` снова работает; рабочие файлы на диске целы. Но СЛЕДУЮЩИЙ commit через lint-staged под той же нагрузкой снова портит — recover не лечит причину, fresh clone лечит.
3. **Освободить ресурсы** (диск + RAM) и ретраить в тихом окне — помогает только если причина чисто транзиентная contention; при ~98% диске часто НЕ хватает (в инциденте disk 98%→92%, 36Gi свободно — всё равно падало).

## ⛔ Запреты

- ⛔ `--no-verify` / `HUSKY=0` — hard-floor (память + global rule). Даже при verified-green gates НЕ обходить hook. Fresh-clone — легитимная замена (hook отрабатывает), bypass — нет.
- ⛤ Не трогать `gc.auto` в repo config (hard-floor «не модифицируй git config»).
- ⛤ Не дропать чужой stash из shared-стека (другая сессия) без координации.

## Escalate-faster эвристика (главный процесс-урок инцидента)

Когда commit-hook **детерминированно** корраптит индекс **2-3 раза подряд** при **всех gates green** (typecheck/lint/tests/build verified независимо) — это **инфраструктурный** блокер, НЕ качество. **Не уходить в длинный диагностический цикл** (в инциденте — 8 попыток + ~десятки Bash-вызовов). После 2-3 детерминированных падений → сразу **fresh-clone commit** ИЛИ эскалация оркестратору. Стоимость долгого диагноза >> стоимость fresh-clone.

## Когда правило срабатывает

- Commit в `exocortex-development/worktrees/*` через husky/lint-staged на машине с многими параллельными claude/node-сессиями И/ИЛИ диском ≥95%.
- Симптом `unable to read <obj>` / `invalid object ... for '.gitmodules'` / `Error building trees` в pre-commit.
- vault-репы (vault-2025/vault-exodev) husky НЕ имеют → проблема специфична для exocortex-repo; vault-коммиты идут штатно.
