# Obsidian plugin update — только через BRAT, не manual file copy

## Правило

Для обновления Obsidian plugin в vault для verification (visual smoke, regression check, dogfood) — **использовать BRAT**, не manual copy `main.js`.

### Workflow

1. Merge PR → triggers Auto Release workflow (GitHub Actions auto-bump version + publish release)
2. В Obsidian: `Cmd+P` → `BRAT: Check for updates to all beta plugins`
3. BRAT fetches new release from GitHub, updates manifest.json + main.js + styles.css consistent
4. Если нужен hard restart: `Cmd+P` → `Reload app without saving` (НЕ Cmd+R — Cmd+R reloads renderer only, plugin lifecycle в main process, см. aiKnow `2d7dd8c1-...`)
5. **Verify new version landed** — ⛔ необходимо, но НЕ достаточно: версия может быть от ЧУЖОГО intermediate-релиза (при rapid releases), поэтому обязателен ещё **bundle-grep уникального символа** (§Addendum 2026-06-07):
   ```bash
   cat /Users/kitelev/vaults/vault-my/.obsidian/plugins/exocortex/manifest.json | python3 -c "import json, sys; print(f'Version: {json.load(sys.stdin)[\"version\"]}')"
   ```
   Если version mismatched (старая) → BRAT update не applied / reload не сработал. Не делать UI smoke на этом state — это будет проверять старый код. Re-trigger BRAT check + reload, или ask user.

## Addendum (2026-06-07) — release-bundle-verify + DevTools-eval для smoke

### Verify BUNDLE CONTENT, не только version/tag
При rapid releases (несколько PR подряд → v16.71.1/.2/.3…) Monitor/проверка на «tag > baseline» **может поймать ЧУЖОЙ intermediate release** (из параллельного merge), опубликованный за секунды до твоего target. Manifest version будет «новее baseline», но НЕ содержать твою фичу.

**Mandatory перед smoke:** grep сам бандл на expected symbol, не доверяй только manifest version:
```bash
MJS=/Users/kitelev/vaults/vault-my/.obsidian/plugins/exocortex/main.js
grep -c '"<expected-command-id-or-symbol>"' "$MJS"   # должен быть >0
grep -c '<symbol-that-should-be-GONE>' "$MJS"          # должен быть 0
```
При rapid releases — дождись **точного target-tag** из child COMPLETED ping (не первого `>baseline`), затем BRAT-update. Empirical: Phase 5 T2 потребовал re-BRAT (16.70.11 foreign → 16.71.0 target).

⛔ **Рецепт выше работает для СТРОКОВЫХ ЛИТЕРАЛОВ (command-id в кавычках), но НЕ для ИДЕНТИФИКАТОРОВ: esbuild переименовывает локальные функции, и грепать имя нельзя ни в ту, ни в другую сторону.** Литерал `"exocortex:archive"` бандлер сохраняет дословно — потому исходная форма с кавычками верна. Имя функции/переменной он минифицирует, и это даёт **два симметричных ложных вывода**:

| Наблюдение | Ложный вывод | Что на самом деле |
|---|---|---|
| нового символа **0 вхождений** | «фича не отгружена» | имя переименовано (`resolveKeyPath` → `S4`), код на месте |
| символ **есть, 1 вхождение** | «фича отгружена» | совпадение может принадлежать **ОДНОИМЁННОМУ чужому** символу |

- ✅ **Floor: грепать УНИКАЛЬНУЮ СИГНАТУРУ — форму кода, а не имя.** Минификация переименовывает идентификаторы, но **не меняет структуру**: последовательность операций, строковые литералы, регэкспы и порядок веток переживают сборку. Ищи связку, которую может дать только твоя правка:
  ```bash
  # пример: новая ветка «первый элемент массива → wikilink → резолвер» внутри обхода key-path
  python3 - <<'PY'
  import re; s=open("<path>/main.js",encoding="utf-8",errors="replace").read()
  hits=[m.start() for m in re.finditer(r'split\("\."\)', s)]      # структурный якорь
  print([i for i in hits if 'Array.isArray' in s[i:i+500]])       # + твоя новая ветка рядом
  PY
  ```
- ⛔ **Совпадение по имени метода класса — НЕ доказательство: проверь ТЕЛО.** Имена **методов** (в отличие от локальных функций) обычно переживают минификацию, поэтому `createMetadataResolver` в бандле найдётся — но найтись может и **сосед с похожей логикой**. Дискриминатор — деталь, различающая их: у меня `split("|")[0]` (мой срез алиаса, берёт ПЕРВЫЙ элемент) против `split("|").pop()` (чужой `resolvePropertyKey`, берёт ПОСЛЕДНИЙ). Я чуть не засчитал чужое окно за своё.
- ⚠ **Симптом-tell:** число вхождений `1` у символа, чьё имя **родовое** (`isWikilink`, `resolve`, `normalize`, `parse`). Родовое имя почти наверняка есть и у соседей ⇒ грепни его **без** своей правки (`git show origin/main~1:…` собранный бандл предыдущего релиза) и посмотри, было ли оно там ДО тебя.
- ⛤ **Дешёвая проверка «сигнатура достаточно уникальна»:** она обязана давать **ровно 1** совпадение. Больше одного (у меня `split("|")[0]` → 19, `Array.isArray`+`"[["` → 2) = сигнатура слишком общая, сужай до тех пор, пока не останется одно.

<!-- Added 2026-07-04 by /session-retrospective (child claude-3809-today) — root: release-watcher инвертировал ancestry-направление (`identical||behind` вместо `identical||ahead`) → false-positive RELEASE_OK на СТАРОМ теге. -->
⛤ **Инвертированная ancestry-грабля (2026-07-04, PR #3810 release-watch).** `gh api .../compare/<merge>...<tag> --jq .status` — направление коварно, легко перепутать оператор в watcher-скрипте:
- **`ahead`** = tag **впереди** merge (у tag есть коммиты, которых нет у merge) → merge **является предком** tag → **tag СОДЕРЖИТ merge** ✅ (released).
- **`identical`** = tag == merge ✅.
- **`behind`** = tag **позади** merge (у merge есть коммиты, которых нет у tag) → tag **СТАРШЕ** merge → **tag НЕ содержит merge** ❌ (это предыдущий релиз!).
- `diverged` — обе стороны разошлись, merge НЕ в tag ❌.

Правильное условие «релиз содержит мой merge» = **`status ∈ {identical, ahead}`**, НИКОГДА `behind`. Инцидент: первый release-watcher использовал `[ "$ST" = identical ] || [ "$ST" = behind ]` → на старом `v16.170.2` (`compare merge...v16.170.2 = behind`, т.к. тег предшествовал merge) выдал ложный RELEASE_OK. Self-caught (заметил «behind = tag старше»). Cost: 1 false-positive + переписанный watcher (~2 мин). Floor: в release-watcher ключевать ТОЛЬКО `identical|ahead` + доп. gate на **auto-release run conclusion=success** для merge-SHA (per `auto-release-gated-on-ci-workflow-conclusion`) — «latest tag появился» ≠ «мой merge в нём», особенно при back-to-back релизах.

### DevTools RESOLVER-eval — authoritative для inline-button visibility (без мутации vault)

Для проверки, появится ли **inline-кнопка** (homoiconic `exocmd__CommandBinding` → button) на инстансах класса/прототипа — `app.commands.listCommands()` НЕДОСТАТОЧЕН: status/context-bound команды (напр. «Mark Done», «Mark Done Post Factum») **inline-only, НЕ регистрируются в палитре** → `listCommands` для них возвращает `[]` (ложно-отрицательно). Inline-кнопки идут через отдельный pipeline (`findBindings` → `loadCommand` → precondition eval), не через `app.commands`.

**Read-only authoritative проверка** (плагин экспонирует `commandResolver` + `sparql` на `app.plugins.plugins.exocortex`):
```js
const cr=app.plugins.plugins.exocortex.commandResolver;
const cmd=await cr.loadCommand('<command-uid>');                              // null если команда не в store
const bs=await cr.findBindings(undefined,'<prototype-or-class-file-IRI>');    // биндинги для прототипа/класса
JSON.stringify({cmd:cmd&&cmd.name, prec:!!cmd?.precondition, grounding:!!cmd?.grounding, bindings:bs.length, mine:bs.filter(b=>JSON.stringify(b).includes('<command-uid>')).length})
```
`findBindings(assetClass?, prototypeIRI?, assetIRI?)` разворачивает `prototypeIRI` через `expandPrototypeChain` (транзитивная цепочка `exo__Asset_prototype`, v16.170.0+). Если `mine>=1` + `cmd`/`prec`/`grounding` truthy → цепочка visibility резолвится вживую → кнопка отрисуется, когда precondition пройдёт. **Никакой мутации vault** (в отличие от создания Doing-инстанса). Для визуального пиксель-подтверждения (нужен инстанс в целевом статусе) — только с явным mutation-aware подтверждением: disposable-инстанс → screenshot → удалить, БЕЗ push (per `gui-mutation-test-on-temp-vault`).

⛤ **CommandResolver discovery — по UID + rdf:type, БЕЗ path/isDefinedBy-фильтра** (verified origin/main 2026-07-05: `loadCommand` = `findSubjectByUID` + `rdf:type exocmd__Command`; `findBindings` = все `CommandBinding` по типу). Обновляет stale-эмпирику `migration-pre-verify-use-case` (2026-05-23 инцидент: тогда фильтр был по path-prefix `assetspaces/exocmd/` ИЛИ isDefinedBy `60967c6a` — с тех пор убран). Следствие: команда/биндинг в ЛЮБОМ смонтированном ассетспейсе (не только `exoas-exocmd`) находится по UID из биндинга — location-independent. Precondition висит на команде (`exocmd__Command_precondition`), а НЕ на биндинге (у `exocmd__CommandBinding` нет precondition-override — свойства: command/group/order/overrides/position/targetClass/targetPrototype/variant; `overrides` = capability-inheritance, не precondition) → чтобы варьировать precondition per-context, нужна ОТДЕЛЬНАЯ команда, не переопределение на биндинге.

## Запреты

- ⛔ **Не копировать `main.js` вручную** в `<vault>/.obsidian/plugins/<id>/`. Bypass'ит BRAT version tracking, manifest stays stale, partial reload state может maskировать bugs.
- ⛔ **Не полагаться на `Cmd+R`** для plugin reload — это renderer reload, не plugin lifecycle.
- ⛔ **Не toggle plugin через Settings UI** для reload — может work но не corresponds к user's real upgrade path (BRAT auto-update). Verification должна mirror что real users делают.

## Почему

BRAT (Beta Reviewer's Auto-update Tester) — стандартный pre-release distribution channel для Obsidian plugins. Real users получают updates через BRAT, не через manual file ops. Если verification идёт через manual copy:

- Manifest.json не sync'нут — version mismatch может скрыть compat issues
- BRAT lock-state не triggered — race conditions при concurrent reload missed
- User real workflow (BRAT check → restart) не verified
- Discoverable behavior (BRAT shows update notification) не tested

## Edge case — dev hot reload

Если plugin имеет dev hot-reload mechanism (например esbuild watch + plugin-side onFileChange handler) — это OK для local development iteration. НО для verification что reproduces user experience — ВСЕГДА через BRAT.

## Addendum 2026-07-12 — vault-DATA (exo__DisplayNameSpec) propagation ≠ plugin-CODE: spec-only изменения подхватываются БЕЗ reload (auto-rescan на metadataCache resolve)

BRAT/reload — механизм для plugin **КОДА** (main.js). Но гомоиконичные фичи всё чаще = чистые vault-**ДАННЫЕ** (`exo__DisplayNameSpec` ассеты), и они распространяются к живому плагину иначе:

- **Новый/изменённый vault-spec-файл на диске** (добавленный child-сессией, ExoSync-синком или Write) подхватывается **запущенным** плагином на следующем **metadataCache resolve** (`PrintNameRuleService.scanVault` пере-сканирует vault-спеки) — **БЕЗ полного reload**. Эмпирика 2026-07-12: child добавил `ems__Action ✅`-спеку (`80254619`) на диск ПОСЛЕ последнего reload; открытие Done-Action **без нового reload** сразу показало «✅ <label>». То же для триплет-спеки.
- **Следствие для pixel-visual vault-DATA фич:** сначала попробуй просто **открыть** целевой ассет (spec мог уже подхватиться) — reload делай только если не отрисовалось. `Reload app without saving` гарантирует re-scan (детерминированно), но для spec-only обычно избыточен.
- **Что реально требует BRAT/reload:** только смена plugin **КОДА** (новый релиз — движок/матчер/рендерер). Для чистой vault-DATA спеки версия плагина не меняется → BRAT не нужен, достаточно того, что файл на диске + metadataCache перечитал.
- ⚠ Не путать: `exosync-parity N/N in parity` НЕ значит «Obsidian уже видит spec» — parity про remote↔local диск, не про in-memory scan плагина. Если diск-файл есть, а рендер старый → нужен resolve/reload, не sync.
