# Unpinned CI tool (`npm install -g <tool>`) → silent version drift → repo-wide break; diagnose via publish-timeline vs run-times

## Принцип

A CI step that installs a global tool **without a version pin** — `npm install -g <tool>`, `pip install <tool>`, `go install <tool>@latest`, `curl … | sh`, `brew install`, unpinned GitHub Action `@main` — resolves **whatever is latest at run time**. When the upstream tool ships a breaking change (a tightened lint/security policy, a new default, a removed flag), **every CI run after the publish moment fails** — on code that didn't change and a PR author who caused nothing. The failing check is **required** → it blocks *all* PRs until someone pins or adapts. The signature is confusing: the **same base commit** passes on an earlier run and fails on a later one, because the two runs pulled **different tool versions**.

## Диагностический ключ (когда a required check fails on something you didn't touch)

1. **Confirm you didn't touch it** — the failing file/rule is one your diff doesn't include (`git diff --stat` has none of it; the offending import/config is already on `origin/main`).
2. **Same base commit passes elsewhere?** Check the **main-push** run of your PR's base SHA vs your **pull_request** run. If push passes and PR fails on the identical base → suspect version drift, not push-vs-PR semantics.
3. **Is the tool pinned?** `grep -nE 'npm install -g|pip install|go install|uses: .*@(main|master|v[0-9])' .github/workflows/*.yml`. A bare `npm install -g <tool>` (no `@version`) = unpinned = prime suspect.
4. **Timeline proof — the smoking gun:** `npm view <tool> time --json` (or the tool's release page). Compare the newest publish timestamp against the timestamps of the **passing** run and the **failing** run:
   - passing run ⟶ tool version = the one before the publish;
   - failing run ⟶ tool version = the freshly-published one.
   The `started_at` of each check-run: `gh api repos/<o>/<r>/commits/<sha>/check-runs -q '.check_runs[]|select(.name=="<job>")|.started_at'`.
5. If the failing run's time is **minutes after** a new tool publish → confirmed drift.

## Фикс (ranked)

1. **Pin to last-known-good, immediately** — `npm install -g <tool>@<good-version>`. Restores determinism, unblocks **all** PRs in one small ci.yml PR. ⛤ The pin PR **self-unblocks**: its own CI checks out the PR's ci.yml (with the pin) → runs the good version → passes. No chicken-egg, no admin-merge.
2. **Propagate the pin to in-flight PRs** — a PR opened *before* the pin still has the unpinned ci.yml → its check still fails. `gh api repos/<o>/<r>/pulls/<n>/update-branch -X PUT` (server-side merge of pinned main) so the PR inherits the pin → its check re-runs on the good version → green → merge normally.
3. **Deliberate upgrade as a follow-up issue** — adapt the repo to the new tool version's stricter policy (fix the rule files / config), then bump the pin. This is a *chosen* upgrade, not a surprise. Keep a pin afterward (never go back to bare `latest`).

## Запреты

- ⛔ Don't `rerun --failed` repeatedly hoping it clears — version drift is **deterministic**, not a flake (`gh-retry-limit`). A fresh re-run pulls the *same* broken latest.
- ⛔ Don't admin-merge your PR bypassing the broken required check as the *first* move — it leaves the tool broken for everyone else. Pin first (fixes the root cause repo-wide); admin-merge only if a pin is somehow impossible and the failure is provably unrelated (`pr-auto-merge-chicken-egg` Option B).
- ⛔ Don't "fix" it by editing the thing the tool now complains about **without understanding the tool change** — you may be adapting to a policy you could instead pin away from, at higher risk (the complaint is often about the repo's own valid config that an older tool accepted).
- ⛔ Don't blame your own PR / spin a child to "investigate a behavioral regression" when the failure is structural (tooling), not behavioral.

## ⛔ ЗЕРКАЛО того же класса: версия ЗАПИНЕНА в ДВУХ местах, а бампается в ОДНОМ — «manifest ↔ environment»

Тело правила про **отсутствие** пина. Зеркальный отказ — пин **есть**, и их два: один в манифесте (`package.json`), другой в описании окружения (тег контейнера, `node-version:`, образ, sdk-версия). Бампалка видит первый и не видит второй, потому что второй записан **инлайном в воркфлоу**, а не как зависимость.

⛤ Замер 2026-08-20 — **два экземпляра за один час**, разной формы отказа:

| пара | манифест | окружение | как проявилось |
|---|---|---|---|
| Playwright | `@playwright/test` 1.57 → 1.62 | `container.image: mcr.microsoft.com/playwright:v1.57.0-jammy` (**3** вхождения в `ci.yml`) | `test-component`: **322 failed**, все — `Executable doesn't exist at /ms-playwright/chromium_headless_shell-1234/…` |
| Node | `@types/node` 20 → 26 | `node-version: "22"` (8 воркфлоу), один на 20 | ⛔ **ничего**: CI зелёный, потому что он компилирует, а не исполняет. Окно «tsc принял → Node бросил `ReferenceError`» — предъявлено пробой: `new URLPattern(...)` (глобал Node 24) краснеет под типами 22 и чист под 26 |

- ⚠ **Формы отказа противоположны, и вторая опаснее.** Playwright падает громко и сразу (сотни красных с одной строкой). Типы **не падают вовсе** — расхождение уезжает в main под зелёным CI и ждёт первого вызова нового API. ⇒ «CI зелёный» **не является** проверкой этой оси там, где вторая поверхность — рантайм, а не бинарь.
- ✅ **Floor при бампе, который трогает инструмент с окружением: грепни ВТОРУЮ поверхность ДО мержа.** `git grep -n '<имя-инструмента>:v\?[0-9]' -- .github/workflows` и `grep -rhoE 'node-version:\s*\S+' .github/workflows/*.yml | sort | uniq -c`. Одна команда; она же сразу даёт **число** вхождений.
- ⛔ **Считать вхождения, а не «есть/нет».** Мой первый проход прочитал «два» из усечённого `grep … | head -20`, фактически было **три**. Поймал `assert n == 3` в скрипте правки — то есть спас гвард, а не внимательность (`self-satisfying-metric-weak-verifier` §`head` на перечислении).
- ✅ **Барьер против рецидива ставится там же, где уже стоят соседи.** Для типов — `ignore` на major в `.github/dependabot.yml` рядом с `obsidian`/`react`/`react-dom`, **с механизмом и условием снятия в комментарии**: «поднимать вместе с `node-version`». ⛔ Но комментарий — это **подпись, а не гейт**: он не покраснеет, если кто-то поднимет одну сторону. Механическая форма — archgate-правило «major(манифест) ≤ версия(окружение)» (issue `kitelev/exocortex#4162`).
- ⛤ **Дискриминатор, отделяющий этот класс от тела правила:** спроси не «запинен ли инструмент», а **«сколько мест объявляют его версию»**. Одно ⇒ читай тело (дрейф от отсутствия пина). Два и больше ⇒ этот раздел: дрейф от **частичного** бампа, и лечится он не пином, а синхронной правкой всех поверхностей.
