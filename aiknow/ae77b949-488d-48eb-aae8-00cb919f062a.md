# Homoiconic inline button not rendering → check for a MISSING CommandBinding FIRST (orphan command), before the precondition/converter

## Принцип

Инлайн-кнопка гомоиконичной команды (`exocmd__Command`) рендерится ТОЛЬКО если существует `exocmd__CommandBinding`, чей `exocmd__CommandBinding_command` указывает на команду И чей `targetClass`/`targetPrototype` матчит класс/прототип ассета. Путь рендера — `DynamicCommandButtonGroupBuilder.resolveVisibleCommands → resolveViaFullPath → CommandResolver.resolveForAssetMulti(...)` возвращает **только** команды, у которых ЕСТЬ подходящий binding; затем per-команда `PreconditionEvaluator.evaluate`. **Нет binding → команда никогда не попадает в набор → precondition даже не оценивается → кнопка не рендерится.**

⛤ **CLI `apply <cliName>` работает БЕЗ binding** — он резолвит команду напрямую по `cliName` через `loadCommand`, минуя bindings. Поэтому **«CLI работает / precondition passed» НЕ доказывает наличие binding** и НЕ доказывает, что кнопка отрендерится. Это ловушка: расхождение «CLI работает, кнопка нет» на первый взгляд выглядит как converter/precondition-баг (dual-IRI и т.п.), а на деле часто = **отсутствующий binding** (данные, не код).

⛔ **Создавая binding ЗЕРКАЛОМ СИБЛИНГА — не тиражируй `exocmd__CommandBinding_group`: поле МЁРТВО.** Снято RFC f1dc284a Phase 8; в `packages/*/src` его не читает **ни одна** строка (`CommandResolver.ts:1005` — комментарий «parser silently ignores»; прочитано на `origin/main` `6c0df739`), а секционирование кнопок идёт по `exocmd__Command_category`. ⇒ у вопроса «в какую группу класть» степеней свободы нет.

- ⚠ **Симптома-tell НЕТ по построению — его заменяет ЗАМЕР:** `_group` несут **84 из 88** живых биндингов (SPARQL по `CommandBinding_group`, 2026-09-07) ⇒ шанс взять чистый образец — 4.5 %. Образец учит мёртвому полю ПОЧТИ ВСЕГДА.
- ✅ **`exo__Asset_isDefinedBy` брать у КОМАНДЫ, а не у образца:** папка биндинга = папка его команды у **80 из 84** (замер тикета `61a72179`).

## Диагностический порядок (binding FIRST, потом precondition/converter)

Когда «кнопка X не рендерится, а CLI apply работает» — **сначала** проверь наличие binding (дёшево, авторитетно), и только если binding есть — копай в precondition/converter:

1. **Authoritative visibility-oracle** (лучший первый шаг) — CLI `resolve-buttons` (Issue #3833, «binding-match ∩ precondition-eval; strictly more complete than apply --dry-run»):
   ```bash
   npx -y @kitelev/exocortex-cli@latest resolve-buttons <vault-rel-path-to-asset> --vault <vault> --json
   ```
   - Команда в `visible` → binding есть + precondition true → кнопка рендерится (баг не здесь).
   - ⛤ **Зови с `--show-hidden` — тогда ответ ТРЁХЗНАЧНЫЙ и шаг 2 не нужен:** `visible` → кнопка будет · `hidden` → **биндинг матчит, precondition вернул false** · нет нигде → биндинга нет либо `targetClass` не матчит.
   - ⛔ **БЕЗ флага `hidden` пуст всегда, и тогда отсутствие в `visible` ДВУСМЫСЛЕННО** (binding нет ИЛИ precondition false) — различает только шаг 2 (SPARQL по биндингам). Проверено изоляцией одной переменной на CLI 16.215.0: тот же ассет без флага `hidden: 0`, с флагом `hidden: 29`. См. §КОРРЕКЦИЯ 2026-08-09.
   - ⛔ **Прежняя формулировка (до 2026-08-09) была ЛОЖНОЙ и вредной:** «отсутствует и в `visible`, и в `hidden` → binding НЕТ → создать binding». Это нормальное состояние ЛЮБОЙ загейченной команды ⇒ следуя ей, заводишь **дублирующий** binding поверх существующего.
2. **Orphan-command SPARQL** (подтверждает «binding нет вообще»):
   ```bash
   npx ...cli query --vault <v> "SELECT ?s ?p WHERE { ?s ?p ?o . FILTER(CONTAINS(STR(?o),'<command-uid>')) }" --format json
   ```
   Если единственные ссылки на команду — её собственные `Asset_uid`/`Asset_filename` self-triples (никакой `CommandBinding_command` → команда) → команда **orphan** (ни один binding не ссылается).
3. ⛤ **Проверить САМ предикат ДО отгрузки — но `exocortex-cli query` НЕ исполняет `ASK`** (`❌ Error: Unknown operation type: ask`; поддержан только SELECT). Переписать ASK в SELECT, **заякорённый на сам таргет**, и читать число строк как булево:
   ```sparql
   SELECT ?u WHERE { <obsidian://vault/<путь>.md> exo:Asset_uid ?u .
                     <тело ASK как последовательность FILTER/EXISTS> }
   ```
   1 строка = ASK true, 0 = false. ⛤ **Якорь `Asset_uid` — не украшение, а канарейка**: у предиката ожидаемый ответ часто «0 строк», и такой тест **тождественно зелен** при сломанном запросе (опечатка в префиксе, необъявленный namespace, dual-IRI). Прогон того же SELECT **без** конъюнктов обязан дать 1 — иначе ноль означает «запрос мёртв», а не «предикат ложен» (`self-satisfying-metric-weak-verifier`).
4. **Сверься с sibling-командами** того же семейства: у работающих кнопок-сиблингов binding ЕСТЬ (`SELECT ?b WHERE { ?b exocmd:CommandBinding_command ?c . FILTER(CONTAINS(STR(?c),'<sibling-uid>')) }`). Если сиблинги забиндены, а твоя — нет → binding просто не создан.

## Фикс (missing binding = данные, не код)

Создать `exocmd__CommandBinding` ассет, **зеркалящий verified sibling** (тот же класс `exocmd__CommandBinding`):
```yaml
exo__Instance_class: [ "`<CommandBinding-class-uid>`" ]
exo__Asset_isDefinedBy: "`<анкер онтологии КОМАНДЫ>`"   # см. со-локацию ниже
exocmd__CommandBinding_command: "`<command-uid>`"
exocmd__CommandBinding_targetClass: exo__Asset   # или ems__Task — по scope команды (см. сиблинг)
exocmd__CommandBinding_position: inline
exocmd__CommandBinding_order: <N>
```
`targetClass exo__Asset` = широчайший scope (резолвится и для подклассов вроде `ems__Task` через иерархию); сузь до конкретного класса только если команда применима лишь к нему. Precondition висит на КОМАНДЕ — но у биндинга есть и **свой** `exocmd__CommandBinding_precondition` (override), если гейт нужен только этой привязке.

⛔ **`exocmd__CommandBinding_group` НЕ ПИСАТЬ — поле МЁРТВОЕ** (прежняя редакция блока его предписывала). Парсинг снят RFC `f1dc284a` Phase 8 (`CommandResolver.ts:1005`: «parser silently ignores»); секция кнопки задаётся **`exocmd__Command_category`** (`DynamicCommandButtonGroupBuilder.ts:187`) ⇒ у биндинга степени свободы нет. Читаемые поля: `target*`, `position`, `order`, `variant`, `precondition`, `style`, `overrides`.

⛤ **Со-локация — с КОМАНДОЙ, а не «в папке exocmd»** (прежняя редакция говорила второе и промахивалась для команд вне `$exocmd`): `isDefinedBy` берётся у команды, поэтому команда в `exoas-public/period-commands` ⇒ биндинг **туда же**. ⚠ Tell: копируешь образец из `$exocmd` для команды, живущей в другом ассетспейсе.

_Замер 2026-09-06 (`origin/main` 6c0df739): биндингов 84, папка совпадает с командой у **80**._

**Верификация фикса (revert-verify для data-фикса):** `resolve-buttons` ДО фикса (команда ОТСУТСТВУЕТ = RED) → создать binding → `resolve-buttons` ПОСЛЕ (команда в `visible` = GREEN). Это авторитетный resolver-eval — тот же путь, что инлайн-кнопки. Плюс `validate schema --shapes-mode` (0 violations, cache cleared) + `exosync push` в canonical-репо + parity clean. Пиксель-визуал (DOM в живом Obsidian) — ~30-сек user-confirm (reload + открыть ассет), НЕ мутировать живой vault ради теста (`gui-mutation-test-on-temp-vault`).

## Addendum 2026-07-11 — vault-wide orphan audit + delete-side discipline (когда orphan → удалить, а не забиндить)

Найдя один orphan, часто стоит **проаудитить весь vault** — orphan-команды приходят батчами (кто-то создал набор команд, забыл создать биндинги). И не каждый orphan = missing button: многие redundant/superseded → удалить, не биндить.

**Vault-wide orphan-audit query (reusable):**
```
# все команды (grounding = все реальные команды) MINUS все забинженные
A: SELECT ?cmd WHERE { ?cmd exocmd:Command_grounding ?g }           # все команды
B: SELECT ?c   WHERE { ?b exocmd:CommandBinding_command ?c }          # забинженные
orphans = A − B (по UID)
```
**Сигнал bind-vs-CLI-only:** сплить orphans по наличию `exocmd__Command_precondition`. **Precondition = высокий сигнал «intended-inline-but-orphaned»** (precondition существует ТОЛЬКО чтобы гейтить видимость инлайн-кнопки — «Has start timestamp», «Is in wrong folder»). Orphan БЕЗ precondition → скорее intentionally CLI/palette-only (забиндженный, он рендерился бы безусловно). Плюс: **counterpart-asymmetry** — если set-сторона забинжена инлайн (Start Effort → Task+Project), а remove-сторона orphan → почти наверняка missing button.

**Delete-side дисциплина (когда orphan = redundant/superseded → удалить):**
1. ⛔ **Reverse-ref КАЖДОГО ассета (command + precondition + grounding) как OBJECT ПЕРЕД удалением — по ОБЕИМ IRI-формам, иначе ложный ноль.** Ссылка на команду с parseable-меткой эмитится **symbolic**, и фильтр по одному UID её не видит ⇒ «безопасно удалить» будет неверным (`sparql-iri-form-pre-verify`):
   ```
   SELECT ?s ?p WHERE { ?s ?p ?o . FILTER(CONTAINS(STR(?o),'<uid8>') || CONTAINS(STR(?o),'<SymbolicLocalName>')) }
   ```
   ⚠ **`<uid8>`, не полный UID** — в `CONTAINS` хвост не нужен и потому вреден (его дописывают по памяти). ⛤ **Канарейка обязательна:** тот же запрос на ЖИВОМ соседнем ассете обязан вернуть непусто, иначе ноль означает «запрос мёртв». Только self `Asset_uid`/`Asset_filename` → безопасно удалить.
2. **Grounding часто SHARED с workflow-transitions** (`ems__WorkflowTransition_postActions`) — «Re-open»/«Move to Backlog» переиспользуют «delete endTimestamp/startTimestamp» grounding. Referenced workflow'ами → **KEEP grounding** (удали только command + non-shared precondition). Это и есть источник redundancy: standalone remove-команда дублирует то, что workflow-переход уже делает.
3. **supersedes/deprecatedBy provenance:** exocmd-ассеты несут двунаправленные `Asset_supersedes` ⇄ `Asset_deprecatedBy`. ⚠ **`-N` суффикс в cliName НЕ значит «-N это stale дубль»** — новый КАНОНИЧНЫЙ ассет часто получает `-N`, потому что чистый cliName занят старым. Проверяй НАПРАВЛЕНИЕ supersedes: `X supersedes Y` → Y старый, X новый (и его grounding — тот, что workflow'ы используют). Удаляя старый (superseded) ассет, чей на него `Asset_supersedes` указывает выживающий ассет → **strip dangling `Asset_supersedes` строку из выживающего** (иначе dangling wikilink).
4. **Surgical remote-propagation удаления:** `gh api -X DELETE repos/<o>/<r>/contents/<path> -f sha=<sha> -f branch=main` per-file — хирургично, тратит только эти файлы. ⛤ Предпочтительнее `exosync sync` для deletions, т.к. sync оперирует ВСЕМИ репо устройства и может протолкнуть **несвязанные pending-изменения** (напр. правку концепта пользователя). Verify remote 404 через `gh api contents` (НЕ `gh search code` — code-search лагает минутами → ложный 404/present). Local `rm` + gh-DELETE = local+remote consistent; манифест self-heal'ится на следующем exosync-scan.
5. **SHACL post-validate после каждого удаления** (cache cleared) — ловит dangling refs. ⚠ Различай: violation на НЕсвязанном ассете (не тронутом тобой) = pre-existing/coincidental (live-vault sync между валидациями) — **restore-backup + re-validate** чтобы изолировать (если persists с восстановленными файлами → не твоё).
6. **Backup ПЕРЕД каждым удалением** (`cp → /tmp/...`); удаление shared-repo ассетов recoverable из git-history remote, но локальный backup дешевле.
