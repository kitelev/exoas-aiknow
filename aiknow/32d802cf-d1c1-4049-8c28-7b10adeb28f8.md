# Verify before assert

⛔ **БАРЬЕРА НЕ БУДЕТ — замер 2026-08-22 (метод задачи 7156e4c2).** Нарушение — УТВЕРЖДЕНИЕ без проверки, а утверждения живут в тексте ответа, куда хук не смотрит; вызова инструмента у ненаписанной проверки нет ПО ПОСТРОЕНИЮ (отсутствие действия недетектируемо). ⇒ 7 рецидивов за 30 дней остаются на дисциплине и на симптомах-tell — это потолок, а не недоработка.

При любом утверждении о возможностях кодовой базы / тулинга / системы — **особенно негативных** («X не поддерживает Y», «Z требует доработки», «сейчас не работает») — обязана быть свежая (в этом турне) проверка через Read / Grep / Glob.

## Когда правило срабатывает

- Сравнение вариантов решения с указанием стоимости каждого.
- Архитектурные оценки масштаба переделки («это потребует переписать X»).
- Утверждения о текущем состоянии системы пользователя («CLI поддерживает только single vault»).
- Pitching trade-offs в CustDev / архитектурном interview — там цена ошибки выше, потому что искажает решение пользователя.

## Запреты

- ⛔ Опираться на априорные обобщения («типичные CLI», «обычно такие плагины») при оценке конкретного проекта пользователя.
- ⛔ Substitute «I assume X» → confident «X is the case». Если не проверил — формулировка `«насколько я вижу, X — но не уверен, надо проверить»`, не `«X»`.
- ⛔ **Особо опасно:** confident negative claims в trade-off comparison — выглядят как факты, искажают decision пользователя, ловятся им как ложь, тратят turn на correction.

## Floor — mechanical pre-check: четыре шага перед любым claim о возможностях

Перед confident assertion о capability проекта:

```bash
# 1. Локализовать source
find <repo> -path '*/src/*' -name '*<feature>*'

# 2. Grep на конкретные опции / параметры / методы
grep -rE '<expected_pattern>' src/

# 3. Read релевантного файла, если grep дал кандидатов

# 4. Только после этого — utterance с claim
```

Если шаги 1-3 невозможны (нет доступа к репо, артефакт не найден) — это разрешённый «не знаю», говорить именно так, не догадкой.

Before claiming «all callers go through X»:

## Mandatory addendum для multi-tree audit claims

Before claiming "N files across M trees":

```bash
# 1. Per-tree breakdown — explicit per-tree count, не aggregated find
for tree in <list>; do
  echo "=== $tree ==="
  find "$tree" -name "*.md" 2>/dev/null | xargs grep -l "<pattern>" 2>/dev/null | wc -l
done

# 2. Verify each tree still exists в repo HEAD (not just on disk — disk может иметь stale dirs)
git -C <repo> ls-tree -r HEAD --name-only | grep -E "<tree-path-prefix>" | head -1
# Empty result → tree retired, drop from audit scope

# 3. Sum at end, не средину — иначе single big find query masks per-tree drift
```

Особенно опасно для **multi-repo / multi-tree migrations** где audit drives migration scope. Per-tree allocation error = wrong commit chain plan, wrong PR count, wrong test fixture regeneration trigger.

## Mandatory addendum для refactor scope/cost claims

Перед confident assertion «можно сделать в N LOC» / «небольшой refactor» / «trivial sync override» / «scope X is bounded»:

```bash
# 1. Identify FULL call chain — public API down to data layer
codegraph_callees <public-fn>   # → next layer
# Recurse для каждого callee пока reach data layer

# 2. For EACH layer verify language/runtime constraint claim:
#    - `async` keyword в signature ≠ `await` в body — но does signature force callers to await?
#    - `async function*` generators MUST be drained с `for await` — CANNOT sync-drain
#    - `for await` chain → upstream caller forced async even if every layer below sync-underneath
#    - Returning `Promise<T>` from function БЕЗ internal await is STILL `Promise<T>` at type level

# 3. Aggregate cost across layers
#    N LOC × M layers in chain = NM total LOC (часто)
#    Plus dependent test fixture rewrites at each layer

# 4. Only after full audit — utterance с capability/cost claim
```

Single-method verification («I checked X.match() is sync») — necessary but **not sufficient**. Chain above determines whether sync API is achievable.

Особо опасно для **architecture pitch в interview / scope decision** — confident scope/cost claim formulates pitch которая binds user decision before reality check. Если пользователь явно не просит empirical verification → silently launch child session с false premise → reality wall → revert/rescope cycle. Cheap to verify (10 min codegraph chain + grep), expensive to retract (RFC rewrite, child pivot, user trust hit).

## Mandatory addendum для binding positive recommendations об action с irreversible consequence

Перед confident positive statement что user-visible irreversible action ("safe to kill", "safe to delete X", "you can drop database Y", "force-push is OK here") безопасно — **обязательны N≥3 independent verification angles**, не один. Каждый angle должен probe different system layer:

## ⛔ Собирая ПЕРЕЧЕНЬ вызовов функции по корпусу — популяция это файлы, где она ОПРЕДЕЛЕНА, а не где встречается

Инвентаризация «все значения, которыми зовут `<функцию>`» (словарь исходов, список кодов ошибок,
набор фич-флагов) естественно пишется как греп по каталогу. Каталог при этом содержит **не только
прод**: харнессы (`*-verify.sh`), генераторы мутантов, фикстуры, скомпилированные `.pyc` — и все они
цитируют ту же функцию с **выдуманными** значениями, которые прод не эмитит **никогда**.

- ⛔ **Отказ тихий и в СТОРОНУ ЗАВЫШЕНИЯ:** лишние значения выглядят настоящими (правильная форма,
  правдоподобные имена), а «пропущенных» нет — то есть обычная проверка полноты («канарейка
  на месте?») их не видит **по построению**. Она ищет недостачу, а здесь избыток.
- ✅ **Floor — сузить популяцию ОПРЕДЕЛЕНИЕМ, а не именем каталога:**
  ```bash
  # файлы, где функция ОПРЕДЕЛЕНА, — только они эмитят прод-значения
  grep -rln '^<имя_функции>()' <корпус> | cat
  ```
  Дальше отсеять из полученного списка харнессы/мутанты (`*-verify.*`, `*-mutants.*`, `*.pyc`) —
  они определяют функцию-**заглушку**, а не прод.
- ⚠ **Симптом-tell, ловится счётом:** число файлов корпуса на порядок больше числа файлов,
  определяющих функцию (у меня 59 против 4, из них прод 2). Расхождение в разы = греп меряет
  каталог, а не механизм.
- ⛤ **Разводить с `migration-pre-verify-use-case`:** там дефект обратный — популяция **уже**
  предмета (discovery-фильтр не видит часть носителей). Здесь она **шире**, и лечение
  противоположное: не расширять охват, а привязать его к определению.

## ⛔ Факт о КОДЕ («функция делает N хопов») ≠ факт о СТОИМОСТИ: цена = глубина × ЧИСЛО ВЫЗОВОВ, и второй множитель не читается

Читая код в поисках «где тормозит», находишь дорогую по виду функцию — рекурсия, пять `await`,
разворачивание цепочки — и называешь её узким местом. ⛔ Утверждение о **глубине** при этом верно,
а вывод о **стоимости** не следует: он умалчивает второй множитель — **сколько раз она зовётся**.

- ⛤ **Дефект тише обычной ошибки: все факты истинны.** «Пять хопов» — правда; «рекурсия по шагам» —
  правда; «на регистрации не используется» — правда. Ложна только привязка, а её ничто в коде не
  опровергает: число вызовов **не написано** нигде, оно есть свойство **данных**.
- ⚠ **Симптом-tell, ловится ДО вывода:** ты называешь функцию дорогой и **не можешь назвать
  числом**, сколько раз она исполняется на измеряемом пути. Не «примерно много» — число.
- ✅ **Floor — один запрос к данным, а не к коду:** посчитать популяцию, по которой идёт цикл.
  Условие отбора обычно прямо в коде (`paletteEnabled = true`, `status = Doing`, `type = X`) ⇒
  переносится в запрос дословно. Секунды работы против неверной декомпозиции.
- ⛔ **Ошибка ведёт не к лишней работе, а к НЕ ТОЙ.** Оптимизировав глубину при двух вызовах,
