# Reference — детальные механики граблей zsh/Bash tool

⛤ Справочник к правилу `~/.claude/rules/bash-loop-eval-pitfalls.md`. Правило держит во флоре
**таблицу «симптом → грабля → floor»** (индекс, которым грабля опознаётся) и счётчик рецидивов;
этот ассет — **детальный разбор каждой грабли**, читаемый ПОСЛЕ опознания симптома.

⛔ Не читать целиком «на всякий случай» — вход через таблицу симптомов в правиле: увидел симптом
→ узнал номер грабли (Г1…Г19) → прочитал её раздел здесь.

## Механики

### Г1 — word-split: zsh НЕ разбивает unquoted `$VAR`

Вся строка становится **одним** словом. Три поверхности, один корень:

- **цикл** — `for x in $LIST` → одна итерация, `$x` = весь список;
- **аргументы команды** — `cmd $VAR` (`git add $F`, `eslint $CHANGED`, `grep "$p" $DIRS`) → один аргумент;
- **команда-в-переменной** — `CLI="npx -y pkg"; $CLI verb` → вся строка = один command-токен → not-found.

⛤ **Обратный flavor** (`${4:+--property "k=$4"}`): расширение НЕ переразбивается там, где нужно **два** токена → флаг с пробелом внутри имени опции.

Годные формы: литералы в `for` · `while IFS= read -r x; do … done <<'EOF'` · `${=VAR}` (zsh-split, непортативно) · массив `"${arr[@]}"` · python-цикл.

⚠ **`2>/dev/null` превращает эту граблю в ложный ноль** — «no such file» скрывается, пустой результат выглядит валидным.

### Г2 — eval-контекст тела цикла теряет PATH

Внешние бинарники внутри `for`/`while`-тела → `(eval):N: command not found` (exit 127), те же команды top-level работают штатно. Затрагивает и `$(...)` + pipe compound, не только циклы. Механизм не verified, паттерн стабилен.

### Г3 — zsh reserved variables

⛔ Не использовать как имена: **`status`** (read-only, синоним `$?` — и как capture, и как `for status in …`), **`path`** (= `$PATH` array), `signals`, `options`, `argv`, `pipestatus`, `USERNAME`, `LINENO`, и integer-typed **`UID`/`GID`/`EUID`/`EGID`**.

⛤ `UID` даёт **три разных симптома** одного корня: `bad math expression` (строка ушла в арифметику), `failed to change user ID` (в compound-`$(…)` триггерит setuid-попытку), реже `read-only variable`. Не искать три разные причины.

Для release/CI-watch предпочитать `gh run watch <id> --exit-status` поллинг-циклу с `$(...)`-захватом.

### Г3b — exit-код пайпа врёт

`${PIPESTATUS[0]}` (uppercase) в zsh **не существует** → пусто. Массив — lowercase `${pipestatus[1]}` (1-индексация). Обычный `$?` после пайпа = exit **последней** команды (`head`/`tail` = 0), а не смысло-несущей.

⛔ **Когда exit-код несёт вердикт** (gate, revert-verify RED/GREEN, `git push`, `git rebase`) — НИКОГДА не пайпить через `head`/`tail` ради косметики: отдельный top-level вызов в файл + `$?`, затем читать файл. Пайп маскирует ровно тот код, ради которого проверка и затевалась.

⚠ Если exit-код чисто косметический (успех очевиден из вывода) — `${PIPESTATUS[0]}` лучше не писать вовсе: он всегда пуст и вводит в заблуждение.

### Г3c — `set -euo pipefail` + `| head` → SIGPIPE(141), скрипт умирает молча

`head -N` закрывает пайп → писатель получает SIGPIPE → под `pipefail` статус пайпа 141 → `set -e` убивает скрипт **до любого `echo`**. Наружу: rc=141 и пустой вывод.

⛤ **Особо коварно для ГЕЙТОВ**: срабатывает на **успешном** пути (grep НАШЁЛ → head закрыл пайп раньше), т.е. гейт умирает на первой корректной проверке. Вызывающий видит «не exit 1» и считает, что прошло. **Гейт может быть мёртв с первого коммита и не жаловаться годами.**

- ✅ `VAR=$(producer | head -N || true)` · `grep -m1` · `head -N < <(producer)`
- **Verify обязателен:** фикстура-должна-пройти → `✓` + rc=0; фикстура-должна-упасть → rc=1 + сообщение. **rc=141 / пустой вывод = сломан**, а не «прошёл».

⛤ **Мета-урок:** *зарегистрированные* хуки исполняются на каждом tool-call → ломаются шумно и чинятся сразу. Скрипты, **вызываемые вручную из скилла**, исполняются только при запуске того скилла → **гниют тихо**. Аудитируя скилл, который мандатит скрипт, — **прогони его на фикстуре**, не полагайся на «он в hooks/, значит работает».

### Г3e — `grep -c` при НУЛЕ совпадений ПЕЧАТАЕТ «0» и возвращает rc=1 ⇒ `|| echo 0` дописывает ВТОРУЮ строку

<!-- Added by /session-retrospective 2026-08-03 — root: наступил на это в СВОЁМ харнессе, редактируя файл, где та же грабля описана в комментариях ДВАЖДЫ; в корпусе правил её не было. -->
`grep -c` — единственная форма grep, которая **и печатает результат, и сигналит «не найдено» кодом возврата**. Поэтому рефлекторный `|| echo 0` (страховка «а если пусто») даёт `"0
0"`: сначала печатает сам grep, потом `echo`. Дальше `[ "$n" -eq 0 ]` падает `integer expression expected`, а `[ "$a" = "$b" ]` тихо не совпадает.

- ⛤ **Асимметрия отказа делает его коварным: падают РОВНО те проверки, чей ожидаемый ответ — «пусто».** Ветки «должно быть N>0» работают штатно (там grep нашёл, rc=0, `echo` не сработал). То есть ломается **негативный контроль** — половина харнесса, которая и доказывает, что тест умеет краснеть.
- ✅ `n=$(grep -c … 2>/dev/null || true); printf '%s' "${n:-0}"` — `|| true` глотает rc, `${n:-0}` закрывает случай «файла нет» (там grep не печатает ничего).
- ⚠ Не путать с `grep -c` **без** `|| …` под `set -e`: там rc=1 просто убьёт скрипт — симптом громкий и опознаётся сразу.
⛤ **Тот же exit-код рушит и `&&`-ЦЕПОЧКУ фильтрации — `grep -v`.** Идиома «выбросить строку из файла» `[ -s "$F" ] && grep -vxF "$k" "$F" > "$F.tmp" && mv "$F.tmp" "$F"` **молча не выполняет `mv`**, когда после фильтра не осталось ни строки: `grep -v` при пустом выводе возвращает **1**, и цепочка обрывается ровно на «файл стал пустым» — то есть в самом частом случае (в файле была одна строка, её и удаляли). Симптом: элемент, который ты «снял», на месте. Floor — `if`-блок вместо цепочки + `|| true` на самом grep. **Empirical 2026-08-04:** снятие латча уведомлений (файл из одной строки `disabled`) не срабатывало → второе самоотключение петли прошло бы молча; поймано осью revert-verify «ручное включение снимает латч», которая единственная и краснела.

⛤ **ТИХИЙ вариант того же корня: пустой вывод, скормленный СТРОКОВОМУ сравнению, даёт вакуумно-ЗЕЛЁНУЮ ось, а не громкую ошибку.** Асимметрия выше описывает случай, где пустота попадает в **арифметический** тест (`[ "$n" -eq 0 ]`) и роняет его громко. Но счётчик «до/после» сравнивают обычно **строкой** — `[ "$AFTER" = "$BEFORE" ]`, — и тогда `пусто = пусто` **истинно**: ось проходит, ничего не измерив, и красного симптома не возникает вовсе.
- ⛔ Бьёт ровно по осям, доказывающим, что нечто **НЕ произошло** (не обошёл vault, не отправил тревогу) — то есть по негативному контролю, но уже без единого признака поломки. Это тождественно-зелёный верификатор ([[self-satisfying-metric-weak-verifier]]), а не сломанный тест.
- ⚠ **Бывает ЛАТЕНТНЫМ и потому переживает ревью:** если к моменту замера файл уже создан предыдущей осью, счётчик отдаёт настоящее число, и сегодня всё честно. Но гарантия держится на **порядке осей**, а не на конструкции: добавили ось выше по потоку — и соседние молча стали вакуумными.
- ✅ Floor тот же (`${n:-0}`), но проверять его надо **прямой пробой хелпера на несуществующем пути**: прогон набора зелен в обоих состояниях и потому ничего не доказывает.
- **Empirical 2026-08-05** (`bot-quarantine-watch-test.sh`): три счётчика (`SCANNED` · вызовы CLI · тревоги) написаны как `grep -c … || true` и сравнивались строкой. Правило было в system-reminder, и его floor цитирует случай «файла нет» дословно. Поймал не я и не набор (24/24 зелёных), а `code-reviewer`, **инструментировавший** харнесс, — латентность доказана прогоном, а не выведена чтением.

⛤ **СОСЕДНИЙ механизм с тем же исходом, но БЕЗ участия `grep -c`: `wc -l <file` печатает ПАДДЕД-ноль, а фолбэк `|| echo 0` — голый.** Обход из floor выше (`${n:-0}`) здесь **не спасает**: значение не пустое, оно `"       0"` против `"0"`, и строковое сравнение считает их разными.

```bash
n=$(wc -l <"$F" 2>/dev/null || echo 0)   # файл есть  → "       0"   (macOS/BSD)
                                          # файла нет → "0"          (ветка echo)
[ "$AFTER" = "$BEFORE" ]                  # ⇒ ложно-КРАСНОЕ на исправном коде
```

- ⛔ **Достижимое состояние конкретно:** на `BEFORE` файла ещё нет, на `AFTER` он создан-но-пуст. Ровно так выглядит счётчик «сколько отправлено» в харнессе, где отправок не было.
- ⚠ **Латентность держится на ПОРЯДКЕ ОСЕЙ** (как и у тихого варианта выше), но просыпается от другого: не от пустого входа, а от **перестановки осей** — ось выше по потоку всегда создаёт файл, обе выборки читают существующий и обе паддед ⇒ зелено, пока порядок не сменится.
- ✅ **Floor: `printf '%s' "$((n))"`** — арифметическое раскрытие нормализует и паддинг, и пустоту разом (`${n:-0}` закрывает только вторую половину).
- ⛤ **Симптом-tell виден без отладки: паддинг ПРОТЕКАЕТ в текст сообщения** — `отправок:        1` вместо `отправок: 1`. Лишние пробелы в собственном выводе = число пришло из `wc -l` и не нормализовано.
- **Empirical 2026-08-05** (`claude-bloat-check-test.sh`, порт selftest-режима): дефект внесён вместе с новой осью и был зелёным — маскировался тем, что предыдущая ось всегда создаёт файл. Поймал `code-reviewer` (MEDIUM), доказав достижимость **реконструкцией состояния**, а не чтением; я его не увидел, хотя floor про `grep -c` цитировал в соседней строке того же файла.

- **Empirical 2026-08-03:** в `alp-notify-verify.sh` `notify_lines() { grep -c . "$LOG" || echo 0; }` дал **10 ❌ из 34** — все с сигнатурой `ожидал=0 получил=0` и лишним `0` на следующей строке; RED-оси revert-verify при этом отработали правильно, загрязнена была только строка сравнения. Правило-предупреждение лежало в комментариях **редактируемого в тот же момент** `alp-tick.sh` (два вхождения, `|| true`, НЕ `|| echo 0`). Цена: 1 ложно-красный прогон + 1 правка.

### Г3d — pipefail + `cmd | grep -q X && ok || bad`, где `cmd` легитимно exit≠0 на успехе

Под `pipefail` статус пайпа = non-zero от `cmd`, а не 0 от grep → ветка `&&` промахивается, **хотя grep сматчил**. Типично для CLI-обёрток, где `exit 2` = «доступ запрещён» = желаемый исход теста.

Симптом-tell: **denial/negative-проверки падают массово**, positive проходят → это misattribution, а не регрессия.

✅ Capture-then-grep: `OUT=$(cmd 2>&1); echo "$OUT" | grep -q "…" && pass || fail` (command-substitution изолирует exit).

### Г4 — спецсимволы в double-quoted аргументе

Backtick внутри `"…"` = command substitution — в `echo`, в `git commit -m`, в `gh pr create --body`, в `--title`. Три backtick-а подряд (markdown-fence) дают `parse error in command substitution`. Круглые скобки `()` в `-m "…"` — `parse error near '()'`. Слово может **молча выпасть** из сообщения (subject исказится, и это заметят потом).

- ✅ Текст со спецсимволами (backtick, `$`, `()`, `!`) → **`-F <file>` / `--body-file`** (Write-тулом в файл, флаг читает буквально).
- ✅ Grep-паттерн с backtick — в переменную одинарными кавычками + `grep -F "$VAR"`.
- ✅ Line-start сканирование fence — python `re.compile(r'^\s*```(exoql|sparql)')`, полностью минует shell-quoting.

### Г5 — unquoted `?`/`*` → pathname-glob

zsh глобит **любой** unquoted аргумент с `?`/`*`/`[…]`, включая URL. Не сматчилось → `no matches found`, и **команда не запускается вовсе** (в bash несматченный glob передался бы литералом).

Частые формы: `gh api …?ref=main` / `?per_page=100` / `?recursive=1`, `--include=*.ts`, `find . -name *.md`.

- ✅ **Квотировать весь аргумент**: `gh api "repos/o/r/commits/$SHA/check-runs?per_page=100"` — в double-quotes `$SHA` всё ещё расширяется, а `?` становится литералом.
- ✅ Либо префикс `noglob` (zsh-специфично): `noglob gh api …?per_page=100`.

⛤ **Multi-pattern**: `ls -d A* B*` — ОДИН несматченный паттерн роняет **всю** команду, включая валидный `A*`. Использовать `find -iname A -o -iname B` (no-match безвреден).

⛔ **Если пустой вывод = положительный вердикт** («хвостов нет», «нарушений нет») — glob-команда даёт **правильный ответ по неправильной причине**, и это невидимо: `0` — не подозрительная пустота, а ожидаемое значение. Тот же механизм «подтвердил» бы чистоту и при реально оставшихся хвостах. Только `find -name` либо явная проверка exit-кода самой команды.

⛤ **Отказ роняет ВСЮ строку, поэтому цена определяется СОСЕДОМ по `;`, а не самим glob'ом.** `no matches found` — ошибка **разбора**, она возникает до запуска и снимает **все** команды строки, включая стоящие после `;` (не только после `&&`). Значит безобидная уборка (`rm -f <dir>/tmp.*`) в одной строке с чем-то значимым уносит это значимое молча — в выводе остаётся только строка про glob, и её легко прочесть как «ну, нечего было удалять».
- ⛔ **Худший сосед — ПИНГ/уведомление:** он и есть единственный сигнал наружу, поэтому его пропажу нечем заметить изнутри. Автономный воркер при этом выглядит для петли как «не отчитался», хотя работа сделана.
- ✅ **Floor:** команду, чей результат кто-то ЖДЁТ (ping, уведомление, запись вердикта), не ставить в одну строку с glob-содержащей уборкой. Уборку — отдельным вызовом либо через `find … -delete` (no-match безвреден).
- ⚠ **Tell:** вывод состоит ровно из одной строки `no matches found`, а ты ожидал ещё и результат соседней команды. Отсутствие ожидаемого вывода — не «тихо отработало», а «не запускалось».
- **Empirical 2026-08-05** (ALP `9386951e`): `rm -f <dir>/parity.* ; <ping> COMPLETED …` — файлов `parity.*` не осталось, glob не сматчился, **`COMPLETED`-пинг не ушёл**. Поймано только тем, что в выводе не было `ping-rc`; пере-отправлен отдельным вызовом. Урон 0, но это ровно тот сигнал, ради которого петля наблюдает за воркером.

### Г6 — `$VAR[:N]` → zsh array-subscript

В zsh `$VAR[...]` — array-subscript, и `[:8]` уходит в арифметический парсер → `bad math expression: operand expected at ':8'`.

✅ `${VAR:0:8}` (полная bash-форма работает и в zsh) ЛИБО `cut -c1-8` / `head -c8`.

⚠ Коварно в фоновых watcher-скриптах: падает на runtime **внутри** цикла → watcher молча крэшит (exit 1), verdict-файл не пишется. «Watcher упал без verdict» → грепни вывод на `bad math expression`.

### Г7 — `[ "$a" '>' "$b" ]` не сравнивает строки

Одинарный `[ ]` в zsh **не поддерживает** `>`/`<` как строковые операторы → `condition expected: >` на каждой итерации (а без кавычек `>` — вообще redirection). В watcher-цикле это значит: крутится, но **никогда не срабатывает** до таймаута.

✅ `[[ "$a" > "$b" ]]` (работает и в bash, и в zsh). Для дат/версий надёжнее python. Для «релиз позже моего merge» — вообще не сравнивать даты, а тянуть `gh api …/runs --jq 'select(.head_sha=="<merge-sha>")'` + bundle-grep.

⚠ Три сигнатуры не путать: `condition expected: >` (Г7) ≠ `bad math expression` (Г3/Г6) ≠ `no matches found` (Г5).

### Г8 — GNU-only флаг в BSD-утилите macOS

`find -newermt` — GNU-расширение; BSD-find отвечает `unknown primary` и **пустым stdout**. С `2>/dev/null` это читается как достоверное «ничего не найдено».

✅ «Что изменилось недавно» — python `os.walk` + `st_mtime`; либо BSD-форма `find -newer <reference-file>`.

⛤ **Второй живой инстанс класса — `ps`: `-o etimes=` (GNU/procps) на macOS даёт `ps: etimes: keyword not found`.** Отличается от `find -newermt` знаком отказа: падает **громко** (ненулевой rc + stderr), поэтому ловится сразу — но ровно до тех пор, пока не заглушён (см. ⛔ ниже). ⛔ **`2>/dev/null` НЕЛЬЗЯ на команде, чей ПУСТОЙ вывод трактуешь как факт.** При negative-existence claim — сперва прогнать БЕЗ подавления.

⛤ **Сосед по macOS-специфике: `mktemp -d` кладёт каталог в `$TMPDIR` (`/var/folders/…`), а НЕ в `/tmp`.** Поэтому поиск собственных сохранённых прогонов (`--keep`-каталоги, scratch, артефакты) по `/tmp/<prefix>-*` даёт **пусто** — и в zsh это ещё и `no matches found` (Г5), то есть роняет всю строку. Floor: искать `find "$TMPDIR" -maxdepth 1 -name '<prefix>-*'`, а не глобить `/tmp`. _(Empirical 2026-08-05: `ls -dt /tmp/beh-*` → no matches, при том что каталоги существовали в `$TMPDIR`.)_

⚠ Соседний слой того же обмана — **result-cache**, но **уже`е`, чем формулировалось раньше.** Замер 2026-08-03 (три прогона на hard-link копии vault): повтор идентичного запроса отдаёт `📦 (cached)`, **но добавление файла в граф кэш инвалидирует** — третий прогон снова считает. ⇒ **в пределах ОДНОГО vault кэш не отдаст «пусто» из окна ДО появления нарушающего ассета.** ⛔ Но это НЕ индульгенция: [[self-satisfying-metric-weak-verifier]] §Addendum 2026-08-03 показал соседний, более злой случай — прогон на **заведомо пустом каталоге** вернул числа предыдущего прогона **на другой фикстуре**, т.е. инвалидация по содержимому не спасает, когда меняется **сам путь vault**. Сложив обе пробы: кэш реагирует на мутацию графа, но не гарантирует различение источников. Остаточная staleness внутри долгоживущего движка — отдельный слой, **triple-кэш**, собранный в начале хода ([[homoiconic-external-engine-config]] §Read-after-write). ### Г11 — Bash tool сохраняет рабочий каталог между вызовами

`cd` персистентен. Одинокий `cd` ради одной операции остаётся активным для всех последующих вызовов — команда **выполняется не там** и возвращает правдоподобный мусор.

**Два подвида, второй опаснее:**

1. **Команда падает абсурдно** — `npm run check:types` из чужого каталога → exit **254**, jest → `Cannot find module`. Легко прочитать как «мой код сломан» и уйти чинить несуществующий баг. Плюс относительные пути молча меняют смысл (`prettier --write packages/…` из vault-каталога = no-op).

2. ⛤ **Команда успешно отрабатывает на НЕВЕРНОМ объёме** — `--vault .` из подкаталога vault: валидатор честно проверил **поддерево** и напечатал `✅ conforms, 0 violations`. Абсурдного exit-кода тут НЕТ.

**Tell для второго подвида — не exit-код, а МАСШТАБ выдачи.** Загружено `20 759` триплов вместо `141 374` (−85%). У любой команды, печатающей объём обработанного (триплы, файлы, ассеты), сверяй **порядок величины** с ожидаемым.

⛤ **Особо коварно для revert-verify:** обе стороны сравнения меряются одинаково-неверно, поэтому «дельта = 0» выглядит как успешное доказательство нейтральности.

⛤ **Эталон сверять ТЕМ ЖЕ замером.** На одном и том же корне `validate schema --shapes-mode` печатает `Loaded 141374 triples`, а `query 'SELECT (COUNT(?s)…)'` даёт **128 825** — это разные величины, а не дрейф. Подставив COUNT под эталон 141k, получишь мнимую просадку −9% и уйдёшь расследовать несуществующий unmount. Дискриминатор «поддерево vs корень» надёжен по **порядку** (20k против 128-141k); ±10% между двумя разными замерами — шум.

⛤ **Третья форма симптома (2026-08-04, ×2 за сессию): вывод УСЕЧЁН до одной служебной строки.** `npx …` из чужого каталога напечатал ровно `Node.js v25.8.1` и больше ничего — ни ошибки, ни результата. Это не «команда молчит» и не подвид 2 (там объём МЕНЬШЕ, но осмысленный): выполнялся не тот `node_modules`, и запуск умер до собственного вывода, оставив лишь баннер рантайма. **Tell:** вывод состоит из одной строки, которую ты не просил и которая описывает СРЕДУ (версия ноды/питона, путь интерпретатора), а не работу. Первым делом `pwd`, а не отладка команды.

✅ **Floor:** любой вызов-вердикт начинать `cd <корень> && …` **в той же команде**; путь-таргет — абсолютный, не `.`. ⚠ Рецидивы 2026-08-04 показали, что «безобидный» `cd` в vault ради одного `apply`/`validate` — ровно тот случай: следующий вызов в код-репо уже отравлен, и симптом приходит с задержкой в 1-2 команды, когда связь с `cd` уже не очевидна.

### Г12 — `${VAR:-<дефолт>}` закрывается на ПЕРВОМ `}`; хвост дефолта вытекает наружу литералом

Подстановка с дефолтом парсится до **первой незаэкранированной `}`** — а не до «парной». Если дефолт сам содержит фигурные скобки (SPARQL `WHERE { … }`, JSON, regex `{2,3}`), подстановка обрывается внутри него, остаток уезжает в командную строку как отдельные слова, и вызываемая программа получает синтаксически битый ввод.

```bash
CANARY="${DLP_CANARY:-SELECT ?s WHERE { ?s a :X }}"   # ⛔ закроется на `{`-парной? НЕТ — на первой `}`
```

- ⛤ **Коварство — дефолтная ветка может «работать» СЛУЧАЙНО.** Вытекший хвост иногда сам достраивает синтаксис (лишняя `}` закрывает недозакрытый `WHERE`), поэтому прогон **без** переменной проходит, а прогон **с** переменной падает. Симптом читается как «сломался параметризованный путь», хотя сломаны оба — просто у одного ошибки взаимно погасились.
- ✅ **Floor:** дефолт со скобками — только явным ветвлением; многострочный текст — из файла:
  ```bash
  if   [ -n "${VAR_FILE:-}" ]; then TEXT=$(cat "$VAR_FILE")
  elif [ -n "${VAR:-}" ];      then TEXT="$VAR"
  else TEXT='SELECT ?s WHERE { ?s a :X }'   # одинарные кавычки, отдельным присваиванием
  fi
  ```
- **Tell:** сообщение об ошибке от вызываемой программы цитирует **обрывок** твоего дефолта с лишней скобкой на конце.

### Г13 — bash 3.2 (macOS): `${#ARR[@]}` на массиве, в который НИ РАЗУ не писали, под `set -u` = `unbound variable`

Отличается от остальных граблей этого файла контекстом: она не про zsh в Bash tool, а про **bash-скрипты** (launchd-джобы, хуки, мониторы), где `#!/bin/bash` на macOS — это **3.2**. `ARR=()` создаёт массив, но пока в него не добавлен ни один элемент, `${#ARR[@]}` под `set -u` роняет скрипт.

- ⚠ **Симптом появляется ТОЛЬКО на пустом входе** — то есть ровно в том состоянии, ради которого проверку и писали. На непустом всё зелено, поэтому обычный прогон дефект не показывает.
- ⛔ **Падение происходит ДО записи в лог**, если счёт стоит в строке лога: монитор не «сообщает про пустоту», а молча умирает. Наивный фикс «рапортовать размер входа» тогда **вводит** то самое молчание, против которого написан ([[self-satisfying-metric-weak-verifier]] §ТРЕТЬЯ ось).
- ✅ **Floor:** считать отдельной переменной при добавлении (`N=$((N+1))` рядом с `ARR+=(…)`), а раскрытие защищать `${ARR[@]+"${ARR[@]}"}` — эта форма сохраняет и корректный word-splitting непустого массива (каждый элемент отдельным словом, пробелы внутри элементов целы).
- ⛤ **Ловится только пробой на ПУСТОМ входе.** Три вердикта (норма / пусто / находка) надо предъявлять достижимыми на фикстуре; чтение кода этого не даёт — я написал фикс, прочитал его и не увидел.
- **Empirical 2026-08-04:** `bot-quarantine-watch.sh` — добавил `log "SCANNED: ${#VAULTS[@]} …"` + ветку «пустой вход = BROKEN». На фикстуре с нулём vault скрипт упал `VAULTS[@]: unbound variable`, не написав ни строки. Исправлено `NVAULTS`/`NPROB` + `${ARR[@]+…}`; после — все три вердикта достижимы.

### Г14 — `${VAR:+NAME=value}` НЕ становится присваиванием: bash распознаёт присваивания ДО раскрытия параметров

Рефлекс «передам переменную только когда надо» в форме `cmd ${flag:+FOO=1} prog` **не работает**: shell размечает командную строку на присваивания-и-слова **до** подстановки параметров, поэтому раскрывшееся `FOO=1` — обычное **слово-аргумент**, а не env для `prog`. Программа получает лишнюю строку в argv, а переменной не видит.

- ⚠ **Симптом мягкий и обвиняет не то:** вызываемая программа ведёт себя так, будто флаг не передан (у меня — молчала вместо отправки), и первая гипотеза — «сломан код программы», а не «переменная не доехала».
- ⛔ Особо коварно в **харнессе**: тестируешь ветку, она «не срабатывает», и вывод пишется как дефект предмета — тогда как красной была сама проба ([[verify-before-assert]] §«проверка была, но проверяла не то»).
- ✅ **Floor:** ветвить **вызов целиком**, а не собирать присваивание подстановкой:
  ```bash
  if [ -n "${esc:-}" ]; then FOO=1 prog "$@"; else prog "$@"; fi
  # либо: env ${flag:+FOO=1} prog …   ← env(1) разбирает argv сам, поэтому здесь форма законна
  ```
- **Empirical 2026-08-04:** проверка канала уведомлений — `run() { … ${2:+LOOPHEALTH_ESCALATE=1} python3 checker.py; }`; все четыре оси показали «отправлено 0», и это читалось как «эскалация сломана». Переписал явным ветвлением — 1/1/1/2 как задумано. Цена: один ложно-красный прогон.

### Г15 — паттерн (или значение), начинающийся с `-`, разбирается grep как НАБОР ФЛАГОВ, а не как данные

`grep -E "$re"` при `$re`, начинающемся с дефиса (`-----BEGIN … PRIVATE KEY-----`, `--verbose`, любой CLI-флаг в списке запрещённых), передаёт его как **опции**: grep печатает usage и выходит с ошибкой, **не выполнив поиска**. То же у `grep -F "$val"`, когда из данных пришло дефисное значение.

- ⛔ **Два симптома, и второй тише первого.** Голый вызов кричит `unrecognized option` + usage. Но рядом почти всегда стоит `2>/dev/null` (шум подавляют рефлекторно) — и тогда остаётся **0 совпадений**, неотличимых от честного «не нашлось». Для проверки, чей ожидаемый ответ и есть ноль, это даёт **тождественно-зелёный** результат ([[self-satisfying-metric-weak-verifier]]).
- ⛤ **Зеркальный вред в ТЕСТЕ:** `printf … | grep -qF "$VAL" && bad "утёк секрет" || ok "не утёк"` при дефисном `$VAL` уходит в ветку `||` **потому что grep упал**, и проверка зеленеет, ничего не проверив. То есть та же грабля даёт ложно-красное в проде и ложно-**зелёное** в его тесте.
- ✅ **Floor: `-e` для паттерна, `-F -e` для литерала** — `grep -HnoaE -e "$re"`, `grep -qF -e "$val"`. Универсально: `--` перед аргументом-данными там, где программа его поддерживает.
- ⚠ Особенно вероятно в **массиве паттернов**: 7 записей начинаются с буквы, восьмая — с дефиса, и ломается ровно она. Общий прогон при этом выглядит рабочим.
- **Empirical 2026-08-05** (`dotfiles-secret-scan.sh`): паттерн `private-key-block` не работал **с первого дня** — 1 из 8. Ни один прогон этого не показывал; поймала только по-паттернная канарейка ([[self-satisfying-metric-weak-verifier]] §ТРЕТЬЯ форма). Тот же дефект нашёлся и в харнессе, где проверка редакции зеленела по ветке `||`.

### Г16 — правая часть ПАЙПА исполняется в СУБОБОЛОЧКЕ: счётчики теста умирают вместе с ней, и набор перестаёт уметь краснеть

<!-- Added by /session-retrospective 2026-08-05 — root: `"$@" 2>&1 | tally` в самотесте харнесса; ✅ печаталось 24, а PASS показывал 13, FAIL не рос вовсе. -->

`producer | while read …` и `producer | myfunc` кладут **правую** часть в субоболочку. Всё, что она присваивает — `PASS=$((PASS+1))`, `FAIL=…`, накопленный массив — **исчезает вместе с ней**. При этом `echo` изнутри печатается нормально (stdout общий), поэтому глазами прогон выглядит рабочим.

- ⛔ **Главное — не потеря числа, а то, что набор ПЕРЕСТАЁТ УМЕТЬ КРАСНЕТЬ.** Счётчик провалов не растёт ⇒ финальный гейт `[ "$FAIL" -eq 0 ] && exit 0` проходит **всегда**, при любом состоянии предмета. Тест печатает свои ❌ и завершается успехом: это тождественно-зелёный верификатор ([[self-satisfying-metric-weak-verifier]]), собранный не логикой, а формой вызова.
- ⚠ **Симптом-tell дешёвый и чисто арифметический: две величины об одном и том же расходятся.** Число напечатанных ✅/❌ ≠ `PASS`/`FAIL` в итоговой строке ⇒ одна из них приехала из субоболочки. Печатать обе и сверять — одна строка кода, и она ловит дефект без всякой отладки.
- ✅ **Floor: `while … done < <(producer)`** (process substitution — цикл остаётся в текущей оболочке) ЛИБО `done <<< "$(producer)"`. Годится и накопление в файл с подсчётом в конце; ⛔ не годится `producer | while` ни в какой форме.
- ⛤ **Не путать с Г3b:** там врёт **exit-код** пайпа, здесь код честный, а теряются **переменные**. Проверка `$?` дефект не покажет.
- ⛤ **Зона риска — именно САМОТЕСТЫ**, где помощники печатают `PASS:`/`FAIL:`, а обёртка их считает: скармливать помощника обёртке пайпом — первый же рефлекс, и он ломает ровно гейт, ради которого самотест написан.
<!-- Added by /session-retrospective 2026-08-09 — root: `d=$(run …)` в alp-digest-verify.sh; `RUN_RC=$?` внутри run умирал в субоболочке, и ось A8 читала rc ОТ СОСЕДНЕЙ оси A7 → ложно-красная. -->
- ⛤ **ВТОРАЯ форма того же корня — COMMAND substitution `out=$(fn …)`, и она ХУЖЕ пайпа: ось читает не «пусто», а ЧУЖОЕ значение.** `$( )` — такая же субоболочка, поэтому `RC=$?` / `PASS=…`, присвоенные **внутри** вызванной функции, снаружи не видны. ⛔ Отличие от пайпа решающее: пайп теряет счётчик в **ноль** (расхождение двух чисел заметно), а здесь переменная сохраняет **значение от ПРЕДЫДУЩЕГО вызова** ⇒ проверка читает результат соседней оси и краснеет/зеленеет по чужому исходу. Симптом-tell из пункта выше («две величины расходятся») **не срабатывает**: величина одна и она правдоподобна.
  - ✅ **Floor: возвращать вердикт ФАЙЛОМ, а не переменной** — `fn(){ …; printf '%s' "$?" >"$TMP/rc.txt"; }` + отдельный `rc_of(){ cat "$TMP/rc.txt" 2>/dev/null || printf 'нет'; }`. Файл переживает субоболочку по построению; фолбэк `'нет'` отличает «не записано» от честного `0`.
  - ⚠ **Ловится только сверкой с ОЖИДАЕМЫМ исходом оси** ([[sparql-iri-form-pre-verify]] §Addendum 2026-08-05): я знал, что A8 обязана быть зелёной, — иначе «красная ось» читалась бы как найденный дефект предмета. _(Empirical 2026-08-09, `alp-digest-verify.sh`.)_
- **Empirical 2026-08-05** (`bot-engine-harness-test.sh`): `tally(){ while IFS= read -r l; do …; done; }` вызывался как `"$@" 2>&1 | tally`. Прогон печатал **24 ✅**, а итог — `PASS=13 FAIL=0`; при заведомо сломанной копии предмета набор всё равно завершался нулём. Поймано сверкой двух чисел, не отладкой. Фикс — `tally(){ … done < <("$@" 2>&1); }`; после него PASS совпал с числом ✅, а мутант дал `PASS=17 FAIL=1`, exit 1.

### Г17 — `ln -sf` в цикле: на КАТАЛОГЕ он кладёт симлинк ВНУТРЬ цели, то есть пишет в чужое дерево

<!-- Added by /session-retrospective 2026-08-06 — root: цикл подмены библиотеки стабами `for f in "$LIB"/*; do ln -sf "$f" "$STUB/$(basename "$f")"; done` — на втором прогоне кладёт симлинки внутрь боевого ~/.claude/lib. -->

`ln -sf <src> <dst>` при `<dst>`, который **сам является каталогом или симлинком на каталог**, трактует `<dst>` как **папку назначения** и создаёт `<dst>/<basename src>`. В цикле `for f in <dir>/*` это стреляет так:

| прогон | что уже лежит в `$DST` | что делает `ln -sf "$SRC/subdir" "$DST/subdir"` |
|---|---|---|
| 1-й | ничего | создаёт симлинк `$DST/subdir → $SRC/subdir` (норма) |
| **2-й** | симлинк на каталог | идёт **сквозь него** и создаёт `$SRC/subdir/subdir` — **внутри источника** |

⛔ Если источник — боевое дерево (`~/.claude/lib`, симлинк в dotfiles), второй прогон **мутирует dotfiles**. Тот же класс, что «`cat >` пишет сквозь симлинк» ([[developer-config-symlinks-into-dotfiles]]), но приходит не от записи, а от **разыменования цели**.

- ⚠ **Латентно по построению:** на свежем `mktemp`-каталоге не воспроизводится никогда, потому что первый прогон всегда чистый. Проявляется у того, кто переиспользует каталог — то есть позже и не у автора.
- ✅ **Floor:** `for f in "$DIR"/*; do [ -f "$f" ] || continue; ln -sf "$f" "$DST/$(basename "$f")"; done` — фильтр по типу, а не надежда, что каталогов в источнике нет.
- ⛤ **Гвард изоляции обязан покрывать ВЕСЬ каталог**, а не пару файлов: манифест из двух хешей совпадает, пока рядом появился посторонний симлинк ([[self-satisfying-metric-weak-verifier]] §манифест содержимого).
- **Проверять ДВУМЯ прогонами.** Одиночный прогон пробы даёт «чисто» и на сломанной, и на исправленной форме — дискриминатор именно повтор.
- **Empirical 2026-08-06** (`alp-failure-coverage-verify.sh`): цикл без `[ -f ]` при двух прогонах на одном `$STUBLIB` оставлял `…/lib/__pycache__/__pycache__` и `…/lib/test-harnesses/test-harnesses`. Поймал `code-reviewer` пробой, не чтением; в самой сессии не стреляло (каталог всегда свежий).

### Г18 — ПОРЯДОК перенаправлений: `2>/dev/null` ПОСЛЕ `< file` не подавляет отказ ОТКРЫТИЯ этого файла

<!-- Added by /session-retrospective 2026-08-07 — root: `read -r a b c < "$AGEC" 2>/dev/null` в alp-tick.sh печатал `No such file or directory` в лог launchd на ПЕРВОМ тике каждого воркера. -->

Перенаправления применяются **слева направо**, и отказ открытия файла печатается **в тот stderr, который активен НА МОМЕНТ открытия**. Значит порядок несущий, а не косметический:

| Форма | Что происходит |
|---|---|
| `read … < "$F" 2>/dev/null` | сперва пытается открыть `$F` (stderr ещё **боевой**) ⇒ `No such file or directory` **просачивается**; `2>/dev/null` применяется уже после |
| `read … 2>/dev/null < "$F"` | stderr заглушён **до** попытки открытия ⇒ тихо ✅ |

- ⛤ **Дефект бьёт по ШТАТНОМУ пути, а не по краю.** Идиома «прочитать необязательный state-файл, если он есть» по построению встречает отсутствующий файл на **первом** запуске — то есть каждый нормальный старт выглядит ошибкой в логе. У фонового демона это прямая порча наблюдаемости: лог засоряется строкой, за которой нет проблемы, и настоящие ошибки в нём тонут ([[self-satisfying-metric-weak-verifier]] §«канал, ставший потоком»).
- ⚠ **`|| true` НЕ лечит** — он глотает код возврата, а сообщение уже напечатано. Симптом-tell: у команды есть И `2>/dev/null`, И `|| true`, а строка всё равно в логе.
- ✅ **Floor:** `2>/dev/null` ставить **первым** среди перенаправлений всякий раз, когда подавляется отказ **самого открытия** (`< опциональный-файл`, `> путь-в-несуществующем-каталоге`). Для подавления вывода **программы** порядок безразличен — путать эти два случая и есть корень.
- ⛤ **Ловится ХАРНЕССОМ, а не чтением:** глазами форма выглядит корректной (подавление же есть). Первый же прогон нового набора выдаёт постороннюю строку в stderr — и это единственный дешёвый сигнал. ⇒ шум в выводе харнесса разбирать, а не списывать на «фикстурный мусор».
- **Empirical 2026-08-07** (`alp-tick.sh`, `slot_age_guard`): `read -r a_worker a_stamp a_n < "$AGEC" 2>/dev/null || true` печатал `…/worker-age: No such file or directory` на первом тике каждого воркера — то есть **каждый** штатный старт. Поймал новый харнесс на первом прогоне; подтверждено двухслучайной пробой (обе формы на несуществующем файле), исправлено перестановкой.

### Г19 — `)` паттерна `case` ЗАКРЫВАЕТ `$( … )` в **bash**; ⛤ в **zsh** та же строка работает ⇒ инлайн-проба в Bash tool ЗЕЛЕНЕЕТ, а скрипт падает

<!-- Added by /session-retrospective 2026-08-08 — root: аргумент-стаб `npx(){ … }` внутри `$( … )` с `case "$a" in *originRun=*)` → `syntax error near ';;'` в bash-харнессе. -->

Внутри `$( … )` **bash** закрывает подстановку на первом же неэкранированном `)` — а у `case` этот `)` стоит в **паттерне**, не в конце команды. Проверено пробой (три формы, один и тот же вход):

| Форма внутри `$( … )` | bash | zsh |
|---|---|---|
| `case "$v" in *=*) … ;; esac` | ⛔ `syntax error near unexpected token ';;'` | ✅ `yes` |
| `case "$v" in (*=*) … ;; esac` — **ведущая `(`** | ✅ `yes` | ✅ `yes` |
| `${v#*=}` — отрезание префикса | ✅ | ✅ |

- ⛤ **Полярность этого файла ИНВЕРТИРОВАНА, и в этом главная ловушка.** Весь корпус выше — про «zsh ломает bash-рефлексы»; здесь наоборот: **Bash tool (zsh) выполняет форму без ошибки**, поэтому инлайн-проба даёт зелёный — а тот же текст в `#!/usr/bin/env bash`-скрипте падает на разборе. То есть «я это только что проверил» — **ложное** свидетельство, если проверял в Bash tool, а кладёшь в скрипт.
- ⚠ **Симптом указывает НЕ ТУДА:** сообщение цитирует `;;` или `esac`, тогда как сломан **разбор `$( )`** несколькими символами раньше. Родственно Г9b (ошибка на `}` при сломанном heredoc в теле функции) — там же и floor «вынеси в файл».
- ✅ **Floor:** внутри `$( … )` `case` не использовать. Ветвление — `if`, выбор значения — раскрытие параметра (`${v#*=}`, `${v%%…}`), которое не содержит `)` вовсе и работает в обеих оболочках. Ведущая `(` в паттерне лечит разбор, но полагается на то, что следующий читатель знает **почему** она там стоит.
- ⛤ **Проверять форму ТОЙ оболочкой, в которой она будет исполняться:** `bash /tmp/probe.sh`, а не инлайн-строкой Bash tool. Одна команда; без неё разница bash/zsh невидима по построению.
- **Empirical 2026-08-08** (`dlp-finish-prompt-verify.sh`, ось F1): аргумент-стаб `npx(){ for a in "$@"; do case "$a" in *originRun=*) printf '%s' "${a#*originRun=}" ;; esac; done; }` внутри `$( … )` → `syntax error near ';;'`. Переписан на `[ "${a#*originRun=}" != "$a" ] && printf …` (отрезание префикса, ноль `)`), после чего ось заработала и покраснела на всех трёх целевых мутантах.
