# Pre-spawn issue staleness check + fresh-source spike

Перед spawn'ом child (или orchestrator-direct работой) над backlog GitHub issue — **обязательная mechanical pre-check**, что issue ещё актуален и не overtaken by events. И: любой orchestrator-side Phase 0 spike, читающий код, обязан использовать **fresh** source (origin/main), не stale main checkout.

## Когда правило срабатывает

- `/orchestrator` выбирает backlog issue для child (спавн через `/spawn-nested-claude` + `spawn-session.sh`)
- Issue был filed недели/месяцы назад ИЛИ относится к кластеру, где недавно мёржились related PRs
- Issue — umbrella / epic с sub-tasks (могли закрыться по отдельности, оставив umbrella orphan-open)
- Orchestrator делает Phase 0 spike, читая код из read-only main checkout (`exocortex-development/exocortex` — НЕ auto-fetch)

## Mechanical pre-check (≤60 секунд, ДО написания child prompt)

```bash
N=<issue-number>; REPO=kitelev/exocortex
# 1. Orphan-umbrella / overtaken: есть ли merged PR ссылающийся на issue?
gh pr list -R $REPO --state merged --search "$N in:title,body" --json number,title \
  --jq '.[] | "merged PR #\(.number): \(.title)"' | head -5
# Непустой результат → issue МОГ быть уже (частично) решён. Прочитай те PR + issue body
# (особенно секции «sub-task A/B/C», «Closes #X», «Addresses #X»).

# 2. Sub-task decomposition: упоминает ли body sub-issues которые уже закрыты?
gh issue view $N -R $REPO --json body --jq .body | grep -iE "sub-task|Closes #|Addresses #|parent of|#[0-9]+"

# 3. Cluster recency: мёржились ли related PRs за последние дни в той же области?
gh pr list -R $REPO --state merged --limit 15 --json number,title,mergedAt \
  --jq '.[] | "\(.mergedAt[:10]) #\(.number) \(.title)"'
# Если recent merges покрывают symptom issue → высокий риск overtaken.
```

**Решение по результату:**

| Pre-check signal | Действие |
|---|---|
| Merged PR ссылается на issue / sub-tasks закрыты | НЕ spawn слепо. Instruct child **verify-first** (проверить эмпирически закрыт ли de-facto) перед любым фиксом. ИЛИ закрыть как orphan-umbrella сразу. |
| Recent cluster merges покрывают symptom | Высокий stale-риск. Verify-first обязателен. |
| Чисто, нет related merges | Genuinely open — обычный spawn OK. |

## Fresh-source spike rule (orchestrator-side)

⛔ Phase 0 spike оркестратора, читающий код из `/Users/kitelev/Developer/exocortex-development/exocortex` (read-only main checkout), **stale-prone** — checkout НЕ auto-fetch, может отставать от origin/main на дни/недели (см. `multi-parser-predicate-migration.md` «stale main checkout» + `verify-before-assert.md`). Спайк может дать неверную картину текущего кода.

Перед spike state-claim:
- `git -C <repo> fetch origin main && git -C <repo> log HEAD..origin/main --oneline | head` — насколько stale?
- ЛИБО читай из свежего worktree / `git show origin/main:<path>`
- ЛИБО **явно caveat'ь** в child prompt: «spike из возможно-stale checkout — verify CURRENT state в свежем worktree; line numbers могут отличаться». Child работает в fresh worktree из origin/main — он authoritative.

## Запреты

- ⛔ Spawn child на backlog issue без orphan/overtaken pre-check, особенно для issues в кластере недавней работы.
- ⛔ Делать confident state-claim в Phase 0 spike, основанный на чтении stale main checkout, без fetch/caveat.
- ⛔ Передавать stale line numbers / «код silent на line N» в child prompt как факт — caveat обязателен.

## ⛔ Addendum 2026-07-30 — `gh issue list --repo X --search "A OR B"` УТЕКАЕТ в глобальный GitHub-поиск → ложный dedup-результат из ЧУЖИХ репо

<!-- Added by /session-retrospective 2026-07-30 — root: dedup-проверка перед созданием issue вернула чужие репо, номера не из целевого репо. -->

Dedup/staleness-проверка «нет ли уже такого issue» через `gh issue list --repo <o>/<r> --state all --search "<term1> OR <term2>"` может вернуть результаты **из чужих репозиториев** — `--search` с булевыми операторами уходит в глобальный `search/issues`, и `--repo` перестаёт скоупить выдачу. Симптом-tell: **номера issue не похожи на нумерацию целевого репо** (напр. `#2`, `#9`, `#373` в репо, где актуальные номера ~`#39xx`), и/или в списке видны явно посторонние проекты.

Опасность обоюдная: (а) **ложно-положительный dedup** («такой issue уже есть» → не создаёшь нужный), (б) шум, маскирующий реальный дубль.

- ✅ **Надёжный dedup** — тянуть issues целевого репо и фильтровать локально:
  ```bash
  gh api "repos/<o>/<r>/issues?state=all&per_page=100" --paginate \
    --jq '.[] | select(.pull_request == null) | "#\(.number) [\(.state)] \(.title)"' \
    | grep -iE '<term1>|<term2>'
  ```
  (`select(.pull_request == null)` отсекает PR — REST `issues` возвращает и их.)
- ✅ Либо `--search` **без** булевых операторов + `in:title,body` (как в §Mechanical pre-check выше — там форма `"$N in:title,body"` работает); множественные термы гнать отдельными вызовами.
- ⚠ Не путать с корректным `gh pr list -R $REPO --search "$N in:title,body"` из pre-check выше — там один терм без `OR`, скоуп держится.

**Эмпирика 2026-07-30** (аудит GitHub Packages → issue #4004): `gh issue list --repo kitelev/exocortex --state all --search "provenance OR sigstore OR opencontainers OR SLSA"` вернул 10 issue **чужих** репо (`#373 [skill-suggestion] Sigstore / cosign`, `#2700 Codex runtime image…`, `#55 PyPI publish…`). Поймал по несовпадению нумерации → пере-проверил через `gh api repos/…/issues --paginate` → в целевом репо совпадений **нет** (только 3 closed на смежные темы) → issue создан обоснованно. Cost: 1 ложный dedup-результат + 1 authoritative redo; урон 0 (дубль не создан, нужный issue не подавлен).

## ⛤ Addendum 2026-07-31 — АВТОМАТИЧЕСКАЯ петля (ALP) диспатчит из vault-бэклога и внешнего состояния НЕ видит: гейт живёт в генераторе промпта и ИНЖЕКТИТ факт, а не отбрасывает задачу

Всё правило выше адресовано **оркестратору** (человеку/агенту), который сам выбирает issue. Автономная петля (`alp-tick.sh`) выбирает иначе: SPARQL по vault — `ems__Project` в Doing → `Effort_parent+` → листья в Backlog. **GitHub в этом пути не участвует вообще**, поэтому задача, чей issue закрыт месяц назад, диспатчится как ни в чём не бывало, а 60-секундный pre-check из §Mechanical выполняет уже **исполнитель**, сжигая на это стартовые ходы сессии.

- ⛔ **Не «скипать» задачу с закрытым issue.** Соблазн — отфильтровать её прямо в тике. Это **потеряло бы реальную работу**: issue закрывают по существу (движок починен), но **остаток данных** часто остаётся неприведённым (ассеты не закрыты, ссылки не переписаны). Эмпирика ниже — ровно такой случай.
- ✅ **Гейт живёт в генераторе промпта** (`alp-worker-prompt.sh`), не в селекторе: извлечь `github.com/<o>/<r>/issues/<N>` из тела задачи → `gh issue view --json state,closedAt` → если CLOSED, **инжектить блок** «issue закрыт <дата>, начни с верификации, ожидай остаток, `/feature-sdd` может быть неприменим». Fail-open: нет ссылки / нет `gh` / issue OPEN → блок пуст, промпт **байт-идентичен** прежнему.
- ⛤ **Сопутствующе смягчить жёсткий мандат старта.** Промпт петли предписывал «затем `Skill: feature-sdd`» безусловно; при overtaken-задаче кода менять не нужно, и исполнитель оказывается зажат между мандатом и реальностью. Формулировка стала условной («если работа действительно требует изменения кода»).
- **Валидация гейта** — три прогона генератора: задача с CLOSED issue (блок есть, верные `repo#N` + дата), с OPEN issue (блока нет), без ссылки (блока нет, промпт цел). Это и есть RED/GREEN-дискриминатор: без третьего прогона блок мог бы печататься всегда и это выглядело бы «работающим».

Т.е. hard-skip уничтожил бы ценность, а инжекция факта её сохраняет. Cost: ~10 tool-call'ов discovery; митигация — гейт выше.

## ⛔ У ОТЛОЖЕННОГО issue протухает не только постановка, но и ОБОСНОВАНИЕ ОТЛОЖЕНИЯ — и оно однооосно по построению

Тело правила ловит **overtaken by events** (issue решён чужим PR). Отложенный issue стареет иначе и тише: он **не решается**, поэтому детектор «есть merged PR» молчит вечно. Протухают две вещи, и обе читаются как проверенный факт:

| что записано при отложении | почему протухает |
|---|---|
| **описанный «сегодняшний обход»** («пока приходится делать X») | окружение изменилось — либо обход стал не нужен, либо его **никогда не существовало** |
| **причина defer** («экономит ресурс, который не в дефиците») | она измерена по ОДНОЙ оси; вторая ось могла и не рассматриваться |

⛤ **Обоснование defer особенно уязвимо, потому что его пишут в момент отказа от работы** — то есть когда предмет не изучают дальше, а закрывают. Одноосность там норма, а не небрежность.

- ⛔ **Цена — не потерянный цикл, а построенное НЕ ТО.** Постановка, чей обход вымышлен, диктует архитектуру под несуществующую боль (у меня: «clone/cache архивного репо в temp-dir» — при том что архив **смонтирован**, и запрос его уже видит). Исполнитель по букве построит клон-механизм поверх готовых данных.
- ✅ **Floor — ОДНА команда перед взятием: проверь, что описанный обход СУЩЕСТВУЕТ.** Постановка почти всегда его называет («сегодня приходится …»). Не существует ⇒ боль не воспроизводима ⇒ переизмерить, а не исполнять.
  ```bash
  <cli> <verb> --help | grep -- '--<флаг из постановки>'   # обход через флаг
  ls -d <путь из постановки>                                # обход через файл/маунт
  ```
- ✅ **Второй floor — назвать ОСЬ, по которой мерили defer, и спросить, есть ли вторая.** Квота ≠ латентность; размер ≠ частота; частота ≠ цена одного случая. Причина defer, верная по своей оси, ничего не говорит о соседней.
- ⚠ **Симптом-tell:** ты цитируешь причину отложения в своём решении («отложено, потому что …») и **не можешь назвать команду**, которой она проверена сейчас. Тогда ты наследуешь чужой замер как факт (`self-authored-claim-loses-its-provenance` — но источник тут ещё и чужой).
- ⛤ **Исход переизмерения — НЕ «закрыть».** Вывод «работа нужна» часто выживает, меняется **обоснование и дизайн**; это и надо выписать в тело issue вслух (`graph-record-outlives-its-referent` §A8b: премисса опровергнута ≠ работа не нужна).
