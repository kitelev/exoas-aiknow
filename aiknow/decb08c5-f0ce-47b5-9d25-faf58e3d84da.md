## Разборы

## §A1 Empirical reference (onto-enum/class removal: SPARQL by-predicate НЕДОсчитывает — grep raw wikilink-refs ДО удаления)

При удалении **enum-значения / класса из онтологии** blast-radius **нельзя** мерить только SPARQL-запросом по свойству-предикату — он считает лишь **frontmatter-присвоения**, но **пропускает body/prose-wikilink-ссылки** на удаляемый UID (в aiKnow/RFC/задачах, документирующих сущность). Удалишь файл — они станут **dangling wikilinks**.

**Pre-check ДО удаления enum/class-файла:**
1. **Frontmatter-инстансы** (сколько «в статусе X» / «класса X») — SPARQL по предикату (`?s ems:Effort_status <uid>`).
2. **⛤ ВСЕ raw-ссылки** на UID (frontmatter + body + option-lists) — `grep -rl '<uid>' <vaults>/*/assetspaces`. Разделить: `[[<uid>]]`-**wikilink**-форма (создаёт dangling → переписать/удалить) vs backtick/plain-text-упоминание (историческая проза, НЕ link → оставить).
3. **Option-set / SHACL-ссылки** — enum обычно в `exo__schema_options` list (`optionSetFor` свойства) И/ИЛИ SHACL `sh:in`. Их править **удалением строки списка** (multi-value REMOVE → hook блокирует Edit → Bash-python + SHACL post-validate), НЕ text-конвертацией строки (сломает YAML-список).
4. **Что создаёт значение** — команды/groundings, переводящие в удаляемый статус (`grep <uid>|<Label>` в exocmd). Орфан (0 создателей) = чище.

**Removal-цепочка:** мигрировать frontmatter-инстансы (санкц. CLI, напр. `apply mark-done-post-factum`) → убрать из option-set (все vault-копии shared-TBox) → переписать `[[<uid>]]`-wikilinks → `rm` enum-файл (все копии) → **verify 0 `[[<uid>]]` осталось** → SHACL post-validate 0 → ExoSync (shared-TBox → все устройства) → verify на remote (файл 404 + option-set 0 refs).

## §A3 Empirical reference (class-CONSOLIDATION миграция инстансов: issue-count из ОДНОГО vault недосчитывает per-profile; 3-persistent-vault даёт direct-migration без temp-vault; swap на pre-dual-typed инстансе → DUPLICATE класса)

Миграция инстансов с **deprecated-класса на canonical** (`exo__Instance_class [[old]]→[[new]]`, тот же UID/filename → incoming `[[uid]]`-wikilinks к инстансам НЕ переписывать, только verify) в EKA-архитектуре из **трёх persistent-vault** (vault-my/tbank/exodev, git-free ExoSync, каждый монтирует свой набор assetspace'ов). Три reusable-приёма:

1. **⛤ Issue-заявленный instance-count из ОДНОГО vault СИСТЕМАТИЧЕСКИ недосчитывает** — тот же profile-mount undercount, что [[verify-before-assert]] (2026-06-16). Если issue/характеризация запрашивала SPARQL по `vault-tbank`, а часть инстансов живёт в `exoas-my` (монтируется ТОЛЬКО в vault-my) — они невидимы. **ДО «полной» миграции — cross-vault sweep по ВСЕМ трём vault** (`SELECT ?s WHERE { ?s exo:Instance_class <ontology/<ns>#<Class>> }` в каждом; symbolic-IRI-форма per [[sparql-iri-form-pre-verify]]) + дедуп по assetspace (shared-* считаются в нескольких vault, но это ОДИН файл). 2. **3-persistent-vault → DIRECT migration, temp-vault НЕ нужен.** Старый план (temp-«всё»-профиль в fresh vault, т.к. ни один профиль не монтировал my+tbank вместе) устарел: теперь three vaults TOGETHER монтируют все нужные assetspace'ы. **Рецепт:** редактируй каждый assetspace в ТОМ vault, что его монтирует (exoas-my→vault-my; exoas-tbank/shared-tbank→vault-tbank; shared-* — В ОДНОМ vault один раз). **Порядок (Андрей):** tbank+shared-AS ПЕРВЫМ (правь shared-identities/private/public в vault-tbank, push), ПОТОМ `exosync sync` vault-my/exodev чтобы ПОДТЯНУТЬ мигрированные shared (converge локальные копии), затем правь vault-специфичные (exoas-my, exoas-pmbok). Property domain/range-refs (`[[old]]→[[new]]`) идут вместе с инстансами (для AC «0 [[old-uid]] refs»). Класс оставить `exo__DeprecatedClass` (не удалять — subclass-bridge). ## §A4 Empirical reference (retiring a SCRIPT: caller-check ОБЯЗАН включать `.md`/skill-файлы — скиллы вызывают скрипты как шаги)

При ретайре/удалении shell-скрипта (launchd-джоб, helper) discovery-фильтр «кто его вызывает» **нельзя** ограничивать `.sh`/код-файлами. **Скиллы (`SKILL.md`) и доки вызывают скрипты как шаги воркфлоу** (`bash ~/dotfiles/scripts/X.sh …` внутри SKILL.md) — они полноценные callers. Caller-grep, исключающий `.md$`, **молча прячет skill-callers** → удаляешь скрипт → в скиллах остаются dangling-ссылки на несуществующий шаг (латентно — всплывёт при следующем запуске скилла).

- **Floor:** `grep -rln '<script-basename>' ~/.claude ~/dotfiles` **БЕЗ** `grep -v '\.md$'` (исключать только `graveyard` + session-`.jsonl`-логи). `.md`/`SKILL.md`-совпадения = реальные callers, проверить каждый.
- ⚠ Родственно config-hardcoded-path discovery-dependency (пре-греп `<abs-path>`, floor ниже): та же ошибка «искал не во всех типах файлов, где живёт зависимость».
- **Empirical (2026-07-29):** удалил `vault-sync-cycle.sh` после caller-grep, который исключал `.md$` → пропустил, что **3 live-скилла** (pmbok-status/close/orchestrator-prompt) мандатят его как шаг «свежий cache перед SPARQL». Оставил dangling-ссылки; поймал при попытке ретайра самого скилла (grep без `.md`-исключения). Fix: заменил vault-sync-cycle-шаг на `rm cache` во всех 3 скиллах. Cost: 1 недосмотр + 9 доп. правок в 3 скиллах. Cross-tie [[verify-before-assert]] (negative «нет живых callers» = grep всех типов файлов, не подмножества).

## §A5 ⛤ Addendum 2026-08-02 — «migration-first» без ДОКАЗАТЕЛЬСТВА паритета = обычный remove с лишними шагами; и перенос тестов обязан сохранить их в ГЛОБЕ сканера

Секция §CLI-command removal (2026-07-11) отвечает на вопрос «можно ли удалять» (enumerate consumers). Этот аддендум — про **как исполнить перенос**, когда ответ «нельзя удалять, пока не мигрируешь живого консьюмера». Два механизма; оба — про то, что делает migration-first проверяемым, а не декларативным.

**1. ⛤ Паритет доказывается ЗАПУСКОМ обоих путей на ОДНОМ дереве, до удаления старого — и сравнением КАНОНИЗОВАННОГО вывода.**

Порядок обязателен: старый путь ещё жив ⇒ можно получить эталон. Удалил сначала — эталона больше нет, и «оно работает так же» становится непроверяемым навсегда.

- Прогнать оба на **реальном** корпусе (не на фикстуре) с одинаковыми аргументами, сохранить JSON.
- Сравнивать **канонизованно** (рекурсивно отсортировать массивы + ключи), а не `diff` байт-в-байт: перенос почти всегда меняет ПОРЯДОК (другой обход файлов), и сырой diff утонет в перестановках, пряча настоящее расхождение.
- Сравнивать И **exit-код** — для гейта он и есть вердикт.
- ⚠ **Эталон снимать на ТОМ ЖЕ дереве, что и новый путь.** Снимок «до копирования файлов» даёт ложную дельту: у меня `tagCount` 431→433, и это были ровно два `@req`-токена в скопированном тесте — то есть артефакт момента съёмки, а не расхождение инструментов. Пересъёмка эталона на текущем дереве дала полное совпадение.
- Порядок как таковой при этом **улучшать можно** (детерминированная сортировка вместо сырого glob-обхода) — но назвать это отдельным швом в описании переноса, иначе следующий читатель примет перестановку за дрейф.

**2. ⛤ Тесты, несущие `@req`-биндинги ACTIVE-требований, обязаны приземлиться в путь, который сканер ВСЁ ЕЩЁ матчит.**

§CLI-command removal уже требует проверить `@req` в тестах удаляемой команды. Недостающая половина: при **переносе** (а не удалении) биндинг выживает, только если новый путь попадает в `DEFAULT_TEST_GLOBS` аудита (`**/*.test.ts|tsx`, `**/*.spec.ts|tsx` от корня репо, см. [[req-first-sdd-ci-binding]]).

- ⛔ Это **отсекает** соблазн переписать перенесённые тесты на `node --test`/`*.test.mjs` ради «самодостаточности тула»: `.mjs` в глоб не входит ⇒ ACTIVE-требования осиротеют ⇒ `requirements-trace` красный на КАЖДОМ PR репо-wide. Форма раннера здесь диктуется не вкусом, а глобом сканера.
- Практическое следствие: цель переноса — **приватный workspace-пакет с jest** (`packages/<tool>/tests/**/*.test.ts`), а не «скрипт в `scripts/` + node:test». Тогда перенос тестов = смена одной строки импорта.
- **Verify — эмпирический, не рассуждением:** `tagCount` до/после переноса и `activeViolations` в отчёте. Биндинги живы ⇒ счёт тегов вырос/не изменился; осиротели ⇒ `activeViolations` непуст. Авторитетно это подтверждает **CI гейт на PR**, а не локальный прогон.
- ⛤ **Оба шага в ОДНОМ PR, если перенос временно ДУБЛИРУЕТ биндинг.** Копия тестов + оригинал = один UID в двух путях (`duplicates` в отчёте — warning, не блокер). Разнеся шаги по двум PR, кладёшь это состояние в `main` на весь промежуток. Порядок «сначала мигрируй консьюмера, потом удаляй» сохраняется **внутри** PR последовательностью коммитов — этого достаточно, окна в `main` при этом не возникает вовсе.

**Empirical (2026-08-02, RFC 7c7859d1 W-req, PR #4015 → v16.206.1):** `requirements audit` вынесен из `@kitelev/exocortex-cli` в приватный `packages/req-audit` (ноль импортов core/services/cli ⇒ CI-джоба перестала собирать три пакета), `ci.yml`/ADR REQ-001/доки переключены, затем верб удалён (реестр 26→25). Паритет: 150 req / 433 tag / 6 orphans / 3 floor / 0 activeViolations и exit 1 — идентично старому пути на одном дереве. ## §A6 ⛤ Addendum 2026-08-02 — ретайр АРХИТЕКТУРЫ: ХЕДЖ над мёртвым путём ≠ его ЗАМЕНА; аннотация оставляет путь исполнимым на вид и живёт дольше самого пути

Секция §«retiring a SCRIPT» (2026-07-29) требует включать `.md`/скиллы в caller-check. Недостающая половина — **что делать с найденным caller'ом**. Естественный (и неверный) ход: дописать сверху предупреждение — «⛔ возможно, X больше нет; сначала проверь `[ -e … ]`; если нет — шаги ниже неприменимы» — и **оставить мёртвые шаги на месте**. Выглядит как добросовестная осторожность, а на деле оставляет три дефекта:

- ⛔ **Хедж заставляет КАЖДОГО будущего читателя платить пробой** за факт, который устанавливается один раз. «Может быть git-free» — незакрытый вопрос; «git-free, ветки git не существует» — закрытый.

- ⛤ **Хедж переживает свой предмет.** Аннотация датируется моментом сомнения; когда сомнение разрешается (архитектура снята **полностью**), никто не возвращается её снять — она не «сломана», она просто устарела и потому не привлекает внимания. Мёртвый блок под ней тем более.

**Floor:** ретайр архитектуры (не одного скрипта) закрывается только **заменой** пути в caller'е на работающий, а не предупреждением над ним. Проверка: *«может ли читатель, следуя этому файлу, всё ещё попытаться пойти по снятому пути?»* Да → работа не завершена. И **удаляй сам хедж вместе с блоком**: оставшись, он противоречит новому пути и указывает на шаги, которых уже нет (ровно тот класс, что ловит `/contradiction-sweep`).

⚠ **Признак незавершённого ретайра — условная формулировка в caller'е** («may be», «возможно», «probe first», «если ещё существует»). Грепнуть их по скиллам при закрытии любого ретайра: `grep -rn 'probe first\|may be a\|если ещё' ~/dotfiles/.claude/skills/*/SKILL.md`.

## §A7 ⛤ Addendum 2026-08-03 — переезд vault: grep по ПУТЯМ находит скрипты, но НЕ находит два класса потребителей, где путь лежит как ДАННЫЕ

✅ **Floor (поднят в тело из вынесенной эмпирики 2026-06-27):** перед relocation/переименованием vault — пре-греп `<abs-path>` по скиллам и хукам. Он ловит потребителей, у которых путь — **строка в исполняемом коде**. Но переезд vault ломает ещё два класса, и в обоих путь лежит **как данные**, поэтому грепу по коду они видны хуже, а последствия — тише:

1. ⛔ **Реестр фонового демона** (список «за какими vault я слежу»). Демон продолжает работать, регулярно просыпается, пишет бодрый лог — и **смотрит не туда**. Не падает, не ругается, метрик не портит. Обнаруживается только когда человек замечает, что чего-то не происходит.

**Floor:** относить к discovery-dependency не только «где путь написан», но и «где путь **зарегистрирован**». При переезде/переименовании vault ревизовать, помимо кода:

```bash
grep -rln "$OLD" ~/dotfiles/scripts/*/            # реестры демонов (BOTS=[...], VAULTS=(...))
grep -rln "$OLD" ~/.*-claude/settings.json        # allow-list песочниц

```

  ```bash
  for j in $(launchctl list | grep -oE 'com\.kitelev\.[a-z-]*assistant\.poll' | sort -u); do
  ```

## §A9 ⛔ Addendum 2026-08-03 — ПЕРЕсчёт при классификации «дефектных» ассетов: признак-по-одному раздувает scope на порядок и предлагает снести живое

§2026-07-12 (выше) закрывает **недо**счёт: замер по одному vault пропускает инстансы. Зеркальная и более опасная ошибка — **пере**счёт: замер, который решает, *что дефектно*, помечает таковым легитимные данные. Недосчёт оставляет работу недоделанной; пересчёт **назначает разрушительную мутацию** и выглядит при этом как добросовестная уборка.

⛤ **Механизм — классификация по ОДНОМУ признаку там, где истина определяется ЦЕПОЧКОЙ.** «Цель не прототип» нельзя решить по имени класса или по одному значению `exo__Instance_class`: у цели этих классов бывает **несколько**, и достаточно, чтобы **хоть один** дошёл по `exo__Class_superClass` до нужного предка. Замер, взявший первый попавшийся класс, объявляет дефектным всё, чей «главный» класс назван иначе.

**Три независимых источника пересчёта — проверять каждый до мутации:**

| Источник | Симптом | Floor |
|---|---|---|
| **Один класс из нескольких** | В группировке доминирует класс, который «не похож» на нужный (`ems__Recurring` вместо `ems__TaskPrototype`) | Классифицировать по **всем** `exo__Instance_class` + обходу `superClass` (как это делает движок), не по первому |
| **Цель не резолвится в ЭТОМ vault** | Массовые `TARGET-MISSING` | Строить индекс UID по **всем** vault; отсутствие в одном ≠ отсутствие ([[exocortex-cold-archive-assetspace]] §Addendum 2026-08-02) |
| **Разные дефекты в одном счёте** | «N дефектных» без разбивки | Разложить по видам: у каждого своя операция, и «удалить» подходит меньшинству |

- ⛤ **Симптом-tell, сильнее любых проверок: доля «дефектного» неправдоподобно велика.** Если механизм чинили давно, а «сломанного» половина корпуса — почти наверняка сломан замер, а не данные. Живой контрпример находится за минуту: посмотри на **самые свежие** записи в «дефектной» группе. Свежие ⇒ механизм работает сейчас ⇒ это не мусор.
- ⛤ **«Битая ссылка» — гипотеза, а не приговор.** Прежде чем удалять, попробуй **зарезолвить UID из старого пути**: цель часто жива, а устарела только форма ссылки. Тогда правильная операция — **восстановить** в UID-canon, а не вычистить. Обратный порядок необратим.
- ⛔ Не принимать число из issue / прошлой сессии / RFC за факт: оно тоже чьё-то измерение ([[graph-record-outlives-its-referent]]). Пересчитывать своим проходом **перед** мутацией, а не после.
- ✅ **Verify — пост-замер тем же кодом:** дефектных `0`, а легитимных **больше**, чем до правки (на число восстановленных). Убыль легитимных = ты снёс живое.
**Cross-tie:** [[verify-before-assert]] (число из артефакта = claim), [[sparql-iri-form-pre-verify]] (dual-IRI ломает join цель→класс→superClass — при отказе SPARQL честный обход делается скриптом с `# dogfood-fallback`), [[vault-asset-creation]] (bulk-python + backup + SHACL floor), [[concurrent-session-vault-write-isolation]] (пушить из vault без чужого WIP).

## §A10 ⛤ Addendum 2026-08-05 — «куда перенацелить путь» — УЖЕ неверный вопрос, если мёртв ПОТРЕБИТЕЛЬ: отчёт называет один слой, решает другой

§Addendum 2026-08-02 (выше) отвечает на «что делать с найденным caller'ом» — **заменить** путь, а не аннотировать. Недостающий предшествующий вопрос: **а надо ли заменять вообще.** Отчёт о мёртвом пути (issue, задача, находка ревью) по построению называет **тот слой, который сломался заметно** — обычно producer: «скрипт вызывает несуществующий файл». Дальше рука сама тянется к «перенацелить под новую архитектуру», и это ощущается как добросовестная починка.

⛤ **Но у фичи, дожившей до смерти producer'а, обычно мертвы ВСЕ слои** — просто остальные умерли **тихо**, потому что их отказ никто не наблюдает:

| слой | как умирает | как выглядит снаружи |
|---|---|---|
| **producer** | путь/скрипт снесён | громко: `No such file`, если кто-то смотрит в лог |
| **транспорт** | демон/диспетчер декоммиссирован | тихо: процесса нет, порт не слушается — но никто не проверяет |
| **потребитель** | обработчик удалён вместе с архитектурой | ⛔ **невидимо**: вход просто дропается штатной веткой |
| **схема** | property-def / класс удалён | ⛔ **невидимо**: значения во frontmatter остаются валидными строками |

- ✅ **Floor: до решения «переписать или удалить» — перечисли ВСЮ цепочку и предъяви каждый слой отдельно.** Решающий слой почти всегда **не назван в отчёте**: он потому и не назван, что его смерть бессимптомна.
- ⛤ **Дискриминатор для потребителя — ЧИТАТЬ ОБРАБОТЧИК, а не грепать имя фичи.** Потребитель имени фичи не содержит (он ловит транспортный примитив), поэтому `grep <имя-фичи>` даёт честный ноль и читается как «потребителя нет в этом файле». Смотреть надо на **форму сравнения**: точное сравнение (`text in ("/start","/help")`) + следом обобщённый ранний выход (`if text.startswith("/"): return`) означает, что параметризованный вход **явно отбрасывается**, а не «просто не обработан». Это сильнее, чем «обработчик не найден».
- ⛔ **Данные, пережившие механизм, — ловушка, а не доказательство жизни.** Ассеты продолжают нести значения, которые фича когда-то записала; выглядит как работающая фича (та же ось, что [[graph-record-outlives-its-referent]]). Проверяется ровно наоборот: **кто эти значения ЧИТАЕТ**. Никто → это осадок, а не функция.
- ⛤ **Асимметрия цены решает развилку.** «Переписать» без аудита потребителя = построить фичу, у которой потребителя нет (и обнаружить это после отгрузки). «Удалить», когда producer невосстановим, не теряет ничего: переиспользовать нечего, а будущая реализация под новую архитектуру всё равно проектируется с нуля — то есть удаление ей **не мешает**, и это стоит написать в решении явно, иначе следующий читатель прочтёт его как закрытие темы.

**Revert-verify для УДАЛЕНИЯ** (форма неочевидна — казалось бы, «нечему краснеть»):
1. **RED = доказательство мёртвости на ДО-состоянии**, исполняемое: скормить хуку/скрипту квалифицирующий вход, показать, что все гейты проходят, payload падает, а вызывающий видит `exit 0`. **Обязателен негативный контроль** (вход, не проходящий гейты, до payload не доходит) — иначе «payload не сработал» тождественно-истинно и ничего не доказывает ([[self-satisfying-metric-weak-verifier]]).
2. **GREEN = утверждения о ПОСЛЕ-состоянии** (артефакт удалён, регистрация снята, конфиг валиден, счётчик −1 и **ровно один** элемент исчез).
3. **Revert-verify самих утверждений** — прогнать их против **восстановленной копии** в `/tmp` (рабочее дерево не трогать, [[integration-test-revert-verify]] §ZERO-GIT-TOUCH): дискриминирующие оси обязаны покраснеть, не-дискриминирующие — остаться зелёными.

⚠ **Payload, запущенный фоном (`&` + `disown`), пишет свой лог ПОСЛЕ выхода хука** — проверка того же тика даёт **ложно-отрицательное** «payload не запускался». Между запуском и наблюдением нужен settle (~1 с). Без него доказательство мёртвости само оказывается сломанным — и в сторону, подтверждающую желаемое.

⛤ **Класс дефекта мерить ДО того, как строить против него guard.** Мёртвый payload-путь выглядит как эпидемия («сколько ещё таких?»), но это гипотеза: один проход по всем зарегистрированным хукам даёт точное число. Популяция = 1 ⇒ постоянный guard не строить ([[pilot-tool-before-broad-rollout]]), тем более в репозитории без CI, где ручной скрипт тихо сгниёт ([[bash-loop-eval-pitfalls]] Г3c). Замер — одна команда, и он же становится доказательством «после правки ноль».

## §A11 ⛔ Addendum 2026-08-05 — «вынести из КОНТЕЙНЕРА X» — постановка по ИМЕНИ; реальный scope задаёт ПРИЗНАК, и он почти всегда шире одного контейнера

Задача на вынос/расчистку формулируется через **имя вместилища** («вынести всё из `exoas-shared-identities`», «почистить папку X», «разгрузить репо Y») — потому что именно там дефект **заметили**. Но вместилище — это место обнаружения, а не определение множества. Настоящее множество задаётся **признаком** («ассет, чей дом ≠ его текущий ассетспейс»), и по признаку оно, как правило, лежит в **нескольких** контейнерах сразу.

- ⛔ **Мигрируя по имени, получаешь работу, которая выглядит завершённой и не завершена.** Названный контейнер пустеет, приёмочный критерий «в X ничего не осталось» выполняется — а тот же дефект продолжает жить в соседнем контейнере, который никто не назвал. Обнаружится он не сразу и будет выглядеть как новая проблема.
- ✅ **Floor: до миграции сформулировать ПРИЗНАК и прогнать его по ВСЕМУ графу, без фильтра по контейнеру.** У «дома» ассета признак структурный — где резолвится его `ems__Effort_area` / `_parent` / `exo__Asset_prototype` (см. §STEP 1 в `/cross-vault-migrate`), а не в какой папке он сейчас лежит. Запрос без ограничения по ассетспейсу и есть проверка полноты.
- ⛤ **Разница «имя vs признак» — это же и объяснение расхождения счёта.** Оценка из постановки (~50) и замер по признаку (101) расходятся не потому, что кто-то ошибся в арифметике: они считают **разные множества**. Поэтому вопрос «почему у меня в два раза больше?» решается не пересчётом, а сверкой определений — и ответ обычно «нашёлся источник, которого постановка не знала».
- ⚠ **Симптом-tell:** приёмочный критерий сформулирован через контейнер («в X пусто»), а не через признак («нет ассетов, чей дом ≠ ассетспейс»). Первый выполним при незакрытом дефекте; второй — нет.

### ⛔ Addendum 2026-08-11 — ложным разделителем бывает не только ИМЯ КОНТЕЙНЕРА, но и ИДИОМА РЕАЛИЗАЦИИ; а признак — не только структурный, но и КЛАСС ДАННЫХ

| | постановка / первый заход | настоящее множество |
|---|---|---|
| §выше | имя контейнера (`exoas-shared-identities`) | структурный признак («дом ≠ ассетспейс») |
| **здесь** | **идиома записи** (`tmp → os.replace`) | **класс данных** («несёт текст пользователя») |

- ⛔ **Идиома — особенно убедительный ложный разделитель, потому что она ТЕХНИЧЕСКИ ОСМЫСЛЕННА.** «Атомарные писатели» — настоящая категория с общим рецептом фикса (chmod на TMP, а не на цель), поэтому граница по ней выглядит выведенной из механизма, а не назначенной. Имя контейнера так не выглядит — оно очевидно про место обнаружения.
- ⛔ **Пропущенная половина систематически БОЛЬШЕ названной.** Постановка называет то, где дефект **заметили**, а заметен он чаще на транзиентном/маленьком объекте (его открывают глазами). Долгоживущая копия того же класса — лог, дамп, кэш, снапшот — накапливается молча и потому в постановку не попадает. ⇒ «починил названное» защищает **меньшую** часть поверхности, а отчёт при этом верен пословно.
- ✅ **Floor: сформулировать признак ТРЕБОВАНИЯ и прогнать его по всему дереву, игнорируя идиомы.** Один обход: «какие файлы несут <класс данных>?» — а не «какие файлы пишутся так же, как названный». Для секретов/PII это буквально `find <корни> -name '<имена артефактов>'` + перечисление режимов; идиома тогда решает лишь **как** чинить каждый найденный, но не **кого** искать.
- ⚠ **Симптом-tell, ловится до правки:** ты можешь назвать общий **приём фикса** для найденных мест («у всех chmod на tmp») раньше, чем назвал общий **признак**, по которому их искал. Это признак, что множество собрано по реализации.
- ⛤ **Следствие для DoD:** критерий «оба писателя ставят 0600» проверяем и выполним при незакрытом дефекте — ровно как «в контейнере X пусто». Честная форма — по признаку: «нет файла с <классом данных>, чей режим шире 0600», и она автоматически втягивает писателей, которых постановка не знала.

## §A12 ⛔ Addendum 2026-08-06 — ассет может быть ПОЛОВИНОЙ сущности: архивация/удаление одной половины ХУЖЕ бездействия, а проверка «есть ли двойник» по ОДНОМУ классу даёт ложный ноль

Все секции выше проверяют **сам ассет** (кто на него ссылается, где его дом, что он несёт). Недостающий вопрос: **а один ли он?** Одна реальная сущность нередко живёт как **2-3 файла разных классов** — результат недомигрированного namespace, параллельного моделирования или того, что её завели дважды в разных ролях.

- ⛔ **Архивировать/удалять половину — активный вред, а не половина уборки.** Оставшаяся половина продолжает резолвиться и выглядеть живой, а половина рёбер сущности исчезает из выдачи. Получается состояние **хуже исходного**: до операции сущность была раздвоена, но целиком видима; после — раздвоена и наполовину невидима, причём молча.
- ⛤ **Дискриминатор «ошибка копирования vs функциональное расщепление» — РАСПРЕДЕЛЕНИЕ ПРЕДИКАТОВ по половинам.** Если у одной половины систематически справочные рёбра, а у другой — рабочие, это **не дубль по недосмотру**, а неотмоделированная двойная роль. Считать так:
  ```sparql
  SELECT ?o ?p (COUNT(?s) AS ?n) WHERE { ?s ?p ?o . FILTER(?s != ?o)
    FILTER(?p != exo:Asset_uid && ?p != exo:Asset_filename && ?p != exo:Asset_isDefinedBy) }
  GROUP BY ?o ?p
  ```
  Роли разошлись ⇒ наивное слияние сломает одно из двух употреблений; сперва решается **модель**, потом переписываются рёбра.
- ⛔ **Проверять двойника надо по ВСЕМ классам, а не по тому, о котором подумал первым.** Ноль пересечения с одним слоем **не** доказывает отсутствие дублей — сущность могла раздвоиться с легаси-классом, о котором ты не вспомнил. Дёшево: сгруппировать по label и посчитать **число ФАЙЛОВ** на label, не сверяя со списком классов вручную:
  ```sparql
  SELECT ?s ?l ?c WHERE { ?s exo:Asset_label ?l . ?s exo:Instance_class ?c
    FILTER(CONTAINS(STR(?l),'<ключевое слово домена>')) }
  ```
  → `label → {файл: [классы]}`; **файлов > 1 = дубль**, `len(классы) > 1` у одного файла = dual-typing (это другое и обычно норма).
- ⚠ **Симптом-tell:** ты сравниваешь два слоя по названиям, получаешь **ровно 0 совпадений** и делаешь вывод «слои описывают разные сущности». Нулевое пересечение подозрительно само по себе: если слои и правда про одно, хоть одно имя совпало бы. Ноль обычно означает, что сравнил не с тем слоем.
- ✅ **Цена сведения меряется рёбрами, а не файлами** — и она, как правило, мала: сущностей-двойников единицы, рёбер на них десятки. Дорогая часть — **решить модель** (какой слой каноничен, куда цепляются рабочие ссылки), а не переписать ссылки.

**Empirical 2026-08-06** (разбор 39 областей vault-tbank без эффортов): оргструктура смоделирована **тремя** слоями (`orgunit__OrgUnit` 18 · легаси `inbox__Chapter` 9 + `inbox__BusinessUnit` 3 · `ems__Area` ~18). Пересечение имён с `orgunit__OrgUnit` — **0**, и я почти записал «слои описывают разные сущности». Сверка по label **без** фильтра по классу дала **8 сущностей как 2 файла** (`CVM QA Chapter`, `TOOS Group IT/QA/SA/SDE/SRE/Technical Chapter`, `Sales Offering SA Chapter`). Распределение предикатов: Chapter-половины — `Asset_relates` + `OrgUnit_parent` (14 рёбер), Area-половины — `ems__Effort_area` (10 эффортов) + `Area_parent` (21 ребро) ⇒ функциональное расщепление, не копипаста. Три из них стояли в списке на архивацию; архивация спрятала бы рабочую половину живой сущности. Blast-radius сведения — 35 рёбер на 16 файлов.

## §A13 ⛔ Addendum 2026-08-07 — ОБРАЗЕЦ ПОКРЫВАЕТ НЕ ВСЁ: прецедент доказывает ФОРМУ, но не РАЗМЕЩЕНИЕ; рецепт переноса КЛАССА не покрывает СВОЙСТВО

Два механизма одного класса: ты копируешь работающий образец, он честно работает — и молчит ровно о том измерении, которое в твоём случае решающее. Оба вскрылись в одном заходе.

### 1. ⛤ Прецедент доказывает, что форма ВАЛИДНА, и НЕ доказывает, что размещение ВЕРНО

«Gate-0 через прецедент» (эмпирика — в архиве) — сильная техника: живой аналог в целевом паттерне доказывает, что движок такую конструкцию поддерживает, и это дешевле чтения исходника. Но у неё есть граница, которую сама формулировка не называет: **прецедент — свидетельство о МЕХАНИЗМЕ, а не об АРХИТЕКТУРЕ.** Он может нести собственный латентный дефект, и тогда копирование целиком его тиражирует.

- ⛔ **Самый частый дефект прецедента — НАПРАВЛЕНИЕ ВИДИМОСТИ.** Определение живёт в более широко видимом пространстве, а его `range`/зависимость — в более узком. Отказ **тихий**: у того, кто монтирует широкое пространство без узкого, ссылка не резолвится, и `sh:class` **не падает, а замолкает** — «unresolvable ref, not validated». То есть констрейнт формально есть и фактически не проверяет ничего.
- ✅ **Floor: у прецедента копируй ФОРМУ, а размещение выводи из СВОЕЙ пары видимостей.** Перед копированием — один `find` по обоим концам прецедента (`domain` и `range`) и вопрос «направление у него вверх или вниз?». Вниз ⇒ образец несёт дефект, бери из него только конструкцию.
- ⚠ **Симптом-tell:** прецедент и твой случай различаются тем, **в каких ассетспейсах лежат половины**. Если различаются — размещение обязано быть выведено заново, даже когда форма совпадает дословно.
- ⛤ **Побочная выгода проверки:** она вскрывает дефект в самом прецеденте. Это находка, а не помеха — но чинить чужое в том же заходе не обязательно; достаточно не воспроизвести.

⛔ **Дефект прецедента ОКАЗАЛСЯ ЖИВЫМ, а не латентным — «латентный» был непроверенным предположением.** Формулировка выше по умолчанию считает такой дефект спящим («сломается у того, кто смонтирует…»), и это усыпляет: спящее чинить не срочно. Замер того же дня опроверг: **8 из 18 монтажей** держали публичное пространство БЕЗ приватного, то есть `range` был неразрешим и `sh:class` молчал **прямо сейчас**, на **12 живых рёбрах**.
- ✅ **Floor: «латентный» — claim, а не вывод из направления.** Стоит одну команду — перечислить монтажи и посчитать, у скольких есть верхний конец без нижнего:
  ```bash
  for d in ~/vaults/*/; do k="$d/assetspaces/kitelev"; [ -d "$k" ] || continue
    [ -d "$k/<где-определение>" ] && [ ! -d "$k/<где-range>" ] && echo "ЖИВОЙ: $(basename $d)"; done
  ```
  Пусто ⇒ действительно латентный. Непусто ⇒ дефект работает, и «не воспроизводить» уже недостаточно.
- ✅ **Рецепт починки — двигать НАМЕСПЕЙС ЦЕЛИКОМ вниз, к `range`, а не переписывать ссылки.** Анкер онтологии едет вместе с определениями ⇒ `exo__Asset_isDefinedBy` **не меняется**, и co-location сохраняется **by construction**: это чисто физическая релокация. Гвард в скрипте — сверить состав папки с ожидаемым множеством (анкер + классы + предикаты) и отказаться при расхождении; тогда «намеспейс целиком» становится проверяемым фактом, а не намерением.
- ⛤ **Семантика фикса честнее, чем кажется:** после переноса у монтажа «только верхний конец» определение не «чинится», а **исчезает вместе со своим предметом** — инстансы всё равно живут ниже. Констрейнт, который молча не проверял, заменяется отсутствием констрейнта там, где нечего проверять.
- ⛤ **Канарейка даёт КОЛИЧЕСТВЕННОЕ подтверждение покрытия, а не только «жив/мёртв».** Нацелив `range` на не-класс (анкер онтологии) и вернув обратно, смотри **дельту**: она обязана совпасть с числом живых рёбер. Совпала ⇒ констрейнт покрывает ровно их; разошлась ⇒ покрытие не то, что ты думаешь. Эмпирика: 6 → **18** → 6, дельта 12 = ровно 12 рёбер.
### 2. ⛤ Единица миграции у КЛАССА и у СВОЙСТВА — РАЗНАЯ

Рецепты выше отработаны на **классах**, и там верно: переименование = правка **одного файла определения**, а все `[[uid]]`-ссылки следуют сами (голый UID к метке не привязан). Перенося **свойство**, тот же рецепт даёт молчаливую поломку.

- ⛔ **Свойство употребляется как КЛЮЧ frontmatter, а ключ — это его МЕТКА, не UID.** Переименовал определение, не тронув употребления ⇒ получил ровно **orphan-предикат**: ключ в инстансах ссылается на имя, которого больше нет; определение существует, но ни с чем не связано. Ни SHACL, ни `validate-wikilinks` этого не ловят — ключ синтаксически валиден, просто необъявлен.
- ✅ **Floor: единица переноса свойства = файл определения ПЛЮС каждое употребление.** Перед переносом — `grep -rn '^<old-label>:' <vault>/assetspaces` (якорь на начало строки: ключ стоит в начале, упоминание в прозе — нет). Число совпадений и есть объём правки.
- ⚠ **Дискриминатор общий:** спроси, **может ли переименовываемое появиться как ключ frontmatter**. Да ⇒ метка несущая, автоматики не будет. Нет ⇒ ссылки последуют сами.
- ⛤ **Трио «родитель + подкласс + предикат» переносится НЕРАЗРЫВНО**: у подкласса `superClass` ведёт к родителю, у предиката `domain` — к одному из них. Разнеся их по namespace, получишь ту же ссылку вниз, что в п.1.

## §A14 ⛤ Addendum 2026-08-07 (кросс-трековый) — КРИТЕРИЙ ОТБОРА НА УДАЛЕНИЕ систематически меряет ПРОКСИ, а не несущее свойство: три арки, три разных прокси, один промах

Секции выше лечат **отдельные** ошибки замера (недосчёт по одному vault, пересчёт по одному признаку, пропущенный слой). Срез поверх целой сессии показывает, что это не три случая, а **один класс**: всякий раз, когда работа начиналась с плана «убрать N штук по признаку», признак оказывался **коррелятом**, а несущее свойство лежало в другом месте — и подмножество, которое нельзя было трогать, **выглядело неотличимо** от остальных.

| арка | критерий отбора | что на самом деле несло нагрузку |
|---|---|---|
| ревью 96 ассетов в Doing | **номер в списке** | класс и тело ассета |
| разбор областей без работы | **ноль эффортов** | вторая половина расщеплённой сущности |
| чистка легаси-префикса | **ноль инстансов / ноль ссылок по UID** | роль родителя в иерархии + ссылки в symbolic-форме |

- ⛔ **Ни один пер-оконный разбор класс не назовёт**, потому что в своём окне каждый промах выглядит частным: «номера бывают не тем, чем кажутся», «областей без эффортов не бывает мёртвых», «UID-поиск не видит symbolic». Три частных объяснения вместо одного общего.
- ✅ **Floor перед любым bulk-removal: назови НЕСУЩЕЕ свойство вслух и предъяви, что критерий меряет ЕГО, а не коррелят.** Один вопрос: «что именно сломается у того, кого я уберу?» Ответ («его перестанут находить по ссылке», «его половина осиротеет», «его подкласс потеряет родителя») сразу показывает, тот ли признак ты считаешь.
- ⛤ **Тели у трёх арок РАЗНЫЕ и потому не переносятся** (доля дефектного неправдоподобна · нулевое пересечение имён · ноль по UID при живом классе). Переносится не тель, а **вопрос**. ⇒ не пытайся собрать один детектор; собери привычку спрашивать.
- ⚠ **Цена асимметрична всегда:** проверка критерия стоит один запрос, удаление необратимо. При этом во всех трёх арках проверку запускало **внешнее сомнение** (реплика фаундера, канарейка, несовпадение двух форм поиска), а не сам план — то есть по умолчанию критерий не проверяется вовсе.

## §A15 ⛔ Addendum 2026-08-07 — перенос СЕКЦИИ внутри корпуса — это МИГРАЦИЯ, и у неё ДВА невидимых потребителя: скрипт-парсер и in-file ссылка «§X выше/ниже»

Тело правила требует характеризовать discovery-фильтр **перед перемещением файлов**. Тот же чек-лист обязателен при переносе **секции** (архивация истории, вынос эмпирики, дробление правила) — и там его пропускают, потому что «файл-то остаётся на месте».

Дискриминатор «в секции нет оперативных маркеров ⇒ её можно выносить» защищает **инструкцию** и НЕ защищает три вещи:

| что уезжает незаметно | почему невидимо | чем проверить |
|---|---|---|
| **машинно-читаемые данные** | счётчик/таблица — не проза, маркеров не несёт | грепнуть имя поля по `scripts/`, `~/.claude/bin`, `lib/` |
| **ссылка ПО ИМЕНИ из оперативной части** | `§X выше/ниже` — обычный текст | in-file: `§…` в 40 симв. от `выше\|ниже\|этого файла` |
| **инструкция БЕЗ маркеров** | обычные `-` буллеты, floor в последней строке | прочитать тело, а не грепать маркеры |

- ⚠ **Симптом-tell отсутствует по построению:** после выноса правило читается связно, ничего не падает, а метрика **улучшается**. Обнаруживается только адресной проверкой.
- ✅ **Floor:** вынес секцию → (1) грепни её имя как строку по потребителям-скриптам; (2) прогони проверку висячих `§`-ссылок по **всему** корпусу, а не по правленому файлу — **командой `python3 ~/dotfiles/scripts/rules-xref-check.py`** (rc 0 CLEAN / 1 висячие **либо регрессия охвата** / 2 BROKEN **либо протухшая базовая линия храповика**; `-v` — очередь прозы к ручной переадресации); (3) машинно-читаемую секцию **верни и запломбируй** ⛔-строкой, объясняющей, почему она живёт в правиле — появившийся маркер делает её неподвижной для будущего автопрохода **по построению**, а не по памяти.
- ⛤ **In-file ссылку отличать от cross-file:** `[[другое-правило]] §Секция` легитимна и доминирует численно — сырой регэксп дал **201** совпадение против **4** настоящих. Дискриминатор — соседство слов `выше/ниже/этого файла`.
