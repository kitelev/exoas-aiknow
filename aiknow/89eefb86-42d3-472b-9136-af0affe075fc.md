# Auto Release gates on CI **workflow_run.conclusion == success** — a non-required job failure blocks the release silently

## Принцип

В этом репо (`kitelev/exocortex`) **Auto Release** триггерится не на push, а на `workflow_run` завершение workflow с именем **"CI"**, и его job гейтится:

```yaml
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
    branches: [main]
jobs:
  auto-release:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
```

⛤ **`workflow_run.conclusion` = success ТОЛЬКО если ВСЕ jobs в CI прошли — включая non-required.** Required-checks (branch protection, 13 шт.) гейтят **merge**, но НЕ гейтят `workflow_run.conclusion`. Поэтому возможна ситуация: **PR смержен (все required green), но Auto Release НЕ выходит**, потому что какой-то **non-required** job (напр. `docs-property-validation`) упал на post-merge push-to-main → весь CI workflow concludes `failure` → `auto-release.if` = false → release **тихо скипается** (run появляется как `completed/skipped`, не `failure`).

## Симптом / detection

- PR смержен, `gh pr view` = MERGED, required checks все green, НО `gh release list` не показывает новую версию через >5 мин.
- `gh api .../workflows/auto-release.yml/runs` показывает run для merge-SHA = **`completed/skipped`** (не success, не failure).
- Корень: `gh api .../workflows/ci.yml/runs?branch=main` для merge-SHA = **`completed/failure`** (event=push), хотя PR-level required checks были green.
- Часто **серия** подряд скипнутых релизов (N merge подряд) — значит non-required job сломан на main для ВСЕХ pushes, не специфично одному PR.

## Диагностика (порядок)

```bash
REPO=kitelev/exocortex; MERGE=<merge-sha>
# 1. Auto Release run для merge-SHA — skipped?
gh api "repos/$REPO/actions/workflows/auto-release.yml/runs?per_page=10" --jq '.workflow_runs[]|select(.head_sha=="<full-merge-sha>")|"\(.status)/\(.conclusion)"'
# 2. CI workflow run для merge-SHA — failure? (event=push)
gh api "repos/$REPO/actions/workflows/ci.yml/runs?branch=main&per_page=10" --jq '.workflow_runs[]|select(.head_sha=="<full-merge-sha>")|"\(.status)/\(.conclusion)"'
# 3. КАКОЙ job уронил CI workflow (non-success, non-skipped):
CIRUN=$(gh api "repos/$REPO/actions/workflows/ci.yml/runs?branch=main&per_page=10" --jq '.workflow_runs[]|select(.head_sha=="<full-merge-sha>")|.id'|head -1)
gh api "repos/$REPO/actions/runs/$CIRUN/jobs?per_page=40" --jq '.jobs[]|select(.conclusion!="success" and .conclusion!="skipped")|"\(.name): \(.conclusion)"'
# 4. Лог упавшего job → root cause
```

## Что делать

0. ⛔ **Ждун релиза обязан гейтить conclusion CI, а не только `gh release list`:** `~/.claude/bin/wait-release.sh <merge-sha>` — на каждом опросе читает `gh run list --branch main --workflow CI` для этого sha и при `completed/failure` выходит **rc=2 BROKEN** с перечнем упавших jobs (2026-09-19: 25 мин ожидания при уже красном `npm-audit-exocortex`, required 14/14 были green — правило это знало, ждун без гейта нет). RELEASED = rc 0, TIMEOUT = rc 4.
1. **Не паниковать про свой код** — если required checks green и merge прошёл, твой код в main корректен и БЕЗОПАСЕН. Release выйдет автоматически, как только non-required job починят (release строится из main HEAD ⊇ твой merge).
2. **Определи владельца упавшего non-required job** — часто это чужой PR (docs drift, flaky job) → **cross-session blocker**. Если фикс вне твоего scope (напр. `docs/rfc` принадлежит другой сессии) → **escalate оркестратору**, НЕ чини сам (`child-scope-immutability`).
3. **Confirm release когда выйдет** — следующий success-CI на main → Auto Release публикует версию, бандлящую все pending merge. Verify **bundle-grep** уникального символа твоего PR в released main.js (`obsidian-plugin-update-via-brat` «verify BUNDLE CONTENT»), не только tag>baseline.
4. **Fix-варианты для упавшего non-required job** (если в твоём scope): (a) убрать причину, (b) добавить отсутствующее, (c) whitelist/exception (напр. `KNOWN_EXCEPTIONS` в validation-скрипте) если это false-positive.
   - ⛤ Типовой false-positive `docs-property-validation` (замер 2026-09-15, PR #4240): markdown-ссылка на ЯКОРЬ заголовка свойства `[…](#exo__asset_archived)` — слаг СТРОЧНЫЙ, а регэксп скрипта `\b(exo|ems|…)__\w+_\w+\b` (`scripts/validate-docs-properties.js:20`) читает его как необъявленное свойство `exo__asset_archived`. ⇒ в `docs/**` на свойства ссылаться прозой/бэктиком, не якорем; ⛔ не «чинить» whitelist'ом — ложных слагов столько же, сколько ссылок.

## Запреты

- ⛔ Считать «PR merged + required green = released». Release — отдельный гейт на полном CI workflow conclusion.
- ⛤ Чинить чужой non-required-job-блокер вне своего scope молча — escalate (`child-scope-immutability`, `pre-spawn-parallel-session-conflict-check`).
- ⛔ Релиз-watcher, который ждёт `auto-release` run = success по merge-SHA, **зависнет** (run будет `skipped`, не success). Ключуй watcher на **появление новой release tag > baseline** + bundle-grep, а не на conclusion конкретного auto-release run.

Две поправки к §A2, обе установлены замером сегодня.

**1. «Проверить `directory:` в `.github/dependabot.yml`» было непроверяемым предписанием.** Файла **не существовало** с **2025-12-14** — снесён побочно коммитом `4e42ceaa` («refactor: rename packages», 512 файлов). ⇒ ⚠ Предписание «проверь X в файле Y» устаревает **молча**, когда Y исчезает: читатель грепает, получает пусто и трактует это как «нет такой записи», а не «нет файла». Различать: `git cat-file -e origin/main:<путь>`.

| запись в `dependabot.yml` | что трогает PR | исход |
|---|---|---|
| `directory: "/"` | корневой лок **+ манифесты всех членов** синхронно | ✅ корректно |
| `directory: "/packages/core"` | **только** манифест члена и его лок | ⛔ `npm ci` в корне: `Missing: <pkg> from lock file` |

- ⚠ **Симптом-tell:** у PR Dependabot упал **ровно один** чек, и это тот, что делает `npm ci` (здесь `NPM Security Audit`), при зелёных тестах. Значит ломает не обновление, а рассинхрон локов.
- ⛤ **Ошибка соблазнительна ровно потому, что член-лок СУЩЕСТВУЕТ.** «У core свой лок ⇒ нужна своя запись» — вывод из **наличия** артефакта, а не из его **роли**. Роль здесь третья: `cache-dependency-path` + вход `npm audit --omit=dev`, и обе не про установку.
- ⚠ Дрейф member-лока от корневого (`js-yaml` 3.14.2 против 3.15.1) этим **не лечится** и остаётся открытым — см. #4128.

## ⛔ Update 2026-08-20 (c) — ПЕРЕЗАПУСК релизного прогона НЕ проверяет кредо: шаги, которые его используют, УСЛОВНЫ

Починил секрет (`NPM_TOKEN`, ключ подписи, токен реестра) — рефлекс «перезапущу упавший прогон и посмотрю». ⛔ Этот перезапуск **не является проверкой** и систематически даёт **вакуумный зелёный**.

**Механизм.** `auto-release` начинается с `Get last release tag` → `Get commits since last tag`, и **весь** релизный хвост условен по их результату. Перезапуск идёт на **текущем** состоянии репо, а тег к этому моменту уже создан — значит коммитов после него **ноль**, и всё от `Determine version bump type` до `Publish CLI to npm` уходит в `skipped`. Прогон рапортует `success`, **ни разу не коснувшись кредо**.

| что видно | что это значит |
|---|---|
| `RUN … -> success` | ⛔ ничего: успех получен веткой, не касающейся публикации |
| `Verify npm auth: skipped` | шаг, который падал, **не исполнялся** |
| `npm view <pkg> version` не сдвинулся | ⇒ публикации не было |

- ⚠ **Опаснее обычного ложного зелёного, потому что он приходит СРАЗУ ПОСЛЕ починки** — то есть ровно тогда, когда его ждёшь. Подтверждение ожидания не перепроверяют.
- ✅ **Floor: вердикт брать из АРТЕФАКТА реестра, а не из сводки прогона** — `npm view <pkg> version` (или `gh release view` для другого канала). Сводка отвечает «отработал ли workflow», артефакт — «доехало ли».
- ✅ **Чтобы кредо реально задействовалось, нужен путь БЕЗ условности.** В этом репо он есть: `npm-publish-cli.yml` имеет `workflow_dispatch`, берёт последний релиз при пустом входе и **не имеет** предварительного гейта — публикация там и есть проверка. ⛔ Но это **outward и практически необратимо** (npm-unpublish ограничен) ⇒ только с явной санкцией владельца, не автономно.
- ⛤ **Проверять кредо по ЧАСТЯМ: «публикует» ≠ «проходит `whoami`».** Успешный `npm publish` **не доказывает** прохождение гейта `Verify npm auth`: granular-токен может публиковать и отдавать 401 на `whoami`. Если гейт остался неисполненным — issue закрывать **нельзя**, сколько бы ни было зелёного.
- ⚠ **Симптом-tell:** в списке шагов больше `skipped`, чем `success`, а ты собираешься написать «починено».
