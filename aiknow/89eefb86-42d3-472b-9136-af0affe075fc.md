# Auto Release gates on CI **workflow_run.conclusion == success** — a non-required job failure blocks the release silently

⛔ **Заголовок и имя скилла — ИСТОРИЧЕСКАЯ редакция (до #4488, 2026-10-02).** Сейчас релиз гейтит REQUIRED-набор check-run'ов, а не вердикт всего CI: красный НЕ-required джоб релиз НЕ роняет. Механизм — §Принцип ниже; ⛔ выводить «релиза не будет» из `conclusion` CI-прогона нельзя.

## Принцип

⛔ **Механизм СМЕНИЛСЯ 2026-10-02 (#4488) — прежняя редакция ниже, под «До #4488», историческая.** `auto-release.yml` по-прежнему триггерится на `workflow_run` воркфлоу **"CI"** (плюс `workflow_dispatch` на `main`), но джоб `auto-release` гейтит не `workflow_run.conclusion`, а отдельный джоб **`gate (required-set, not the run verdict)`**: `.github/scripts/release-required-gate.mjs` читает REQUIRED-набор из `GET /branches/main` и судит check-run'ы merge-sha по нему.

- ⛔ **Красный НЕ-required джоб (docs-link-check, npm-audit-*, docs-property-validation) релиз БОЛЬШЕ НЕ роняет.** Замер 2026-10-09: CI на `d0cf90c1` / `c2133616` / `64d6bd4e` = `failure` (docs-link-check, npm-audit-exocortex), Auto Release = `success`, v17.10.1 / .2 / .3 вышли с каждого. Ждун, гейтивший conclusion CI, на всех трёх соврал `BROKEN`, и ложное «релиз заблокирован» породило лишний PR.
- **Что осталось от класса:** релиз не выходит, когда на merge-sha не зелен **REQUIRED**-набор — `gate` отдаёт `release=false`, джоб `auto-release` = `skipped`, а **прогон** Auto Release при этом `completed/success` ⇒ судить по ДЖОБУ `auto-release`, не по прогону. Пропуск при зелёном required ловит джоб `audit (silent skip at green-required must go RED)`.
- **Восстановление:** перезапустить упавший required-джоб, либо `workflow_dispatch` Auto Release на `main`; следующий merge в `main` тоже забандлит пропущенный.
- ⚠ **Tell, что читаешь по старой памяти:** вывод «релиза не будет» сделан из `conclusion` CI-прогона. Механизм читать в `auto-release.yml` на `origin/main`, а не в этом тексте — он уже однажды устарел молча.

### До #4488 (историческая редакция, 2026-06-21 … 2026-10-02)

Джоб гейтился так:

```yaml
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
    branches: [main]
jobs:
  auto-release:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
```

`workflow_run.conclusion` = success ТОЛЬКО если ВСЕ jobs в CI прошли — включая non-required. Поэтому PR мог быть смержен (все required green), а Auto Release тихо скипался из-за упавшего non-required job (run `completed/skipped`).

## Симптом / detection

- PR смержен, required checks все green, НО `gh release list` не показывает новую версию через >5 мин.
- Прогон Auto Release для merge-SHA = `completed/success`, а его **джоб** `auto-release` = **`skipped`** ⇒ `gate` отказал: на merge-sha не зелен REQUIRED-набор (отменённый/упавший required check). ⛔ Прогон CI = `failure` при этом НЕ доказательство — с #4488 он релиз не гейтит.
- Часто **серия** подряд скипнутых релизов — значит required-джоб сломан на main для ВСЕХ pushes, не специфично одному PR.
- ⛤ До #4488 (историческое): run Auto Release = `completed/skipped`, корень — `ci.yml` run = `completed/failure` из-за non-required job.

## Диагностика (порядок)

```bash
REPO=kitelev/exocortex; MERGE=<полный merge-sha>
# 0. Самое дешёвое — ждун, он делает 1-2 сам: ~/.claude/bin/wait-release.sh <merge-sha>
# 1. Прогоны Auto Release для merge-SHA (ОБЩИЙ листинг, фильтр по name на клиенте — workflows/<file>/runs отдаёт протухшее окно)
gh api "repos/$REPO/actions/runs?branch=main&per_page=30" -H "Cache-Control: no-cache" \
  --jq ".workflow_runs[]|select(.head_sha==\"$MERGE\" and .name==\"Auto Release\")|\"\(.id) \(.status)/\(.conclusion)\""
# 2. ДЖОБЫ прогона: auto-release skipped ⇒ gate отказал; смотреть, какой REQUIRED check не зелен на merge-sha
gh api "repos/$REPO/actions/runs/<run-id>/jobs" --jq '.jobs[]|"\(.name): \(.conclusion)"'
gh api "repos/$REPO/commits/$MERGE/check-runs?per_page=100" --jq '.check_runs[]|select(.conclusion!="success" and .conclusion!="skipped")|"\(.name): \(.conclusion)"'
# 3. Сверить с REQUIRED-набором: gh api repos/$REPO/branches/main/protection/required_status_checks --jq .contexts
```

## Что делать

0. ⛔ **Ждун релиза — `~/.claude/bin/wait-release.sh <merge-sha>`; гейтит ИСХОД ДЖОБА `auto-release` прогона Auto Release для этого sha, НЕ conclusion CI** (переведён 2026-10-10: прежний гейт по CI на трёх merge подряд соврал BROKEN при вышедших релизах). rc 2 BROKEN = все прогоны Auto Release по sha завершены, ни в одном `auto-release` не success, и тег merge не содержит; RELEASED = rc 0 (`compare` ∈ {identical, ahead}), TIMEOUT = rc 4. `ci-watch.py --release` делегирует ему же.
1. **Не паниковать про свой код** — если required checks green и merge прошёл, твой код в main корректен и БЕЗОПАСЕН. С #4488 красный non-required job релиз не держит вовсе; пропущенный из-за REQUIRED-джоба релиз забандлит следующий merge (release строится из main HEAD ⊇ твой merge).
2. **Определи владельца упавшего non-required job** — часто это чужой PR (docs drift, flaky job) → **cross-session blocker**. Если фикс вне твоего scope (напр. `docs/rfc` принадлежит другой сессии) → **escalate оркестратору**, НЕ чини сам (`child-scope-immutability`).
3. **Confirm release когда выйдет** — следующий success-CI на main → Auto Release публикует версию, бандлящую все pending merge. Verify **bundle-grep** уникального символа твоего PR в released main.js (`obsidian-plugin-update-via-brat` «verify BUNDLE CONTENT»), не только tag>baseline.
4. **Fix-варианты для упавшего non-required job** (если в твоём scope): (a) убрать причину, (b) добавить отсутствующее, (c) whitelist/exception (напр. `KNOWN_EXCEPTIONS` в validation-скрипте) если это false-positive.
   - ⛤ Типовой false-positive `docs-property-validation` (замер 2026-09-15, PR #4240): markdown-ссылка на ЯКОРЬ заголовка свойства `[…](#exo__asset_archived)` — слаг СТРОЧНЫЙ, а регэксп скрипта `\b(exo|ems|…)__\w+_\w+\b` (`scripts/validate-docs-properties.js:20`) читает его как необъявленное свойство `exo__asset_archived`. ⇒ в `docs/**` на свойства ссылаться прозой/бэктиком, не якорем; ⛔ не «чинить» whitelist'ом — ложных слагов столько же, сколько ссылок.

## Запреты

- ⛔ Считать «PR merged + required green = released». Release — отдельный гейт (`gate` по REQUIRED-набору на merge-sha) плюс сам джоб публикации; ⛔ и обратное: «CI на main красный ⇒ релиза не будет» тоже ложно с #4488.
- ⛤ Чинить чужой non-required-job-блокер вне своего scope молча — escalate (`child-scope-immutability`, `pre-spawn-parallel-session-conflict-check`).
- ⛔ Релиз-watcher, который ждёт `auto-release` **прогон** = success по merge-SHA, ничего не доказывает: прогон `success` и при джобе `skipped`. Ключуй watcher на **тег, содержащий merge** (`compare` ∈ {identical, ahead}) + bundle-grep, а пропуск определяй по ДЖОБУ `auto-release` (так делает `wait-release.sh`).

## ⛔ Update 2026-08-20 (c) — ПЕРЕЗАПУСК релизного прогона НЕ проверяет кредо: шаги, которые его используют, УСЛОВНЫ

Починил секрет (`NPM_TOKEN`, ключ подписи, токен реестра) — рефлекс «перезапущу упавший прогон и посмотрю». ⛔ Этот перезапуск **не является проверкой** и систематически даёт **вакуумный зелёный**.

**Механизм.** `auto-release` начинается с `Get last release tag` → `Get commits since last tag`, и **весь** релизный хвост условен по их результату. Перезапуск идёт на **текущем** состоянии репо, а тег к этому моменту уже создан — значит коммитов после него **ноль**, и всё от `Determine version bump type` до `Publish CLI to npm` уходит в `skipped`. Прогон рапортует `success`, **ни разу не коснувшись кредо**.

| что видно | что это значит |
|---|---|
| `RUN … -> success` | ⛔ ничего: успех получен веткой, не касающейся публикации |
| `Verify npm auth: skipped` | шаг, который падал, **не исполнялся** |
| `npm view <pkg> version` не сдвинулся | ⇒ публикации не было |

- ⚠ **Опаснее обычного ложного зелёного, потому что он приходит СРАЗУ ПОСЛЕ починки** — то есть ровно тогда, когда его ждёшь. Подтверждение ожидания не перепроверяют.
- ✅ **Floor: вердикт брать из АРТЕФАКТА реестра, а не из сводки прогона** — `npm view <pkg> version` (или `gh release view` для другого канала). Сводка отвечает «отработал ли workflow», артефакт — «доехало ли».
- ✅ **Чтобы кредо реально задействовалось, нужен путь БЕЗ условности.** В этом репо он есть: `npm-publish-cli.yml` имеет `workflow_dispatch`, берёт последний релиз при пустом входе и **не имеет** предварительного гейта — публикация там и есть проверка. ⛔ Но это **outward и практически необратимо** (npm-unpublish ограничен) ⇒ только с явной санкцией владельца, не автономно.
- ⛤ **Проверять кредо по ЧАСТЯМ: «публикует» ≠ «проходит `whoami`».** Успешный `npm publish` **не доказывает** прохождение гейта `Verify npm auth`: granular-токен может публиковать и отдавать 401 на `whoami`. Если гейт остался неисполненным — issue закрывать **нельзя**, сколько бы ни было зелёного.
- ⚠ **Симптом-tell:** в списке шагов больше `skipped`, чем `success`, а ты собираешься написать «починено».
