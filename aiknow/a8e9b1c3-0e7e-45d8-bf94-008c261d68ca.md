# Харнесс, вызывающий предмет ИНТЕРПРЕТАТОРОМ, мерит НЕ ТУ ПОВЕРХНОСТЬ, что прод, вызывающий ПО ПУТИ

## Принцип

У исполняемого артефакта (shell-скрипт, python-скрипт, бинарь-обёртка) есть **две разные поверхности вызова**, и они проверяют разное:

| Как вызван | Что проверяется ОС | Что проверяется НЕ будет |
|---|---|---|
| **по пути** — `~/.claude/bin/x.sh`, `./x.sh`, `$(which x)` | **бит исполнения** (`+x`), **shebang**, PATH-резолюция | — |
| **интерпретатором** — `bash x.sh`, `python3 x.py`, `node x.js` | ничего из перечисленного (файл читается как **данные**) | ⛔ бит исполнения, ⛔ shebang, ⛔ PATH |

⛔ Значит харнесс, гоняющий `bash "$SUT"`, **структурно не может** увидеть дефект поверхности вызова. Файл в режиме `644` пройдёт **все** его оси зелёными, а прод, зовущий тот же файл по пути, получит `permission denied` (**rc=126**) с первой же секунды.

⛤ Это **третья, независимая** ось расхождения харнесса с продом — к уже задокументированным добавляется своя:

| ось | правило-хозяин | что расходится |
|---|---|---|
| форма/тип данных | `test-fixture-realism` | фикстура не воспроизводит реальный контракт значения |
| граница стаба | `test-fixture-realism` §стабь ПРОЦЕСС | застаблена функция, внутри которой живёт фича |
| **поверхность вызова** | **это правило** | **предмет запускается иначе, чем в проде** |

Закрытие любой из них не закрывает остальные: у меня фикстуры были production-shape, граница стаба — процессная (подменён бинарь `tmux`), и всё равно 10/10 зелёных при неработающем в проде скрипте.

## Почему тише обычного дефекта

- ⛔ **Симптом отсутствует со стороны харнесса.** Не «упало», не «покраснело» — **зелено**, причём осмысленно зелено: каждая ось честно проверила свою логику. Единственный след — в проде, куда никто не смотрит до инцидента.
- ⛤ **Провал терминального/фонового артефакта не выводится никому.** Если предмет — скрипт **самозакрытия**, уведомления, cleanup'а или cron-джоба, его `rc=126` не читает ни человек, ни лог; наблюдаемо лишь **последствие** (сессия не закрылась, уведомление не пришло) — и оно правдоподобно объясняется чем угодно другим.
- ⛔ **Последствие бывает НЕ нейтральным, а регрессией той самой метрики, ради которой писался фикс.** Упавший «финал» не отправляет свой пинг ⇒ наблюдатель видит «шаг не выполнен» ⇒ включается компенсатор-ожидание ⇒ ресурс держится **дольше**, чем до фикса. Проверять надо не «сломается ли», а **«что делает система, когда этот вызов вернул 126»**.

## Дискриминатор (один вопрос)

> **Какой СТРОКОЙ зовёт предмет прод — и зовёт ли его харнесс той же строкой?**

- **Той же** (по пути, если прод по пути; интерпретатором, если прод интерпретатором) ⇒ ось меряет
  ту поверхность, на которой предмет живёт.
- **Другой** ⇒ целый класс дефектов невидим ПО ПОСТРОЕНИЮ: `bash x.sh` читает файл как данные и не
  проверяет ни бит исполнения, ни shebang, ни PATH — 10/10 зелёных при `permission denied` в проде.

⛔ Строку прода **читать**, а не вспоминать: `case` раннера, `ProgramArguments` в plist, строка из
промпта. Формулировка «прод зовёт по пути» — claim, и проверяется одним `grep`.

⚠ **Входов бывает НЕСКОЛЬКО** (плановый раннер + прямой вызов), и они проверяют разное: перечисли
их и скажи, какой вход какой осью покрыт, иначе «доезд подтверждён» окажется шире замера.

## Floor

1. ✅ **Ось нулевая, ПЕРВОЙ строкой харнесса — проверка самой поверхности:**
   ```bash
   [ -x "$SUT" ] && ok "A0 скрипт исполняем (прод зовёт ПО ПУТИ, не через bash)" \
     || bad "A0 скрипт НЕ исполняем ($(ls -l "$SUT" | cut -c1-10)) — прод получит permission denied"
   ```
   Одна строка; стоит ноль; закрывает класс целиком. **Ставить ПЕРВОЙ** — иначе десять зелёных осей ниже создают ложную уверенность до того, как дойдёт очередь.
2. ✅ **Хотя бы одна ось обязана звать предмет ТОЙ ЖЕ формой, что прод.** Если прод зовёт по пути — пусть одна ось зовёт `"$SUT"` без интерпретатора и утверждает `rc != 126`. Остальные могут остаться на `bash` ради удобства инъекции.
3. ⛤ **Флип предъявлять исполнением:** снять `+x` → ось краснеет и **реальный вызов по пути** даёт `permission denied`; вернуть → `rc=0`. Без этого «ось есть» не равно «ось различает» (`integration-test-revert-verify`).
4. ⛤ **Бит исполнения ХРАНИТСЯ В GIT — и его надо проверить на remote, а не локально.** `git` пишет режим `100755`/`100644`; свежесозданный файл получает `644` по umask, и `chmod +x` — **отдельное изменение**, которое легко не закоммитить. Проверка по содержимому:
   ```bash
   gh api "repos/<o>/<r>/contents/<path>?ref=main" --jq .  # либо:
   git ls-tree origin/main -- <path>                        # ожидается 100755
   ```
5. ⚠ **`chmod +x` — часть отгрузки, а не «наведение порядка».** Ставить его в том же коммите, что и сам файл: иначе между коммитами существует окно, в котором артефакт отгружен и неработоспособен.

## Tell (симптомы)

- ⚠ **Ловится чтением, до любого прогона:** в харнессе `bash "$SUT"` / `python3 "$SUT"`, а в проде (промпт, launchd-plist, cron, вызывающий скрипт) — **голый путь**. Расхождение этих двух строк и есть дефект.
- ⚠ Новый исполняемый артефакт создан `Write`-тулом — он **всегда** `644`. Спроси: «а прод его как зовёт?»
- ⚠ Ты пишешь в отчёт «N/N осей зелены» про артефакт, который **ни одна ось не запускала так, как это делает прод**.

## ⛔ ФОРМА ВЫЗОВА ПРОДА резолвится ТРЕМЯ источниками, и замер по ОДНОМУ описывает НЕ ТУ ПОПУЛЯЦИЮ

Правило требует, чтобы харнесс звал предмет **так же, как прод**. Значит гейт на это обязан
знать, **как именно** прод зовётся, — а источников формы **три**, и каждый покрывает свой класс
предметов:

| источник | что покрывает | форма |
|---|---|---|
| `launchd` → `ProgramArguments` | демоны, тики | argv хранится целиком ⇒ позиция пути = **факт** |
| вызывающие скрипты | предметы, которые зовёт другой скрипт | ⛔ ДВУХШАГОВО: `VAR="…/x.sh"` … `"$VAR"` |
| **`settings.json` → `hooks[].command`** | **ХУКИ** — ни в launchd, ни в скриптах их нет ВОВСЕ | строка команды |

- ⛔ **Замер по ОДНОМУ источнику даёт верное число о НЕ ТОЙ популяции — и вывод из него ложен.**
  Замер 2026-08-30: по `launchd` **24 из 41** пути зовутся интерпретатором (80 % живых джобов) ⇒
  вывод «требование бита исполнения — ложная краснота» **напрашивается**. Но предметы харнессов
  этого корпуса — преимущественно **хуки**, а по `settings.json` **54 из 57** зовутся **ПО ПУТИ**
  ⇒ требование бита для них **верно**. Оба числа корректны; ложен переход между ними.
- ⚠ **Симптом-tell, ловится ДО вывода:** ты меришь долю в одном реестре, а применяешь её к
  множеству, которое этим реестром **не перечисляется**. Спроси не «сколько процентов», а
  **«лежат ли МОИ предметы в том реестре, где я мерил»**.
- ⛔ **Резолвер такой формы ломается ТИХО, и `selftest` на фикстурах его НЕ ловит по построению:**
  фикстуры проверяют **функцию**, а мёртвым бывает её **вход**. Замер того же дня: `_form_in_caller`
  проходил все 7 фикстур, а список источников собирался **пустым** (`code_only` принимает путь, я
  подал текст, `OSError` проглочен `except`) ⇒ форма резолвилась у **2 из 14** вместо 9, и гейт
  молча возвращался к прежнему строгому требованию.
- ✅ **Floor: КАНАРЕЙКА ОХВАТА на живом корпусе рядом с фикстурами** — «форма установлена у ≥N из
  M», порог **ниже факта** (чтобы штатный дрейф не краснил), число печатается всегда. Ноль и
  единицы означают мёртвый резолв, а не «предметы никем не зовутся».
- ⛤ **Ошибка резолва обязана уходить в БЕЗОПАСНУЮ сторону:** форма не установлена ⇒ остаётся
  **строгое** требование. Тогда мёртвый резолвер даёт лишнюю красноту (шумно, заметно), а не
  лишнюю зелень (тихо, необнаружимо).

⛔ **КОРРЕКЦИЯ ЗАПУШЕННОГО КОММИТА (мостик находимости, §ЧЕТВЁРТЫЙ носитель
`retracted-claim-outranks-its-correction`):** dotfiles `7bb15ba` содержит обоснование
«**80% продов** зовутся интерпретатором» и «расширение дало бы **22 красных из 76** с
**систематической ложной** компонентой» — это **опровергнуто** замером выше в `4dd0a80`.
Честные числа: 96 харнессов вне предмета (не 27), **186** красных, чистых **4**; Т3 даёт 80, и
они по большей части **настоящие**. Обе цитаты приведены здесь дословно, потому что
`git log --grep` по ним ведёт **только** к ложному коммиту — ключи коррекции и оригинала
разошлись, а историю общего remote не переписывают.

## Обобщение за пределы бита исполнения

Бит исполнения — самый дешёвый и частый экземпляр, но ось шире: **всё, что различает «как запущено», является частью предмета проверки**. Расходиться с продом можно и по:

- ⛔ **ФОРМУЛИРОВКЕ ЗАДАНИЯ, когда предмет — LLM-актор: caveat, добавленный РАДИ БЕЗОПАСНОСТИ, меняет его РЕЖИМ.** Прочие оси — про то, что предмет **запускается** иначе; здесь он запущен верно, а **задание** переключило его с исполнения на инвентаризацию. Оговорка вида «это проверка механизма, не реальная просьба» звучит как рамка эксперимента и читается актором как **смена задачи**: он честно меряет — и меряет не то. ⚠ **Симптом-tell:** харнесс даёт **ноль** там, где данные заведомо есть, а предмет на прямой вопрос отвечает верно ⇒ подозревать формулировку, а не предмет (`verify-before-assert` §A14 — тот же класс, но там носитель технический: env, кред, недостающая ветка). ✅ **Floor: безопасность брать из ЕСТЕСТВЕННОЙ ОСТАНОВКИ** («покажи, что собираешься сделать, применять пока не надо»), а не из caveat, отменяющего задачу. ⛔ Прогон с caveat вердиктом о проде не является.
- **окружению** (`launchctl print` даёт env живого джоба — ⚠ но он показывает переменную ещё ДО того, как прогон её употребит: вердикт даёт новая строка в логе, а не наличие переменной, см. §РЕЖИМ ЗАПУСКА ниже; выборочный перенос теряет то, о чём не подумал — `homoiconic-external-engine-config` §Addendum 2026-08-04);
  - ⛔ **`launchctl print` печатает PATH ДВАЖДЫ, и первая строка — НЕ твоя.** `default environment` — узкий дефолт launchd (`/usr/bin:/bin:/usr/sbin:/sbin`), `environment` — объявленное джобом. Наивный `grep PATH` отдаёт **обе**, и первая читается как «фикс не доехал». ✅ Floor: читать секцию по имени (`environment`), а не первое совпадение; ⚠ tell — в выдаче две строки PATH разной длины. _(Empirical 2026-08-27: приёмка PATH-фикса `self-compact.sh`.)_
- **рабочему каталогу** (`cd` меняет смысл относительных путей — `bash-loop-eval-pitfalls` Г11);

- ⛔ **СОСТАВУ КАТАЛОГА — предмет читает не только СЕБЯ, но и СПУТНИКОВ рядом.** Фикстура копирует файлы предмета и выглядит полной; прод же дочитывает **парные** артефакты из ТОГО ЖЕ каталога (`<stem>.spec.json`, `<stem>-mutants.py`, конфиг рядом) ⇒ у скопированного элемента спутника нет, и проверка, которая его требует, краснеет **на исправном коде**. ⚠ Tell: находок у оси БОЛЬШЕ боевого, а лишние — ровно те, чьих спутников ты не копировал. ✅ Floor: копировать **по основе имени** (`<stem>.*`), а невакуумность доказывать совпадением с боевым прогоном **поимённо**, не только числом. _(Empirical 2026-08-28, `033dfb7f`: «7 из 117» против боевых «6» — лишняя пара читалась бы как регрессия правки.)_
- **PATH** (прод зовёт короткое имя, харнесс — абсолютный путь ⇒ подмена через PATH не проверена);
  - ⛤ **Та же поверхность — ГОТОВЫЙ ДИСКРИМИНАТОР «дотянулся ли прогон до ЖИВОЙ машины»: обёртка-регистратор в начале PATH.** Проверка изоляции обычно упирается в то, что доказать надо **отрицательное** («ни один call-site не позвал живой ресурс»), а отрицательное не наблюдаемо: живой ресурс молчит и при нуле вызовов, и при неудачных. Обёртка переводит его в **положительное**: считает вызовы и проксирует в настоящий бинарь, поэтому прогон остаётся боевым.
    ```bash
    mkdir -p "$SP/probe-bin"
    cat > "$SP/probe-bin/tmux" <<'EOS'
    #!/bin/bash
    printf '%s ARGS: %s\n' "$(date '+%FT%T%z')" "$*" >> "$0.log"   # ⛤ журнал из $0 ⇒ копии не делят лог
    exec /opt/homebrew/bin/tmux "$@"
    EOS
    chmod 0755 "$SP/probe-bin/tmux"
    PATH="$SP/probe-bin:$PATH" <прогон>          # → счёт строк в tmux.log и есть число живых вызовов
    ```
    ⛔ **Абсолютный путь внутри обёртки обязателен** (`exec /opt/homebrew/bin/tmux`), иначе она найдёт себя и уйдёт в бесконечную рекурсию. ⚠ **И работает она ТОЛЬКО для короткого имени:** call-site, зовущий бинарь абсолютным путём, обёртку обойдёт — ноль в её журнале тогда означает «не звал ЧЕРЕЗ PATH», а не «не звал вовсе»; проверять `grep -c '<абсолютный путь>' <предмет>` рядом. ⛤ **Но эта оговорка про CALL-SITE, а не про РЕЗОЛВЕР: предмет, резолвящий бинарь лестницей `env → which → абсолютные кандидаты`, покрыт обёрткой ПО ПОСТРОЕНИЮ** — она находится на второй ступени, до третьей дело не доходит. ⛔ Тогда предписанный `grep -c` даёт **ЛОЖНОЕ «не покрыто»**: он считает константы фолбэка, НЕДОСТИЖИМЫЕ при этом порядке. ⚠ Дискриминатор — не «встречается ли абсолютный путь», а **«достижим ли он»** ⇒ прочитать резолвер, а не грепнуть предмет. _(Empirical 2026-08-28, `25f1de4f`: `_resolve_tmux()` в `vteam-supervise-detect.py:753-764` — env → `shutil.which` → 3 абсолютных кандидата; ноль в журнале обёртки полон, хотя абсолютные пути в файле есть.)_ ⛤ На релизном флипе она даёт **число, а не вердикт** (у меня 52 против 0 между двумя ревизиями) — то есть различимость предъявляется счётом, как того и требует `integration-test-revert-verify` §A51. _(Empirical 2026-08-27, тикет `41543fbc`: три неизолированных call-site до фикса → 52 реальных вызова живого `tmux`; после — 0 при том же прогоне.)_
- **argv[0] / символической ссылке** (скрипт, ветвящийся по имени, под другим именем идёт другой веткой);
- **интерпретаторе** (`sh` против `bash`: прод-shebang `#!/usr/bin/env bash`, харнесс зовёт `sh x.sh` ⇒ bash-измы не проверены).
- ⛔ **ВЕРСИИ того же интерпретатора** — ось тише всех перечисленных: имя совпадает, путь выглядит правильным, а исполняется **чужая сборка**. Прод зовёт `npx <pkg>@latest`; харнесс, экономя холодный старт, резолвит бинарь из кэша `ls ~/.npm/_npx/*/node_modules/<pkg> | head -1` — и **`head` берёт первый по глоб-порядку, а не старший по версии** (в кэше их накапливаются сотни). ✅ Floor: пинить **замером** — один `npx <pkg>@latest --version`, затем резолвить в кэше **ровно эту** версию, `fail-loud` если её там нет. ⛤ **Для `@kitelev/exocortex-cli` это УЖЕ написано:** `~/.claude/lib/resolve-exocortex-cli.sh` печатает путь к `dist/index.js` старшей версии (числовое сравнение, `rc=3` при пустом кэше и при полой установке — пустая строка превратила бы `node ""` в REPL). Вызывать `IDX=$(…) && node "$IDX" …`; ⛔ не `CLI="node /path"` — под zsh не расщепится (Г1). ## ⛔ ДВЕ формы «набор массово красный» в монорепо, и обе — СРЕДА, а не код: судить по ДОЛЕ, а не по факту красноты

Обе поверхности ниже дают **лавину** красного (десятки-сотни сьютов), и обе чинятся одной командой.
⚠ Дискриминатор общий и дешёвый: **доля**. Твоя правка трогала один-два файла — красных сьютов
единицы; красных **больше половины набора** ⇒ ты запустил его не так, как это делает пакет.

| наблюдаемое | корень | лечение |
|---|---|---|
| «Jest encountered an unexpected token» / «failed to parse» в **каждом** сьюте | пакет требует флага раннера, которого нет у твоей формы запуска | взять команду из `package.json` пакета (`scripts.test`), а не собирать `node …/jest.js` руками |
| интеграционные сьюты падают, юнит-сьюты зелены; ошибки вида «exit code 1» у под-процесса | интеграционные гоняют **собранный артефакт**, а ты правил ИСХОДНИК | пересобрать пакет (`npm run build -w <pkg>`) перед прогоном |

- ✅ **Floor: форму запуска брать ИЗ ПАКЕТА, а не изобретать.** `python3 -c "import json;
  print(json.load(open('packages/<x>/package.json'))['scripts']['test'])"` — одна строка, и она же
  показывает нужные флаги (`--experimental-vm-modules` и т. п.). ⛤ Это тот же принцип, что вся эта
  страница: **предмет надо запускать так, как его запускает прод/CI**, — просто здесь «прод» это
  `npm test` пакета.
- ⚠ **Второй tell для сборочной формы:** после `npm run build -w <pkg>` число падений **резко**
  падает (замер: 10 → 1). Резкое улучшение от сборки означает, что мерил ты не свой код.
- ⛔ **И только ПОСЛЕ этих двух — сравнение с родителем.** Сравнивать «мои 112 красных» с
  «родительскими 112 красных» бессмысленно: совпадут оба, и вывод «регрессии нет» будет верным по
  ложному основанию, а настоящая регрессия утонет в шуме среды.

## ⛔ ЛОКАЛЬНЫЙ `npm install` ТЕРПИТ рассинхрон лока, `npm ci` — НЕТ: зелёные тесты не доказывают, что CI поставится

Правя манифест (`overrides` / `resolutions` / диапазон версии), проверяют естественно так: `npm install` → прогнать тесты → зелено → отгружать. ⛔ Это проверяет **не тот** установщик: локально идёт `npm install`, который **дописывает лок под себя**, а CI делает `npm ci`, который отказывается ставить при малейшем расхождении лока с манифестом.

- ⛤ **Механизм расхождения:** твоя правка вытесняет версию, на которую ещё ссылаются соседи. `npm install` молча пересобирает дерево (и оно работает — тесты зелёные!), но в локе исчезает запись, которую требуют другие пакеты. `npm ci` это ловит: `npm error EUSAGE … Missing: <pkg>@<ver> from lock file`.
- ⛔ **Отказ максимально обманчив: локально ВСЁ зелено, включая целевые тесты.** У меня `test-ui` дал `53 passed` на дереве, которое в CI не устанавливается **вовсе** — то есть положительный замер был верным про поведение и ничего не говорил про устанавливаемость.
- ⚠ **Симптом в CI — ЛАВИНА, а не точечный красный:** падает половина чеков и больше (у меня 17), потому что не собралось окружение. ⇒ доля красных > половины = среда, и первый вопрос «а `npm ci` вообще прошёл?», а не «что я сломал в коде».
- ✅ **Floor: `npm ci` — обязательный локальный гейт после ЛЮБОЙ правки манифеста/лока**, и гонять его надо на **чистом** дереве:
  ```bash
  rm -rf node_modules packages/*/node_modules && npm ci --no-audit --no-fund; echo "rc=$?"
  ```
  Только `rc=0` даёт право отгружать. Прогон тестов делать **после** него — тогда он ещё и воспроизводит CI-топологию (см. §следующую секцию про `cp -a`).
- ⛤ **Побочно `npm ci` отвечает на вопрос, на который иначе нужен цикл CI:** «мою правку вообще можно поставить?» Один локальный прогон против ~10 минут и красного PR.
- ⛤ **Если `npm ci` падает — правка не «требует доработки», а НЕПРИМЕНИМА на этой базе.** У меня override был жизнеспособен только вместе с бампом, поднимающим соседей до совместимых версий; отдельным PR он не существовал в принципе.

**Empirical 2026-08-20** (PR #4154, `kitelev/exocortex`): `overrides: {"jest-environment-obsidian": {"jest-mock": "^30.4.1"}}` на `main` с jest 30.2. Локально: `npm install` rc=0, `test-ui` 53/53. В CI: `npm ci` → `Missing: jest-mock@30.2.0 from lock file` ×6 → **17 красных чеков**. На ветке с бампом jest→30.4 та же правка: `npm ci` rc=0 (947 пакетов), `test-ui` 53/53. ### ⛔ ЗЕРКАЛО: локальное дерево УШЛО от лока настолько, что сьют НЕ СТАРТУЕТ — а читается это как дефект кода

Секция выше — про направление «локально зелено, CI не поставится». Обратное встречается у **чужого
общего чекаута**, куда ты пришёл только ПРОЧИТАТЬ код: `npm ci` там не делали месяцами, `npm install`
дописывал дерево под разные ветки, и оно разошлось с локом. Тогда `npm ci` в CI зелен, а у тебя
сьют **не запускается вовсе**.

- ⚠ **Наблюдаемое отличается от обычного красного и этим обманывает:** `Test suite failed to run`
  при `Tests: 0 total` — то есть тестов не было ни одного, а не «упали». Текст ошибки указывает на
  ЧУЖОЙ модуль (`Must use import to load ES Module … node_modules/uuid`, `Cannot find module 'nanotar'`),
  и рефлекс — искать поломку в коде, который ты пришёл прочитать.
- ✅ **Дискриминатор — ОДНА команда, и он терминальный:** `npm ls <пакет-из-ошибки> --depth=1`.
  `invalid: "<диапазон>" from <workspace>` ⇒ дерево разошлось с локом; `extraneous` рядом ⇒ остатки
  удалённой зависимости. Оба — свойства **установки**, не кода.

## ⛔ Свежий worktree, засеянный `cp -a node_modules`, НЕ ЭКВИВАЛЕНТЕН `npm ci` — и расходится ТРЕМЯ независимыми способами

Заводя worktree под задачу, `node_modules` копируют из соседнего: это секунды против минут. Копия
воспроизводит **содержимое**, но не **топологию**, и ломается по трём разным осям — каждая со своим
симптомом, так что чинить их приходится по одной, теряя цикл на каждой.

| ось | симптом | почему копия его порождает |
|---|---|---|
| **пакет-локальные дубли** | `Must use import to load ES Module: …/uuid/dist-node/index.js`, `Tests: 0` | `npm ci` кладёт `packages/core/node_modules/uuid@11` (CJS) рядом с хойстнутым v13 (ESM); копия несёт только хойстнутый |
| **транзитивные зависимости** | `TS2307: Cannot find module 'nanotar'` у файлов, которых ты не трогал | пакет объявлен в трёх `package.json`, но физически лежит в одном месте, и оно в копию не попало |
| ⛔ **АБСОЛЮТНЫЕ симлинки воркспейсов** | `TS2307: Cannot find module '@kitelev/exocortex-core'` **при сборке**, `64 unresolved bare workspace import(s)` | часть симлинков в `node_modules/@kitelev/` абсолютные и продолжают указывать на **исходный** чекаут — то есть ты собираешь ЧУЖОЕ дерево |

⛔ **Третья ось тише двух первых и опаснее их.** Первые две падают громко и очевидно «не про мой код».
Абсолютный симлинк **работает** — просто ведёт не туда: сборка проходит по чужим исходникам,
ratchet считает чужие диагностики, а разница проявляется лишь тем, что твои правки на результат не
влияют. Замер: в одном каталоге `@kitelev/` соседствовали относительный (`../../packages/cli`) и

## ⛔ ИНЪЕКЦИЯ ВНЕШНЕГО СОСТОЯНИЯ — предусловие тестируемости гварда, а не удобство: без неё харнесс либо БЬЁТ ПО ПРОДУ, либо не существует

⛤ **Счёт за одну сессию 2026-08-21: ТРИ харнесса оказались АКТИВНЫМИ ДЫРАМИ** — брали боевой
sentinel обхода · ставили боевую метку сверки · держали боевой single-flight лок (то есть
могли СНЯТЬ его, открыв окно параллельному прогону). Во всех трёх инъекция была не удобством,
а условием того, чтобы харнесс перестал быть уязвимостью. ⚠ Третий нашёлся только потому, что
его собственный набор покраснел ВО ВРЕМЯ боевого прогона — то есть симптом виден лишь при
одновременности, и в тихом окне харнесс выглядит исправным.

Гвард по природе читает **внешнее состояние**: каталог меток, файл-sentinel, живую сессию,
счётчик соседей, путь охраняемого дерева, репозиторий. Пока эти входы захардкожены, у
харнесса ровно два исхода, и оба плохие:

| путь | что происходит |
|---|---|
| «проверю на боевом» | харнесс МУТИРУЕТ то, что гвард охраняет: ставит боевую метку, открывает окно обхода, пишет в живой журнал |
| «не буду проверять» | гвард остаётся без харнесса — а он единственный класс, который блокирует работу и может разоружиться молча |

⛔ **Худшая форма первого пути: харнесс РАЗОРУЖАЕТ гвард ровно там, где тот охраняет.**
Проверка escape-окна создаёт боевое окно; упав до уборки, она оставляет защиту снятой на
часы. Проверка гварда сверки ставит боевую метку и **открывает** отгрузку, которую никто
не сверял. То есть цена «проверить на боевом» не в риске испортить данные, а в том, что
сама проверка становится дырой.

- ✅ **Floor: инъекция ДО написания осей, отдельной правкой, с боевым дефолтом.**
  `X="${X_OVERRIDE:-<боевое>}"` — поведение не меняется, а харнесс получает свой каталог,
  свою метку, своё имя сессии. Правка на одну строку, и она предусловие, а не часть теста.
- ✅ **Писать атомарной заменой** (временный файл + `os.replace`), если гвард может
  исполниться параллельно: обычная перезапись даёт окно, в котором он читает полуфайл.
- ⛤ **Имя переменной брать у ПРЕЦЕДЕНТА в корпусе**, а не изобретать: единообразие делает
  инъекцию узнаваемой, и следующий автор харнесса не ищет, как подсунуть состояние.
- ⚠ **Симптом-tell до начала работы:** ты собираешься проверить гвард и первым делом думаешь
  «а не испорчу ли я этим боевое состояние». Этот вопрос и есть сигнал, что нужна инъекция,
  а не аккуратность.
- ⛤ **Побочная выгода крупнее ожидаемой:** инъекция вскрывает, ЧТО именно гвард читает.
  Дважды за сессию она опровергла мою же модель предмета — оказалось, что каталог меток
  используется только для вето (а не для регистрации), и что fail-closed на неразрешённом

## ⛔ КОРЕНЬ протухших анкеров: ты копируешь текст из СВОЕГО ЖЕ вывода, а он напечатан с ТВОИМ префиксом

Корпус уже требует «анкер строить ИЗ ФАЙЛА, а не копировать» и называет виновником `sed 's/^/  /'`
при чтении. Недостающая половина — **почему floor не срабатывает**: ты его исполняешь (читаешь
файл), но печатаешь для себя через `| sed 's/^/  /'` **ради читаемости вывода**, а затем копируешь
анкер оттуда — вместе с этими двумя пробелами. Мотив косметический, последствие семантическое.

- ⚠ **Симптом:** `assert s.count(old) == 1` падает `x0` на строке, которую ты **видишь на экране**,
  причём файл между чтением и правкой не менялся.
- ✅ **Floor: печатать БЕЗ префикса ровно тогда, когда собираешься копировать анкер.** Префикс —
  для чтения глазами, не для копирования. Либо (надёжнее) **не копировать вовсе**: находить
  границы блока по устойчивому фрагменту и править **по индексам строк**, беря отступ из файла
  (`ind = len(l) - len(l.lstrip())`).
- ⛤ **Правка по индексам строго лучше на многострочных блоках:** она не зависит ни от отступа, ни

## ⛔ РАННЕР, выбирающий интерпретатор ПО РАСШИРЕНИЮ, ломает zsh-харнесс — и отказ читается как «харнесс сломан»

§Обобщение выше называет интерпретатор одной из осей расхождения. Практический случай, который
стоит помнить отдельно: **диспетчер** (раннер, CI-шаг, обёртка) выбирает интерпретатор по
**расширению файла**, а не по shebang:

```bash
case "$name" in *.py) cmd=(python3 "$h");; *) cmd=(bash "$h");; esac   # ⛔
```

⇒ любой `.sh` с `#!/usr/bin/env zsh` запускается **через bash** и падает синтаксически на
конструкциях, законных в zsh (`{ …; exit 2 }` без `;` перед `}`, `((PASS++))` в некоторых формах,
`print`, `typeset -A` с другим синтаксисом индексации).

- ⚠ **Симптом обманывает дважды.** `bash: line N: syntax error: unexpected end of file`, где N
  **больше** числа строк файла, читается как «харнесс сломан» — при том что он исправен, а
  `bash -n` подтверждает «ошибку» и укрепляет ложный вывод.
- ⛤ **Дискриминатор — один запуск ЗАЯВЛЕННЫМ интерпретатором:** `zsh <файл>`. Зелено ⇒ сломан
  **диспетчер**, а не предмет. Стоит секунды и снимает вопрос целиком.
- ✅ **Floor: диспетчер читает SHEBANG**, а расширение использует только как последний фолбэк:
  ```bash
  case "$name" in
    *.py) cmd=(python3 "$h") ;;
    *)    case "$(head -1 "$h")" in *zsh) cmd=(zsh "$h") ;; *) cmd=(bash "$h") ;; esac ;;
  esac
  ```
- ⛔ **Тот же floor ЛОМАЕТСЯ на ТРЕТЬЕМ интерпретаторе: `.sh` с `#!/usr/bin/env python3`.** Ветка
  `*zsh)` — перечень из ОДНОГО, поэтому python-скрипт под именем `.sh` уходит в `bash` и даёт
  `rc=2` на ЛЮБОМ входе (bash исполняет докстринг: `Enter: command not found`). ⚠ Tell тот же,
  что в `self-authored-claim-loses-its-provenance` §A13: **одинаковый отрицательный вердикт на
  ВСЕХ различающихся входах** ⇒ сломан общий слой, а не предмет.
- ✅ **Структурный floor вместо третьей ветки — исполнять ПО ПУТИ** (`cmd=("$h")`): ядро само
  чтит shebang, и диспетчера не существует *by construction*. ⛔ Требует бита исполнения; нет
  бита ⇒ ветвиться по ТОМУ, ЧТО В SHEBANG, а не по одному заранее известному имени.
- ⛔ **Латентность выше, чем кажется:** сегодня zsh-харнесс может быть один и вне маски раннера —
  тогда дефект не проявляется вовсе. Он «ждёт» первого zsh-файла, попавшего под маску, и тот
  молча получит `rc=2` в батче.
- ⛤ **Смежный floor того же захода: харнесс, названный вне конвенции обнаружения, не гоняется
  вовсе.** `*-test.sh` при маске `*-verify.{sh,py}` = 12 живых осей вне регулярного прогона.
  Лечится **переименованием в конвенцию**, а не расширением маски: вторая маска плодит второй
  способ обнаружения, и следующий автор не будет знать, какой действует.

**Empirical 2026-08-21:** `orch-watchdog-verdict-test.sh` (`#!/usr/bin/env zsh`) под `bash` давал

## ⛔ Прямой запуск харнесса ≠ запуск ИЗ РАННЕРА: он не наследует ОПТИМИЗАЦИИ окружения, и разница читается как contention

Оси выше — про то, что предмет **исполняется** иначе (бит, shebang, cwd, PATH). Соседняя форма:
предмет исполняется одинаково, а **инструмент, которым он работает**, резолвится по-разному —
потому что оптимизацию экспортирует **вызывающий**, и при прямом запуске её просто нет.

Типовая пара: раннер резолвит тяжёлый CLI **один раз** и экспортирует путь
(`VTEAM_CLI="node …/dist/index.js"`), а харнесс читает его из окружения с фолбэком на
`npx -y <pkg>@latest`. Запустишь харнесс руками — фолбэк, и **каждый** его вызов платит
холодный старт npm.

- ⛔ **Наблюдаемое коварно: разница выглядит как ЗАМЕДЛЕНИЕ ОТ НАГРУЗКИ.** Тот же харнесс в
  раннере укладывается в 1290 с, а «одиночный прогон в тишине» не заканчивается за 2400 с
  (`rc=124`). Естественный вывод — «шумит машина», и он **неверен**: шумит отсутствующая
  переменная.
- ⚠ **Симптом-tell, ловится ОДНОЙ командой:** `pgrep -lf '<pkg>'` во время прогона показывает
  `npm exec <pkg>@latest …`. Значит инструмент резолвится заново на каждом вызове.
  У правильного прогона там был бы `node …/dist/index.js`.
- ✅ **Floor: перед ручным прогоном прочитать, какие переменные харнесс берёт из окружения**
  (`grep -nE 'environ.get|\$\{[A-Z_]+' <харнесс>`), и передать те, что даёт раннер.
  Одна строка `grep` против часов ложной диагностики.
- ⛤ **Резолвить надо ЗАМЕРОМ версии, а не «что нашлось в кэше»:** `npx <pkg>@latest --version`
  → найти в `~/.npm/_npx/*/node_modules/<pkg>` ровно эту версию → `node <путь>/dist/index.js`.
  ⛔ `ls … | head -1` даст произвольную старую сборку (кэш накапливает сотни).
- ⛤ **Побочно: python буферизует вывод при перенаправлении в файл** — прогон «идёт, а файл 0
  байт» пугает и провоцирует лишние проверки. `python3 -u` снимает это бесплатно.
- ⛤ **ВТОРОЕ наблюдаемое того же корня — НЕДОСЧЁТ ОСЕЙ, а не замедление:** ось, обёрнутая в
  `[ -n "${VAR:-}" ] && {…}`, при прямом прогоне **не исполняется**, и `PASS` выходит меньше
  заявленного разработчиком. ⚠ Tell: `PASS` ниже самоотчёта при `FAIL=0` ⇒ это ФОРМА ЗАПУСКА,
  а не регрессия. ✅ Приёмщику: проверить такую ось вручную и назвать расхождение вслух;

## ⛔ ЗАЩИТА, живущая в РАННЕРЕ, ручным вызовом НЕ НАСЛЕДУЕТСЯ — и ты воспроизведёшь ровно ту ловушку, от которой раннер тебя бережёт

Раннер, обходящий набор харнессов, обычно централизует хрупкие решения: резолв бинаря по версии,
пин окружения, таймаут, изоляцию состояния. Это правильно — инвариант живёт в одном месте.

⛔ Но когда ты запускаешь ОДИН харнесс **руками** (диагностика красного, повтор ради улики), ты
собираешь окружение заново по памяти — и промахиваешься мимо той самой защиты, которая у раннера
уже написана и **задокументирована в его же коде**.

- ⚠ **Симптом читается как дефект ПРЕДМЕТА:** ручной прогон краснеет там, где раннер зелен, ЛИБО
  краснеет **иначе** (у меня контроль дал 18 красных осей вместо ожидаемой одной). Первая гипотеза
  — «харнесс нестабилен»; верная — «я собрал не то окружение».
- ⛤ **Дискриминатор — ЧИТАТЬ РАННЕР, а не изобретать:** он резолвит то же самое и обычно объясняет
  почему. У меня строка 44 буквально гласила «⛔ Первая редакция брала `ls … | head -1` и взяла из
  кэша 16.187.1 при актуальной 16.234.0» — то есть предупреждение о моей ошибке было написано
  раньше, чем я её совершил.
- ✅ **Floor: ручной прогон брать ТЕМ ЖЕ способом, что раннер** — либо запускать через него
  (`VHR_DIR=<каталог с одним харнессом>`), либо скопировать его блок резолва дословно. ⛔ Не
  «примерно так же».
- ⚠ **Инъекцию сверять с ИМЕНЕМ переменной в коде.** `VHR_DIRS` вместо `VHR_DIR` не падает — она
  просто игнорируется, и прогоняется **боевой** набор; замечаешь по числу прогнанных, а не по ошибке.
- ⛤ **Побочно это тест самого раннера:** если ручной прогон с его же окружением даёт другой исход,
  чем раннер, — расхождение в раннере, и оно найдено. Совпал — предмет ведёт себя одинаково, и
  копать надо в харнессе.

**Empirical 2026-08-21:** диагностируя `rc=1` у `vteam-record-verify.py`, я резолвил CLI через
`ls -d ~/.npm/_npx/*/… | head -1` → **16.187.1** при актуальной **16.234.0**; прогон упал за 2 мин
с `КОНТРОЛЬ КРАСНЫЙ (18)` вместо своих 21 минуты. Раннер тем временем пинует 16.234.0 и содержит
явное предупреждение об этой форме. Итог: два потраченных прогона и ложный вывод «харнесс сломан».
