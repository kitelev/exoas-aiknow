# Child scope immutability: не расширять scope работающей child-сессии

## Принцип (user directive 2026-06-11, «Гарантируй это»)

Scope child-сессии **фиксируется при спавне** (промпт-файл). Оркестратор НЕ дописывает в работающую child-сессию задачи, для которых она изначально не предназначалась — даже «родственные», даже «дешевле одним PR/release».

**Новая проблема → отдельный issue → отдельная child-сессия** (с обязательным pre-spawn conflict-check, включая соседство с уже работающими child'ами: непересекающиеся участки файлов, протокол BEHIND → `gh pr update-branch`).

## Что МОЖНО слать в работающую child-сессию

- Уточнения/коррекции её СОБСТВЕННОЙ задачи (например «промпт ошибся в пути — вот верный»).
- Протокольные директивы: push-discipline, conflict-соседство, отмена/**сужение** scope.
- Resume-директивы после краша («продолжай с места остановки»).

## Что НЕЛЬЗЯ

- ⛔ Добавлять новый issue/баг/фичу в scope («расширение scope: добавь в этот же PR …»).
- ⛔ Rationalization «тёплый контекст, один release, оба бага одного кластера» — издержки (размывание ответственности, усложнение review «один PR — N задач», стоимость отзыва при несогласии пользователя) перевешивают экономию спавна.
- Исключение единственное: **явное указание пользователя** расширить конкретную сессию.
