# WAITING_DECISION: Bash tool timeout overrides script timeout

> **⛔ ROOT-CAUSE FIXED 2026-06-05 (separate from the Bash-timeout issue below):** `child-await-decision.sh` грепал reply по литералу `"decision_uid":"<uid>"` (без пробела), а `parent-reply.sh` писал через `json.dumps` с пробелом после двоеточия (`"decision_uid": "<uid>"`) → **grep никогда не матчил** → child всегда уходил в timeout/default несмотря на доставленный reply. Это и есть «possible bug in script's reply parsing» из Incident 2 ниже. Fix: child-await грепает по **голому UID** (format-agnostic), parent-reply пишет **compact** JSON. Round-trip verified. Если видишь старый симптом — убедись, что обе lib-версии свежие (`~/.claude/lib` → dotfiles).

При вызове `~/.claude/lib/child-await-decision.sh` из child Claude Bash tool — **обязательно** передавать `timeout: 600000` в Bash invocation. Script's внутренний default `-t 1800` (30 min) **бесполезен** — Bash tool обрезает на `BASH_DEFAULT_TIMEOUT_MS=300000` (5 min) → script killed на 300s → child получает false timeout exit 124 → applies default option (часто wrong choice). ⛔ (уточнено 2026-09-13: строка выше — ИСТОРИЯ; сейчас Bash-тул на 600 с НЕ убивает скрипт — переносит в фон и присылает уведомление, `-t` работает, rc=124 настоящий — §Родитель на СЕЛЕКТОРЕ ниже.)

## Когда правило срабатывает

- Child Claude orchestrated parent (autonomous AI) ждёт parent decision via blocking `child-await-decision.sh`
- Question complexity такая, что parent decision может занять >5 min (parent thinks, consults advisor, или is busy with other tools)
- Default fallback option может быть wrong choice если parent не отвечает

## Правильный паттерн

В child Claude:

```bash
# WRONG — Bash tool 300s default kills script before parent reply
ANSWER=$(~/.claude/lib/child-await-decision.sh "Question..." "opt-a|opt-b")

# RIGHT — explicit timeout: 600000 in Bash tool invocation
# Inside child's Bash tool call:
#   command: ~/.claude/lib/child-await-decision.sh -t 540 "Question..." "opt-a|opt-b"
#   timeout: 600000  ← MANDATORY
ANSWER=$(~/.claude/lib/child-await-decision.sh -t 540 "Question..." "opt-a|opt-b")
```

Note: `-t 540` (9 min) leaves 60s headroom для Bash tool 600s cap. Don't set `-t 600` — race condition с Bash tool kill.

⛤ **`timeout` > 600000 НЕ отвергается — кэпится молча** (замер 2026-09-16, child gate0det: промпт предписал `timeout: 1600000`; тул-описание Bash: «max 600000»): через 600 с вызов уходит в ФОН с уведомлением, `ANSWER=$(…)` не присваивается, но stdout лежит в файле задачи (`tasks/<id>.output`) — ответ читается оттуда. ⚠ Tell: спавн-промпт называет число > 600000 — это claim автора промпта о туле, не свойство тула; ждать дольше 10 мин — `run_in_background` + файл ответа, а не большой `timeout`.

## Workaround если await pattern всё равно ломается

Direct reply file write (no UUID coupling):

```bash
# Parent side:
REPLY_FILE=~/.claude/audit/parent-replies-<child-tmux-name>.jsonl
python3 -c "import json; print(json.dumps({
    'ts': '<timestamp>',
    'child': '<child-tmux-name>',
    'decision_uid': 'inline-await-no-uid',
    'answer': '<answer text>'
}))" > "$REPLY_FILE"
```

Child's inline polling loop checks `[ -f "$REPLY_FILE" ]` и exits 0 как только файл exists — UUID игнорируется. Подходит когда `parent-reply.sh` не сработал (нет decision UID в WAITING_DECISION ping).

## Pattern summary (decision tree для child Claude)

| Situation | Approach |
|---|---|
| Quick yes/no parent decision, <2 min expected | `child-await-decision.sh` default timeout, no Bash tool override needed |
| Architectural decision, parent may take 5-30 min | `child-await-decision.sh -t 540` + Bash tool `timeout: 600000` |
| Long-running coordination, >10 min wait | Inline polling shell loop (file-existence check, no UID matching) + parent writes directly to reply file |

## ⛔ Родитель стоит на СЕЛЕКТОРЕ фаундера — ответа не будет, пока фаундер не выберет; проверять ПЕРЕД await, а не после таймаута

- ⚠ Tell (одна команда): `tmux capture-pane -p -t "$ORCH_TARGET" | grep -qE 'Enter to select · ↑/↓ to navigate'` ⇒ панель родителя занята `AskUserQuestion`; твой пинг он прочтёт только после выбора фаундера ⇒ блокирующий `await` сгорит целиком. С 2026-09-13 `child-await-decision.sh` печатает это предупреждение сам (stderr, fail-open) сразу после эмиссии пинга.
- ✅ Floor при занятом селекторе: не блокироваться — повторный `WAITING_DECISION` + inline-поллер файла ответа в ФОНЕ (`run_in_background`, форма «>10 мин» из §Pattern summary) + независимый трек работы; ответ читать из `parent-replies-<child>.jsonl` по появлению строки.
- ⛤ Поправка к шапке про «script killed на 300s»: в текущем харнессе Bash-тул на своём лимите (600 с) НЕ убивает скрипт — переносит вызов в фон (`moved to the background`) и присылает task-notification; `rc=124` тогда НАСТОЯЩИЙ (истёк `-t`), а не ложный.

_Empirical 2026-09-13 (L3 `d859b517`): `-t 1800` → rc=124 после полных 1800 с; панель оркестратора всё это время показывала селектор («4. Пауза … Enter to select»); ответ пришёл через 72 мин после первого запроса, уже на повторный WAITING_DECISION + файловый поллер._

## ⛔ Ожидание, чей цикл ЗАВЕДОМО длиннее cap Bash-тула (merge-гейт с ревью оркестратора) — `-t 1800` в `run_in_background`, не `-t 540` в foreground

Протокол `-t 540` + Bash `timeout: 600000` рассчитан на БЫСТРЫЕ решения родителя (минуты). У merge-гейта родитель гонит `code-reviewer` на копиях `git show` — цикл 10–20 мин ⇒ 540 с закрывают гейт таймаутом ДО вердикта, и родитель вынужден слать формальные `fix-first`-hold, чтобы удержать его.

- ✅ Floor (ребёнок): ждун `-t 1800` запускать в `run_in_background`, ANSWER писать в файл и читать по завершении; таймаут 1800 = merge по умолчанию, назвать в PR-body.
- ✅ Floor (родитель, автор промпта): в шаге «merge-гейт» писать `-t 1800` фоном; ⚠ tell — в промпте стоит `-t 540`, скопированный из §4.4 `spawn-nested-claude` (там протокол быстрых решений).
- ⛤ Родитель, получивший гейт с коротким таймером: ответить формальным `fix-first` с текстом «правок нет, ревью идёт, пришли новый WAITING_DECISION с -t 1800» — гейт держится, ветка не мержится.

_Empirical 2026-09-16 (orch main-27887 → child rsrmut): гейт `-t 540` истёк бы за 9 мин при ревью 18 мин ⇒ два hold-ответа; третий запрос `-t 1800` фоном дождался вердикта Approve-with-fixes._

- ⛔ **`run_in_background` ВЛАДЕЕТ процессом: `TaskStop` фоновой задачи убивает и порождённый ею долгий прогон** (драйвер мутантов, харнесс, синк) — не только ждун. Прогон, чей результат нужен независимо от формы ожидания, запускать ОТЦЕПЛЕННЫМ (`nohup <скрипт> > <лог> 2>&1 < /dev/null & disown`, rc — в файл), а ждать — отдельным `until [ -f <rc-файл> ]`-ждуном в `run_in_background`; тогда смена/остановка ждуна прогон не трогает. ⚠ Tell: хочешь остановить фоновую задачу, а в её команде стоит не `sleep`/`until`, а сам предмет. _(2026-09-17, child descgate: TaskStop обёртки «драйвер → rc-файл» снял драйвер вместе с ней; перезапуск через nohup, потеря ≈1 мин)_
