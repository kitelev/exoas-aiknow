# Anthropic API rate-limit silent child death — pattern + mitigation

При spawn нескольких child Claude sessions (дефолт `claude-opus-5[1m]`; исходная эмпирика снята на Opus 4.7) parallel или sequential rapid-fire, child может die silent rc=1 на orientation phase (первые 5-15 мин после spawn). Cause: Anthropic API rate-limit hit; child process exits **без EXITED ping** через `~/.claude/lib/child-ping-progress.sh` потому что claude TUI exit не graceful.

## Когда правило срабатывает

- Multi-task project orchestration с ≥3 concurrent или rapid-fire child spawns
- Heavy tasks (~400 LOC + advisor + code-reviewer round) saturating per-session token throughput
- Long-running orchestrator session с ≥4h uptime accumulating cumulative usage

## Detection signals

1. tmux session alive (`tmux list-sessions`) но child Claude process not progressing
2. No PROGRESS pings от child в `~/.claude/audit/child-lifecycle.jsonl` after ≥10 min post-STARTED
3. Vault task asset stays Doing с stale `updatedAt` past heartbeat cadence (15 min)
4. Pane capture shows `claude` exited (back to zsh prompt) но `[Child]` EXITED ping не emitted
5. `claude --version` works для new processes — это per-session quota, не global outage

## Mitigation tiers

### Tier 1 — Detective (orchestrator-side)

Standard heartbeat check за `updatedAt > timeout_hours` (per `orchestrator-prompt` Step 4 stale reset). After **2nd** silent death within session — escalate к Tier 2.

### Tier 2 — Strategy pivot к orchestrator-direct

⛔ **Mandatory after 2+ silent deaths in session** (steady-state) **OR 1 silent death in cold-start scenario** (см. ниже).

Switch к `orchestrator-direct` execution для remaining tasks (single API stream eliminates rate-limit risk). См. aiKnow `[[b9f65d5f-0a78-4274-9aa9-e51225b7c58a|Orchestrator-direct strategy ROI]]` для decision tree:
- LOC ≤200 + mechanical → ALWAYS orchestrator-direct
- LOC ≥400 + security-critical → still child IF rate-limit cleared (≥30 min между spawns)
- LOC ≥400 + low-security → orchestrator-direct (sacrifice code-reviewer round для recovery)

В **cold-start scenarios** Tier 2 fires AT **1 silent death**, не 2+. Cold-start = ANY of:

- Parent session has burnt heavy quota in last 60 min (multi-PR work, releases, multiple prior child spawns)
- Other claude processes active on same machine consuming quota (ccgram tenants, parallel user sessions, restored heavy sessions)
- Recent silent death events for unrelated children в last 30 min (death cluster signal)
- Just-recovered session post-SIGKILL (parent's quota state unknown but likely strained)
- Overnight delegation scenario (no human supervision, cost of cascade compounds)

В этих сценариях **первый silent death = catastrophe**, не сигнал. Subsequent spawns в same window будут also die (~30 min до rate-limit ceiling resets). Pivot immediately, не retry.

**Detection signals для orientation-phase death** (per `~/dotfiles/.claude/rules/overnight-orchestration-design.md` Type 2 section):
- Child STARTED ping received, но NO PROGRESS ping в 60-90 sec
- Pane content empty / shows только zsh prompt после claude TUI render attempted
- lifecycle.jsonl EXITED rc=1 within seconds of STARTED, no intermediate events
- Pane capture показывает claude version banner но no further activity

### Tier 3 — Resurrection (for died-mid-task)

Если child died **после** PR opened (B.3 RFC 0a0791c1 case):
1. Verify PR mergeable + CI checks SUCCESS (`gh pr view N --json mergeable,mergeStateStatus,statusCheckRollup`)
2. Manually `gh pr merge N --squash` если safe
3. Update vault task asset → Done с handoff note explaining resurrection
4. **Note follow-up:** code-reviewer round не выполнен → file Issue для post-merge audit

### Tier 4 — Recovery (for died-at-orientation)

Если child died **before** any meaningful work (≤5 min, no PR):
1. Reset task vault asset → Backlog (clear lock fields)
2. Sweep zombie tmux session (`tmux kill-session`)
3. Apply Tier 2 pivot

Different mechanism от Tier 2 orientation-phase silent death. Signatures:

| Signal | Mid-work stall (Tier 5) | Orientation cascade (Tier 2) |
|---|---|---|
| Child uptime when stuck | ≥10 min — substantial work done | ≤90 sec — never made progress |
| Tokens consumed | Real (100k+ typical) | Minimal (orientation-phase amount) |
| Pane content | Rich (tool results, plans, TODO progression) | Empty или just claude banner |
| Last tool call в jsonl | Substantial implementation work | None / aborted orientation |
| Error message | `API Error: Server is temporarily limiting requests (not your usage limit) · Rate limited` | Silent (no error logged) |
| Auto-recovery | None observed после 30+ min idle | N/A (already dead) |

### ⛔ Tier 5b — `403 Unable to verify organization membership`: НЕ троттл, и re-push БЕСПОЛЕЗЕН по построению

Tier 5 выше лечится ожиданием и re-push (серверный throttle снимается сам). Соседняя
сигнатура выглядит так же — cost заморожен, live-маркеров нет, idle-промпт, — но лечению
re-push **не поддаётся**: у сессии не проходит верификация, а не исчерпан темп.

| различитель | Tier 5 (throttle) | **Tier 5b (403 auth)** |
|---|---|---|
| строка в панели | `temporarily limiting requests` / `Overloaded` / `Rate limited` | `API Error: 403 Unable to verify organization membership` **+ `Please run /login`** |
| соседние сессии | обычно тоже страдают (аккаунт-wide) | ⛤ **работают** — проблема СЕССИОННАЯ |
| re-push / `C-m` | помогает, когда окно прошло | ⛔ **не помогает никогда** — cost остаётся замороженным |

- ⚠ **Симптом-tell, отличающий за один взгляд: `Please run /login`.** Троттл никогда не
  просит логина; 403 просит всегда.
- ✅ **Floor: не тратить циклы на nudge — сразу проверить СОСЕДА.** Работает ⇒ токен в целом
  валиден, сломана конкретная сессия (её процесс держит устаревший токен в памяти) ⇒
  снимать и дать планировщику пере-спавнить. Не работает ни один ⇒ это аккаунт-wide,
  и снимать бесполезно.
- ⛔ **Перед снятием — детектор осиротевшей работы, а не «дерево выглядит чистым».**
  `~/.claude/bin/orphaned-work-detect.sh` отвечает по ВСЕМ деревьям и отличает содержательный
  WIP от собранных артефактов (`dist/`), которые ни спасать, ни бояться не нужно.
- ⚠ **Статусбар `+N-0` — НЕ незакоммиченная работа**, а статистика сессии. Проверять
  `git status --porcelain`, а не читать футер.

**Empirical 2026-08-24** (`vteam-33ae6e4e`, движок vteam): 403 + `Please run /login`, cost
замер на `$26.06`, контекст 95 %, 30 мин простоя. Nudge с досылкой `C-m` — cost не сдвинулся.
Соседний воркер (`vteam-4518cfef`) в ту же минуту работал штатно ⇒ сессионное. Снят; детектор
осиротевшей работы дал единственную запись — `packages/cli/dist/index.js` (артефакт сборки).

**Tier 5 mitigation:**

1. **Don't kill immediately** — give 30 min для server throttle к clear naturally
2. **If still stuck after 30 min** — kill tmux session к release resources
3. **Preserve work — ⛔ «сохранено» ≠ «найдено».** Worktree + branch переживают kill, но незакоммиченное **никто не ищет** (два случая за двое суток, оба спасены случайно). ⇒ ДО kill перечислить вслух: `git -C <дерево> status --porcelain` + `find <дерево> -newermt '<STARTED>' ! -newermt '<EXITED>'`, и отдать в лог/уведомление (§Addendum 2026-08-10).
4. **Resume options для user morning:**
   - `claude --resume <session-id>` — re-load child's full conversation context
   - `cd <worktree>` + manual commit + PR — если work was mostly complete
5. **Do NOT re-spawn same task** — likely re-triggers throttle. Wait 1-2h before retry.

**Detection** (⛔ применимо, пока ребёнок ЖИВ и завис; после `kill-session` сообщения нет нигде — §A5):
```bash

# Empirically: appears as final assistant text before stall
```

## Addendum — proactive weekly-limit % как pre-spawn signal (не только post-mortem detection)

<!-- Added by /session-retrospective 2026-07-07 — root: composite-preconditions marathon session, 8+ child spawns, deferrals-backlog child словил orientation-phase server-throttle (0 tokens); statusline показывал 7d:94% (weekly limit) уже В МОМЕНТ спавна. -->

Существующие Tier 1-5 выше — **post-mortem detection** (ребёнок уже умер/завис, диагностируй сигнатуру). Дополнительный **pre-spawn** сигнал: TUI statusline футер несёт `7d:N%` (weekly account limit usage, сбрасывается по расписанию — формат `resets <date> at <time> (<TZ>)`). Если `7d:` приближается к 90%+ ПЕРЕД спавном очередного child'а в марафонской сессии (8+ детей, несколько ревью-панелей) — throttle-риск на orientation-фазе растёт некоррелированно с per-child Tier 2/5 сигнатурами (это account-level ceiling, не conversation-level).

**Практика:** при `7d:≥90%` — не паниковать (throttle транзиентен, снимается за минуты-часы), но: (1) не спамить retry-циклами при первой же неудаче — дать больше времени между попытками (эмпирика: провал → ~9ч пауза → успешный ре-спавн); (2) низкоставочные задачи (create-3-tasks) допустимо отложить без давления вместо форсирования сквозь throttle; (3) явно сообщить пользователю остаток недельного лимита в финальном отчёте сессии, если он высокий.

**Cost:** 1 упавший spawn (0 токенов, self-caught через orientation-phase health check per Tier 2 doctrine) + ~9ч естественная пауза до успешного ре-спавна. Урон 0 — низкоставочная задача, deferrals уже задокументированы в RFC (не потеряны на момент stall).

## Запреты

- ⛔ Re-spawn same task с idential child template ≥2 times — rate-limit will persist для ≥30 min
- ⛔ Ignore stale lock detection и assume child alive — wastes orchestrator monitoring cycles
- ⛔ Skip Tier 2 pivot после 2+ deaths — burns cumulative ~$60-90 на repeated orientation attempts
- ⛔ Lose work — если PR opened, **don't reset** task; resurrect (Tier 3)

## ⛤ Proactive detection: frozen-spinner FALSE-NEGATIVE + arm a pane-watcher (NEW 2026-07-12)

⛤ **ПЕРВЫЙ шаг, если пришёл с симптомом «спиннер на месте, а прогресса нет»:** слово спиннера
(`Brewed`/`Pondering`) — **НЕ маркер**, оно замерзает вместе с сессией. Живой = `esc to interrupt`
**ИЛИ** тикающий `↓ N.Nk tokens`. ⛔ Замороженный cost сам по себе столла НЕ доказывает —
он обновляется на ГРАНИЦЕ хода и замерзает на длинном xhigh-ходе. Столл ⇔ есть API-строка
**И** нет live-маркера **И** токен-счётчик не сдвинулся между двумя сэмплами.
⛤ Ниже раздел дважды сам себя квалифицирует — эта строка сводит все три слоя в один шаг.

Tier 1-5 above are **post-mortem** (диагностируй уже-зависшего). Но orientation-phase rate-limit stall **не пингует** (ребёнок не дошёл до PROGRESS → Monitor на lifecycle.jsonl слеп) — и **одноразовый capture-pane spot-check может FALSE-NEGATIVE**:

⛔ **Замороженная спиннер-СТРОКА обманывает stall-детекцию.** После зависа последний спиннер-кадр (`✻ Brewed for 36s` / `Pondering` / `Cogitated` / `Generating`) **ОСТАЁТСЯ на экране**. Grep этих СЛОВ → ложно читается как «активно генерирует». **Единственный надёжный маркер активной генерации — `esc to interrupt`** (присутствует ИСКЛЮЧИТЕЛЬНО во время генерации; исчезает на idle/stall). Замороженные спиннер-слова — НЕ маркер.

**Надёжная stall-сигнатура (для capture-pane проверки):** API-error/rate-limit строка в pane (`temporarily limiting requests`|`Rate limited`|`Overloaded`|`Internal server error`|`API Error`) **И** отсутствие `esc to interrupt` **И** (подтверждение) **замороженный cost/token-delta между двумя captures**. НЕ полагаться на наличие спиннер-СЛОВА.

⛤ **ОБРАТНАЯ ловушка — frozen-cost сам по себе ≠ stall во время ДЛИННОГО reasoning-хода (added 2026-07-30).** Footer-`$N.NN` cost обновляется на **границе хода**, а НЕ внутри него → на длинном xhigh-effort ходе (минуты чистого reasoning) cost **замерзает, пока ребёнок АКТИВНО генерирует**. Двух-capture frozen-cost проверки тогда ложно кричат «stall» → лишний nudge **прерывает валидный многоминутный ход**. Различитель: спиннер несёт **живой тикающий token-счётчик** `✻ <word>… (Nm Ns · ↓ N.Nk tokens · … thinking with xhigh effort)` — если `↓ N tokens`/«thinking»-часть **растёт** между captures ИЛИ таймер спиннера тикает, это АКТИВНЫЙ ход (cost догонит на границе), НЕ stall. Т.е. `esc to interrupt`-присутствие И тикающий token-counter — оба самодостаточные live-маркеры; frozen-cost — подтверждение stall **только когда И `esc to interrupt` отсутствует, И спиннер-token-counter не тикает**. Empirical 2026-07-30 (оркестрация remainder-issue): child orch-exosync показал `✻ Honking… (4m 1s · ↓ 13.2k tokens · almost done thinking with xhigh effort)` при cost, замороженном `$48.99→$48.99` — по one frozen-cost был бы ложный stall-nudge; token-counter `↓ 13.2k` + «almost done thinking» доказали активный ход (req-flip+retro), не тронул → child штатно завершил. Cost ложного nudge: прерванный многоминутный xhigh-ход (потеря reasoning-прогресса) — избежан.

**Мех-детектор (arm ОДИН раз при взятии роли, не per-spawn → низкий wallpaper-риск):** `~/.claude/lib/child-ratelimit-watch.sh "^issue-|^claude-child-" 45` как **persistent Monitor**. Каждые ~45с сканит панели детей; эмитит `RATE-LIMIT-STALL: <session> …` когда сигнатура держится 2 полла подряд без `esc to interrupt` (2-полловое подтверждение фильтрует транзиентные auto-retry). На событие → capture-pane подтвердить → **re-push** (re-send `Выполни под ключ <prompt>` — чистый рестарт если ~0 токенов; recovery проверено). Детекция-латентность ~90с vs пропущенный 1ч.

- **Empirical 2026-07-12** (issue-burndown оркестрация, 8 детей): 2 ребёнка (issue-3798/issue-3781, спавнились вместе 18:03) словили `Server temporarily limiting requests` на orientation → зависли **1ч7м** без auto-retry (idle `❯`, cost заморожен $2.56/$2.27). Мой spot-check (18:15) увидел `✻ Brewed for 36s` → grep матчнул как spin=1 → счёл 🟢 и пошёл дальше. Андрей поймал («проверь все дочерние сессии»). Re-push обоих → возобновились за секунды (были в самом начале). Fix: этот детектор + corrected active-marker. Cost промаха: ~1ч простоя 2 детей (низкий — ранняя фаза, работа не потеряна).

⛤ **ЛИТЕРАЛЬНЫЕ pane-паттерны для самодельного watchdog'а (added 2026-07-30 — иначе ложная stall-тревога на здоровом ребёнке).** Секции выше называют маркеры **семантически** («тикающий token-счётчик», «`esc to interrupt`»), и при написании своего детектора легко закодировать **неверную подстроку** — грепнуть `tokens ·`, тогда как реальный формат footer'а `· ↑ 36.2k tokens` (порядок обратный, стрелка обязательна). Такой греп даёт `live_markers=0` на **активно генерирующем** ребёнке → ложная тревога → лишний nudge, прерывающий валидный ход. Копировать буквально:

```bash
LIVE='esc to interrupt|thinking with|[↑↓] [0-9.]+k? tokens|◯ [A-Za-z]|· [0-9]+ shell'   # ЛЮБОЙ матч = ребёнок жив
STALL='temporarily limiting requests|Rate limited|Overloaded|Internal server error|API Error'
# stall ⇔ STALL-строка присутствует И LIVE отсутствует И cost ($N.NN) заморожен между 2 captures
```

<!-- Added by /session-retrospective 2026-08-03 — root: watcher выдал STALL-SUSPECT (cost замер на $74.99, 12 мин) на ребёнке, который штатно ждал СВОЙ фоновый CI-watcher между ходами. -->
⛤ **Две последние формы в `LIVE` — про «ребёнок ЖДЁТ СВОЮ РАБОТУ, а не завис», и без них детектор ложно срабатывает на самом частом состоянии.** Пока крутится суб-агент (`◯ Explore …` в сайдбаре) или фоновый bash (`· 1 shell` в статус-строке), **главный ход ЗАВЕРШЁН**: спиннера нет, токены не тикают, cost стоит на границе хода — то есть все три «классических» live-признака отсутствуют одновременно. А это ровно то, как выглядит ожидание CI: ребёнок армировал watcher и лёг между ходами на 10-15 минут.
- ⚠ **Симптом-tell, отличающий от настоящего затыка:** нет ни одной STALL-строки в панели. Настоящий затык всегда несёт `API Error`/`Rate limited`; «тихое» замирание без ошибки — почти всегда ожидание собственной фоновой работы.
- **Двухсигнальный детект обязателен** (нет LIVE **И** заморожен cost) — одного признака мало в обе стороны: frozen cost сам по себе бывает на длинном reasoning-ходе (§выше), а отсутствие LIVE бывает на границе хода.
- **Floor:** написав свой watchdog — **сначала прогони его на заведомо ЗДОРОВОМ ребёнке** и убедись, что он даёт `live=1`. Ложноположительный детектор хуже отсутствующего: он провоцирует nudge'и, прерывающие работу.

## ⛔ ГРУБЫЙ фильтр живости без `capture-pane`: `window_activity` РАБОТАЕТ, `session_activity` ВРЁТ У ВСЕХ

Секции выше требуют `capture-pane` на каждого ребёнка — это верно для **вердикта**, но
дорого как **первичный отсев**: наблюдателю над десятком сессий хочется одним вызовом
отбросить заведомо спящих. Естественный кандидат — `session_activity`; он для этого
**непригоден**, и непригоден тихо.

**Замер 2026-08-31 (11 сессий, одна команда, свои же панели):**

| поле | моя АКТИВНО работающая сессия | сейчас |
|---|---|---|
| `#{t:session_activity}` | **Sun Aug 30 13:39:30** (сутки назад) | Mon Aug 31 13:42:01 |
| `#{t:window_activity}` | **Mon Aug 31 13:42:01** (секунда в секунду) | — |

`session_activity` отстаёт у **всех 11** сессий (27-30 августа), включая attached. То есть
вывод «все сессии мертвы» из него получается **всегда** — это не редкий промах, а свойство.

- ⛔ **Они меряют РАЗНОЕ, а не «одно точнее»:** у одной сессии замера `window_activity`
  (26 авг) оказался **старше** `session_activity` (27 авг). Значит «взять большее» —
  не эвристика; надо брать именно `window_activity`.
- ✅ **Floor: грубый отсев — `tmux list-sessions -F '#S|#{t:window_activity}'`**, одна
  команда на все сессии; вердикт по-прежнему даёт `capture-pane` с `LIVE_RE` (§выше).
- ⚠ **Граница названа:** `window_activity` растёт от **любого** вывода, включая тик
  спиннера и печать статики ⇒ он отвечает «когда в панели последний раз что-то
  происходило», а НЕ «идёт ли ход». Ребёнок, замерший на idle-промпте после API-ошибки,
  какое-то время выглядит свежим. ⇒ это фильтр «кого можно НЕ смотреть», а не детектор
  затыка.
- ⛤ **Побочно тем же вызовом решается «жив ли владелец чужой правки»**: mtime файла
  сверяется с `window_activity` сессий — совпадение по времени называет кандидата за один
  вызов, без перебора панелей грепом (у которого своя слепая зона: сессия могла
  скроллнуться, и `capture-pane -S -400` её упоминания не увидит).

## ⛤ Re-push MECHANICS — как ДОСТАВИТЬ nudge застрявшему child'у (2026-07-25)

Секции выше говорят «re-push / nudge», но САМА доставка nudge к застрявшему child'у имеет две неочевидные механики (эмпирика 2026-07-25: тяжёлый child 8ч / 541k токенов / параллельная сессия на машине, **2 транзитных столла** — оба recovered):

1. **Enter проглатывается** (тот же класс, что `gui-input-verify-then-poll`): `tmux send-keys -t "$S" "<nudge>"` + `send-keys Enter` часто ставит текст в **очередь без сабмита** (pane показывает «Press up to edit queued messages» / текст в `❯`, спиннера нет). Fix: после Enter — **bare `tmux send-keys -t "$S" C-m`**. Verify: input пуст + появился спиннер («thinking with … effort» / `esc to interrupt`). Без verify легко счесть «пнул» за «доставил».
2. **Child «waiting on 1 shell» ≠ API-столл** — если child завис, ожидая СВОЙ фоновый шелл (напр. сам заармил tap-watcher: pane показывает `✻ Baked for Nm · 1 shell still running`, cost заморожен, но **нет API-error** в pane) — обычный nudge/`C-m` НЕ сабмитится (turn не завершён, ввод копится в очередь). Fix: **`tmux send-keys -t "$S" Escape`** (завершает зависший turn) → ТОЛЬКО потом `send-keys "<nudge>"` + `C-m`. Отличать от ECONNRESET/rate-limit-столла: столл несёт `API Error`-строку у дна + нет «1 shell»; waiting-on-shell несёт «1 shell still running» + нет API-error.

<!-- Added by /session-retrospective 2026-08-13 — root: вердикт merge застрял в очереди ребёнка за его же CI-вотчером (`· 1 shell`); повторная отправка с Escape доехала как `ERGE APPROVED`, и ребёнок всё равно эскалировал «оркестратор молчит 31 мин». -->
   - ⛔ **`Escape` СЪЕДАЕТ ПЕРВЫЙ СИМВОЛ следующего `send-keys`, если они идут в одном вызове.** Наблюдаемое: в панели `ERGE APPROVED` вместо `MERGE APPROVED`. Смысл обычно выживает (текст читаем), поэтому промах **не выглядит промахом** — но команда//слэш с отрезанной первой буквой уже не команда. ✅ Floor: `Escape` **отдельным** `send-keys`, затем текст **следующим** вызовом; либо начинать текст с пробела-жертвы. ⚠ Verify — не «текст виден в панели», а первое слово целиком.
   - ⛔ **Задержка доставки читается получателем как МОЛЧАНИЕ ОТПРАВИТЕЛЯ, и его dead-man таймер срабатывает ЛОЖНО.** Ребёнок мерил интервал от СВОИХ пингов, а не от времени моей отправки, — то есть измерял не ту сторону (`mid-turn-user-message-is-not-noise`: своя очередь ввода не доказывает молчание отправителя). ✅ Floor отправителю: доставку **verify'ить сменой состояния получателя** (появился спиннер / пустой ввод / он ответил), а не фактом, что твой текст виден в его scrollback — застрявший в очереди текст выглядит там ровно так же, как обработанный.

⛤ **Frozen-COST как watcher-сигнал (робастнее frozen-spinner-слов И grep «API Error»).** Bespoke pane-watcher для ОДНОГО интерактивного child'а (`run_in_background` until-loop) детектит столл по **замороженной стоимости в статус-баре** (`$NN.NN` не растёт 3 полла × 30с) **И** отсутствию generation-маркеров (`esc to interrupt|thinking with|↑/↓ tokens·|ing…`). ⛔ **НЕ грепать «API Error» как stall-сигнал** — старый API-error остаётся в scrollback после recovery → **ложное срабатывание** (было 2026-07-25: watcher матчнул stale «ECONNRESET» пока child уже генерировал). Cost растёт ТОЛЬКО при реальной генерации → замороженный `$` = не работает; это единственный надёжный «сейчас idle»-сигнал из pane. (Сигнатуры глифов спиннера варьируются — enumeration хрупок, см. §frozen-spinner.)

⛔ **НО frozen-cost В ОДИНОЧКУ — НЕ детектор столла; см. §ОБРАТНАЯ ловушка выше.** Footer-`$N.NN` обновляется на **границе хода**, поэтому на длинном xhigh-ходе он замерзает у ЖИВОГО ребёнка. **Watcher обязан ключеваться на СЧЁТЧИКЕ ТОКЕНОВ, а не на стоимости:** `grep -oE '[0-9]{6} tokens'` (общий контекст в статус-баре) и/или `↓ N.Nk tokens` спиннера — они тикают внутри хода. Минимальный корректный предикат столла: **токен-счётчик не изменился N сэмплов подряд** И нет `esc to interrupt` И нет открытого селектора.
⛤ **`esc to interrupt` / замороженный спиннер — сосед по наблюдаемому:**
`waiting-decision-ping-before-selector` — там сторож и его вердикты (`HALTED` / `PARKED` /
`BLOCKED`), здесь — сигнатура затыка и re-push. ⚠ Реакции ПРОТИВОПОЛОЖНЫ: ждущего человека
толкать нельзя, застрявшего на API — нужно.
