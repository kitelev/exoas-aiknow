## Разборы

## §A1 Empirical reference (child TUI-selector без jsonl-пинга → Monitor(jsonl) слеп → 70-мин завис)

<!-- Added by /session-retrospective 2026-07-04 — root: orchestrator onto-url-canon, child висел в interactive-selector ~70 мин, Monitor(jsonl) не сработал (selector не пишет в jsonl), оркестратор полагался только на пинги. -->

- **Date:** 2026-07-04, orchestrator `[Orch] Ontology_url #-канон` (child `onto-url-canon`, interactive-делегирование ExoSync-scope решений).
- **Инцидент:** child завершил под-шаг и построил **interactive TUI-selector** (AskUserQuestion-подобный, ждущий решения parent/user), но **НЕ эмитил lifecycle-пинг** (`child-ping-progress.sh WAITING_DECISION`). Мой `Monitor` был армирован на `tail -f child-lifecycle.jsonl` (jsonl-append). Рендер selector'а в TUI **в jsonl ничего не пишет** → Monitor молчал → сигнала «child ждёт» не пришло. Я сидел в «паузе до COMPLETED», на каждый дубликат старого notification отвечал «жду» + re-stop через interview-gate. Child висел в selector **~70 мин** (14:16→15:32), пока пользователь не пнул «почему завис».
- **Root cause (тройной, сложился):** (1) child не пингует при selector → jsonl-Monitor слеп; (2) оркестратор полагался ТОЛЬКО на пинги, **ни разу не сделал proactive `capture-pane`** за 70 мин (recurrence memory-правила 2026-06-22 «stalled child НЕ пингует → capture-pane обязателен, не полагаться на пинги»); (3) не армирован fallback (long ScheduleWakeup ИЛИ pane-watcher) на случай молчания Monitor.
- **Усугубитель:** interview-gate заставлял «отвечать» на каждый дубликат-notification → иллюзия активности («я же отвечаю»), маскируя, что 6+ одинаковых «жду» подряд без нового содержательного события — САМИ сигнал сделать health-check.
- **Fix that worked (митигация root cause):** армировал **pane-watcher** параллельно jsonl-Monitor — `Bash run_in_background` `until tmux capture-pane -t <child> | grep -qE 'Enter to select|↑/↓ to navigate'; do i++; [ $i -ge 45 ] && { echo TIMEOUT; exit; }; sleep 20; done` → одно уведомление когда child покажет selector ИЛИ ~15-мин timeout → proactive health-check. Ловит selector-без-jsonl-пинга. Двойное покрытие: jsonl-Monitor (пинги) + pane-watcher (selector-маркер). После этого зависов не было (переармировал ×3 до COMPLETED).
- **Lesson:**
  1. **Monitor на jsonl-append СЛЕП к TUI-selector'у child'а** (selector в jsonl не пишет). Для interactive-child армируй ЛИБО `Monitor` на **pane-content** (строка 9 — Monitor умеет `tmux pane content change`), ЛИБО параллельный **pane-watcher** (`run_in_background` until selector-маркер), не только jsonl-Monitor.
  2. **Child-side дисциплина** (эмить `WAITING_DECISION` ДО построения selector'а — signal-then-wait) вынесена в отдельное canonical-правило [[waiting-decision-ping-before-selector]]; ЭТО правило — про **orchestrator-side** (что делать, когда child всё же не запинговал: pane-watcher + proactive capture-pane). Две стороны одного урока.
  3. **N (≥2-3) одинаковых «жду» подряд БЕЗ нового содержательного события = триггер proactive `capture-pane`**, не продолжать пассивно ждать. «Silence is not success» применяется и к молчанию Monitor: если он давно молчит при активном child — проверь pane, не полагайся на «он запингует».

### ⛤ Размер слепой зоны ИЗМЕРЕН (2026-07-30): **14 % детей молчат полностью** — pane-watcher не «на всякий случай», а по базовой ставке

Аудит всей истории `~/.claude/audit/child-lifecycle.jsonl` (**737 дочерних сессий**, 6422 события):

| Сигнал | Доля сессий |
|---|---|
| дошли до `COMPLETED` | 77 % |
| потребовали решения человека (`WAITING_DECISION`) | 13 % |
| эскалировали (`ESCALATE`) | 3 % |
| упёрлись в блокер (`BLOCKED`) | 1 % |
| ⛔ **молчали — только `STARTED`/`EXITED`, ни одного `PROGRESS`** | **14 %** |

Т.е. **каждый седьмой child невидим для jsonl-Monitor по всей своей жизни**, а не в редком edge-case. Ping-дисциплина child-side (промпт мандатит пинги) на практике даёт ~86 % покрытия — оставшиеся 14 % ловятся ТОЛЬКО orchestrator-side (pane-watcher / proactive `capture-pane`). ⇒ **pane-watcher для любого долгоживущего child — базовая практика, а не подстраховка для «интерактивных».**

## §A2 Empirical reference (child в НЕПРЕРЫВНОМ stall не эмитит событий → passive Monitor слеп → 6.5-ч завис; heartbeat ОБЯЗАТЕЛЕН)

Родственно 70-мин-завису выше (Monitor слеп к TUI-selector'у), но здесь Monitor слеп к **непрерывному API-stall**, а не к selector'у:

- **Date:** 2026-07-30, оркестратор `main-67024` (overnight autonomous, 3 child-полосы).
- **Инцидент:** волна Anthropic **529/500 Overloaded** (concurrency-amplified) застопорила детей. plugin+core восстановились по nudge (R8) и закрылись. Последний child (orch-cli) застрял в **НЕПРЕРЫВНОМ** 529 → **оркестратор провисел 6.5ч** (01:52→08:26), пробуждён только сообщением Андрея.
- **Root cause:** armed только 2 **пассивных** Monitor'а (lifecycle-jsonl + rate-limit-watch) **БЕЗ ScheduleWakeup-heartbeat**. Оба слепы к непрерывному stall: (a) lifecycle-Monitor фаерит на COMPLETED/WAITING/EXITED — застрявший child их **не эмитит**; (b) rate-limit-watch фаерит на stall-**ONSET** (2-полл-подтверждение) — для НЕПРЕРЫВНОГО stall после первого события **новых нет**. → оба канала молчат навсегда → сон бесконечный. Усугубление: recovery-nudge `C-m` **не verify-сабмитился** (Enter проглочен занятым TUI, [[gui-input-verify-then-poll]]) → retry сидел несабмиченным часами.
- **Fix (митигация):** **ScheduleWakeup-heartbeat (600-900s) ОБЯЗАТЕЛЕН при активных детях** (не «только safety-net»). Heartbeat — ЕДИНСТВЕННЫЙ wake-канал в non-emitting тишине: на каждом wake проактивно `capture-pane` КАЖДОГО ребёнка, nudge с **verify-submit** (bare `C-m` + re-capture), **пере-арми** следующий heartbeat. ⛔ «жду только пассивный Monitor» без armed heartbeat = anti-pattern. Cost: 4 CLI-issue простояли 6.5ч (529 был перемежающимся — heartbeat пересабмитил бы retry в окно clear).
- **Cross-tie:** `/orchestrator` R5 (усилен этим инцидентом), [[waiting-decision-ping-before-selector]] (70-мин, selector-side), [[gui-input-verify-then-poll]] (nudge verify-submit), [[anthropic-api-rate-limit-child-death]] (529 concurrency-amplified).

## §A3 ⛤ Addendum 2026-08-02 — индикатор, обновляющийся на КАЖДОМ такте, не может быть детектором СОБЫТИЯ: watcher выходит на первом же такте

<!-- Added by /session-retrospective 2026-08-02 — root: watcher вышел на "worker-alive" (штатный пропуск тика), приняв его за завершение цикла. -->

Классическая ошибка при написании watcher'а за периодическим процессом (петля, cron, launchd-джоб): взять в качестве условия выхода **факт обновления** файла состояния (`health.json`, `status.txt`, mtime лога). Но такой файл переписывается на **каждом** такте — в том числе когда процесс штатно **ничего не сделал** («ещё работает», «нечего брать», «пропускаю»). Тогда watcher срабатывает на первом же такте и рапортует о событии, которого не было.

- ⚠ **Тот же класс, что frozen-cost/спиннер-слова выше** и что `statusCheckRollup` в [[ci-watch-check-runs-not-rollup]]: сигнал коррелирует с наблюдаемым, но не тождествен ему. Здесь — вырожденный случай: корреляция **нулевая**, индикатор меняется всегда.
- ✅ **Floor: условие выхода — по СОДЕРЖИМОМУ, а не по факту изменения.** Читай поле исхода и исключай штатно-пустые значения:
  ```bash
  if [ "$NOW_MT" != "$BASE_MT" ]; then
    BASE_MT="$NOW_MT"                                   # ⛤ сдвинуть базу, иначе сработает на следующей итерации
    grep -q '"outcome":"<штатно-пустой>"' "$H" || { echo СОБЫТИЕ; exit 0; }
  fi
  ```
- ⛤ **Сдвиг базы обязателен.** Если оставить `BASE_MT` прежним, каждая следующая итерация снова увидит «изменилось» — и watcher выродится в busy-loop с ложными срабатываниями.
- **Как выбрать условие за 10 секунд:** спроси «может ли этот индикатор измениться, когда НИЧЕГО не произошло?». Да → он не детектор, ищи поле исхода. Родственный тест — [[self-satisfying-metric-weak-verifier]]: там метрика не может быть красной, здесь — не может быть спокойной.

## §A4 ⛔ Addendum 2026-08-06 — у сторожа терминальные вердикты только для МАШИННЫХ событий: ребёнок, ждущий ЧЕЛОВЕКА, выкручивает полный потолок и возвращает `re-arm` — инструкцию, неверную ровно в этом состоянии

§ДИРЕКТИВА выше требует сторожа, пока жив хоть один ребёнок, и (п. 3) **re-arm после КАЖДОГО fire**. Оба требования верны — но покрывают только те исходы, которые сторож умеет назвать. `orch-child-health-watchdog.sh` знал три: `STALL` (API-ошибка + нет генерации + замороженный cost), `DONE` (сессия исчезла / `COMPLETED`), `ALLDONE`. Все три описывают **машинные** события.

⛤ **Ребёнок, припаркованный на СВОЁМ `AskUserQuestion`, не матчит ни один:** сессия жива, `COMPLETED` не эмитился, API-ошибки нет ⇒ `err=0` ⇒ `STALL` не сработает никогда. Цикл честно докручивает 48 итераций и возвращает `CEILING: 4h elapsed, children still active — re-arm`.

- ⛔ **Возвращаемая инструкция активно вредна в этом состоянии.** Re-arm не заставит человека ответить быстрее; он лишь купит ещё 4 часа опроса и ещё одно пробуждение оркестратора. Дисциплинированное следование п. 3 **и есть** источник шума.
- ⛤ **Вердикт сторожа ПРОТИВОРЕЧИЛ пингу самого ребёнка.** Ребёнок эмитил `WAITING_DECISION` («жду решения»); сторож в ту же минуту говорил «children still active — re-arm». Два наблюдателя одного объекта, противоположные выводы — и авторитетнее выглядел неверный (у скрипта есть «вердикт», у пинга только строка в журнале).
- ⚠ **Дискриминатор физически лежал в захваченной панели:** хвост вердикта 01:20 содержал `Enter to select · ↑/↓`. Данные были, ветки не было.
- ⛤ **Sibling-sweep — вот что делает это классом, а не багом одного скрипта.** У тика автономной петли ветка «ждёт решения» **есть** и она **безгранична** (57 мин простоя, [[waiting-decision-ping-before-selector]] §Addendum 2026-08-03 («панель на селекторе» ≠ вопрос к фаундеру)); у сторожа оркестратора её **нет вовсе**. Один объект, одно состояние, **зеркальные** отказы: там ждут вечно, здесь вечно опрашивают. Правило починило первого наблюдателя и не подмело второго — ровно [[verify-before-assert]] §A1 (sibling-symbol cascade).
- ⚠ **Симптом-tell, ловится счётом:** N одинаковых `CEILING` подряд при живом ребёнке. Одинаковый исход, повторённый без нового содержания, означает, что сторож наблюдает то, чего не может разрешить ([[activity-signal-is-not-progress]]).

**Floor (отгружено 2026-08-06):** два терминальных вердикта сверх машинных — `BLOCKED` (permission-prompt харнесса, нужен человеческий keypress) и `PARKED` (открыт селектор ассистента, ждёт фаундера). Оба **обязаны требовать `gen==0`** (сессия, ПЕЧАТАЮЩАЯ чужую панель, матчит те же регэкспы, пока генерирует — [[gui-input-verify-then-poll]] §A4 (`capture-pane | grep` матчит панель, которую сессия САМА напечатала)), и `BLOCKED` стоит **выше** `PARKED` (реакции противоположны — [[gui-input-verify-then-poll]] §Addendum 2026-08-05). П. 3 директивы получает вырез: после `PARKED`/`BLOCKED` **сперва релей человеку, re-arm только после ответа**. Заодно окно захвата поднято `-S -14` → `-S -30 | tail -25` (было ниже корпусного пола ≥25 строк, [[gui-input-verify-then-poll]] §Addendum 2026-08-06 (узкий `tail -N` не вмещает живой маркер)).

**Verify:** `~/.claude/bin/orch-watchdog-verdict-test.sh` — извлекает блок предикатов **из прода** и eval'ит (ручная копия проверяла бы себя); 6 фикстур, 5 исходов. `~/.claude/bin/orch-watchdog-revert-verify.py` — 3 мутанта прода, каждый краснит свою ось. ⛤ Первая версия харнесса держала guard-условия ручной копией — и два мутанта из трёх остались зелёными; поймано ровно ревёрт-верификацией, а не чтением.
