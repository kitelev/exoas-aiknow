## §A1 (2026-07-30) — bare-модель СГОРАЕТ на orientation: «100% context used» с нулевого хода

- **Date:** 2026-07-30, оркестрация проекта `8b5511fb` (reply-threading), спавн Phase 1.
- **Инцидент:** `claude-child-1c663b3d-1785406889` на bare `claude-opus-5` стартовал на «100% context used», ушёл в компакцию с нулевого хода, сжёг **$3.21 и ~20 мин** до первого tool-call, произвёл **0 работы** → killed. Замер после инцидента: baseline-корпус **545K** — в 200K не влезает физически. Модельная матрица meta-промпта исправлена на месте: все фазы → `[1m]`; повторный спавн прошёл R4-gate чисто (54% контекста).
- **Cost:** $3.21 + ~20 мин + один цикл правки промпта. Полностью предотвратим 30-секундной сверкой «контекст модели vs размер корпуса».
- ⚠ Порог **ползёт вверх**: корпус правил растёт с каждой ретроспективой. Матрица моделей в orchestrator-промптах — кандидат на периодическую ре-валидацию.

## §A2 (2026-08-06/09) — ПЕРЕ-ЗАМЕР 545K → 753K → 836K; `--setting-sources user` флор НЕ лечит

Предупреждение «порог ползёт вверх» материализовалось за **семь дней**. Пере-замер:

```bash
du -sk ~/dotfiles/.claude/rules            # 2616 КБ, 104 файла — ДОМИНИРУЮЩАЯ статья
wc -c ~/.claude/CLAUDE.md ~/dotfiles/Developer/CLAUDE.md \
      ~/dotfiles/Developer/exocortex-development/CLAUDE.md \
      ~/Developer/exocortex-development/exocortex/CLAUDE.md   # 93 КБ суммарно
# итого всегда-загружаемого текста: 2511 КБ ≈ 753 000 токенов (1 КБ русского md ≈ 300 токенов)
```

⇒ ребёнок на `[1m]` стартует с **~75 % занятого окна ДО первого tool-call**. Наблюдённое следствие: через 7 минут (прочитал промпт + задачу + RFC + пару исходников) — **91 %**, через 10 минут — 92 % и вход в компакцию.

⛤ **Update 2026-08-09 — оценку `du × 300` можно заменить ФАКТОМ API (одна команда, ноль коэффициентов):** первый ответ каждой сессии несёт полный префикс в `usage`, поэтому замер не требует ни `du`, ни допущения «1 КБ ≈ 300 токенов»:

```python
# ~/.claude/projects/<slug>/<session_id>.jsonl → первая запись с usage
u = msg["usage"]; floor = u["input_tokens"] + u["cache_creation_input_tokens"] + u["cache_read_input_tokens"]
```

Замер 09.08 по 34 сессиям: медиана **830 697**, свежая сессия **836 290** (84 % окна 1M). Разложение: `rules/` 494 626 (59 %) · харнесс (tool schemas + MCP + листинг агентов + системный промпт) ~304 000 (36 %) · `CLAUDE.md` ×3 20 002 · листинг 91 скилла 15 344.

⚠ **Не путать две величины (я на этом чуть не написал ложное расхождение):** `753K` выше — всегда-загружаемый **ТЕКСТ**; `836K` — **весь префикс**, текст плюс харнесс. Они и не должны совпадать; сверять замер надо со строкой «средний ход перечитывает 887 K», а не с 753 K. Коэффициент `×300` при этом занижает: фактическое отношение по `rules/` ≈ **326** ток/КБ.

- ⛔ **`--setting-sources user` этот флор НЕ лечит.** Корпус правил приезжает **user**-уровнем; project-уровень (`exocortex/CLAUDE.md` + два ancestor-`CLAUDE.md` + `.claude/settings.local.json` репо) — суммарно ~68 КБ ≈ 20K токенов, то есть 2.7 % проблемы. Рычаг из `nested-memory-project-duplicate` адресует **дубль** project-уровня, а не размер user-корпуса — не путать: там лечится 96 % объёма ТРАНСКРИПТА, здесь речь о стартовом occupancy окна.
- ⛔ **Респавн бесполезен** — флор общий для любого ребёнка. Увидев 90 %+ у свежего ребёнка, не убивай его: получишь то же самое.
- ⛤ **Актуальное следствие для ОРКЕСТРАЦИИ, а не для выбора модели.** Многочасовая петля `/feature-sdd` (worktree → npm → тесты → PR → CI-watch → SHACL → ретро) больше **не вмещается** в окно одного ребёнка: остаётся ~250K нормально и ~90K после разведки. Значит либо (а) резать задачу ребёнку мельче, либо (б) в промпте требовать **экономии контекста**: после КАЖДОЙ компакции пере-читать durable-тело задачи (там AC и ловушки) вместо доверия саммари; исходники и RFC читать **диапазонами** (`sed -n`), не целиком.
- ⚠ **Симптом-tell:** футер свежего ребёнка показывает ≥90 % контекста в первые 10 минут. Это **не** свойство его задачи и не аномалия — это флор. Не расследуй «что он прочитал такого большого».
- ⛤ **Проверять числом, а не «ну корпус вырос».** Один `du -sk` + `wc -c` стоят секунды и дают сравнимую с прошлой величину; вехикл, раздающий детям объём работы по устаревшему 545K, планирует по несуществующему запасу.

### ⛔ Коррекция 2026-08-09 (замер `20780efb`) — разложение выше ЗАНИЖАЕТ `rules/` и ЗАВЫШАЕТ харнесс: оно построено на коэффициенте, а не на факте

Строка 67 даёт `rules/ = 494 626 (59 %)` и `харнесс ~304 000 (36 %)`. Это соответствует ≈0.20 ток/байт, то есть **сырой оценке токенизатора**, а не замеру. Калибровка **фактом API** двумя независимыми путями:

| путь | что мерили | результат |
|---|---|---|
| регрессия по **21 дню** роста корпуса (868 КБ → 2 471 КБ, ×2.85) | `префикс = 132 898 + 0.2766 × байт(rules)` | **R² = 0.9804** |
| контроль: **180 сессий** бот-песочниц с **пустым** `rules` | префикс без корпуса | медиана **42 715** |

| статья | было (стр. 67) | факт |
|---|---|---|
| `rules/` | 494 626 (59 %) | **683 365 (83.7 %)** |
| харнесс + MCP + скиллы + `CLAUDE.md` | ~304 000 (36 %) | **132 898 (16.3 %)** |

Предсказание регрессии на сегодняшний корпус — **816 163** против наблюдаемых 793 277…836 384 (медиана 809 441), расхождение <1 %. ⇒ **ток/байт корпуса = 0.2766**, и доля, возвращаемая сокращением правил, в полтора раза больше, чем считалось. Пофайловая таблица + кандидаты — в задаче `20780efb-ea34-4e35-a2a5-f2b887b37481`.

⛤ **Вторая поправка того же замера — про РИСК, а не про размер.** «81 % занятого окна» само по себе воркера не убивает: на **70 воркерах** ALP пик контекста исходы **не разделяет** (умершие 602 K–968 K, выжившие 666 K–**970 576**, максимум у выжившего). Разделяет **одновременность**: у **3 из 3** оборвавшихся суб-агент был жив в момент обрыва (лаг ≤ 0), у остальных 67 — завершался за 12–48 мин до конца. ⇒ флор здесь **усилитель** (съедает запас, при котором ревью-гейт ещё безопасен), а не причина; отсюда практика «звать `code-reviewer` рано», а не «бояться большого контекста».

## §A3 (2026-08-07) — флор платится КАЖДЫМ ХОДОМ (cache-read): 95 % капасити на пере-чтение корпуса

Оба аддендума выше меряют флор как **occupancy** — сколько окна занято на старте (75 %). Это верно и **радикально недооценивает** его цену, потому что occupancy — свойство одного момента, а платится флор **на каждом ходу**: префикс перечитывается из кэша заново при каждом обращении к API.

**Замер собственного транскрипта (61.9 ч, 2214 ходов ассистента, 846 исполненных tool-call):**

| статья | токенов | капасити | доля |
|---|---|---|---|
| **output** — собственно работа | 3.6 M | $90 | **4.8 %** |
| cache **write** — пере-установка префикса | 128 M | $800 | 42.7 % |
| cache **read** — пере-чтение префикса | **1.965 **B**** | $983 | 52.5 % |
| | | **$1 872** | |

- ⛤ **Средний ход перечитывает 887 K токенов.** Флор (753 K) — **85 %** этого префикса ⇒ перечитывается именно **корпус**, а не разговор. Т.е. occupancy 75 % — это не «тесно», это **множитель на всю длину сессии**.
- ⛔ **Один ход стоит ~$0.80 в накладных НЕЗАВИСИМО от длины ответа** (output-часть хода — $0.04, в 20 раз меньше). Значит «сжать ответ» экономит 5 % статьи, а «не делать ход» — 100 %. **Рычаг — количество ХОДОВ и длина СЕССИИ, не лаконичность.**
- ⛤ **Supervisory-подпись прямо умножает счёт.** 2214 ходов / 846 вызовов = **2.6 хода на вызов** — та же величина, что `autonomous-mandate-drive-dont-idle` §Addendum 2026-08-06 (2.4). Раньше она читалась как «признак пассивности»; замер даёт ей цену: каждый лишний ход-подтверждение = $0.80, и полтора лишних хода на вызов — это **~60 % накладных сверх необходимого**.
- ⚠ **Доллары здесь — ПРОКСИ капасити, а не счёт** (Max-план). Ценность числа в том, что 7-дневный потолок рационирует ровно эту величину: в момент замера **7д = 84 % израсходовано при 38 % прошедшего**, и петля поставки стояла в `burn-rate-hold`.
- ⛔ **Структурная асимметрия, которая и делает это классом: у КАЖДОГО автономного актора есть предел, у интерактивного оркестратора — НЕТ.** Воркер петли получил возрастной предел 2026-08-07 (24 тика ≈ 6 ч, `waiting-decision-ping-before-selector` §Addendum 2026-08-07); ребёнок ограничен окном; тик — гвардом темпа. Сессия-оркестратор может идти 62 часа, и **ничто не сигналит** — её расход атрибутируется «аккаунту», а не актору.
- ✅ **Floor: на долгой сессии мерить СВОЙ cache-read, а не полагаться на ощущение «я же почти ничего не делал».** Одна команда по своему транскрипту (`usage.cache_read_input_tokens`), и она отвечает на вопрос «пора ли перезапускать оркестратора» числом. Перезапуск сбрасывает **разговорную** часть префикса; флор остаётся, но множитель обнуляется.
- ⚠ **Симптом-tell:** сессия идёт >суток И её ходы преимущественно надзорные («жду ребёнка», «продолжаю мониторить»). Тогда её главная статья расхода — не работа, а собственное существование.
## §A4 (2026-08-09) — флор делает СПАВН дорогим носителем: ~836K токенов за одну строку

Флор делает спавн дорогим не только для работы, но и для **микро-действий**. Типовой рефлекс: модель не может вызвать built-in команду харнесса (`/compact`, `/clear`, `/rename`) ⇒ «пусть дочерняя сессия пошлёт её мне через `tmux send-keys`». Дизайн рабочий и стоит **~836 000 токенов** — ребёнок грузит весь корпус, три `CLAUDE.md` и листинг скиллов, чтобы выполнить одну строку.

- ✅ **Floor: спросить, нужна ли для действия МОДЕЛЬ.** «Нажать клавиши через N секунд», «дождаться состояния панели», «переслать файл» — функции обычного фонового процесса. Claude-сессия нужна там, где требуется **суждение**; всё остальное дешевле на порядки (`rule-carrier-follows-function`: носитель следует функции).
- ⛤ **Побочная экономия крупнее самой цены:** у shell-процесса нет lifecycle-обвязки — не нужны retro-then-close (R7), `ORCH_TARGET`, pane-watcher, kill дочерней. Исчезает не только флор, но и весь протокол вокруг него.
- ⚠ **Симптом-tell:** ты формулируешь задачу ребёнка одной фразой без «реши / выбери / разберись». Одна фраза без суждения = не нужна модель.
## §A5 (2026-08-22) — формула регрессии ПРОТУХЛА на 16 %: мерить фактом, не предсказывать

Замер тем же инструментом, что описан ниже (`claude -p 'x' --model claude-haiku-4-5-…` печатает
точное число в отказе): **префикс = 653 483 ток** (65 % окна).

Формула из §Коррекция выше на тех же данных предсказывает **756 666**
(`132 898 + 0.2766 × 2 255 126` байт always-on правил) ⇒ **завышение на 103 K (16 %)**.

⛤ **Почему разошлось — не «формула плоха», а мир изменился под ней:** между её калибровкой
(2026-08-09) и сегодня введена **условная загрузка** (`paths:`, 9 правил = 153 756 байт), которой
в регрессии не было вовсе. Регрессия снималась на корпусе, где грузилось **всё**.

- ✅ **Floor: для решения брать ФАКТ, для планирования — формулу как ВЕРХНЮЮ оценку.** Замер
  стоит один вызов и не требует ни коэффициента, ни допущения о размере харнесса.
- ⛔ **Пере-калибровать коэффициент по одной точке НЕЛЬЗЯ:** неизвестных два (ток/байт и размер
  харнесса, который сам растёт с числом MCP-серверов и агентов), уравнение одно. Обратный счёт
  даёт 0.2308 ток/байт при допущении «харнесс = 132 898» — но допущение и есть слабое звено.
- ⚠ **Симптом-tell протухшей регрессии:** предсказание превышает **весь** наблюдаемый префикс,
  хотя предсказывает лишь его часть. Это арифметически невозможно ⇒ модель, а не данные.
- ⛤ Практически: все проценты флора, посчитанные через 0.2766, завышены примерно на пятую часть.
  Порядки при этом не меняются — выводы, опирающиеся на «единицы процентов», устояли.
