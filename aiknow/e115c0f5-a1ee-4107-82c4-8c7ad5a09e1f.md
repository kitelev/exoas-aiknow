# RFC-first verification protocol

## Принцип

При вопросах о value / scope / приоритете любого `ems__Project` (или работе которая может иметь RFC anchor) — **сначала читать source artifacts, потом задавать вопросы пользователю**.

## Правило

⛔ **Перед интервью / pitch / decision о проекте — обязательная mechanical pre-check:**

```bash
# 1. Найти project file
find /Users/kitelev/vaults/vault-exodev /Users/kitelev/vaults/vault-my /Users/kitelev/vaults/vault-tbank -name "<UUID>*.md"
#    ⛔ прежняя редакция звала `/Users/kitelev/vault-2025` — vault ДЕКОММИССИРОВАН 2026-06-27; исправлено 2026-09-10

# 2. Извлечь RFC anchors из exo__Asset_relates
grep "exo__Asset_relates\|Source RFCs\|Charter:\|RFC:" <project-file>

# 3. Прочитать RFC files
# Read tool на каждый найденный RFC UID
```

## Дискриминатор (один вопрос)

> **Отвечает ли на мой вопрос уже СУЩЕСТВУЮЩИЙ артефакт — и открывал ли я его в этом ходе?**

- **Открывал** (RFC по `exo__Asset_relates`, charter, handoff, датированное решение в графе) ⇒
  интервью законно, но только на **конкретный gap**, и этот gap называется цитатой из артефакта.
- **Не открывал** ⇒ интервью не выясняет, а **дублирует**: пользователь платит вниманием за то,
  что уже сказал и оцифровал.

⛔ **«Интервью ощущается продуктивным, а грепать — откладыванием» дискриминатором не является:**
это bias комфорта, а не протокол. Порядок обратный — сперва источник, потом вопрос.

⚠ **Второй вопрос — для темы БЕЗ входного UUID** (роль, процесс, модель, приоритизация): §Правило
буквально неисполнимо, и потому правило ощущается неприменимым. Оно применимо — заменяются только
входные запросы: артефакты по ключевому слову · журнал **ПРИНЯТЫХ** решений (`dec__Option_outcome`
= `OutcomeChosen`, иначе прочитаешь отвергнутые варианты как решения) · существующие скиллы.

## Tell

- ⚠ Ты собираешься спросить про value/scope проекта и **не резолвил** его RFC anchors.
- ⚠ Интервью идёт ≥3 раундов, к графу ты не обращался ни разу, а тема — из тех, что система
  оцифровывает массово (роли, процесс, жизненный цикл, приоритизация).
- ⚠ Ты копируешь способ проверки прошлого проекта, не спросив, **есть ли у ЭТОГО** RFC: «для N был
  интервью» не значит «для N+1 тоже».
- ⚠ Problem statement собирается из label задачи и имён фаз WBS — это спекуляция в обёртке анализа.
- ⚠ Самое дорогое здесь — **не дубль, а ПРОТИВОРЕЧИЕ**: решение, отменяющее уже принятое фаундером,
  выглядит новой договорённостью и тихо возвращает ему работу, которую он с себя снял.

## Что делать — decision tree

| Что нашлось в RFC trail | Действие |
|---|---|
| RFC существует, отвечает на вопросы scope/value | **Использовать RFC как ground truth.** Pitch / decision на основе RFC, а не speculation. |
| RFC существует, но ambiguous по конкретному вопросу | Цитировать RFC + конкретный gap → interview только по этому gap |
| RFC отсутствует, есть handoff doc / charter | Прочитать их сначала. Interview только если они тоже не отвечают |
| Никаких anchors в vault | Interview допустим — это true unknown, не lazy bypass |

## Запреты (anti-patterns)

- ⛔ Pattern-matching previous project verification approach без проверки доступности RFC (если для project N был interview, не значит что для project N+1 тоже нужен — может быть RFC).
- ⛔ Pitch / problem statement из speculation основанной только на project label / WBS phase names. Без RFC текст pitch becomes hallucination dressed as analysis.
- ⛔ «Conversational comfort» — interview feels productive, grep feels like deferment. Это bias, не правильный protocol.
- ⛔ Skip /knowledge-search skill для project value questions. Knowledge-search существует именно для этого.

## Floor — интервью по ТЕМЕ (роль / процесс / модель), а не по проекту: три запроса до первого вопроса пользователю

Входного UUID у темы нет, «## Правило» выше буквально невыполнимо — pre-check заменяют три запроса ниже. Механизм пробела, ⛤ «оцифровано ШИРЕ, чем помнишь», ⛤ «ПОЗДНИЙ сигнал» и разбор «⛔ Отсутствующий рецепт читается как ЗАПРЕТ» — в разделе «⛤ Интервью по ТЕМЕ …» (граф, оглавление роутера).

- ✅ **Floor — три запроса до первого вопроса пользователю** (⛔ не `grep -r` по vault, он блокируется хуком):
  ```bash
  V=~/vaults/vault-exodev
  # 1. артефакты по теме (label содержит ключевое слово)
  npx -y @kitelev/exocortex-cli@latest query --vault $V --no-cache \
    "SELECT ?s ?l WHERE { ?s exo:Asset_label ?l . FILTER(CONTAINS(STR(?l),'<ключевое слово темы>')) }" --format json
  # 2. журнал ПРИНЯТЫХ решений (тема могла быть закрыта интервью, не артефактом)
  #    ⛔ dec__Option — это ОПЦИИ развилок, ВКЛЮЧАЯ НЕВЫБРАННЫЕ. Дискриминатор —
  #       dec__Option_outcome: OutcomeChosen (принято) против OutcomeRejected (отклонено).
  #       Без него читаешь отвергнутые варианты как решения — хуже, чем не читать вовсе.
  npx -y @kitelev/exocortex-cli@latest query --vault $V --no-cache --format json \
    "PREFIX dec: <https://exocortex.my/ontology/dec#>
     SELECT ?l ?d WHERE { ?o dec:Option_outcome ?out . FILTER(CONTAINS(STR(?out),'OutcomeChosen'))
       ?o dec:Option_label ?l . OPTIONAL { ?o dec:Option_description ?d }
       FILTER(CONTAINS(LCASE(STR(?l)),'<корень темы>') || CONTAINS(LCASE(STR(?d)),'<корень темы>')) }"
  #    ⛤ Сильнее — вместе с ФОРМУЛИРОВКОЙ развилки: видно и отклонённые варианты,
  #       то есть ПОЧЕМУ выбрано именно это (снимает риск перетолковать решение):
  #       ?o dec:Option_fork ?fk . ?fk dec:Fork_question ?q  + печатать outcome каждой опции.
  # 3. скиллы (роль может быть уже автоматизирована)
  grep -rln '<ключевое слово>' ~/dotfiles/.claude/skills/*/SKILL.md
  ```
- ⛔ **Самое дорогое последствие — не дубль, а ПРОТИВОРЕЧИЕ.** Дубль виден и склеивается; решение, отменяющее уже принятое фаундером, выглядит как новая договорённость и тихо возвращает ему работу, которую он с себя снял. Ищи в найденном не «похожие идеи», а **датированные решения о своей роли**.
- ⚠ **Симптом-tell:** интервью идёт ≥3 раундов, ты ни разу не обратился к графу, а тема — из тех, что система оцифровывает массово (роли, процесс, жизненный цикл, приоритизация). Отсутствие входного UUID — не индульгенция.

## ⛤ Интервью по ТЕМЕ (роль / процесс / модель), а не по проекту — pre-check ДРУГОЙ, и потому правило ощущается неприменимым

Тело правила требует pre-check **перед интервью**, но выражает его через **проект с известным UUID** (`find <UUID>*.md` → RFC anchors). Когда интервью идёт по **теме** — «как устроен процесс», «какие роли», «какой жизненный цикл у X» — входного UUID нет вовсе, шаг 1 буквально невыполним, и правило читается как «не про этот случай». Пробел не в знании, а в **отсутствии механики для темы**.

- ⛤ **Тема почти всегда оцифрована ШИРЕ, чем помнишь.** Один RFC найти легко; но модель процесса живёт **россыпью**: onto-RFC про конвейер + RFC на каждую роль + aiKnow с проверенным воркфлоу + журнал решений интервью. Ни один из них не назван так, как ты формулируешь тему.
- ⛤ **Обнаружение по просьбе пользователя («поищи параллельную сессию») — ПОЗДНИЙ сигнал.** Он означает, что связь с существующим заметил он, а не ты; к этому моменту решения уже приняты и их приходится пересобирать.

### ⛔ Отсутствующий рецепт читается как ЗАПРЕТ: floor, назвавший носитель без исполнимого запроса, гарантирует, что носитель не откроют

Пункт 2 списка выше **год существовал заголовком без команды** — только ⛔-строкой «`dec__Option` это
опции, не решения». Формально верно и практически вредно: читатель видит **предупреждение** и не
видит **способа**, поэтому вывод — «сюда лучше не лезть», а не «вот дискриминатор». Носитель при
этом самый населённый из перечисленных: замер 2026-08-22 — **980 выбранных решений** против
единиц RFC по любой конкретной теме.

- ⛤ **Дефект тише отсутствия пункта.** Пункта нет ⇒ ты замечаешь пробел и ищешь сам. Пункт есть,
  но неисполним ⇒ floor **выглядит пройденным** («три запроса» — я же прочитал список), а третий
  источник не открыт. Тот же класс, что `rule-carrier-follows-function` §Floor выноса п.3
  (строка индекса без действия хуже отсутствующей).
- ⚠ **Симптом-tell, ловится при чтении собственного floor'а:** пункт списка состоит **только** из
  ⛔-предупреждения о том, как делать НЕ надо. Предупреждение без положительной формы — это не
  инструкция, а тупик; допиши рабочий вариант либо убери пункт.
- ⛔ **Цена промаха ассиметрична и платит её ФАУНДЕР.** Не «лишний запрос» — **повторно заданный
  вопрос**, то есть его время на решение, которое он уже принимал. Реакция на это (2026-08-22,
  дословно): «Я на все эти вопросы уже отвечал. Не собираюсь повторяться. Найди у Санья в памяти,
  истории, знаниях и тд.»
- ⛤ **Формулировка развилки ценнее самого выбора.** Запрос по `Fork_question` + `outcome` каждой
  опции показывает и **отклонённые** варианты — то есть границы решения. В наблюдённом случае
  именно это спасло от перетолкования: выбранное «весь конвейер → `flow__`» соседствовало с
  «личное остаётся `ems__`», и без второй половины поправка была бы применена шире, чем решено.

**Empirical 2026-08-22** (дочерняя сессия-интервью, 16 вопросов): три вопроса подряд оказались
переспросом. Журнал отдал ответы **первым же запросом** после того, как Андрей на него указал:
механизм ревьюера («ревью ОТДЕЛЬНОЙ ЗАДАЧЕЙ очереди, следующий воркер ревьюит коммит предыдущего
своим свежим окном»), аккаунты («обе подписки твои — под запреты не попадает»), рамка онтологии
(«весь конвейер, включая RFC и требования» → `flow__`/`team__`). Ни один не потребовал нового
интервью; все три были в графе к моменту вопроса.
