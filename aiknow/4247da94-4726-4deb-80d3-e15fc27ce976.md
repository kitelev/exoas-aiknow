# Commit & Push Rule

При изменении файлов в git-репозиториях (dotfiles и любых других; ⛤ каноничные vault **git-free** — там ExoSync, не git) — ВСЕГДА коммитить и пушить изменения перед тем как сообщить "Готово".

## Порядок
1. Изменить файлы
2. `git add` только изменённые тобой файлы (⛔ перечислять ФАЙЛЫ, не каталоги)
3. `git diff --cached --stat` — в индексе ровно твои файлы → `git commit <файл1> <файл2> -m "…"` **pathspec-формой**. ⛔ НЕ bare `git commit`: он уносит весь индекс, включая чужое pre-staged (§Bare `git commit`)
4. `git push`
5. Только после успешного push — "Готово"

## Исключения
- Репозитории без remote (локальные)
- Когда пользователь явно просит НЕ пушить

## ⛔ `git rm` + `git add` interaction (не передавать удалённый путь в git add)

`git rm <path>` **уже стейджит удаление**. Если потом передать тот же `<path>` (или путь
удалённой папки) в `git add` — `git` возвращает `fatal: pathspec '<path>' did not match any
files` и **прерывает весь `git add` целиком**, не застейдив остальные (Edit-модифицированные)
файлы. В результате `git commit` уносит только удаления (staged через `git rm`), а правки
выживающих файлов **молча теряются** из коммита.

**Правило:** после `git rm X` — в последующий `git add` включать **только отдельно
отредактированные файлы**, НИКОГДА не путь `X` (он уже staged). Проверка: `git status --short`
до commit — все ожидаемые `M`/`D` строки на месте.

## ⛔ `git add -A` в worktree после build/test сметает артефакты + submodule-указатели (selective-staging trap)

<!-- Added by /session-retrospective 2026-06-22 — root: child al-night-dogfood git add -A swept build/test residue + submodule pointers -->

`git add -A` (или `git add .`) кажется безопасным в «свежем worktree, всё моё» — но как только в worktree прогнаны **build** (tsc/esbuild dist-артефакты) и **tests** (flaky-reports, test-vault `main.js`), а также если worktree содержит **git submodules** (их gitlink-указатели могут «дрейфовать»), `git add -A` стейджит **всё это** вместе с твоими правками. На multi-package repo с submodules это особенно коварно: staged submodule-указатели + отсутствующий/несвежий `.gitmodules`-blob дают `error: invalid object … for '.gitmodules'` + `Error building trees` при commit (тот же класс симптома, что lint-staged-corruption — легко спутать).

**Правило:** в worktree, где прогонялись build/test, — **selective staging пофайлово** (`git add <path1> <path2> …`), НИКОГДА `git add -A`/`git add .`. Перед commit — `git diff --cached --name-only`: список должен быть **ровно** твои файлы (нет `dist/*.d.ts`, `flaky-report*.json`, `test-vault/**`, submodule-путей, которые ты не менял намеренно).

## ⛔ КАТАЛОГ в `git add` — тот же selective-staging trap, что `-A`, но выглядит «уже селективным»

`git add -A` настораживает; `git add .claude/rules/ .claude/skills/` — **нет**: перечислены конкретные каталоги, ощущение «я же указал, что именно». Но в общем dotfiles-репо каталог **шире твоей работы** — в нём живут файлы, которые прямо сейчас правит параллельная сессия, и каталожная форма забирает их **все**.

- ⛤ **Дискриминатор простой: `git add <каталог>` стейджит по СОСТОЯНИЮ дерева, `git add <файл> …` — по твоему СПИСКУ.** Первое — снимок чужой активности вместе с твоей; второе — утверждение о собственной работе. В репозитории с одним писателем разницы нет, в общем — это разные операции.
- ⚠ **Симптом-tell до коммита:** `git status --short` показывает файл, которого ты не открывал. ⛔ Не списывать на «наверное, я задел» — открой `git diff <файл>` и посмотри на `stat` mtime: свежий mtime (минуты) = живая чужая работа, а не твой след.
- ✅ **Floor: перечислять ФАЙЛЫ** (`git add <p1> <p2> …`) → `git diff --cached --name-only` (ровно твой список) → `git commit <p1> <p2> … -m` (pathspec-форма, игнорирует прочий индекс — §ниже).
- ⛔ **Каталожная форма особенно живуча, потому что её мандатят ИНСТРУКЦИИ.** `/session-retrospective` Step 8.5 печатает буквально `git add .claude/hooks/ .claude/skills/ .claude/rules/` — то есть шаг, требующий персистить митигации, сам же и бандлит чужое. Читать его как «перечисли свои файлы из Step 6.5», а не исполнять дословно (`declaration-and-executable-carrier`: правило объявляет selective staging, носитель мандатит каталог — побеждает носитель, потому что его читают в момент работы).
## ⛔ Даже `git add <ФАЙЛ>` забирает чужое: `git status` показывает `M`, но НЕ показывает ЧЬЁ

Секции выше лечат **область** staging (каталог вместо файлов, bare `commit` поверх чужого индекса). Остаётся третий вход, который они не закрывают: ты стейджишь **ровно один файл**, дисциплина соблюдена — а в файле лежит **твоя правка ПОВЕРХ чужой незакоммиченной**. `git status --short` печатает `M <путь>` в обоих случаях; признак авторства в нём отсутствует **по построению**.

- ⛤ **Механизм появления чужой правки:** автономный воркер (петля, демон) правит общий файл и **умирает до коммита** — его работа остаётся в рабочем дереве как обычная модификация (`anthropic-api-rate-limit-child-death` §Addendum 2026-08-10). Живых сессий рядом может не быть вовсе, поэтому «сейчас никто не работает» ложным чувством безопасности **усиливает** промах.
- ⚠ **Симптом-tell до коммита, стоит один вызов:** `git diff <файл>` показывает hunks, которых ты не писал. ⛔ Не списывать на «наверное, задел рефакторингом» — посмотреть их содержательно: чужой код обычно решает **другую** задачу, чем твоя правка.
- ✅ **Floor для файла, который трогают автономные акторы:** перед `git add` — `git diff <файл> | grep -c '^+'` против числа строк, которые ты сам добавил. Расхождение = чужая работа в дереве; решать её судьбу **отдельно** (проверить харнессом, закоммитить с атрибуцией), а не заметать в свой коммит.
- ⛔ **Уже уехало — не переписывать историю** (на remote, force-push запрещён): атрибуция фиксируется **следующим** коммитом с явным «код уехал в `<sha>` по моей ошибке staging». Обнаруживается постфактум одной командой: `git log -S '<строка чужого диффа>' -- <файл>` покажет **твой** коммит там, где строку ты не писал.

- ⛤ **Самый дешёвый tell — ДИФФСТАТ вывода `git commit`, и он работает ПОСТФАКТУМ, когда floor выше уже пропущен.** Floor требует свериться до `git add` (то есть помнить, сколько строк ты добавил); диффстат печатается сам и сверяется с порядком величины: «правил один блок и два комментария» ≈ десятки строк, а `343 insertions(+)` — нет. **Расхождение НА ПОРЯДОК = в коммите чужое**, и проверяется одной командой: `git show HEAD -- <файл> | grep '^+' | grep -v '<маркеры своей темы>'`.
  - ⚠ Работает и там, где `git diff` до коммита **бесполезен**: чужая правка может быть в **том же** файле и внешне однородна твоей (комментарии того же стиля, соседний блок) — глазами в диффе она не выделяется, а в счёте выделяется сразу.
  - ✅ **Не запушено ⇒ чинится дёшево и без переписывания истории:** `git commit --amend -F <файл>` с честной атрибуцией (чья работа, из какой задачи, почему подобрана). Запушено ⇒ следующим коммитом, как выше.
  - ⛤ **Найдя чужое — проверь, не осталась ли его задача в `Doing`**, и допиши в её тело, где теперь лежит работа: иначе её преемник увидит чистое дерево и начнёт с нуля (`anthropic-api-rate-limit-child-death` §A3).

## ⛔ Чужой коммит в общем репо бьёт ДВАЖДЫ: превентивный `rebase` отказывает, а КРАСНЕЕТ у тебя ЧУЖОЕ

Секции выше — про **staging** (не забрать чужое в свой коммит). Оставшиеся два входа не про staging вовсе, и оба возникают в общем репо (dotfiles правят все параллельные сессии + hourly auto-backup), где рабочее дерево почти никогда не чистое:

1. ⛔ **Не делать `git fetch && git rebase` ПРЕВЕНТИВНО — сперва посчитать `behind`.** `rebase` **требует чистого дерева**, поэтому при живых чужих правках он отказывает **штатно** (`cannot rebase: You have unstaged changes` / `Please commit or stash them`) — и толкает ровно к запрещённому: `git stash` чужого WIP. При этом он чаще всего не нужен: `behind = 0` ⇒ push и так пройдёт fast-forward.
   ```bash
   git -C <repo> rev-list --left-right --count origin/main...HEAD   # "<behind>\t<ahead>"
   ```
   `behind = 0` ⇒ rebase не нужен · `ahead = 0` ⇒ коммит уже на remote (вероятно, забрал auto-backup) · rebase только при `behind > 0` **и** чистом дереве.
   ⛤ Прежде это знание жило **только** в `session-retrospective` §Step 8.5 — то есть доезжало к моменту ретро, а не к моменту работы, когда push и делается (`rule-carrier-follows-function`: барьер обязан стоять там, где действие).

2. ⛔ **Красный тест / мутант на компоненте, который ты НЕ ТРОГАЛ, при зелёном проде — сперва `git log` по этому пути, а не поиск своей регрессии.** В общем репо между твоей базовой линией и повторным прогоном мог лечь чужой коммит; если он правил код, **общий** с твоим (вторая петля, соседний адаптер, разделяемый хелпер), краснеет у тебя — а причина в чужой правке.
   ```bash
   git -C <repo> log --oneline -3 -- <путь-который-покраснел> | cat
   ```
   - ⚠ **Симптом-tell:** красное там, куда твой диф не заходил **вообще**. Не «наверное, я задел» — посмотри лог: коммит с чужой темой и временем внутри твоей сессии закрывает вопрос за секунды.
   - ⛔ **Проверь, не затираешь ли ты их правку:** твой рабочий файл мог разойтись с HEAD (`git show HEAD:<путь> | diff - <путь>`). Их коммит мог обновить то, что ты сейчас переписываешь.
   - ⛤ **Чинить — можно и нужно, если красное блокирует ТВОЙ DoD** (мутант — часть твоей приёмки). Но чинить **минимально** и сказать вслух, чью правку это восстанавливает; ⛔ не расширять правку на их свежую поверхность — заведи остаток задачей.

## ⛔ `git diff` ПОСЛЕ `git add` — ПУСТО: спасая работу патчем перед сносом worktree, бери `git diff HEAD`

Стандартный сценарий потери: pre-commit не пропустил коммит (тесты красные по независимой причине), обходить его нельзя, работу надо сохранить — делаешь `git diff > /tmp/x.patch`, кладёшь патч куда-то durable, сносишь worktree. ⛔ Если перед этим был `git add`, патч выйдет **пустым**: `git diff` без аргументов показывает только **неиндексированное**, а твои правки уже в индексе.

- ⚠ **Отказ тихий:** `git diff` возвращает `rc=0` и пустой файл — команда «выглядит» отработавшей. Дальше `worktree remove --force` уносит и дерево, и индекс.
- ✅ **Floor: `git diff HEAD`** (всё против последнего коммита — и staged, и нет). `--cached` покрывает только индекс, то есть половину случая.
- ✅ **И проверять размер:** `[ -s patch ] || { echo "⛔ патч пуст"; exit 1; }` — одна строка, ловит класс целиком.
- ⛤ **Патч часто вообще не нужен: механическую правку дешевле описать РЕЦЕПТОМ.** Замена «N файлов × 1 вхождение» воспроизводится скриптом с `assert n == 1`, и такой рецепт **не протухает** от смены контекста вокруг, в отличие от diff'а.
- ⚠ **Ветка при этом выживает и вводит в заблуждение:** `git branch --list` покажет её живой, но она указывает на коммит **без** твоих правок — они были только в индексе снесённого worktree.

**Empirical 2026-08-20** (задел `quotingType → quoteStyle` ×7 под #4156): pre-commit корректно отверг коммит (CLI-тесты красные из-за js-yaml 5), `git add -u` уже отработал, `git diff > patch` дал **0 строк**, worktree снесён. Работа восстановлена только потому, что была механической — в issue ушёл исполнимый рецепт вместо патча.

## ⛔ Bare `git commit` сметает PRE-staged файлы из чужих сессий (selective-commit trap)

`git add <file1> <file2>` стейджит твои файлы, но индекс мог **уже содержать** staged-изменения, оставленные **другой/прошлой сессией** (или процессом). Bare `git commit` (без pathspec) коммитит **весь индекс** → подметает эти pre-staged файлы в твой коммит под твоим (нерелевантным им) commit-message. В лучшем случае — blemish трассируемости; в худшем — забандлишь чужую WIP / sensitive файл.

**Правило (selective commit):**
- Перед commit — **`git diff --cached --stat`**: убедись, что staged ровно твои файлы. Если видишь чужой staged файл — реши осознанно (committed by you? leave for owner?).
- Коммить **pathspec'ом**: `git commit <file1> <file2> -m "..."` — коммитит ТОЛЬКО перечисленные пути из индекса, игнорируя прочие staged. Это надёжнее, чем `git add <files> && git commit`.

## ⛔ Переименование (`git mv`) в pathspec-коммите обязано нести ОБА пути — иначе коммит кладёт КОПИЮ без удаления

`git commit <pathspec>` берёт из индекса только записи, попадающие в pathspec. У переименования их **две** — удаление старого пути и добавление нового; pathspec из одних новых путей уносит **добавления**, а staged-удаления остаются в индексе ⇒ в дереве коммита лежат **оба** файла (дубль UID / basename), и push доставит дубль на remote (`vault-operations` §File Movement — тот же класс, что «перенос без удаления»).

- ⚠ **Tell ловится диффстатом ДО push:** `git show --stat HEAD` даёт insertions размером с полные файлы (у меня 714 при ожидаемых 112) и `git status --short` после коммита по-прежнему непуст (staged `D`).
- ✅ **Floor:** список путей для `git commit --pathspec-from-file` = **новые + старые** пути переносов + правленые файлы; проверка — `git show --name-status -M HEAD` печатает `R` (rename), а не `A` + оставшиеся `D`.
- ⛤ Не пушен ⇒ `git reset --soft HEAD~1` и коммит заново (не `--amend`: rule запрещает его как класс, а reset локального непушенного коммита — нет). ⛔ Многострочную переменную путей в `git add $VAR` zsh НЕ расщепляет (Г1) — `--pathspec-from-file`.
