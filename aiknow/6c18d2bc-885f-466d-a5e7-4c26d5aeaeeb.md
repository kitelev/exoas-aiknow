## Разборы

## §A1 Addendum 2026-07-18 — `archgate` = ОТДЕЛЬНЫЙ required-чек (ADR compliance), НЕ lint; version-drift ломает репо-правила, и ADR-правило фейлит PR только когда тот трогает оцениваемый файл

`archgate` — самостоятельный required-чек (`archgate check --ci`, ADR-compliance), не связан с `lint`-job. Три грабли (эмпирика PR #3914, debounce scanVault):

1. **Version-drift: CI качает archgate-**БИНАРЬ** свежий каждый ран** (`archgate: binary not found, downloading v0.50.0…`), `npm install -g archgate` не пинит. Между 07-16 (main green) и 07-18 (моя PR) вышел **v0.50.0** со **строже rule-file security-scanner**. Main passed на старом, PR failed на новом → **не мой код, не флак, а version-drift**. `gh run rerun --failed` НЕ помогает (детерминированно).
2. **ADR-правило фейлит PR, ТОЛЬКО когда PR трогает файл, который правило ОЦЕНИВАЕТ.** MOBILE-004 (desktop-only-command-gate) сканирует `ExocortexPlugin.ts`. Мой фикс (debounce metadataCache-handler) обязан менять там строку → MOBILE-004 запускается → под v0.50.0 его rule-файл (`.archgate/adrs/MOBILE-004-*.rules.ts`) падает. Другие PR (main/#3913/#3826) не трогают ExocortexPlugin.ts → правило не запускается → зелено. Симптом: `check failed: 22 passed, 0 failed, 41 warnings` exit 2 (main: 23 passed exit 0) — **один чек «отвалился» из passed** (rule execution error), а НЕ «1 failed».
3. **v0.50.0 запрещает rule-файлам импортить ЛЮБОЙ local-модуль** (только `node:path/url/util/crypto`) → `##[error]rule file blocked by security scanner … Import of ../lint/desktopOnlyCommandGate is blocked … use the RuleContext API`. **Fix:** заинлайнить чистые функции ВНУТРЬ rule-файла как named exports (единый источник); jest-тест импортит их ИЗ rule-файла (ts-jest резолвит global `RuleSet` через `/// <reference path="../rules.d.ts" />`) → **без дрейфа**. ⛤ `npx archgate` **локально может НЕ воспроизвести** CI-фейл (иной дистрибутив/версия vs CI-бинарь) — верифицировать fix только через CI-прогон gating-PR (authoritative=CI, [[pre-spawn-issue-staleness-check]]). Bundling infra-fix в тот же PR, что триггерит правило = единственный способ проверить (правило срабатывает только на PR, трогающем ExocortexPlugin.ts).

## §A2 Addendum 2026-07-27 — АВТОРИНГ нового archgate-правила: report-API = `ctx.report.violation` (НЕ `.error`); revert-verify против ЛОКАЛЬНОГО бинаря ловит API/логику, которую «N passed» скрывает

Обратная сторона аддендума 2026-07-18 п.3 («локальный `npx archgate` может НЕ воспроизвести CI-фейл»): при **создании** нового rule-файла локальный бинарь (даже версией НИЖЕ CI, здесь 0.43.0 vs pinned 0.50.0) **ловит** ошибки авторинга, которые тихо ушли бы в CI. Две конкретные грабли:

1. ⛤ **`ctx.report.error(...)` НЕ существует** — на 0.43.0 даёт `Rule execution error: ctx.report.error is not a function`. Правильный API для finding'а любой severity — **`ctx.report.violation({...})`** (уровень задаётся полем `severity: "error"|"warning"` самого правила, не именем метода). Все существующие error-правила (`MOBILE-004`, `ARCH-008`, `SEC-001`, …) используют `ctx.report.violation`; ровно один файл использовал `.error` — моё новое правило, и оно упало. **Floor: НЕ угадывать report-API — грепнуть `ctx\.report[.(]` в соседних `.rules.ts` и зеркалить рабочую форму** (verify-before-assert: `report.error` в грепе матчился на severity-строку, не на реальный метод-вызов — читать контекст, не только имя).

2. ⛤ **Revert-verify нового правила ОБЯЗАТЕЛЕН против бинаря, не только «check passed: N».** Счётчик `passed` рос 23→24 (правило зарегистрировано + скомпилировалось) — но это НЕ доказывает, что оно ФАЙРИТ finding корректно (метод-вызов достигается только когда правило что-то нашло). Revert-verify (убрать fix → правило должно дать `check failed: 1` с моим ADR-id; вернуть → `0 failed`) — единственное, что упражнило `ctx.report.*`-путь и вскрыло `.error`-баг. Дёшево: временно strip'нуть литеральный anchor из тестируемого файла → `archgate check --ci` → grep на `<my-rule-id>|check (passed|failed)` → restore. Плюс python-эквивалент регэкспа правила = детерминистичный второй свидетель (флагует ровно ожидаемое).

3. **Precision-детект для «title-opener vs fixture-string»:** regex `\b(?:it|describe|test)\s*\(\s*` + backtick + `[^`]*@req:\$\{` матчит РЕАЛЬНЫЙ биндинг `` it(`…@req:${…}`) `` (opener→backtick), но НЕ fixture-строку `` `it("@req:${…}")` `` (backtick-первый → `it(` за ним `"`). Ключ: где стоит открывающий backtick относительно `it(`. `ctx.grep` матчит **по строке** — для single-line it-титулов это ок; `[^`]*` не пересекает newline.
