# exocortex CI `lint` job ≠ just eslint — 3 guard scripts gate it; eslint step is `continue-on-error`

## Принцип

В `kitelev/exocortex` required-check **`lint`** (ci.yml `lint:` job) — это НЕ только eslint. Его первый шаг `npm run lint` помечен **`continue-on-error: true`** → eslint warnings/errors **НЕ валят job**. Реальные блокирующие гейты `lint`-job'а — **три guard-скрипта** после eslint:

1. `node scripts/validate-shard-assignments.mjs` — каждый `*.spec.ts` должен быть ровно в одном e2e-shard.
2. **`bash scripts/check-test-antipatterns.sh`** — **ratchet**, банит НОВЫЕ low-value test-asserts сверх baseline:
   - `expect(typeof x).toBe("function")` (method-exists — verifies nothing TS doesn't; rename = compile error) — baseline счётчик (был 55).
   - vacuous `toBeGreaterThanOrEqual(0)` length-asserts.
   - non-canon-service-dir, over-mock.
3. `node scripts/check-coverage-monotonic.mjs` — coverageThreshold.global может только расти.

## Следствие (что ломается неожиданно)

- Добавил тест с `expect(typeof fn).toBe("function")` → husky pre-commit (lint-staged eslint --fix) **проходит** (это не eslint-правило по умолчанию), локальный `npm run lint` **exit 0** (warnings + continue-on-error) → **но CI `lint`-job КРАСНЕЕТ** на `check-test-antipatterns.sh` («method-exists asserts increased: N > baseline N-1»).
- Диагностика «lint упал» легко мис-атрибутируется на eslint (`--max-warnings=0` гипотеза). **Неверно** — eslint-шаг continue-on-error. Смотри, какой из 3 guard-скриптов упал: `gh api repos/kitelev/exocortex/actions/runs/<id>/jobs --jq '.jobs[]|select(.conclusion=="failure")'` + читай step-логи, ИЛИ прогони все 3 скрипта локально.

## Floor-практика

- **Не писать `expect(typeof x).toBe("function")` / `.toBe('function')` в новых тестах** — вместо method-exists ассертить ПОВЕДЕНИЕ (вызвать функцию, проверить эффект). Это и есть фикс: `props.onEditRelations()` + `expect(executeCommandById).toHaveBeenCalledWith(...)` вместо `expect(typeof props.onEditRelations).toBe("function")`.
- Перед PR с НОВЫМИ тестами в этом репо — прогнать локально **все 3 guard-скрипта** (не только `npm run lint`):
  ```bash
  node scripts/validate-shard-assignments.mjs
  bash scripts/check-test-antipatterns.sh   # ← ratchet; чаще всего ловит
  node scripts/check-coverage-monotonic.mjs
  ```
- `check-test-antipatterns.sh` печатает текущий vs baseline (`method-exists=55/55`, `vacuous-length=21/21`, …) — exit 0 = ок.

## ⛔ Guard-скриптов в `lint`-job БОЛЬШЕ, чем перечислено выше — их пять, и два из них РАТЧЕТЫ ТИПОВ

Тело правила называет три guard-скрипта. Замер 2026-08-20 (CI-лог упавшего job'а) показывает ещё два —
**ратчеты типов**, каждый со своей базой:

| скрипт | предмет | база |
|---|---|---|
| `check-cli-types.mjs` | `packages/cli/**/src` | `scripts/cli-type-errors.baseline.json` |
| **`check-test-types.mjs`** | **весь тест-корпус (989 файлов)** | своя, ~433 пары |

⛔ **`rc=2` у `check-cli-types` — «проверка НЕ ОТРАБОТАЛА», и локально это состояние ПО УМОЛЧАНИЮ.** Ратчет компилирует `packages/cli/src`, который импортирует workspace-соседей по имени пакета; если те не **собраны**, он видит `65 unresolved bare workspace import(s)` и честно выходит `rc=2` со словами «says nothing about the cli package's own type health». В CI сборка идёт шагом раньше, поэтому там его не видно; в свежем worktree — видно всегда.

- ✅ **Floor:** перед прогоном ратчета — `npm run build -w @kitelev/exocortex-core && npm run build -w @kitelev/exocortex-services` (~3.5 с; ровно это делает CI-шаг).
- ⚠ **Симптом-tell:** `rc=2` **сразу после создания worktree** или после `git merge origin/main`, затронувшего core/services. Читать как «сборка устарела», а не «в cli появились ошибки типов».
- ⛤ Три исхода различать по коду: `0` — новых пар нет · `1` — есть новые (чинить код, ⛔ не базу) · `2` — прогон невалиден, вердикта нет вовсе.

⛔ **Прогнав один, ты НЕ проверил второй** — и второй покрывает ровно то, что чаще всего добавляет
правка: **новый тест**. Симптом: `check-cli-types` печатает `✅ no new type errors`, и следом
`❌ NEW type error(s) in test files`.

- ✅ **Floor: перед push перечислить скрипты ИЗ job'а, а не по памяти** —
  `grep -nE 'node scripts/|bash scripts/' .github/workflows/ci.yml | sed -n '/lint:/,/^  [a-z]/p'`
  либо просто прогнать все, что найдены в `scripts/check-*`.
- ⛤ **Оба ратчета fail-loud В ОБЕ стороны** и оба говорят «Fix the error — do NOT add it to the
  baseline» на НОВОЙ паре. Это верный вердикт: база замораживает **существующий** долг, а не служит
  свалкой.

### ⛔ И главный способ его нарушить — СКОПИРОВАТЬ ФОРМУ У СОСЕДА, чей долг ЗАМОРОЖЕН

Новый тест естественно пишется по образцу соседнего в той же папке. Если сосед старше базы, его
типовые ошибки **grandfathered**, он зелёный — и его форма выглядит одобренной. Скопировав её, ты
воспроизводишь замороженный долг **в файле, у которого долга нет**, и ратчет отказывает.

- ⚠ **Симптом-tell, ловится ДО прогона:** ты скопировал setup-блок целиком, и в нём есть конструкции,
  которых ты сам бы не написал (`jest.SpyInstance`, `mockImplementation()` без аргумента, нетипизированные
  колбэки). Возраст соседа — не одобрение.
- ✅ **Floor: прогнать ратчет на СВОЁМ файле сразу после написания**, до реализации фикса. Три строки
  разницы дешевле разбора красного CI.
- ⛤ **Чинить деривацией, а не переписыванием чужих внутренностей:** `jest.spyOn` перегружен, поэтому
  `ReturnType<typeof jest.spyOn<T, K>>` тоже не резолвится (TS2344/TS2635). Работает вывод **из
  вызова**: `const mk = () => jest.spyOn(...); let s: ReturnType<typeof mk>` — он переживает смену
  версии jest, в отличие от имени внутреннего типа.

**Empirical 2026-08-20** (PR #4110): локально прогнан только `check-cli-types` (rc=0), CI упал на
`check-test-types` с 4 парами — TS2694 · TS2554 · TS2345 · TS7006. Три из четырёх пришли из
setup-блока соседнего `ErrorHandler.test.ts`, который использует те же формы и зелен только потому,
что заморожен.

## ⛔ СОСЕДНИЙ required-check `typecheck` — тоже НЕ то, что ты думаешь: он покрывает `packages/<не-cli>/src` и БОЛЬШЕ НИЧЕГО

Тело правила говорит: `lint` ≠ eslint. Тот же класс — у **`typecheck`**, и он дороже, потому что «typecheck rc=0» уходит в тело PR и в отчёт как **гарантия**. Замер трёх конфигов (2026-08-18, `origin/main`):

| tsconfig | `include` | `exclude` |
|---|---|---|
| `packages/core/tsconfig.json` | `src/**/*` | `node_modules`, `dist`, **`tests`** |
| `packages/cli/tsconfig.json` | `src/**/*` | `node_modules`, `dist` |
| **корневой** `tsconfig.json` | `packages/**/*.ts(x)` | **`packages/**/tests/**/*`**, **`packages/cli/**/*`**, … |

⇒ **НИ ОДИН** конфиг не типизирует `tests/**`, и корневой вдобавок выбрасывает **весь** `packages/cli`.

- ⛔ **Отсюда прямая ложная гарантия в отчёте: «typecheck core rc=0» на PR, чей главный артефакт — ТЕСТ-файл, не покрывает этот файл ВООБЩЕ.** Единственная типизация тестов — **ts-jest в момент прогона**, поэтому ошибка типа в тесте всплывает не как красный `typecheck`, а как `● Test suite failed to run` + `Tests: 0` — форма, которую легко прочесть как «ничего не упало» (`integration-test-revert-verify` §A3).
- ⛤ **Половина `packages/cli` УЖЕ закрыта — ratchet'ом `scripts/check-cli-types.mjs`** (PR #4074): baseline = множество пар `(file, code)`, fail-loud в обе стороны, `rc=2` = «проверка не смогла отработать». Его собственный докстринг фиксирует цену дыры: `packages/cli/src` не типизировался **нигде**, накопив 24 ошибки, и PR #4070 отгрузил чтение `BlankNode.value` (TS2339) **через два раунда ревью** — компилятор флагировал всё это время, но его никто не запускал.
- ⛔ **Половина `tests/**` НЕ закрыта ничем** — ratchet выше её не покрывает. Это тот же класс, что три HIGH арки 8 («починил экземпляр, а не класс»): найдя дыру покрытия `tsc`, я спросил «какой ПАКЕТ не покрыт?» вместо «какие ОБЛАСТИ не покрыты?».
- ✅ **Floor до отгрузки:** отчитываясь о гейтах, писать **что именно** покрыл прогон, а не только его rc — `typecheck core rc=0 (⚠ тест-файлы им НЕ покрыты: tsconfig исключает tests/**)`. Голое «rc=0» читается как «весь диф проверен» и потому врёт.
- ⚠ **Симптом-tell:** ты пишешь «typecheck зелёный» про PR, где `git diff --name-only` состоит преимущественно из `tests/`. Спроси, какой конфиг эти пути **включает** — ответ проверяется одной командой (`include`/`exclude` каждого tsconfig).

## ⛔ `lint` ЗЕЛЁН НА MAIN, красен у тебя — потому что eslint-шаг ТАМ НЕ ЗАПУСКАЛСЯ: долг копится за paths-фильтром и достаётся первому, кто тронул директорию

Секции выше — про то, что `lint` ≠ eslint. Отдельный, более тихий случай: eslint **есть** в job'е и **не исполняется**, потому что `detect-changes`/`paths` не пропустили шаг — merge-коммиты трогали `.github/`, `docs/`, манифесты, но не исходники пакета.

⇒ job рапортует `success`, а eslint по директории не проходил **месяцами**. Долг, внесённый давним PR, лежит невидимым — и падает на **первом же** PR, который тронет эту директорию по любому поводу.

- ⚠ **Симптом читается как СВОЯ регрессия, и это худшая его часть:** «на main зелено, у меня красно» ⇒ первая гипотеза «я сломал». Файл при этом ты не открывал.
- ✅ **Дискриминатор — три вопроса, все дешёвые:**
  1. `git show origin/main:<файл>` — нарушение **уже там**? (да ⇒ не ты внёс);
  2. `git log -1 --format='%ad %h %an' origin/main -- <файл>` — когда и кем менялся;
  3. у последних main-прогонов посмотреть **не `conclusion` job'а**, а исполнялся ли шаг: `gh api .../runs/<id>/jobs --jq '.jobs[]|select(.name=="lint")|.conclusion'` даст `success`, а внутри шаг был **skipped**.
- ⛔ **«Починить как требует правило» — НЕ автоматический ответ.** Читай, что стоит **над** строкой: у долга бывает развёрнутое обоснование автора со ссылкой на требование и тест. Тогда исполнение правила = регрессия, а верный ход — **точечный `eslint-disable-next-line` с причиной**, не правка кода и не исключение на весь файл.
- ⚠ **`eslint-disable-next-line` относится к СЛЕДУЮЩЕЙ строке буквально.** Блок комментариев между директивой и кодом делает её мёртвой; eslint честно скажет `Unused eslint-disable directive` — читать это как «директива не на своём месте», а не «disable не нужен». ⇒ порядок: обоснование → директива → код.
- ⛤ **Выносить в ОТДЕЛЬНЫЙ PR.** Долг блокирует любой PR в эту директорию, то есть он не твой концерн, но общий блокер: смешав его со своей работой, ты и ревью усложняешь, и разблокировку задерживаешь.

## Когда правило срабатывает

- PR в `kitelev/exocortex`, добавляющий/меняющий тесты.
- CI `lint`-job красный, а локальный `npm run lint` / husky pre-commit зелёные.
- Соблазн объяснить lint-fail через eslint `--max-warnings` (тот шаг continue-on-error — не он).
