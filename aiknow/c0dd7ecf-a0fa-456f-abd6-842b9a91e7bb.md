# GitHub-репозиторий как цель мутации: три состояния, невидимые в обычном замере

## Принцип

Замер «пригоден ли репозиторий» рефлекторно собирается из **видимых** полей: `createdAt`,
`visibility`, `defaultBranch`, `pushedAt`, дерево `HEAD`, число коммитов. Все три отказа ниже
**не видны ни в одном из них** — и каждый инвертирует не деталь, а **исполнимость действия**.

⛔ Общее у всех трёх: замер выглядит **полным**, и потому его не перепроверяют.

| # | что невидимо | чем оборачивается | чем мерить |
|---|---|---|---|
| 1 | `archived` | репо **read-only**: не примет ни файл, ни смену видимости, ни CI | `gh api repos/<o>/<r> --jq .archived` |
| 2 | история (удалённые файлы) | публикация раскрывает **весь** объектный граф, а не дерево | обход коммитов с перечислением путей |
| 3 | scope токена | запись в `.github/workflows/*` отдаёт **404**, а не 403 | `gh auth status` |

- ✅ **Обход для состояния 3 — `git push` по SSH** — он OAuth-scope'ом **не ограничен** (клон → замена файла → `git -C <d> commit <pathspec>` → `push origin HEAD:main`). ⛔ `gh auth refresh -s workflow` интерактивен и в автономной сессии непригоден. (Строка скопирована из §3 — floor остаётся во флоре при выносе тела; партия 13.)

## Дискриминатор (один вопрос)

> **Мой замер описывает репозиторий как ЦЕЛЬ ЧТЕНИЯ — или как ЦЕЛЬ ЗАПИСИ?**

- **Цель чтения** — `visibility`, `createdAt`, `defaultBranch`, `pushedAt`, дерево `HEAD`, число
  коммитов. Все видимы, все правдоподобны, и ни одно из трёх состояний выше в них не отражается.
- **Цель записи** — те же поля **плюс** три невидимых: `archived` (можно ли писать вообще) ·
  **вся история**, а не `HEAD` (что раскроется при публикации) · **scope токена** (чем именно пишу).

⛔ Полнота набора видимых полей дискриминатором **не является**: замер из шести полей выглядит
исчерпывающим и при этом описывает репо, в которое нельзя писать. Вопрос не «сколько полей я снял»,
а «отвечают ли снятые поля на то действие, которое я собираюсь совершить».

⚠ Второй вопрос при **`404`**: одинаков ли отказ на различающихся входах (разные репо, разные sha)?
Одинаков ⇒ сломан общий слой (права), и следующая команда — `gh auth status`, а не поиск пути.

## Tell

- ⚠ Ты пишешь в репозиторий, которого не трогал месяцами, и в твоей таблице пригодности **нет
  колонки `archived`**.
- ⚠ Безопасность публикации обоснована **листингом дерева** или **числом коммитов** — оба про `HEAD`,
  а раскрывается объектный граф.
- ⚠ `404` пришёл на путь, который `GET` отдавал минутой раньше, и ты пошёл проверять путь/ветку/регистр.
- ⚠ Ты пишешь «репо пригоден» и не можешь назвать **команду**, которой это установлено.
- ⚠ Замер снят **до** того, как решение назначило репо целью записи: тогда он отвечал на другой
  вопрос и к сегодняшнему действию отношения не имеет.

## ⛔ 1. `archived` — репозиторий read-only, и это не поле «состояния», а запрет на запись

`gh repo view --json visibility,createdAt,defaultBranch` архивность **не покажет**; репо выглядит
живым и отвечает на все чтения. Первая же мутация падает
`HTTP 403: Repository was archived so is read-only`.

- ✅ **Floor: замер пригодности репозитория как ЦЕЛИ ЗАПИСИ обязан включать `archived`.** Без него
  вся проверка описывает репо, в которое нельзя писать.
- ⚠ **Tell:** ты собираешься писать в репозиторий, которого не трогал месяцами, и в твоей таблице
  замера колонки `archived` нет.
- ⛤ **Снятие обратимо одной командой** (`gh repo archive` возвращает), ничего не раскрывает и
  является **предусловием**, а не новым решением, — если целевое решение уже назначило этот репо
  (дескриптор/RFC/issue на него ссылаются). Тогда это `decision-surface-must-derive-from-mechanism`
  §ВТОРОЕ ЗЕРКАЛО: намерение сохраняешь, механизм меняешь, расхождение называешь вслух.
- ⛔ **Но назвать вслух ОБЯЗАТЕЛЬНО, и четырьмя фактами**, иначе следующий читатель увидит
  воскрешение осознанно уволенного репо: **когда и почему** заархивирован · **кто и когда** снял ·
  **чем откатить** · **надпорядок решений** (что ретайр старше действующего решения).

## ⛔ 2. Публикация приватного репозитория проверяется по ВСЕЙ ИСТОРИИ, а не по дереву HEAD

Флип `private → public` раскрывает **весь git-объектный граф**. Файл, существовавший в раннем
коммите и удалённый позже, в листинге `HEAD` **невидим**, но после флипа доступен любому через
`git log` / `git show` / `git cat-file`.

⇒ проверка «раскрывать нечего», сделанная по дереву, **вакуумна ровно в том случае, ради которого
писалась** — когда чувствительный файл был удалён.

- ⚠ **Tell:** ты обосновываешь безопасность публикации **листингом дерева** и **числом коммитов**.
  Оба описывают HEAD; раскрытие описывает историю.
- ✅ **Инструмент** (секунды на репо с единицами коммитов):
  ```bash
  gh api "repos/<o>/<r>/commits?per_page=100" --jq '.[].sha' |
    while read -r S; do gh api "repos/<o>/<r>/commits/$S" --jq '.files[].filename'; done | sort -u
  ```
  Каждый путь классифицировать: инфраструктура / уже-публичный / ⛔ прочее. Ноль засчитывать
  только с живой канарейкой (эталонное множество непусто).
- ⛔ Раскрытие **необратимо по факту**: откат видимости не отзывает то, что уже склонировали.

## ⛔ 3. Contents-API PUT в `.github/workflows/*` отдаёт **404** при отсутствии scope `workflow` — отказ ПРАВ маскируется под отсутствие ПУТИ

`gh api -X PUT repos/<o>/<r>/contents/.github/workflows/ci.yml` возвращает `HTTP 404 Not Found`,
хотя `GET` того же пути минутой раньше отдаёт файл, а admin-операции (`gh repo edit`) проходят.

- **Механизм:** у OAuth-токена `gh` может не быть scope **`workflow`**; GitHub отвечает на запись в
  `.github/workflows/*` без него не `403`, а **`404`** — кодом «нет объекта», а не «нет прав».
- ⚠ **Почему уводит:** естественная реакция на 404 — проверять путь, ветку, регистр имени файла,
  существование репо. Всё это исправно, и проверка даёт круг.
- ✅ **Дискриминатор:** **одинаковый отказ на различающихся входах** (разные репо, разные sha,
  разное содержимое → один и тот же 404) ⇒ сломан **общий слой**. Следующий вопрос не «где файл»,
  а «чем я пишу» ⇒ `gh auth status` (одна команда, печатает scopes).
- ✅ **Обход: `git push` по SSH** — он OAuth-scope'ом **не ограничен** (клон → замена файла →
  `git -C <d> commit <pathspec>` → `push origin HEAD:main`). ⛔ `gh auth refresh -s workflow`
  интерактивен и в автономной сессии непригоден.

## Когда правило срабатывает

- Собираешься писать файл, менять видимость или гонять CI в репозитории, который вёл не ты.
- Обосновываешь публикацию приватного репо тем, что «там нечего раскрывать».
- Получил `404` от `gh api` на пути, который заведомо существует.
- Пишешь таблицу «пригодность репозиториев» перед фазой миграции/переноса.
