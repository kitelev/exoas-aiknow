# CI watch: gate on `commits/<sha>/check-runs` ∩ required-set, НЕ на statusCheckRollup "0 pending"

## Принцип

При автоматическом наблюдении за CI PR (фоновый watcher до merge) — источник истины = **`gh api repos/<owner>/<repo>/commits/<HEAD-sha>/check-runs`**, сверенный с **набором required-checks** (`gh api repos/<owner>/<repo>/branches/main/protection/required_status_checks`). НЕ полагаться на `gh pr view --json statusCheckRollup` с эвристикой «0 pending → settled».

**Почему:** GraphQL `statusCheckRollup` возвращает **непоследовательные частичные снимки** — в момент, когда часть required-чеков ещё не создана как check_runs, rollup отдаёт только уже-стартовавшие (напр. 8 SUCCESS) и НИ ОДНОГО из ещё-не-созданных. Эвристика «pending==0 в текущем rollup» → **ложный «all settled»**, хотя e2e-shard'ы ещё в очереди. `mergeStateStatus` при этом = `BLOCKED`/`UNKNOWN` (верный сигнал, что НЕ готово). Плюс старое правило (`anthropic-api-rate-limit-child-death.md:59`) рекомендует `statusCheckRollup` для verify — это и есть ловушка.

## Когда правило срабатывает

- Фоновый watcher статуса CI PR (child/orchestrator), решающий «можно ли merge».
- Любой `until`-цикл, ждущий «CI зелёный» перед `gh pr merge`.
- Особенно после `update-branch` (новый HEAD → чеки пересоздаются → rollup снова частичный на старте).

## Правильный паттерн

```bash
SHA=$(gh pr view <N> --repo <owner/repo> --json headRefOid --jq '.headRefOid')  # НЕ локальный HEAD после update-branch
# settled ТОЛЬКО когда КАЖДЫЙ required-чек присутствует в check-runs И completed/success:
python3 - "$SHA" <<'PY'
import json,subprocess,sys
sha=sys.argv[1]
req=set(json.loads(subprocess.run(["gh","api","repos/<owner>/<repo>/branches/main/protection/required_status_checks","--jq",".contexts"],capture_output=True,text=True).stdout or "[]"))
runs=json.loads(subprocess.run(["gh","api",f"repos/<owner>/<repo>/commits/{sha}/check-runs?per_page=100","--jq","[.check_runs[]|{n:.name,s:.status,c:.conclusion}]"],capture_output=True,text=True).stdout or "[]")
by={x["n"]:x for x in runs}
fail=[n for n in req if by.get(n,{}).get("c") in ("failure","timed_out","cancelled","action_required","startup_failure")]
PASS={"success","skipped","neutral"}
notdone=[n for n in req if n not in by or by[n].get("c") not in PASS]
print("FAIL=",fail); print("NOTDONE=",notdone); print("DONE=%d/%d"%(sum(1 for n in req if by.get(n,{}).get("c") in PASS),len(req)))
PY
# settled ⇔ FAIL пуст И NOTDONE пуст. «NOTDONE пуст» ловит ещё-не-созданные required-чеки (n not in by).
# ⛤ КЛЮЧ НА conclusion, НЕ на status (коррекция §A1b; прежняя форма `s!="completed"` СНЯТА):
#    (1) агрегатор `test-coverage` лагает `status=in_progress` при УЖЕ проставленном `conclusion=success`
#        ⇒ вечно в notdone ⇒ 80 итераций и ложный TIMEOUT;
#    (2) docs-only PR даёт required-чекам `conclusion=skipped` ⇒ счёт по одному `success`
#        НЕ СОЙДЁТСЯ НИКОГДА. `skipped`/`neutral` = SATISFIED.
```

## ⛔ Вотчер, считающий `pending` по ВСЕМ чекам вместо required-подмножества, НЕ СОЙДЁТСЯ НИКОГДА

Рецепт выше явно говорит «required-set ∩ check-runs», и всё равно самая частая форма самодельного вотчера —

```bash
PEND=$(printf '%s' "$J" | jq '[.check_runs[]|select(.conclusion==null)]|length')
[ "$PEND" -eq 0 ] && merge     # ⛔ по ВСЕМ чекам
```

⛤ Она **выглядит строже** (ждём вообще всё) и потому кажется безопасным упрощением. Фактически она вводит зависимость от чеков, которых гейт не касается: замер 2026-08-21 на `kitelev/exocortex` — **14 required против 22 non-required**, и среди вторых есть висящие (`performance-tests`) и вечно-`skipped` (`Generate Security Report`, `smoke`, `deploy to GitHub Pages`). PR с **14/14 зелёными required** ждал в таком вотчере до потолка итераций.

- ⚠ **Симптом-tell, ловится по СОБСТВЕННОМУ логу:** строки вида `req_fail=0 … pend>0` идут десятками, а `gh pr view --json mergeable_state` уже показывает `unstable`. `UNSTABLE` = **mergeable** (non-required краснота/skip), и если вотчер его не принимает — он ждёт не того.
- ✅ **Floor: считать `notdone` ПО required-списку, а не по выдаче**, иначе ещё-не-созданный required-чек тоже проскочит:
  ```bash
  REQ=$(gh api "repos/$REPO/branches/main/protection/required_status_checks" --jq '.contexts|@json')
  jq --argjson req "$REQ" '
    [.check_runs[] | select(.name as $n | $req | index($n))] as $r
    | { fail:    [$r[] | select(.conclusion|IN("failure","timed_out","cancelled"))] | length,
        notdone: [ $req[] | . as $n | ($r|map(select(.name==$n))|.[0])
                   | select(. == null or (.conclusion|IN("success","skipped","neutral")|not)) ] | length }'
  ```
  Мержить при `fail=0 ∧ notdone=0 ∧ mergeable_state ∈ {clean, unstable, has_hooks}`.
- ⛤ **`skipped`/`neutral` у required — это PASS**, а не «не готов»: docs-only PR штатно даёт `skipped` там, где `detect-changes` отсёк code-джобы. Счёт по одному `success` не сойдётся никогда (это же зафиксировано в §A1b).
- ⚠ **Промах рецидивный при знании правила.** Автор этого вотчера имел строку «gate on check-runs ∩ required-set» в контексте и всё равно написал счёт по всем — потому что `pend==0` короче и читается как то же самое. Дискриминатор при написании: **назови число required вслух**. Не можешь — значит ты его не запрашивал, и предикат считает не то множество.


## ⛔ ПУСТОЙ required-set делает предикат settle ТОЖДЕСТВЕННО-ИСТИННЫМ — резолвить его fail-loud, а не «как получится»

Рецепт выше берёт список required **до** цикла — и это верно (он не меняется по ходу). Незакрытым
остаётся вопрос, что делать, когда он пришёл **пустым**: транзиентный сбой `gh`, срезанный
токен, изменившийся ключ ответа. Обёртка вида «вернуть `stdout` при rc=0, иначе `None`» отдаёт
`None` → `json.loads("[]")` → `req = []`, и дальше **всё** ломается разом:

```python
notdone = [n for n in req if by.get(n) not in PASS]   # req == [] ⇒ notdone == [] ВСЕГДА
if not notdone and ms in ("CLEAN", "UNSTABLE"): print("SETTLED-GREEN")
```

⇒ вотчер объявит зелёным **любой** PR, как только `mergeStateStatus` станет проходным, ни разу
не посмотрев ни на один чек. Это не «менее строгий гейт» — это его отсутствие.

- ⚠ **Симптом-tell, ловится с ПЕРВОЙ строки лога:** счётчик читается `0/0`. Ноль в **знаменателе**
  — не «чеки ещё не созданы» (тогда было бы `0/14`), а «я не знаю, чего жду».
- ⛔ **Отказ живёт ровно один такт и потом невидим:** список резолвится один раз при старте, так
  что транзиент на первой секунде отравляет **весь** прогон, а `gh api` при ручной проверке минуту
  спустя отвечает нормально — и подтверждает, что «всё в порядке».
- ✅ **Floor: резолвить с ретраем и падать отдельным кодом, а не продолжать.**
  ```python
  for _ in range(5):
      raw = sh([...,"--jq",".contexts"])
      req = json.loads(raw) if raw else []
      if req: break
      time.sleep(5)
  if not req:
      print("BROKEN: required-set пуст — вердикт был бы тождественно-зелёным"); sys.exit(2)
  print(f"required: {len(req)}")     # ⛤ печатать ЗНАМЕНАТЕЛЬ: он и есть предмет доверия
  ```
- ⛤ **Тот же класс шире вотчеров:** любой предикат вида «всё из множества M удовлетворяет P»
  тождественно истинен при пустом M. Спрашивать надо не «пусто ли то, что осталось», а
  **«знаю ли я, из чего выбирал»**.

**Empirical 2026-08-21** (PR #4182): вотчер 11 опросов подряд печатал `req 0/0 ms=BLOCKED`, при
том что `gh api …/required_status_checks --jq '.contexts|length'` в тот же момент отдавал **14**.
До ложного «SETTLED-GREEN» не дошло только потому, что `mergeStateStatus` держался `BLOCKED`
(в очереди действительно висел красный `archgate`) — то есть от отгрузки непроверенного PR спасло
совпадение, а не гвард.

## Запреты

- ⛔ Считать «settled» по `statusCheckRollup`-снимку с `pending==0` без сверки с полным required-set — частичный снимок даёт ложный positive.
- ⛔ После `update-branch` ключевать watcher по локальному `git rev-parse HEAD` — GitHub создаёт merge-commit, HEAD PR'а = `headRefOid` (другой SHA). Тянуть свежий `headRefOid`.
- ⛤ Не доверять одному снимку rollup — он флапает между вызовами (видел `DONE=6/13` при `NOTDONE` пустом — внутренне противоречивый снимок).
- ⛤ **`headRefOid` — поле `gh pr view` (GraphQL), у REST его НЕТ.** Перенеся форму из строки выше в `gh api repos/<o>/<r>/pulls/<N> --jq .headRefOid`, получишь **`null`** — без ошибки; watcher затем спросит `commits/None/check-runs` → `HTTP 422 No commit found for SHA: None` и будет бесконечно печатать `0/N fail=0`, что читается как «CI ещё не стартовал». В REST поле называется **`.head.sha`**. Симптом-tell: `sha: None` в первой же строке лога watcher'а + 422 при нулевом прогрессе (в отличие от честного «чеки ещё не созданы», где 422 нет). _(Empirical 2026-08-02, PR #4020: watcher крутился вхолостую, пойман чтением его собственного лога.)_

## ⛔ `mergeStateStatus: UNKNOWN` — НЕ вердикт, а «GitHub ещё вычисляет»: вотчер, трактующий его терминально, выходит рано

Гейт слияния читает `mergeStateStatus`, и известные значения делятся на «можно» (`CLEAN`, `UNSTABLE`+`MERGEABLE`) и «нельзя» (`BLOCKED`, `BEHIND`, `DIRTY`). ⛔ Но есть **третий** класс: `UNKNOWN` (и пустая строка) означает, что GitHub **ещё не посчитал** mergeability — это состояние **переходное**, оно разрешается за секунды-десятки секунд.

- ⚠ **Отказ тихий и правдоподобный:** вотчер с `case` вида `CLEAN|UNSTABLE) merge;; BEHIND) …;; *) BLOCKED` ловит `UNKNOWN` последней веткой и рапортует «заблокирован» — при полностью зелёном CI. Дальше идёт лишний цикл диагностики того, чего нет.
- ✅ **Floor: `UNKNOWN` и пустое значение — `continue`, а не вердикт.** Отдельной веткой ПЕРЕД catch-all:
  ```bash
  case "$MS" in
    CLEAN|UNSTABLE|HAS_HOOKS) merge;;
    BEHIND)      exit 4;;   # нужен update-branch
    UNKNOWN|"")  sleep 20; continue;;   # ⛤ ещё вычисляется
    *)           exit 5;;   # реально заблокирован
  esac
  ```
- ⛤ **`UNKNOWN` возникает штатно и часто** — сразу после `update-branch`, после push, после мержа соседнего PR: любое событие сбрасывает вычисленную mergeability. То есть вотчер, ходящий по серии PR, встретит его почти гарантированно.
- ⚠ **Симптом-tell:** вердикт «BLOCKED» при `failure=0, pending=0` и свежем `update-branch`. Перепроверь `mergeStateStatus` вручную через 20-30 секунд — если стал `BEHIND`/`CLEAN`, вотчер вышел рано.

⛔ **`BLOCKED` неоднозначен ТОЧНО ТАК ЖЕ — и это ловит уже не вотчер, а ТВОЮ ad-hoc проверку.** `BLOCKED` означает «правила ветки не пускают», а «required-чек ещё идёт» — их частный случай. ⇒ в ручном цикле «посмотрю статус и смержу» `BLOCKED` читается как отказ, хотя через две минуты станет `CLEAN`.
- ⛤ **Дискриминатор — `pending`, а не сам `mergeStateStatus`:** `BLOCKED` + `pending > 0` ⇒ ждать; `BLOCKED` + `pending = 0` ⇒ реально заблокирован (нужен review / провалился чек / правило).
- ⛤ **В вотчере из §Floor этой ловушки НЕТ по построению**: `case "$MS"` стоит **внутри** `if [ "$NOTDONE" -eq 0 ]`, то есть до вердикта доходим только с нулём pending. Ошибку делает **ручной** цикл, где такого охватывающего условия нет. ⇒ копируя логику вотчера в ad-hoc проверку, копируй и гейт `pending=0`, а не только `case`.
- ⚠ **Симптом-tell:** ты только что отправил `update-branch`, и следующий же опрос дал `BLOCKED`. Это не отказ — это перезапущенный на новом SHA CI.

⛔ **ТРЕТИЙ корень «вечного BEHIND» — 403 `workflow` scope, и он МОЛЧАЛИВ, если глушить вывод.** `update-branch` на PR, чей дифф трогает `.github/workflows/*`, отвергается, когда токен — OAuth App без `workflow`-scope:
```
403 refusing to allow an OAuth App to create or update workflow `.github/workflows/ci.yml`
    without `workflow` scope
```
- ⚠ **Симптом — цикл:** отправляешь `update-branch`, ждёшь, снова `BEHIND`, снова отправляешь. У меня так ушло **шесть** попыток подряд, потому что вызов стоял под `>/dev/null 2>&1` (⛤ Г1×Г8: глушение stderr превращает громкий отказ в молчаливый no-op).
- ✅ **Floor: НЕ глушить `update-branch`** — читать тело ответа. Успех печатает `{"message":"Updating pull request branch."}`, отказ — текст 403; различаются мгновенно.
- ⚠ **Дешёвый предиктор ДО первой попытки:** PR трогает `.github/workflows/**`? Тогда `update-branch` из-под этого токена не пройдёт **никогда**, сколько ни повторяй.
- ✅ **Обход — обычный `git push`, и он работает ДАЖЕ когда правка ТРОГАЕТ workflow-файлы.** Ограничение висит на **API** (`PUT /pulls/:n/update-branch` от OAuth App), а не на git-транспорте: `git merge origin/main` в ветке + `git push origin HEAD:<ветка>` проходит по SSH-ключу. Для Dependabot-PR это единственный путь, когда он сам отказался («PR has been edited by someone other than Dependabot» — так бывает после ЛЮБОГО твоего `update-branch`).
- ⛔ **ПРЕЖНЕЕ УТВЕРЖДЕНИЕ СНЯТО (опровергнуто исполнением 2026-08-20):** здесь стояло «со `strict:true` это ТУПИК: PR, трогающий `.github/workflows/**`, из-под токена без `workflow`-scope невозможно ни обновить, ни смержить — **ни API, ни локальным push** (push в его ветку упрётся в то же ограничение)». Вторая половина неверна. Замер: PR #4151 (`upload-artifact` 4→7, дифф из 5 workflow-файлов) — `update-branch` давал 403 двое суток, а `git push origin HEAD:dependabot/...` прошёл fast-forward (`3317af70..2e4f47e5`), после чего PR стал `clean` и смержился. Оговорка строки выше («если ты не менял workflow-файл») тоже снята — ветка их меняла.
- ⛤ **Урок про класс:** «API отказал» ≠ «прав нет». У GitHub **две независимые поверхности** записи (REST/OAuth-scopes и git-транспорт/SSH-ключ), и scope-ограничения REST на вторую не распространяются. Прежде чем писать «структурный тупик», проверь ВТОРУЮ поверхность — это один вызов.
- ⚠ **`strict: true` при этом остаётся верным** и по-прежнему требует up-to-date ветки: он объясняет, ПОЧЕМУ `BEHIND` блокирует merge. Ложен был только вывод «обновить нечем».
- ⚠ **Проверять `strict` ДО того, как решать «красный чек не required, значит смержу»:** non-required краснота действительно не мешает, а `BEHIND` при `strict:true` — мешает, и это разные оси. Один вызов: `gh api repos/<o>/<r>/branches/main/protection/required_status_checks --jq .strict`.

**Empirical 2026-08-20** (PR #4145): вотчер вернул `VERDICT=BLOCKED ms=UNKNOWN` при `success=31, skipped=3, failure=0`; ручная проверка через полминуты — `BEHIND`, то есть требовался обычный `update-branch`. Дефект был в **моём** вотчере, а не в PR.

## ⛔ Частота flake, померенная по `/runs/{id}/jobs`, — САМОСТИРАЮЩАЯСЯ метрика: ретрай перезаписывает исход, и ответ всегда стремится к 0 %

Естественный замер «часто ли падает этот джоб» — обойти последние прогоны и посчитать
`conclusion` у нужного джоба. ⛔ Эндпоинт `/actions/runs/{id}/jobs` отдаёт **последнюю
попытку**, а `gh run rerun --failed` создаёт попытку №2 ⇒ каждый успешный ретрай **стирает
собственную улику**, и корпус, где ты лично видел падения, честно возвращает **0 %**.

⛤ Отказ тише обычного ложного нуля: он **согласуется с желаемым** («flake'а нет, можно не
чинить») и потому не перепроверяется. Плюс он **тем сильнее, чем дисциплинированнее** команда:
каждый ретрай, сделанный по правилам, уменьшает измеряемую частоту, не трогая настоящую.

- ✅ **Floor: считать ПО ПОПЫТКАМ** — `runs/{id}` → `run_attempt`, затем цикл
  `runs/{id}/attempts/{n}/jobs`. Разница не косметическая: замер 2026-08-19 по 14 прогонам
  `ci.yml` дал **2 падения из 16 (12 %)** у `e2e-shard (5)`, тогда как дефолтный путь —
  **0 из 17**.
