# `prettier --write` on a pre-existing-dirty file bundles unrelated reformatting

## Принцип

`prettier --write <file>` reformats the **ENTIRE** file. If the file was already **prettier-dirty on origin/main** (and in this monorepo ~1083 files are — `format:check` is non-gating, so drift accumulates), running `--write` to "clean up my added lines" silently reformats hundreds of lines you never touched. That **bundles unrelated reformatting** into your feature diff — the exact anti-pattern `commit-and-push` / `pre-migration-submodule-stash` warn about, but via a formatter rather than a stray `git add`.

Symptom: a 4-edit logical change shows a **300+-line diff** with ~30 hunks spread across the whole file (line 415 → line 2870), most of them whitespace/line-wrapping with no logical change. On a hot file (e.g. `ProfileApplyManager.ts`) that diff is **merge-conflict-prone** against parallel sessions and **destroys review traceability**.

## Когда правило срабатывает

- You edited a `.ts`/`.tsx` (or any prettier-governed) file and want to ensure your **added** lines are prettier-clean before commit.
- The repo has pre-existing format drift (`format:check` reports many `[warn]` files; not a gating CI check).
- Especially on large, frequently-touched files where a whole-file reformat = big diff + conflict risk.

## Правильный паттерн

1. **Check whether the file was already dirty on origin/main BEFORE deciding:**
   ```bash
   git show "origin/main:<path>" | npx prettier --check --parser typescript >/dev/null 2>&1 \
     && echo "CLEAN — --write only touches your additions, safe" \
     || echo "DIRTY — --write reformats the whole file, DO NOT blanket-write"
   ```
   ⛔ **`--parser` здесь нужен ТОЛЬКО потому, что вход идёт через stdin (имени файла нет) — и он же делает пробу ложной, если угадать парсер неверно.** Прогоняя эту форму на НЕ-`.ts`, не подставляй парсер «по расширению»: prettier выводит его из **имени файла**, а не из расширения-как-типа. Для `package.json` / `package-lock.json` он берёт **`json-stringify`** (сохраняет форму `JSON.stringify`), а не `json`. Форсированный `--parser json` переформатирует их иначе и рапортует **DIRTY на чистом файле** — ложно-положительный, из-за которого откажешься от безопасного `--write` и уйдёшь править руками.
   - ✅ **Floor: мерить БЛАСТ-РАДИУС, а не верить вердикту** — он и есть настоящий вопрос («сколько строк уедет сверх моих»), и он парсер-агностичен:
     ```bash
     mkdir -p /tmp/pp && git show "origin/main:<path>" > /tmp/pp/<basename>   # ⛤ ИМЯ файла сохранить —
     cp /tmp/pp/<basename> /tmp/pp/<basename>.orig                            #    от него prettier и выводит парсер
     npx prettier --write /tmp/pp/<basename> >/dev/null 2>&1
     diff -u /tmp/pp/<basename>.orig /tmp/pp/<basename> | wc -l   # 0 ⇒ CLEAN, --write безопасен
     ```
     Ноль строк = `--write` не тронет ничего сверх твоих правок, независимо от того, что сказал `--check`.
   - ⚠ **Симптом-tell:** `--check` через stdin говорит DIRTY, а `git diff` после `--write` пуст (или lint-staged отработал no-op). Это не «повезло» — это доказательство, что DIRTY был артефактом твоего `--parser`.
   - **Empirical 2026-08-07** (PR #4034, deps-bump): проба `git show origin/main:$f | npx prettier --check --parser json` объявила DIRTY **оба** `package-lock.json` и `packages/cli/package.json` ⇒ вывод «lint-staged забандлит массовый реформат». Замер блast-радиуса на копиях: дельта **0 и 0**. Коммит вышел ровно 39/39 строк, lint-staged-prettier отработал no-op. Cost: одна лишняя проба; предотвращено — ненужный ручной обход `--write` на чистых файлах.
2. **CLEAN file** → `prettier --write <file>` is safe (it only formats your new lines). New files you authored are CLEAN by definition — write them freely.
3. **DIRTY file** → do **NOT** blanket `--write`. Instead:
   - Write your added lines in prettier style by hand (4-space-ish, ≤80-col wrapping matching the file), and **leave the pre-existing drift alone** — it's the repo's debt, not yours, and `format:check` isn't gating.
   - If you ALREADY ran `--write` on a dirty file and bundled the reformatting: **restore origin/main and re-apply only your logical edits** —
     ```bash
     git checkout origin/main -- <file>      # discards BOTH reformatting AND your edits (uncommitted)
     # then re-apply your logical edits via Edit tool (old_strings now match origin/main again)
     ```
     This is a legitimate use of `git checkout origin/main -- <file>` (you intend to discard the working-tree formatting and re-apply logic) — distinct from the `integration-test-revert-verify` "checkout-before-commit loses your edit" footgun, because here you re-apply immediately and verify the diff shrank.
4. **Verify the diff is minimal after:** `git diff --stat <file>` + `git diff <file> | grep -cE '^@@'` — hunk count should match your edit count (≈3-5), not 30+.

## Запреты

- ⛔ `prettier --write` на pre-existing-dirty файле, чтобы "почистить свои строки" — reformats the whole file. Проверь origin/main cleanliness FIRST.
- ⛔ Committing a 300-line "feature" diff that is 80% whitespace reformatting of lines you didn't logically change.
- ⛤ Не полагайся на `format:check` как gate — в этом monorepo он non-gating (1083 dirty files), `lint` (eslint) is the gating format-ish check and it does NOT care about prettier wrapping. lint-staged pre-commit гоняет `eslint --fix` **только на `packages/!(cli)/src/**/*.{ts,tsx}`** — ⛔ **но на `*.{json,md}` он гоняет `prettier --write --ignore-unknown`** (проверено живым `package.json` репо), то есть markdown/json хук переформатирует ВСЁ РАВНО, и для них верен §Addendum 2026-06-20, а не эта строка. Для `.ts` вне этого glob — да, unformatted-but-eslint-clean строка коммитится.

## Addendum 2026-06-20 — lint-staged `prettier --write` на `*.{json,md}` + `git commit <pathspec>` → partial-format коммит + working-tree-residual loop

_(Added by /session-retrospective 2026-06-20 — root: child `al-polish-ship`, docs-PR #3664 `Getting-Started.md` table-cell widening.)_

lint-staged-конфиг репо гоняет `prettier --write --ignore-unknown` на `*.{json,md}` в pre-commit. Если коммитишь markdown через **`git commit <md-file>` (pathspec)**, а правка изменила ширину колонки markdown-таблицы (длинная новая ячейка) — возникает рассинхрон:

- pathspec-commit фиксирует **рабочее-дерево-версию ДО** того, как hook-овский prettier дорегялил остальные строки таблицы → в коммит уходит **частично-выровненная** таблица (твоя строка широкая, соседние — старой ширины).
- lint-staged restore возвращает в working tree **полностью-выровненную** prettier-версию → `git status` показывает `MM` (staged+unstaged) residual.
- Повторный `git commit <md>` **зацикливается** (prettier снова перевыравнивает working tree, pathspec снова фиксирует частичное); `git reset; git add <md>; git commit` (bare) на идемпотентно-выровненном файле даёт «nothing to commit».

**Урон 0** в инциденте: format:check **non-gating** (см. тело правила), а markdown-таблица **рендерится идентично** независимо от исходного padding (`|`-разделители решают, не пробелы). Принял частично-выровненный коммит, working tree вычистился сам.

**Fix (чтобы коммит был чисто-выровнен):** для markdown, который lint-staged всё равно прогонит через `prettier --write` — **сначала сам `prettier --write <md>`** (файл был CLEAN-on-main → форматит ТОЛЬКО твою таблицу, full-align, без bundling), **затем `git add <md> && git commit`** (bare, индекс single-file, verified). Тогда hook-овский prettier идемпотентен (уже выровнено) и в коммит уходит финальная версия. ⛤ Pathspec-commit (`git commit <file>`) и lint-staged-`--write` **плохо сочетаются** — `git add`+bare-commit (с verify `git diff --cached --stat` single-file) надёжнее для hook-форматируемых путей. Cross-tie `lint-staged-worktree-commit-corruption` (другой lint-staged+commit рассинхрон), `commit-and-push` (pathspec vs bare trade-off).

## ⛔ АВТОФИКСЕР СОСЕДНЕГО ИНСТРУМЕНТА (`npx xo --fix`, `npx eslint --fix` без конфига репо) правит по СВОЕЙ конвенции — и ломает сборку НАПОЛОВИНУ

Тело правила — про `prettier --write` на **уже грязном** файле (бандлится чужой
реформат). Соседний, более разрушительный случай: файл **чистый**, а ты зовёшь
автофиксер, который **не является линтером этого проекта**. Тогда он приводит файл к
**своим** правилам, и они противоположны тем, что гоняет `npm run lint`.

- ⛔ **Дифф раздувается на сотни строк чужой косметики.** Замер 2026-08-21: моя правка —
  67 вставок; `npx xo --fix` на тех же двух файлах дал **204 вставки / 103 удаления**,
  переписав JSDoc-звёздочки, импорты и стрелочные функции по всему файлу. В PR про кэш
  это 100 строк, к предмету не относящихся.
- ⛔ **Хуже бандлинга: правка бывает ПОЛОВИННОЙ и ломает сборку.** `xo` применил своё
  правило `no-null` к **типу** (`| null` → `| undefined`) и **не тронул инициализатор**
  (`= null`) ⇒ `TS2322: Type 'null' is not assignable`. Тесты при этом зелены (ts-jest /
  vitest транспилируют без `tsc`), красным становится только `npm run build`.
- ⚠ **Симптом-tell, ловится ОДНОЙ командой до коммита:** `git diff --stat` показывает
  **удаления** там, где правка задумывалась аддитивной. Ноль-или-единицы удалений =
  норма; десятки = ты запустил чужой фиксер.
- ✅ **Floor: фиксер — ТОЛЬКО тот, что зовёт сам проект** (`npm run lint -- --fix`,
  `npm run format`). ⛔ Не `npx <любой-линтер> --fix`: он не читает конфиг репо и
  считает своё умолчание истиной.
- ⛤ **Уже запустил — не «дочинивай», а накладывай заново.** `git checkout -- <файл>` до
  пристинного состояния и повторно внеси **свою** правку: она мала и известна, а
  вычитывать 100 строк чужой косметики дороже и ненадёжнее. Проверка результата — тот же
  `git diff --stat`: удалений должно остаться ровно столько, сколько строк ты переписал.
- ⚠ **Ручную починку остатка мерить БАЗОЙ, а не нулём.** У проекта обычно есть
  пред-существующие ошибки линтера; «стало 5» при базе 5 = чисто. Снимать базу
  `git stash -u` + прогон на пристинном дереве, иначе будешь чинить чужой долг.
