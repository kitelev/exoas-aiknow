# Reference — ExoSync sync topology, timing, pinned-loop

Verified 2026-07-14 by reading `origin/main` source + measuring 3 live vaults (published CLI `@kitelev/exocortex-cli` 16.185.9).

## Sequential, not parallel

`SyncEngine.syncAll(specs)` (`packages/core/src/services/sync/SyncEngine.ts`) iterates AssetSpaces (sync-units/repos) **sequentially** — a plain `for (const spec of specs) { results.push(await this.syncLocked(...)) }`. No `Promise.all`. Three deliberate reasons:

1. **Single-flight mutex** — `this.opInProgress` guard taken ONCE for the whole run (D11); any concurrent `sync()`/`syncAll()` returns `busyResult`. Parallelism is disallowed engine-wide, not just between units.
2. **`orderChildrenFirst`** — CLI sorts specs deeper-path-first (D12, children before parents) before the run; ordering only matters under sequential execution.
3. **Best-effort isolation (D12)** — a per-repo failure becomes that repo's `result.error`, never an exception; the rest keep going.

Inside one repo (`syncLocked`, pull/merge/push) — also sequential `for…of`, no fan-out over files/blobs. One atomic `restCreateCommit` per repo (N writes + M deletes = one commit).

## Timing (read-only `exosync-parity`, no-op)

| Vault | Repos | Wall-clock | CPU idle | ~sec/repo |
|---|---|---|---|---|
| vault-exodev | 15 | 31.1 s | ~88% | 2.07 |
| vault-tbank | 13 | 25.9 s | ~88% | 1.99 |
| vault-my | 10 | 23.5 s | ~84% | 2.35 |

**Non-obvious:** per-repo latency ~2 s is **stable regardless of repo content size** (vault-exodev holds 1581/1498-file AssetSpaces, vault-my smaller — same ~2 s). The cost is a **fixed GitHub REST round-trip per AssetSpace**, so wall-clock scales with the *count* of AssetSpaces, not the file count. ~85% of wall-clock is network idle (CPU ~4 s). Real `exosync sync` with changes is slower by `fetch blobs + push commit` only on repos that actually diverge.

## Should it be parallelized? — Not now

Potential is real (85% idle → 31 s could drop to ~6–8 s at concurrency 4–5), BUT the fixed-latency-per-repo (each repo = a burst of REST calls) is exactly what triggers **GitHub secondary rate-limit / abuse-detection** under parallelism. `transportBackoff.ts` handles 429/403 reactively but concurrency provokes it. Cost also: remove the D11 guard, per-repo the shared `activeLocalIoProgress` state, lose children-first ordering, worse diagnosability of the tricky convergence bugs. Absolute pain is moderate (23–31 s no-op). The canonical answer to "sync is slow" is **Profile → mount fewer AssetSpaces** (fewer N), not parallel N. Revisit only on *measured* pain → bounded concurrency (semaphore 3–4 + token-bucket vs secondary-limit) as a separate `/feature-sdd`.

## Divergence triage + #3835 pinned-loop (operational)

- `quarantine list` empty while `parity` shows `quarantine-pinned` = **transient re-derive pins**, NOT registered conflicts. `exosync quarantine resolve` is a no-op for them. `pending-remote-*` in parity = benign "local behind remote" convergence (sync pulls/applies; local was unchanged).
- **#3835 unresolvable pinned-loop** = a stale watermark base-entry for a path dead EVERYWHERE (absent on remote head AND local disk — a dead tmp/transient from an old move) is diffed as a phantom remote DELETE; sharing the asset's `exo__Asset_uid` with the real change, `matchLocalVsRemote` groups both → `remotes.length===2` → merge raises "ambiguous conflict: local overlaps 2 remote changes" → PINS without registering in `quarantine list` → every sync re-defers the same phantom.
- **FIXED**: `c6a1742f` (v16.184.1, drop phantom cross-path watermark delete) + `45e7b3a1` (v16.184.7, rename-with-conflicting-edit #3886). Both are in published ≥16.185 → the loop no longer forms on current CLI.
- **Operational**: pins you still see in parity are **watermark residue from pre-fix syncs**. The fix lives in `matchLocalVsRemote` (runs during `sync`), and `parity` is read-only → it reports the pins but cannot clear them. The authoritative test = one `exosync sync` on ≥16.185: phantom-class pins drop; genuine content-divergence (both sides exist & differ, e.g. `exocmd/3dfa3379`) becomes a normal registered conflict in `quarantine list`, not a loop.
