# Exocortex cold-archive AssetSpace: dated-namespace offload из mounted-профиля (принцип + рецепт)

## Принцип (user directive 2026-07-16)

Когда личный vault (vault-my) распух настолько, что монтируемая на iPhone масса вредит производительности (crash-loop, медленная индексация), **холодная разгрузка** = вынести завершённое/историческое в **отдельный assetspace `exoas-my-archive`, НЕ включённый ни в один `Profile_includes`** → после `apply-profile` на iPhone он физически не монтируется → отсутствует в `scanVault`/triple-store.

**Датированный принцип (rolling, ежемесячно):** каждый месячный батч холодного архива получает **свою онтологию `$my-archive-YYYY-MM`** внутри `exoas-my-archive`. Перенесённые ассеты **переякориваются** `isDefinedBy → $my-archive-YYYY-MM` (co-location чистая). Warm-архив (кнопка «Archive Ontologically» → `$my-efforts/archived`, `9d1d2e9d`) остаётся в exoas-my как **lifecycle-состояние** — это НЕ то же, что cold offload (разные вещи: warm = «заархивировано онтологически, но ещё смонтировано»; cold = «вынесено с устройства»).

## Что переносить (scope)

- **Архивируемо (ДЕФОЛТ) — warm-archived набор** `my-efforts/archived/` (anchor `9d1d2e9d`): замер **352 из 358 чистых**. ⛔ Age-based «Done+Trashed старше месяца» — **альтернатива, а не дефолт**: тот же замер дал **7 из 92** (85 linked-by-active, вплетены в активный граф) ⇒ батч схлопывается почти в ноль. Прежняя формулировка «архивируемо = Done+Trashed, опционально cutoff» СНЯТА (§A1).
- **⛔ НЕ трогать (живой граф):** non-effort (концепты/персоны/области/заметки/daily-notes — reference-data) + активные статусы (Draft `c42245d0`, Backlog `753a44d5`, Doing `027e78f4`, ToDo `6a0e933a`, Analysis `cde3525c`, ThisWeek `a6c289a0`).
- **⛤ Исключать linked-by-active** (blast-radius): move-кандидат, на который ссылается ассет, ОСТАЮЩИЙСЯ на iPhone, → dangling wikilink на iPhone. Считать входящие `uid` из non-move-set; кандидаты с такими — оставить смонтированными. (Эмпирика: 87 из 2193 кандидатов.)

## Рецепт переноса (DATA, per batch)

1. **Backup** move-set в scratchpad (`cp`).
2. **Move + re-anchor** одним python-скриптом: `mv` файла exoas-my/… → exoas-my-archive/my-archive-YYYY-MM/ (plain mv, cross-assetspace, git-free ExoSync = delete-source + add-target) + переписать `exo__Asset_isDefinedBy` line → `<archive-anchor-uid>`. **Line-based split/join (НЕ regex-replace тела)** — тело verbatim, безопасно от `$`-corruption (`string-replace-dollar-corruption`). Bulk-python обходит хуки → **SHACL floor обязателен**.
3. **SHACL post-validate** → no-regress (та же pre-existing violation-база, 0 новых). Archive-онтология БЕЗ `imports` violations не даёт (class-резолюция идёт через `exo__Instance_class`, не через isDefinedBy-imports).
4. **ExoSync sync** — cross-repo move = **delete(exoas-my) + add(exoas-my-archive) в ОДНОМ раунде** (`migration-pre-verify-use-case`). Verify: `exoas-my deleted N`, parity M2=∅.
5. **Remote verify** (`gh api …/git/trees/main?recursive=1`): moved-файлы в archive, отсутствуют в exoas-my.

## Как это доходит до iPhone

- **Автоматически:** N файлов **удалены** из exoas-my → iPhone на след. ExoSync подтянет удаления → exoas-my на iPhone −N. Archive-assetspace **новый + не в профиле** → на iPhone не материализуется → файлы не возвращаются.
- **Усилить:** iPhone `Cmd+P → Apply profile → $$kitelev-my` — гарантирует, что archive не смонтирован + дополнительно убирает shared-private/public, если смонтированы.

## ⛤ Root cause — ИСТОРИЯ: половина (а) ОТГРУЖЕНА 2026-07-16, открыт только (б)

iPhone Obsidian **crash-loop каждые 1-2 мин** = iOS Jetsam убивает приложение из-за memory/CPU-шторма. Дымящаяся пушка: `ExocortexPlugin.ts` `metadataCache.on("changed") → printNameRuleService.refresh() → scanVault()` — **полный обход ВСЕХ markdown-файлов (`getMarkdownFiles()` + `rules.clear()` + чтение каждого frontmatter) на КАЖДОЕ изменение файла, БЕЗ debounce** (в отличие от SPARQL-пути с 150ms debounce). На 10k+ vault при sync-всплеске (много «changed» подряд) = O(K·N) шторм → Jetsam. Впустую: перечитывает 10 612 frontmatter'ов, чтобы найти ~18 `exo__DisplayNameSpec` (590:1). `PrintNameRuleService` создан 2026-07-05, обострён 2026-07-10…12 (displayName composition #3851/#3877/#3879) — совпадает с onset. ⛤ **Update 2026-07-16 — debounce ОТГРУЖЕН** (`#3914` / `b422f7c6` → **v16.185.13**, `PrintNameRuleService.scheduleRefresh()`), то есть половина (а) больше НЕ «будущий фикс»; активна при плагине ≥ v16.185.13, разгрузка и debounce работают В СВЯЗКЕ. Открыт остаётся только (б) инкрементальный scanVault. Ниже — исходный разбор как ИСТОРИЯ: **разгрузка снижает N (каждый scan дешевле), но НЕ чинит O(N)-per-change баг** — гарантия только код-фикс: (а) debounce `refresh()` на «changed», (б) инкрементальный scanVault (проверять, был/стал ли changed-файл DisplayNameSpec; иначе no-op).
