# UI smoke transitive proof: acceptable fallback при заблокированной manual verification

UI smoke в live Obsidian является **обязательным** gate для API-integration changes (см. `test-fixture-realism.md`). Если physical UI smoke невозможен (Mac в deep sleep, screen lock без access к hardware), допустим **transitive proof** при строгих conditions.

## Когда правило срабатывает

- Code change shipped (PR merged + release published)
- Manual UI smoke required per `test-fixture-realism.md`
- Physical access к Obsidian blocked: Mac sleep cycle, lid closed, vault на remote machine, network outage
- Continuing to retry UI smoke incurs disproportionate cost (>2 wake-up cycles, >10 min wasted)

## Required conditions для accept transitive proof

**ALL must be true** (not OR):

1. **Identical code path** — new fix uses *exactly* the same function/method that's been UI-smoke-verified in a prior release. Not "similar", not "follows the same pattern". The literal call signature and resolution path.
2. **Production-shape unit tests** — fakes mirror real API contract per `test-fixture-realism.md`. NOT stub-returning-any.
3. **Code-reviewer agent APPROVE** — 0 CRITICAL/HIGH findings on the actual change.
4. **Advisor consulted round-2** — if first review caught anything, advisor signed off after fixes.
5. **Class assets / target data exist on disk** — verified by `ls` or `Read`, not assumed.

Если any condition fails → escalate to user, do NOT silently ship.

## Example (2026-05-22, PR #3226 для #3222)

Convert paths `executeConvertToTask` + `executeConvertToProject` got `resolveClassRefToUid()` wired. Same method I (orchestrator) personally UI-smoke-verified in v16.13.4 для `executeCreateInstance` produces ``1b20a8f0-...`` UID-form. Transitive proof acceptable:

- ✅ Identical code path (`resolveClassRefToUid` — same method, same impl)
- ✅ Production-shape tests (5 unit tests mirroring real API)
- ✅ Code-reviewer APPROVE 0 CRIT/HIGH/MED
- ✅ Advisor round-2 approve
- ✅ Class assets exist: `assetspaces/ems/1b20a8f0-...md` + `7db5eeff-...md`

## Anti-pattern: "similar" не достаточно

Если change implements **new** resolver logic (даже если "intent identical"), это **новый** code path. Transitive proof не применим — requires fresh UI smoke. Example: `findUidByLabel` (CommandResolver layer) ↔ `createObsidianClassLabelResolver` (plugin layer) — оба resolve label→UID, но different implementations, different runtime contexts. Each requires its own UI smoke verification.

## Addendum 2026-07-10 — headless "real-file resolution proof" over the SHIPPED data = valid authoritative-resolver substitute when the live pixel-visual is environment-blocked (NEW logic, not transitive)

The anti-pattern above says **new resolver logic requires a FRESH UI smoke** (transitive-from-a-prior-release does NOT apply to genuinely-new code). But there is a stronger-than-transitive substitute for the *authoritative resolver-level* half of a UI smoke that works even for NEW logic, when the live in-app DevTools-eval is blocked by the environment (screen-lock, a full-screen orchestrator Space, no physical access): **run the EXACT released engine code over the EXACT shipped data files, headless.**

**When it applies (all required):**
1. The feature's UI surfaces all funnel through ONE resolver/render function (here: `DisplayNameResolver.resolve` → `PrintNameRuleService.getTemplateForClass`), and that funnel's surface-side code is unchanged (v1-UI-smoke-verified) — your change is *inside* the funnel.
2. You can load the **actual shipped data assets** (the released vault spec files, not a fixture mirror) + the **actual released engine code** into a harness that drives the real pipeline with a faked platform boundary (fake Obsidian `App`/metadataCache whose only job is to hand back the same frontmatter dict the real one would).
3. **Bundle-grep** confirms the code is in the released artifact (`main.js`).

**Why it's stronger than transitive proof (and honest about its gap):** a transitive claim says "identical code path shipped before, verified before". The real-file proof instead *executes the new code path now* over the real shipped data → observes the exact output the authoritative DevTools-eval would return (`getTemplateForClass(taskUID, {ems__Effort_status:"`<doing-uid>`"})` → the 🔄 template). The ONLY delta from the in-app DevTools-eval is the metadataCache SOURCE (fake vs Obsidian) — both are standard YAML→dict parses producing identical input. So this substitutes for the **DevTools resolver-eval** (the authoritative check named in `obsidian-plugin-e2e`/`obsidian-plugin-update-via-brat`). It does **NOT** substitute for the **pixel-visual** (DOM render across the surfaces + re-render-on-change dynamic) — that gap must be stated explicitly and handed to the user as a ~30-sec confirmation, with a temp-vault pre-loaded with the released plugin ready.

**Recipe:** write a throwaway test in the plugin's jest harness that reads the released `.md` spec files from disk (`fs` + a YAML parse) into `createMockApp`, adds synthetic instances, and asserts the real `scanVault → resolve` output. Run, capture the result, delete the throwaway (don't commit). Pair with bundle-grep of a unique symbol in the released `main.js`.
