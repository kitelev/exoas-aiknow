## §A1 — ⛔ Addendum 2026-06-27 — transitive `exo:Class_superClass*` walk BROKEN by dual-IRI gap (subClass-in-SPARQL не работает)

Тот же symbolic↔file-IRI дуализм ломает **transitive property-path по class-hierarchy** в любом runtime-SPARQL (precondition / CQ / ad-hoc), не только literal-сравнения. **Нельзя пройти `$asset exo:Instance_class/exo:Class_superClass* <SomeClass>` в реальном store** — путь обрывается после первого шага.

**Механизм (verified CLI SELECT против реального vault):**
- `<asset-file-iri> exo:Instance_class <symbolic-class-iri>` — объект instance_class = **symbolic** IRI (напр. `ems#TaskPrototype`).
- `<class-FILE-iri> exo:Class_superClass <symbolic-parent-iri>` — субъект superClass = **file IRI** (`obsidian://vault/<uid>.md`), объект — symbolic родитель.
- **Нет трипла, связывающего symbolic class IRI с его file IRI.** Резолвер (`CommandResolver.expandClassHierarchy`/`computeAncestorDepths`) мостит их **в коде** (label→uid→file lookup, `resolveClassFileIRI`), чего SPARQL сделать не может.
- → `$asset exo:Instance_class ?c` даёт symbolic `?c`; `?c exo:Class_superClass*` от symbolic IRI находит **0** триплов (superClass живёт на file IRI) → путь достигает только самого `?c`, НИКОГДА предка. `ASK { FILTER NOT EXISTS { … superClass* … } }` всегда true.

**Запрет:** ⛔ Не писать runtime-SPARQL (precondition `sparqlAsk`/`query`, CQ, ad-hoc), полагающийся на `exo:Class_superClass*`/`+` от symbolic instance_class IRI для определения subClass-membership. На реальном store это **тихо не сработает** (молчаливый false на ASK-вето / пустой результат на SELECT).

**Что работает вместо transitive:**
- **Suffix/naming-convention check** на symbolic IRI: `$asset exo:Instance_class ?c . FILTER(STRENDS(STR(?c), "Prototype"))` — queryable, ловит все конвенционально-именованные классы. Прагматичный homoiconic workaround (prototype not-a-prototype precondition).
- **Enum-list** symbolic IRI родителей (хрупко — легко пропустить класс; prototype-case пропустил `exo#Prototype`+`ems#EffortPrototype`).
- **hostFunction** (TS class-chain walk через резолвер) — семантически верно, но требует кода (sync-host-fn constraint усложняет async store-walk).

**Test-fixture caveat (test-fixture-realism):** synthetic store, кладущий `Class_superClass` на **symbolic** IRI (`<ems#TaskPrototype> superClass <exo#Prototype>`), даёт **false-pass** transitive-форме — он НЕ зеркалит реальный store (где superClass на file IRI). Production-shape fixture обязан: `instance_class` объект = symbolic; `Class_superClass` субъект = **file IRI** класса (+ Asset_label/uid для резолвера). Verify-before-assert: гонять кандидат-precondition против РЕАЛЬНОГО vault (`exocortex-cli query SELECT`) ДО ship, не только синтетический jest.

**Empirical:** 2026-06-27, prototype not-a-prototype precondition (req `5579ffa1`, PR #3740). Designed `$target exo:Instance_class/exo:Class_superClass* exo:Prototype` шипнут INERT (exocmd `dfe3c8d`) — synthetic-спайк (superClass на symbolic) дал false-pass. CLI SELECT против реального vault показал путь достигает только `ems#TaskPrototype`, не `exo#Prototype` → fix-forward на STRENDS-суффикс (`6d70c37`). Cost: 1 inert-ship + fix-forward commit-цепочка (~3 submodule re-pushes) + переписанные тесты на real-shape. Self-caught verify-before-assert'ом ДО закрытия (inert-версия безвредна: NOT EXISTS true = команда показана, как было).

## §A2 — ⛔ Addendum 2026-07-02 — `FILTER(!CONTAINS(?status, "<status-UID>"))` для non-Done проверки ПОЛЛЮЦИРУЕТСЯ symbolic-IRI-формой → ложные red-flags

_(Added by /session-retrospective 2026-07-02 — root: PMBOK batch-closure WBS-completeness check.)_ Тот же symbolic↔file-IRI дуализм ломает **status-фильтрацию через substring-CONTAINS на UID**. `ems__Effort_status` эмитится **в двух формах** для одного и того же статуса: **file IRI** `obsidian://vault/.../7b9b3116-...md` (UID-form) И **symbolic IRI** `https://exocortex.my/ontology/ems#EffortStatusDone` (без UID). Фильтр «найти non-Done узлы» через `FILTER(!CONTAINS(STR(?status), "7b9b3116"))` **пропускает** все Done-задачи, чей статус хранится в symbolic-форме (в ней нет UID `7b9b3116`) → они ложно попадают в «non-Done» → раздутые red-flags.

- ⛔ Не фильтровать `ems__Effort_status` (и любой enum-статус) через `CONTAINS(?status, "<enum-UID>")` — поймает только file-IRI-форму, symbolic-форма проскользнёт.
- ✅ Матчить **обе** формы: `FILTER(!CONTAINS(STR(?status), "7b9b3116") && !CONTAINS(STR(?status), "EffortStatusDone"))` (UID **И** symbolic-localname).
- ✅ Либо резолвить status→label и сравнивать по label; либо ключеваться на symbolic-форме (`ENDS/CONTAINS "#EffortStatusDone"`), которая единообразнее для enum-значений.
- ⚠ Особо коварно как **дефолтный WBS-completeness gate**: сырой non-Done count выглядит как «незакрытые leaf-узлы» (red-flag под AllAccepted), хотя половина — Done-в-symbolic-форме. **Обязательна** пере-проверка status-breakdown ДО решения об outcome.

**Empirical:** 2026-07-02, PMBOK batch-closure (12 root проектов в vault-exodev). WBS-completeness query `FILTER(!CONTAINS(?status, "7b9b3116"))` вернул «non-Done» descendants для 7 проектов (напр. 4ef4acc6=12, e5939fb2=32, 9b4f1f59=40) — все на самом деле **Done** в symbolic-форме (`ems#EffortStatusDone`). Реальные open-Backlog (после status-breakdown reconcile) — только 3 проекта (87c94939/e743da83/a68dd4ad). Без reconcile 4 AllAccepted-проекта были бы ложно понижены до PartialAcceptance. Self-caught вторым запросом (status-breakdown), 0 урона (не доверился сырому count как факту — verify-before-assert). Cost: 1 диагностический breakdown-запрос.

## §A3 — ⛔ Addendum 2026-07-04 — production-shape precondition `evaluate()` test с `$today`/date-token: store literal ОБЯЗАН быть typed `xsd:date` + `PREFIX xsd:` объявлен (иначе ASK молча false → vacuous)

_(Added by /session-retrospective 2026-07-04 — root: #3811 PreconditionEvaluator `$today`→LOCAL, ~6 probe-прогонов чтобы построить не-vacuous production-shape `evaluate()` тест.)_ Date-токены `PreconditionEvaluator.substituteVariables` (`$today`/`$yesterday`/`$thisWeekStart`/…) эмитятся как **typed literal** `"YYYY-MM-DD"^^xsd:date`. Чтобы написать НЕ-vacuous production-shape тест через реальный `evaluate()`-путь (ASK, сравнивающий asset-дату против `$today`), эмпирически (verified против движка):

1. **`PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>` ОБЯЗАН быть в `sparqlAsk`.** `xsd:` НЕ pre-bound в ExoQL-парсере. Без него `"...^^xsd:date"` (из подстановки `$today`) → **parse error → `evaluate` возвращает false (fail-closed)** → тест проходит ОБОИМИ способами (vacuous, [[integration-test-revert-verify]]).
2. **Store-литерал даты ОБЯЗАН быть typed** `new Literal("2026-07-03", new IRI("http://www.w3.org/2001/XMLSchema#date"))`. **Plain-vs-typed НЕ матчатся** в движке: `<a> p "2026-07-03"` (plain store) против `$today` → `"2026-07-03"^^xsd:date` (typed query) = разные термы → no match → false. Term-match работает ТОЛЬКО typed↔typed (одинаковый lexical + datatype).
3. **`STR(?d) = STR($today)` НЕ работает** для `xsd:date`: `STR("2026-07-03"^^xsd:date)` НЕ возвращает plain lexical `"2026-07-03"` в этом движке (канонизация). Использовать **`FILTER(?d = $today)`** (typed `=` работает — component/lexical comparison) ИЛИ triple-pattern `{ <a> p $today }` с typed store-литералом.
4. **FakeOffsetDate-совместимость:** typed `xsd:date` `=` НЕ ломается под глобальным `Date`-override `installFakeOffsetDate` (движок сравнивает компоненты, не через `new Date()`-реканонизацию) — так что boundary-revert-verify (fake-date) + real-`evaluate()` **совместимы** при typed store + `PREFIX xsd:`. (Раньше казалось, что fake ломает движок — это был симптом plain-store и/или отсутствия `PREFIX xsd:`, НЕ fake-интерференции.)

**Floor:** production-shape precondition-`evaluate()` тест с date-токеном → (a) `PREFIX xsd:` в ASK, (b) typed `xsd:date` store-литерал, (c) `FILTER(?d = $token)` или typed triple-match, (d) negative-control (asset=другой-день → false) для доказательства non-vacuity. Сначала прогони probe (isolate: base triple → typed-match → filter) — не доверяй первому `false` как «фикс не работает»; чаще это отсутствующий `PREFIX xsd:` или plain store-литерал.

## §A4 — ⛔ Addendum 2026-07-05 — перемещение filename-IRI target'а МОЛЧА ломает хардкод-IRI в precondition-SPARQL (comparison перестаёт матчить → precondition мис-оценивается)

_(Added by /self-improve 2026-07-05 — root: миграция команд зон критичности в `$jedi`.)_ Когда ассет, чьё значение эмитится в **filename-IRI-форме** (human-labeled enum/zone — не parseable как `prefix__Local`, см. тело правила), **перемещается** в другую папку/ассетспейс, его emitted IRI меняется (`obsidian://vault/<new-path>/<uid>.md`). Любой **хардкод этого IRI внутри precondition-`sparqlAsk`** (`FILTER(?z != <obsidian://vault/<old-path>/<uid>.md>)`) становится **stale**: сравнение `<new-path-IRI> != <old-path-IRI>` всегда true → «not in zone»-гейт всегда пропускает → кнопка/команда показывается даже когда не должна. **Тихо** — SHACL не ловит (IRI-строка в блок-скаляре валидна), wikilink-хук не ловит (это `obsidian://`-IRI, не `[[uid]]`).

- **Особо коварно:** filename-IRI хардкодится, потому что target human-labeled (по телу правила это единственный корректный способ его сослаться) — но именно поэтому он **не защищён UID-инвариантностью**: переезд target'а его ломает, тогда как `[[uid]]`-wikilink пережил бы переезд. Плюс двойная staleness: старый путь может быть ещё и pre-EKA layout (`assetspaces/shared-identities/` vs текущий `assetspaces/kitelev/exoas-*/`).
- **Pre-check (перед/после перемещения filename-IRI target'а):** грепни precondition-SPARQL на **старый path-IRI** target'а (`grep -rl '<old-path>/<uid>.md' <vault>/assetspaces` — или per-hook: любой `sparqlAsk` со `<obsidian://vault/...<uid>.md>`). Каждое вхождение → обновить на текущий путь.
- **Как получить ПРАВИЛЬНЫЙ текущий IRI (verify-before-assert, не по памяти):** запроси **реальный** трипл, где target — объект (`SELECT ?z WHERE { ?t <prop> ?z . FILTER(CONTAINS(STR(?z),'<uid>')) }`), и возьми точную строку. ⛤ **CLI-таблица ОБРЕЗАЕТ длинные IRI** (`…exoas-shar...`) — использовать **`--format json`** для untruncated-значения, не конструировать путь руками.
- **Revert-verify фикса:** задача, которая В зоне → precondition теперь FALSE (кнопка скрыта); задача вне зоны → PASSES (без регрессии). Прогон через реальный `apply <cliName> <target> --dry-run` (упражняет `PreconditionEvaluator`), не только SPARQL-обход.

**Empirical:** 2026-07-05, миграция 15 команд зон критичности `exoas-exocmd`→`exoas-public/jedi`. Зона Today (`e266a2e9`, filename-IRI) ранее переехала shared-identities→jedi; **все 3** zone/status atomic (`7fd20d07`/`0af27ad0`/`a2919027`) хардкодили pre-EKA `assetspaces/shared-identities/<uid>.md` → сравнение никогда не совпадало → Set Criticality High/Medium/Low показывались даже на задаче уже-в-зоне. Fix: `--format json`-запрос дал точные текущие IRI; Edit 3 atomic; revert-verify (Today-задача → «Precondition not satisfied» ✓, вне-зоны → «precondition passed» ✓); SHACL 0. Cost: латентный баг предшествовал миграции; пойман попутно.

### ⛤ Батч-форма того же гейта: при переносе N ассетов спрашивай «где ВООБЩЕ есть хардкод-IRI», а не «есть ли он у КАЖДОГО»

Pre-check выше сформулирован **per-target** (`grep -rl '<old-path>/<uid>.md'`) и предполагает, что старый путь уже известен. Для батча это плохо масштабируется дважды: N команд вместо одной **и** необходимость заранее знать путь каждого. Обратная форма дешевле и полнее — спросить у графа **все** хардкоды сразу, затем пересечь с move-set:

```bash
npx -y @kitelev/exocortex-cli@latest query --vault <V> --no-cache --format json \
  "SELECT ?s ?p ?o WHERE { ?s ?p ?o . FILTER(CONTAINS(STR(?o), \"<obsidian://vault\")) }"
# → пересечь UID внутри ?o с move-set: попал — исключить ассет из переноса (или чинить хардкод следом)
```

- ⛤ **Канарейка обязательна: пустой результат здесь неотличим от «хардкодов нет».** Гейт, чей ожидаемый ответ — «моих UID среди найденных нет», тождественно зелёный при любой поломке запроса ([[self-satisfying-metric-weak-verifier]]). Дискриминатор бесплатный: в корпусе **уже есть** известный хардкод (зона `jedi`, эмпирика выше) — он обязан найтись. Не нашёлся ⇒ сломан запрос, а не «чисто».
- ✅ **Гейт до мутации, не после.** Найденный хардкод даёт выбор: исключить ассет из батча (дёшево, обратимо) либо чинить IRI следом за переносом. После `mv` первый вариант уже недоступен.
- ⚠ **Экранирование в shell:** `"<obsidian://vault"` внутри двойных кавычек SPARQL-строки требует `\"` — иначе zsh съест кавычку и фильтр молча не сматчит ([[bash-loop-eval-pitfalls]] Г4).
- **Empirical 2026-08-05:** батч из 101 UID; гейт нашёл **3** хардкода в vault, из них **2 моих** (`6968a0fc`/`c7f1a968` — зоны критичности, вшиты в `exocmd__Precondition_sparqlAsk` preconditions `a2919027`/`0af27ad0`), третий — известная `jedi`-зона, служившая канарейкой. Оба исключены из переноса → кнопки Set Criticality не сломаны. Стоимость гейта: один запрос; стоимость пропуска — тихо мёртвый visibility-гейт у двух команд.

## §A5 — ⛔ Addendum 2026-07-11 — enumerate INSTANCES of a class via SPARQL: `?s Instance_class <class-UID>` МИМО (объект — symbolic IRI, не UID)

Рефлекс «найти инстансы класса» — `SELECT ?s WHERE { ?s exo:Instance_class <…#<class-UID>> }` (матч объекта по UID) — **возвращает 0**, когда LABEL класса parseable как `prefix__Local`: `exo__Instance_class: [[<uid>|exo__DisplayNameSpec]]` эмитит объект как **symbolic IRI** `https://exocortex.my/ontology/exo#DisplayNameSpec` (из label), НЕ как UID. Поэтому `CONTAINS(STR(?c),'<uid>')` / exact-UID-матч тихо не находит ничего (то же dual-IRI, что тело правила, но со стороны **subject-класса**, а не value).

- **Использовать вместо:** `FILTER(CONTAINS(STR(?c), '<ClassLocalName>'))` (symbolic localname) ЛИБО `find <vault> -name '<class-UID>*.md'` + резолв инстансов чтением. Verify-before-assert: на «0 инстансов» для класса с `prefix__Local`-label **НЕ** заключай «их нет» — пере-зонди по symbolic-localname (dual-IRI); почти всегда это форма запроса, а не отсутствие данных.
- **Empirical (2026-07-11, req a577316f):** `?s exo:Instance_class <…07eab746…>` (DisplayNameSpec UID) → **0**; но `find … -name 'd069c316*.md'` + `CONTAINS(STR(?c),'DisplayNameSpec')` нашли живые инстансы (12 spec'ов). ## §A7 — ⛔ Addendum 2026-07-24 — onto-RFC: транзитивная агрегация через `Instance_class` НЕ работает в чистом SPARQL — probe ДО записи в RFC, не assert по subClassOf-аналогии
<!-- Added by /session-retrospective 2026-07-24 — root: RFC 2705027a claimed transitive Instance_class/property* aggregation «works like subClassOf [in SPARQL]» без probe; verify-before-assert lapse, contained by commissioned 4-reviewer pass. -->

Тело правила («enumerate инстансы класса по symbolic-localname») + аддендум 2026-07-02 (status-фильтр по обеим IRI-формам) касаются **одношаговых** матчей. Ещё коварнее — **транзитивный property-path через `Instance_class`-джойн**: `?i exo:Instance_class ?cls . ?cls <class-authored-prop>/…* <target>`. Он **тихо возвращает 0** на реальном store, потому что `Instance_class`-**объект** = **symbolic-IRI** (`ems#Task`, из parseable label), а субъект любого **class-authored** свойства (`exo__Class_superClass`, `exodoc__implementsConcept` и т.п.) = **file-IRI** (`obsidian://…/<uid>.md`) — джойн `?cls` не сшивается, моста symbolic↔file в store нет (он в TS-коде `ClassHierarchy`/resolver, НЕ в property-path).

- ⛔ **Не assert'ить в onto-RFC/доке «транзитивный резолв работает, как subClassOf-обход»** — это ложно для property-path (работает только через код-резолвер). Это verify-before-assert lapse: capability-claim в durable-артефакте (RFC) по аналогии, без пробы.
- **Floor:** прежде чем писать в onto-RFC CQ с транзитивной агрегацией через `Instance_class` — **прогони её пробу на живом vault** (`?i Instance_class/<prop>* <target>` на существующем аналоге). Если 0 — CQ требует **TS inference-pass** (materialized bridging-трипл `owl:sameAs` symbolic↔file, как `exo:inferred`), а НЕ property-path; RFC обязан назвать это «ядро обработки» (Homoiconicity Q3), а не выдавать за «выпадает из запросов».
- **Class-centric CQ работают** (старт от class-file-IRI, без `Instance_class`-хопа): `<class-file-iri> <prop>/broader* <target>` сшивается file-IRI→file-IRI. Ломается именно джойн через `Instance_class`.
- **Bare `<UUID>` target = parse error** (`Cannot resolve relative IRI`); концепты/классы эмитятся file-IRI → target CQ должен быть полной `<obsidian://vault/.../<uuid>.md>` формой, не bare-UID и не symbolic.
- **Containment:** lapse пойман **заказанным** мной 4-ревьюерным адверсарным проходом (SPARQL-ревьюер, 9 проб) ДО реализации — mandatory-review в onto-rfc = рабочий safety-net для этого класса claim'ов.

## §A11 — ⛤ Addendum 2026-07-30 — dual-IRI seam теперь БРИДЖИТСЯ на query-time (`ClassHierarchyResolvingStore`), а Instance_class-эмиссию можно ФЛИПНУТЬ на file-IRI за флагом; при флипе `rdf:type` держать в LOCKSTEP (co-emit из одного объекта)

Тело правила + аддендумы 07-24/07-27 констатируют: pure-SPARQL **не переходит** dual-IRI seam (symbolic `Instance_class`-объект vs file-IRI `superClass`-субъект). RFC 78572fa9 Phase 0+3 добавили **query-time мост** и **опциональный флип формы эмиссии** — реальные механизмы, знать при работе с этим seam:

1. **`ClassHierarchyResolvingStore`** (thin `ITripleStore`-декоратор, обёрнут ОДИН раз в `ExoQLQueryExecutor` ctor; req `9fddda62`, PR #3984, v16.198.0) резолвит `Instance_class/superClass*`-hierarchy на **match-time** — pure-SPARQL транзитивный обход subClassOf (мёртвый per аддендум 07-24) теперь **работает через этот резолвер**, БЕЗ роста store (predicate-scoped, count-invalidated WeakMap index, `resolveClassHierarchy` toggle). Generalized (req `c359e3d2`, PR #4005, v16.203.0) чтобы бриджить и **membership**: `?s exo:Instance_class <symbolic>` матчит, даже когда объект хранится file-IRI (и наоборот) — читаемо-symbolic vault-SPARQL продолжает матчить независимо от формы эмиссии.
2. **Эмиссию `exo__Instance_class`-объекта можно ФЛИПНУТЬ symbolic→file-IRI** (`NoteToRDFConverter` ctor-опция `emitInstanceClassAsUid`, **default OFF** = byte-identical, per RFC F4; флип default-ON — отдельная поздняя стадия). Флип живёт в `valueToClassURI` (**Instance_class-специфичный путь, Issue #663** — НЕ `valueToRDFObject`; попытка флипнуть в `valueToRDFObject` = **dead code**, Instance_class туда не роутится).
3. ⛤ **CO-EMISSION LOCKSTEP (главный урок):** `valueToClassURI` со-эмитит `<subject> rdf:type <classObject>` из **ТОГО ЖЕ объекта**, что `exo__Instance_class`. Значит **флип формы одного значения меняет ДВА предиката разом** (`Instance_class` + `rdf:type`). Query-time мост ОБЯЗАН бриджить **ВСЕ** co-emitted-предикаты в lockstep (`MEMBERSHIP_PREDICATES = {exo__Instance_class, rdf:type}`) — иначе `?s rdf:type <symbolic>` ломается при флипе ON, хотя `?s exo:Instance_class …` работает. Это отдельная ось от [[multi-parser-predicate-migration]] (там N ПАРСЕРОВ читают один предикат; тут один ОБЪЕКТ co-emit'ится в N предикатов). Floor: флипая форму эмиссии значения, грепни ВСЕ предикаты, куда это значение co-emit'ится (`grep 'rdf:type\|Namespace.RDF' <converter>`), и покрой каждый в бридже + revert-verify каждый.
4. **Comprehensive label-index ⊇ hierarchy-edge-subjects:** резолвер строит `label→symbolic→file-IRI` из ВСЕХ `exo__Asset_label`/`rdfs:label` (не только из subject'ов `Class_superClass`-рёбер) — иначе метаклассы (`exo__Class`, чей own-`Instance_class` = `exo__Class`) не резолвятся. ## §A13 — ⛔ Addendum 2026-07-31 — `UNION` + ДВА независимых label-join'а = **OOM движка**; CQ с «двумя путями к сущности» надо МАТЕРИАЛИЗОВАТЬ, а не выводить в запросе

Аддендум 2026-07-24 (выше) фиксирует: транзитивная агрегация через `Instance_class` не работает. Соседний, независимый предел — **ёмкостный**, и он бьёт по совершенно легальному SPARQL:

⚠ **ОПРОВЕРГНУТО ЧАСТИЧНО 2026-08-02** (замер на 142k триплов: та же форма отработала, 4343 строки). Потолок зависит от **кардинальности ветвей**, а не от синтаксиса ⇒ читать эту секцию как **флаг риска**, а не как закон: `UNION` требует ПРОБЫ на живом графе, но не запрещён по построению. Наблюдение ниже остаётся верным для того графа и той кардинальности, на которых снято.

**`UNION` из двух веток + последующий join к ДВУМ label-паттернам роняет node по памяти** (`JavaScript heap out of memory` после «Translating to algebra») на графе ~140k триплов. Бисекция (каждый пункт проверен отдельно):

| Форма запроса | Исход |
|---|---|
| `UNION` голый (две ветки, без меток) | ✅ 89 строк |
| `UNION` + метка ОДНОЙ переменной | ✅ ok |
| `UNION` + `ORDER BY` (без меток) | ✅ ok |
| **`UNION` + метки ОБЕИХ переменных** | ⛔ **OOM** |
| `UNION` + обе метки + `ORDER BY` | ⛔ **OOM** |
| БЕЗ `UNION`: одна ветка + обе метки + `ORDER BY` | ✅ 58 строк |

⛤ **`ORDER BY` ни при чём** — он проходит и с `UNION`, и с двумя метками по отдельности. Роняет именно **комбинация UNION × 2 join'а** (похоже на декартово раздутие при исполнении union-then-join).

**Следствие для моделирования, а не только для запросов.** Паттерн «к сущности можно привязаться двумя способами, целевое значение выводится» (напр. работа → инициатива → цель ИЛИ работа → цель напрямую) **нельзя** реализовать запросом с `UNION` + резолюцией меток. Варианты:

1. ✅ **Материализовать выведенное значение** отдельным свойством, которое пишет тот, кто грумит/индексирует. Запрос становится однобранчевым (проверено: одно ребро + метка + `ORDER BY` = 2206 строк без проблем). Ценой одного избыточного свойства покупается выполнимость всех CQ. **Рекомендуется.**
2. Держать `UNION`, но **не резолвить метки в том же запросе** — вернуть IRI, метки добрать вторым запросом. Работает, но неудобно для потребителя.
3. Ограничиться одним путём привязки — часто противоречит уже принятому дизайн-решению.

**Floor:** CQ, содержащий `UNION`, **обязан быть прогнан на живом графе в Phase 1** до фиксации в RFC. «Синтаксически валиден» и «исполним на 140k триплов» — разные вещи, и вторая не следует из первой. Материализация выведенных значений — это **онтологическое** решение (лишнее свойство в TBox), поэтому цена ошибки — не переписанный запрос, а переписанная онтология.

**Empirical:** 2026-07-31, Фаза 0 онтологии приоритета роли PO (`exoas-po`). VL#PO-9 разрешил привязку к обоим уровням (цель ИЛИ инициатива) с выводимой целью. Первая формулировка CQ1 — `UNION` + метка работы + метка цели + `ORDER BY` — уронила движок. Бисекция дала таблицу выше → в онтологию добавлено `po__Work_derivedGoal` (материализованная цель, пересчёт при каждом груминге), CQ1 стал однобранчевым и заработал. Без пробы в Phase 1 дефект всплыл бы на Фазе 3, когда TBox уже был бы отгружен.

## §A14 — ⛤ Addendum 2026-08-02 — WRITE-form ≠ READ-form: пишешь `[[uid]]`, читаешь **symbolic**; UID-ключующий мэппер молча отдаёт `None`, и это читается как «значения нет»

Тело правила объясняет МЕХАНИЗМ (объект эмитится symbolic, если метка цели парсится как
`prefix__Local`). Практическое следствие, на которое легко напороться **сразу после собственной
записи**: ты кладёшь значение как `set-property --value '[[<uid>]]'`, а обратно из SPARQL получаешь
`https://exocortex.my/ontology/<ns>#<Local>` — **UID в ответе отсутствует**. Любой пост-процессор,
ключующийся на UID (`re.search(r'([0-9a-f]{8})', value)`, словарь `{uid: label}`), вернёт `None`
по КАЖДОМУ такому полю.

- ⚠ **Симптом обманчив: это выглядит как «поле не забиндилось».** Строка в JSON присутствует, но
  твой маппинг пуст ⇒ естественный (и неверный) вывод — «движок потерял биндинг». Особенно
  правдоподобно, когда в том же запросе **datatype-свойство** (integer/string, напр. `_rank`)
  маппится нормально: возникает ложная корреляция «объектные свойства не биндятся» / «многие
  `OPTIONAL` ломаются».
- ✅ **Floor:** прежде чем объявлять дефект движка — **распечатай СЫРОЕ значение** (`print(r)`), а не
  результат своего маппинга. Форма ответа отвечает на вопрос за один взгляд. Матчить на чтении по
  **symbolic-localname**; UID держать для ЗАПИСИ.
- ⛔ **Не персистить диагноз, пока он не изолирован.** Ложный «баг движка», записанный в скилл /
  дайджест / handoff-промпт, дороже отсутствия записи: он читается будущими прогонами как
  проверенный факт ([[verify-before-assert]]; тот же класс, что stale-утверждение в

## §A15 — ⛤ Addendum 2026-08-02 — НЕОБЪЯВЛЕННЫЙ PREFIX не роняет запрос: он исполняется и молча отдаёт НОЛЬ ⇒ «запрос отработал без ошибки» не является проверкой

Третий независимый источник молчаливого нуля (после dual-IRI и over-constrained фильтра): **префикс, не объявленный блоком `PREFIX` и не входящий в зашитый список движка** (`rdf, rdfs, xsd, owl, ems, exo, ims`). Замер на живом графе:

| Запрос | Результат |
|---|---|
| `PREFIX zz: <…/ems#>` + `?s exo:Instance_class zz:Task` | **674** |
| тот же запрос, `zz:` **не объявлен** | **0 — без ошибки и предупреждения** |
| `ems:Task` (префикс в списке движка) | **674** |

- ⛔ **Отсюда главное: прогон «а не упал ли запрос» — НЕ проверка.** При отсутствующих данных и при неверном префиксе исход **идентичен**: ноль строк, exit 0. Такая «проверка» тождественно зелёная — она не может показать плохой результат ([[self-satisfying-metric-weak-verifier]]).
- ⛤ **Особо коварно для НОВОЙ онтологии**, чей префикс по определению не в списке движка: все запросы новой модели выглядят рабочими и возвращают пустоту, которая читается как «таких данных пока нет» — а это ровно то, чего и ждёшь на новой онтологии. Дефект маскируется собственной правдоподобностью.
- ✅ **Проверка, умеющая краснеть — две ступени:**
  1. **До появления данных** — структурная проба: та же форма запроса (соединения, `FILTER`, `OPTIONAL`, `NOT EXISTS`) поверх **заведомо населённого** namespace (`ems:`); зелёным считается только **непустой** ответ. Проверяет форму, не префикс.
  2. **После появления данных** — непустой **ожидаемый** результат на реальных инстансах. Только он отличает «работает» от «молча пусто».
- ✅ **Floor:** каждый SPARQL для нового namespace несёт собственный блок `PREFIX` — включая тела `query__NamedQuery` и строки в `exocmd__Command`. `exo:`/`ems:` работают без объявления, и по аналогии автор решает, что новый префикс тоже работает.
- ⛔ **Худший случай — ИНВАРИАНТ, чей ожидаемый ответ и есть ноль** («этот запрос обязан всегда возвращать 0 строк»). Здесь необъявленный префикс даёт **тождественно зелёный гейт**: нечем отличить «нарушений нет» от «запрос не туда смотрит», потому что оба вида пустоты выглядят как успех. Такой инвариант — слабый верификатор по построению ([[self-satisfying-metric-weak-verifier]]). **Принимать его можно только после пробы на способность краснеть:** подставить заведомо нарушающий ассет → запрос вернул строку; убрать → ноль. Без флипа «0 строк» не является доказательством. _(2026-08-02: инвариант DLP#1 в RFC разведки был написан без блока `PREFIX` — то есть был бы вечно зелёным ровно в том разделе, который его и вводит против самоудовлетворяемых метрик; поймано адверсарной панелью до отгрузки.)_

**Empirical 2026-08-02** (onto-RFC `agr__`, соглашения): ревью сообщило «пять запросов не парсятся — нет `PREFIX agr:`». Формулировка **неверна**: запросы парсились и возвращали ноль, то есть модель тихо врала бы нулём на каждом процессинге. Обнаружив это, я прогнал все шесть блоков RFC, получил «0 строк, ошибок нет» и **едва не записал это как «проверено»** — та же тождественно-зелёная проверка. Дискриминатор (объявленный алиас на тот же namespace против необъявленного: 674 против 0) вскрыл и механизм, и порок собственной проверки. Заменено структурной пробой: 4 формы из 4 дали 3 / 159 / 156 / 354 строки, включая `FILTER NOT EXISTS`.

## §A16 — ⛤ Addendum 2026-08-03 — на СТОРОНЕ ПОТРЕБИТЕЛЯ literal приходит в ДВУХ формах: `"текст"` и `"значение"^^<datatype>`; наивное «снять кавычки по краям» на второй молча ломает ВСЁ, что зависит от значения

Addendum 2026-07-29 (§выше) фиксирует, что `exocortex-cli query --format json` оборачивает
plain-литерал в двойные кавычки, и требует их снять перед деривацией. Недостающая половина:
**вторая форма — типизированный литерал**, и на ней тот же приём не срабатывает вовсе.

```
plain:        "ztlk_v2__FleetingNoteStateResolved"
типизированный: "2026-08-02T23:18:13.000Z"^^<http://www.w3.org/2001/XMLSchema#dateTime>
```

Условие «первый и последний символ — кавычка» на второй форме **ложно** (справа `>`),
поэтому значение уходит дальше **сырым, вместе с дататипом**. Молча.

- ⛔ **Два последствия, и второе тише первого.** (а) Значение непригодно к разбору
  (`fromisoformat` падает, число не парсится) — это заметно. (б) **Лексическое сравнение
  ломается инвертированно:** ведущая `"` (0x22) сортируется **раньше цифр**, поэтому
  `'"2026-08-02…' >= '2026-07-01'` даёт **False** — то есть фильтр «свежее отсечки»
  отбрасывает **всё**, и поток данных гаснет целиком, не подав признака.
- ✅ **Floor:** распаковывать ОБЕ формы, типизированную — первой:
  ```python
  TYPED = re.compile(r'^"(.*)"\^\^<[^>]*>$', re.DOTALL)
  m = TYPED.match(s)
  if m: return m.group(1)
  if len(s) >= 2 and s[0] == '"' and s[-1] == '"': return s[1:-1]
  ```
- ⚠ **Какие предикаты типизированы — проверять, а не помнить.** `exo__Asset_label` приходит

  Один `--format json` на реальном запросе показывает форму за секунду.
- ⛤ **Фикстура теста обязана нести РЕАЛЬНУЮ форму.** Придуманная «наивная» строка

## §A17 — ⛔ Addendum 2026-08-02 — ДИЗЪЮНКЦИЯ теряет строки, когда одна ветвь падает на несвязанной переменной: `!BOUND(?x) || <условие по ?x>` молча отбрасывает ровно те строки, ради которых написан

Четвёртый источник молчаливой неполноты (после dual-IRI, over-constrained фильтра и необъявленного префикса) — и единственный, где виноват **движок**, а не форма запроса.

**Замер на живом графе** (8 экземпляров, у 4 свойство есть, у 4 нет):

| Фильтр | Ожидается | Получено |
|---|---|---|
| `!BOUND(?ds)` | 4 | 4 ✓ |
| `CONTAINS(STR(?ds), "…")` | 4 | 4 ✓ |
| **`!BOUND(?ds) \|\| CONTAINS(STR(?ds), "…")`** | **8** | **4** ⛔ |
| `CONTAINS(…) \|\| !BOUND(?ds)` (порядок не важен) | 8 | 4 ⛔ |
| `!BOUND(?ds) \|\| (1=1)` — контроль | 8 | 8 ✓ |
| `!BOUND(?ds) \|\| !BOUND(?ds)` — контроль | 4 | 4 ✓ |
| `CONTAINS(COALESCE(STR(?ds), "…"), "…")` — обход | 8 | 8 ✓ |

По SPARQL 1.1 §17.2 `true || error` = `true`. Контроль с константой справа доказывает, что **дизъюнкция сама по себе исправна** — ломается обработка **ошибки внутри неё**: результат ошибки поглощает истину соседней ветви.

- ⛔ **Бьёт по самому ходовому паттерну необязательных фильтров.** `!BOUND(?x) || <условие>` — стандартный способ сказать «свойство не задано ИЛИ подходит». Значит под ударом любой запрос вида «покажи всё применимое, включая безусловное», а теряются именно записи **без** необязательного свойства — как правило, большинство.
- ✅ **Обход: `COALESCE(STR(?x), "<значение по умолчанию>")`** вместо `!BOUND`. Ошибка не возникает, дизъюнкция не нужна вовсе. Не зависит от исправления движка.
- ⛤ **Tell:** запрос **не падает** и возвращает непустой, но подозрительно ровный результат — ровно ту подгруппу, у которой необязательное свойство задано. Если ждал «эти плюс безусловные», а пришли только «эти» — проверяй дизъюнкцию, а не данные.
- **Обнаружение возможно только проверкой на непустой ОЖИДАЕМЫЙ результат** (§Addendum выше): «отработал без ошибки» здесь зелено всегда.

**Empirical 2026-08-02** (онтология соглашений `agr__`, пилот из 8 записей): запрос «что действует прямо сейчас» вернул **1** строку вместо 5 — выпали все безусловные соглашения (границы, право не посвящать), остались только записи с временным окном. Бисекция по таблице выше локализовала дефект за 6 запросов. Заведено: [kitelev/exocortex#4016](https://github.com/kitelev/exocortex/issues/4016) + зеркало-задача в vault. Запросы RFC переписаны на `COALESCE`; после этого 09:20 → 5 строк, 09:50 → 6 (окна корректно сменились).

⛤ **Факт (verified `NoteToRDFConverter.ts`, Issue #1329):** вики-ссылки **в теле** заметки индексируются наравне с frontmatter — предикатом `exo:Asset_bodyLink` (`convertBodyWikilinks`, вызывается из основного конверта). То есть «на что ссылается ассет» — это **объединение** двух непересекающихся множеств предикатов, а не одно frontmatter-множество.

- ⛔ **Недосчёт не пропорционален, он структурный.** Считая только frontmatter, ты видишь ссылки, поставленные **машиной** (команды, шаблоны, `set-property`), и не видишь поставленные **человеком по ходу письма** — а именно вторые доминируют в слое заметок. Эмпирика ниже: 1860 body-прозы против 2070 frontmatter, то есть **47 %** внешних связей.
- ⛤ **Вывод меняется качественно, а не количественно.** Реификация (`exo__Statement`) применима к **frontmatter**-связи; прозу реифицировать нельзя, не удалив ссылку из читаемого текста. Значит вопрос «сколько связей починит реификация» без разделения каналов отвечается **вдвое оптимистичнее**, чем на самом деле, — и предложение выглядит выполнимым там, где половина задачи не решается вообще.
- ✅ **Floor:** меряя связность («сколько ссылок ведёт в X», «что сломается, если вынести X»), **сначала распечатай распределение по предикатам** (`SELECT ?p (COUNT(*) AS ?n) … GROUP BY ?p`), а потом фильтруй. Одна команда; она же показывает и `isDefinedBy`-самоссылки, которые иначе раздувают счёт (в эмпирике — 5552 из 9015 «внутренних»).
- ⚠ **Симптом-tell:** ты перечисляешь предикаты **по памяти** («ну, `_relates`, `_genus`, `_broader`»). Список из головы — это гипотеза о содержимом графа; `GROUP BY ?p` — факт.

## §A19 — ⛤ Addendum 2026-08-02 — ТРИ формы, возвращающие НЕПУСТОЙ неверный результат; и floor «гейт обязан уметь краснеть»

Все предыдущие аддендумы этого правила описывают **молчаливый НОЛЬ** (необъявленный префикс, dual-IRI, over-constrained фильтр). Замер 2026-08-02 на живом графе (142 077 триплов) вскрыл три формы противоположного, более опасного класса: они возвращают **непустой правдоподобный** результат вместо верного, поэтому не вызывают подозрений вовсе.

| Форма | Ожидалось | Получено |
|---|---|---|
| `FILTER NOT EXISTS` + inner-`FILTER` по **ВНЕШНЕЙ** переменной | 116 | **519 из 519** (всегда TRUE) |
| **`MINUS`** с всегда-матчащим inner | 0 | **519** (no-op) |
| **`MAX`/`MIN`** по `xsd:dateTime` | `2026-08-02T20:07…` | **`"2026"^^xsd:decimal`** |

⛤ **Граница первого дефекта узкая** — корреляция через **triple pattern** ✅, inner-`FILTER` по **inner-only** переменной ✅, сравнение с **константой** ✅. Ломает ровно ссылка на внешнюю переменную внутри `FILTER` под `NOT EXISTS`. Значит идиому «нет более позднего события» надо строить как: корреляция triple-pattern'ом + сравнение только с константой (порог подставляет вызывающий).

⛔ **Оба естественных обхода первого дефекта тоже сломаны** (`MINUS`, `MAX`) — то есть наткнувшись на него, легко перебрать все три и заключить «задача невыразима». Она выразима, но единственной формой.

**Floor — гейт обязан уметь краснеть.** Запрос-инвариант, чей ожидаемый ответ есть **ноль**, тождественно зелёный при любой из этих поломок и при любом молчаливом нуле из аддендумов выше. Прежде чем считать «0 строк» доказательством: подсунуть **контрпример**, убедиться, что он находится, убрать. Без этого флипа пустой результат не означает ничего ([[self-satisfying-metric-weak-verifier]]).

**Метод обнаружения — счётный дискриминатор, а не разглядывание выдачи.** Первый прогон дал правдоподобное число, и принять его за успех было естественно. Вскрыло расхождение сравнение **двух счётчиков**: всего строк против прошедших фильтр, при независимо известном ожидании. «Прошли все» там, где должна пройти часть, — доказательство; «выглядит разумно» — нет.

**Побочно, но влияет на дизайн:** `NOT EXISTS` исполняется вложенным циклом без индекса — 0.85 с при 519 строках внешнего множества против **62 с** при 8304 (квадратично). Загрузка графа сама по себе 6–7 с на вызов CLI и доминирует над запросом.

**Также опровергнуто тем же замером:** транзитивные пути **работают** между двумя file-IRI (`+` дал 2939 против 519 одношаговых) — мёртвость касается только обхода через `Instance_class` (symbolic-объект против file-IRI-субъекта). Формулировку «транзитивная агрегация не работает» читать строго в этой границе.

Полная запись с измерениями, изоляцией границы и декомпозицией — `ems__Bug` `[[0c24668f-63ea-4daa-b4c1-947ca4ec5dcf]]` (vault-exodev). ⛔ На GitHub намеренно не заводилось: свои дефекты ведём в своей системе ([[exocortex-self-improving-dogfood]]).
