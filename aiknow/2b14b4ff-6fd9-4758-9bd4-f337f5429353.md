# ⛔ НЕ запускать Docker/QEMU e2e во время multi-child orchestration → kernel panic

## Принцип

На Apple Silicon **Docker real-Obsidian e2e гоняется под QEMU amd64-эмуляцией** (см. `obsidian-plugin-e2e-docker-emulation.md`) — это CPU-тяжёлая нагрузка сама по себе. Если запустить её **одновременно с несколькими активными Claude-детьми** (multi-child orchestration: каждый ребёнок крутит builds / codegraph / tests / TUI), суммарная нагрузка перегружает систему до **kernel panic по watchdog-таймауту** → форсированный ребут.

**Это ТРЕТИЙ независимый system-side failure-mode** оркестрации, отдельный от:
- **Type 1 — Jetsam memory pressure** (`overnight-orchestration-design.md` + `tmux-send-keys-bash-sigkill-pattern.md`): SIGKILL exit 137 одного процесса/дерева.
- **Type 2 — API rate-limit cascade** (`anthropic-api-rate-limit-child-death.md`): тихая смерть child на orientation.
- **Type 3 (этот) — QEMU-emulation + concurrency overload → watchdog kernel panic**: **катастрофа уровня всей машины** (ребут убивает ОРКЕСТРАТОРА И ВСЕХ детей разом), хуже per-child смерти.

Сигнатура panic-репорта: `watchdog timeout: no checkins from watchdogd in 94s` — `watchdogd` не смог зачекиниться → kernel форсит panic+reboot. CPU настолько забит (QEMU + N×Claude), что даже системный watchdog-демон голодает по планировщику.

## Когда правило срабатывает

- Оркестратор активен с ≥1 живым child И планирует/директивит запуск Docker-e2e (real-Obsidian Playwright под `ghcr.io/kitelev/exocortex-ci` + xvfb через QEMU amd64) — у себя ИЛИ в одном из детей.
- Особенно: AC задачи требует UI-smoke реального плагина, и соблазн «запущу e2e в child, пока другие дети идут параллельно».
- Любой Docker-build/run amd64-образа на Apple Silicon при параллельной Claude-нагрузке.

## Запреты

- ⛔ **НЕ запускать Docker/QEMU e2e (ни у себя, ни в child) пока есть ≥1 другой активный Claude-child.** QEMU-эмуляция + N child = overload → panic.
- ⛔ НЕ директивить child «сделай Docker UI-smoke» как часть параллельной волны. Если AC требует Docker-e2e — это **сериализуется** (дренировать всех других детей сперва), не параллелится.
- ⛔ НЕ трактовать как «просто медленно» — это не latency, это risk катастрофического ребута, теряющего ВСЮ in-flight работу всех сессий.

## Mitigation — как всё-таки получить UI-proof

| Нужен UI-proof реального плагина | Безопасный путь |
|---|---|
| User present (computer-control доступен) | ✅ **UI-smoke через computer-control** на живом Obsidian (per `obsidian-plugin-update-via-brat.md` + DevTools-eval). Нулевая Docker-нагрузка. Предпочтительно. |
| User absent, нужен автоматический e2e | ✅ Запускать Docker-e2e **изолированно: 0 других активных Claude-детей** (дренировать волну → один Docker-прогон → возобновить спавны). |
| Identical code path уже UI-verified | ✅ **Transitive proof** (`ui-smoke-transitive-proof.md`) — без нового Docker-прогона вовсе. |
| CI | ✅ e2e-shard в GitHub Actions (нативный amd64 раннер, без QEMU, не на твоей машине). ⛤ Это правильный дом для GUI-BDD specs (см. GUI-BDD-CI задача — specs в CI, ⛔ не локальный Docker). |
