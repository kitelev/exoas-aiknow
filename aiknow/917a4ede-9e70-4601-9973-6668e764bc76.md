## §A1 — 2026-07-26 — 2-й инстанс (INVERTED listen-bot) + 4 новых леска

Второй внешний движок по этому рецепту — **входящий дневник-бот** (Telegram → `ztlk__FleetingNote`): пишешь мысль, каждое сообщение = отдельная fleeting-заметка. **Инвертирован** относительно check-in: тот СПРАШИВАЕТ (send+poll+batch), этот СЛУШАЕТ (poll-only). Общий skeleton переиспользован 1:1 (`inbox_lib`≈`checkin_lib`: `tg`/`parse_frontmatter`/`_wl_*`/homoiconic-loader/defensive-load/`_npx`). Рецепт §Принцип держится чисто; 4 уточнения:

1. **⛤ Reuse-existing-bot ДО `/newbot` (verify-before-assert).** @BotFather-история часто УЖЕ содержит бота под задачу — Андрей пре-создаёт боты и не дописывает движок. Перед созданием нового: открыть @BotFather, глянуть recent-ботов / историю (`kitelev_inbox_sender_bot` был создан 4 июля ровно под этот сценарий → переиспользован, дубликат не плодил). Единственное жёсткое требование — **dedicated single-consumer getUpdates** (два poll-демона на одном боте крадут апдейты друг у друга) → убедиться, что бот не поллится другим процессом (`getWebhookInfo` webhook пуст + `getMe` ok).
2. **⛤ Токен из BotFather надёжно = клик по code-span → буфер → `pbpaste` → `getMe`.** ⛔ НЕ транскрибировать со скриншота (0/O, l/I, 1/l). В Telegram Desktop одиночный клик по моноширинному `code`-спану токена копирует его в clipboard; `pbpaste` в Bash даёт точное значение; провалидировать `getMe` (даёт заодно точный `username`+id) + `getWebhookInfo` (webhook пуст = getUpdates работает). Клипборд после — очистить (`printf '' | pbcopy`).
3. **⛤ Dogfood-split создания ассетов: instances → `exocortex-cli create`, TBox → Write.** Config-ИНСТАНСЫ (singleton config, кнопки-Option, enum-инстансы вроде FleetingNoteType) создавать через `create` (реальный продуктовый путь; так же движок создаёт заметки — главная dogfood-поверхность). TBox (классы `exo__Class`, анкер `exo__Ontology`, registry `exo__AssetSpace`) — Write (метаклассы, `create` их не делает). Если инстансы уже созданы Write'ом bulk-inter-referential + SHACL-floor — санкц., но при строгой директиве **recreation-via-CLI** чист: `create` каждый (новые UID ок для self-contained config-графа — TypeOption→config/type перевязать на новые UID), затем `rm` старых Write-файлов, один `exosync sync` (delete N + push N в одном раунде). `create` печатает JSON `{uuid,path,label}` (даже без `--format`) → UID/path парсятся легко; `--body-file` для тела (обходит shell-quoting `$`/эмодзи).
4. **⛤ Push из launchd-демона: токен через `GH_TOKEN` env, НЕ `--token`.** exosync push читает `GITHUB_TOKEN`/`GH_TOKEN` из env → резолвить `gh` самому (как `_npx`: `/opt/homebrew/bin/gh`), `gh auth token` → передать в subprocess `env={**os.environ,"GH_TOKEN":tok}` (не в argv → не видно в `ps`, не зависит от gh в PATH демона). **Debounced push** (threading.Timer, reset на каждой заметке) батчит всплеск мыслей в один push; guard `_push_running` от наложения.

**Empirical:** 2026-07-26, дневник-бот `@kitelev_inbox_sender_bot` (переиспользован, не создан). MOUNTED `exoas-my-inbox` (anchor `$diary` `ebecde82`, дескриптор `6281df30`, namespace `diary` — `inbox` был занят, коллизию поймал SPARQL по `Ontology_url`) + 2 класса (`diary__InboxConfig`/`diary__TypeOption`) + config-инстансы через CLI + FleetingNoteType Observation/Idea. Движок `~/dotfiles/scripts/inbox-diary/` (poll_inbox+note_writer+inbox_lib, dotfiles `d62c422`); homoiconic revert-verified (правка метки кнопки в /tmp-фикстуре → движок читает новую). **Live e2e через computer-control** (сам создал/активировал): /start→WELCOME (chat_id bound), тест-мысль→FleetingNote (create, тело с `$`/эмодзи сохранено), тап 👁 Наблюдение→тип обновлён Insight→Observation на диске И remote, debounced push rc=0. Cost: чистый проход; 1 мелкий лог-баг (дубль ключа `type` в log_event → перезапись; пофикшен).

## §A2 — 2026-07-26 — MULTI-bot / multi-user: изоляция = отдельная VAULT-ПАПКА на бота (не отдельный репо), профиль = scope, sandbox по отсутствию

Когда бот-движок — это **интерфейс к ЧАСТИ** экзокортекса пользователя (часть определяется профилем), и таких ботов/пользователей несколько (напр. 2 бота для альфа-тестера Оли — её личное пространство + shared), изоляция моделируется НЕ отдельным репо-assetspace, а **отдельной vault-папкой** (как `vault-my`/`vault-tbank`/`vault-exodev`). Три reusable-решения (все user-confirmed 2026-07-26):

1. **⛤ Бот ↔ vault-папка ↔ профиль = 1:1; изоляция «по физическому отсутствию».** Каждому боту — своя vault-папка (`~/vaults/vault-<bot>`), к которой применён СВОЙ профиль (`apply-profile` = strict-replace → материализованы ТОЛЬКО assetspace'ы этого профиля). Демон запускается с `--vault <эта-папка>` → **физически не может случайно достучаться до того, что вне профиля** — файлов просто нет на диске в его папке. Это сильнее «union-mount всего на хост-маке» (тот держит всё в одной папке → буг демона мог бы забрести в чужой AS; union теряет изоляцию). Несколько vault-папок сосуществуют на одном маке (это просто разные директории); apply-profile per-vault → у каждой свой смонтированный набор ОДНОВРЕМЕННО, без конфликта strict-replace (strict-replace скоупится к `--vault`-таргету). Так у Андрея УЖЕ устроено: vault-my/tbank/exodev = 3 папки-скоупа; паттерн просто расширяется на per-бота.
2. **Два независимых слоя безопасности.** (a) **vault-папка = disk-scope** — демон не ВИДИТ файлы вне профиля (нет на диске). (b) **fine-grained PAT = remote-write-scope** — `exosync push` пушит только в разрешённые репо. Для бота в чужой leaf (напр. leaf Оли `kalashnikova0410/exoas-my`) — узкий PAT с write ТОЛЬКО на её leaf, лежит в конфиге на ТВОЁМ маке; утечёт → скомпрометирован только leaf, не весь граф. Профиль (disk) и PAT (remote) — ортогональны, оба нужны.
3. **⛤ Capture-цель зависит от вовлечённости пользователя (не от «изоляции» — та решена п.1-2).** Раз безопасность закрыта vault-папкой+PAT, вопрос «выделенный capture-inbox vs прямо в основной граф» становится чисто **workflow**: (a) **процессор** (разбирает inbox, fleeting→permanent, как Андрей) → выделенный capture-inbox выгоден (сырое отдельно, триаж позже — это $diary). (b) **low-adoption юзер** (почти не пользуется) → **прямо в leaf** (fleeting/notes-подпапка), ноль триажа: заметка сразу видна в графе → нет риска inbox-**кладбища** (наполняется, никогда не разбирается). Триаж-шаг = трение = анти-adoption. Класс `ztlk__FleetingNote` остаётся типом ноты в обоих случаях. ⛔ Не дефолтить в capture-inbox «как у себя» — асимметрия процессор↔low-adoption решает.

**Empirical:** 2026-07-26, декомпозиция идеи `19185371` (Adoption экзокортекса Калашниковой через захват-бот; EA-сессия). WBS-проект `ab52aee1` в vault-my: 2 бота → 2 vault-папки (`vault-kalashnikova-my` c профилем `$$kalashnikova-my` · `vault-kalashnikova-shared` над `exoas-shared-kalashnikova`), демоны на маке Андрея (у Оли мака нет — пишет/читает с телефона), capture прямо в её leaf (low-adoption). Модель прошла через `interactive-interview` (4 раунда, по 1 вопросу); первую мою версию («union-mount на хосте») Андрей поправил на vault-папку-per-бота (лучше — sandbox по отсутствию). Cost: чистый дизайн-проход, 0 регрессий; архитектура зафиксирована durable в теле проекта + T3/T5. NB: демоны на ОДНОМ маке-хосте, но у КАЖДОГО своя vault-папка+профиль (НЕ union-mount).

### ⛤ Addendum 2026-07-27 — конкретный BUILD-рецепт multi-user shared-бота (реализация DESIGN-аддендума выше)

Реализация shared-бота Андрей+Оля (@ao_shared_exo_bot, 3-й демон) дала конкретный воспроизводимый рецепт для «peer-бота над общим пространством» (несколько равноправных пользователей, НЕ owner-tester):

1. **⛤ Scoped-vault = `cp -a <tester>-my → <tester>-shared` + `rm -rf` приватного leaf** (НЕ re-bootstrap). Каноничные vault git-free (tarball mounts) → scoped-vault для shared-бота собирается **копированием уже-смонтированного** `vault-<tester>-my` минус приватный leaf: `cp -a` → `rm -rf assetspaces/<owner>/exoas-my` (Олин личный) → выкинуть его stanza из `.gitmodules` (python re-split по `[submodule`). Изоляция = **sandbox-by-absence** (exoas-my физически нет → бот не видит личное). TBox-floor (exoas-exo/public/exocmd/registry/w3c) остаётся → class-resolution/`apply`/exosync работают. **Verify:** `exosync-parity --token-from-gh` показывает РЕДУЦИРОВАННЫЙ набор репо (без приватного leaf) + query грузит TBox (20k+ триплов). Дёшево (~секунды), не требует network-bootstrap.
2. **⛤ `authorized_chat_ids` shared-mode (фикс-список равных, БЕЗ owner-binding) ≠ просто закинуть обоих в `admin_chat_ids`.** Для peer-бота нужна ОТДЕЛЬНАЯ ветка авторизации в движке: `authorized = cfg.get("authorized_chat_ids") or []; if authorized: return if chat_id not in authorized`. ⛔ Наивное «оба chat_id в `admin_chat_ids`, owner unset» — **НЕБЕЗОПАСНО**: случайный третий (не-admin) первым сообщением сработает owner-bind-once → забиндится владельцем. Правильно: непустой `authorized_chat_ids` **выключает** owner-binding целиком, список = единственный allowlist. Backward-compatible: single-tester конфиг (без `authorized_chat_ids`) остаётся в owner-mode. **Один env-параметризованный движок** (`poll_assistant.py`) обслуживает и single-tester, и shared-бота (env: `ASSIST_BASE_DIR`/`ASSIST_VAULT`/`ASSIST_CLAUDE_CONFIG_DIR`/`ASSIST_PERSONA_FILE`/`ASSIST_WRAPPER_DIR`/`ASSIST_PUSH_TOKEN_FILE`).
3. **⛤ Push-токен = токен ВЛАДЕЛЬЦА shared-репо, НЕ tester-PAT.** Shared-AS `kitelev/exoas-shared-kalashnikova` — kitelev-owned (`gh api repos/... .permissions.push=true` у токена Андрея). Демон пушит `gh auth token` Андрея (в `~/.olya-bots/shared/push-token.txt` 600). ⛔ НЕ Олин PAT — он allowlist'ит только Олин leaf (`exoas-my` → 404 у токена Андрея, но shared-vault его не монтирует → не проблема). `exosync push` толкает только ИЗМЕНИВШИЕСЯ репо (бот пишет только в shared-AS через anchor) → TBox-репо не пушатся.
4. **Формальный `exo__Profile` = декларация-намерения, НЕ драйвер mount'а.** Running-vault собран cp-a; формальный `$$<tester>-shared` профиль (`_includes = [shared-AS-descriptor, exocmd-descriptor]`, isDefinedBy=$profiles) создаётся ОТДЕЛЬНО через `exocortex-cli create --class exo__Profile` для гомоиконичной чистоты графа (если vault пере-монтировать `apply-profile` → тот же mount-set). Профиль в vault-владельца (vault-my), co-located в `exoas-profiles/profiles/`, SHACL-clean, push токеном владельца.
5. **Тот же hardened-wrapper паттерн** (`shared-exo`, allow-list verbs + deny `--body-file`/`--vault`/`--token`/`--created-by`, `--vault` пиннится, `--created-by` = agent__Agent shared-space) + отдельный sandbox `~/.shared-claude/settings.json` (`Bash(shared-exo:*)` + Read/Grep/Glob на shared-vault, deny секретов).

### ⛤ Addendum 2026-07-28 — bot-движок в TELEGRAM-ГРУППЕ + свежесть KB (pre-pull) + per-sender git-атрибуция (расширения shared-бота)

Пять reusable-расширений bot-движка (`poll_assistant.py`), когда бот работает НЕ только в 1:1-личке:

1. **⛤ Group support = mention-triggered (privacy mode ВКЛ, НЕ выключать).** Бот в группе получает от Telegram ТОЛЬКО сообщения, которые (@)-упоминают его / reply на его сообщения / `/команды` — если `can_read_all_group_messages=false` (privacy ВКЛ, дефолт). **Это ЖЕЛАЕМО** для группового ассистента (не отвечать на каждую строку → шум+cost). ⛔ НЕ выключать privacy через @BotFather. Код: (а) `is_group = chat.type in (group,supergroup)`; (б) **авторизация по ОТПРАВИТЕЛЮ** `m.from.id` (в личке `chat.id==from.id`), а **ответ/сессия/rate — по `chat.id`** (группа = один тред); (в) **strip @mention** из текста (`text.replace("@"+BOT_USERNAME,"")`; `BOT_USERNAME` из `getMe` при старте, module-global — переживает per-loop `state=load_state()`); (г) owner-mode (single-tester без `authorized_chat_ids`) — **DM-only** (`if is_group: return`). Grep: авторизация была по `chat.id` → в группе `chat.id`=id ГРУППЫ (отрицательное), не в user-allowlist → бот молчал.
2. **⛤ Forum-топики: reply в тот же топик через `message_thread_id`.** Форум-супергруппа тредит по `message_thread_id`; без него ответ на упоминание в НЕ-General-топике уходит в General. Helper `send(method, params)` добавляет `params["message_thread_id"]=m.get("message_thread_id")` на КАЖДЫЙ исходящий `sendMessage`/`sendChatAction` (None в личке/не-форуме = no-op). Все исходящие — через helper.
3. **⛤ Pre-pull свежего KB перед КАЖДЫМ содержательным ответом.** Бот читает локальный vault → может быть устаревшим (peer правил с телефона). `exosync pull` (remote-changes-only, «nothing leaves the device» — дёшево ~3с, read-safe) ПЕРЕД `ask_claude`, под тем же push-lock, best-effort (при сбое отвечает по локальным). Ставить после typing-индикатора (юзер видит «печатает» во время pull). Push (после write) — отдельно, как было. (`exosync pull` есть отдельной субкомандой; НЕ полный `sync` — тот ещё пушит.)
4. **⛤ Two-token pull для tester-бота над OWNER-приватным shared-AS.** Fine-grained PAT тестера **404-ит на приватный репо ЧУЖОГО аккаунта** (kitelev/exoas-shared-kalashnikova), даже если тестер — коллаборатор (fine-grained PAT читает только ресурсы своего owner'а). → его pre-pull не тянет shared-контент. Fix: **второй pull-pass** другим токеном (env `ASSIST_SHARED_PULL_TOKEN_FILE` = токен-читатель owner'а, напр. `gh auth token` Андрея в `~/.olya-bots/kitelev-reader.txt` 600). Union: pass-1 (свой токен) = leaf+public; pass-2 (reader) = shared. Оба best-effort. Shared-бот его OWN токен (Андрея) уже читает всё → второй pass не нужен (env не задан).
5. **⛤ Per-sender git-атрибуция = push токеном ОТПРАВИТЕЛЯ.** «Автор коммита» в ExoSync-REST = **владелец токена** (нет `exosync push --author`). Чтобы git-автор отражал, КТО попросил (Оля/Андрей): `push_vault(cfg, sender_id)` резолвит push-токен по config `push_token_by_chat_id` (chat_id→token-FILE); fallback на дефолт-токен, если не смаплен / файл отсутствует (graceful, пока PAT не выдан). ⛔ **Токен тестера обязан быть CLASSIC PAT (scope `repo`)** — classic-токен коллаборатора пушит в приватный репо owner'а; его fine-grained PAT — НЕ может (тот же 404, что п.4). Verify перед доверием: `GH_TOKEN=<pat> gh api user --jq .login` (owner) + `gh api repos/<owner>/<repo> --jq .permissions.push` (=true). **Live-verified:** create-task + push Олиным classic-PAT → git-автор `kalashnikova0410`; Андрей → `kitelev`.

**Empirical:** 2026-07-28, расширение @ao_shared_exo_bot до группы «Home sweet home» (форум-супергруппа Андрей+Оля+бот). ### ⛤ Addendum 2026-07-28 — HOMOICONIC time-based feature = inbound (LLM создаёт граф-ассет) + outbound checker-daemon (poll due → deliver → stamp fired-marker → push); recipient-property pinned обёрткой, НЕ LLM

Рецепт для **время-триггерной** фичи бота (напоминания, отложенные действия), гомоиконичной: сущность = граф-ассет, а не крон-запись в коде. Отработано на one-off напоминаниях (любой ассистент-бот: «напомни завтра в 15:00 …» → пуш в 15:00). Три reusable-приёма:

1. **⛤ Разделение inbound/outbound.** **Inbound** = LLM-персона создаёт граф-ассет через тот же валидированный `create`-путь (`create --class ems__Reminder --property ems__Reminder_at=<ISO-local> --property ems__Reminder_text=<текст>`); LLM НЕ доставляет — только декларирует намерение как данные. **Outbound** = отдельный **checker-демон** (launchd, poll ~30с): сканит ассеты класса, находит **due & не-fired** (fires-once via `_firedAt` absent + ISO `_at` <= now-local; **ISO-строки сортируются хронологически** → сравнение строк = due-check, без date-parse), доставляет (`_text` → `_chatId` через токен бота), **штампует `_firedAt`** (insert перед закрывающим fence — НИКОГДА не перевыстрелит), затем `exosync push` под push-lock бота. Один демон обслуживает все боты (реестр). Read-only кроме fired-штампа. Тот же fresh-read-per-tick принцип, что движок бота (нет кэша = нет staleness).
2. **⛤ `create` авто-quote'ит значения свойств с `:`/`$` → свободный текст = property, НЕ body.** Значит `ems__Reminder_text=позвонить X в 15:00` идёт `--property`, а НЕ `--body-file` — что важно, т.к. hardened-обёртка **запрещает `--body-file`** (anti-exfil, §Addendum 2026-07-27 prompt-injection). Убирает конфликт «текст с двоеточием требует body» ↔ «body запрещён».
3. **⛤ Security-sensitive recipient-property ПИНИТ обёртка, LLM не может задать.** Кому слать (`_chatId`) — не аргумент LLM: обёртка на `create --class ems__Reminder` **стрипает** любой caller-переданный `_chatId` и **инжектит** демон-пиненный (из env `REMIND_CHAT_ID` = chat текущего разговора, прокинутый движком в `ask_claude`). Prompt-injection не разошлёт напоминание в чужой чат. Персона инструктируется НЕ ставить `_chatId` (пинится).

⚠ **Честная тензия с device-local floor** ([[developer-config-symlinks-into-dotfiles]] нет; §Addendum 2026-07-27 auth/PII ниже): `ems__Reminder_chatId` **лежит в СИНКАЕМОМ графе** (уезжает в приватный remote бота) — п.3 того floor'а («синк = утечка») применяется. **Severity ниже**, чем durable `person__Person_telegramChatId`: (a) chat_id здесь = **транзитный self-chat** разговора (не cross-person identity-binding), (b) ассет **эфемерный** (fires-once), (c) **токен бота НЕ в графе** → голый chat_id-integer без токена низкоценен (нельзя написать в чат, зная лишь id). Обёртка пинит (частично закрывает «механически неэнфорсимо»). Но floor прав в принципе → **hardening-follow-up**: резолвить recipient device-local на fire-time (checker знает chat из config/маппинга), хранить в ассете только WHO-ref/ничего. ## §A3 — ⛤ 2026-07-27 — auth-секрет/PII (chat_id) в СИНКАЕМОМ графе неэнфорсим → device-local, а не «только приватный leaf»

Пункт 6 «Секрет НЕ в vault» расширяется на **user-facing auth/PII-биндинги** (chat_id ↔ person, credential ↔ identity). Соблазн ради Homoiconicity-цели «вся user-семантика в графе» — положить allowlist-биндинг (напр. `person__Person_telegramChatId`) свойством на person-ассете. **Это дефект по трём причинам** (council `/council full` + Migration + Security ревьюеры конвергентно, ≥2× независимо):

1. **Механически неэнфорсимо.** Нет SHACL-констрейнта на **placement свойства** (в каком ассетспейсе оно может появляться); `co-location-enforce` гейтит по `isDefinedBy`, не по присутствию свойства. Констрейнт «chat_id только в приватном leaf» = проза, не guard. `copy-from-neighbour` тихо реплицирует свойство в shared-person ([[artifact-class-neighbour-check]]), ExoSync пушит → PII уезжает.
2. **Shared-класс распределён по shared-ассетспейсам.** `person__Person` — SHARED-класс; его инстансы физически распределены (напр. person Андрея `0aa339bc` живёт в `exoas-shared-identities`, не в приватном leaf). Персоны, которым ты хочешь привязать chat_id — как раз те, что констрейнт запрещает → «только приватный leaf» **не может держаться**.
3. **Синк = утечка при первой ошибке.** ExoSync/git-history даже приватного leaf уходит в remote тестера; при компрометации токена/репо или неверном `isDefinedBy` — PII в public. Audit-метрика **детективна** (срабатывает post-push, PII уже в remote), не превентивна.

**Floor.** Auth/PII-биндинг (chat_id, credential↔identity) → **device-local map** (`{ person-UID → chat_id }` рядом с secrets, chmod 600), как admin-floor. В граф кладётся только **WHO** (`_authorizedUser → person`-refs = intent, PII-free, self-service). Движок резолвит WHO-persons → chat_id из локального binding. Если граф-placement всё же выбран (вижн-решение пользователя) — обязателен **превентивный** gate (pre-push hook / secret-scan pattern), не audit. ⛤ Смежное: **prompt-injection в write-capable headless-агенте** над untrusted free-text — Bash-allowlist сабкоманды (`olya-exo create --body-file <секрет>`) **обходит** Read-deny-list → exfil `~/.claude/.credentials.json`; обёртка обязана парсить args (запрет `--body-file`/`--vault`/mount-verbs), не blind-forward `$@`. Empirical: bot-onto-RFC 2026-07-27 — оба дефекта пойманы адверсарной панелью ДО формализации; chat_id переведён в device-local (Alt-B), prompt-injection поднят в BLOCKING-фикс. Cross-tie [[adversarial-panel-before-foundational-rfc]] (панель ловит placement-дефект до shipping), [[developer-config-symlinks-into-dotfiles]] (secret-в-tracked-config = утечка).

## §A4 — ⛤ 2026-07-29 — БОЛЬШОЙ vault → triple-cache: `index --force` post-pull + `query --use-cache` (env-gated per-vault, ~5× per query)

Assistant-бот над **большим** vault (vault-my ~120k триплов) страдает от того, что `exocortex-cli query` по дефолту (`useCache=false`) **пере-парсит весь граф на КАЖДЫЙ запрос** (~5.8с). Планирующий вопрос («план на завтра» = ~13 SPARQL) = ~223с → **таймаут** демона. Фикс (2-плечий, отгружен, замерен):

1. **B — triple-cache в движке (`poll_assistant.py`):** opt-in `ASSIST_BUILD_CACHE=1` → после `pull_vault()` один раз за ход `index --vault <V> --force` строит персистентный `triples.json`. Обёртка (`kitelev-exo`) добавляет `--use-cache` к `query` → загрузка из кэша (**1.16с vs 5.80с = 5.0×**). Сборка — **8.7с раз/ход** (амортизируется на N запросах). Итог: ~223с → ~30с.
2. **⛤ `--force` ОБЯЗАТЕЛЕН:** `CacheManager.isCacheValid` ключует валидность на mtime **КОРНЯ** vault, а он НЕ меняется при правке файлов под `assetspaces/**` → без `--force` кэш считается валидным и НЕ перестраивается (stale). Post-pull `--force` гарантирует свежесть.
3. **⛤ Env-gated per-vault (НЕ глобально в движке):** `ASSIST_BUILD_CACHE` в plist ТОЛЬКО у большого vault (kitelev). Мелкие боты (olya/shared) НЕ платят 8.7с build — их vault мал, дефолтный re-parse дёшев. Один env-параметризованный движок обслуживает оба класса без ветвления кода.
4. **Fresh-per-turn = нет staleness:** кэш строится post-pull КАЖДЫЙ ход → правка vault отражается на след. вопрос без рестарта. Caveat: read-after-write **в ТОМ ЖЕ ходу** (create → query) может промахнуть свою запись (кэш построен в начале хода) — для персонального ассистента редко (обычно read-to-answer / read-then-write), задокументировано в обёртке.
5. **Sibling — result-cache (отдельный слой):** дефолт-он result-cache (повторные ИДЕНТИЧНЫЕ запросы) — отдельная оптимизация; её key-bug (read-key≠write-key из-за prefix-injection) исправлен #3979 (v16.196.1), unbounded-рост — eviction+`cache clear` #3981 (v16.197.0). Триаж «медленный бот» → сначала triple-cache (B, главное), не result-cache.

**Empirical:** 2026-07-29. @KITELEV_EXOASSISTANT_BOT ускорен B+D (dotfiles `0f1c700`); замер vault-my: query 5.80с→1.16с (5.0×), build 8.7с/ход. #3979 (result-cache key) + #3981 (eviction+`cache clear`/`stats`) отгружены → CLI ботам 16.195→**16.197.0** (все 3 бота = единый глобальный бинарь). ## §A5 — ⛤ 2026-08-03 — ПРОИЗВОДНЫЙ артефакт из личных логов: единицей извлечения обязан быть ФИКСИРОВАННЫЙ СЛОВАРЬ, а не отрезок пользовательского текста

§Addendum 2026-07-27 (auth/PII) закрывает вопрос «что НЕ класть в граф». Соседний, менее
очевидный: что происходит, когда из личных логов (дневник, ADHD-чек-ины, диалоги ассистентов)
**производится** технический артефакт — сводка отказов, статистика жалоб, вход для другой петли.

Естественная реализация — «взять предложение, где встретились жалоба и упоминание инструмента,
и положить его в поле». Она **выносит личное**, когда оно стоит в том же предложении:

> «Диагноз подтвердился, начал таблетки — и кнопка в obsidian падает»

Формально граница соблюдена (взята «жалоба на инструмент»), фактически — нет. **Предложение
не является единицей**: пользователь не пишет техническое и личное в разных предложениях.

- ✅ **Floor: наружу идёт только то, что взято из ЗАКРЫТОГО СЛОВАРЯ.** Не отрезок текста, а
  совпавшие **токены** твоих же регулярок: `инструмент=<token> отказ=<token>`. Тогда у
  произвольного пользовательского текста **нет пути** в поле — это структурное свойство, а не
  качество фильтра. Сам текст остаётся за ссылкой (`evidence_ref`), которую человек открывает
  осознанно.
- ⛤ **Границы слова в словаре обязательны.** Без `\b` короткий токен матчится внутри чужого
  слова (`бот` в «сра**бот**ала»), и **личное сообщение проходит как жалоба на инструмент** —
  фильтр не просто пропускает лишнее, он неверно классифицирует.
- ⛔ **Флаг `sensitive` — метка, а не защита.** Если ни один потребитель его не читает, он
  документирует намерение, которое никто не исполняет. Считать его пометкой для человека и
  дополнять её тем, что реально энфорсится: файл-выход в режиме `600`, тело без прозы.
- ⚠ **Живой корпус не доказывает, что фильтр работает.** Проверять надо на **сконструированном**
  враждебном входе (медицинское / финансовое / третьи лица в одном предложении с жалобой).
  «На реальных данных ничего не утекло» — это про удачу выборки, а не про поведение фильтра.

**Empirical 2026-08-03** (DLP Ф2, адаптер бот-логов): первая реализация писала предложение
целиком; ревью воспроизвело утечку на сконструированных входах (диагноз, зарплата, имя партнёра).
Переведено на два токена из фиксированных словарей; отдельно вскрылось, что `бот` без `\b`
матчился в «сработала», то есть личное сообщение классифицировалось как жалоба. После правки
на живых данных: 4 sensitive-сигнала, все вида `инструмент=граф отказ=не нашёл` — прозы нет.

## §A7 — ⛤ 2026-07-29 — изоляция нужна и для бота над СОБСТВЕННЫМ живым vault пользователя (same-user concurrent-edit), не только multi-user; naming `vault-bot-<кто>`; cascade discovery-dependency

Addendum 2026-07-26 (§выше) вводит «отдельная vault-папка на бота» для **multi-USER** случая (Оля правит с телефона → бот-папка на маке Андрея, он её не трогает → чисто). Пропущенный случай: **бот над СОБСТВЕННЫМ живым vault пользователя** (личный ассистент Андрея над `vault-my`). Там **тот же пользователь правит vault параллельно** (Obsidian-Mac, EA-сессии) → shared working-tree → **та же контенция, что multi-user**, но внутри одного пользователя. Изоляция обязательна и здесь.

- **Почему (механизм):** после хода, изменившего граф, бот делает `push_vault` → `exosync push --vault <ASSIST_VAULT>`. `exosync push` толкает **ВЕСЬ pending-delta working-tree** (нет per-repo/per-file флага) → если бот работает на ЖИВОМ vault пользователя, его автономный push **публикует концертные СЫРЫЕ правки пользователя** в момент, который пользователь не выбирал. ⛤ Хуже: `_vault_fingerprint()` считает отпечаток ВСЕГО `<vault>/assetspaces/**/*.md` (file-count + newest mtime) → если пользователь правит vault ВО ВРЕМЯ хода бота, отпечаток меняется → бот пушит **даже на read-only ходе** (и пушит правку пользователя). Push-lock защищает только бот-vs-бот, НЕ бот-vs-пользователь.
- **Fix = каждый бот в СВОЕЙ `vault-bot-<кто>` папке** (naming-конвенция Андрея 2026-07-29): `vault-bot-kitelev` (личный), `vault-bot-kalashnikova` (Оля), `vault-bot-ao` (общий). Бот-папку трогает только бот → отпечаток меняется только на его записи → push отправляет только его правки. Сходимость с живым vault пользователя — **через общий remote** (бот пушит → remote → пользователь пуллит; и наоборот), НЕ через shared working-tree. Пользователь синкает свой живой vault своими путями (EA-сессии/iPhone/ручной exosync) — бот перестаёт быть его «побочным» синкером.
- **Рецепт:** для НОВОЙ изоляции существующего живого vault — `exosync-parity --vault <live>` (убедиться M2=∅, чтобы клон был чистый и первый push бота не толкнул pending) → `cp -a <live> <vault-bot-X>` (git-free vault, ~сек/десятки-МБ; ExoSync watermark копируется → первый pull no-op) → перенацелить `ASSIST_VAULT` + wrapper `VAULT=` (+ `VAULT_PUSH_LOCK`) → `cp` plist в `~/Library/LaunchAgents/` → `launchctl bootout … && bootstrap …` (env перечитывается только при reload, НЕ `kickstart`) → verify: `<wrapper> query "SELECT (COUNT(?s) AS ?n) …"` возвращает N триплов из новой папки. Для ПЕРЕИМЕНОВАНИЯ уже-изолированной папки — `mv` (сохраняет ExoSync state 1-в-1), не cp.
- **⛤ Cascade discovery-dependency (migration-pre-verify ОБЯЗАТЕЛЕН перед rename):** vault-путь бота захардкожен в НЕСКОЛЬКИХ подсистемах, не одной — (1) wrapper `<bot>-exo` `VAULT=`, (2) **engine-default `poll_assistant.py` `VAULT = os.environ.get("ASSIST_VAULT", …/vaults/<default>)`** (общий движок; kitelev/shared override через plist ASSIST_VAULT, olya полагается на default), (3) **sibling-боты, делящие ту же папку** (diary-capture `INBOX_VAULT` над той же `vault-kalashnikova-my`), (4) **reminder-checker registry** (`poll_reminders.py` per-bot vault+lock). ## §A8 — ⛤ 2026-07-29 — per-message dialog log в BORN-COLD assetspace: dedicated write-vault + DIRECT template-write (`create` блокирует dangling wikilinks); `_sender` cross-space = warning не violation; SHACL sh:class требует RANGE-класс смонтирован

Ключевое отличие: лог **рождается в холодном** AS, объём высок, hot-path-adjacent. Reusable-механика:

2. **⛤ `exocortex-cli create` БЛОКИРУЕТ dangling wikilink** («Wikilink [[uid]] — file not found in vault») — валидирует ВСЕ wikilink-свойства против смонтированного vault. Т.е. dangling person-ref ≠ SHACL-fail; dangling range-класс = SHACL-fail.

Диагностика — два запроса:
1. `SELECT ?l ?r WHERE { ?p exo:Asset_label ?l . FILTER(CONTAINS(?l,'<Property>')) OPTIONAL { ?p exo:Property_range ?r } }` → чего требует свойство;
2. `SELECT ?s WHERE { ?s exo:Instance_class ?c . FILTER(CONTAINS(STR(?c),'<RangeClass>')) }` → есть ли такие инстансы в ЭТОМ vault. Ноль → корень найден.

**Фикс (двухслойный; одного слоя мало):**

Так follow-up «глянуть логи 1-го числа» превращается в проверенный факт заранее.
3. **⛤ Строя sibling-vault рядом — наследуй СОШЕДШИЕСЯ watermark'и, не пере-пуллься.** `cp -a` shared-ассетспейсов + `.obsidian/plugins/exocortex/exosync-*.local.json` из уже сконвергированного vault ⇒ в новом vault `exosync sync` даёт shared-репо `pulled 0, pushed 0` и работает только со своим лог-репо. Порядок: сначала довести источник до `M2=∅`, ПОТОМ копировать (иначе унаследуешь stale watermark и начнёшь качать блобы). На 3 vault экономия ≈ 1400 REST-вызовов — прямая профилактика secondary rate-limit ([[exosync-bulk-push-secret-scan-and-rate-limit]]). ⛤ Копировать только shared-деревья + ExoSync-state; лог-AS не трогать, и в окно, когда демон ещё не писал (проверить по `botlog.log`) — иначе можно затереть свежий watermark лог-репо.
4. **⛤ No-churn write-smoke (усиливает harness-smoke из §Addendum 2026-07-27 п.5).** Чтобы доказать РЕАЛЬНЫЙ write-path, а не только резолюцию: вызвать боевой `log_turn` в **отдельном процессе** с env, снятым из `launchctl print` живого демона → процесс завершается **до** debounce-окна, а таймер пуша `daemon=True` ⇒ умирает с интерпретатором ⇒ **в remote не улетает ничего**. Затем проверить файлы (свой ns, свой анкер) и удалить. Отсутствие `push`-записей в `botlog.log` после проб = доказательство, что remote не тронут.
5. **Двухуровневый gate «логирование не сломано молча»:** (1) резолюция — проба движка в env из `launchctl print` (`_enabled(bot_uid)=True`, AS на диске, свой ns, анкер найден и НЕ создан заново); (2) реальный write per bot (п.4). Одного уровня мало: резолюция может пройти, а запись упасть, и наоборот. Это ровно тот failure-mode, ради которого написан [[exocortex-cold-archive-assetspace]] §Addendum 2026-07-30 — `_enabled()` гейтится существованием папки, поэтому неверный путь **молча** отключает логирование при живых ответах бота.
6. **Изоляция — формулировать точно.** Operative guarantee = **отсутствие пути**: `BOTLOG_VAULT` per bot, `AS_DIR` выводится из него, в vault бота физически нет папок лог-AS других ботов (проверять перечислением + SPARQL «сколько чужих ботов видно»). ⛔ НЕ писать «нет пути/токена», если токен общий: при owner-owned репо все демоны пушат owner-токеном (fine-grained PAT тестера в чужие owner-репо не пишет), и все демоны и так под одним OS-юзером ⇒ threat model = **баг/prompt-injection в одном боте**, не враждебный доступ. Per-token изоляция = вижн-решение (новые PAT / смена владельца репо), не техдолг фазы. Cross-tie [[verify-before-assert]] (не переоценивать гарантию).
7. **Аналитика — единственный легитимный читатель всех логов.** Скрипт, агрегирующий лог, обязан **циклиться по per-bot vault** (он запускается от владельца, не от демона). Хардкод единого vault после split возвращает **нули с exit 0** — молча.

## §A11 — ⛤ 2026-07-30 — запись ID ВНЕШНЕЙ системы в граф-лог: reorder «send-then-log» обязан сохранить ВСЕ ветки логирования; id внешней системы = unquoted-int + int-guard + STR-safe CQ

Продолжение born-cold-лога (§Addendum 2026-07-29). Как только лог-запись должна нести **идентификатор, который существует только ПОСЛЕ внешнего вызова** (Telegram `message_id` из результата `sendMessage`), запись обязана переехать **после** отправки — и это порождает ловушку, которую не поймает ни один тест.

1. **⛤ Позиция вызова логирования сама была покрытием.** До реорядка `log_turn(...)` стоял **ВЫШЕ** ветки `if answer is None:` (та шлёт «не смог обработать» и делает ранний `return`) ⇒ **провалившиеся ходы логировались как побочный эффект позиции**, а не по замыслу. Наивный перенос «после успешного send» **тихо прекращает логировать ошибочные ходы** — регрессия наблюдаемости: пользователь видит ответ, тесты зелёные, а в графе исчезает целый класс событий (именно тот, по которому потом диагностируют бота). **Floor:** перенося observability-вызов вниз по потоку, **перечисли ВСЕ ветки, которые раньше до него доходили**, и залогируй каждую **явно** (локальный `log_this_turn(...)` + вызов в каждой ветке), а не полагайся на новую позицию.
2. **`try/finally` сохраняет свойство «упавшая отправка всё равно логируется».** Раньше оно возникало само (лог шёл первым); после реорядка нужен `finally`, иначе исключение транспорта = потерянная запись. Отсутствие id в такой записи — уже сигнал «не доставлено» (не нужен отдельный флаг).
3. **Форма id: unquoted YAML int + обязательный int-guard.** Значение приходит из внешней системы и попадает во frontmatter **без кавычек** ⇒ любой non-integral мусор (`:`/newline) сломал бы YAML ([[yaml-frontmatter-colon-space-breaks-parse]]). Коэрсить `int(v)` и при неудаче **дропать строку**, а не инжектить. Bool отсекать отдельно (`isinstance(v, bool)` — в Python `int(True)==1`).
4. **CQ по такому id — только STR-safe.** Unquoted int эмитится `xsd:decimal` (не `xsd:integer`) ⇒ `FILTER(STR(?id) = "N")` матчит, bare-int (`?m p N`) даёт **0**. Проверено независимо в Phase 3 на реальном vault: STR-safe 1/1, bare-int 0/0.
5. **Расширение сигнатуры логгера — keyword-only с дефолтами** (`def log_turn(..., model=None, *, user_message_id=None, answer_message_id=None)`): позиционные вызовы не ломаются, best-effort-контракт «never raises into the caller» и `_enabled(bot_uid)`-гейт сохраняются.
6. **Reply-параметры — ПОВЕРХ существующей send-обёртки, не вместо неё.** `send()` уже прокидывает `message_thread_id` (форум-топики); новый `send_answer()` добавляет `reply_to_message_id` сверху ⇒ на одном исходящем присутствуют оба (проверено харнессом для группы). Плюс двойная защита от протухшего reply-таргета: `allow_sending_without_reply` + `except`-фолбэк на plain-send, чтобы устаревший таргет не стоил пользователю ответа.

- **Empirical:** 2026-07-30, child Phase 3 (RFC `f7e8d6cd` VL#6, task `91539237`), dotfiles `6ec6122`. Revert-verify через broken-COPY дерева ([[integration-test-revert-verify]] §Update 2026-07-30): наивный реорядок → error-ветка `logged_messages: []` (RED), фикс → user-сообщение записано (GREEN); happy-path идентичен в обоих ⇒ дискриминатор именно error-ветка. Production-shape запись в реальный log-vault из env живого джоба (`launchctl print`) + CQ3 round-trip + удаление smoke; SHACL 0-new; живой Telegram подтвердил применение reply ([[verify-before-assert]] §Addendum 2026-07-30).

## §A12 — ⛤ 2026-07-30 — ГРАФ как носитель памяти (reply-READ): кросс-ходовая связь обязательна, иначе up-walk не выходит за один ход; пустая выборка CLI ≠ пустой JSON; стаб LLM-функции обходит сборку промпта → ЛОЖНЫЙ RED

Замыкающая половина reply-цепочек (§Addendum 2026-07-30 выше — write-side). Демон резолвит входящий Telegram-реплай в свой cold-лог и вклеивает тексты ветки в промпт, а `claude --resume` уходит навсегда: два носителя памяти (граф + резюмируемая сессия) неизбежно разойдутся. Четыре не-очевидных вещи:

1. **⛤ Без кросс-ходовой связи многозвенная ветка НЕВОЗМОЖНА — и это невидимо, пока не проверишь на 3-м ходу.** Write-side пишет `inReplyTo` только ВНУТРИ хода (assistant → user того же хода), поэтому **каждое** user-сообщение остаётся корнем, и up-walk от любого ответа собирает ровно **один ход**. Двух-ходовой тест (вопрос → ответ → реплай) проходит и создаёт ложную уверенность. Лечится тем, что **user-сообщение, являющееся реплаем, само получает `inReplyTo` → ассет реплайнутого сообщения** — резолвер для этого появляется только на read-стороне, т.е. это работа read-фазы, а не write-фазы. **Floor:** тест ветки обязан иметь **≥3 хода** (реплай НА РЕПЛАЙ) — только он отличает «связь есть» от «связь есть лишь внутри хода».
2. **⛤ Пустая выборка `exocortex-cli query --format json` печатает пустоту в ДВУХ РАЗНЫХ ФОРМАХ, и выбирает форму result-кэш.** Парсер, ищущий JSON-массив в stdout (искать его ОБЯЗАТЕЛЬНО — впереди идут прогресс-баннеры, `json.loads(stdout)` падает всегда), обязан распознавать **обе**:

   | Путь | Что печатается |
   |---|---|
   | **свежий** запрос | `✅ Found 0 result(s)` + **`No results found.`** — JSON-массива нет вовсе |
   | **повторный** идентичный запрос (cache-hit) | `📦 (cached) …` + `✅ Found 0 result(s)` + **`[]`** — строки «No results found» нет |

   ⛔ **Прежняя формулировка этого пункта («печатает НЕ `[]`, а „No results found.“») верна ТОЛЬКО для свежего пути и ложна для кэш-хита** — исправлено 2026-08-03 изоляцией: два прогона одного запроса подряд дали разные формы; дискриминатор — именно result-кэш, а НЕ наличие TTY (проверено и это).

   ⛤ **Опаснее, чем разница форматов: бьёт по ПОВТОРЯЮЩИМСЯ прогонам.** Гейт, узнающий пустоту грепом по `No results found`, отработает **первый** раз (свежий путь) и будет молча брать неверную ветку на **каждом последующем** (кэш-хит) — то есть сломается ровно тогда, когда станет расписанием, и в режиме, за которым никто не смотрит. Наблюдалось 2026-08-03: интерактивный прогон еженедельного чекера дал `CLEAN`, первый же запуск под launchd — `VIOLATION`, при неизменных данных.

   **Floor:** считать строки **разбором массива**, а не грепом человекочитаемой строки: `[]`/`[…]` → длина; текст содержит `No results found` → 0; ни одно не распозналось → **не CLEAN, а «не смог определить»** (для гейта — отдельный терминальный исход, а не молчаливый успех).
3. **⛤ Стаб функции, ВНУТРИ которой живёт добавляемая фича, даёт ЛОЖНЫЙ RED.** Харнесс стабил `ask_claude` (казалось — «граница LLM»), но именно `ask_claude` собирает промпт из `branch_context` + вопроса; стаб забирал только `question` и обходил сборку ⇒ фиксированный движок выглядел сломанным. Правильная граница — **процесс**: подменить `CLAUDE_BIN` фейковым бинарём, который дампит `sys.argv` и печатает JSON нужной формы. Тогда `ask_claude` работает по-настоящему, а харнесс **бесплатно** получает доказательство по argv (напр. `--session-id` присутствует на каждом ходу, `--resume` — ни разу), которого грепом по исходнику не добыть. **Floor:** стабь ПРОЦЕСС/HTTP, а не питоновскую функцию, если фича живёт внутри неё. Sibling — [[test-fixture-realism]].
4. **Hard-link копия живого лог-vault как тест-субстрат** (`cp -al` живой → `/tmp`): настоящий TBox ⇒ настоящие IRI-формы (file-IRI субъекты/объекты, symbolic role-энумы), при этом `_write_file` идёт через tmp+`os.replace` и заменяет **ссылку в копии** — живой vault не мутирует (проверено: счётчик файлов до/после не изменился). ⛤ Копию **пересоздавать на каждый прогон**: иначе повторные запуски сами наплодят дубли `telegramMessageId` и упрутся в собственный ambiguity-guard.
5. **Двусмысленный внешний id → фолбэк, а не догадка.** Telegram `message_id` уникален лишь В ПРЕДЕЛАХ чата, а лог намеренно не хранит chat_id (device-local privacy floor, §Addendum 2026-07-27). У бота в нескольких чатах один id может встретиться дважды ⇒ >1 совпадения = **не выбирать «поновее»**, а падать в fresh с записью `ambiguous_tmid`: подмешать в ответ историю ЧУЖОГО чата хуже, чем потерять контекст.
6. **Побочный эффект always-fresh, который надо назвать вслух:** `--session-id` обязан быть неиспользованным uuid ⇒ каждый ход = свой `bot__Session`. Поле-ссылка на сессию и класс пишутся как раньше (аналитика цела), но метрика «уникальных сессий» теперь равна числу ходов, а лог растёт на +1 ассет за ход. Это смена СМЫСЛА метрики, не поломка — но молча оставлять её нельзя.

- **Empirical:** 2026-07-30, child Phase 4 (RFC `f7e8d6cd` VL#6, task `025d1435`), dotfiles `b145c22` + `76107c2`. Revert-verify по ДВУМ осям: снять вклейку → реплай-ходы теряют контекст (RED), снять кросс-ходовую связь → ветка из 4 сообщений схлопывается до 2 (RED); ход без реплая идентичен во всех трёх состояниях ⇒ он НЕ дискриминатор. Fallback-матрица 6/6 (`bad_id` / `disabled` ×2 / `query_failed` / `ambiguous_tmid` / `not_found`, где последний — сообщение ЧУЖОГО бота, т.е. фильтр по боту работает), 0 исключений. Read-only проба в env живых джобов (`launchctl print`): kitelev-бот резолвил РЕАЛЬНОЕ сообщение живого лога и собрал ветку; у ao/kalashnikova ещё нет ни одного telegram-id (свойство going-forward). SHACL 0-new (3 лог-vault + vault-exodev = baseline 589 warn), живой лог не тронут.

## §A13 — ⛤ 2026-07-30 — ПРОГРАММНАЯ правка plist: `plutil -lint` OK ≠ `plistlib`-parseable (`--` в XML-комментарии роняет Python)

Правка `EnvironmentVariables`/путей в plist через Python `plistlib` (естественный выбор для bulk-переконфигурации N демонов) имеет тихую мину: **двойной дефис `--` внутри XML-комментария** (`<!-- … --use-cache … -->`) **незаконен по спецификации XML**. При этом:

| Проверка | Вердикт на таком файле |
|---|---|
| `plutil -lint <plist>` | **OK** ✅ |
| `launchctl` загрузка job | **работает** ✅ |
| Python `plistlib.load()` | **`ExpatError`** ❌ |

Т.е. файл одновременно «валиден» для системных инструментов и непарсибелен для скрипта, который собрался его править.

- ⛔ **Не считать `plutil -lint` / «система его читает» доказательством**, что ТВОЙ парсер файл прочитает.
- **Floor:** перед bulk-правкой прогнать целевым парсером **КАЖДЫЙ** файл, а не первый попавшийся — падение на третьем из трёх оставляет систему в **наполовину применённом** состоянии (двое демонов переконфигурены, третий нет).
- **Обход:** точечная **текстовая** правка (`Edit`/sed по конкретной строке) вместо `plistlib.load()`→`dump()`. Бонус: сохраняет комментарии и форматирование живого конфига, которые перезапись из `plistlib` уничтожает.
- **Empirical:** 2026-07-30, оркестрация `8b5511fb` Phase 2. Оркестраторский pre-verify нашёл `--` в комментарии на стр. 29 `kitelev-assistant.poll.plist`; ребёнок планировал программную правку трёх plist → упал бы **именно на боте Андрея** (личный ассистент), уже переконфигурировав два других. Релей → ребёнок обошёл текстовой правкой, комментарии целы. Cost предотвращённого: наполовину применённая конфигурация live-демонов + вероятная потеря комментариев при «починке».

## §A14 — ⛤ 2026-07-31 — ВТОРОЙ подвид «бот просит открыть Claude Code»: sync ЖИВ, но Keychain-токен истёк ⇒ отказ ШТАТНЫЙ (не баг); repro с протухшим файлом ОПАСЕН (ротирует общий refresh-token); запрос пользователя в это окно ТЕРЯЕТСЯ

§Addendum 2026-07-29 (выше) описывает **первый** подвид: `sync_credentials()` отсутствовал/симлинк висел → `claude` → `Not logged in`. После его внедрения появился **второй**, внешне идентичный для пользователя («бот просит открыть Claude Code»), но с противоположным диагнозом: **всё работает как задумано**.

- **Механизм:** `sync_credentials()` возвращает **False**, когда Keychain-токен истекает раньше, чем может завершиться максимальный ход (`exp <= now + CLAUDE_TIMEOUT_SEC`). Вызывающий обязан **прервать ход, НЕ вызывая `claude`** — иначе `claude` сам рефрешит токен, **провернёт общий refresh-token** и может сломать интерактивную сессию-владельца Keychain. Т.е. отказ — это **защита**, а не сбой.
- ⛤ **Различитель в `conversations.jsonl` (решает диагноз за один взгляд):**

| Последние записи | Диагноз |
|---|---|
| `cred_expired` (+`expiresAt`) → `cred_stale_abort` | **штатный отказ** — токен протух; лечится ИНТЕРАКТИВНЫМ логином, код чинить не надо |
| `claude_error` + `result:"Not logged in"`, `wall_s ~1.5s` | подвид №1 — sync не отработал (dangling симлинк / нет файла) |
| `timeout` (== `ASSIST_TIMEOUT_SEC`) | ни то, ни другое → §Addendum 2026-07-30 (mount/промпт) |

- **Диагностика без запуска `claude` (безопасна):** сравнить **хеш** токена файла vs Keychain + остаток жизни (⛔ токен не печатать — только `sha256[:8]` и `expiresAt`). Три исхода: (а) файл старый, Keychain свежий ⇒ корень уже устранён, следующий ход подтянет сам; (б) Keychain тоже протух ⇒ нужен интерактивный логин, ботам помочь нечем; (в) файл = симлинк ⇒ подвид №1.
- ⛔ **НЕ делать repro `claude -p` из bot-config-dir с ПРОТУХШИМ файлом** — это ровно то, что предотвращает `cred_stale_abort`: `claude` рефрешит и ротирует общий refresh-token. Порядок обязателен: **сперва материализовать свежий Keychain-cred** (unlink симлинка → write → `chmod 600`), **потом** repro. Тогда токен живёт дольше таймаута и рефреша не будет.

- ⛔ **Цена окна: запрос пользователя, пришедший в момент протухания, ТЕРЯЕТСЯ безвозвратно** — движок не ставит его в очередь на повтор, отвечает отказом и забывает. Проверять `conversations.jsonl` на **последнее входящее до `cred_stale_abort`** и явно возвращать пользователю: «вот этот твой запрос не выполнен». Известный gap (кандидат на фикс: очередь отложенных ходов ИЛИ проактивный монитор, предупреждающий за ~40 мин ДО истечения, пока пользователь ещё за маком).
- ⛤ **Сопутствующая находка — stale-путь в allow-list после изоляции vault.** `~/.<bot>-claude/settings.json` разрешает `Read/Grep/Glob(/Users/kitelev/vaults/vault-my/**)`, тогда как рабочий vault бота после §Addendum 2026-07-29 (изоляция) — `vault-bot-<кто>`. Симптом мягкий и легко списывается на «ограничения»: бот отвечает «файл в vault'е мне недоступен напрямую, но все данные из графа у меня есть» — SPARQL через wrapper работает, прямое чтение файлов нет. **Floor:** переименовывая/изолируя vault бота, включай `~/.<bot>-claude/settings.json` в тот же cascade-grep, что wrapper/engine-default/plist ([[migration-pre-verify-use-case]]).

Сообщение бота «оба инструмента для веба заблокированы» — корректный отчёт, не поломка. Расширять surface — осознанное решение владельца, не «починка».

## §A15 — ⛔ 2026-08-03 — ОДИН движок = N job'ов с ОДИНАКОВОЙ командной строкой: «launchd его не знает» НЕ доказывает сироту; дискриминатор — env процесса

Прямое следствие того, ради чего вся эта архитектура и строилась (§Принцип: один env-параметризованный движок на всех): в `ps` несколько демонов выглядят **байт-в-байт одинаково** — различает их только окружение. Отсюда диагностическая ловушка, дорогая именно потому, что выглядит как аккуратная проверка.

**Ложная цепочка (я прошёл её целиком):** вижу два процесса `poll_inbox.py` → спрашиваю `launchctl print gui/$UID/com.kitelev.inbox-diary.poll` → он называет ОДИН pid → второй, значит, «осиротел» → у второго вдобавок `INBOX_VAULT=vault-bot-kalashnikova`, что читается как «старое значение до изоляции» → диагноз «дубль со stale-путём» → kill.

⛔ **Каждое звено верно, вывод ложен.** Второй процесс принадлежал **другому job'у** — `com.kitelev.olya-capture.poll`, и его vault был не «старым», а **правильным для другого пользователя**. Я спрашивал про job A и делал вывод обо всех процессах скрипта.

- ⛤ **`launchctl print <job>` отвечает только за СВОЙ job.** «Этот pid мне неизвестен» ≠ «pid ничей». При общем движке job'ов столько, сколько ботов, и половина живёт в чужих папках (`~/.olya-bots/*`), которые не приходят в голову, когда чинишь свой.
- ⛤ **`ppid=1` — НЕ признак сироты у launchd-демонов.** launchd и есть pid 1: у **всех** его job'ов родитель первый. Признак, который я счёл уликой, на самом деле общий для здоровых и мёртвых.
- ✅ **Дискриминатор — окружение процесса, а не имя скрипта и не «кого знает один job»:** `ps eww -p <pid> | tr ' ' '
' | grep -E '^(BASE_DIR|.*_VAULT|.*BASE_DIR)='`. Разные `BASE_DIR` = разные боты, и это видно за одну команду.
- ✅ **Полный перебор владельцев дешевле догадки:** `launchctl list | grep com.kitelev` → `launchctl print` каждого кандидата, пока pid не найдётся. Не нашёлся ни у одного — только тогда сирота.
- ⚠ **KeepAlive спасает, но не оправдывает.** Убитый бот поднялся за ~2 с с тем же `offset` (0 потерянных сообщений). Это свойство конфигурации, а не моей осторожности: у job'а без KeepAlive та же ошибка означала бы молчащего бота до ручного вмешательства.

**Симптом-tell, отличающий настоящий дубль от соседа:** у настоящего дубля **совпадает `BASE_DIR`** (два поллера одного бота крадут друг у друга `getUpdates` — §Addendum 2026-07-26 п.1). Разные `BASE_DIR` = разные боты на общем движке, всё в порядке.

**Empirical 2026-08-03:** проверка голосового ввода → обнаружены 8 python-демонов, среди них два `poll_inbox.py`. Признал pid 618 осиротевшим дублем дневника и снял его; он оказался живым Олиным ботом-захватом (`~/.olya-bots/capture`, `vault-bot-kalashnikova`). launchd перезапустил его за 2 с, offset сохранён, сообщения не потеряны. Cost: обрыв чужого бота на 2 с + разбор. Тот же класс, что [[verify-before-assert]] §«проверка была, но проверяла не то»: признак («job A не знает pid») не покрывал гипотезу («pid ничей»).

## §A16 — ⛤ 2026-08-03 — тяжёлая МОДЕЛЬ в движке масштабируется ЧИСЛОМ БОТОВ: выносить в общий сервис, но как ОПТИМИЗАЦИЮ с фолбэком, а не как зависимость

§Принцип строит движок так, что боты делят **код**. Но всё, что движок грузит в **память процесса**, делится ровно наоборот — оно копируется на каждого бота. Пока ботов было двое, это не замечалось; на седьмом стало доминирующей статьёй расхода.

- **Замер (2026-08-03):** `faster-whisper small int8` = **801 МБ на процесс** поверх 17-39 МБ холостого следа, и это **синглтон, который никогда не освобождается** — держится до перезапуска демона. Семь ботов, получивших по одному голосовому, = **~5.7 ГБ** резидентно.
- ⛤ **Tell, что пора выносить:** объект, который (а) грузится лениво, (б) живёт до конца процесса, (в) на порядок больше самого процесса. Три признака вместе — и стоимость растёт линейно по числу ботов, а не по нагрузке.
- ✅ **Выносить в отдельный демон-сервис, но через два решения, каждое под свой риск:**
  1. **Сервис принимает ПУТЬ К ФАЙЛУ, не токен и не file_id.** Каждый бот качает своё своим токеном; через границу идёт только путь. Иначе N токенов собираются в одном долгоживущем процессе — ровно то, чего избегает §Addendum 2026-07-27 (auth/PII).
  2. **Unix-сокет 0600, не TCP-порт.** Боты обрабатывают недоверенный текст из Telegram; лишний слушающий порт — расширение поверхности без выгоды, а права на файл сокета энфорсит ОС.
- ⛔ **Сервис обязан быть ОПТИМИЗАЦИЕЙ, а не зависимостью.** Недоступен → бот делает работу сам, как раньше. Недоступный сервис должен стоить лишней памяти, никогда — потерянного сообщения пользователя.
- ⛤ **Фолбэк только на ОТКАЗ СВЯЗИ.** Сервису, который ответил содержательной ошибкой («пустая транскрипция»), — верить: повтор локально сожжёт 800 МБ ради того же ответа. Это разделение обязано быть в коде явно (`reachable` отдельно от `err`), иначе фолбэк срабатывает на штатных отказах.
- **Revert-verify — по дискриминатору «загрузилась ли модель в процесс бота»**, а не по «пришёл ли текст»: текст приходит в обоих состояниях. Сервис жив → модель НЕ в боте; сервис остановлен → модель в боте. Флип этого признака доказывает и экономию, и что фолбэк не мёртвый код.
- ⚠ **Новый сервис сам попадает в класс, за которым следит монитор памяти** ([[process-memory-monitoring-metric]]): он долгоживущий и держит большую модель. Добавлять его в фильтр в том же заходе — иначе повторяешь ровно ту ошибку, которую этим выносом и лечишь.

**Empirical 2026-08-03:** `voice-service` (unix-сокет, ленивая загрузка) заменил семь копий модели одной. Замер после: сервис 813 МБ, боты 15-17 МБ. Живое голосовое из Telegram: транскрипция через сервис (`ok chars=17 transcribe=2.0s`), бот остался 38 МБ, ответ с записью в граф за 47 с. Второй запрос — 2.9 с (модель держится).

## §A17 — ⛔ 2026-08-03 — инструкция персоны без КОНКРЕТНОГО запроса даёт ложное «нет» и порождает дубли

Персона может содержать правильное правило и всё равно не работать, если правило не говорит **чем именно** проверять. «Перед созданием по возможности проверь, нет ли похожего» — это намерение, а не процедура: бот выполняет какой-то поиск, не находит, и честно отвечает «нет».

- ⛔ **Цена ложного «нет» для человека с СДВГ — не косметическая.** Он просит завести то, что уже заводил и забыл; молча созданный дубль превращает список задач в свалку, которую разгребает он же. Бот, плодящий дубли, работает **против** того, ради чего создан.
- ✅ **Floor для персоны:** (1) dedup — обязательный шаг, не «по возможности»; (2) задан **конкретный запрос** (поиск по `exo__Asset_label` через SPARQL, одно узнаваемое слово в нижнем регистре); (3) прямой запрет отвечать «нет нигде» шире проверенного — искал ссылку, скажи «ссылки нет»; (4) нашёл похожее — **показать** (название + статус) и спросить, а не создавать молча.
- ⛤ **Проверять фикс персоны живьём обязательно** — это промпт, а не гейт. Дёшево и без Telegram: вызвать `claude` тем же способом, что движок (`--append-system-prompt-file <персона>`, тот же `CLAUDE_CONFIG_DIR`, тот же `PATH` с обёрткой, тот же `cwd`) и задать провоцирующий вопрос. Упражняется всё, кроме транспорта.
- ⚠ Персона передаётся флагом `--append-system-prompt-file` и читается при **каждом** вызове ⇒ перезапуск демонов после правки НЕ нужен.

## §A18 — ⛔ 2026-08-03 — у бота ДВА источника инструкций (персона + его память); сверка allow-list по одному оставляет второй в противоречии, и отказ выглядит как «бот сломался»

Сужая allow-list обёртки, естественно свериться с **персоной**: она в репозитории, её легко грепнуть, и ревьюер её прочитает. Но LLM-ассистент получает инструкции из **двух** мест, и второе — `~/.<bot>-claude/projects/*/memory/*.md` — живёт вне dotfiles, не попадает ни в один ревью и **переживает любую правку обёртки**.

- ⛔ **Противоречие не даёт fail-fast.** Обёртка отвечает `not permitted (security allow-list)` — это отказ **инструмента**, а не сигнал «путь закрыт навсегда». Бот не знает, что запрет постоянный, и начинает искать обход: пробует `--help` (тоже в deny), читает соседние ассеты, реверс-инженерит свойства через SPARQL. Ход упирается в `ASSIST_TIMEOUT_SEC`, и пользователь получает «не смог обработать» — при том, что работа могла быть выполнена.
- ⛤ **Стоимость асимметрична:** цена сужения списка платится один раз, цена противоречия — **на каждом** запросе этого класса, и выглядит она как деградация бота, а не как последствие правки политики.
- ✅ **Floor при любом сужении allow-list:** грепнуть **оба** источника, не только персоны.
  ```bash
  grep -rl '<команда>' ~/dotfiles/scripts/*/persona.md \
                       ~/.*-claude/projects/*/memory/*.md 2>/dev/null
  ```
  Совпадение в памяти ⇒ либо оставить команду разрешённой, либо **в том же заходе** переписать память на разрешённый путь. ⛔ Оставлять расхождение «память учит запрещённому» нельзя: оно не самоисправляется.
- ⚠ **Память переживает и обратную правку.** Сняв ограничение, проверь, не осталась ли в памяти инструкция, написанная как обход — она будет применяться и после того, как канонический путь снова доступен.

## §A19 — ⛤ 2026-08-03 — снимая контроль, раздели ЗАМКИ и ФУНКЦИОНАЛЬНЫЕ ПИНЫ: они лежат в одном блоке, а стоимость их потери несопоставима

Директива «снять все ограничения» звучит однородно, но в обёртке рядом живут два разных класса пинов, и различает их **последствие удаления**, а не форма кода:

| | что делает | цена потери |
|---|---|---|
| **Замок** | запрещает caller-у то, что он не должен мочь (`--body-file`, чужой `--vault`, произвольный якорь) | возвращается вектор атаки |
| **Функциональный пин** | дописывает то, без чего работает **хуже** (`--vault` назначения, `--created-by`, `--use-cache`, дефолтный якорь) | **тихая деградация уже отгруженной функциональности** |

- ⛔ **Buldozer-снятие ломает второе вместе с первым, и это не замечается**: у меня blind forward отключил маршрутизацию `ems__Bug` в `$product-kitelev` — баги от бота стали падать в `01 Inbox/`, невидимые петле разработки (ради чего маршрутизацию и делали), а обычные ассеты потеряли co-location. Ни один тест этого не показывал: тесты проверяли **замки**.
- ✅ **Floor: перечислить, что блок делает, ДО его обхода**, и по каждому пункту спросить «это запрет или дополнение?». Дополнения перенести выше `exec` явным ветвлением; запреты — снимать, раз так решено.
- ⛤ **Компромисс, сохраняющий обе цели, — «дефолт, а не пин»:** подставлять значение, **когда caller промолчал**, и уступать, когда он его задал. Ограничением это уже не является (caller всесилен), а функциональность сохраняется. Так же удобно откатывается: одно ветвление.
- ⚠ **`--created-by` принимает не всякая субкоманда** — безусловное дописывание роняет `apply` с `unknown option`. Функциональные пины навешивать **по субкоманде**, а не глобально.
- ✅ **Код замков не удалять, а обходить ранним `exec`**: откат = снятие одного блока, и диагностика будущих сессий видит, что именно было отключено.
- **Cost 2026-08-03:** дефект найден не тестом, а вопросом «а куда теперь поедет баг?» — то есть случайно. Тест зафиксирован уже после (см. ниже).

### ⛔ Recurrence 2026-08-07 — ВТОРОЙ пин, потерянный ТЕМ ЖЕ `exec`, пережил написание этого правила: floor «перечислить» исполнили на ОДНОМ найденном пункте, а не как перечисление

Секция выше написана сессией 2026-08-03 по горячим следам потерянного пина (маршрутизация `ems__Bug`). Через 4 дня выяснилось, что **тот же самый `exec` унёс и второй** — `ems__Reminder_chatId` в `kitelev-exo`: ранняя ветка `create` несла anchor-дефолт, `--vault` и `--created-by`, но не инъекцию получателя, а её `exec` сделал живой блок ниже недостижимым. Напоминания создавались **без адресата**, демон молча пропускал, фича была мертва всё это время.

⛤ **Правило не забыли — его исполнили не как перечисление.** Floor гласит «перечислить, что блок делает, ДО его обхода», и автор честно закрыл **тот пункт, который заметил**. Оставшиеся не были ни проверены, ни опровергнуты: enumeration по памяти отвечает на «что я помню», а не на «что там есть», и разницу между этими вопросами не видно изнутри.

- ✅ **Floor становится МЕХАНИЧЕСКИМ: перечисление = ДИФФ argv двух путей, а не список из головы.** Прогнать `--dry-run` через обход и через обойдённый блок, сравнить итоговый argv — расхождение и **есть** список потерянных дополнений, целиком и без пропусков. Стоит два вызова; ровно этим репродуцировался дефект (с `REMIND_CHAT_ID` и без него вывод оказался **байт-идентичным**).
- ⚠ **Симптом-tell при написании такого правила:** ты формулируешь класс по **одному** экземпляру и переходишь к тексту. Класс, найденный в одном месте, обязан быть **померен** в этом же файле, прежде чем стать правилом, — иначе правило описывает дефект, который рядом продолжает жить.
- ⛔ **Цена несимметрична и потому невидима:** потеря замка ломает **тест** (заметно), потеря пина ломает **пользователя**. Здесь: 4 дня мёртвых напоминаний; нашёл не тест и не ревью, а Андрей — «пару раз просил напомнить, он не сделал». Диагностика вскрыла **третье** застрявшее напоминание сутками раньше, о пропаже которого не знал никто.
- ⛤ **Однократная проверка радиуса дешевле повторной диагностики:** «у остальных четырёх обёрток ранней ветки нет» устанавливается чтением четырёх файлов и снимает вопрос навсегда; без неё каждый следующий инцидент начинается с нуля.

## §A20 — ⛤ 2026-08-03 — тест, из которого исключили обёртку, обязан ПРОВЕРЯТЬ ТО, ЧТО ОСТАЛОСЬ, иначе исключение делает его вечнозелёным

Сняв замки у одной из N обёрток, её приходится исключить из общего GREEN-цикла — иначе набор красный навсегда и перестаёт быть гейтом. Но простое исключение создаёт **слепое пятно**: обёртка больше не проверяется ничем.

- ✅ **Floor:** исключение сопровождается **отдельной секцией**, фиксирующей фактическое состояние: (а) что уцелело как гарантия (у меня — пин `--vault`), (б) позитивный контроль самого снятия (ранее запрещённая команда **доходит** до CLI). Тогда откат директивы тоже покраснеет — а это ровно то, что нужно знать.
- ⛤ **Утверждение, ставшее ложным, ПЕРЕВОРАЧИВАЙ, а не удаляй.** Проверка «caller не может переопределить назначение» после снятия пина неверна — но её противоположность («воля caller уважается») истинна и ценна. Удаление уносит покрытие; переворот сохраняет.
- ⛔ **Дискриминатор обязан различать ТРИ исхода, а не два.** Наивная проверка «есть ли preview» краснеет и когда пин потерян, и когда замки вернули — с одним и тем же текстом, то есть дезинформирует. Нужно: упоминание подставного значения ⇒ пин потерян; `not permitted` ⇒ откат директивы; иначе ⇒ норма.
- ✅ **Флип проверять на КОПИИ обёртки**, а не правкой живой: скопировать, вырезать блок `exec`, подменить путь в копии теста. Ноль риска для работающего бота.
- **Empirical 2026-08-03:** три оси — живое состояние `123 PASS / 0 FAIL`; замки возвращены в копии → 3 FAIL с корректными текстами; blind forward в копии **чужой** обёртки → 26 FAIL (доказывает, что исключение одной не ослабило гейт для остальных).

## §A21 — ⛔ 2026-08-03 — ТРЕТИЙ подвид «бот не отвечает»: ДИАГНОСТ ЛОМАЕТ БОТА САМИМ ФАКТОМ ПРОВЕРКИ — `claude` в песочнице БЕЗ файла cred создаёт ПУСТУЮ Keychain-запись, и она перекрывает файл навсегда

Два предыдущих подвида (§2026-07-29 dangling симлинк, §2026-07-31 протухший Keychain-токен) — про состояние, возникшее **само**. Третий возникает **от проверки**: чем добросовестнее воспроизводишь путь демона, тем вернее ломаешь бота.

**Механизм (установлен эмпирически):**
1. `claude` с заданным `CLAUDE_CONFIG_DIR` держит cred **в СВОЕЙ записи Keychain**, имя = `Claude Code-credentials-<sha256(config_dir)[:8]>`. Проверено: `sha256("/Users/kitelev/.kitelev-claude")[:8]` = `33a88821`, и такая запись существует. На машине их **161** — по одной на каждую когда-либо запускавшуюся песочницу.
2. Запуск в песочнице, где **нет** `.credentials.json`, оставляет запись с **пустыми** токенами (`accessToken`/`refreshToken` длины **0**, `expiresAt: 0`).
3. Дальше эта запись **имеет приоритет над файлом**. `sync_credentials()` продолжает исправно писать валидный файл каждый ход — и он больше **ни на что не влияет**. Бот отвечает `Failed to authenticate: OAuth session expired and could not be refreshed` **каждому**, бесконечно.

⛔ **Ловушка в самой диагностике.** §2026-07-29 предписывает «воспроизвести ТОЧНЫЙ путь демона» — верно для подвидов 1-2. Но если файла cred в песочнице нет (штатная ситуация: демон создаёт его перед ходом), первый же такой repro **и есть причина поломки**.
- ✅ **Floor: проверять бота ЧЕРЕЗ БОТА** — написать ему в Telegram и ждать `qa` в его `conversations.jsonl`. Живое сообщение упражняет ВЕСЬ путь (включая `sync_credentials`) и ничего не портит.
- ✅ Нужен именно прямой repro — **сперва** `[ -s <dir>/.credentials.json ]`; нет файла → материализовать из Keychain, как делает движок, и только потом запускать.

⛤ **Ложный след, снимающий с тебя подозрение.** `.claude.json` песочницы при этом **не меняется**: diff до/после даёт только `cachedGrowthBookFeatures` + его timestamp. Проверка «я не трогал его конфиг» возвращает честное «не трогал» и читается как «не я». Меняется артефакт **в Keychain**, куда никто не смотрит — ровно [[verify-before-assert]] §«проверка была, но проверяла не то».

**Диагностика (один шаг):**
```bash
D=/Users/kitelev/.kitelev-claude
S="Claude Code-credentials-$(python3 -c "import hashlib;print(hashlib.sha256(b'$D').hexdigest()[:8])")"
security find-generic-password -s "$S" -w | python3 -c "
import sys,json; o=json.load(sys.stdin).get('claudeAiOauth',{})
print('accessToken len', len(o.get('accessToken') or ''), '| expiresAt', o.get('expiresAt'))"
# len 0 / expiresAt 0 ⇒ запись-пустышка, она и есть причина
```
⛤ **Дискриминатор «моя ли это работа» — дата создания записи:** `security find-generic-password -s "$S" | grep cdat`. Время в **UTC** — сверять с локальным через +5, иначе [[verify-before-assert]] §Addendum 2026-08-02 (две шкалы) даст фантомный разрыв.

**Починка — УДАЛИТЬ запись, а не чинить:** `security delete-generic-password -s "$S"` → `claude` падает обратно на файл, то есть возвращается к задуманной схеме. ⛔ Не записывать в неё валидный токен: это размножает общий refresh-token по песочницам, а движок специально гейтит рефреш (§2026-07-31), чтобы бот не ротировал токен основной сессии.

**Empirical 2026-08-03:** проверяя новую персону, вызвал `claude -p` в `~/.kitelev-claude`, где файла cred не было. Запись `…-33a88821` создалась в `16:31:30Z` (= 21:31 Алматы) с пустыми токенами. Бот молча отказывал **всем** — включая живой запрос Андрея «Начал курить плум» в 22:18, написанный им самим и не связанный с проверкой. Удаление записи вернуло бота за один ход (`qa` 22:22, корректный ответ по графу). Цена: ~50 мин неработающего личного ассистента + один неверный промежуточный вывод «сломал не я».

## §A22 — ⛔ 2026-08-04 — правка ПЕРСОНЫ, добавляющая многошаговую ветку: без ЯВНОГО перехода бот идёт коротким путём, а без ЗАПАСА ВРЕМЕНИ обрывается на середине и оставляет полуфабрикат в ОБЩЕМ пространстве

§Addendum 2026-08-03 («инструкция персоны без конкретного запроса») — про **неполноту** инструкции. Здесь две другие оси, и обе проявляются, только когда инструкция описывает **длинную ветку** (достроить недостающую структуру, провести миграцию, собрать составной ассет).

**1. ⛤ Раздел с готовой командой «завершающего» действия ПЕРЕХВАТЫВАЕТ поток, если к альтернативной ветке нет явного перехода.** Персона обычно устроена как «шаг 1 — найди · шаг 2 — уточни · шаг 3 — создай (готовая команда)». Ветка «а если не нашёл — сперва построй недостающее» живёт **отдельной секцией ниже**. Бот доходит до шага 3, видит исполнимую команду и **адаптирует её** (подставив общий класс вместо конкретного), а не уходит в секцию, на которую ничто не ссылается.

- ⚠ **Симптом обманчив: бот отвечает УСПЕХОМ и создаёт ассет.** Ответ звучит как выполнение («начал сессию X»), но создано не то — общий класс вместо конкретного, без предметных полей. Ни ошибки, ни отказа; дефект виден только сверкой созданного класса с ожидаемым.
- ✅ **Floor:** в шаге, где ветка расходится, ставить **явный переход по имени раздела** («прототипа нет → сперва целиком выполни раздел X, вернись сюда только с готовым прототипом») **плюс запрет** на суррогат («⛔ никогда не создавай общим классом — он не несёт предмета занятия»). Одного перехода мало: без запрета короткий путь остаётся допустимым.
- ⛤ Родственно [[skill-discipline-under-pressure]] §Addendum 2026-08-02, но механизм ДРУГОЙ: там инструкция проигрывает **конкурирующему громкому правилу**, здесь конкурента нет — есть **доступный короткий путь и отсутствие моста** к длинному.

**2. ⛔ Фикс инструкции БЕЗ проверки бюджета времени = регрессия ХУЖЕ исходного состояния.** Длинная ветка стоит 8-10 обращений к графу подряд (каждое ~6-7 с только на загрузку) плюс reasoning. Если `ASSIST_TIMEOUT_SEC` рассчитан на обычный вопрос, ход обрывается **посередине**: бот успевает создать первые сущности и умолкает.

- ⛔ **Это хуже, чем до правки.** До неё бот делал неполно, но **целостно** и отвечал; после — оставляет **полуфабрикат** (класс без документации и прототипа), причём демон успевает его **запушить в общее пространство** между твоими прогонами. То есть улучшение инструкции без запаса ресурса ухудшает систему.
- ✅ **Floor:** вводя в персону ветку длиннее ~3 шагов — **замерить прогоном и поднять лимит В ТОЙ ЖЕ правке**. Замер честный: сколько шагов из N успело пройти до обрыва. ⛔ Не оставлять «пока хватит, потом посмотрим»: между правкой и «потом» живой пользователь получает мусор в графе.
- ⚠ **Прежняя формулировка «поднимать до 300 — но это паллиатив» (§Диагностика, 2026-07-30) верна для ЗАЦИКЛИВАНИЯ и НЕВЕРНА для длинной ветки.** Различитель: зациклился — в графе **ничего не создано**; не уложился — создана **часть цепочки** в правильном порядке. Во втором случае лимит и есть корень, а не паллиатив.

**3. ⛤ env харнесса снимать ПРОГРАММНО целиком, а не переносить руками** (нарушение §Addendum 2026-07-27 п.5, требующего «env из `launchctl print` живого джоба»). Выборочный перенос «нужных» переменных теряет ровно те, о которых не думаешь, — и проверка выносит **ложный вердикт о боте**:

```python
_dump = subprocess.run(["launchctl","print",f"gui/{os.getuid()}/<job>"],
                       capture_output=True, text=True).stdout
_env = dict(re.findall(r"^\s*(ASSIST_\w+|CLAUDE_\w+)\s*=>\s*(.*)$", _dump, re.M))
if not _env: sys.exit("не снял env живого джоба — прогон был бы не тем")
os.environ.update({k: v.strip() for k, v in _env.items()})
```

- ⛤ **Tell:** харнесс показал отказ, а живой бот на похожем запросе отвечает. Прежде чем чинить бота — **распечатай env, с которым шёл прогон**, и сверь с `launchctl print`. Отказ проверки чаще дефект проверки, чем предмета ([[verify-before-assert]] §«проверка была, но проверяла не то»).

**Empirical 2026-08-04** (обучение личного ассистента достраивать новый вид занятия): правка персоны накануне добавила ветку «занятие новое — дострой сам». Прогон на заведомо новом занятии дал три исхода подряд. (а) Выборочный env потерял `ASSIST_TIMEOUT_SEC=300` (движок взял дефолт 180) → **ложный отказ**, выглядевший дефектом бота. (б) С верным env бот ответил успехом, но создал **голую `ems__Session`** — раздела достраивания не достиг. (в) После добавления явного перехода бот пошёл верно и **оборвался на 2 шагах из 5**, оставив класс без документации в `exoas-public`, который демон уже запушил на remote. Итог после лимита 900 с: концепт → класс → документация → прототип → сессия нужного класса, всё за один ход. Cost: 3 лишних прогона + уборка полуфабриката с диска и с сервера.
